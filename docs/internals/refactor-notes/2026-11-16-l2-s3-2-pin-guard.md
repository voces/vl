# L2 S3.2: the pin guard, 2026-11-16

The third step of the S3 plan (`2026-11-16-l2-s3-plan.md`), marked **identical**, stacked on S3.1
(#8571). The design (§10, M3) does not rely on `relate` never pinning a hole. Instead, while the
solver asks a fit question, a hole write must show up loudly, and the full corpus runs under that
check. This PR builds the check and runs the corpus.

## The guard

- **State.** `compiler/check_types.vl` holds it, beside the writers `holeSolve` and `holeLink`. It
  is off unless a host arms it with `pinGuardArm(on, control)`, so an ordinary compile reads one
  boolean per write and changes nothing.
- **What it counts.** Armed, it counts each write made while `ifaceSolveAt` (S3.1) is open and a
  delivery question (`assignableExpr`, and `fitsExpr` through it) is open inside it. The key is the
  writer and the delivery's node.
- **The control.** `control` 1 counts every write, labelled by whether a solve and a delivery
  question were open. The census needs a control that is known to fire, because a guard that
  counts nothing proves nothing.
- **Instrument and test.** `scripts/pin-guard-census.ts` runs the guard over a corpus.
  `tests/vl_pin_guard_test.ts` keeps it from going blind: the control fires, a disarmed compile
  records nothing, and a solve that writes holes writes none inside a delivery question.
- **Not covered.** Bare `assignable` calls are not covered, because wrapping that hot function
  would cost every compile. The delivery relation M3 measured is `assignableExpr`.

## The census

Run over `tests/fixtures`, `tests/cases`, `distilled/cells` and `distilled/named` (20,601 programs),
with the control on:

| writer | where | delivery question | writes | program rows |
|---|---|---|---:|---:|
| `holeSolve` | outside a solve | no | 41,301 | 5,748 |
| `holeLink` | outside a solve | no | 292 | 72 |
| `holeSolve` | inside a solve | no | 13 | 4 |
| any | inside a solve | **yes** | **0** | **0** |

- **The solver's delivery questions pin nothing.** That is the property S3.3 to S3.5 build on.
- **13 writes happen inside a solve but outside any delivery question**, in three programs:
  `functions/hole-callback-empty-list-per-instance.vl`, `functions/hole-param-literal-per-caller.vl`
  and `functions/hole-param-lambda-open-map-result-pinned-by-callee.vl`. These are the validators'
  own pins, an empty list built at the type the callee reads it as. The design keeps these as the
  solver's writes ("pins remain, as the solver's writes", §7).
- **Almost every hole write is made outside the solver**, by the body check and the call's earlier
  steps. That matches M3's measurement: holes are pinned outside the delivery relation.
