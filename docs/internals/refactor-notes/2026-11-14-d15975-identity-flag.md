# D15975: identity rides an equality node (`BinExpr.binIdent`), 2026-11-14

Lane E. A representation change ahead of the `==`-on-functions refusal (the orchestrator split
it out so it can be measured alone). It comes after step 2 (`2026-11-14-d15975-identity-emit.md`).
No program changes meaning; shapes `===` refused under step 2 now run.

## Why

Step 2 lowered `===` as its own op. About 40 checker and emitter passes special-case a function
compare by testing `binOp == "=="`, and none of them saw `===`. So on a generic or
un-annotated (hole) function value, `===` met emit refusals where `==` ran ("cannot take the
generic function `x` as a value", "call to unknown function").

## What changed

- **AST.** `mkBinary` builds `===`/`!==` as `==`/`!=` with `binIdent: 1`. Node clones and the
  parse bank carry the flag, the parse image records it, and `fmt` prints the third `=`. Every
  pass that reads an equality now reads an identity compare, so functions, holes, generics and
  `x === null` have exact `==` parity by construction.
- **Removed from step 2:** the emit-time node swap, the checker's `x === null` rewrite (a null
  operand now takes the equality path directly), and the closure-eq scan extensions.
- **Checker.** The operand rule runs only for a non-null identity compare. "No value can share"
  first goes through `eqDeadByFlow`, as `==` does, so a compare that a narrowing made impossible
  is the ruled dead-test warning (owner ruling 2026-11-12).
- **All-function unions.** A union whose arms are all functions has an identity, as an all-record
  union does: the ruling excludes only scalars, `string` and a union with a scalar or string arm.
  A mixed record-and-function union also has an identity under the ruling, but no per-arm
  identity core exists yet. It is refused on the unsupported-lowering channel ("narrow both to
  one arm first"), filed as D16039 with the probe `identity-eq-mixed-union.vl`, so it is not a
  silent narrowing of the ruling.
- **Emitter dispatch.** An operand that holds a function directly, through a nullable, or as a
  union arm (`tyFnPosition`) takes the `==` lowering, where function identity lives. Records,
  lists, maps and record unions take `ref.eq`. This is the ruling's own text: a function is the
  same "iff same table index AND the same captured-environment object", and "the closure struct
  is per-binding and is NOT what is compared" (DECISIONS A15). The all-function-union case was
  first caught as a wrong answer: D7701's shape printed `false`, since `ref.eq` compared two
  closure structs of one declaration.

## Audit: where `==` means something identity must not inherit

All 88 op-string sites (77 functions) that test `"=="` were read. Identity diverts before two of
them:

- `checkBinExprNodeReal`, before `checkEqualityBinNode`. That covers its structural warnings,
  hole constraints (`noteBinCstrAt`, and so `binCstrEqRefused`) and the literal-never refusals.
- `emitBinExprNode`, before the `==` lowering, for every `ref.eq` operand.

Of the rest, these give `==` a structural meaning, and each now reads `binIdent`:

| pass | `==` meaning | identity | matrix cell |
| --- | --- | --- | --- |
| `leqScanExpr` (emit_collect) | reserves list and struct eq frames | reserves only the closure frame a function operand's lowering takes | `identity-eq-list`, `identity-eq-record` |
| `synthRecEqCores` (emit_rewrite) | synthesizes a recursive row's `$eqc` core | skipped: reads no field | `identity-eq-recursive-record` |
| eq classifiers (`binEqStructRow`, `binEqVariantRow`, `binEqNulVariantRow`, `exprIsStrEq`, `exprIsUnionStrEq`, `eqgListKindOfBin`, `listOpKindOfBin`; emit_fn_scans) | name the field-wise or element-wise core, and so the scratch frame a function reserves | answer none; `eqCoreKindOfBin` answers only for a function operand (`identityOperandIsFn`, now its one home) | `identity-eq-record`, `identity-eq-list`, `identity-eq-map` |
| the coming `==`-on-functions refusal | refuses two function-holding operands | must not fire on `===` (the refusal PR reads `binIdent`) | `identity-eq-record-fn-field`, `identity-eq-fn` |

These are read and shared on purpose, since identity needs the same answer:

- **Narrowing** (`check_narrow_flow` ×3, `guardFactOf`, `ifCondIsDiscriminating`,
  `checkTrailingChainTotal`, `ifChainExhausts`): only null and literal compares narrow.
  `x === null` narrows as `== null`, and a literal operand of `===` is refused, so no record
  narrows structurally under either spelling. Cell: `identity-eq-null-narrow`.
- **Mono** (`monoEqOfTpJoin`, `monoPinBin`): pins value lambdas at a join so the operands agree,
  and folds a dead null test. Identity needs the same agreement.
- **Value-use scans** (`nameUsedAsValueIn`, `monoNamesUsedAsValue`, `vrStep`, `collectFnValUse`,
  `ftCtxOk`, `ftHoldCtxOk`, `crSubtreeTests`, `ctnGetKept`, `cwIxNote`): a compared function is
  not an escaping value, and that sharing is the parity.
- **Opcode tables, `exprIsBool`, the numeric adopters:** an identity compare never reaches them
  with a numeric operand, since the operand rule refuses one.

None of the scans refuses (no `emitFail` in any of the ten eq scans), so a shared reading costs
at most an over-reservation. The first sweep found one: `exprIsStructEq` reserved the string-op
frame for a record identity compare (three bytes-only movers, 12 unused locals). The
classifiers above now read `binIdent`, and those programs emit the same bytes as on master.
