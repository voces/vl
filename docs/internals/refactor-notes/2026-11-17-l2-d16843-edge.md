# L2: the place classes draw the call-result edge from a closure a callee's instance made, 2026-11-17

[D16843](../inventory/D16843.md): `eplCallResultFlow` keyed a member of a call's class only
among the calling instance's ancestors (`eplKeyOfFn`). A closure made in a callee's instance is a
sibling there, not an ancestor, so no edge was drawn: `w()(3)` was not a call through `a`, and mono
refused with the place classes' message instead of its own.

## The change

`eplMemberKeys(m, k)` asks `eplKeyOfFn` first, as before. When that finds nothing (-2), it returns
each instance of the member's frame that a call in instance `k`'s own body reached: the pairs
`elabCallKeys` records for the calls `elabKeyCalls` lists.

- **One hop only.** An instance reached through another instance is not asked. The first fix, which
  followed every instance of the frame the calling instance reaches, made this program's compile
  hang and was reverted.
- **The instance tree is flat here.** `wrap`'s instance has parent -1, not `mid`'s, so the
  instance children (`ekKids`) cannot answer it, and the call keys are what can.

## What it moves

D16843's fixture refuses with mono's per-type split message again, which is the row's grading
target. The program is still refused, and no neighbouring spelling changes outcome:
- a closure called at one type, with or without a direct call at the same type;
- the same at `string`;
- the un-annotated spelling.

The remaining question is the coordinator's. A generic function handed through a call and called at
two types is refused at check when the callee calls it directly (`call1(a)` with `g(3)`). Here it
comes back in a closure check does not follow, so check accepts what emit refuses.
