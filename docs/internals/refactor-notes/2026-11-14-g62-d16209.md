# D16209: a set-carrying parameter is closed when a hole member's result is asked, 2026-11-14

Lane G.

`f(__add)`, with `f` a `const` value-`if` of the hole relays `__ap2` and `__ap3`, was typed as an
open hole. The checker accepted any destination for it and stored an `i32` at an un-annotated
map's guess. The coordinator assigned lane S's narrow fix: `elabFnValNote` records a declared hole
function's singleton set. A probe build showed the sets were already there. `holeSetCallRetOf`
saw `f`'s two members and `__add`'s own set, but asked each member's result of `holeLamRetAt`,
which refused any open parameter type, so the join gave up.

## Change (`check_relate_core`, net compiler lines +15; pin-helper delta 0)

- When the set join asks a member's result (`setMemberRetAt`), and the member is a named
  function, `holeLamRetIn` treats a parameter type carrying a set of functions as closed. That is
  the rule `holeSetCallRetOf` already applies to the call's own arguments. Each relay's body is
  typed with `g` bound to `{__add}` and calls it through that set. `holeLamRetAt`'s other callers
  are unchanged.
- Named members only. With a `const` lambda member, the call is then noted at a signature its
  dispatch arms are never built at. Three `tests/cases/closures` programs (`via(neg, 4)` and two
  more) went from runs to an emit reject in the first, unscoped version.
- I also tried S's singleton-set note and a set-keeping argument substitution. Removing each one
  left the acceptance cells passing, so neither ships.
