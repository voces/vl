# D17127: a function forwarded through a parameter into a record (IR-C1, express)

`ftHoleParamOf` keeps a function handed to an un-annotated parameter a closure, rather than its
id, when `ftParamStored` says the callee's body stores the parameter: a `push`, a `set`, or
(D16738) a field of a literal built with a closure. A body that only hands the parameter on as a
call argument stored nothing, so `outer(inc0)` took the id, and `mk` wrote that i32 into its
closure field: an invalid module, the same under the IR and claimless.

`ftParamStored` now asks `ftForwardStored` of a read that is a positional or named argument of a
call to a named function's un-annotated parameter. The question is the same one, of the callee's
parameter. `seen` holds the declarations on the path, so mutual or self recursion stops. It walks
a path, not a fixed depth.

Matrix (checker-clean): 1, 2 and 3 hops, a nested record, a named argument, a local alias, an
imported builder and an imported forward all ran invalid and now print `4`. A generic, a list
push, a bare return and a self- or mutually-recursive forward already ran and still do. A forward
through a closure called later is legacy's loud function-value refusal on both seeds, already
filed (D16938 and kin). `f.mk()` on a function value is a check error.

## Legacy tails the IR calls

This is a checker change that claims nothing new. One function moves to legacy: the spellings
fixture's `mkl` (`xs.push(f)` into `[inc0]`) takes the existing `push operand coercion` miss now
that `f` is a closure. The base seed claimed it only on a build that then failed. The class is
master's: the same spelling behind a second call misses there on the base seed too. The output
is unchanged (`4`), and the claimless build is identical.
