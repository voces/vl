# IR-N3 batch 1: long list literals (2026-11-22, lane IR-N3)

Two mechanisms, one commit each, batched under the coordinator's 2026-11-22 rule. Family C (a list
argument boxed at a generic union parameter's own union) was dropped from this batch: IR-N9's
`ir-n9-declaration-coercion` makes the same split.

## Long string lists past the operand cap (D17054)

A string list literal past `allocLitChunk()` (256) is legacy's chunked build. `emitArrStr`'s chunk
loop is now `arrLitStrChunkOpen`, `arrLitStrChunkStep` and `arrLitStrChunkClose`, which legacy and
the IR's `makeList` both call. The IR takes it only where every element is a string literal: an
immediate lowers at its use, so the chunk opens before the first element as legacy writes it. A
computed element is built before the list node and would land ahead of the opening.

## Long constant lists from a data segment (#9275's phase A)

Ported from `ir4-long-data` and re-measured on this tree. `arrLitLongRouteOf` is the route decision
(`dataConst`, `dataComputed`, `chunk`); `arrLitDataTry` asks it, and all three legacy arms call it.
The IR builds `dataConst` only. Its elements are immediates for the verifier, and the lowering
writes the segment from the AST. `litSegOf` makes a segment idempotent by content, the one legacy
byte change: two long literals of the same bytes share a segment.

`dataComputed` and `chunk` stay named misses (`array long dataComputed`, `array long chunk`).
Legacy evaluates a computed element after the segment or the chunk is open, and the IR builds
element temps before the list node.
