### D4065 — `export` on a declaration inside a function or a block is accepted and does nothing

**open · accepted where the design owes a refusal (no outcome word fits: `vl check` rc 0 and the program runs, so it grades as runs today and must keep running until the refusal lands) · found writing `docs/spec/modules.md` (lane SPEC) · filed 2026-10-11 against master `98a4ed71b`**

Repro:

    if true {
      export const q = 1
      print(q)
    }
    // vl check: rc 0, no diagnostic.  vl run: rc 0, prints 1

Want:

    1

#### Mechanism

`docs/internals/modules-design.md` §5, decided direction 8: visibility is a top-level
`export` or private. The parser accepts the `export` modifier on any declaration
statement, and only the top-level collection reads it; a nested one is dropped without a
word. An importer that names the nested binding is refused with `"q" is not exported by
"./c"`, which points at the import rather than the misplaced modifier.

#### Ablation

| variant | outcome |
| --- | --- |
| `export const` inside an `if` block | accepted, ignored |
| `export const` inside a function body | accepted, ignored |
| `export function` nested in a function | accepted, ignored; the function is called locally |
| an importer naming the nested `export const` | refused, "is not exported by" at the import |
| `import` inside a function | refused at parse, "expected an expression but found IMPORT" |

#### Grading list

Each accepted row should be refused at the `export` keyword, saying `export` is allowed
only at a module's top level. The want above then becomes that refusal.
