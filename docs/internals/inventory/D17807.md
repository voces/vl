### D17807 — a written `let` of an un-annotated higher-order function, copied into a record field before its write, must keep running under the onesig rule

**runs today and must keep running · prints `3` · a refutation pin for the onesig rule (COV-CLOS-3's one-member, one-signature function set held as closures): on its seed the copy refuses `cannot take the generic function apply3 as a value` at `{ f: h }` · filed 2026-11-28 against master `8dea9c36` by COV-CLOS-3 (found ablating `closures/hole-hof-written-let-in-record-field-called-with-fn.vl`; routed to COV-CLOS-3 by the coordinator)**

Repro:

    function apply3(g) { print(g(1, 2)) }
    function add(a: i32, b: i32) { return a + b }
    let h = apply3
    const r = { f: h }
    h = apply3
    r.f(add)

Want:

    3

#### Mechanism

Under the rule, D17740's rule applies to the copy: the field copy and the binding are one value,
so the call through the field should pin `apply3`. On the rule-on seed the refusal is the value
floor (`closureValueWhy`, wasmEmit.vl): mono never instances the generic the copy reads. Letting
both alias readers (`elabAliasGenFn`, `cboxReadGenFn`) accept a `let` whose every write names its
initialiser's generic changed nothing, and was reverted. Mono's own alias walks refuse any written
`let` (`monoLetWrittenIn` at the copy, cell-read and pin sites), and a written generic `let` has
its own route (`monoWrittenGenLetFrame`); the copy into a field is not on it.
