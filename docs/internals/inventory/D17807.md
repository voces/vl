#### Mechanism

Under the rule, D17740's rule applies to the copy: the field copy and the binding are one value,
so the call through the field should pin `apply3`. On the rule-on seed the refusal is the value
floor (`closureValueWhy`, wasmEmit.vl): mono never instances the generic the copy reads. Letting
both alias readers (`elabAliasGenFn`, `cboxReadGenFn`) accept a `let` whose every write names its
initialiser's generic changed nothing, and was reverted. Mono's own alias walks refuse any written
`let` (`monoLetWrittenIn` at the copy, cell-read and pin sites), and a written generic `let` has
its own route (`monoWrittenGenLetFrame`); the copy into a field is not on it.

Parked 2026-11-28 with the coordinator's ruling for the fix: not a narrowing of "written" at
each site, but the binding's set (D17740). A written `let` every write of which stores the same
generic has a one-member set, and a copy of it into a field is the same value, so mono's alias
walks ask the binding's set rather than whether it was written.

Tried 2026-11-28, and the rule-on refusal stands: one predicate, `cwDeclHoldsOneFn` (the `let`'s
init and every write name one function), asked by all six alias walks that refuse a written `let`
(`elabAliasGenFn`, `cboxReadGenFn`, `monoAliasLetEnd`, the two mono alias and cell-read walks, the
alias collector, and `monoWrittenGenLetFrame` through `monoLetMoves`). Rule off nothing moved;
rule on every spelling still refuses. The gate is elsewhere: 15 `cwDeclAssigned` sites and the
mono written-name readers remain, and the call through the field likely takes its set from the
written binding's widened type (`holeSetBindingWider`). Work in progress: branch
`cov-clos-written-let-copy` (b0a7cf428). Parked behind the onesig rule's other blockers
(coordinator, 2026-11-28).
