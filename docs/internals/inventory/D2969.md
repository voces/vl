#### Mechanism

Located 2026-11-02. With a spread in it, a list literal's storage kind came from its spread
source alone (`spreadDestKind` inside `arrLitNumKind` and `arrLitIsStr`), so `[...fs, "s"]` read
as an `f64` list and `[...ss, 2]` as a string list. `arrLitUnionElemName` then declined the
literal's own `(f64 | string)` element, no union row was minted, and the boxing path found none.
The non-spread path already asked `arrLitBoxElem` first; an `i32` source worked only because
`i32` is the kind the scan defaults to. The note from filing:

D2868 builds an un-annotated union-element spread at the literal's own union-box
row when every source boxes into it (`spreadOwnBoxRow`); the `i32[]` twin `[...ints, "s"]` runs
that way. For `(f64 | string)` no row answers, so `rlSlotOfTy` of the literal's element, or the
row's `RLK_UNION` kind, is the first thing to print.
