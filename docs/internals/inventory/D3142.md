### D3142 — a hole's field function bound from an inline record literal argument is called with no function type, so `true` prints as `1`

**closed · a record argument whose anonymous row a hole parameter registered with `_` at a function field binds its own field function types, as D3110's twin-row rung already did for two concrete rows (`monoObjDiffersInFnFieldsOnly` admits a hole on the row's side) · fixture `tests/cases/generics/hole-bound-inline-record-field-function.vl` · was check-clean silently wrong · clause 1 · found by lane FF beside D3117 · the same on master `07d414042` · filed 2026-09-29 against master `07d414042`, closed 2026-09-29 against master `934f169f4`; lane HF's 714-cell grid moved 78 cells to `runs` and lost none**

Repro:

    function F(z) {
      const g = z.f
      print(g())
    }
    F({ f: () => true })
    // PRINTS 1

Want:

    true

#### Mechanism

D3117's close reads the bound callee's function type from the instance's hole binding. The
literal's own node type is concrete (`{f: () => boolean}`), but the instance binds the
parameter to the literal's anonymous row (`#anon0`), and that row holds `{f: _}`, the field
typed in the hole's context. D3110's rung that binds a record's own type where it differs from
its row only in function fields declined, because it required both sides concrete. Measured
by printing the binding: `?F.0 := {f: _}` for the literal, `{f: () => boolean}` for a named
record. An `f64` or `string` field was the loud face of the same missing type.
