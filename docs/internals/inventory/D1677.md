### D1677 — `.get` re-reads its index and its receiver, so a call at either is refused, in the plain and the fused `?.`/`??` spelling alike

**loud emit reject · filed 2026-09-05 against master `a0fa9533c` · found while closing D1670,
which retired the same re-readability gate one layer up · clause 2: `vl check` returns 0 and
the refusal concedes the program is type-valid**

Repro:

    type S = { s: i32 }
    function ix(): i32 { 0 }
    const xs: S[] = [{ s: 3 }]
    print(xs.get(ix())?.s ?? 0)
    // vl check: rc 0.  vl run: emit error,
    // emitProgram: .get index must be a literal or a name

#### Mechanism

`.get` lowers to a bounds test and an element read, and it emits BOTH the index and the
receiver twice — once for `idx u< len` and once for the `array.get`. Rather than stage
either, it gates: the index must be a `NumLit` or an `Ident`, and the receiver a local or a
struct field. The fused `xs.get(i)?.f ?? d` arm carries its own copy of the same two gates,
so the refusal is reached with and without the `?.`.

This is D1670's mechanism in another lowering. A `?.` chain now stages a non-re-readable base
in the frame's `(ref null struct)` stash (`optRecvSlot`, `emitOptRecvBase`), and the same
treatment fits here: an i32 index wants an i32 stash and the receiver the ref one, after
which both gates answer "does this need staging" rather than "is this legal".

Both faces refuse identically — annotating the list or the index changes nothing.

#### Grading list

The `?.`-free spelling is the one to fix first, since the fused arm only inherits the gate.
Grade both, so the fused path is not narrowed instead of built.
