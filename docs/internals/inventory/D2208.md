### D2208 — a module-scope un-annotated join whose fresh member set equals a declared alias's builds an invalid module

**closed — `ifJoinTypedAtom` asks whether the join's set is a registered literal union by MEMBER SET, as a binding's rep does, not by arena index · was check-clean invalid wasm (`type mismatch: expected i32, found (ref $type)` in the module's top-level code) · the same on the seed built before #3056 and on master · found reviewing #3066 (`p66/e4.vl`, filed there as an inline-typed-field defect; the ablation below refutes that ingredient) · filed and closed 2026-09-23 against master `54d2a0dde` with [D2206](D2206.md) · `tests/cases/literal-unions/if-join-arms-disagree-unannotated-binding.vl`**

Repro (runs, prints `blue`):

    type C = "red" | "green" | "blue"
    const G: "green" = "green"
    function one(): i32 { 1 }
    type S = { c: "red" | "blue" }
    const st: S = { c: "blue" }
    const v2 = if one() > 0 { st.c } else { G }
    print(v2)

#### Mechanism

The join of `"red" | "blue"` with `"green"` mints a fresh arena index, and its member set is
exactly `C`'s. The binding's rep resolves a literal union by member set
(`litUnionAliasNameOfTy`), so `v2` read as the atom; the D2206 test resolved by arena index
(`tyIsLitUnionAlias`), called the join a string, and the module cell and its initializer
followed it. The declared alias is load-bearing and it need not be used: without `type C` no
alias has that set, both answers are "string", and the program ran on every seed.
