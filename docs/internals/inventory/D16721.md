#### Mechanism

The literals `{ f: inc0 }` and `{ f: dbl }`, joined across an `if`'s arms, mint an anonymous row
whose field stores `FC_CLOSURE` (14). Its storage type's rep is `i32`, the set id, and the
module emits the row as `(struct (field (mut i32)))`. So the stored code is stale, and every
emitted read agrees with the rep. Readers of the code: `sFieldTypeAt`, `fieldRowCode`,
`storeAlike`, `refsElemHeap`, `layoutId`: 49 disagreeing reads in 3 files. Function-typed fields
agree on 27,591 other reads. A scratch compiler that derives the code is byte-identical on all
3 files, so no read of the stale code feeds a call or a store today. Stage 3c-ii keeps the stored
code for every function-typed field (`fcKeptFnRep`). The close: lane SLOT's function-storage
stage (S stage 2, function storages as reps) writes the field's `RClosure`/`RSetId` rep, and the
fallback is deleted.
