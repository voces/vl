### D15085 — a diagnostic renders a transparent alias by its member, losing the user's name

**closed 2026-11-03 · runs, prints `3` then `circle`, and the hints read `Id` and `KC | null` · a redundant-annotation hint renders the annotation of the declaration the value reads when it names a transparent alias (`userSpellingOfValue`) · was a diagnostics-quality pin (runs today and must keep running) · filed 2026-11-03 against master `4a114e6c`**

Repro:

    type Id = i32
    function g(): Id { 3 }
    const h: i32 = g()
    print(h)
    type KC = "circle"
    function k(): KC | null { "circle" }
    const e: "circle" | null = k()
    print(e ?? "n")
    // vl check: rc 0, and the redundant-annotation hints read "`h` is inferred as `i32`" and
    // "`e` is inferred as `"circle" | null`", never `Id` or `KC | null`

Want:

    3
    circle

#### Mechanism

A one-member alias is transparent (D3870, `docs/json-design.md`): `singleAliasMemberTyIx` makes the
name denote its member, so the arena holds no trace of the alias and every render of the type
(`tyToStrUser`) spells the member. That has always held for a primitive alias (`type Id = i32`)
and holds for a literal alias since D15082. The program is right; only the diagnostic loses the
name the user wrote. Keeping it needs the alias's provenance carried beside the type, which no
render reads today.
