### D1976 — the emitter keeps each output buffer as an `i32[]` with one slot per byte, so a module past 2^23 bytes (8 MiB) traps the compiler

**compiler trap (`allocation size too large`, exit 70) · filed 2026-09-22 against `490229809` (#3013) · re-witnessed 2026-09-22 as a two-file program so the ENTRY FILE stays under 1.5 MiB and `vl build`/`vl run` keep the null collector (an entry file of 1.5 MiB or more compiles under the copying collector, which has no 64 MiB object cap and does not reach this trap) · found in review of D1975 · the output-side twin of D1975's intake ceiling**

Repro (a 2.85M-character literal in an IMPORTED module, written as `@@repeat` so the row can hold it):

    // file: m.vl
    export function f0(): string { "@@repeat(2850000, "a")@@" }
    // file: main.vl
    import { f0 } from "./m"
    print(f0().length)
    // vl check: rc 0.  vl build / vl run: the compiler traps, exit 70 (entry file 45 bytes: null collector)

#### Mechanism

The emitter writes bytes with `wU8` (`emit_bytes.vl`), which pushes `b & 0xff` onto the current
buffer. Every buffer is an `i32[]`: the module's own `W.bytes` (`emit_state.vl`,
`{ bytes: i32[] }`) and each function body's buffer before `wBytes` appends it. The compile
store for an entry file under 1.5 MiB runs under the null collector, where one object is at most 64 MiB, so `.push`'s growth
to 2^24 slots traps as soon as a buffer passes 2^23 bytes. Named backtrace for the first filed witness (two functions):
`wU8@emit_bytes.vl:261` ← `wBytes@emit_bytes.vl:305` ← `emitFuncCode@emit_sections.vl:801`,
appending the second function to `W.bytes`. A single function past 8 MiB, as in today's
repro, traps in its own buffer first (`wSLEB` ← `fbI32Const` ← `emitStr`). A string literal emits about three module
bytes per character, so the trap needs about 2.8M characters of literal. plumb's shape (D1975)
emits about 0.3 bytes per source byte and reaches the 4 GiB heap ceiling first.

A separate ceiling, not this row ([D2092](D2092.md)): wasmtime refuses any function body over 7,654,321 bytes
(`function body size count exceeds limit of 7654321`). A single 2.75M-character literal builds
an 8.26 MB module that the engine then rejects, exit 70 with the invalid-module banner.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the literal's length (1.6M characters, a 4.8 MB module) | builds and runs | **yes** |
| the null collector (`VL_COMPILE_GC=copying`) | no trap; the module is refused at the engine's function-body limit, [D2092](D2092.md) | **yes** |
| the module split (the literal in the entry file, which is then 1.5 MiB or more and gets the copying collector) | as the row above, [D2092](D2092.md) | **yes**, under the default collector choice |
| the emit (`vl check`, no emit) | rc 0 | **yes** |

The first filed witness, two 1.6M-character functions in ONE 3.2 MB file, stopped trapping when
the host moved entry files of 1.5 MiB or more to the copying collector: it now runs, after
127 s and 25 GB of Cranelift. It still traps under `VL_COMPILE_GC=null`.

#### Grading list

- The fix must hold at the next buffer too: a module and a function body each past 8 MiB,
  and the function past 7,654,321 bytes must then fail at the engine's limit, not in the compiler.
- A byte buffer (`u8[]`, a quarter of the memory) moves the ceiling to 2^25 bytes (32 MiB);
  chunking `W.bytes` the way D1975 chunked the intake removes it.
