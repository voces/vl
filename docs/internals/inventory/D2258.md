### D2258 — a closure capturing a `for-in` variable over an annotated nullable-scalar list types the variable as the bare scalar

**closed 2026-10-27 — the witness prints `false`, and an `(f64 | null)[]` loop prints `false` too · was check-clean invalid wasm, clause 1 · closed by lane s7 with the list-row reroute against master `082f7edd3`: a captured loop variable is read at the rep its list is built as · fixture `tests/cases/closures/closure-captures-for-in-var-of-nullable-scalar-list.vl` · 18 cells of the D2252 closure grid · filed 2026-09-23 against master `b2b56b450`**

Repro:

    function mk() {
      const xs: (i32 | null)[] = [41]
      for r in xs {
        const g = () => r
        print(g() == null)
      }
    }
    mk()
    // vl check: rc 0.  vl run: invalid module,
    // "type mismatch: expected i32, found (ref $type)"

#### Mechanism

The disassembly shows the loop variable's local declared `i32` while the element read leaves
the `(ref $uBox)` the list holds. A captured loop variable is typed through
`captureLoopVarIterOf` / `forInElemKind` in the type section, where no frame's locals are
bound; for a bare local iterable that ladder cannot see `xs`'s annotation (`exprRefArray`'s
`Ident` arm has no `frameLetOf` rung) and re-asks the initializer instead, and `[41]` alone
classifies as an `i32` list. An initializer holding a `null` (`[41, null]`) classifies as the
box list and runs. A prediction until a close confirms which rung.
