#### Mechanism

`monoCellReadName` is a spelling test. Twelve callers use it as "is this a cell read", or take the
name it returns as the cell's binding, without the `monoGeneratedCellElem` check
`monoIsCellRead` makes:

- **Name extractors.** For a user list `r`, these read `r[0]` as a read of `r`:
  - `monoLamValueFe` (two sites), the alias chain to a closure's function;
  - `monoNoteBindDeliveryCall`, a delivery's name;
  - `monoFrameNameUnread`, a write target's name;
  - `monoReadNameNode`.
- **Write and frame bookkeeping:**
  - `monoLetWriteFrame` and `monoLetWritesExtend` file `r[0] = f` as a cell write;
  - `monoReadLetFrame`, `monoRetypeLamCells` and `monoValueMayNameLam`.
- **The call arm `monoWalk`** (`monoCellCall`): it resolves through the cell's declaration, so a
  user list falls through.
- **`monoCoerceFnValueTys`**: guarded downstream, where `monoCoerceWrittenCell` refuses a
  declaration with no generated cell.

The witness above, a `let` list written through `r[0]`, called through it and re-pointed, and its
`const` spellings (fixtures `closures/user-list-element-0-*`) run with the split plan on and off.
Change one of these callers only with a witness that fails.
