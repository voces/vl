### D12701 — a list of hole functions handed a frame's forwarded hole function and a value has no interned signature

**loud emit reject · `vl check` rc 0 · clause 2 · CAPABILITY: the same loop handed the named `add` runs ([D10700](D10700.md)) · found closing [D10700](D10700.md) · filed 2026-10-25 against master `a448ccb42`**

Repro:

    function add(a, b) { return a + b }
    function apply2(g, s) {
      print(g(1, 2))

      for f in [apply2, apply3] { f(h, k) }

#### Mechanism

Narrowed 2026-10-25 by lane L1. Elements whose calls each agree on one key now run
([D13102](D13102.md)). What still refuses is two elements whose keys mix a key with no open
slot and one naming an element's value parameter.

The split gives `h` and each element's `g` one slot per call key. Here the keys are
`c:_,f64,` (lane 0), `c:i32,i32,` and `c:_,_,`. The instance of `add` that fills each of `h`'s
slots is chosen at the OUTER call `inner(0.5, add)` (`monoPinHoleParam` → `monoHoleGenFnPin`,
emit_mono.vl), from the checker's binding (`callBindTyOf`) or else the flow pin.

Measured with a probe on that choice:
- the checker binds `c:i32,i32,` to `(i32, i32) => i32`;
- it binds `c:_,_,` to `(f64, f64) => f64`;
- lane 0, the key `g(s, 0.25)`, gets NO checker binding. It falls back to the flow pin, which
  is merged across the elements and answers `add`'s `i32` instance.

The element-side typing ([D13102](D13102.md)) closes the call when each element's own keys
agree with the one instance `h` holds. Here they cannot: one parameter carries three lanes.
What is missing is the checker's instance for the lane whose key names `s`. It is computed at
the outer call by `instGenFnHolePins` → `genFnHoleInstance` (check_demands.vl,
check_relate_core.vl), which returns -1 when an argument stays open. Whether `s` reaches it
unsubstituted is not yet confirmed.
