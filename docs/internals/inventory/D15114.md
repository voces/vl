### D15114 — two record literals of one shape holding different un-annotated functions build an invalid module

**check-clean invalid wasm · `type mismatch: expected i32, found (ref $1); $1 is string` · clause 1 · open · pre-existing: the bound spelling is invalid on #6148's branch `d3ae7d29` before D15206; the inline spelling was a loud emit reject there only because its first call already failed, and since D15206 it is invalid as well · found closing D15206 · filed 2026-11-03**

Repro:

    function inc0(a) { return a + 1 }
    function ex(s) { return s + "!" }
    const a = { f: inc0, n: 1 }
    const b = { f: ex, n: 1 }
    print(a.f(3))
    print(b.f("a"))

Want:

    4
    a!

#### Ablation

| spelling | outcome |
| --- | --- |
| the witness (bound) | invalid module |
| the same two literals unbound, `{ f: inc0, n: 1 }.f(3)` and `{ f: ex, n: 1 }.f("a")` | invalid module (since D15206) |
| either literal alone, bound or unbound | runs |

#### Mechanism

Not yet ablated. The likely mechanism is that both literals are adopted at one record row whose `f`
is coded at the first literal's signature (`nodeRepTyIxOf`), so `ex`'s closure is stored where an
`(i32) => i32` one is read. D15113 (one function at two signatures, unbound) is probably the same
fact.
