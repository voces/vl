### D15114 — two record literals of one shape holding different un-annotated functions build an invalid module

**closed 2026-11-04 by lane G2, runs, prints `4`, `a!` · was check-clean invalid wasm (`expected i32, found (ref string)`), clause 1, pre-existing on master · `print` chose its sink from `exprString`, whose field-closure arm asked `fieldClosureFeOfRecv` which closure the field holds: its D3110 row scan answered the first literal of the shape whose open function can take the wanted type (`a`'s `inc0`), though the checker had typed `b.f("a")` `string`; a field call the checker typed closed now takes that type, and the resolver is asked only where it is open · fixture `closures/fn-same-shape-records-different-fns-called.vl` · named set `d15114-same-shape-record-fns` · found closing D15206 · filed 2026-11-03**

Repro:

    function inc0(a) { return a + 1 }
    function ex(s) { return s + "!" }
    const a = { f: inc0, n: 1 }
    const b = { f: ex, n: 1 }
    print(a.f(3))
    print(b.f("a"))

Want:

    4
    a!

#### Ablation

| spelling | outcome |
| --- | --- |
| the witness (bound) | invalid module |
| the same two literals unbound, `{ f: inc0, n: 1 }.f(3)` and `{ f: ex, n: 1 }.f("a")` | invalid module (since D15206) |
| either literal alone, bound or unbound | runs |

#### Mechanism

The checker's facts are right and distinct: `b.f("a")` is typed `string`, the two literals are
adopted at two records, and the emitted `call_indirect` uses `ex`'s signature. Only the print sink
was wrong. `exprString`'s field-closure arm asked `fieldClosureFeOfRecv(b, "f")`. Its raw walk
followed `b` to its own literal, but the D3110 correction rescanned the struct row for a closure
of the wanted type and answered `inc0`, the first open one. So the arm reported a non-string, and
`print` used `__print_i32__`. Declaring `b` first ran, because the first literal was then `ex`.
The checker's closed call type now decides the arm, and the resolver keeps its job where the type
is open.
