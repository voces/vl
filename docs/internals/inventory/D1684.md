**closed 2026-09-06 — the witness prints `b` · was check-clean invalid wasm (a loud emit
reject in a module with no i32 list) · filed 2026-09-06 against master `ee017cf9b` · isolated
while closing D1410, whose grading list carried the `string[]` cell · fixture
`tests/cases/arrays/listget-string-element.vl` · matrix
`scripts/capability-probes/matrix/listget-string-element.matrix.vl`**

Repro:

    const nums = [1, 2]
    print(nums[0])
    const ys: string[] = ["a", "b"]
    print(ys.get(1) ?? "z")
    // was: vl check rc 0, then the emitted module failed to validate —
    // type mismatch: expected (ref $type), found (ref $type). Now prints 1 then b.

#### Mechanism

`emitListGetOr` picks the wrapper, the backing, the `if` blocktype and the collected-ness
guard from four ladders keyed on the element kind — `scalarListWrap`, `scalarListBack`,
`scalarListBlocktype`, `scalarListUsed` — and **all four fell through to the i32 list's
answer** (`lTypeIdx`, `aTypeIdx`, `0x7f`, `lUsed`). A `string[]` reaches them because
`scalarListElemKind` has no string arm and `exprArray`'s typed-IR fast path (`tyKindOf == 2`)
claims ANY array, so the classifier answers `"i32"`.

The two outcomes are the same hole read twice:

* with **no** i32 list in the module, `lUsed` is false and the guard refuses
  `.get but list type not collected` — a sentence about a list the program does not have;
* with **one**, `lUsed` is true, the guard passes, and the read is emitted against the i32
  wrapper and backing — `vl check` rc 0 and an invalid module.

Each ladder now names `"str"` (wrapper `mkListIdx`, backing `mkArrIdx`, collected
`slUsed || mUsed`, and the blocktype through `fbIfRef(sTypeIdx)`, since a string element is a
REF and has no valtype byte), names `"i32"` explicitly, and ends in a NAMED default so the
next unlisted `VKind` refuses instead of reading as the i32 list. The element's backing slot
is `(ref null $str)` while the `if` joins on the non-null rep, so the hit arm recovers with
`ref.as_non_null` — an in-range element of a live list is never null.

**The classifier itself is unchanged.** Teaching `scalarListElemKind` the string arm was the
first candidate and it broke the compiler's own build: ten other callers route a string list
already, and one of them tests `== "i32"` outright. The question is asked at the `.get` site
instead.

#### Ablation

Every list element kind, at six delivery positions, with and without an i32 list in the module
(108 cells; the value is printed, not just its nullness):

| element kind | `?? d` | bare `.get` | under `?.` | argument | return | field |
| --- | --- | --- | --- | --- | --- | --- |
| `string`, no i32 list | **emit → runs** | runs | runs | **emit → runs** | **emit → runs** | **emit → runs** |
| `string`, with one | **SILENT → runs** | runs | runs | **SILENT → runs** | **SILENT → runs** | **SILENT → runs** |
| `i32`, `boolean`, `f64`, `i64`, `f32`, struct, nullable struct, `i32[]` | runs | runs | runs | runs | runs | runs |

**100 of 108 before, 108 of 108 after.** `string` is the only affected kind, and the four
failing positions are exactly the ones routed through the fused `?? d` read; `bare .get` and
`under ?.` take other paths and always ran. `u8` is out of the grid: it is a storage type, not
a value type, so its non-array positions are a design refusal.

#### Grading list

The other seven element kinds must keep running at all six positions — the fixture pins one
per rep family. The `.get but list type not collected` sentence stays in the compiler and
stays correct for a kind whose types genuinely are not minted.
