### D1819 — an INFERRED return that hands back a `T[]` local emits a function whose result kind fell to i32, while the body builds the list ref

**closed · by design: the refusal is a contract, re-graded 2026-11-13 on master `11274d920` (coordinator) · was check-clean invalid wasm, now a loud check reject · filed 2026-09-06 against master `9a0143a1a`**

Repro:

    function mk<T>() {
      const xs: T[] = []
      return xs
    }
    mk()
    // vl check: cannot infer type parameter `T`: `mk`'s return type is inferred as
    // `T[]`, which names it, and no parameter does, so a call has nothing to bind it
    // from — give `T` a parameter position, or make the return type concrete

#### Mechanism

The disassembly named the disagreement — the BODY was right and the SIGNATURE was wrong:

    (func $0 (type $4) (result i32)          ;; the declared result
     (local $0 (ref $3))                     ;; the local, correctly the list wrapper
     (local.set $0 (struct.new $3 (array.new_fixed $0 0) (i32.const 0) (i32.const 0)))
     (return (local.get $0)))                ;; a (ref $3) returned into an i32 result

The rung's INPUT settles it, measured rather than predicted. An instrumented
`emit_collect` reads `inRow=-1 inferRetName=[] retTyIx=-1` for `mk`, so the
inferred-return kind chain has no row and `fRetKind` keeps its `retAnnKindChain(-1)`
seed. That decline is deliberate — the A20 recorder skips a generic return because it
is per-call-site — and it is NOT the defect: `mk<T>(seed: T)` reads `inRow=-1` too and
RUNS, since the pin substitutes `T` and both ends agree; `return xs.length` banks
`inRow=0 inferRetName=[i32]` and runs. What separates the witness from both controls
is that nothing can bind `T` at all, which is a CHECKER fact.

`bindGenWalk` binds a generic call from its ARGUMENTS, and VL has no explicit
type-argument spelling, so a parameter only the return names is bound by nothing.
D1813 built that refusal for the DECLARED return, reading the return ANNOTATION, which
this program has none of. `checkRetTyParamBound` now also asks the settled return type
the call site already holds — `ft.fnRet` direct, `retTy` UFCS — for a `TyVar` named by
a type parameter no parameter ANNOTATION mentions. The parameter side stays a SPELLING
question in both faces, which is what keeps the phantom `Bare<A>` running.

#### Closed by design (2026-11-13)

The refusal names a contract, not a missing mechanism. VL has no explicit type-argument
spelling, so a caller cannot bind a `T` that only the return names. DECISIONS, "An unbound type
parameter defaults at the call" (D4551), defaults such a parameter to `i32` only because it
"names only body locals" and the choice is not observable. Here `T` escapes through the return,
so a default would be observable in the caller's types (`const ys = mk()` then
`ys.push("s")`). DECISIONS, "A parameter a call leaves open is `never` in that call's deferred
return" (D14802), keeps "its own declaration-time refusal" for a parameter no parameter
annotation names. The nine positions above are the refusal's scope. Binding an escaping `T` from
the call's destination (`const ys: string[] = mk()`) would be new language design, not a fix.
