### D1819 — an INFERRED return that hands back a `T[]` local emits a function whose result kind fell to i32, while the body builds the list ref

**check-clean invalid wasm (`the emitted module failed to validate inside `mk`: Invalid input WebAssembly code at offset 130: type mismatch: expected i32, found (ref $type)`, exit 70) · filed 2026-09-06 against master `9a0143a1a`**

Repro:

    function mk<T>() {
      const xs: T[] = []
      return xs
    }
    mk()
    // vl check: rc 0.  vl run: the emitted module failed to validate inside `mk`:
    // Invalid input WebAssembly code at offset 130: type mismatch: expected i32,
    // found (ref $type)

#### Mechanism

The disassembly names it without ambiguity — the BODY is right and the SIGNATURE is wrong:

    (func $0 (type $4) (result i32)          ;; the declared result
     (local $0 (ref $3))                     ;; the local, correctly the list wrapper
     (local.set $0 (struct.new $3 (array.new_fixed $0 0) (i32.const 0) (i32.const 0)))
     (return (local.get $0)))                ;; a (ref $3) returned into an i32 result

So the local's rep classifier resolves `T[]` to the list wrapper, and the function's RESULT
kind falls to the `"i32"` default. The type parameter is bound by no parameter, so nothing
at the pin substitutes it; with the return ANNOTATED (`function mk<T>(): T[]`) the same
program is a loud emit reject instead, because `monomorphize`'s substitution guard is asked
only when `fn.fnRet >= 0`. An inferred return never reaches that guard, and the kind reader
downstream has no arm for a type still carrying an unresolved type variable.

**Prediction, to be confirmed by whoever fixes it, not assumed here.** The owing rung is the
inferred-return kind reader — the `retResultVKind` / `fnRetKind` family fed by the checker's
inferred type — falling through to the bare `"i32"` that ends `vtKindOfType`'s ladder, which
is the ladder-with-a-hole shape `kind-ladder-incomplete` exists for. The fix is a NAMED
default there, and the diagnosis the design owes is the same one the annotated spelling
already gets: a type parameter the return names and no parameter binds cannot be inferred at
a call. Predicting a rung is not measuring one — print what the reader receives for this
instance before editing it.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the inferred return — annotate it `: T[]` | loud emit reject (`a return type parameter of \`mk\` is not bound by any parameter`) | **yes** |
| the call — the declaration alone | runs | **yes** |
| `T` unbound — give it a parameter, `mk<T>(seed: T)` | runs, prints `0` | **yes** |
| the type parameter in the local — `const xs: i32[] = []` | runs, prints `0` | **yes** |
| the annotation on the local — `const xs = []` | loud check reject (`cannot infer a type for 'xs'`) | **yes** |
| returning the local — `return xs.length` instead | runs, prints `0` | **yes** |
| the depth — `const xs: T[][] = []` | the same silent, at the same offset | no |
| the LIST spelling — `const m: {[string]: T} = Map()` | loud emit reject (`unsupported map value type`) | **yes** |

The two right-hand rows are what makes this a family rather than a message: the defect needs
the value to ESCAPE through the inferred return (`return xs.length` runs), and it needs the
LIST spelling (a map local refuses loudly instead). A second unbound parameter beside a bound
one (`mk<T, U>(seed: T)` with `const xs: U[] = []`) is a different cell — it refuses loudly
with `'.length' on a receiver the emitter cannot classify`.

#### Grading list

The witness above, and the annotated twin `function mk<T>(): T[] { return [] }; mk()`, whose
checker-side refusal for a type parameter only the declared RETURN names is filed separately
and does NOT close this row: that gate reads the return ANNOTATION, and this program has
none, so the gate never sees it. Re-grade both together — a fix here that also silences the
annotated twin has moved the refusal to the wrong tier.
