### D2292 — a call as a body's first statement, followed by a brace-led tail, parsed as a bogus method-shorthand member

**closed 2026-09-23 — now runs · was a parse error (`expected an identifier but found`, then a
cascade) · found in review of #3100 · filed against master `b088e0749` · fixtures `tests/cases/parser/call-first-stmt-then-brace-tail.vl`, `tests/cases/parser/call-first-stmt-then-brace-tail-getter.vl`**

Repro:

    type Q = { x: i32 }
    function mk(n: i32): Q {
      print("mk")
      { x: n }
    }
    print(mk(3).x)
    // vl check (as filed): rc 1 — 3:9 expected an identifier but found `"mk"`, then a cascade.
    // Fixed: vl run prints `mk` then `3`.

#### Mechanism

`looksLikeObject` (`compiler/parser.vl`) decides whether an ambiguous `{` opens a block or an
object literal, and one of its arms exists to recognise object-literal method shorthand
(`{ add(a,b){…} }`): an IDENT directly followed by a balanced `(…)` and then (past an optional
`: type`) a `{` reads as that member's signature. The arm never checked that `(…)` actually
looked like a parameter list — every `parseParam` starts with an identifier or `...`, never a
literal — so it fired on an ordinary CALL statement whenever a brace-led statement happened to
follow shortly after (skipping the intervening NEWLINEs the same way a real signature's
optional return-type clause does): `print("mk")` read as the member name `print` with `"mk"`
as its first "parameter", and the returned `{ x: n }` on the next line read as that member's
body. The whole enclosing brace was then handed to `parseObjLit`, whose own method-shorthand
branch parses `(…)` as a real parameter list and diagnosed the string where a name was wanted.

The RETURN TYPE was never the ingredient (the working hypothesis going in): `looksLikeObject`
runs on the body's opening `{` regardless of what precedes it, and the same misparse hits a
bare function with no return type at all, a bare block statement, and the `else` arm of an
`if` (the `then` arm never reaches this lookahead — it always requires a brace block, via
`parseBracedBody`) — the two other call sites sharing the one lookahead. What matters is only
the BODY'S FIRST STATEMENT'S shape: a call whose argument list is not parameter-shaped,
followed by another brace-led statement.

Fixed by requiring the body `{` (or, with a return annotation, the `:` that precedes it) to
sit on the SAME LINE as the parameter list's closing `)`. A real signature's body already
requires that adjacency — `parseFuncBodyAndBuild`'s own `peekKind() != LBRACE` check never
skips a NEWLINE first, so a genuine method-shorthand `f()` with its `{` on the next line was
ALREADY a parse error before this row, at every position (confirmed: no file under
`tests/cases/`, `std/`, `compiler/`, `scripts/` or `bench/` pairs a signature-shaped line with
a brace-led next line except this row's own fixtures, and `vl fmt` never produces that shape).
A NEWLINE there is therefore always a statement boundary, never a signature continuing — and
this rule alone rules out every shape this row's own ablation names (a literal argument, zero
arguments, or a single bare-identifier argument), since all three share the same call-then-
brace-tail structure: two sibling statements, never adjacent on one line.

**First draft, reverted in review.** The fix originally shipped as a SEPARATE, positive check,
`parenLooksLikeParamList`: it walked the parenthesized run and required every top-level comma-
separated item to start with an identifier or `...`, tracking paren/brace/bracket depth to
step over a parameter's own type annotation — but never `<…>` depth. A multi-argument generic
type annotating a parameter (`Pair<i32, {[string]: i32}>`) has a top-level comma *inside* the
angle brackets that this check could not see, so it read the comma as splitting the parameter
list and rejected the second "item" for not starting with an identifier — turning a genuine,
same-line method shorthand into a block and reproducing this row's own defect one layer up
(review of #3102). Removed rather than patched: the same-line rule above already covers every
case the positive check was added for, so it bought no coverage its own family did not already
have, at the cost of exactly this regression.

#### Ablation

Every combination below is a call with a **string-literal argument** as the first statement,
followed immediately by a `{`-led statement, inside the position named. Return type identity
never mattered — the italicised column proves it independent of the container.

| ingredient | outcome (before fix) | outcome (after fix) |
| --- | --- | --- |
| return type: a user record (`Q`) | parse error | runs |
| return type: `i32` (primitive) | parse error | parses (a later type error is the program's own, not a parse error) |
| no return type at all | parse error | runs |
| return type: a generic alias (`Box<T>`) | parse error | runs |
| return type: a union (`Q \| null`) | parse error | runs |
| return type: a nominal `new` type | parse error | parses |
| container: a lambda's return annotation (`(): Q => {`) | parse error | runs |
| container: a getter's body | parse error | parses (reaches the getter's own no-allocate check) |
| container: a bare block statement | parse error | runs |
| container: the `else` arm of an `if` (the `then` arm never uses this lookahead) | parse error | runs |
| control: first statement is `const s = …` (a statement keyword) | ran (never reached the LPAREN arm) | ran, unaffected |
| control: first statement is a bare identifier | ran (warns, unrelated) | ran, unaffected |
| control: genuine method shorthand `{ add(a,b){…} }` | ran | ran, unaffected |

Two narrower shapes — a call with **zero arguments** (`foo()`) and a call whose sole argument
is a **bare identifier** (`print(n)`), each followed by a brace-led statement — are the same
family and are closed by the same-line rule too: neither is distinguishable from an
equally-shaped parameter list on SHAPE alone (a positive, item-starts-with-IDENT check, as
`parenLooksLikeParamList` was, cannot rule either out), but both still fail because their
`{` sits on the next line.

| ingredient | before | after |
| --- | --- | --- |
| `foo()` then a newline then `{ x: n }` | parse error | runs |
| `print(n)` then a newline then `{ x: n }` | parse error | runs |
| control: a genuine zero-arg method `greet() { "hi" }`, same line, as a function body's sole statement | ran | ran, unaffected |
| control: a genuine one-arg method `double(n: i32) { n * 2 }`, same line, as a function body's sole statement | ran | ran, unaffected |

**The controls must be routed through `looksLikeObject` itself, not `parseObjLit`'s disjoint
shorthand arm.** A first attempt spelled the controls as `const o = { greet() { "hi" }, … }` —
which passes today, but proves nothing about this row: expression position has no block/object
ambiguity for `looksLikeObject` to resolve, so `const o = { … }` never reaches it, taking
`parseObjLit`'s own method-shorthand arm (line 1461 of `compiler/parser.vl`) instead, a
disjoint path this row never touches. The corrected controls make the SHORTHAND the sole
content of a function body (`function mk() { greet() { "hi" } }`), so `looksLikeObject`'s own
LPAREN branch is what decides the body is an object, not a block.

Both residual rows and their corrected controls are exercised in `call-first-stmt-then-brace-
tail.vl`, but the fixture's own controls are canonicalised to arrow fields by the required
`vl fmt -w` pass (an object literal with a method-shorthand member is exactly what `vl fmt`
rewrites), so they no longer exercise `looksLikeObject`'s LPAREN branch once committed. The
durable pin for that branch is `tests/vl_fmt_test.ts`'s dedicated same-line-shorthand test,
which reads its own RAW, unformatted source and is immune to the corpus-wide `vl fmt --check`
sweep; the fixture's committed (post-format) controls remain a values-correct regression net.

**The regression `parenLooksLikeParamList` introduced and its own control**, both same-line
method shorthands whose parameter's type annotation is a multi-argument generic
`Pair<i32, B>`, so the top-level comma the removed check misjudged sits inside `<…>`:

| ingredient | with `parenLooksLikeParamList` | with the same-line rule alone |
| --- | --- | --- |
| `B = {[string]: i32}` (a map type — the reviewer's own witness) | parse error (regression) | runs |
| `B = (i32) => i32` (a function type — its own `(…)` is balanced, still inside `<…>`) | parse error (regression) | runs |
| `B = !string` (a negation type) | parse error (regression) | check-clean, then a separate emit reject — [D2294](D2294.md), unrelated to this row |

The `!string` row is not a fixture in `call-first-stmt-then-brace-tail.vl`: it does not run
either before or after this row (confirmed identical on master before D2292, commit
`b088e0749`), so it cannot serve as an `@run` regression pin without first fixing D2294. Its
witness is D2294's own filed repro instead.

#### Grading list

Three `looksLikeObject` call sites share the one lookahead fixed here — a function/getter/
lambda body, a bare block statement, and the `else` arm of an `if` (never the `then` arm) —
and all three are exercised in the fixtures. `tests/vl_fmt_test.ts` carries two tests this row
must not regress: the pre-existing object-method-shorthand test (a disjoint code path,
`parseObjLit`'s own shorthand arm, never touched by this row) and the same-line-shorthand test
this row added (the durable pin for `looksLikeObject`'s own LPAREN branch). A future change to
this lookahead must re-grade both, plus [D2293](D2293.md) (the confusing diagnostic a next-line
body brace produces) and [D2294](D2294.md) (the unrelated negation-in-generic-argument gap this
row's own fixture work surfaced) if either is later closed.
