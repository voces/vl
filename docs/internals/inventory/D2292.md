### D2292 — a call as a body's first statement, followed by a brace-led tail, parsed as a bogus method-shorthand member

**closed 2026-09-23 — now runs · was a parse error (`expected an identifier but found`, then a
cascade) · found in review of #3100 · filed against master `b088e0749` · fixtures `tests/cases/parser/call-first-stmt-then-brace-tail.vl`, `tests/cases/parser/call-first-stmt-then-brace-tail-getter.vl`**

Repro:

    type Q = { x: i32 }
    function mk(n: i32): Q {
      print("mk")
      { x: n }
    }
    print(mk(3).x)
    // vl check (as filed): rc 1 — 3:9 expected an identifier but found `"mk"`, then a cascade.
    // Fixed: vl run prints `mk` then `3`.

#### Mechanism

`looksLikeObject` (`compiler/parser.vl`) decides whether an ambiguous `{` opens a block or an
object literal, and one of its arms exists to recognise object-literal method shorthand
(`{ add(a,b){…} }`): an IDENT directly followed by a balanced `(…)` and then (past an optional
`: type`) a `{` reads as that member's signature. The arm never checked that `(…)` actually
looked like a parameter list — every `parseParam` starts with an identifier or `...`, never a
literal — so it fired on an ordinary CALL statement whenever a brace-led statement happened to
follow shortly after (skipping the intervening NEWLINEs the same way a real signature's
optional return-type clause does): `print("mk")` read as the member name `print` with `"mk"`
as its first "parameter", and the returned `{ x: n }` on the next line read as that member's
body. The whole enclosing brace was then handed to `parseObjLit`, whose own method-shorthand
branch parses `(…)` as a real parameter list and diagnosed the string where a name was wanted.

The RETURN TYPE was never the ingredient (the working hypothesis going in): `looksLikeObject`
runs on the body's opening `{` regardless of what precedes it, and the same misparse hits a
bare function with no return type at all, a bare block statement, and an `if`/`else` arm — the
three other call sites sharing the one lookahead. What matters is only the BODY'S FIRST
STATEMENT'S shape: a call whose argument list is not parameter-shaped, followed by another
brace-led statement.

Fixed by `parenLooksLikeParamList`, called before the method-shorthand arm commits: it walks
the parenthesized run and requires every top-level comma-separated item to start with an
identifier or `...`, tracking paren/brace/bracket depth only to step over a parameter's own
type annotation. A call argument that is a string, number, or any other non-identifier-leading
expression now fails this check immediately, so the enclosing `{` reads as a block and each
subsequent `{`-led statement is disambiguated on its own account by the same function.

#### Ablation

Every combination below is a call with a **string-literal argument** as the first statement,
followed immediately by a `{`-led statement, inside the position named. Return type identity
never mattered — the italicised column proves it independent of the container.

| ingredient | outcome (before fix) | outcome (after fix) |
| --- | --- | --- |
| return type: a user record (`Q`) | parse error | runs |
| return type: `i32` (primitive) | parse error | parses (a later type error is the program's own, not a parse error) |
| no return type at all | parse error | runs |
| return type: a generic alias (`Box<T>`) | parse error | runs |
| return type: a union (`Q \| null`) | parse error | runs |
| return type: a nominal `new` type | parse error | parses |
| container: a lambda's return annotation (`(): Q => {`) | parse error | runs |
| container: a getter's body | parse error | parses (reaches the getter's own no-allocate check) |
| container: a bare block statement | parse error | runs |
| container: an `if`/`else` arm | parse error | runs |
| control: first statement is `const s = …` (a statement keyword) | ran (never reached the LPAREN arm) | ran, unaffected |
| control: first statement is a bare identifier | ran (warns, unrelated) | ran, unaffected |
| control: genuine method shorthand `{ add(a,b){…} }` | ran | ran, unaffected |

Two narrower shapes were found and are **not** closed by this row, because they are not the
filed defect's family — no parenthesized argument the misdetection can see is ever
non-identifier-shaped: a call with **zero arguments** (`foo()`) and a call whose sole argument
is a **bare identifier** (`print(n)`), each followed by a brace-led statement, still misparse
before and after this fix (`parenLooksLikeParamList` cannot tell an empty or one-identifier
argument list from an equally-shaped parameter list without deeper, non-syntactic context).
Neither regressed — both already misparsed on master before this row.

#### Grading list

The four `looksLikeObject` call sites (function/getter/lambda body, statement position, and
both `if`/`else` arms) all share the one lookahead fixed here, and all four are exercised in
the fixtures. `tests/vl_fmt_test.ts`'s object-method-shorthand test (a disjoint code path,
`parseObjLit`'s own shorthand arm) still passes unmodified — this row never touched it.
