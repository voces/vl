### D1799 — the covariant-write analysis does not run at a monomorphization pin, so a write through a generic list parameter is check-clean and the write is silently lost

**check-clean silently wrong · filed 2026-09-07 against master `0c76469bd`**

Repro:

    type Circle = { r: i32 }
    type Sq = { s: i32 }
    type Shape = Circle | Sq
    function poison<T>(self: T[], other: T[]) {
      other.push(self[0])
    }
    const shapes: Shape[] = [{ s: 1 }]
    const circles: Circle[] = [{ r: 7 }]
    shapes.poison(circles)
    print(circles.length)
    // vl check: rc 0.  vl run: exits 0 and the push is lost — no trap, no diagnostic.
    // PRINTS 1

#### Mechanism

**The analysis DOES run at the pin — the gate misreads its answer.** An instrumented
checker prints the whole chain for the witness:

    D1799-ASK       root=[circles] fr=-1             the predicate IS asked
    D1799-HASWRITE  YES                              the program does contain a write
    D1799-GROWCALL  calleeRoot=[] pushIntoNamed=no   the UFCS callee spells no name
    D1799-ANS       root=[circles] ans=2             so the closure answers UNKNOWN
    D1799-UFCSARG   got=Circle[] expected=Shape[] -> admit

Two rungs, and the second is the defect. `cwGrowCall` reads `covarRootName(n.callFn)`,
which is `""` for a UFCS member callee, and the call is not a `push` into a named receiver
either — so it returns `2` before reaching the argument loop. The set never grows from
`circles` to `other`, `cwWrites` never sees `other.push(self[0])`, and the closure
correctly answers **unknown**.

`covarWriteThrough` then gates on `covarValueWriteState(root, rootFr) != 1`, so **unknown
falls through as "nothing writes it"** and the covariant assignment is admitted. Its
sibling asker states the opposite convention in its own comment — "An unknown write state
(2) keeps the refusal" — so one column has two readers with opposite defaults, and the
permissive one is on the soundness path.

The two faces are one ingredient apart, and the direct spelling never reaches this code at
all: it refuses earlier, at the push site, where the parameter types are concrete (the
probe prints no `D1799-ASK` for it).

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the type parameter — `poison(self: Shape[], other: Circle[])` | loud check reject, `push: cannot add Shape to Circle[]` | **yes** |
| the covariance — pass a `Shape[]` as `other` | runs, and the push lands | **yes** |
| the WRITE — read `other` instead | runs correctly; reading a narrower list as wider is sound | **yes** |
| `readonly` on the parameter — `other: readonly T[]` | loud refusal naming the view | no |
| the UFCS spelling — `poison(shapes, circles)` written directly | still silent, same `ans=2` | no |

The last row is the workaround and the reason `std:array`'s `extend` declares `other` as
`readonly T[]`: a read-only parameter cannot reach this hole at all.

#### Grading list

`tests/cases/std/array-extend.vl` must keep running — `extend` is the shape this row is
about, with the `readonly` spelling that avoids it. `tests/cases/unions/list-covariant-readonly-view-write-rejected.vl`
must keep refusing: the DIRECT spelling's analysis is not what is broken. When this row
closes, the generic spelling above becomes a loud check reject and the `readonly`
declaration becomes belt-and-braces rather than the only guard.

**Three rungs, and closing the row needs the first two at least.**

1. **`cwGrowCall` declines the UFCS callee.** Teaching it `cwUfcsDeclOf` (the member's
   PROPERTY names the function, the receiver fills parameter 0, so an argument at `k` is
   parameter `k + 1`) moves the witness from `ans=2` to `ans=1`, and the distilled corpus
   moves **0 cells**. But the edge has a SIBLING: `cwArgParamName` reads the same
   argument→parameter question for the claim pass, and its header records the invariant that
   the two "read this one resolver, so neither can outrun the other" (D1658). Teaching only
   the closure breaks that, so both move together or neither does.
2. **`covarWriteThrough` returns 0 even at `ans=1`.** Past the write state it still requires
   `covarValueSplitStorage` or `covarValueTwoUnions`, and this shape — a plain struct row
   into a boxed union, written through at a pin — answers neither, so the refusal never
   fires. Measured: with rung 1 applied the witness still runs and prints `1`.
3. **`covarWriteThrough` reads an UNKNOWN write state as "no write"** (`!= 1` returns 0)
   while its sibling asker's comment states the opposite convention — "An unknown write
   state (2) keeps the refusal". Making the two agree is sound by default and closes every
   unknown-shaped hole at once, but it would refuse covariant assignments that run today, so
   it is a ruling with a corpus reading behind it, not a fix.
