### D3045 — a loop variable forwarded through a second generic at a `string[]` pin builds invalid wasm

**closed 2026-09-28 — the filed repro prints `[p]` `[q]` · was check-clean invalid wasm, clause 1, the same on master `6c2dafc0b` · closed with [D3044](D3044.md): one mechanism, a forwarded argument pinned its callee at the forwarder's own type parameter · fixture `tests/cases/generics/loop-var-forwarded-through-generic.vl` · filed 2026-09-28 against master `3a71bb1f9`**

Repro:

    function inner<U>(x: U) { print("[\{x}]") }
    function mid<T>(l: T[]) { for e in l { inner(e) } }
    function outer<T>(l: T[]) { mid(l) }
    const v: string[] = ["p", "q"]
    outer(v)
    // vl check: rc 0.  vl run: invalid module inside `mid$m0`

Want:

    [p]
    [q]

#### Mechanism

The string twin of [D3044](D3044.md), and the same mechanism: `mid`'s instance, built from
`outer`'s call, banked `outer`'s `T[]` as its parameter's type, so its loop variable bound the
`i32` default and `inner` was cloned at `i32` while handed a string ref. An `f64` list is the same
invalid module (`expected i32, found f64`).

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `mid(v)` called directly, no `outer` | prints `[p]` `[q]` | **yes** (the forwarding) |
| `inner(l[0])`, no loop | prints `[p]` | **yes** (the loop variable) |
| `print(x)` in `inner` | invalid wasm | no |
| `function inner(x)`, a hole | invalid wasm | no |
