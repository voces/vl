### D2715 — a function value returning a union of two same-struct maps, delivered as one returning one of them, traps at the call

**closed · now a loud check reject: the adapter's result shares a map that may be an `A` at the wider value type, which the record-covariance ruling allows only a fresh value · fixture `tests/cases/closures/error-fn-value-map-union-result-shared.vl` · was loads then traps · found in the #3198 review · filed 2026-09-26 by the NR lane, closed 2026-09-30 against master `3291e99e1`**

Repro:

    type A = {[string]: string}
    type B = {[string]: string | null}
    function uA(): A | B {
      const a: A = Map()
      a["k"] = "x"
      a
    }
    const f: () => B = (): A | B => uA()
    print(f().length)
    // vl check: rc 0.  vl run: wasm trap: indirect call type mismatch

#### Mechanism

The checker accepted `() => A | B` as `() => B` because the result is assignable, while the
lambda's signature returned the union box and the call site's `$fnsig` the bare map. The
[D3073](D3073.md) adapter now calls the lambda and delivers its result as `B`, and that delivery
is the record-covariance one: a map that may be an `A` taken at `{[string]: string | null}`
could have `null` stored into it through the wider handle. A call through a function value is
not provably fresh, so the check refuses it, as it refuses the same delivery written by hand.
