### D15533 — two different generics written by `.set` as record fields of one un-annotated map, called at their types, reach no instance

**loud emit reject · `vl check` rc 0 · `a generic function taken as a value reaches no call that fixes its type` · clause 2 · the `.set` spelling of D15493, closed for the index store · a record literal `.set` stores into a map of records is not admitted by the tag rule, and the call's argument adoption retypes its function field to a closed instance · filed 2026-11-07 against master `2edf7d1c`**

Repro:

    function id<T>(x: T): T { x }
    function k2<T>(x: T): T { x }
    const b = Map()
    b.set("k", { f: id })
    b.set("j", { f: k2 })
    const bj = b.get("j")
    if bj != null {
      print(bj.f(3))
      print(bj.f("t"))
    }
    const bk = b.get("k")
    if bk != null { print(bk.f(true)) }
    // vl check rc 0.  vl run: emit error: a generic function taken as a value reaches no call that fixes its type

Want:

    3
    t
    true

#### Mechanism

The map's record field joins `{id, k2}` at the `.set` pin as it does at an index store
(`elabSlotRecJoinTy`), but four layers stand between that and a tagged set, measured on branch
`claude/mrec-set-admit`:

1. the tag rule admits a record literal into a map of records only through an index store
   (`ftRecIntoMapSlot`); a `.set` argument needs the same admission (`ftRecIntoMapSet`);
2. `ftSlotOp` takes a map's entry methods for maps of functions only (`ftHoldKind` 3 and 5), not a
   map of records (8);
3. `ftScan`'s slot-write join runs the scalar `ftJoinAt` on the `.set` record literal, which only a
   list of records (6) sends through `ftRecWriteJoins`;
4. the second literal's `k2` field ends typed `(i32) => i32`, a closed instance, outside every set:
   the `.set` argument's adoption (`adoptFnNameAt` and the call argument's re-check) retypes it, and
   growing it to the slot's joined record afterwards does not hold.

With 1–3 built, the plan fails only on 4: the record join finds no leaf for `k2`.
