### D4490 — the wasm-backed LSP reported and read columns in UTF-8 bytes where the protocol counts UTF-16 code units

**closed — `lsp/src/utf16Columns.ts` converts every column at the seed boundary in `lsp/src/wasmChecker.ts`, both directions, per module text; the server now advertises `positionEncoding: "utf-16"` · graded by `tests/lsp_utf16_columns_test.ts` (2-byte, 3-byte and surrogate-pair prefixes) · filed 2026-10-13 against master `0a6bd6ccc`, found by #3696 · was an editor-only defect: the CLI's own columns are bytes by design and the program below always ran**

Repro:

    const s = "é—"
    const n: i32 = 1
    print(n)
    print(s)

Want:

    1
    é—

#### Mechanism

The seed counts a column in UTF-8 bytes; LSP positions default to UTF-16 code units. The
wasm checker handed seed columns to the editor unchanged and handed cursor columns to the
seed unchanged, so on any line with a non-ASCII character before the position every
diagnostic, semantic token, inlay hint, lint range and declaration extent shifted right by
the byte excess, and every cursor query (hover, definition, references, signature, scope,
completion) landed short of the name it was aimed at. The CLI witness above runs either way;
the defect is only observable through the LSP, so its gradeable witness is the test file,
which puts `const s = "é—"; const t: i32 = s` on one line and wants the diagnostic at
UTF-16 character 31 (master reported 34).

#### Grading list

`tests/lsp_utf16_columns_test.ts` — type-error range, lexical and semantic tokens (comment
length included), hover/definition/references/signature/scope, inlay hints, a lint start,
declaration extents, cross-file import sources, module surface and references in the entry,
and a dependency's diagnostic converted against the dependency's own text.
