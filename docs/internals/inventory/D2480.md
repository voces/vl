### D2480 — a UFCS call inside a lambda is treated as capturing the name of an already-closed block's local

**loud emit reject · clause 2 · found in review of #3148 against master `0a0d24ac9`, filed 2026-09-25**

Repro:

    function name(self: i32): i32 { self }
    function main() {
      {
        const name = 10
        print(name)
      }
      const f = () => 5.name()
      print(f())
    }
    main()
    // vl check: rc 0.  vl run: emitProgram: captured variable not found in enclosing frame

#### Mechanism

Not ablated to a rung. The lambda `f`'s body makes a UFCS call `5.name()`, which — after D2384's
positional fix — resolves to the module function `name`, not to the already-closed block's
local. Something upstream of that resolution still treats `name` as a free variable the lambda
must capture, because a binding of that name was seen earlier in the enclosing frame; the
block's `const name = 10` does not outlive its block, so the lambda's capture step asks the
frame for a cell that is no longer there. D2384's own mechanism names this gap: its fix
positions a UFCS call that mints "past the frame's body" directly, but "any other node past the
body" — a UFCS call nested inside a further lambda — keeps the old, name-only ladder.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the UFCS call (`name(5)` direct instead of `5.name()`) | runs, prints `10` then `5` | **yes** |
| the block's binding renamed away from `name` (e.g. `x`) | runs, prints `10` then `5` | **yes** |
| the lambda (`print(5.name())` written inline instead of through `f`) | runs, prints `10` then `5` | **yes** |
