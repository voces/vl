### D1100 — a `??`-moved function delivered through a CONTAINER (struct field, array element, wrapping lambda) is check-clean invalid wasm: the family mints, the delivery does not follow

**closed 2026-09-03 at FOUR of its five positions — the struct FIELD, the array ELEMENT, the
array of STRUCTS and the returned VALUE all RUN · was check-clean invalid wasm, clause 1 ·
the fifth (a wrapping LAMBDA) ablates to a DIFFERENT mechanism and is [D1420](#d1420) ·
ZERO corpus cells · fixture
`tests/cases/types/coalesce-merged-row-fn-value-container-delivery.vl` · found 2026-09-02
while closing [D1090](#d1090), as the half its position matrix does not reach**

D1090 closed every position where the function VALUE's identity is knowable from bindings,
parameters and returns. These five are the positions where it is knowable only from a CONTAINER
read, and they need the delivery wired rather than the analysis widened.

Repro (prints `9` then `7`; before the fix `vl check` rc 0 and the module did not load):

    function src(p: {r: i32}): {r: i32} | null {
      p
    }
    function rd() {
      const o = {f: src}
      const v = o.f({ r: 9 }) ?? { r: 0 }
      print(v.r)
      const g1 = src({ r: 7 }) ?? { r: "s" }
      print(g1.r)
    }
    rd()

Before the fix: `Invalid input WebAssembly code … type mismatch: expected i32, found
(ref $type)` in `rd`.

#### How it closed — the gate LAST, and both halves per position

**THE DELIVERY WAS THE MISSING HALF, AND IT IS TWO ANSWERS PER POSITION, NOT ONE.** A call
through a container needs the delivered function's own interned `$fnsig` (or the
`call_indirect` signature-checks against the DECLARATION's arrow and traps), and it needs the
merged RETURN ROW (or the local the `??` binds is declared at the pre-merge row and
`br_on_non_null` disagrees with its own block result). Both are `anonLeafRetRowOf` /
`cloSigKeyExt` answers the emitter already had for a BINDING; what was missing was a resolver
from each container to the function it holds.

| container | the `$fnsig` | the return ROW |
| --- | --- | --- |
| struct FIELD `o.f(…)` | `cloCallSigKey`'s `Member` arm, ahead of its divergence override | `structIndexOfExpr`'s `Member` arm, through `anonLeafRetRowOf` |
| array ELEMENT `a[0](…)` | `anonLeafArrElemSigKey`, ahead of `cloArrSlotSigKey` | `structIndexOfExpr`'s new `Index` arm |
| array of STRUCTS `a[0].f(…)` | the FIELD row above (the receiver is an index) | the FIELD row above |
| returned VALUE `pick()(…)` | `cloCallSigKey`'s new `Call` arm | `structIndexOfExpr`'s new `Call` arm |

**AND THE GATE IS NOW AN ATTRIBUTION QUESTION, NOT A KIND ONE.**
`anonLeafCalleeIsFnValue` keeps [D1401](#d1401)'s receiver allow-list and adds: a callee whose
delivered function this pass can NAME is not an unattributable indirect call. The resolver
(`anonLeafDeliveredFnName`) is the collect-pass twin of the three emit-side ones, and it
refuses exactly what they cannot serve — a LAMBDA in the field (no name to key the moved
`$fnsig` on), two different functions in one container, a receiver built where it cannot
follow. Refusing keeps the veto, which is the safe direction.

**THE ONE UNUSED HOF PARAMETER THAT TURNED THE FIX INTO A DIFFERENT MISCOMPILE.**
`cloCallSigKey`'s `Member` arm carries an INTERNED-DIVERGENCE OVERRIDE — prefer the callee
node's arena functype when the syntactic key names no interned `$fnsig`. With the delivery
wired but the override still first, ONE unused `function hof(cb: ({r: i32}) => {r: i32} |
null)` anywhere in the module interns the NARROW arrow, the override fires, and the
`call_indirect` gets the pre-move functype while the row redirect has already moved:
`expected (ref null $type), found (ref null $type)`, disassembled at `call_indirect (type $12)`
against a merged `(ref $2)` local. Ablated: an unrelated `{r: i32}` annotation does NOT do it,
and `pick` returning a DIFFERENT function does — so the ingredient is the ARROW annotation,
not the function. A moved function's own key is now authoritative ahead of the override.

**THE RESOLVER IS NAME-KEYED, WHICH IS A BOUND AND IS PINNED AS ONE.** The collect pass has no
scope, so the gate answers per NAME and requires every binding of that name to deliver the
SAME function — D1090's rule for a callback parameter, one holder over. Two same-named
bindings holding DIFFERENT containers answer "" and the whole family declines. That is not
hypothetical: the first draft of this row's fixture reused `a` for both the closure array and
the array of holders, and it pinned nothing — every cell in the module, including the
unrelated struct-FIELD one, went back to invalid wasm, because the veto is a WHOLE-PROGRAM
question.

* **THE FIVE, ONE PROGRAM EACH, ALL `vl check` rc 0 — graded on an 18-cell matrix (the five,
  a NO-MERGE twin of each, D1090's three closed controls, and the field call whose result is
  not the `??`'s operand). `runs 12 of 18 -> 17 of 18`, 0 runs lost, 0 silent left except the
  fifth.**

  | how `src` reaches the call | before | after |
  | --- | --- | --- |
  | struct FIELD (`{f: src}`, called through it) | check-clean invalid wasm | **runs `9`** |
  | array ELEMENT (`[src]`, called through it) | check-clean invalid wasm | **runs `8`** |
  | array of STRUCTS (`[{f: src}]`) | check-clean invalid wasm | **runs `6`** |
  | calling a RETURNED value directly (`pick()({r: 4})`) | check-clean invalid wasm | **runs `4`** |
  | a field call BESIDE the merge (`o.f(…) != null`) | check-clean invalid wasm | **runs `true`** |
  | wrapping LAMBDA (`apply((q) => src(q))`) | check-clean invalid wasm | unchanged — [D1420](#d1420) |

  Every NO-MERGE twin and all three of D1090's controls run on both sides.

* **IT IS DELIVERY, NOT ATTRIBUTION, AND THAT IS MEASURED.** Forcing
  `anonLeafAnyIndirectCall` to `false` — i.e. granting the family every attribution it could
  ever want — does NOT make them run. They move instead to `wasm trap: indirect call type
  mismatch` (the lambda and the returned value), a DIFFERENT `expected (ref null $type), found
  (ref null $type)` (the field and the nested element), and `emitProgram: function-value call
  arity has no interned signature` (the array element). So the missing half is the stored
  closure carrying the moved `$fnsig` and the literal argument at the `call_ref` being built at
  the merged row — the same two halves D940 built for a parameter slot, one holder over.

* **THE ORDER IS D965'S AND D1090 ALREADY PAID FOR HALF OF IT.** Wire each delivery FIRST, then
  admit the position; admitting it first is what turns one invalid module into another, and the
  forced-veto experiment above is the cheap way to see that before writing any of it.

* **THE ATTRIBUTION SIDE ALSO HAS A PRICE THAT IS ALREADY MEASURED.** Teaching
  `anonLeafCalleeFnName` to follow a CALL in callee position (which is all `pick()({r: 4})`
  needs) makes the compiler's own self-compile stop finishing: the resolver is a whole-arena
  scan and a module is full of `x.push(…)` member calls. It was written, measured and reverted;
  whatever closes this position has to carry an early-out, the way `anonLeafNarrowUseMark` and
  `anonLeafCloBindMark` do.

* **RE-MEASURED 2026-09-02 ON A 13-CELL DELIVERY MATRIX, and the veto's own arm is now named per
  cell.** The five positions plus D1090's three closed controls (argument / binding / annotated
  binding) plus a NO-MERGE twin of each of the five. Standing: **5 invalid, 8 runs** — and every
  no-merge twin RUNS, so the container delivery itself is fine and the merge is the whole
  ingredient. `anonLeafAnyIndirectCall` vetoes four of the five through its `else { return true }`
  arm (a non-`Ident` callee: `o.f(…)` is a `Member`, `a[0](…)` an `Index`, `pick()(…)` a `Call`);
  the wrapping LAMBDA is vetoed one level in, because the argument is not a plain function NAME
  and `anonLeafParamFnTargetAt` answers "".

* **AND LAYER TWO IS THE `??` RESULT'S OWN ROW READER, which is a new fact.** With the veto forced
  off, the struct-FIELD cell's `call_indirect` DOES use the moved functype — and the local the
  `??` binds is still declared at the PRE-merge row, so `br_on_non_null` disagrees with its own
  block result (`expected (ref null $type), found (ref null $type)`, offset 0x1a3, disassembled).
  So closing this needs the merged-row redirect at an ELEVENTH owner — the local bound to a `??`
  whose left operand is a field-closure call — beside the stored closure carrying the moved
  `$fnsig`. That is why narrowing the veto alone is not the fix, and it is the D965 order again:
  build the lowering, wire every delivery, THEN narrow the gate.

* **RE-GRADED 2026-09-03 ON A 15-CELL MATRIX, and the five positions are exactly as filed** —
  four check-clean invalid wasm (struct FIELD, array ELEMENT, array of STRUCTS, wrapping
  LAMBDA), the fifth (`pick()({r: 4})`) a loud `emitProgram: function-value call arity has no
  interned signature` at the spelling graded, and every no-merge twin plus both of D1090's
  closed controls RUNNING. **The veto arm this row names has since been NARROWED** — a
  `Member` callee over a LIST / MAP / PRIMITIVE receiver no longer counts as an indirect call
  ([D1401](#d1401)) — and that narrowing moves NONE of these five: a struct receiver is exactly
  the case it keeps refusing, which is what makes it a control for this row rather than a
  partial close of it.

* **A CANDIDATE THAT ADMITS THE STRUCT RECEIVER WAS BUILT, MEASURED AND REFUSED (2026-09-03),
  and its price is the reason.** One line — `if o is TyObj { return false }` in
  [D1401](#d1401)'s allow-list — passes all nineteen gates, loses ZERO `runs`, and buys ONE
  cell: a field-closure CALL whose result is not the `??`'s left operand
  (`print(o.f({r: 3}) != null)` beside a merge elsewhere) goes SILENT -> runs. It does NOT
  close this row. The FIELD and array-of-STRUCTS cells move from
  `expected i32, found (ref $type)` to `expected (ref null $type), found (ref null $type)` —
  layer two, this row's own eleventh owner, reached but not served — so one invalid module
  becomes a differently invalid one, which is exactly what admitting a position before wiring
  its delivery does. The array-ELEMENT, wrapping-LAMBDA and returned-VALUE cells are vetoed by
  other arms and do not move at all. Take it as the SECOND step, after the merged-row redirect
  lands; taking it first buys one cell and hides the layer-two message that names what is left.

**THE FIFTH POSITION IS NOT THIS ROW'S MECHANISM, and the ablation says so.** The wrapping
LAMBDA fails identically when the lambda is replaced by a NAMED relay, and identically again
when the relay is called DIRECTLY with no function value anywhere
(`function mid(q) { src(q) }`, `mid({r: 5}) ?? {r: 0}`) — so neither the lambda nor the
delivery is the ingredient. What is: the relay's own return row does not follow the move its
BODY's call already made. Filed as [D1420](#d1420), unmoved by this fix, identical on the
pre-fix seed.
