### D15604 — [CLOSED 2026-11-09] a `const` lambda of a generic encloser, handed to `F` and `G` of one call, has no pin for either parameter

**closed 2026-11-09, runs and prints `4`, `y`, `4`, `3`, `w`, `y`, `w`, `3` · was loud emit reject, clause 2, `vl check` rc 0, then `emitProgram: monomorphize: unsupported argument type for `a` in a call to `midTwo`` · D15601's neighbour · filed 2026-11-09 against master `ee306138` · closed in `monoPinAnnotatedParam` (emit_mono.vl): the bare-only arm that pins a parameter at the elaboration's own closed type now takes a hole lambda (`monoIsHoleLamArg`) as well as a declared generic · fixture `generics/capturing-const-lambda-to-two-type-params.vl`**

Repro:

    function midTwo<F, G>(a: F, b: G) {
      print(a("y"))
      print(b(3))
    }
    function outerTwo<U>(u: U) {
      const same = (k) => {
        print(u)
        k
      }
      midTwo(same, same)
    }
    outerTwo(4)
    outerTwo("w")

Want:

    4
    y
    4
    3
    w
    y
    w
    3

#### Mechanism

`F` and `G` are two type parameters, so D15598's join of one type parameter's parameters does
not apply; each parameter holds the one lambda at its own signature. The elaboration closes
each parameter on its own (`elabCallParamTyOwn` gives `(string) => string` for `a`), but mono's
arm that reads it took only a read naming a declared generic (`monoNamesDeclaredGeneric`). A
`const` lambda binding is none, so `a` fell to the hole-generic pin, which found no flow, and
then to the refusal.
