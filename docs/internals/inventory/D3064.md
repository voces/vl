**closed 2026-09-28 — the witness prints `b` · was check-clean silently wrong · `monoPinnedTyOf` reads a hole instance's list literal, element read and function-value call at the instance's hole binding, which the parameter binding `monoPinBodyLambdas` walks with does not name · grid rows graded against master `d408f2da4`, 0 runs lost · fixture `tests/cases/generics/hole-list-literal-in-any-position.vl` · first filed as: check-clean silently wrong · clause 1 · found by the #3270 review (`rv3270-q7k2/g2` `I_holelit_*`) · invalid wasm at the `string` and `f64` pins · the same on master `614fe177c` · filed 2026-09-28 against master `614fe177c`**

Repro:

    type AB = "a" | "b"
    function g(x) { const y = x; h([y, y]) }
    function h<W>(w: W[]) { print(w[1]) }
    const v: AB = "b"

    // vl check: rc 0.  vl run: PRINTS 0

Want:

    b

#### Mechanism

A hole instance shares its template's expression nodes, so a list literal of the parameter, an element read and a call of a function value keep the recorded type over the hole's variable. `monoPinBodyLambdas` re-types such nodes through the instance's binding, but a hole function's binding names its type parameters, of which it has none; the hole's own binding (`monoHoleBinding`) was read only for a binding's initializer and a for-in iterable. `monoPinnedTyOf` now substitutes through the hole binding too, for those three node kinds, so the literal builds at the pin wherever it stands. A record-element list is left to the rows its literal collects, and a method call's result to its receiver.
