### D15099 — two union arms of one field set with a map field trap the compiler when a struct holds one

**closed 2026-11-03 by lane column-G1 · runs, prints `9` · was a compiler trap (`vl check` rc 0, then the seed's `out of bounds array access`, exit 70), clause 1, live on master `cbb7e2b90` · `variantFieldElemName` read the struct table's `sFieldElemName` at an arm field's index, and before `armsAdopted` the arm's fields live in the arm staging table, so the twin check `collectS` runs for `QD.d` read past the end of a table that does not hold them; it now reads `armFieldElemName()`, the accessor that follows the arm table across its adoption and is the same array after it · closed beside [D15097](D15097.md), whose early intern also keeps this read from being reached · fixture `tests/cases/unions/struct-holding-arm-with-map-field.vl` (`QG`) · found closing D15097**

Repro:

    type A = { n: i32, g: Map<string, string> }
    type D = { n: i32, g: Map<string, { r: i32 }> }
    type P = { m: i32 }
    type U = A | P | D
    type QD = { d: D }
    const gd: Map<string, { r: i32 }> = Map()
    gd.set("k", { r: 9 })
    const qd: QD = { d: { n: 1, g: gd } }
    print(qd.d.g.get("k")?.r ?? 0)

Want:

    9

#### Mechanism

The seed built with `--names` on master's source traps at
`variantFieldElemName ← uFieldMapShape ← variantStructHeapTwinAt ← fieldCodeOfSpelling ←
fieldTypeCode ← collectS`. The twin check asks for the arm's map value name by flat field
index, and `variantFieldElemName` indexed `sFieldElemName`, which `collectS` has just reset.
