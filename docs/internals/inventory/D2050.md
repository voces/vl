### D2050 — a loop `continue` or `break` inside a value-position `if` arm branches one frame short, because the result-typed `if` frame is not counted

**check-clean invalid wasm · `vl check` rc 0, then the module fails to validate inside `f`, clause 1 · filed 2026-09-22 against master `48a295c72`, found reviewing #3032 (D1990), which leaves it unchanged**

Repro:

    function f(n: i32): i32 {
      let acc = 0
      for i in 0 to 3 {
        const v = if i == 1 { if n == 2 { continue }; 5 } else { 7 }
        acc = acc + v
      }
      return acc
    }
    print(f(2))
    // vl check: rc 0.  vl run: invalid module — `type mismatch: expected i32 but nothing on stack`

#### Mechanism

A value-position `if` lowers through `emitIfExprAs` (and `emitIfExprRef` for a ref result),
which open a result-typed `if` frame without `ctrlEnter()`, where every statement-position
`if`, loop and union-sink `if` counts its frame. A `continue` or `break` in an arm computes its
`br` depth from `ctrlDepth`, so it lands one frame inside its target. The `break` spelling shows
it plainly: the disassembly is `br $label`, the loop head, where the `break` means the block
around the loop. That is a `continue` that skips the loop's increment, so the program never
ends. The `continue` spelling lands on the value `if`'s own frame, which expects an `i32` that
nothing pushed.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `continue` → `return 9` | runs, prints `9` | **yes** (a branch to a loop frame) |
| `continue` → `break` | loads and never terminates (`br` to the loop head) | no — same defect, worse symptom |
| the arm's statements on two lines instead of `;` | still invalid wasm | no |
| the `if` in statement position (`let v = 7; if i == 1 { if n == 2 { continue }; v = 5 }`) | runs, prints `21` | **yes** (the value position) |
