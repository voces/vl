### D10520 — a generic's typed binding column carries the FIRST call's map type into a later call whose inline record argument holds a different map

**runs today and must keep running · prints `7`, `true` · the spelling path binds `T` right at both calls; the typed column (`letBT`, and the `monoSubstInst` return built from it) binds the second call's `T` to the first call's `{[i32]: i32}` (or `{[i32]: boolean}`, in the other order) · latent: the instance is minted from the spelling, so nothing reads the wrong row yet · it becomes clause 1 the day C1 step 1 mints instances from the typed column · found by the C1 step-1 probe ([render-parse residue](../render-parse-residue-2026-10.md) §C1) · filed 2026-10-22 against master `ba14205a8`**

Repro:

    function g<T>(b: { m: T }): T { b.m }
    const v: {[i32]: i32} = Map()
    v[3] = 7
    print(g({ m: v })[3] ?? -1)
    const s: Set<i32> = Set()
    s.add(7)
    print(g({ m: s }).has(7))

#### Mechanism

At the second call, the pin spelling is `{m:{[i32]:boolean}}` and `tvV` binds `T` to
`{[i32]:boolean}`. But `monoBindCols` binds `T` to `{[i32]:i32}`, and the return's `sub2`
agrees with it, so `letBT` holds the first call's map. The spelling path has the binding
right. The typed column goes wrong before `monoBindCols`, in `pinnedTyIx` or `pinTys` for the
inline record argument. Both maps fill `{m: <map>}`, so the likely cause is the anonymous-row
family: an `#anon` row keyed on field names and codes only.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the first call (`Set` call alone) | typed and spelled agree | **yes** |
| the second call (map call alone) | typed and spelled agree | **yes** |
| the call order (Set first, then map) | disagree the other way | no |
