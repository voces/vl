### D10520 — a generic's typed binding column carries the FIRST call's map type into a later call whose inline record argument holds a different map

**runs today and must keep running · prints `7`, `true` · the typed column's stale binding is fixed: `monoMakeInstanceParams` keeps the argument's own record type when the row's rendering differs from the pin spelling (`monoSpelledRecordLeavesRow`), and the probe's three disagreements on this fixture fell to 0, with byte-identical output · kept as the pin C1 step 1 must keep running · found by the C1 step-1 probe ([render-parse residue](../render-parse-residue-2026-10.md) §C1) · filed 2026-10-22 against master `ba14205a8`**

Repro:

    function g<T>(b: { m: T }): T { b.m }
    const v: {[i32]: i32} = Map()
    v[3] = 7
    print(g({ m: v })[3] ?? -1)
    const s: Set<i32> = Set()
    s.add(7)
    print(g({ m: s }).has(7))

#### Mechanism

At the second call, the pin spelling is `{m:{[i32]:boolean}}` and `tvV` binds `T` to
`{[i32]:boolean}`. But `monoBindCols` binds `T` to `{[i32]:i32}`, and the return's `sub2`
agrees with it, so `letBT` holds the first call's map. The spelling path has the binding
right. The typed column went wrong in `monoMakeInstanceParams`: the pin type was replaced by
`anonHandleTyIx`, the first row of the argument's layout. A layout keys a map field by its rep,
so `{m: Set<i32>}` and `{m: {[i32]: i32}}` share a row. The fix keeps the argument's type when it
renders as the pin spelling and the row does not.
