### D9620 — an un-annotated parameter whose body meets an `i64` literal refuses an `i32`-range argument, where the annotated parameter widens to `i64`

**loud check reject · clause 2 · CAPABILITY: `function f(x: i32) { x + 5000000000 }` prints `5000000002`, and so does the direct `a + 5000000000` · found closing [D9560](D9560.md) · present on master `95725e040` · filed 2026-10-22 against master `95725e040`**

Repro:

    type S = 1 | 2
    const a: S = 2
    function f(x) { x + 5000000000 }
    print(f(a))
    // vl check: argument 1: S cannot hold the 64-bit operand it meets (the body of `f` computes with it and a 64-bit value)

Want:

    5000000002

#### Mechanism

The body of an un-annotated parameter is checked once with `x` a hole, and an `i64` literal
beside it records `OP_LITFIT` (D2712, D3426), which a call refuses when the argument is
narrower than 64 bits: the body alone cannot see the width, so the rule assumed the result
must fit the argument's type. That holds for an annotated `: T` return or a `T`-typed store,
not for an un-annotated return. Since D9560, arithmetic over a hole is a derived hole that
resolves at the pin to the operand's base (`binArithPinTy`, check_union_mint.vl), so the pin
could type `x + 5000000000` at `i64` as the annotated `x: i32` does; a close would admit the
operand where the result reaches no destination typed by the hole.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| the literal union (`const b: i32 = 2`, `f(b)`) | same refusal, naming `i32` | no |
| the argument a bare literal (`f(2)`) | same refusal, naming `i32` | no |
| the annotation `x: i32` | prints `5000000002` | **yes** |
| a lambda `(x) => x + 5000000000`, or `<T>(x: T)` | same refusal | no |
| the argument at `i64` (`1 \| 5000000000` or `i64`) | runs | **yes** |

#### Grading list

The `<T>(x: T): T` spelling must keep refusing: its result is `T`. The lambda and `<T>`
spellings of the repro, and `-`, `*`, `/` with the same literal.
