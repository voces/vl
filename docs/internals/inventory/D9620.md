### D9620 — an un-annotated parameter whose body meets an `i64` literal refuses an `i32`-range argument, where the annotated parameter widens to `i64`

**closed · runs, prints `5000000002` · was loud check reject, clause 2 · CAPABILITY: `function f(x: i32) { x + 5000000000 }` prints `5000000002`, and so does the direct `a + 5000000000` · found closing [D9560](D9560.md) · filed 2026-10-22 against master `95725e040` · closed by typing arithmetic over a hole at `i64` at a narrower pin when its other operand is `i64` (`binArithPinTy`'s `wide`, check_union_mint.vl), so every destination re-asks the widened result, and dropping `OP_LITFIT` for plain arithmetic and comparisons (`binNoteHoleCstr`, check_operators.vl) · fixtures `generics/hole-param-meets-i64-literal.vl` and `generics/error-hole-param-i64-result-into-hole-store.vl`, matrix `hole-i64-literal-arith` (0 → 64 of 66) · with [D9630](D9630.md), [D9631](D9631.md) and [D9632](D9632.md) filed open**

Repro:

    type S = 1 | 2
    const a: S = 2
    function f(x) { x + 5000000000 }
    print(f(a))
    // vl check: argument 1: S cannot hold the 64-bit operand it meets (the body of `f` computes with it and a 64-bit value)

Want:

    5000000002

#### Mechanism

The body of an un-annotated parameter is checked once with `x` a hole, and an `i64` literal
beside it recorded `OP_LITFIT` (D2712, D3426), which a call refused when the argument was
narrower than 64 bits. Since D9560, arithmetic over a hole is a derived hole that resolves at
the pin (`binArithPinTy`). The close records the concrete `i64` operand in the derived hole's
`alt` (`mkBinOpRetTy`, check_leaf_steps.vl; the name carries it, `hdRenderName`), and the pin
types the result at `i64` when the operand pins narrower. A destination typed by the hole (a
`<T>(x: T): T` return, a store back into `x`'s type) then refuses the `i64` at the pin, as the
annotated spelling does. A compound write (`y += 5000000000`) keeps `OP_LITFIT`.

The derived hole was invisible to a generic parameter the same hole binds (`tyParamsApart`
skips derived holes), so `g(x, x + 5000000000)` into `g<T>(a: T, b: T)` recorded no argument
constraint. `tyArithMeetsParam` (check_hole_pins.vl) records it in `argParamsApart`
(check_calls.vl). The same fix makes a literal-union pin refuse `g(x, x + 2)` at `S = 1 | 2`,
which printed `4` on master.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| the literal union (`const b: i32 = 2`, `f(b)`) | same refusal, naming `i32` | no |
| the argument a bare literal (`f(2)`) | same refusal, naming `i32` | no |
| the annotation `x: i32` | prints `5000000002` | **yes** |
| a lambda `(x) => x + 5000000000`, or `<T>(x: T)` | same refusal | no |
| the argument at `i64` (`1 \| 5000000000` or `i64`) | runs | **yes** |

#### Grading list

The `<T>(x: T): T` spelling must keep refusing: its result is `T`. The lambda and `<T>`
spellings of the repro, and `-`, `*`, `/` with the same literal.
