### D2294 — a negation type nested inside a generic type argument is missed when it types an object-literal method-shorthand's own parameter, unlike the identical annotation on a `function` declaration

**closed 2026-09-24 — now a loud check reject, the owner ruling's one sentence (`` `!string` is a
NEGATION …``) · was a loud emit reject (`ref valtype with no interned shape`) after `vl check` rc 0 · found
while adding [D2292](D2292.md)'s fixture · filed 2026-09-24 · fixture
`tests/cases/unions/negation-in-nested-fn-param.vl`**

Repro:

    type Pair<A, B> = { a: A, b: B }
    function mk(n: i32) {
      process(_x: Pair<i32, !string>): i32 {
        n
      },
      base: n
    }
    print(mk(3).base)
    // vl check: rc 0, "Found 0 errors, 1 warning" (only the unrelated unused-parameter hint).
    // vl run: rc 1, "Error: emit error / emitProgram: ref valtype with no interned shape".

The identical annotation on a plain `function process(x: Pair<i32, !string>): i32 { 3 }`
declaration IS caught: `vl check` rejects it at rc 1, "`!string` is a NEGATION, which says
what a value is not …" — see the ablation table.

#### Close

The prediction named the wrong ingredient. The shorthand is scenery: ANY function nested in an
un-annotated function lost the refusal — a nested `function g(_x: Pair<i32, !string>)`, a lambda
parameter, even a bare `!string` there, and a generic arity error the same way — while a
top-level one, or one inside an annotated function, was caught. The return pre-pass
(`inferReturnsPrePass`) checks an un-annotated body quietly and rolls its diagnostics back, and
`resolveAnnotTs` banked the annotation's answer in its name-keyed memo during that pass, so the
real pass hit the memo and never re-raised. The memo now declines to bank a resolution that
raised a diagnostic. The refusal is the design's (the 2026-09-06 ruling), so this row closes at
the loud check reject.

#### Mechanism

`negInAnnotationMsg` is raised at two routes so a rule enforced on one is not one a re-render
walks around (`tsToTyReal`'s `TS_NEG` arm and `nameToTyReal`'s `name[0] == '!'` check, both in
`compiler/typecheck.vl`). The plain-function repro above reaches one of them from the same
generic argument position the shorthand repro uses, so the argument itself is not the missing
ingredient — something about how an object-literal method shorthand's own parameter type gets
resolved (its declaration is parsed by `parseFuncTail` from the shorthand arm of `parseObjLit`,
`compiler/parser.vl`) reaches neither route for a NESTED negation, while a direct (non-generic)
negation on a shorthand parameter IS caught (confirmed: `{ process(x: !string): i32 { 3 } }`
alone, with no generic wrapper, correctly type-errors at the same message). The gap is
specifically a negation ARGUMENT of a GENERIC type annotating a SHORTHAND parameter — not
plain shorthand parameters, and not this exact generic argument at a non-shorthand parameter.

#### Ablation

| ingredient | outcome |
| --- | --- |
| shorthand parameter, `Pair<i32, !string>` (as filed) | check-clean, then emit reject |
| shorthand parameter, bare `!string` (no generic wrapper) | loud check reject — caught |
| plain `function` parameter, `Pair<i32, !string>` | loud check reject — caught |
| the generic argument replaced with `(i32) => i32` (D2292's own fixture) | runs — not a negation, unaffected |

#### Grading list

Any fix must keep the plain-function and bare-shorthand-parameter cases rejecting with the
same message, and must not touch D2292's own fixtures (`tests/cases/parser/call-first-stmt-
then-brace-tail.vl`), none of which annotate a parameter with a negation type.
