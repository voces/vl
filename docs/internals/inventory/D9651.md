### D9651 — a generic stored by `.set` through an un-annotated map parameter, then overwritten at module level with a fixed-type function, reaches no call that fixes its type

**loud emit reject · `vl check` rc 0 · `a generic function taken as a value reaches no call that fixes its type` · clause 2 · found closing [D9591](D9591.md) · present on master `92d03ef36` · filed 2026-10-22 against master `92d03ef36`**

#### Mechanism

Partly traced 2026-10-22 (lane-D9653); not the hole split. `mm` is never called, so
`fsHoleKeys` (fn_split.vl) never sees it, and the split of [D9653](D9653.md) leaves it as it was.
The refusal is `emitIdentNonLocalRead`'s (wasmEmit.vl): `id` has a stub slot and its read
inside `fill` is neither instanced nor in `monoInertValues` (`monoStubValueOk`, emit_state.vl).
The map-value flow cannot note it: `monoFlowMapVals` (emit_mono.vl) gives up on the map once a
write stores `inc`, which names no generic. What pins `id` is the stored value's slot, and it
is order-sensitive: the overwrite before `fill(m)` runs, after it refuses, and a second
`fill(m)` after the overwrite still refuses. Annotating the map
(`const m: Map<string, (x: i32) => i32> = Map()`) or `fill`'s parameter runs, `3`, so the gap
is the pin an un-annotated map parameter takes from a map whose value type a later write fixes.
