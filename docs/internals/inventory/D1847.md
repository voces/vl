### D1847 — a write to a narrowed PROPERTY PATH retires the narrowing instead of re-narrowing to the written member, so the reads after it are at the declared type

**loud check reject · filed 2026-09-07 against master `db7b35248` · the residue
[D1845](D1845.md)'s close named, and the one place the reads-only rule is spelled differently
for a path than for a bare name · clause 2 · 0 corpus cells**

Repro:

    type O = { v: i64 | boolean }
    function f(o: O) {
      if o.v is i64 {
        o.v = true
        if o.v { print(1) } else { print(2) }
      }
    }
    f({ v: 3 })
    // vl check: rc 1, if-condition must be boolean, got i64 | boolean

#### Mechanism

[D1736](D1736.md)'s rule gives a write two effects — retire the fact it falsified, and
re-narrow the place to the member it wrote — and only the FIRST reached the path channel.
`retireNarrowingsForWrite` marks the overlay entry (`npInvBy[i] = atIx`) and banks the place's
DECLARED type at the assignment node, which is what the emitter's `retireNarrowFor` mirrors.
The bare-name arm does more: it shadows the written member in the current scope and banks that
member, which `pushNarrowWriteReNarrow` selects out of the declared set.

So the two spellings of the same program disagree — `if x is i64 { x = true; if x { … } }`
prints `1` and `if o.v is i64 { o.v = true; if o.v { … } }` refuses. The refusal is honest
about what both halves believe, so this is a lost capability and not a rep disagreement; the
`if` and the `while` spellings refuse identically, so it is not a loop question either.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the path (`x = true` on a bare `x`) | runs, prints `1` | **yes** |
| the demanding read (`print(o.v)` instead of `if o.v`) | runs, prints `true` | **yes** |
| the loop (the same body under `while o.v is i64`) | refuses identically | no |
| the two-member union (`i32 \| string \| boolean`, write `"s"`, read `.length`) | refuses; the bare-name twin prints `1` | no |
| a write the narrowing ADMITS (`o.v = 5` under `o.v != null`) | runs, prints `6` — nothing retires | **yes** |

#### Grading list

The four ablation rows, plus `tests/cases/loops/while-body-path-guard-narrows.vl`'s `WRITE`
row (which writes the path and reads nothing narrow after it, so it runs today and must keep
running) and `tests/cases/unions/error-paren-place-write-retires.vl` (the retirement itself,
which a re-narrow must not weaken — its refusal is the read after the write, and a re-narrow
to the WRITTEN member keeps it refusing for a different and equally correct reason).

A close is the path twin of the bare-name machinery, and it is TWO halves or neither: the
checker pushes a fresh `npKeys` entry carrying the written member instead of only marking
`npInvBy`, and the emitter pushes the matching path narrowing where it now only calls
`retireNarrowFor`. The member is already banked at the assignment node, so the second half
reads the same sidecar the bare name does. **Grade the emitted bytes** — a path read at a
member the emitter did not push is check-clean invalid wasm, which is the failure mode D1736's
own close hit before its emitter half landed.
