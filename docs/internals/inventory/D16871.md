### D16871 — one lambda literal pinned at two function types is refused at build, after `vl check` passed it

**closed 2026-11-17 by lane SLOT — the witness prints `5.5` `3`, and J4 the same · each maker call delivered at its own function type is built by the maker's wide twin there, which returns its hole lambda as an instance at that signature (`monoTwinLamInstance`, `emit_mono.vl`), so one literal is no longer pinned at two types · fixture `tests/cases/functions/maker-closure-in-place-at-two-signatures.vl` (H4 and J4) · matrix `plain-maker-hole-lambda-at-two-signatures`: `two_instances` emit refuses → RUNS in both faces · was loud emit reject, breaking the check contract · filed 2026-11-16 against master `8f94d30c2`**

Repro:

    function mk() { return (a) => a + 2.5 }
    function take(a: (a: i32) => f64) { print(a(3)) }
    function half(a: (a: f64) => f64) { print(a(0.5)) }
    take(mk())
    half(mk())
    // vl check: rc 0.  vl run: emit error, `this lambda is handed on at two different function types, and one lambda literal has one signature — bind it once per type, or annotate its parameters`

Want:

    5.5
    3

#### Mechanism

Not traced. The returned lambda literal is pinned in place where each destination's function type
is delivered (`monoDeliverLamLit`); a second pin at another type is refused unless the literal is
an argument of a call that takes an instance per type. The decision is made in emit, so `vl check`
passes the program. The fix that makes it run is lane INIT's per-signature twin build ([D16851](D16851.md) part (b)),
graded on this row's witnesses beside D16851's.
