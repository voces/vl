### D3054 — a literal tree in an i64 join is computed at its own width, not the join's

**check-clean silently wrong · open · needs an owner ruling: is a join a destination? · the same on master `0b618d160` and on #3265 · found by the #3265 review · filed 2026-09-28 against master `0b618d160`**

Repro:

    function f(x: i64) {
      const xs = [x, -(-0x80000000)]
      print(xs[1])
    }
    f(1)
    // PRINTS -2147483648

#### Mechanism

A literal tree adopts 64 bits at a DESTINATION (an i64 binding, return, argument, operator peer
or `as i64`; DECISIONS.md). An array literal's element join and a value `if`'s arm join are not
destinations today: the tree is checked at its own width (i32, where `2147483647 + 1` wraps and
`-(-0x80000000)` is the pattern -2^31), and only the joined VALUE is widened to i64 by
sign-extension. With an annotation the join has a destination and each element or arm adopts
it. Whether an un-annotated join whose other member is i64 should count as a 64-bit destination
is a language question, so this row carries no `Want:`. Recommendation: yes, the i64 member is
the same kind of evidence an operator peer is, and the annotated spelling already reads 2^31.

#### Ablation

| spelling | outcome |
| --- | --- |
| `const xs: i64[] = [x, -(-0x80000000)]` | 2147483648 |
| `const xs = [x, 2147483647 + 1]` | -2147483648 |
| `const v = if c { x } else { 2147483647 + 1 }`, `c` false | -2147483648 |
| `const v: i64 = if c { x } else { 2147483647 + 1 }` | 2147483648 |

#### Grading list

A `match` arm join, a block tail, and a nullable join (`[x, null, 2147483647 + 1]`).
