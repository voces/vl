### D14734 — a forwarder of a hole function whose result joins two of its parameters takes the first parameter's type as its own result

**closed · runs, prints `false` · was check-clean invalid wasm, clause 1 · `g`'s kept-apart join, substituted at the forwarder's own parameter holes, was re-joined there and collapsed to the first hole; members still holes now stay apart over them (`substRejoinApart`), and the instance re-joins them · its 2 corpus cells print their wanted values · filed 2026-10-31 against master `a3c344274`**

Repro:

    function g(a0, a1, k: i32) {
      const r = if k == 0 { a0 } else { a1 }
      return r
    }
    function h(x, y, k: i32) { return g(x, y, k) }
    const x1: boolean = false
    print(h(3, x1, 1))

Want:

    false

#### Mechanism

The checker types the call `h(3, x1, 1)` as `i32 | boolean`, which is right. But `h`'s template
result is the bare hole `?h.0`: the join of `g`'s two parameter holes, carried through `g`'s
result into `h`, collapses to its first member in `h`'s template. The elaboration's instance key
for `h` is `?h.0=i32;?h.1=boolean`, so `elabRetOf` substitutes the result to `i32`, and
`monoInstanceRet` builds `h` returning `i32` while `g`'s instance returns the union box. Making
`elabRetOf` prefer the join of the body's returned values at the instance fixed this witness and
both cells, but moved 7 filed witnesses from runs to invalid wasm and failed 12 oracle cases (list
joins kept apart on purpose): the fix belongs where the hole join collapses, not in the result read.
