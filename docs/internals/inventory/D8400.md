### D8400 — a hole identity called with a `null` argument returns the `i32` kind while its parameter is pinned `nullref`

**closed 2026-10-20 by lane mono-rows · runs, prints `true` · was check-clean invalid wasm · clause 1 · the cause was in the mono pin, not the return-kind rung: an instance whose return expression is a parameter pinned at `null` now takes a synthesized `null` return annotation (`monoParamPinIs`, `emit_mono.vl`) · pins: `tests/cases/generics/hole-identity-null-into-nullable-record.vl` and its annotated twin · present on master `1d64126a7` · found closing [D8361](D8361.md) · filed 2026-10-20 against master `1d64126a7`**

Repro:

    type C = { a: i32, b: i32 }
    function hid(x) { x }
    const nn = null
    const t: C | null = hid(null)
    print(t == null)
    // vl check: rc 0.  vl run: invalid module inside `hid`, expected i32, found nullref

Want:

    true

#### Mechanism

Since [D8280](D8280.md) the hole instance's parameter is pinned `nullref`, but its inferred
return is still the `i32` kind: the instance is emitted as
`(func (param nullref) (result i32) (return (ref.null none)))`. The return-kind rung that maps a
`null` return to `nulnone` reads the checker's recorded return, which for the hole instance is
not `null`, so the result is never re-derived from the pinned parameter. The close is either in
that rung (`emit_collect.vl`) or in the mono pin (`emit_mono.vl`), both outside the lane that
filed this row.

#### Ablation

| ingredient changed | outcome | needed? |

| `function id<T>(x: T): T { x }` | runs | **yes**, the inferred return |
