### D3541 — a literal argument ahead of a typed one binds the type parameter first, so `mix(0.1, x)` with `x: f32` is an `f64[]`

**check-clean silently wrong · clause 1 · found by lane FZ grading D3539's positions · filed 2026-10-03 against master `f6e17953b`**

Repro:

    function mix<T>(a: T, b: T): T[] { [a, b] }
    const x: f32 = 0.5
    const v = mix(0.1, x)
    print(v[1] + 0.1)
    // PRINTS 0.6

Want:

    0.6000000238418579

#### Mechanism

`checkCallOnFuncTy` binds each type parameter at its FIRST argument (first use wins), so a
literal in the first position binds `T` at the literal's default type and the typed `f32`
argument after it widens into that. The swapped call `mix(x, 0.1)` binds `T = f32` and the
literal adapts, printing `0.6000000238418579`. A literal adapts to the value beside it
(the numeric-join ruling), so the order of the arguments should not decide the instance. The
fix is to let a literal-only argument bind last when a non-literal argument binds the same
parameter to a type the literal holds, falling back to today's join when it does not (an
`i32` beside `0.1` must still give `f64`). D3539 covers only parameters bound by literals
alone and leaves this one alone.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the argument order (`mix(x, 0.1)`) | prints `0.6000000238418579` | **yes** |
| the literal (`mix(y, x)`, `y: f64`) | prints `0.6`, both typed and the `f32` widens | **yes** |
| the list result (`T` returned) | same | no |
