#### Mechanism

D15461 hands each parameter back, so the result is one argument's value of the set the parameters
share. With one generic handed to both, that set is the generic's own. With two, it is their
union (D15409's joined set). The check bound `F` from the first argument alone, so the call's
result, and `h`, held `{id}`. Widening the bare-result case of `ftOwnTyParamJoins` to two
joinable generics then has two problems, both measured on 2026-11-05:

1. **The decision does not settle** (`internal: the tag decision after the elaboration did not
   settle`). Only `{id}` was tried, with the union joining it through `ftLateParamOk`. That
   function returns early for a set an earlier round tagged (`ftWas`), before it pushes the joined
   set into `ftSubNeed`, so the rounds alternate `{id}, {dup}, {id, dup}` → `{id}`.
2. **Once settled, `h` called at one type is a wrong answer.** `pick(id, dup, false);
   print(h(3))` printed `3`, because a call through the one-member `{id}` is a direct call to
   `id`.

The close binds `F` to the union of the two sets where the check binds it. A second argument of
another function set rebinds it at a fresh type, as two arms of an `if` join (`elabFnJoinDeepTy`).
The result then holds `{id, dup}`, so (2) cannot arise. The union is tried directly, so (1) does
not arise either, and the `ftWas` early return is left as it is.
