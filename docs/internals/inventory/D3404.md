### D3404 — printing `o ?? b` over an `f64 | null` and a `boolean` is refused by the emitter, not built as the `f64 | boolean` the checker types

**loud emit reject · clause 2 · open · found by the #3317 review (`rv3317-7c184e7a`, P3) · the same on master `8df60e472` · filed 2026-09-30 against master `8df60e472`**

Repro:

    function f(x: boolean) {
      const o: f64 | null = null
      print(o ?? x)
      return 0
    }
    f(3 > 2)
    // vl check: rc 0.  vl run: emitProgram: union atom has no value box

#### Mechanism

A prediction. The checker types the `??` as the join `f64 | boolean` and `print` accepts it,
but the emitter's `??` arm reaches the value-union box path with no box registered for that
join when the result goes straight into `print`, so it refuses. Binding the result first
(`const v = o ?? x; print(v)`) runs, which puts the gap in the unbound delivery, not in the
join itself.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `const v = o ?? x; print(v)` | runs, prints `true` | **yes** (the unbound `print` argument) |
| `x: i32` with `o: string \| null` | the same emit refusal | no |
| generic `f<T>(x: T)` at `boolean` | runs, prints `true` | **yes** (the direct spelling) |

#### Grading list

`o ?? x` as a direct argument to a user function taking `f64 | boolean`, and the
`string | null` left side with an `i32` default.
