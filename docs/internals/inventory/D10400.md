#### Mechanism

Traced, not ablated. `monoFlowLetMapLeaf` follows the stored value through `monoFlowReadElem`
to the `id` inside `{ f: id }` and rewrites the `let`'s reads to `id`. The store's operand
`w0.f` is rewritten in place to the name `id`, at the same node, and that node is never noted
inert, so the map slot, which holds two pins, fails `monoValsInert` and gets no type. The inner
`id` of `{ f: id }` is inert, but for the record slot's reason, so reading the store as inert
because its source is would be unsound wherever the map slot is still called. Tried while closing
D10380/D10381/D10401: a side table of each store's `[operand, source]` pairs, noted when the source
is, fired at neither noting site, because the source is noted inert by the reach analysis
(`value_reach.vl`) rather than by `monoFlowNoteInert`. A fix notes the store operand inert when
every read of the map is rewritten.
