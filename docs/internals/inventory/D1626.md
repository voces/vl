### D1626 — a function value arriving as an UN-ANNOTATED parameter is invisible to both closure resolvers

**loud emit reject · 2 cells (`argument`, `early_return_guard`, un-annotated face) of both `d1623` matrix templates · filed 2026-09-05 against master `8a7b2872`**

Repro:

    function take(a) {
      const v = a
      const g = (m: i32) => (v)(m)
      print(g(54))
    }
    take((n: i32) => n + 1)
    // vl check: rc 0.  vl run: emitProgram: a function-value call statement yields a value
    // the tail-value ladder did not claim

#### Mechanism

Two independent resolvers are asked whether a callee is a function value, and neither can see
through an un-annotated PARAMETER. `nodeTyIsFunc` reads the arena and finds no `TyFunc`
recorded for the binding; `exprIsClosure` walks the syntactic ladder and finds no arm that
claims it. Annotating either end rescues it — the parameter (`a: (i32) => i32`) or the binding
(`const v: (i32) => i32 = a`) — and so does an un-annotated binding whose initializer is a
lambda LITERAL, which is what rules out "un-annotated" alone as the ingredient.

The index spelling reaches the second floor rather than the first: with `const xs = [a]` and
`xs[0](m)` the message is `a call statement's callee is neither a name, a member, nor a
function value`, because `exprIsClosure` also declines. One gap, two messages, and both are
LOUD — D1623's guard makes the non-void case refuse rather than drop, so no spelling of this
is silent.
