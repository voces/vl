### D1626 — a function value arriving as an UN-ANNOTATED parameter is invisible to both closure resolvers

**closed 2026-09-05 · was a loud emit reject · 4 cells (`argument`, `early_return_guard`, un-annotated face) of both `d1623` matrix templates · filed 2026-09-05 against master `8a7b2872`**

Repro:

    function take(a) {
      const v = a
      const g = (m: i32) => (v)(m)
      print(g(54))
    }
    take((n: i32) => n + 1)
    // vl check: rc 0.  vl run: emitProgram: a function-value call statement yields a value
    // the tail-value ladder did not claim

#### Mechanism

**THE ARENA DOES NOT CARRY THE ANSWER HERE, and that is the finding.** The obvious repair —
read the parameter's type the way D1620 read the inferred return — cannot work, because the
checker records no type on the node. Probing the floor this lands on:

    D1626RUNG name=v nodeTyIsFunc(callFn)=F nodeTyIsFunc(unwrapped)=F
              identIsBoundClosure=T cloCallSigKey=[]

Read across, two facts that point opposite ways. `identIsBoundClosure` is **true** — the
syntactic ladder DOES see the binding, through D1608's capture rung and D1621's arena rung on
the initializer. `nodeTyIsFunc` is **false** — the checker propagated no `TyFunc` to the
identifier, so the tail-value ladder (which must run pre-locals and therefore cannot call
`exprIsClosure`) has nothing to ask. And `cloCallSigKey` is **empty**: even with the tail
routed, `emitCallRef` would fall back to the all-i32 arity sig and lower the call at a
functype nobody resolved.

So this row is not one missing rung. It needs the checker to record the inferred parameter
type on the node — or the tail-value ladder to gain a pre-locals-safe closure predicate AND
the sig key to resolve from the same place. Annotating either end rescues it (the parameter
`a: (i32) => i32`, or the binding `const v: (i32) => i32 = a`), and so does an un-annotated
binding whose initializer is a lambda LITERAL, which is what rules out "un-annotated" alone
as the ingredient.

The index spelling reaches the second floor rather than the first: with `const xs = [a]` and
`xs[0](m)` the message is `a call statement's callee is neither a name, a member, nor a
function value`, because `exprIsClosure` also declines. One gap, two messages, and both are
LOUD — D1623's guard makes the non-void case refuse rather than drop, so no spelling of this
is silent.

CLOSED by the second option, without touching the checker: the arena still answers `_` at the
un-annotated face, and the SYNTACTIC key was taught the two hops it was missing. The capture
hop landed first, as D1634's own fix — `calleeCloSigKeySid` re-asks its resolvers in the frame
that OWNS the binding, where the monomorphizer's `PIN_SIGKEY` payload sits on the parameter.
This row owes the other two: `cloCallSigKey` peels parens before dispatching, so a `Paren`
callee reaches the syntactic resolvers at all, and `stmtIsTailValue`'s last arm gates on the
resolved key rather than on `nodeTyIsFunc`, so the claim's warrant is the `$fnsig` the call
will lower at. The two-face reading at the deciding site (`emitFuncBody`'s tail arm) is
`checkerTy=[_] nodeTyIsFunc=F identIsBoundClosure=T cloCallSigKey=[i>i]`, against the annotated
face's `checkerTy=[(i32) => i32] … cloCallSigKey=[i>i]` — the two faces now agree about the REP
while still disagreeing about the TYPE.

The SECOND floor stays refused, and its residue is D1664: an inferred container (`const xs = [a]`,
`const s = { f: a }`) over an un-annotated parameter has no closure element/field kind, which is a
rep question and not a sig-key one.

#### Ablation

Every row is `vl check` rc 0.

| spelling | outcome |
| --- | --- |

| `function take(a: (i32) => i32)` — the param annotated | runs, 55 |
| `const v: (i32) => i32 = a` — the binding annotated | runs, 55 |
| `const v = (n: i32) => n + 1` — a literal, not a param | runs, 55 |

| un-annotated param, parens, but with an explicit `return` | runs, 55 |

Needed: the value arriving as an UN-ANNOTATED parameter AND the callee being a shape the
`Ident` arm does not claim. The last two rows are what separate this row from D1623: the same
un-annotated parameter is fine at the `Ident` callee and in expression position.

#### Grading list

* The five running spellings above, each of which must keep running.
* Both floors: a fix owes the arena resolver and the syntactic one, or one spelling closes
  and its twin keeps the other message.
* `cloCallSigKey` must resolve as part of any close — an empty key is the all-i32 arity
  fallback, so a fix that only routes the tail would lower at an unresolved functype. That is
  what D1623's refuse-don't-drop guard is holding shut, and why every spelling here is LOUD.
