### D16010 — a hole instance's record literal has no elaborated type, so it builds at its minted row, whose field still holds a type parameter

**runs today and must keep running · 1 program: `closures/two-returns-records-of-hole-fns-field-called.vl` · filed 2026-11-12 against master `8bd438de`**

Repro:

    function id1a(a) { return a }
    function id2a(a) { return a }
    function mkA() {
      if 1 > 0 { return { f: id1a } }
      return { f: id2a }
    }
    const ra = mkA()
    print(ra.f(2))
    print(ra.f(2.5))

Want:

    2
    2.5

#### Mechanism

`mkA` is emitted as an instance (`fnInstOrigin >= 0`), because its literals hold hole functions.
`structIndexOfObjCtx` reaches the mint rung (`sLitMintRow`) for `{ f: id1a }`. A debug build at
that rung shows two things:

- `elabNodeTyAt(objIx, fnIx)` is -1: the checker records no elaborated type for the literal in
  the instance;
- the literal's own stamped type still holds the hole.

So no closed type exists to key the row by, and the literal builds at its minted row, whose field
type holds a type parameter. It is the only true instance among the 910 programs lane H's census
counted (`2026-11-12-step7-vkind-uncovered-storage-rows.md`). The other 909 are bodies emitted as
their generic original, which the coordinator ruled a floor. A row-selection rung that reads the
instance's elaborated type before the mint is byte-identical over the sweep, because it never
answers. The fix is checker-side: record the literal's type per instance (step 2, after step 7).
