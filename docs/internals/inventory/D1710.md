    type K = "a" | "b"

Three spellings shared it, all on the un-annotated face and all with a running non-null twin:
`K | null` (the atom niche, code 30), `K[] | null`, and `(K | null)[] | null`. All three now
print their MEMBER, not an atom id.

#### Mechanism

**The design owed a rep, and that was measured before anything was written**: every ANNOTATED
spelling of all three ran at the filing seed, so did the declared `type W = { xs: K[] | null }`,
so did each non-null twin, and so did the struct sibling on the un-annotated face. Only the
anonymous mint's niche refused.

Probed with an `emitFail` at the niche rung, validated on the three failing witnesses (the
struct sibling, which compiles, stayed silent — an `emitFail` probe cannot speak on a program
that works). Three different answers, so three arms:

    PROBE nul-declined code=30 elem=[] ty=[K|null]
    PROBE nul-nocode ty=[K[]|null]        inner=[K[]]        litArr=1
    PROBE nul-nocode ty=[(K|null)[]|null] inner=[(K|null)[]] litArr=0

Code 30 was already COMPUTED and then refused by the admission rule: `anonFieldElemName` had no
code-30 arm, so the union name beside the atom was "" and the gate declined. The two list
spellings had no code at all — D1691's subtraction correctly kept them out of the ref family
and nothing claimed the i32 atom backing they actually use. `tyIsLitUnionArray` and
`tyIsNulLitUnionArr` are the two existing predicates that name them, both already in the tree.
