### D14486 — a returned object literal is built at a number field its literal does not fit

**closed 2026-10-27 · now a loud check reject, `cannot assign {v: i64} to 'wd' of type I` · was check-clean invalid wasm, clause 1, `type mismatch: expected i32, found i64` · filed 2026-10-27 against master `fff894751` · fixed: `recLitFits` (check_fit_rules.vl) admits a number literal at a number field only when its value fits there (`recLitNumFits`: `cexFitsAt` at a number type, whole at an integer one, a member of an integer-literal type) · pins: `tests/cases/soundness/record-fresh-call-literal-field-misfit-refused.vl`**

Repro:

    type I = { v: i32 }
    function d() { return { v: 9999999999 } }
    const wd: I = d()
    print(wd.v)

Want:

    a check refusal at `wd`

#### Mechanism

`recLitFits` accepted any number literal at any field that stores a number, without asking
whether the value fits. On `fff894751` three spellings were check-clean and wrong: an integer
past `i32` (invalid wasm, `expected i32, found i64`), `1.5` at an `i32` field (invalid wasm,
`expected i32, found f64`), and `5` at a `1 | 2` field, which ran and printed `5`. The direct
spelling `const wd: I = { v: 9999999999 }` was already refused. The fix for D14485 alone would
have carried the first two to negated literals (`-9999999999`, `-1e300` at `f32`), which were
refused before it.
