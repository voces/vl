### D2238 — an element read of a narrowed `i64[] | null` hole parameter prints through the i32 import

**closed 2026-09-23 — the witness runs and prints `7` · was check-clean invalid wasm (the instance called `__print_i32__` on an `array.get` of the `i64` backing), clause 1, at every `i64` and `f32` element use, and a loud check or emit reject at every `u8` one · fixed by giving the scalar-list classifiers a rung for a hole read under `!= null` that asks the INSTANCE's own binding for the wrapper, by pinning a `u8[]` argument instead of declining it, and by reading a hole's `u8` element at its value type `i32` while a write through it still checks the `u8` storage · found by the D2236 position matrix · filed against master `5dd67e150` · fixture `tests/cases/lists/narrowed-nullable-list-hole-param.vl`**

Repro:

    function take(a) { if a != null { print(a[0]) } }

    // vl check: rc 0.

#### Mechanism

**The close.** Inside the instance, `a` after `a != null` is a node every instance of `take`
shares, so the checker records it as one type for all of them: the deferred `hole minus null`
(`HD_GNOT` over `TY_NULL`). `exprF64Array` and `exprStringArray` resolved that through
`nodeTyPinIxOf`, which answers only while exactly ONE call pinned the hole; `exprI64Array`,
`exprF32Array` and `exprU8Array` read the raw `nodeTyIxOf` and saw a `TyVar`, so the list was
classified as nothing, the element read as `i32`, and the `array.get` over the i64 backing met
`__print_i32__`. The pin was not the whole answer either: with two instances (`take(i64s)` and
`take(f64s)`) every element type, `f64` and `string` included, went invalid the same way. Three
changes:

- `narrowedHoleNulScalarListKind` (new, `emit_classify.vl`): a read whose recorded type is that
  null-excluding hole (`tyIsNonNullHoleRead`, new in `typecheck.vl`) takes the nullable
  scalar-list kind of its own binding — the instance's pinned parameter annotation — and the
  `i64` / `f32` / `f64` / `string` / `u8` list classifiers accept their own kind there. The
  three that read `nodeTyIxOf` now read `nodeTyPinIxOf`, like their siblings.
- `u8`: `monoArgTyName` declined a `u8[]` argument (a loud floor) and `monoScalarAnnName` had no
  `u8` list, so a `u8[]` or `u8[] | null` argument pinned no instance; both now spell `u8[]`.
- A hole's `a[0]` resolved through `HD_ELEM` to the array's element type raw, so over a
  `u8[]` pin it was `u8`, a storage type (`operator '+' is not defined for u8 and u8`). An
  index READ now mints `HD_ELEMV`, which resolves through `arrElemValueTy` to `i32` as the
  direct spelling's read does; `HD_ELEM` stays the storage type, and an index write through
  a hole checks against it, so `a[0] = 300` and `a.push(1000)` still refuse the literal.

Use-position grid (`i64`, `f64`, `f32`, `u8`, `string` element × print, `+`, interpolation,
return, binding, call argument; the parameter annotated with the CONCRETE list, e.g.
`a: i64[] | null`, or a hole): concrete annotation 29 of 29 RUNS before and after; hole 10 of
29 before (12 SILENT, 3 emit and 4 check refusals), 28 of 29 after. The explicit generic
spelling `a: T[] | null` was a separate gap, [D2244](D2244.md), closed by the same rung. The one left is `print("v=\{a[0]}")` over a `string` element, which refuses for any
string-pinned hole, list or not ([D2241](D2241.md)). Matrices: `nullable-list-join-null-{i64,
f32}` 62 → 64 of 64, `nullable-list-hole-param-i64` 60 → 62 of 62, `nullable-list-hole-param-u8`
47 → 49, the four other `nullable-list-join-null-*` unchanged, 0 runs lost anywhere.

**As filed:**

The instance's parameter is the right cell, `(ref null $i64wrap)`, and the narrowed read
`a[0]` lowers as `array.get` over the `i64` backing; the `print` around it dispatches to
`__print_i32__`, so the read is not classified `i64` at the call. The `f64` and `string`
twins run, and the non-null `i64[]` spelling runs, so the gap is the `i64` element of a
NARROWED nullable hole parameter.
