### D13541 — an `if` of hole functions handed to a parameter called at two types, after an expression that calls in the same statement, is refused at emit

**closed 2026-10-25 · runs, prints `aa` and `2` · fixed: what runs ahead of the choice is bound to `const`s in source order before it, once anything ahead calls (`fsAheadNote`, `fsAheadBind` and `fsApplyChoiceRets`, fn_split.vl) · pins: `tests/cases/generics/hole-fn-choice-ahead-loops.vl` · was loud emit reject, clause 2 · `monomorphize: unsupported argument type for `f` in a call to `both`` · found closing [D13462](D13462.md) · filed 2026-10-25 against master `3b12820b5`**

Repro:

    function both(f) {
      print(f("a"))
      return f(1)
    }
    function inner(s) { return s }
    let k = false
    function flip() {
      k = true
      return 0
    }
    function twice(s) { return s + s }
    function two(a: i32, b: i32) { return a + b }
    print(two(flip(), both(if k { twice } else { inner })))
    // vl check: rc 0.  vl run: emitProgram: monomorphize: unsupported argument type for `f` in a call to `both`

Want:

    aa
    2

#### Mechanism

From the code path. The split runs the choice once before its statement into an arm index
(`fsChoiceArgStmt`, fn_split.vl), so it may only move it past expressions that cannot change
what it reads: `fsChoiceAheadOk` admits pure reads ahead of a pure choice, and only literals
and function names ahead of a choice that calls. `flip()` writes `k`, which the choice reads,
so the plan declines rather than choose by the value of `k` before the write. Binding what runs
ahead to `const`s in order before the choice, as `fsAheadHoists` already does for the call's
own arguments, would run it.

#### Grading list

A record literal with a calling field beside the choice's call, `{ a: tick(), v: both(…) }`; a
calling choice after a parameter read, `z + both(if tick() { inner } else { ask })`.
