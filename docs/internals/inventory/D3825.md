### D3825 — a call through a `const` alias of an un-annotated lambda, made from a nested function, was not re-spelled to the lambda, so the lambda kept its hole's `i32` default

**closed 2026-10-08 by lane SC · was check-clean invalid wasm · found in review of #3425 · filed 2026-10-08 against master `cab1ee907` · pins: `tests/cases/closures/captured-lambda-alias-call.vl`**

Repro:

    function mk(x) {
      const c = (y) => y
      const d = c
      const f = () => d(x)
      return f()
    }
    print(mk(1))
    print(mk("t"))
    // vl check: rc 0.  vl run: invalid module inside `__lambda_3`, `expected i32, found (ref $type)`

Want:

    1
    t

#### Mechanism

`monoRespellLamAlias` (D2896) re-spells a call through an un-annotated `const` alias chain to
the lambda it ends at, so the call instantiates the lambda per argument as a direct call does.
It looked the alias up in the calling frame only. Called from a nested function, `d` is a
capture, the lookup found nothing, and the call kept `d`. The lambda was then emitted at the
hole's `i32` default and handed a string. The lookup now walks enclosing frames the way
`monoCapturedLamFe` does, stopping at a parameter that shadows the name, and the shadow
check on the lambda's own name resolves from the call site the same way.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the alias (`f = () => c(x)`) | runs | **yes** |
| the nested function (`return d(x)` in `mk`) | runs | **yes** |
| the generic frame (`function mk(x: string)`) | still invalid | no |
| the second instance (only `mk("t")`) | still invalid | no |
| an `i32` argument only | runs | **yes** (the default is right) |
| the lambda at module scope, alias in `mk` | still invalid | no |
