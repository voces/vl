### D2192 — a generic close written flush against `=` lexed as one `>=` token, so `const a: Box<i32>= v` was a parse error

**closed 2026-09-23 — `expectTypeGt` splits a fused `>=` / `>>=` / `>>>=` into its `>` run and an `=` token, or an `==` when an `=` abuts it · was a parse error (`expected `>` but found `>=``) · the `>>=` and `>>>=` spellings parsed until PL-021 made them tokens, and are closed by the same change · filed 2026-09-23 against master `66e74235a`**

Repro (runs, prints `6`):

    type Box<T> = { v: T }
    const a: Box<i32>= { v: 1 }
    const b: Box<Box<i32>>= { v: { v: 2 } }
    const c: Box<Box<Box<i32>>>= { v: { v: { v: 3 } } }
    print(a.v + b.v.v + c.v.v.v)

#### Mechanism

The lexer takes the longest operator match with no knowledge of type position, so `>` then `=`
becomes `GE`, and with PL-021's compound shifts `>>=` and `>>>=` become `SHREQ` and `USHREQ`.
`expectTypeGt` already split `SHR`/`USHR` by banking the extra `>`s; it now also splits the three
`=`-suffixed kinds into the `>` run and a separate `EQUAL`, or `EQ` when the next token is an
`=` that abuts it (`u is Box<Box<i32>>== true`, which lexed as `SHR` `EQ` before the new tokens).
The type node's last token stays a real `>`, so `vl fmt`'s verbatim slice ends at the close. The
split REBUILDS `P.toks` rather than editing it: the entry token bank (`vcLoadToksEntry`) holds
the lexed array by reference, and an in-place insert corrupted the second check on one instance,
which is how the LSP runs (`tests/vl_lint_parse_bank_test.ts`, "fused generic close").
