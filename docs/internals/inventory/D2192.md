### D2192 — a generic close written flush against `=` lexed as one `>=` token, so `const a: Box<i32>= v` was a parse error

**closed 2026-09-23 — `expectTypeGt` splits a fused `>=` / `>>=` / `>>>=` into its `>` run and an `=` token · was a parse error (`expected `>` but found `>=``) · the `>>=` and `>>>=` spellings parsed until PL-021 made them tokens, and are closed by the same change · filed 2026-09-23 against master `66e74235a`**

Repro (runs, prints `6`):

    type Box<T> = { v: T }
    const a: Box<i32>= { v: 1 }
    const b: Box<Box<i32>>= { v: { v: 2 } }
    const c: Box<Box<Box<i32>>>= { v: { v: { v: 3 } } }
    print(a.v + b.v.v + c.v.v.v)

#### Mechanism

The lexer takes the longest operator match with no knowledge of type position, so `>` then `=`
becomes `GE`, and with PL-021's compound shifts `>>=` and `>>>=` become `SHREQ` and `USHREQ`.
`expectTypeGt` already split `SHR`/`USHR` by banking the extra `>`s; it now also splits the three
`=`-suffixed kinds, replacing the token with its `>` run and inserting a separate `EQUAL` token
after it. Inserting rather than rewriting in place keeps the type node's last token a real `>`,
so `vl fmt`'s verbatim slice of the annotation still ends at the close.
