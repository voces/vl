### D17109 — an operand that stores is written above an earlier operand read at its use, so that read sees the stored value

**closed 2026-11-24 · runs, prints `12` `2` · was check-clean silently wrong · clause 1 · `vl check` rc 0 · the IR's claim, not legacy: a claimless compiler prints `12` · fixed in ir_build.vl: `irBStageLeads` and `ifBelowLeadOf` miss (`store after an operand`) when a later operand holds a store statement (`storeFrom`), so the function's claim declines to legacy, which writes the operands in order · pins: `tests/cases/assignment/value-after-a-lead-{i32-lit,i32-reread,i32-compound,i32-capture,f64-lit,f64-reread,string}.vl` · found by lane IR-N11 checking that two shadow mismatches it filed shipped legacy's bytes · filed 2026-11-24 against master `334f6958`, pre-existing**

Repro:

    function two(a: i32, b: i32) { return a * 10 + b }
    function m() {
      let b = 1
      print(two(b, b = 2))
      print(b)
    }
    m()
    // shipped before the fix: 22, 2; a claimless compiler: 12, 2.

Want:

    12
    2

#### Mechanism

An assignment used as a value is built as a store statement in the body, then its value. An
earlier operand that is a variable or an immediate is written at its reader, after the body's
statements, so the store lands above it: `local.set b` before `local.get b` for the first
argument, where legacy writes the first argument, then the store inside a block. A shipped
build emits the claim, and the verifier sees well-typed bytes. The armed shadow flags the
function (`fail a claimable function did not match: bytes: call`, modes 1 and 6), but no armed
population had the shape. The `lit` and `nullLit` arms refused only an earlier *temp*
(`endsInTemp`), and the `reRead` arm refused nothing.

#### Ablation

| ingredient | outcome | needed? |
| --- | --- | --- |
| the earlier operand reads another variable than the one stored | runs (the reorder is invisible) | **yes**: the same cell |
| the earlier operand a call or capture read (a temp) | refused (`assignment value lit after an operand`) or unlowered; runs | **yes**: a variable read |
| `print(two(b, b = 2))` → `print(b * 10 + (b = 2))` | refused; runs | no: a call, `==`, a record or array literal all reorder |
| the `lit` arm (`b = 2`) → the `reRead` arm (`b = mk()`) or `+=` | still wrong | no |
| `i32` → `f64` (`b = 2.5`) | still wrong (`27.5` for `7.5`) | no |
| the cell a closure captures | still wrong | no |
| a claimless compiler | runs | **yes**: the IR's claim |

#### Grading list

Ten writers × the call argument (scalar and union parameter), nested call argument, binary
operator, `+` operand, interpolation hole, record field, array element and `==` positions (112
cells). On base, 24 were wrong: the `lit`, `reRead`, `+=`, `f64` and captured-cell writers at a
scalar argument, a nested argument, a record field, an array element and `==`. On the fix, all
112 run with output identical to a claimless compiler. The field, element, global and
effectful-call writers were right on base: their earlier read is a temp.
