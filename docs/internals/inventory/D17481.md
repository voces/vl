### D17481 — a call refused for its argument count keeps the callee's declared return type, so what reads the result is checked against it rather than absorbed as `<error>`

**loud check reject, ruled 2026-11-25 by the coordinator: working as designed · by design, recovery types the call by its declared return (DECISIONS, "A call refused for its argument count is typed by the callee's declared return") · every witness is refused at its arity error · filed 2026-11-24 against master `14e8942af`, from IR-V8's note while verifying #9968 (D17480)**

Repro:

    type A = { x: i32 }
    function mk(x: i32): A { return { x: x } }
    const s: string = mk(1, 2)
    // vl check: rc 2, two errors:
    //   wrong number of arguments: expected 1, got 2
    //   cannot assign A to 's' of type string

#### Mechanism

`callFtyNormArgs` (compiler/check_calls.vl) raises `wrong number of arguments` and returns early,
and the call is typed by the callee's declared return, `A`, as for an accepted call. A reader of
the result is then checked against `A`: here `cannot assign A to 's'` is reported as well, and a
generic callee pinned by it (`show(mk(1, 2))` beside an overload set) takes the `A` instance, so
D17480's `<error>`-receiver path never sees it. Typing the result `<error>` instead would absorb
every such downstream check.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the extra argument (`mk(1)`) | only `cannot assign A to 's'` | **yes** |
| the annotation on `s` | only the arity error | **yes** (for the second error) |

#### Grading list

Ruled as designed: the declared-return recovery reports independent, true
errors after the arity one (the assignment above is wrong at any arity), where `<error>` would hide
them. Six `tests/cases` files pin `wrong number of arguments`, three of them beside other errors
(`numerics/error-trunc-sat-args.vl`, `generics/explicit-type-arguments-errors.vl`,
`intrinsics/error-fs-arity.vl`); any change re-grades them.
