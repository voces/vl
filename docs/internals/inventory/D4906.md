### D4906 — `is K[]` over `i32[] | K[]` with a string literal union `K` cannot tell atom ids from integers

**check-clean silently wrong value · clause 1 · found closing D4902 · the same answer on master before D4902's close · related to D4771 (`is` over a list tests every element) · filed 2026-10-15 against master `0e1ea34b1`**

Repro:

    type K = "x" | "y"
    function f(a: i32[] | K[]) {
      if a is K[] { print("K") } else { print("i32") }
    }
    f([7])
    // vl check: rc 0.  vl run: prints K
    // PRINTS K

Want:

    i32

#### Mechanism

A string literal union is an interned `i32` atom, so `K[]` and `i32[]` share one list rep and
the union is that list with no box (D4743's close). `is K[]` then has no tag to read, and an
element's `i32` cannot say whether it is an integer or an atom id, so the test answers for a
value it cannot see. The scalar `i32 | K` boxes its two arms under different tags and answers
right.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `a: i32 \| K`, `f(7)` | prints `i32`, which is right | **yes** (a list) |
| `f(["y"])` with `if a is i32[]` | prints `i32`, want `K` | no (the other direction) |
| `type K = 0 \| 1` | D4771's element test, right | **yes** (a string literal union) |

#### Grading list

The other direction (`f(["y"])` tested `is i32[]`), and a local `const a: i32[] | K[] = [7]`.
