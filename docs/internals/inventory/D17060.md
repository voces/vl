### D17060 — a start body indexing a list literal whose element is a valued `if` banks its element-read span row where legacy's does not, so the armed shadow refuses the match

**runs today and must keep running · the armed shadow's `mismatch start spans: read index` · found by lane IR-N6 when the closure-record family uncovered a start body holding one · filed 2026-11-23 against master `b12adcce`**

Repro:

    function f(x: i32) { return x }
    const c = 1 > 0
    print(f(1) + [if c { 20 } else { 0 }][0])
    // vl run: prints 21. VL_IR_SHADOW=1 vl check --codegen: "1 mismatch start spans: read index".

Want:

    21

#### Mechanism

The filed spelling, `print([if c { 1 } else { 2 }][0])`, matches since lane IR-N7's batch C: legacy's
`emitIndexBanked` banks the read-index span over the whole receiver when a valued `if` statement
leads the receiver's statements, and `idxRowOpenNote` now takes that lead (`receiverStmtLeads`).
The residue, the same literal as the right operand of a binary operator whose left operand is a
call, matches since the span-compare fix: the lowering noted the row's start before it wrote the
call it stages below the valued `if`, so its row began at the call. It now notes the start where
the receiver's first byte is written: after `stageLead` for an `if` that opens the row, and where a
pending temp that opens it is written. The same spelling in a function body was a claim-fail row
and matches too.

#### Ablation

| ingredient | outcome | needed? |
| --- | --- | --- |
| the left operand a call (`1 + [...][0]` instead) | start uncovered (short-circuit right operand) | **yes** |
| the element a valued `if` (`f(1) + [20][0]` instead) | matched | **yes** |
| the operator's operand position (`print([if c { 1 } else { 2 }][0])` instead) | matched | **yes** |
| at a `const` initializer instead of a `print` argument | mismatch | no |
