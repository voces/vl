### D3713 — lambda lift refuses a check-clean program: a local function in a host specialised per callback is lifted in the host's frame and built as a value in the specialisation's

#### Mechanism

A call passing a known function to a function-typed parameter specialises the callee
(`emit_mono.vl`, the `$cb<N>` arm): the specialisation is a new `fnStmts` slot whose body
`monoBakeCallback` rebuilds copy-on-write, so every statement not mentioning the callback —
here `const g = …` — is the SAME arena node in the original frame and in the specialisation.
The lambda's own slot keeps `fnParent` pointing at the original. `cloLiftDecide` walked only
the original frame, found every use of `g` a direct call, and lifted it, recording the
binding as `(frame of use, let)`. The specialisation emits the shared `LetDecl` too, but
`cloLiftLetFe(<specialisation's slot>, let)` misses, so `emitLetDeclStmt` builds `g`'s
closure value and `emitClosureValueCore` hits the lifted-function floor. Fixed by a pre-pass
in `cloLiftScan` that walks each frame's own code once and marks every lambda `const` and
nested function a second frame reaches; a marked declaration is not lifted, so every frame
that emits it agrees it is a closure (the behaviour before #3381). Lifting it in every frame
that emits it is [D3714](D3714.md).
