### D2484 — an explicit type argument on a generic higher-order call takes the wrong closure signature for a list-of-closures parameter

**check-clean invalid wasm · clause 1 · found in review of #3156 against master `0a0d24ac9`, filed 2026-09-25**

Repro:

    function f10<T>(g: (T[]) => i32, x: T[]): i32 { g(x) }
    print(f10<(i32) => i32>((fs) => fs[0](3), [(z: i32) => z + 1]))
    // vl check: rc 0.  vl run: invalid module, inside `f10`:
    // "type mismatch: expected (ref $type), found (ref $type)"

#### Mechanism

Not ablated to a rung. `f10<T>`'s explicit type argument `(i32) => i32` pins `T` to a closure
type. Called this way, the instance's `g` and `x` parameters are monomorphized against that pin,
but the `call_ref` inside `f10`'s body ends up invoking `g` at a different closure signature
than the one `x`'s elements actually carry, tripping a `(ref $type)`-vs-`(ref $type)` mismatch.
The identical call with `T` inferred instead (dropping `<(i32) => i32>` and annotating the
lambda parameters directly) runs, so the explicit type argument itself — not the list-of-closures
element type — is what the monomorphizer mishandles; annotating the inner lambda's parameter
while still passing the explicit type argument does not help.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the explicit type argument (`T` inferred, inner lambda parameter annotated) | runs, prints `4` | **yes** |
| the inner lambda parameter annotated, explicit type argument kept | still invalid | no |

#### Grading list

The four review templates that grid this cell (explicit-arg / annotated-const / inferred /
both), so a fix re-grades: only the two spellings carrying the explicit type argument fail.
