### D3066 — a hole function's list literal of its parameter at a boxed pin builds an `i32` list outside a binding or `for`-in

**closed 2026-09-28 — the witness prints `1` · was check-clean invalid wasm · `monoPinnedTyOf` reads a hole instance's list literal, element read and function-value call at the instance's hole binding, which the parameter binding `monoPinBodyLambdas` walks with does not name · grid rows graded against master `d408f2da4`, 0 runs lost · fixture `tests/cases/generics/hole-list-literal-in-any-position.vl` · first filed as: check-clean invalid wasm · clause 1 · found grading D3014 (the residue its close does not reach) · the same on master `6c2dafc0b` · filed 2026-09-28 against master `6c2dafc0b`**

#### Mechanism

A hole instance shares its template's expression nodes, so a list literal of the parameter, an element read and a call of a function value keep the recorded type over the hole's variable. `monoPinBodyLambdas` re-types such nodes through the instance's binding, but a hole function's binding names its type parameters, of which it has none; the hole's own binding (`monoHoleBinding`) was read only for a binding's initializer and a for-in iterable. `monoPinnedTyOf` now substitutes through the hole binding too, for those three node kinds, so the literal builds at the pin wherever it stands. A record-element list is left to the rows its literal collects, and a method call's result to its receiver.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `const l = [x]` then `print(l.length)` | prints `1` | **yes** (no binding) |
| `for e in [x]` | prints `2` | **yes** |
| `print([x][0])`, `[x].slice(0)`, `[x].filter(…)` | invalid wasm | no (the same defect) |
| `g([x])` into `g(l: (i32 \| null)[])` | prints `2` | **yes** |
| `function f<T>(x: T)` | prints `1` | **yes** (the hole) |
| a non-null `i32` pin | prints `1` | **yes** |
| `monoPinnedTyOf` without the hole binding | invalid wasm | **yes** (the fix) |
