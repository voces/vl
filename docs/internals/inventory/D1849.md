#### Mechanism

[D1846](D1846.md) joins the arms for a bare NAME, whose narrowing is a scope shadow: the join
writes through `lookupDepth` into the slot the retirement left. A path's narrowing is an
`npKeys` OVERLAY entry the arm's scope already popped, so the join installs a FRESH entry
instead — same fold, different install, and the entry pops with the block the code below the
`if` lives in, which is the lifetime the emitter's own push has.

Two ordering hazards decided the shape, and each is a fixture rather than an argument.

**A CALL in either arm leaves the path unknown, and the ledger is what carries that across the
arms.** `npInvBy` is first-cause-wins, so the then arm's write marks the entry and the else
arm's call finds it already marked — the mark alone cannot tell the join a call happened.
`noteCallInvalidations` therefore records the event in the join's own ledger unconditionally,
and `applyArmJoins` declines a path either arm left unknown. **Validated against a control that
must fire**: with the guard removed, `error-path-arm-join-call-widens.vl` COMPILES and returns
`false`, having stored a `boolean` into a binding typed `i32 | string`.

**And the ledger has to seed an arm whose entry a WRITE already retired.** Both arms writing
the same member joined to the declaration until the second arm's row appeared: the first arm's
retirement marks the entry, so the second arm sees no live fact and recorded nothing. A write's
retirement still seeds the fold; only a call's stops it.

The emitter half is needed for the INDEX key alone, which is worth knowing: a member read's
unbox follows the CHECKER's banked node type (`memReadCheckerAtomKind`), so the checker's join
serves it, while an index read asks the emitter's narrowing stack (`indexUnionReadKind`) and was
check-clean invalid wasm until the join pushed there too.
