### D14383 — a literal-returning function called into an `i64` field and again for a field read builds its literal at its own row

**closed 2026-10-26 · runs, prints `1` `1` · fixed by `recNullWidened` (check_fit_rules.vl) serving a field-read call from a build that widens `i32` to `i64`, which the read narrows back exactly · was check-clean invalid wasm · clause 1 · pin: `tests/cases/soundness/record-fresh-call-into-i64-field-beside-field-read.vl` · found grading the slice 2 follower · introduced by `dbcb67496` (#4902), which removed the emitter's destination walk that had built this literal at `i64` · filed 2026-10-26 against master `dbcb67496`**

Repro:

    function rec() {
      { x: 1 }
    }
    function take(p: { x: i64 }): void { print(p.x) }
    take(rec())
    const a = rec()
    print(a.x)
    // vl check: rc 0.  vl run: invalid module, expected the `{x: i64}` row

Want:

    1
    1

#### Mechanism

`rec` has two call sites: `take(rec())` lands at `{x: i64}`, and `const a = rec()` is read only
for `a.x`. `recSitesLandAt` lets one build serve both when the read-only call can be served from
the build at the landing, which `recNullWidened` limited to a landing that adds `null` to a
field. A numeric widening was excluded because a field read of it can change value. That holds
for `f64`: D8302's fixture `record-fresh-call-into-union-destination.vl` read `e1.v / 2` as `1`
where it is `1.5`. It does not hold for `i32` into `i64`, which is exact, and the emitter narrows
the read back to the `i32` it is typed as (`i32.wrap_i64`), so arithmetic on it still wraps at
32 bits. Before #4902 the emitter's destination walk built the literal at `{x: i64}` anyway. With
that walk deleted the literal stayed at `{x: i32}` and the delivery into `take` was invalid.
Following the numeric join ruling (literals adapt), the literal is now built at `{x: i64}` and
the field-read call reads it narrowed. The `f64` exclusion stays.

| --- | --- | --- |

| `take`'s `i64` (`x: i32`) | runs | **yes** |
