### D16133 — closing a hole-bound lambda's type in the elaboration contradicts the function-set path, which keys that lambda by identity and lowers it as a set id

**loud emit reject · clause 2 · a design item for the function-tag owner (lane A) · found by lane I prototyping D16077's close (branch `i-d16077-hole-param-maker`) · filed 2026-11-14 against master `b8b695bf`**

Repro:

    function inc(x) { x + 1 }
    function run(f) { print(f()(5)) }
    run(() => inc)
    function run2(f) { print(f()(6)) }
    run2(() => inc)
    // master: emitProgram: call to unknown function. The prototype: invalid wasm.

Want:

    6
    7

#### Mechanism

Two representations of one argument disagree.
- The function-set path keys each lambda handed to a hole parameter by identity: the checker's
  hole row binds `?run.0 = Fn#<node>`, and the call site lowers that lambda as a tagged set's
  member id (`i32.const <node>`).
- D16077's close needs the elaboration to give that lambda a closed type,
  `() => ((i32) => i32)`, so that `run`'s instance takes a closure.

With both in play, the second callee's argument is lowered as a set id where its instance takes
a closure. Excluding tagged lambdas (`fnTagLeafSetOf`, `fnTagTyIsTagged`) does not stop it, and
sharing one closed type index across lambdas broke even the single call. The direction recorded
on D16077 is to defer banking the hole row until its delivery is walked, and to key the closure
global and the set member by the closed type, so that the call site and the instance agree.
