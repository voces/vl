### D16133 — closing a hole-bound lambda's type in the elaboration contradicts the function-set path, which keys that lambda by identity and lowers it as a set id

**closed 2026-11-14 · runs, prints `6` `7` · was a loud emit reject, `emitProgram: call to unknown function` · closed by refuting the tag of a set whose member the elaboration closed (D16133's ruling, option (ii), stage 3) · found by lane I prototyping D16077's close · filed 2026-11-14 against master `b8b695bf`**

Repro:

    function inc(x) { x + 1 }
    function run(f) { print(f()(5)) }
    run(() => inc)
    function run2(f) { print(f()(6)) }
    run2(() => inc)
    // master: emitProgram: call to unknown function. The prototype: invalid wasm.

Want:

    6

#### Mechanism

The function-set path keys each lambda handed to a hole parameter by identity and lowers it as
a tagged set's member id, while the elaboration closes the lambda's type at its returned
generic's delivery, so the instance takes a closure. The close is ruling (ii)'s refute arm. Where
`elabLamHoleTysClose` (`emit_elab.vl`) closes a lambda's type, it notes the lambda
(`mintLamClosedNote`, `check_mint.vl`). The decision after the elaboration declines every set
with such a member (`ftPlan`, `check_fn_tag.vl`). A set the check had tagged is dropped through
`ftLateRefused`, so the next round builds the call site's closure. A program with no such lambda
runs no extra round. Deferring the hole row (D16077's note) was not needed.
