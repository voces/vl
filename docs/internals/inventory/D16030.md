### D16030 — variant rows are keyed by the arm's spelling, which is a per-union position label and not a canonical key

**closed 2026-11-13 — the variant field tables are chosen by the arm's type; the witness runs and prints `1` · filed 2026-11-13 against master `2c95179c`**

Repro:

    type Node = { v: i32, next: Node | null }
    type M = Node & { v: i32 }
    const tail: Node = { v: 5, next: null }
    const n: M = { v: 1, next: tail }
    print(n.v)
    // vl run: 1, on master and after the close; the arm's spelling `Node&{v:i32}` names no
    // struct, so master minted no variant row for it and the type-keyed form does

Want:

    1

#### Mechanism

`mintVariantRows` (emit_collect) minted a variant row only where `isStructAtom(stmts, names[i])`
held, a test of the arm's SPELLING: a declared struct name, or an inline `{…}`.
`collectVariantFields` then chose the arm's fields from the same spelling: parse an inline span,
or look up the `TypeDecl` by name. The arm's type `tys[i]` was on hand, but it never decided.
An intersection arm spelled `Node&{v:i32}` is a record by type and neither form by spelling.

A canonical-key probe over the sweep (24,140 programs, `tySame` and `tyEq` equality, one drain
message per program) found the spelling fails both directions:

- one type under two spellings: 358 pairs (aliases of one structural type, `Dot` / `Circle`);
- one spelling at two types: 2 programs (numeric-tag twins softened to `{k:i32,n:i32}`, D14540).

Both are by design: a variant's identity is its position (D14552), so the spelling is a label.
The one decision the spelling made that the type contradicts is the 5 intersection programs.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the intersection (`type M = Node`) | the arm spells `Node`, a declared struct | **yes** |
| the recursive `next` field | still spells an intersection | no |
