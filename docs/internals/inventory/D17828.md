### D17828 — a nullable choice of an un-annotated function delivered at a nullable function of a wider result is refused, with no one place that adapts it

**loud emit reject · clause 2 · `emitProgram: cannot take the generic function \`inc\` as a value` · `vl check` rc 0 · filed 2026-11-28 against master `3b5582185` by COV-UNION (D17818's wider face, coordinator ruling)**

Repro:

    function inc(a) { return a + 1 }
    function two() { return [1, 2].length }
    const h = if two() > 1 { inc } else { null }
    const z: ((x: i32) => i32 | f64) | null = h
    if z != null { print(z(3)) }
    // vl check: rc 0.  vl run: emit error at `inc` (cannot take the generic function `inc` as a value)

Want:

    4

#### Mechanism

D17818's close instances each function arm of the choice at the destination's function, and types
the binding at the nullable of the arm's instance, which the elaboration agrees with. A wider
result needs an adapter at the delivery `z = h`, and none takes it. D17816's nullable adapter
(`fvaAdaptNullable`, check_assignable.vl) is a check-time rewrite that declines a source still open
there. The non-null twin (`else { inc }` at `(x: i32) => i32 | f64`) runs another way: mono
instances the arm at the wider destination and types the binding there. Mirroring that for the
nullable makes `monoBindingAdoptInit` refuse, since the elaboration closes `h` at the instance's own
`((i32) => i32) | null`. Taken without an adapter, the program traps (indirect call type mismatch).
`monoNullChoiceAtDest` (emit_mono.vl) keeps it at this refusal.

Open: where the adapter belongs. Either mono instances at the wider type and the elaboration
agrees, or the check-time adapter takes a source mono closes. The goal is one mechanism for both
faces, the nullable and the non-null. Pinned by
`tests/cases/closures/error-nullable-choice-of-a-hole-function-at-a-wider-nullable-result.vl`.
