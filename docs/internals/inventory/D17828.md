### D17828 — a nullable choice of an un-annotated function delivered at a nullable function of a wider result is refused, with no one place that adapts it

**closed 2026-11-28 by I8-PREP · runs, prints `4` · was: loud emit reject · clause 2 · `emitProgram: cannot take the generic function \`inc\` as a value` · `fvaAdaptNullable` (check_assignable.vl) takes an open source at its hole instance, as `fvaAdapt`'s function arm does; `fvaHoleDeclOf` reads a value join's non-`null` tails; mono delivers an argument at a nullable function parameter of a callee that is no name (`monoCoerceAtValueParams`) · filed 2026-11-28 against master `3b5582185` by COV-UNION (D17818's wider face, coordinator ruling)**

#### Mechanism

D17818's close instances each function arm of the choice at the destination's function, and types
the binding at the nullable of the arm's instance, which the elaboration agrees with. A wider
result needs an adapter at the delivery `z = h`, and none takes it. D17816's nullable adapter
(`fvaAdaptNullable`, check_assignable.vl) is a check-time rewrite that declines a source still open
there. The non-null twin (`else { inc }` at `(x: i32) => i32 | f64`) runs another way: mono
instances the arm at the wider destination and types the binding there. Mirroring that for the
nullable makes `monoBindingAdoptInit` refuse, since the elaboration closes `h` at the instance's own
`((i32) => i32) | null`. Taken without an adapter, the program traps (indirect call type mismatch).
An elaboration guard in `monoCoerceChoiceBinding` (emit_mono.vl) kept it at this refusal.

Open: where the adapter belongs. Either mono instances at the wider type and the elaboration
agrees, or the check-time adapter takes a source mono closes. The goal is one mechanism for both
faces, the nullable and the non-null. Pinned by
`tests/cases/closures/nullable-choice-of-a-hole-function-at-a-wider-nullable-result.vl`.

#### Outcome (2026-11-28, I8-PREP)

The premise above is wrong: no face that runs instances the arm at the wider result. Each, the
non-null binding, the inline choice and a closed source, holds the arm's own instance
(`$inc (param i32) (result i32)`) and is delivered through a check-time adapter at the wider
type; the elaboration types the binding at that narrow instance, which is what it holds. The
nullable binding missed that adapter, for three reasons, each fixed in the general rule:

- `fvaAdaptNullable` declined any open source, and read an open one as a set before trying its
  instance. It now holds one at `fvaHoleInstTy`, as `fvaAdapt`'s function arm does.
- `fvaHoleDeclOf` did not see through a value join. It now takes the one function every
  non-`null` tail holds.
- The adapter is a lambda called in place, and `monoCoerceAtValueParams` delivered no argument at
  a nullable function parameter. It now takes one, as a named callee's parameter does (D9820).

The elaboration guard is deleted. In its place `monoCoerceChoiceBinding` refuses, as an internal
error, a nullable choice reaching a function other than its arm's instance: with the adapter
reverted the witness, its function face and a parameter face refuse there instead of trapping.
A second delivery at another function type stays refused (`monoChoiceBindNote`). The generic
face is D17829, closed with it.
