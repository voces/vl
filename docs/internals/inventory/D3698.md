### D3698 — a line-leading `- b` started a new statement, so a broken subtraction silently dropped its second half (sunpa SP-040)

**closed 2026-10-05 — the witness prints -0.5 · was check-clean silently wrong on master (printed 3) · by the owner's spacing ruling: a line-leading `-` followed by a space or tab continues the previous expression, `-x` stays a statement · sunpa SP-040 · filed and closed by lane SR against master `56af0f07e` · fixtures `tests/cases/parser/leading-minus-spacing.vl`, `tests/cases/lint/unused-pure-expression-scalar-operands.vl`**

Repro:

    function f(a: f64, b: f64): f64 {
      const w = a * 3.0
        - b * 3.5
      w
    }
    print("\{f(1.0, 1.0)}")

Want:

    -0.5

#### Mechanism

`continuesLine` (`parser.vl`) decides whether a NEWLINE run in `parseBinary` leads to an
operator that continues the expression. It is derived from `binPrec`, and outside brackets it
excluded `-` because `-x` can begin a statement (`{ f()` ⏎ `-x }` is a block whose value is
`-x`). So `- b * 3.5` parsed as its own statement and was discarded. The gate now admits a
`-` whose next token sits on the same line after a gap (`spacedAfter`): the lexer skips only
spaces and tabs between tokens on a line, so that gap is horizontal whitespace. A `-` touching
its operand, or ending its line, keeps the old reading. Inside brackets `-` continued already.
DECISIONS.md "A line-leading `-` continues only when whitespace follows it".

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the space after `-` (`-b * 3.5`) | two statements, prints 3, `unused-pure-expression` warns | **yes** |
| the line break (one line) | -0.5 on master too | **yes** |
| the `w` after it (the `-` line is the block's value) | master returns -3.5, the second line alone | **yes** |
| an enclosing `(` around the two lines | -0.5 on master too (bracket gate, D1581) | **yes** |
