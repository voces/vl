### D14568 — an instance's or captured frame's binding keeps its type variable in the held type

**runs today and must keep running · refutation pin for the literal-atom Ident arms reading the binding's held type · filed 2026-10-27 against master `c073bbc52` plus #5047**

Repro:

    type K = "a" | "b"
    function h<T0, T1>(a0: T0, a1: T1, k: i32) {
      const f = (j: i32) => if j == 0 { a0 } else { a1 }
      print(f(k))
    }
    const z0: K = "b"
    h(z0, 4, 0)
    h(z0, 4, 1)
    function m<T>(a: T) {
      const r = a
      const g = () => r
      print(g())
    }
    m(z0)
    // vl check: rc 0.  vl run: prints b, 4, b

Want:

    b
    4
    b

#### Mechanism

The program runs because the literal-atom Ident arms answer a `let` from the slot its frame
collected, else the binding storage column (D14569), and a parameter from its annotation. An
arm-by-arm shadow (each arm against `repOfNodeAt` over the binding's held type) disagrees here: the arm says the read is a literal atom, and the
held type of `a0` inside the lambda, `a` at `m`'s instance, and the captured `r` is still the
TyVar, so the rep layer reports it uncovered. The same split shows on the let, captured-let,
module-let and parameter arms of `generics/coalesce-join-tag-in-instance`,
`hole-pin-nullable-literal-union`, `lambda-join-literal-union-pin`,
`join-gated-list-and-lambda`, `one-union-nullable-literal-pin-prints-member`,
`hole-lambda-join-of-two-holes-first-arm`, and on the narrowed reads of `hole-map-read-atom-value`,
`instance-call-of-nullable-literal-union-function` and `pin-non-null-dead-null-test`. The gap is
the producer: `letBindTy` and the parameter type at an instance or captured frame should be the
instance's substituted type. A reader-side TyVar resolve would be a second producer.

#### What the elaboration now produces (2026-10-27)

Outside every instance, a call that reaches an instance is typed by that instance's result:
the substituted signature, or, for a template with no written result, the one type its
elaboration gives every value the body yields. An un-annotated binding the elaboration leaves
open holds its initializer's type. A binding's type (`letBindTy`) asks the elaboration at
module scope as well; no other module-scope read does. This gives `const r = kept(mk(true))`
in a plain function and the module's `const gr = kept(mkM())` in
`generics/coalesce-join-tag-in-instance` their closed type.

Of the 13 shadow lines this row measured over its nine witnesses, 9 are gone. Six were the
probe asking the template's declaration at the instance; asked of the frame's own declaration
(`readLetDeclOf`), they agree. Three were the call-initialised bindings above. Four remain:

* `generics/hole-pin-nullable-literal-union`, the captured `y` in `cap`. Its storage is asked
  while the instance is still being built, before the `monomorphized` phase, so `nodeTyAt` returns
  the template's type.
* `generics/hole-map-read-atom-value` and `generics/instance-call-of-nullable-literal-union-function`
  (two lines). The binding's type is closed (`AB | null`, `#lu0 | null`). The read is
  narrowed, and the type it narrows from is the template's.

#### Two producers of an instance binding's annotation

The `d3281_join_tp_*` cells and `generics/coalesce-join-at-literal-union-pin` are not a
generation drift. The instance's copy of `r` carries the annotation the monomorphizer mints
by substituting the template's join (`"a" | "b" | i32`). The elaboration of the template's `r`
at the same instance says `K`. Storage reads the copy, so the program runs. The two answers
still disagree.

#### The same two producers at a parameter (2026-10-28)

A parameter-read shadow (the literal-atom Ident arms against the rep of the parameter's type at
its frame) has 6 lines on the parameter arm of four of this row's cells:
`hole-lambda-join-of-two-holes-first-arm` (two), `join-gated-list-and-lambda`,
`lambda-join-literal-union-pin` (two) and `one-union-nullable-literal-pin-prints-member`. Each is
a parameter of a generic or hole instance, captured by a closure. The arm's answer is right and
comes from the instance's own copy of the `Param` (`parentBindingOf`), whose annotation the
monomorphizer minted by substitution, written or not. The template's `Param` at the same
instance still holds the type variable (`_`, `T0`, `T`), so its rep is uncovered. The producer
to fix is the one this row names: a parameter's type at an instance or captured frame is the
substituted type. The minted `parType` is then the second producer, and is deleted.

#### The parameter now answers from the elaboration (2026-10-28)

`scopeTyAt` answers a node the emitter never typed (an instance's copy of a `Param` or a
`LetDecl`) by its source's checker type and the source's elaboration at the instance, from the
copy's first use on rather than only after the `monomorphized` phase. The literal-atom and
nullable-literal-atom `Param` arms (`bindingIsLitAtom`, `bindingIsNulLitUnion`) ask that type
(`nodeRepIsAtom(bindIx, ownerFnIx)`) instead of the copy's minted `parType`. The six
parameter-read shadow lines on the four cells above are 0, and the row's own witness has none.

The minted `parType` is still written (`monoMakeInstanceParams`, `monoLamSubstParams`,
`monoLamParamPinAnn`) and still read: 187 `.parType` reads in 70 functions across 20 emit
files, 110 of them in `emit_mono.vl`. Which of those read an instance copy rather than a
template's written annotation is not yet separated. Deleting the mint is the next target, and
that split is its first step. `monoTpJoinBindAnn` is the same producer for a `let`, and goes
with it. The `d3281_join_tp_*` cells still run and print the same.
