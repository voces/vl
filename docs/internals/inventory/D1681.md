#### Mechanism

`b?.y` over an `S[]` field yields `S[] | null`, and D1676 built the standalone `?.` arm that
delivers it as the ref list's own wrapper. The ANNOTATED spelling ran; the un-annotated one
did not, and the checker calls that annotation redundant — it agrees about the TYPE while the
two spellings disagree about the REP.

The binding's kind resolved (`letIsNulRefArray` asks `exprNullableRefArray`, taught the `?.`
twin by D1676) and its SLOT did not: `nulRefArrayInnerSlot` carried a `Member` arm reading
code 28 and no `OptMember` one, so the local took slot -1 and was declared at a valtype the
module never interned. It is the sixth member of the family D1667 named, after
`exprNullableList`, `exprNulScalarListKind`, `exprNullableRefArray`, `refListElemNameOfExpr`
and `exprEmittedRefListSlot` — and it takes the same widening those did, since the receiver's
`| null` is what makes a non-nullable ref-list field's read nullable: code 5 answers here as
well as code 28.

#### Ablation

| ingredient removed | before | after |
| --- | --- | --- |
| the annotation (`const v: S[] \| null = b?.y`) | runs, prints `4` | runs, unchanged |

Only the REF list was affected: every scalar list (`i32[]`, `string[]`, `f64[]`, `i64[]`,
`f32[]`, `u8[]`) and the already-nullable `i32[] | null` field ran un-annotated before.
