#### Mechanism

The field value here is an IDENT, not a literal, so `anonFieldElemName`'s code-15 arm takes its
non-literal route: `nodeTyCanonObjName`, then `structRowOfObjFieldSet` on the recorded type.
That scan matches a field-name set plus per-field CODES, and every union-box field is code 16
whatever it boxes — so `{xs: U1}` and `Inner` are indistinguishable to it and the first row
wins. The probe, on the witness above:

    ROW 0 Inner    [xs:16:<U2> ]    render={xs:string|boolean}   -> nameRow0
    ROW 1 {xs:U1}  [xs:16:<U1> ]    render={xs:i32|boolean}      -> nameRow1
    ROW 2 #anon2   [f:15:<Inner> ]  render={f:{xs:i32|boolean}}  -> nameRow-1
    LIT node14 -> row1 lit-fields[xs:16:<i32|boolean> ]
    LIT node18 -> row2 lit-fields[f:15:<Inner> ]

Row 2's own render is `{f:{xs:i32|boolean}}` and its recorded element is `Inner`, whose box is
`string|boolean` — the row disagrees with itself. Delete `type Inner` and the same row records
`{xs:U1}` and the program prints `7`.

**This is the THIRD reader in D1690's own table**, and D1690's close deliberately did not touch
it: that close conditions `structIndexOfObjCtxGo` — the NODE reader — on the literal's own
destination, while `structRowOfObjFieldSetK` is the arena reader, whose element preference
(`rowElemDeclConflicts` via `fieldElemDeclConflict`) covers only the named-heap codes 15, 5 and
28 and has no arm for 16. `fieldBoxSetConflict` is that arm — `fieldElemDeclConflict`'s union-box twin, asking
`unionMemberSetsCompat` of the query field's rendered type against the row's recorded set,
ranked rather than vetoed exactly as its sibling is. **Its price is zero**: on its own it moves
**0 of 3,051** `tests/cases` modules and closes this row's witness.

**D1690's close moved one spelling of this row into it, and that is recorded rather than
buried**: with the inner binding UN-annotated (`const inner = { xs: u1() }`) the same program
printed `true` before the close and is invalid wasm after. Both are clause-1 violations, so no
`runs` was lost and the corpus, the matrices and all 3,051 `tests/cases` modules are unmoved —
but a wrong VALUE became a module that will not load, which is a movement worth naming.
