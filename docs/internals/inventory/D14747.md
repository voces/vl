### D14747 — a field typed by a subtraction alias is stored as a string while the same type spelled inline is the atom

**runs, prints `la` — CLOSED 2026-11-01: an alias whose body is one computed literal set holds that set's literals, so `f` is stored as the atom at both spellings · was a step 5 `ctxTy` field decline · filed 2026-11-01 against master `5b24d58b`**

Repro:

    type K = "la" | "lb" | "lc"
    type I = K & !"lb"
    type C = { f: I }
    const c: C = { f: "la" }
    print(c.f)

Want:

    la

#### Mechanism

`I` is the literal union `"la" | "lc"`, whose `repOfTy` is the i32 atom. `{ f: "la" | "lc" }`
stores `f` as the atom, while `{ f: I }` stores it as a string: the row is keyed by the
spelling, not the type. The storage side is the wrong one. A reader asking `repOfTy` of the
field's contextual type gets the atom. `ctxFieldStorageAgrees` declines every record field
until this agrees.

The cause was the declaration fill, not the field ladder. `fillUnionDeclMembers` filled `I`'s
placeholder with ONE member, the subtraction's own literal union, and the literal flatten
(`litUnionFlatMembers`) declines fewer than two members. So `I` was a union holding a union,
`tyIsLitUnion(I)` was false, and `fieldCodeOfTy` fell to the string ref. `litUnionLoneMembers`
now flattens that lone member, so `I`'s members are `"la"` and `"lc"` as at its spelled form.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the alias (`{ f: "la" \| "lc" }`) | `f` stored as the atom | **yes** |
