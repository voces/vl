#### Mechanism

`memberFieldCode` resolves a `Member`'s receiver through `structIndexOfExpr`, which asks
`memberFieldCode` of the receiver's own receiver. Neither memoises, so a `.g.g.g…` chain is
walked once per path that reaches the link — and until D1705's close there was a caller that
produced many such paths, because the capture comparator declined past its depth counter and
the same literal was re-resolved at every level. At depth 70 that was a compiler trap
(`allocation size too large`, D1706).

**The close removed the caller, not the recursion.** The comparator now refutes at every depth,
so the literal mints its own row and the chain is asked once — the ladder is clean to 100 at
both faces. Two probes were written to reach the recursion another way, a 40- and a 70-level
chain with TWO declared rows of the same shape so the row scan is ambiguous at every level, and
both print `7`.

So this is filed as a PIN rather than a defect: there is no program today that reaches it, and
the thing that would bring it back is a second caller with the same shape. **The memo it wants
is known and its first attempt is on the record**: keyed on `(memIx, fnIx)` with `sidArrPut`
growing an `i32[]` to a raw arena node index, dropped and regrown per outer ask, it trapped
inside its own growth on the compiler's own source while passing all 3,059 `tests/cases`
modules. The shape that works is D1705's — an open-addressed table sized once per pass and
generation-stamped on `emitPassGen`, a `pass-stamped` row of the memo-generation census.
