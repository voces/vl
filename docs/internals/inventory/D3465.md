### D3465 — a literal of 2.7 million elements with one computed element still overflows the engine's function-body limit

**check-clean invalid wasm (`function body size count exceeds limit of 7654321`, `vl build` exit 70) · a size cliff at plumb scale · the residue of D3417, whose data segment needs every element to be a literal · found by lane AL · filed 2026-09-30 against master `47aa2950b`**

Repro:

    let m = 3
    m = m + 1
    const xs: i32[] = [m, @@repeat(2700000, "300,")@@300]
    print(xs.length)
    // vl check: rc 0.  vl run: "failed to parse WebAssembly module: function body
    // size count exceeds limit of 7654321"

Want:

    2700002

#### Mechanism

D3417 moved an all-literal scalar literal into a data segment; a literal with any computed element
keeps the chunked build (`arrLitChunkStart` / `arrLitChunkFlush`, compiler/wasmEmit.vl), which is
straight-line code of a few bytes per element in the one function that holds the literal, here the
start function. Wasmtime refuses a body past 7,654,321 bytes, reached between 2.5 and 2.7 million
elements. A close splits the build: the literal elements of a mostly-constant literal could still
come from a segment with the computed ones stored after, or a long chunked build could move into
helper functions of bounded size.

#### Grading list

The same literal in a function body; a record literal of the same length (D3462's chunks keep the
same per-element bytes in one body).
