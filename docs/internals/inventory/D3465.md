#### Mechanism

D3417 moved an all-literal scalar literal into a data segment; a literal with any computed element
keeps the chunked build (`arrLitChunkStart` / `arrLitChunkFlush`, compiler/wasmEmit.vl), which is
straight-line code of a few bytes per element in the one function that holds the literal, here the
start function. Wasmtime refuses a body past 7,654,321 bytes, reached between 2.5 and 2.7 million
elements. A close splits the build: the literal elements of a mostly-constant literal could still
come from a segment with the computed ones stored after, or a long chunked build could move into
helper functions of bounded size.

#### Close

`arrLitDataBuild` now takes a scalar literal past the `array.new_fixed` cap with computed
elements too. Each computed element holds zero bytes in the segment. Once `array.new_data` has
built the backing into a lazy-frame slot, the computed elements are stored with `array.set`, in
source order. The function body is then a few bytes per computed element, not per element.
Admitted for the i32, i64, f32 and f64 forms, and only for elements the literal's own loop would
lower as one scalar of that form. Anything else keeps the chunked build. A string, ref or record
literal of that length still chunks, so the grading list's record spelling is not covered here.
