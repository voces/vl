### D13100 — a hole function in a list literal written in a `for` header, called at a closed type, gets no instance at the loop variable's call

**closed 2026-10-25 by lane L1 · runs, prints `1` and `0.5` · built, not refused: the monomorphizer types a call through a `for` variable over an inline list literal holding a generic element at its elements, as it already did for a call handed a hole parameter (`monoForInlineGenElems`, gating `monoOpenCallAtElems` in `monoWalk`, emit_mono.vl) · pin: `tests/cases/closures/inline-for-list-of-hole-fns.vl` · was a wasm trap at load-and-run, `indirect call type mismatch` in `inner` (clause 1), and a loud emit reject in every neighbouring spelling (clause 2) · `vl check` rc 0 · found grading D12701's ablation · present on master `1b0f55762` · filed 2026-10-25 against master `1b0f55762`**

Repro:

    function apply2(s) {
      print(s + s)
    }
    function inner(k) {
      for f in [apply2] { f(0.5) }
      print(k)
    }
    inner(0.5)
    // vl check: rc 0.  vl run on master: wasm trap in `inner` (indirect call type mismatch)

Want:

    1
    0.5

#### Mechanism

`monoWalk`'s `Call` arm types a call through a list element at its elements
(`monoOpenCallAtElems`) only when an argument is a hole parameter or the call is handed a
generic at an open parameter. A loop variable over a list literal written in the `for` header,
called with a closed value, met neither, so `apply2` was never instanced at `f64`: the element
took `apply2`'s `i32` default and the call site, typed `f64` by the checker, called it through a
table slot of the other signature. Outside a hole function the same gap refuses instead.
