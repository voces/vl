### D16471 — `>>` over a negated radix literal whose digits exceed `0x80000000` computes at 64 bits at an `i32` use

**closed 2026-11-15 · runs, prints `0` · was check-clean silently wrong, clause 1 (`vl check` rc 0), printed `-536870912` · closed by leaving `>>` over a negated pattern whose magnitude exceeds 2^31 unfolded, so it shifts at its use's width (`cexNegPatWraps`, `const_exact.vl`) · found by fuzz-nightly run 43686086648 (oracle leg, `ar_s35_0009`) · filed 2026-11-15 against master `6015bf3ed`**

Repro:

    const a: i32 = (-0xFFFFFFFF) >> 3
    print(a)
    // printed -536870912 before the close

Want:

    0

#### Mechanism

Under the radix ruling (owner, 2026-09-30, ruling A), a negation of a radix literal folds as the
pattern, so `-0xFFFFFFFF` is `1` at `i32`. The compiler gets that right on its own (`print` of
`const a: i32 = -0xFFFFFFFF` is `1`). A `>>` over that negation instead reads the operand as the
64-bit value `-4294967295` and shifts it: `-4294967295 >> 3` is `-536870912`, which fits an
`i32` and is stored. Under the ruling, `1 >> 3` is `0`. The same holds at a `let`, at a `const`
and with no context.
