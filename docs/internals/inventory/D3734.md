### D3734 — a closure-shared `i64` assigned a value `if` of hex literals as an annotated closure's tail returns the 32-bit pattern

**closed 2026-10-06 — the witness prints `4294967294` twice · was check-clean silently wrong, clause 1 · found by lane L2 while grading [D3664](D3664.md) against master `687b42dbe`: the shared-cell spelling of [D3733](D3733.md) · closed by lane S4 against master `a37097b64` · fixture `tests/cases/literals/hex-width-through-assignment-value.vl`**

Repro:

    function t(c: boolean) {
      let x: i64 = 0
      const u = (): i64 => {
        x = if c { 0xfffffffe } else { 1 }
      }
      print(u())
      print(x)
    }
    t(true)
    // vl check: rc 0.  vl run prints -2, then 4294967294

Want:

    4294967294
    4294967294

#### Mechanism

[D3733](D3733.md)'s, through a captured cell: the closure's tail `x[0] = e` (the cell write the
capture lowering makes of `x = e`) was read back, unwrapped to the checker's 32-bit type, and
sign-extended into the `i64` result, `-2`. The written-capture lowering is not an ingredient: the
same tail on a closure-local binding was invalid wasm, and the un-annotated closure already ran
(its `cboxYieldTail` rewrite applies to an un-annotated lambda only). One close, `asgRadixWidePrim`
read at the `i64` delivery, fixes both; it reads the cell write as it reads a name.
