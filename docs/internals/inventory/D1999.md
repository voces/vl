### D1999 — a unit exporting two or more functions puts their functypes in one rec group, so no separately built unit's `extern` import can link to them

**closed 2026-09-22 — the link below succeeds under `wasm-merge` (then `-O3`) and V8 and prints `42`, `10` · was a linking defect, clause 2: both units `vl check` and build, and the link between them was refused at every return type · the `vl run`-based grader cannot perform a link, so the Repro is the exporting unit alone and the link is graded by `tests/vl_extern_link_test.ts` · blocked plumb's multi-unit linking (PL-003, `~/plumb/docs/vl-issues.md`) · found implementing the `: void` extern result (plumb PL-013) · filed 2026-09-22 against master `914d64d65`**

Repro:

    export function f(a: i32): i32 {
      print(a * 2)
      return a
    }
    export function other(a: i32): i32 { return a + 1 }
    f(21)
    // vl run: 42.  The program is not the witness — the two-unit link below is.

The link witness, filed with a `: void` result (the `: void` extern result, plumb PL-013).
The ablation shows the result type is not an ingredient, so the test spells it `: i32` and
does not depend on that feature:

```sh
# unitA.vl
export function f(a: i32): void {
  print(a * 2)
}
export function other(a: i32): i32 { return a + 1 }
# unitB.vl
extern function f(a: i32): void
f(21)

#           type (ref (exact $func.0)) is not a subtype of (ref $func.0).
#           Fatal: import/export mismatches
# V8, B instantiated with `extern: a.exports` (no merge):
#   before: Import #4 "extern" "f": imported function does not match the expected type
# after: both links succeed and print 42 then 10.
```

#### Mechanism

`emitTypeSection` (`compiler/emit_sections.vl`) wrote every defined function's functype as a
member of ONE rec group (`wU8(78)` over `n + typeOffset + hasStart` entries), beside the struct
types. Only the print, fs, helper and extern-import functypes, and the `#1265` export-wrapper
functypes (`exportWrapSlots`, emitted only when `fnValUsed`), were standalone. Under
iso-recursive typing a type's identity is its whole rec group plus its position, so `f`'s
`(func (param i32))` at position 0 of a two-member group is not the standalone
`(func (param i32))` unit B's import declares. A one-function unit linked only because a
singleton rec group is the same type as a standalone one.

#### Fix

The heap types and the closure-signature pool (`emitCloSigFunctype`, at `cloSigBase + pos`)
stay in the rec group, which is omitted when it would be empty. Each user function's own
functype and the start functype are now standalone rectypes after it: they name only
lower-indexed types, so none needs the group, while the grouped types keep it because they
may reference one another forwards. When closures are used, exports get standalone types
through their existing wrappers (`exportWrapSlots`). Otherwise the exported function
carries the canonical type itself, so a cross-unit call is a direct call with no forwarding
wrapper. The row's untested prediction — run the export wrappers for every export — was not
taken: it would add a call per cross-unit call, and a wrapper's standalone type does nothing
for the function's own.
