### D15908 — a function named like a bundle-making callee's parameter, returning its bundle, is refused at check

**closed 2026-11-12, `vl check` clean, runs and prints `5` `2.5` used as a bundle · was loud check reject · clause 2 · `vl check` rc 1, `argument 1: expected i32, got f64 (the call of \`f\` at the call's argument types)` · found filing [D15905](D15905.md) · filed 2026-11-12 against master `96590b46` · closed in the checker: a call's constraint owner is looked up by name only where the callee spelling binds no parameter or `let` (`callFtyPinCstrs`, check_calls.vl; `identBindsNonFn`, check_scopes.vl). The name lookup made `lap`'s calls through its parameter `f` calls of the function `f`, so the elaboration minted an instance of `f` per lambda signature and re-checked `lap` with the lambda at one of them · fixture `tests/cases/closures/hole-lambda-bundle-param-named-like-its-returner.vl`**

Repro:

    function lap(f) {
      f(2.5)
      f(3)
      return f
    }
    function f(n: i32) {
      lap((a) => a + 1)
    }
    f(1)

The module must validate: `vl check` accepts it and the run prints nothing.

#### Mechanism

The same name confusion as D15905, on the checker's side: where `f`'s body returns `lap`'s
bundle as its value, the check of `lap`'s calls at the call's argument types reads `f(2.5)` as
a call of the top-level `f(n: i32)`. Renamed `g`, it checks clean and runs.
