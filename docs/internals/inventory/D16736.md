### D16736 — two recursive records that store a field differently exhaust the compiler's call stack when the recursive field comes first, because `fieldStorageEq` restarts its budget at every record

**closed 2026-11-16 by lane H — now a loud check reject (fixed: "A is not B: they store field `n` differently") · `fieldStorageEq` walks with a stack of the record pairs it is inside, not a budget restarted per record · fixture `tests/cases/types/recursive-record-storage-refused.vl` · was compiler trap · found by the type hash-cons 6b `fieldStorageEq` census · filed 2026-11-16 against master `a9ae9324a`**

Repro:

    type A = { n: A | null, v: i32 }
    type B = { n: B | null, v: i32 | null }
    function show(x: B) { print(x.v ?? 0) }
    const a: A = { n: null, v: 3 }
    show(a)
    // vl check: the compiler itself trapped, "call stack exhausted" (rc 70)

#### Mechanism

`fieldStorageEq(a, b, depth)` (`check_ty_relate.vl`) compares two field types' storage. For two
records it called `recStorageField`, which asked `fieldStorageEq(…, REC_STORE_DEPTH)` of each field
pair: a fresh budget at every record level. A recursive pair (`A` beside `B`) therefore recursed
through its recursive field forever. With the differing field first (`{ v: i32, n: … }`) the walk
returned at it before recursing, and the delivery was a clean check reject. The close threads the
record pairs the walk is inside through `recStorageField`; a pair met again is stored alike so far,
so the answer is decided by the fields outside the cycle, as the exhausted budget answered.
