### D3227 — a rest-parameter function handed to a hole callee is called with a bare element, and the module fails to validate

**check-clean invalid wasm · clause 1 · found by lane BI grading D3225's forwarding cases · the same on master `94670f728` · filed 2026-09-29 against master `94670f728`**

Repro:

    function f(...xs: i32[]): i32 {
      return xs.length
    }
    function H(h, v) {
      return h(v)
    }
    print(H(f, 7))
    // vl check: rc 0.  vl run: invalid module inside `H`: type mismatch: expected (ref $type), found i32

#### Mechanism

Not localised past the ablation. As a value, `f` has the type `(i32[]) => i32`: the rest
parameter is one list parameter, and `const g = f; g(7)` is refused with `argument 1: expected
i32[], got i32`. Through the hole, `h(v)` is never compared with that parameter (D3225 holds
only scalar pairs), and the emitter passes the `i32` where the list is expected. Which answer
is right, the value call's refusal or the direct call's spread (`f(7)` prints `1`), is the
question D3171's design note leaves open for rest parameters, so this row carries no `Want:`.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `f(7)`, the direct call | prints `1` | **yes** (the hole callee) |
| `const g = f`, then `g(7)` | check reject, `expected i32[], got i32` | **yes** (the hole callee) |
| `h(v, v)`, two arguments | the same invalid module | no |
| `f(a: i32, ...xs: i32[])` | the same invalid module | no (a leading parameter) |
