### D14974 — a lambda's open collection result, written into another lambda's, takes a default rep and traps at the call

**closed · runs, prints `q` · was trap after load, clause 1 · closed by linking two open collections that meet at a store, maps as lists already were (D1470), and resolving the links at each scope close (`resolveHoleLinks`); the plain twins now run too · filed 2026-11-02 against master `fe466a461`**

Repro:

    let a = (x: i32) => Map()
    let b = (x: i32) => Map()
    b = a
    const m = b(1)
    m["a"] = "q"
    print(m["a"] ?? "none")
    // vl check: rc 0.  vl run: wasm trap, indirect call type mismatch

#### Mechanism

`b = a` lines `a`'s function type up against `b`'s, and both results are open, so nothing is
pinned and no link is noted; the write through `b(1)` then pins only `b`'s map. `a`'s lambda
is built at the defaulted map and called at `b`'s. The plain twins (`let a = Map()` /
`let a = []`, then `b = a`) are refused at check as `cannot infer a type for 'a'`: an open
result inside a function type is never queued for that scope-close check (`unresolvedHole`
answers false for `TyFunc`), so it reaches the emitter instead.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| module scope (the same bindings inside a function body) | still traps | no |
| the map (`(x: i32) => []`, `m.push("q")`) | still traps | no |
| the lambdas (`let a = Map()` / `let b = Map()`, `b = a`) | loud check reject, `cannot infer a type for 'a'` | **yes** |
| the assignment `b = a` | runs | **yes** |

#### Grading list

`global_assign/un-annotated` of `fn-value-lambda-result-map` and
