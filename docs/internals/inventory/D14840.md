### D14840 — a hole function's result from a call handing it a generic it calls at two types, inside an instance, loses its type once the generic is a set's id

**closed 2026-11-01 · runs, prints `aa` then `10` · was loud emit reject · clause 2 · `holeCallInstOf` (`check_relate_core.vl`) types a call through a hole parameter bound to a tagged set as each member's call at the call's own arguments (`holeSetCallRetOf`), since the set's signature names its members' own holes and is never substituted · pin: `tests/cases/closures/hole-fn-result-of-two-type-generic-handed-on-in-instance.vl` · present on master `f6db0729f`, with the split plan on and off · filed 2026-11-01 against master `f6db0729f`**

Repro:

    function both2(n, f) {
      print(f("a"))
      return f(n)
    }
    function twice(s) { return s + s }
    function two(a, b) { return b }
    function go(z) { print(two(1, both2(z, twice))) }
    go(5)

Want:

    aa
    10

#### Mechanism

The late tag decision tags `{twice}`, the argument `both2` calls at two types. In the elaboration's next round, the instance `go<i32>` re-checks `both2(z, twice)` and gives it no type: the capture of `twice` there is its declaration's hole signature `(_) => _`, not the set's type, so `both2`'s result stays open. The row for `two(1, …)` is then open too, and no instance of `two` is minted. Mono builds a `two` with no parameters, and the call refuses at emit. The first round, with `{twice}` still a closure, types the call `i32` and mints `two<i32, i32>`.
