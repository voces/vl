### D3331 — an integer intrinsic's operand was recorded as a delivery, so `ltU(a, b)` typed a literal `let` `i32` against its own `i64` store

**closed · fixture `tests/cases/numerics/literal-binding-intrinsic-operand.vl` · was a loud check reject (`cannot assign i64 to i32` at the store, plus `` `a` takes its type from its uses, and they conflict ``) · plumb PL-078 (3 of ~400 generated units: chunk_60, chunk_98, chunk_99) · regression from D3246 · filed and fixed 2026-09-29 against master `b6378e95b`**

Repro:

    function get() { 5000000000 }
    function f() {
      let a = 0
      a = get()
      print(ltU(a, 3))
      print(a)
    }
    f()
    // was: vl check refused `a = get()` — cannot assign i64 to i32

Want:

    false
    5000000000

#### Mechanism

`numIntrCallTy` decides an integer intrinsic's width from its operands, then checks each operand
against that width through `assignableExpr`, which records every check as a delivery for the
literal-binding solve (D3246). On the first pass `a` is still `i32`, so `ltU(a, 3)` delivered `a`
whole to an `i32` destination, which conflicts with the `i64` store; a tree operand
(`popcnt(a & 255)`) vetoed `i64` the same way. The operand check now names no destination
(`lbiNoDest`, the flag a type-parameter argument already set), so an intrinsic's operand chooses
and vetoes nothing, as a binary operator's operand does.

#### Ablation

| ingredient changed | outcome before the fix | needed? |
| --- | --- | --- |
| `a < 3` instead of `ltU(a, 3)` | runs | **yes** (the intrinsic) |
| `popcnt(a)`, `divU(a, 7)`, `popcnt(a & 255)` | refused | no (any integer intrinsic, whole or tree operand) |
| drop `a = get()` | runs | **yes** (an `i64` delivery or store) |
| plumb's shift block (`const x = rax; rax = (x << c) & 4294967295`) | the minimiser removed it with the refusal intact | no (scenery) |
| `sqrt(x)` over a float literal `let` stored `f32` | runs, `f64` both before and after | no |

#### Grading list

The three plumb units check. A literal `let` met only as an intrinsic's operand now stays `i32`
where master made it `i64` (`ltU(x64, d)` after `d = 2147483647; d = d + 1` prints `true` with
`d` = -2147483648, as `x64 < d` already did on master); the fixture pins that value.
