### D2400 — a declared operator that writes a field of its operand does not end that field's narrowing

**closed 2026-09-25 — now a loud check reject (`'b.value' is no longer narrowed to f64: the
operator '+' on line 8 may reassign it`) · was loads then traps, clause 1 · filed against master
`2304ece42`, closed against master `a277bf7b0` · fixture
`tests/cases/soundness/declared-operator-ends-operand-narrowing.vl`**

Repro:

    type W = new { value: f64 | boolean }
    function "+"(self: W, o: W): W {
      o.value = true
      self
    }
    function f(a: W, b: W): f64 {
      if b.value is f64 {
        const c = a + b
        print(c.value is f64)
        return b.value as f64
      }
      0.0
    }
    const a: W = { value: 1.0 }
    const b: W = { value: 1.5 }
    print(f(a, b))
    // vl check: rc 0.  vl run: prints true, then wasm trap: cast failure

#### Mechanism

A path narrowing (`b.value`) ends at a call through `noteCallInvalidations`, which only a `Call`
node reaches. `a + b` that dispatches to a declared `"+"` is a call to that declaration, but it is
a `BinExpr`, and `callInvalidatesNarrowedPath` answers false for any node that is not a `Call`,
so the write-effect summary of `"+"` is never asked. The bare-name leg of `callMayWrite` does
treat a dispatched operator as a call (D2390); the path leg needs the operands mapped to the
declaration's parameters, as `callArgPlaces` does for a call.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the `a + b` line | runs, prints `1.5` | **yes** |
| the write `o.value = true` | runs, prints `true`, `1.5` | **yes** |
| the operator (the same body as `add(a, b)`) | loud check reject naming `add` | **yes** — the named call is caught |

#### Grading list

The same shape through an operator declared on a `new v128` brand, and through an operator
closure field; a declared operator whose body calls a function that writes the operand. The
owner floated, not decided, restricting an operator's side effects to its own operands.

#### Close

A dispatched operator now goes through `noteCallInvalidations` like a call, and
`callMayWrite`'s path leg answers for it: `opSiteDecls` names the declaration the checker
resolved at the site (every declaration of the operator when it is not yet resolved, opaque for
an operator closure field) and `opSiteArgs` maps `a op b`, `p[i]` and `p[i] = x` to its
parameters, through the same `declWritesPath` a call uses. An operator site inside a callee's
body now composes into that callee's write summaries (`opEffectsOn`, `opFreeEffects`), which
closes the grading list's operator-in-a-body spelling. An operator closure field is opaque, as a
call through a closure field already is, so a read-only one ends a narrowing it need not.
