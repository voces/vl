### D3043 — `-(-2147483648)` under an i64 operator is emitted as an i32 operand of an i64 instruction

**closed 2026-09-28 — the filed repro prints `2147483653` · was check-clean invalid wasm, the same on master `3a71bb1f9` and `0b618d160` · closed by the one rule both sides now follow: a negation chain over one integer literal is a literal tree, so a 64-bit destination adopts it as it adopts `1 + 2` (`litTreeWideTy` admits `litTreeOps == 0`, except over a decimal that fits i32, which never wraps), and the emitter's I32_MIN arm yields to a chain the checker typed i64 · fixture `tests/cases/expressions/negation-chain-at-i64.vl` · found by the #3262 review · filed 2026-09-28 against master `3a71bb1f9`**

Repro:

    function g(): i64 { 5 + -(-2147483648) }
    print(g())

#### Mechanism

The checker types `-(-2147483648)` in an i64 context as i64 (`5 + -(-2147483647)` prints `2147483652`,
so the sum is i64 math). The emitter's `exprIsI64` exempts `-2147483648` as an i32 literal at `I32_MIN`
and passes that answer up through the outer `-`, so it types the operand as i32. The `+` then emits
`i64.add` over an i32 operand, which is invalid wasm. [D3049](D3049.md) is the same disagreement
where no i64 instruction consumes the value, so it reads the wrong value instead.

#### Ablation

| spelling | outcome |
| --- | --- |
| `5 + -(-2147483647)` in `(): i64` | runs, `2147483652` |
| `5 + -(-2147483648)` with no return annotation | runs, `-2147483643` (i32) |
| `5 / -(-2147483648)` in `(): i64` | invalid wasm, same message |
| `const K: i64 = 5 + -(-2147483648)` | invalid wasm in top-level code |
| `-(-2147483648)` alone in `(): i64` | runs, wrong value ([D3049](D3049.md)) |
