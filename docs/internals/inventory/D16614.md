### D16614 — a push onto a list literal holding a spread of a record list is refused as a write through the spread list

**loud check reject · clause 2 · `a {x: i32}[] cannot be delivered as {x: f64}[] here: the call to v.push on line 3 writes a widened element or field` · a spread copies its list, so `v` shares no list with `s` · found by lane J building D16449 · filed 2026-11-15 against master `e56efd8c2` · open**

Repro:

    const s = [{ x: 1 }]
    const v = [...s, { x: 2.5 }]
    v.push({ x: 7.5 })
    print(v.length)
    // vl check: a {x: i32}[] cannot be delivered as {x: f64}[] here: the call to `v.push` ...

Want:

    3

#### Mechanism

The write scan judges the spread argument `s` as a list delivered into `v`, so a widening write
through `v` is charged to `s`. A spread hands over the list's elements, not the list: `v` is a
new list, and only its records are shared. The records are built where `v`'s are (D16440), so no
write through `v` reaches a record of `s` at the wrong storage; the annotated spelling, where `v`'s
type is not inferred from the spread, already runs.
