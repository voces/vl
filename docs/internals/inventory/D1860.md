### D1860 — a `for`'s SECOND binding name has no declaring-token column, so the editor resolves it to the FIRST name

**runs today and must keep running · filed 2026-09-07 with B8's second binding name · the loop RUNS and both names bind correctly; what is wrong is the editor's answer about the second one**

`declNameTok` is one token per arena node (`ast.vl`), and `parseFor` stamps it with the FIRST
name's token (`mkDeclNameTok(fiix, vTok)`). `checkForInNode` then calls `symDecl` twice against
the SAME node, so `symDeclTok` hands both bindings that one token: hover, go-to-definition and
rename on `i` in `for v, i in xs` resolve to `v`'s token rather than its own. `symbols.vl`'s
`sidOf` arm has the same shape — one sid per node — so the second name has no sid of its own
either. Nothing in the compiler's own pipeline reads either column for a loop variable, which
is why the loop runs correctly and every gate is green.

Repro:

    const xs = [10, 20, 30]
    for v, i in xs {
      print(i)
      print(v)
    }
    // vl run: 0 10 1 20 2 30 — the program is correct.
    // The defect is the EDITOR's: rename `i` and `v` is renamed instead.

#### Mechanism

One `declNameTok[nodeIx]` and one `sidNode[nodeIx]` per node, and a `for` with a second name
declares TWO bindings at one node. The fix is a parallel column (`declName2Tok`) plus a second
sid, or a synthetic node per binding; the second is larger and would move the slot pre-order
the collect pass and the emitter share, so the column is the cheaper shape.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the second name (`for v in xs`) | the editor is correct | **yes** |
| the ARRAY iterable, for a map (`for k, v in m`) | same, one token for two names | no |
| running the program | unaffected either way | no — this is editor-only |

#### Grading list

The close must re-grade hover, go-to-definition and rename on BOTH names, over an array, a map
and a set, and must leave the loop's own slot pre-order untouched — `tests/cases/loops/for-pair-index.vl`
and `for-pair-map.vl` are byte-identity witnesses for that half.
