### D2436 — a declared scalar field's row takes an un-annotated literal's list field

**closed 2026-09-25 — the witness prints `2` then `3` · was check-clean invalid wasm, clause 1 · the D2423 family, found by the #3147 review, filed 2026-09-25 against master `a277bf7b0` · fixture `tests/cases/objects/declared-row-literal-destination.vl`**

Repro:

    type Q = { k: i32 }
    const q: Q = { k: 3 }
    const xs = [1, 2]
    const r = { k: xs }
    print(r.k[1])
    print(q.k)
    // vl check: rc 0.
    // vl run (as filed): Error: invalid module. Now prints 2 then 3.

#### Mechanism

A differing field code against a declared row was lenient, for adoption, and between two codes
whose layout the code alone decides it had no exception. So `{ k: xs }` (an `i32[]`, code 4) took
`Q`'s `i32` row (code 0). No adoption turns a list into a scalar or a string, so
`declRowFieldFits` now refutes a scalar-list or string-list code against any other self-contained
code, in both directions. The `string` against `string[]` twin (codes 3 and 6) failed the same way.
