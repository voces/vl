### D16766 — a same-elements result of a built list is refused where a narrower element type is declared, though its receiver delivered there adopts the build and runs

**loud check reject · clause 2 · CAPABILITY: the receiver runs at the same positions · `this container's {f: null} elements are stored at J, the row its stores build; handing it on as {f: null}[] is type-valid but not supported yet` · the clause-1 close of D16763 left this refusal in place of invalid wasm · found by lane WIDTH · filed 2026-11-16 against master `6822b8e75`**

Repro:

    type J = { f: i32 | null }
    function mk2() { return { f: null } }
    const dA: J = mk2()
    const src = [mk2()]
    const v: { f: null }[] = src.filter((y) => y.f == null)
    print(v[0].f)
    // vl check: rc 1, the built-container refusal at the call

Want:

    null

#### Mechanism

`const v: { f: null }[] = src` runs: the annotated binding takes the receiver's build. A
`filter`, `slice`, `values` or identity `map` result is the receiver's own elements (D16763), so
it should adopt the same way. Instead `recBuiltReadRefuse` refuses it, because the adoption
(`recAnnArgTakesRep` for arguments, the binding's own path for `src`) does not reach a call. A list
twin of `storeRetsResolve`'s record stamp would also cover the list a function returns.

| the annotation on `v` | runs | **yes** |
