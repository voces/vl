### D3867 — a module-scope hole lambda pushed into a typed list inside a function is emitted at the hole's `i32` default

**check-clean invalid wasm · found by the rv3458 review of #3457/#3458 (pa/r16.vl) · filed 2026-10-08 against master `fd225840b`**

Repro:

    const c = (y) => y + "C"
    function m(x: string) {
      const fs: ((y: string) => string)[] = []
      fs.push(c)
      print(fs[0](x))
    }
    m("a")
    // vl check: rc 0.  vl run: rc 70, invalid module inside `c`, `type mismatch: expected (ref $2), found i32; $2 is string`

Want:

    aC

#### Mechanism

A hole lambda takes its parameter type from the call sites and deliveries that pin it. The
typed list `((y: string) => string)[]` pins `c` when the list is BUILT (`[c]`, in or out of a
function), but a `push` of `c` into an existing typed list inside a function delivers it through
a method call the pinning does not read, so `c` keeps the `i32` default and `y + "C"` is emitted
over an `i32`. The same happens for an element store, `fs[0] = c`, and for a module-scope `push`;
a direct call of `c` elsewhere in the program (`print(c("q"))`) pins it and the program runs.
The `f64` spelling is not invalid wasm: it loads and traps with `indirect call type mismatch`.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the `push` (build the list as `[c]` at module scope) | runs, `aC` | **yes** |
| the `push` (build the list as `[c]` inside `m`) | runs, `aC` | **yes** |
| the function scope (the `push` at module scope) | still invalid, inside `c` | no |
| the call `m("a")` | still invalid, inside `c` | no |
| the call `fs[0](x)` (print `fs.length`) | still invalid, inside `c` | no |
| the hole on `c` (`(y: string) => y + "C"`) | runs, `aC` | **yes** |
| a direct call `c("q")` elsewhere in the program | runs, `qC` / `aC` | **yes** |
| the list (a typed binding `const f: (y: string) => string = c`) | runs, `aC` | **yes** |
| the string type (`i32` lambda and list) | runs, `2` | **yes** |
| the string type (`f64` lambda and list, `m(1.0)`) | loads, traps `indirect call type mismatch` | no (other outcome) |
| `push` replaced by `fs[0] = c` over a one-element list | still invalid, inside `c` | no |

#### Grading list

The `f64` spelling above is the same delivery with a different outcome and should be re-graded
when this closes. Neighbours that run today and must keep running: `[c]` at module scope and
inside `m`, the annotated lambda with `push`, and a typed binding `const f: (y: string) =>
string = c`. A sibling pushing a lambda written BY NAME inside the function (not a module-scope
hole) was not probed here.
