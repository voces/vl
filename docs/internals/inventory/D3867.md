### D3867 — a module-scope hole lambda pushed into a typed list inside a function is emitted at the hole's `i32` default

**closed (2026-10-08, lane SC) · was check-clean invalid wasm · found by the rv3458 review of #3457/#3458 (pa/r16.vl) · filed 2026-10-08 against master `fd225840b` · pins: `tests/cases/closures/hole-lambda-pushed-into-typed-list.vl`, `tests/cases/closures/error-hole-lambda-pushed-into-incompatible-list.vl`**

Repro:

    const c = (y) => y + "C"
    function m(x: string) {
      const fs: ((y: string) => string)[] = []
      fs.push(c)
      print(fs[0](x))
    }
    m("a")
    // vl check: rc 0.  vl run: rc 70, invalid module inside `c`, `type mismatch: expected (ref $2), found i32; $2 is string`

Want:

    aC

#### Mechanism

A hole lambda takes its parameter type from the call sites and deliveries that pin it. The
typed list `((y: string) => string)[]` pins `c` when the list is BUILT (`[c]`), but a `push` of
`c` into an existing typed list, or an element store `fs[0] = c`, delivers it through a method
call or an index the pinning does not read, so `c` kept the `i32` default and `y + "C"` was
emitted over an `i32`. Both are now deliveries at the list's element type, as D3862's typed
parameter is (`monoNotePushDeliveries`, the `Index` arm of the assignment walk). A name already
pinned at another signature takes an instance at this one, so `twice` pushed into a list of
`string` functions and a list of `i32` ones runs both. The `f64` spelling runs too. A pushed hole
lambda whose body cannot take the element type (`y * 3` into a list of `string` functions) is
refused at the push, as the element store already was, rather than lowered at the default.

#### Grading list

The `f64` spelling above is the same delivery with a different outcome and should be re-graded
when this closes. Neighbours that run today and must keep running: `[c]` at module scope and
inside `m`, the annotated lambda with `push`, and a typed binding `const f: (y: string) =>
