### D15540 — a list whose element is a literal-union map beside its plain twin (`LM | IM`) has no list rep

**closed 2026-11-09 — the filed repro prints `1` · was a loud emit reject, clause 2 · ruled a capability, not a declaration refusal: a union whose members are one map and its twins (`mapTwinUnionMember`, check_ty_rep.vl) is stored as that one map (`storedTyOf`), and every rep reader and delivery position reads it so, a call result's `exprUnion` included · position matrices `map-twin-union-delivered` and `map-twin-union-through-generic` grade 48 of 48 RUNS after, 0 SILENT · fixture `tests/cases/maps/map-twin-union-is-its-one-map.vl` · filed 2026-11-07 against master `eb8356fe8`**

Repro:

    type LM = {[i32]: 1 | 2}
    type IM = {[i32]: i32}
    const mi: IM = Map()
    const u: LM | IM = mi
    print([u].length)

Want:

    1

#### Mechanism

`{[i32]: 1 | 2}` reads as its base map `{[i32]: i32}` (D2493), so `LM | IM` is a union of two
members with one box representation. The value itself builds and passes. A list of it does not:
neither the list literal's element nor the declared `(LM | IM)[]` gets a list rep, and every
consumer of the list refuses at emit. The checker refuses the analogous `Set<i32> | {[i32]:
boolean}` at its declaration ("a union cannot hold both … yet") but accepts this pair. The ruling
took the list rep: nothing can tell the members apart, so the union is its one map.
