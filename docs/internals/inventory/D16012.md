### D16012 — a nested generic that shadows its encloser's type-parameter name re-parses its `let` annotation, because substituting by name cannot tell the two parameters apart

        const ys: T[] = [y]

#### Mechanism

`letDeclResolveAnnot` re-checks a `let` annotation inside a quiet inference pass. The annotation
node already holds the type an earlier check of the same body recorded, and with the pass's
type-parameter bindings substituted (`substTyDeep(held, tpEnvNames, tpEnvTys)`) that held type is
the re-parse's answer, so the annotation reads it. Here `inner` redeclares `outer`'s `T`, so the
binding list names two parameters `T`. Substitution by name cannot tell them apart and can give a
concrete but wrong type (`boolean[]` for `ys`, which is `f64[]` at `inner(2.5)`). A binding list
with a repeated name therefore re-parses the spelling. The checker keys a type parameter by its
name; telling two parameters with one name apart needs a parameter identity, which is checker
work and is carried past step 7.

#### Grading list

- Every `let` annotation inside a nested generic that redeclares an enclosing type-parameter name,
  at one and several enclosing instances.
