### D3188 — a `.map` callback that joins its hole with an `f64` at an `i32` pin builds an `i32` list its readers take as `f64`

**loud emit reject · clause 2 · the `gen_K4_*_0` cells of the #3280 review's `h` grid (`rv3280r4-3058/h`, the `i32` pin, every receiver and position), invalid wasm on master `a6cb22568` and loud since `scalarListWrap` refuses a wide list no build collected · filed 2026-09-29 against master `a6cb22568`**

Repro:

    function t<T>(x: T) {
      const n = [x].map((e) => {
        if 1 > 2 { return e }
        return 1.5
      })
      for y in n { print(y) }
    }
    const a: i32 = 4
    t(a)
    // vl check: rc 0.  vl run: emit error, a list of this element kind is read where no such list was built

Want:

    1.5

#### Mechanism

The callback's lifted function returns `f64` at the pin, and the checker types `n` as `f64[]`,
but `mfResultKindOf` reads the callback's kind as `i32`, so `.map` builds an `i32` list and no
`f64` list type is collected. The for-in over `n` then named an uncollected wrapper and was
invalid wasm; it is now refused (`scalarListCollected`). With `x: i32` and no type parameter it
prints `1.5`.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `function t(x: i32)` | prints `1.5` | **yes** (the pin) |
| `[4].map(…)` at top level | prints `1.5` | **yes** |
| `return 1.5` alone | prints `1.5` | **yes** (the join with the hole) |
