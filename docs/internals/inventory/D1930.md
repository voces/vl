### D1930 — a union coercion asks which arm stores an i64, at every classified kind except i64 itself, so a big integer literal boxed into a float-only union asked for a value box the module never minted

**closed 2026-09-07 — the witness prints `2147483648` · was a loud emit reject, `emitProgram: union atom has no value box`, `vl check` rc 0 · clause 2 · found by [D1890](D1890.md)'s position matrix, PRE-EXISTING and independent of it · fixture `tests/cases/numerics/f64-literal-adopt-positions.vl`**

Repro:

    // vl check: rc 0.  vl run (before): emitProgram: union atom has no value box

#### Mechanism

`emitUnionCoerce`'s value-atom ladder asks `unionStoreAtomKind` — "which arm does this union
store such a value as" — on the string, list, f32 and i32-classified arms, and D978 wrote the
f32 one out by hand for exactly this reason. The `exprIsI64` arm asked nothing: it set the
atom to `i64` unconditionally. A union with no `i64` member therefore got an `i64` tag, and
the scalar wrap then looked for an i64 value box that a `f32 | null` module never mints.

The only i64-classified value the checker admits into such a union is an integer LITERAL that
the float arm holds exactly — the contextual grant is exactness-gated at both widths — so
adopting the union's float arm is lossless by construction, which is why the arm can be
symmetric with the f32 one rather than needing a new rule.

Two lines below it the same ladder's `else` branch already carried the paragraph this arm
needed: *"Promoting to `i64` alone is not enough: an integer flowing into a union whose only
numeric atom is a float would stay `cak = 0` and box an i32 into the f64 or f32 value box."*
The reasoning was written down one width down and the arm above it never got it.
