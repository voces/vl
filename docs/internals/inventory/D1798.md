### D1798 — substituting a type parameter into `readonly T[]` drops the read-only flag, so the pinned parameter refuses a read-only argument the written spelling accepts

**loud check reject · filed 2026-09-07 against master `5ef63bb50`**

Repro:

    function gen<T>(self: T[], other: readonly T[]): i32 { return self.length + other.length }
    function src(): readonly i32[] { return [5, 6] }
    const xs: i32[] = [1]
    print(gen(xs, src()))
    // vl check: argument 2: expected i32[], got readonly i32[]

#### Mechanism

`readonly T[]` is a `TyArray` carrying an `aRead` flag (#2828). The flag survives a
WRITTEN annotation and it survives into the callee's body — a `push` through `other`
inside `gen` still refuses with the view's own sentence — but it does NOT survive
`substTyDeep` at the pin: `T := i32` rebuilds the parameter as a plain `i32[]`, and a
read-only view is then correctly rejected as an argument to a mutable list.

The tell is that the same parameter type refuses the argument only when it is GENERIC.
Both spellings are the same two words apart, and only the substituted one moves.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the type parameter — `mono(self: i32[], other: readonly i32[])` | accepts the read-only argument | **yes** |
| the read-only ARGUMENT — pass a mutable `i32[]` | accepted, and it licenses the covariant source | **yes** |
| `readonly` on the parameter — `other: T[]` | refuses the read-only argument in the SAME words, and still accepts a covariant source | no |
| the UFCS spelling — `xs.gen(src())` | refuses identically | no |

The second row is what makes this narrow rather than a broken flag: a MUTABLE argument
still reaches the parameter and runs. Only an argument that is ALREADY a read-only view is
turned away — and the third row says the `readonly` spelling is not what turns it away,
since the mutable parameter refuses the same argument in the same words. The flag's work
is in the BODY (D1799), not at the call.

#### Grading list

`std:array`'s `extend<T>(self: T[], other: readonly T[])` is the consumer: its covariant
source runs and its read-only source is refused by this row, so `tests/cases/std/array-extend.vl`
pins what works and `.../error-array-extend.vl` pins this refusal. When this row closes,
the read-only source moves from the error fixture to the running one.
`tests/cases/unions/list-covariant-readonly-view-write-rejected.vl` must keep refusing — the
body-side guard is not what is broken here.
