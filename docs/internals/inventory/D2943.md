### D2943 — an element read off a hole parameter at a `(boolean | null)[]` pin prints the niche's `i32`

**closed 2026-09-28 — the filed repro prints `null` then `true` · was check-clean silently wrong, clause 1, the same on master `8615a730d` · closed by reading an element-value derivation off a hole at the instance's binding (`holePinReadOf`) · filed 2026-09-28 against master `cab9694f8`**

Repro:

    function h(x) {
      print(x[0])
      print(x[1])
    }
    const v: (boolean | null)[] = [null, true]
    h(v)
    // vl check: rc 0.  vl run: prints `2` then `1`

Want:

    null
    true

#### Mechanism

`x[0]`'s recorded type is an element-VALUE derivation off the hole (`HD_ELEMV`, the read's
value type, which differs from the storage type only at a `u8[]` pin). `holePinReadOf`, which
`holeOperandTyOf` asks, followed field and element-storage derivations only, so the read resolved
to nothing and `exprNulBool` fell to the `i32` print. It now follows `HD_ELEMV` too, answering the
element's value type. [D2921](D2921.md) closed the same symptom where the list is a literal the
instance re-makes.

#### Ablation

| ingredient changed | outcome on master | needed? |
| --- | --- | --- |
| `h(x: (boolean \| null)[])` | runs, `null`, `true` | **yes** (the hole) |
| a `boolean[]` pin | runs, `false` | **yes** (the niche) |
| a second instance at `i32[]` | prints `2`, `7` | no |
| a `(string \| null)[]` pin | runs, `null` | **yes** |
