### D14641 — a lambda instanced through a hole parameter types its own parameter read at the non-null twin of the instance's nullable argument

**runs today and must keep running · refutation pin for a `string | null` read recovering by its recorded type instead of the destination seeds · filed 2026-10-28 against master `2405dba16`**

Repro:

    function idv<V>(v: V): V { return v }
    function h<T>(x: T): T {
      let k = idv
      k = (n) => n
      return k(x)
    }
    const sn: string | null = null
    const f = h(sn)
    if f != null { print(f) } else { print("null") }

Want:

    null

#### Mechanism

At `h<string | null>` the lambda's parameter `n` holds the argument's `string | null`. Its read
is recorded (`nodeTyAt` at the lambda's instance) as `string`, so a reader that recovers a
`string | null` cell by the read's recorded type (`ref.as_non_null` where the type excludes
`null`) traps on the null. The emitter today recovers by the destination's `nulString` /
`rawNullRead` seeds, which keep this read raw, so the program prints right. Deletion target of
the seeds' `string | null` rule: the elaboration types the lambda instance's parameter at the
argument's type, after which the recorded type can decide the recovery.

#### Ablation

Graded with the recorded-type recovery switched on (the reader the row pins):

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `let k = idv` then `k = (n) => n` (as filed) | traps | **yes** |
| `const k = (n) => n`, no generic in the binding | prints `null` | **yes** |
| the lambda's parameter annotated `n: T` | prints `null` | **yes** |
| `h` not generic (`x: string \| null`) | prints `null` | **yes** |

So the lambda's instance is mis-typed only as a member of a function set that also holds a
generic declaration: step 4's set machinery (a4cf), not the lambda's own elaboration.
