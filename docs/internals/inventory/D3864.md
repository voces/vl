### D3864 — a nested function nothing names, calling a binding at a signature the live calls do not, is lowered anyway and the module fails to validate

**closed (2026-10-08, lane SC) · was check-clean invalid wasm · 20 of the 700 gen5 function-scope programs (`g5f`) and 30 of a fresh 1,000 (`g5f2`), and 2 of gen4's 1,200 (`g4b`) by a second ingredient · filed 2026-10-08 against master `fd225840b` · pins: `tests/cases/closures/dead-nested-call-through-binding.vl`, `tests/cases/closures/error-hole-lambda-alias-in-written-cell.vl`**

Repro:

    function mk(x: string, n: i32) {
      const e = (y) => y + y + y
      const g = (y) => y
      let d1 = e
      function r1() { d1(x) }
      d1 = g
      print(d1(n))
    }
    mk("a", 4)
    // vl check: rc 0 (r1 unused).  vl run: invalid module inside `r1`,
    // `expected i32, found (ref $type)`

Want:

    4

#### Mechanism

D3857 gives a binding one signature from the calls that can run, and leaves out a call in a
function nothing names (`monoWriteFrameDead`). That function was still lowered, with its call
through `d1` at `string` against the `i32` instance the live calls fixed, so the module did not
validate. A nested function, or a `const`-bound lambda, that neither it nor an enclosing function
is named in its parent's body is now lowered as an empty stub (`monoNestedFnDead`), as an unread
hole lambda is (D3832). A named function a member call spells, which a `self`-function call
would be, is kept. Named anywhere, as a value in a list too, it is live and the two signatures
are refused as before.

The two `g4b` programs are a second ingredient: a hole lambda nothing calls, reaching a capture
cell a nested function writes through another binding (`let d1 = c; let d2 = d1`). By name it is
refused (D3851); through the binding it built invalid wasm. It is now refused the same way.
