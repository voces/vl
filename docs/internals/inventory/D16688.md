### D16688 — a refused map key type cascades into `array index must be i32` at every later index of that map

**closed 2026-11-16 · now a loud check reject reported once: an index of a receiver typed `TY_ERR` adds nothing (`checkIndexNode`, check_access.vl); a parameter or return annotation over a refused key takes the key sentence, as a binding does, where it said `unknown type '{[boolean]:i32}'` (`annUnresolvedErr`, check_annot_resolve.vl); the sentence's article follows the key (`An f64-keyed`) · first-error quality · found writing the A15.2 design note · filed 2026-11-16 against master `d30dbc538` · fixture `maps/error-unsupported-key-no-cascade.vl`**

Repro:

    type P = { x: i32, y: i32 }
    const m: {[P]: string} = Map()
    m[{ x: 1, y: 2 }] = "a"
    print(m[{ x: 1, y: 2 }] ?? "none")
    // was: A P-keyed Map isn't supported yet — `Map`/`Set` keys must be `string`, `i32` or `i64`
    //           array index must be i32, got {x: i32, y: i32}   (at 3:3)
    //           array index must be i32, got {x: i32, y: i32}   (at 4:9)

#### Mechanism

The key-type refusal (check_leaf_steps.vl, the `isn't supported yet` sentence) leaves the
annotation's type as something the index check then reads as a list, so each `m[k]` adds its own
error about an array index, which the program never wrote. The refused annotation should answer the
absorbing error type (or keep the map type with its key unchecked), so only the first error shows.
The sentence also reads `A i32[]-keyed` and `A f64-keyed` where the article should follow the
spelled type. Moot once A15.2 builds struct keys; the cascade stays for any key type still refused.
