### D3376 — an f32 `%` nested under another f32 operator builds a module that fails validation

**closed · runs, prints `1.5` · was check-clean invalid wasm · found by the #3316 review · filed 2026-09-30 against master `5e277ab52` · fixture `tests/cases/arith/float-remainder-f32-nested.vl` · closed 2026-09-30**

Repro:

    function f(x: f32) { x - 0.5 % x }
    print(f(2.0))
    // vl check: rc 0.  vl run: the module fails to validate inside `f`,
    // "type mismatch: expected f32, found f64"

Want:

    1.5

#### Mechanism

`spineFloatLeafBits` (`compiler/emit_classify.vl`) walks the arithmetic spine through `+ - * /`
only, so a `%` under another operator is one of its LEAVES. A leaf that `exprIsF64` claims and
that is not a bare float literal counts as a genuine f64, and `0.5 % x` is such a leaf:
`exprIsF64`'s arm calls a `%` f64 when either operand is (the literal is). So `binMixHardF64`
says the parent `-` has a hard f64 operand and lowers it at f64, while the `%` itself is still
emitted at f32. Adding `%` to `spineFloatLeafBits`'s operator list, the set `exprIsF64` and
`exprIsF32` already recurse through since D1586, made all nine probes below run with the right
values in a scratch build (`1.5`, `2`, `0.25`, `2.5`, `1`, `1.5`, `0.5`, `1`, `1.5`).

Closed by that change plus one more. `%` is now part of the spine `spineFloatLeafBits` walks, so
an f32 `%` whose only f64 claim is a literal operand no longer makes its parent a hard f64. The
first candidate made that change alone, and the #3324 review found 17 cells that ran on master
and built invalid wasm on it: a `%` of two literals (`ay + (ay + 0.5 % 2.0)`), or a `%` over a
literal-only operation, two operators deep. Walking into such a `%` counted no leaf at all, where
the checker and `exprHasHardF64` call it a genuine f64. That is D1983's mismatch, which the old
`%` leaf had been masking. The walk now counts any operation over literals alone as a genuine f64
leaf, which closes D1983 as well.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| the `%` alone (`x % 0.5`, `0.5 % x`) | runs | **yes** |
| `%` over the other operator (`x * 0.5 % x`) | runs | **yes** |
| `x % 0.5` under the `-` (`x - x % 0.5`) | same invalid wasm | no |
| `+` or `*` over the `%` (`x + 0.5 % x`, `x * (0.5 % x)`) | same invalid wasm | no |
| a parenthesised `%` (`x - (0.5 % x)`) | same invalid wasm | no |
| both `%` operands literal (`x - 2.0 % 1.5`) | runs | **yes** |

#### Grading list

The close was graded on a 47,840-case grid against master `afb0ecc08`: every operator in
`+ - * / %` nested under every other, at `f32`, `f64`, `i32` and `i64`, in five shapes
(unparenthesised, right- and left-parenthesised, unary `-` over the inner operation, unary `-`
over the right operand), with every choice of three leaves from two parameters and three
literals (`0.5`, `3`, `0.1` at float; `3`, `7`, `-2` at int). Each value was compared with a
Python evaluation at the same width (numpy `float32` rounding at `f32`, truncating `/` and `%`
at int). Master: 46,530 right, **1,060 invalid wasm** (all `f32`, every one containing `%`, in
all nine operator pairs with `%` on either side), 250 check refusals. With the fix: 47,590
right, 0 wrong, 0 invalid, the same 250 check refusals (an all-int literal compound beside an
`f32`, e.g. `x + (3 + 3)`), 0 runs lost and 0 printed values changed on a case that ran on both.
The binding, field, global, closure, argument and array-element positions of the `%` spine
print the same values as the Python evaluation too.
