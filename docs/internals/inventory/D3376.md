### D3376 — an f32 `%` nested under another f32 operator builds a module that fails validation

**check-clean invalid wasm · found by the #3316 review · the same on master `5e277ab52` · filed 2026-09-30 against master `5e277ab52`**

Repro:

    function f(x: f32) { x - 0.5 % x }
    print(f(2.0))
    // vl check: rc 0.  vl run: the module fails to validate inside `f`,
    // "type mismatch: expected f32, found f64"

Want:

    1.5

#### Mechanism

`spineFloatLeafBits` (`compiler/emit_classify.vl`) walks the arithmetic spine through `+ - * /`
only, so a `%` under another operator is one of its LEAVES. A leaf that `exprIsF64` claims and
that is not a bare float literal counts as a genuine f64, and `0.5 % x` is such a leaf:
`exprIsF64`'s arm calls a `%` f64 when either operand is (the literal is). So `binMixHardF64`
says the parent `-` has a hard f64 operand and lowers it at f64, while the `%` itself is still
emitted at f32. Adding `%` to `spineFloatLeafBits`'s operator list, the set `exprIsF64` and
`exprIsF32` already recurse through since D1586, made all nine probes below run with the right
values in a scratch build (`1.5`, `2`, `0.25`, `2.5`, `1`, `1.5`, `0.5`, `1`, `1.5`). It is not
applied, because a classification change needs its own grids.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| the `%` alone (`x % 0.5`, `0.5 % x`) | runs | **yes** |
| `%` over the other operator (`x * 0.5 % x`) | runs | **yes** |
| `x % 0.5` under the `-` (`x - x % 0.5`) | same invalid wasm | no |
| `+` or `*` over the `%` (`x + 0.5 % x`, `x * (0.5 % x)`) | same invalid wasm | no |
| a parenthesised `%` (`x - (0.5 % x)`) | same invalid wasm | no |
| both `%` operands literal (`x - 2.0 % 1.5`) | runs | **yes** |
