### D2682 — a concatenation delivered to a `string | null` destination reads a narrowed nullable operand raw

**closed 2026-09-26 — the witness prints `ok` · was check-clean invalid wasm (`expected (ref $type), found (ref null $type)`), identical on master before the site-cached append ([D2625](D2625.md)) · found reviewing #3192 · filed 2026-09-26 against master `525837973`**

Repro:

    type N = { s: string | null }
    function main() {
      const n: N = { s: "n" }
      const cur = n.s
      if cur != null { n.s = cur + "x" }
      print("ok")
    }
    main()

#### Mechanism

A `string | null` destination (a field, a local, a binding, a return, an argument, a list cell, a
map value, a struct-literal field) seeds `pendingNulString` for its whole right-hand side, so a
null-keeping value is read raw rather than through `ref.as_non_null`. The seed reached the
OPERANDS of a concatenation too: a narrowed nullable operand (`cur`) was read raw and handed to
`__str_concat__`'s non-null parameter. A three-part chain stashes its parts in nullable slots,
which is why only the two-part spelling failed validation. Closed by `emitStrCatOperand`
(compiler/wasmEmit.vl): every concatenation lowering (pairwise, n-ary, the binding accumulator
and the site-cached append) emits its operands with the raw-read seeds cleared, since an operand
is a string value whatever the destination is. Not in `emitStrValue` itself, which also emits a
nullable list literal's elements, where the seed is what types a bare `null`.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the nullable destination (`s: string`) | runs | **yes** |
| the narrowed nullable operand (`n.s = "a" + "x"`) | runs | **yes** |
| the concat (`n.s = cur`) | runs | **yes** |
| the two-part form (`cur + "x" + "y"`) | runs | **yes** |
| the field (a `let q: string | null` local, a return, an argument, a list cell, a map value) | invalid wasm | no |
| the loop (a site-cached append over `n.s`) | invalid wasm | no |
