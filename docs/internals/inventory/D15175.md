### D15175 — an un-annotated function popped off a list handed to a hole parameter is called through a closure built at another signature

**closed · runs, prints `6` · was trap after load, `vl check` rc 0, `wasm trap: indirect call type mismatch` · clause 1 · found planning [D15174](D15174.md) · filed 2026-11-03 against master `1cce3e60a` · closed 2026-11-03: a read method through an un-annotated parameter reads the argument's slot in the flow table (`ffReadKindOf`, fn_flow_shadow.vl), so the call through its value pins the slot and the function is built at the call's types rather than served by the uncalled stub · fixture `tests/cases/closures/fn-list-pop-get-through-hole-param.vl`**

Repro:

    function half(a) { return a * 2 }
    const m = [half]
    run(m)
    function run(m) {
      const g = m.pop()
      if g != null { print(g(3)) }
    }
    // Want: 6

#### Mechanism

The function set is untagged here, as it is for the `m[0]` spelling that runs, so the call takes
the closure path. What differed was the closure's function: mono's `monoStoredSlotFnTy` found no
pin for the list binding's slot, treated it as uncalled (D9100), and served `half` by the stub an
uncalled function gets, `() -> void`, which the `(i32) => i32` indirect call trapped on. The flow
table took a method on an un-annotated parameter only for a `map`/`filter` callback (D9230) or a
store (D9591); a read (`pop`, `get`) was opaque, so the call through its value pinned nothing.
[D15176](D15176.md) is the same read at module scope, which refused loudly instead.
