### D15366 — two returns of records whose list field holds functions of different results build an invalid module

**closed · runs, prints `1.5` · was check-clean invalid wasm, `vl check` rc 0, `type mismatch: expected (ref $type), found (ref $type)` inside the function · clause 1 · found closing [D15227](D15227.md), whose join note leaves a list a record holds out · filed 2026-11-04 against master `177b27d96` · closed 2026-11-04: a function's return join notes a list its returned records hold, as it notes one it returns bare (`elabFnRetJoinNote`, check_elab_cap.vl); a value `if` or `match` arm's record still is not noted, so [D15303](D15303.md) keeps its refusal · fixture `tests/cases/closures/returned-records-holding-lists-of-fns-of-different-results-runs.vl`**

Repro:

    function inc0(a) { return a + 1 }
    function half(a) { return a / 2.0 }
    function pick(b: boolean) {
      if b { return { fs: [inc0] } }
      return { fs: [half] }
    }
    print(pick(false).fs[0](3))

Want:

    1.5

#### Mechanism

The checker types the call `f64`. Each returned record is built at its own row with a list of its
own one-member set, and nothing tied those sets to the result's, so the set stayed untagged and
the closure lists' two rows disagreed. [D15227](D15227.md) ties them for a list returned bare.

The same note for a list a record holds works at a return and not at a value `if`: a returned
literal is built at the function's result row, while an arm's record is built at its own row, and
noting the list there turned [D15303](D15303.md)'s emit refusal into an invalid module. So the
return's join (`joinRetTys`) now notes a record's lists (`elabFnRetJoinNote`), and the arm join
(`joinArmTys`) does not.
