#### Mechanism

D1689 gave `anonValueFitsField` an element test, but only on its EQUAL-code arm. A code-28
value against a code-5 field is not an equal code: it falls past every composite arm
(`vc == 4 / 14 / 24 / 25 / 26 / 15`) to the terminal `true`, so the nullable holder still
matches the plain holder's row and mints none of its own. The probe, on the witness above:

    ROW 1 #anon1 [xs:5:<A> ]
    LIT node22 -> row1 #anon1 lit-fields[xs:5:<A> ]
    LIT node36 -> row1 #anon1 lit-fields[xs:28:<{r:i32}> ]

Rename one field and the second holder mints `#anon2 [ys:28:<{r:i32}>]` and both run, which
is what makes this the same family as D1689 rather than a niche-lowering gap.

The second half is visible in that same dump and outlives the code ladder: the two companion
columns are **not comparable as written**. Code 5's key is `anonRefListElemKeyOf`, which
renders `tyToNominalName` and reads `A`; code 28's is `refArrElemKeyDeferred(tyToEmitName(…))`,
which renders structurally and reads `{r:i32}` — the same element type, two spellings. So
refuting 28 against 5 is not enough on its own: whichever direction a close takes, one
producer has to answer the other's question.

This is pre-existing and unchanged by D1689's close: both seeds refuse this witness with the
same sentence at the same span. What the close DID change is the four-holder spelling, where
the two elements also differ — master refused it with D1689's own
`unknown struct field in field access` and the close reveals this row's refusal underneath.


**Told apart on the CODE, unified on the ELEMENT.** A code-5 field's slot is `(ref $arr)` and
a code-28 field's is `(ref null $arr)`, so the two are two wasm struct layouts and one row
cannot serve both however their elements are spelled — the refutation is the right answer, not
a merge. What must agree is the element KEY, so that the two fields intern ONE ref-list
wrapper and the two columns can be compared at all.

`anonValueFitsField`'s composite tail refuted `vc == 15` and let every other named-heap value
code fall to the terminal `true`; it now refutes on `fieldCodeRefsElemHeapC(vc)` — the same
predicate the equal-code arm above it and `structRowOfObjFieldSet` already apply — so 5, 15
and 28 each fit only their own code or the union box.

The second half is the column. Code 5's key came from a row-name-first ladder
(`anonRefListElemRow`, then `anonRefListElemKeyOf`'s NOMINAL render) and code 28's from
`refArrElemKeyDeferred(tyToEmitName(...))`, a STRUCTURAL one — so one element type was `A` at
one code and `{r:i32}` at the other. Both now come through `anonRefListElemKeyOfTy`, one
ladder over the array type, with the niche peeled first. **No program distinguishes the two
producers today** — every consumer that compares a code-5 key with a code-28 one goes through
`nestedStructNamesCompat`, which is canon-keyed and reconciles the two spellings, and the
unification is byte-identical over all 3,048 `tests/cases` modules. It is landed as the
prerequisite it is: the day the niche's element ladder admits an element no row names (D1691),
the two producers would key that element two ways.
