### D9731 — a `const` record of an un-annotated function both listed and handed directly to an un-annotated parameter leaves the function unpinned

**closed · runs, prints `4` `4` · was loud emit reject, `vl check` rc 0, `emitProgram: cannot take the generic function `inc0` as a value`, clause 2 · found closing [D9640](D9640.md) · filed 2026-10-22 against master `e8163edd5` · closed by the flow table registering the direct handing's field call (`ffBoundObjHasField`, fn_flow_shadow.vl), so both deliveries pin the binding's function at one slot · fixture `closures/hole-fn-record-relayed-to-param-field-call.vl` · with [D9642](D9642.md) closed; found here and closed with it: [D9950](D9950.md), [D9952](D9952.md)**

Repro:

    function inc0(a) { return a + 1 }
    function take2(a) {
      print(a.f(3))
    }
    const e = { f: inc0 }
    const xs = [e]
    take2(xs[0])
    take2(e)
    // vl check rc 0.  vl run: emit error: emitProgram: cannot take the generic function `inc0` as a value

#### Mechanism

[D9640](D9640.md)'s close follows a read to the record binding only while that read is the
binding's one read (`monoRecSrcReadOnce` in `monoOpenFnRecSrcPin`, emit_mono.vl), so that no
other read can see the binding at another type. Here `e` is read twice, both reads reach the
same parameter, and the pin declines at each.

| the list (`take2(e)` alone) | runs, `4` | **yes** |
| the hole in `inc0` (`inc0(a: i32): i32`) | runs, `4` `4` | **yes** |

#### Grading list

The two reads handed to two different un-annotated parameters calling the field at the same
type, and at two types.
