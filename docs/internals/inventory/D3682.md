### D3682 — a lambda whose body reads a record field is given the field's nullable result type, so a call through its declared function type traps

**closed 2026-10-05 — the witness prints `2` · was loads then traps, `indirect call type mismatch`, clause 1 · found by the #3384 review, pre-existing on master · filed 2026-10-05 against master `56af0f07e` · fixture `tests/cases/closures/lambda-field-read-through-fn-type.vl`**

Repro:

    type V = { x: f64, y: f64 }
    type P = { a: V, n: i32 }
    const p: P = { a: { x: 1.0, y: 2.0 }, n: 0 }

    print(getter()().y)

#### Mechanism

Confirmed. The emitter stores a record field as `(ref null $V)`, and `criClassify`'s field-read
rungs classify an un-annotated function returning one as `nulstruct`, so the lambda `() => p.a`
was `(func (param structref) (result (ref null $V)))`. A call through the declared `() => V` is
`call_indirect` at `(ref $V)`, and `call_indirect` compares function types exactly. The same held
for a named un-annotated `function h() { p.a }` used as a `() => V` value. Fixed by
`criSettleNonNullRecordRet` (emit_classify.vl), run once after `computeRetInference`'s fixpoint:
an un-annotated function whose checker-typed return is a non-null record settles at `struct`,
the kind its function type names, and its returns take the `ref.as_non_null` the return
boundary already owes (`retNeedsNonNullRecover`), as a declared `: V` return does.
