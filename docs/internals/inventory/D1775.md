### D1775 — a `type` ALIAS whose body is a negation type reps as a union BOX while its value stays a bare scalar, so `const x: N = 5` is check-clean invalid wasm; the inline spelling `const x: !string = 5` runs

**check-clean invalid wasm — `type mismatch: expected (ref $type), found i32` · found
2026-09-06 by the ROADMAP re-grade while grading A4 (negation types) · clause 1**

Repro:

    type N = !string
    const x: N = 5
    print(x)
    // vl check: rc 0, "Checked 1 file, no errors."
    // vl run:   Error: failed to parse WebAssembly module
    //           type mismatch: expected (ref $type), found i32 (at offset 0x94)

#### Mechanism

`wasm-dis` on the emitted module names it in one line:

    (global $global$0 (mut (ref $1)) (i32.const 5))

with `$1` the union box `(struct (field i32) (field anyref))`. The global's declared type is
the BOX and its initialiser is a bare `i32.const 5`, so the two disagree at the only place
the value lives. The checker is right to accept the program — `5` is not a `string`, so it
satisfies `!string` — and the rep classifier is what disagrees with it: reading the ALIAS's
body it answers "union" (a negation carries member structure) where the value is a scalar.
Named-vs-inline is the discriminator, which is the "two spellings, print the rep" shape: the
declared alias is what routes the annotation through the union rep, and the inline spelling
never reaches it.
