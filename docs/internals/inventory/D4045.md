### D4045 — an un-annotated lambda's list-literal return does not adapt to a `u8[]` element in a function-typed destination

**closed · runs, prints `2` · was loud check reject, clause 2 · found 2026-10-11 by lane L2's union-arm twin probes · filed 2026-10-11 against master `efd3c3f15` · closed with [D9742](D9742.md): the lambda's inferred `i32[]` is a result the `u8[]` slot's rep refuses, so it takes the slot's result when every value it returns is delivered to it (`finishInferredReturn`, check_inferred_return.vl) · fixture `closures/lambda-result-adopts-slot-result.vl`**

Repro:

    function g(f: () => u8[]) { print(f()[1]) }
    g(() => [1, 2])
    // vl run: 2

Want:

    2

#### Mechanism

The literal `[1, 2]` adapts to `u8[]` in every direct position (`const xs: u8[] = [1, 2]`, a
`u8[]`-returning function's body), and an un-annotated lambda's list-literal return adapts to
`f64[]` and `i64[]` element types in the same function-typed destination. Only the `u8` storage
element is missed. Not localised past the ablation: the message reads as though the lambda's
return were inferred `i32[]` without the expected function type, and whatever rescues
`f64[]`/`i64[]` there does not cover the narrowing to a storage element. The
destination's type is fully known, so under the literal-adaptation rulings (a literal adapts to
its typed destination) the program is legal and the refusal is a capability gap.
