### D1712 — a `??` join is keyed by the OPERAND's member order, so the same union declared the other way round is a different registry key and the name does not resolve

**closed 2026-09-06 — a union is a SET (owner ruling, #2812): `repCanonId`'s union arm sorts
its members' canon ids, the same rule and the same insertion sort its `TyObj` arm already
applies to field names · clause 1**

Repro:

    type A = { r: i32 }
    type M = A | i32
    function mkN(): i32 | null { return null }
    function st(): A { return { r: 8 } }
    const w: M = mkN() ?? st()
    if w is A { print(w.r) } else { print(0) }
    // prints 8 — before the fix, vl check rc 0 then exit 70, the emitted module failed to
    // validate: type mismatch: expected i32, found (ref $type)

#### Mechanism

The `??` result is built from the operand first, so `i32 | null` with an `A` default joins to
`i32 | A` while the program registered `A | i32`. `nodeRegisteredUnionName` resolves through
`unRowOfCanon`, which compares `repCanonId` — the interned STRUCTURAL id — and that id was
built by `hcUnionId` over the members in spelling order, so the two sequences interned as two
ids and the name came back "". The row's own filed measurement is what makes the sort safe and
is now the ruling: **box tags do not depend on member position** — a struct arm tags by its
variant index, an atom by `scalarTagOfKind`, both program-global — so the canon id is a lookup
identity and nothing positional reads it. The `TyObj` arm had already drawn exactly this
conclusion for field names ("`{a: i32, b: string}` and `{b: string, a: i32}` are the same type,
and declaration order alone keyed the twins differently"); the union arm now sorts too. Sorted,
never deduped: two members sharing one id are two arms, and the multiplicity survives a sort.

The order is a **total order over the members' canon ids**, not declaration order of the first
declaration. `repCanonId` runs during interning, with no registry to ask and no pass to be
inside, so a first-declaration rule would make a structural identity depend on program order
and on which spelling was seen first — a memo-generation hazard the id side has no way to
retire. Sorting ids is a pure function of the members, and it is what leaves `tests/cases`
byte-identical in **2,541 of the 2,542** modules that build.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the member order (`type M = i32 \| A`) | ran before and after | **yes** — the only difference |
| the struct arm (`type M = string \| i32` with a string default) | ran before and after | **yes** — a value join resolves without the registry |
| the null value (`return 4`, so the default is dead) | refused identically; now runs | no |
| the call operand (`const v = mkN()` first) | refused identically; now runs | no |
| the MIRROR declared beside it (`type MB = i32 \| A` in the same program) | ran at BOTH seeds | no — but it MASKS the defect, so a fixture carrying both orders sees nothing |
