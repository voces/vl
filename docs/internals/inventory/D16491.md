### D16491 — a radix tree cast `as f64` is computed at 32 bits before it converts

**closed 2026-11-15 · runs, prints `-4294967296` then `214748364700` · was check-clean silently wrong, clause 1 · an `as f64` cast over a radix literal tree reads the tree at `i64` (`litTreeAdoptDst`, check_operators.vl), as an `f64` destination does since D16390 · fixture `tests/cases/numerics/radix-tree-cast-f64.vl` · found by the independent oracle (fuzz-nightly cells `ar_s31_0104`, `ar_s43_0072`) · filed 2026-11-15 against master `7bf2afc7a`**

Repro:

    print(((-1) - 0xFFFFFFFF) as f64)
    print((100 * 0x7fffffff) as f64)
    // master: vl check rc 0, prints 0 then -100

Want:

    -4294967296
    214748364700

#### Mechanism

T2.3 (rulings 4.1, 4.2) makes the operand of `as f64` a float context: a radix literal there is the
value its digits spell, and a radix tree read at an `f64` computes at 64 bits. D16390 did this for
an `f64` destination and an `f64` peer, in `litTreeWideTy`, but the cast typed its operand as the
`i32` tree, so the emitter lowered `f64.convert_i32_s(i32.sub(-1, -1))`. A tree the fold reduces to
one constant (`(0 - 0xFFFFFFFF) as f64`) was already right.

#### Ablation

| spelling | master | needed? |

| `((-1) - 4294967295) as f64` | `-4294967296` | the radix literal: **yes** |
