### D2991 — an `i32 | null` value stored into a declared `f64 | null` field reads back as `null`

**closed 2026-09-28 — the filed repro prints `4` · was check-clean silently wrong, clause 1, identical on master `4dc94bd23` and on #3250 · closed with [D2974](D2974.md): an `i32 | null` box delivered where the destination holds `f64` or `i64` is rebuilt under the widened member (`recordWidenRetag`) · found by the #3250 review grid · filed 2026-09-28**

Repro:

    type D = { v: f64 | null }
    const x: i32 | null = 4
    const o: D = { v: x }
    print(o.v)
    // PRINTS null

Want:

    4

#### Mechanism

Not localised past the review grid. The checker lets `i32 | null` into `f64 | null`. The store
into the `f64 | null` field does not convert the `i32 | null` rep into it, so a non-null `4`
reads back as the field's `null`.

#### Grading list

The same value delivered through a parameter (`function g(d: D) { print(d.v) }` then
`g({ v: x })`) and through an annotated list (`const xs: D[] = [{ v: x }]`), and `i64 | null`
in place of `f64 | null`. All three printed `null` on master `f186a5415` and print `4` now; a
`null` value still prints `null`.
