### D16974 — a `Set` handed to an un-annotated parameter read by `.has` is refused as not a map

**closed 2026-11-19 by lane F1 · runs, prints `true` · was a loud check reject (`argument 1: expected a map, got Set<i32>`), clause 2 · an un-annotated parameter records the container operations its body applies, and the call resolves them against the argument's kind, so `.has` takes a Set or a map (`ctnRefusedOp`, `check_demands.vl`; `docs/internals/refactor-notes/2026-11-19-container-demand.md`) · the re-bound (`const v = a`) and generic-join spellings run too · fixture `tests/cases/maps/infer-param-has-takes-set-or-map.vl` · found by the capability-matrix rot sweep (`generic-tail-join-locals-set.matrix.vl`, `argument` un-annotated) · filed 2026-11-18 against master `bb90aa849` by lane F1**

Repro:

    function take(a) { print(a.has(1)) }
    const s: Set<i32> = Set()
    s.add(1)
    take(s)

Want:

    true

#### Mechanism

The parameter's `.has` call is inferred as a map's, so the argument check expects a map: "argument
1: expected a map, got Set<i32>". A `Set` has `.has` too, and the same call annotated at
`Set<i32>` runs.

#### Grading list

The repro, the parameter re-bound first (`const v = a`), and the set handed through a generic join.
