### D15355 — a map binding written a function outside the set of the map it is then reassigned is refused at emit

**closed 2026-11-09 — the filed repro prints `1.5` · was a loud emit reject, clause 2 (`emitProgram: unsupported map value type`) · the tag plan admits a store of a map whose value set is within the binding's, deciding the two sets together (`ftDstTakes`, check_fn_tag.vl), as D15535 needs · closed with D15535 · fixture `tests/cases/closures/map-binding-of-fns-reassigned-under-if-or-after-a-write.vl` · filed 2026-11-04 against master `73062b83`**

Repro:

    function inc0(a) { return a + 1 }
    function half(a) { return a / 2.0 }
    const fnMap = Map()
    fnMap.set("a", inc0)
    fnMap.set("b", half)
    function dbl(a) { return a * 2 }
    let m2 = Map()
    m2.set("a", dbl)
    m2 = fnMap
    const g = m2.get("b")
    if g != null { print(g(3)) }

Want:

    1.5

#### Mechanism

`m2` holds `{dbl}` and is reassigned a map of `{inc0, half}`: neither set is within the other, so the two cannot share one id numbering as D15233's pair does; running it needs the binding's set widened to the union, with the source's map built at it.

Which gate holds it: `monoStoredSlotFnTy`'s own-type gate (refactor-notes/2026-11-07-slot-type-and-instance-binding.md,
"Slot deliveries, switched"). `inc0` and `half` give different results at the pin, so the slot has
no one rep and declines. Typing it at the elaboration's one delivery instead prints `1.5` here, but
D15353, the same map iterated by key, traps (`indirect call type mismatch`), so a fix needs a
per-value rep, not the delivered type.
