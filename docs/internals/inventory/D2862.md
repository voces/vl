### D2862 — a record with a closure field bound by `let` in a hole-parameter maker reads the closure's result in the first pin's format

**closed 2026-09-27 · was check-clean silently wrong, clause 1, on master `1df19732b` · the `let` residue of [D2853](D2853.md)'s close, found by its `gen_clo` grid · filed 2026-09-27 · fixture `tests/cases/closures/record-closure-field-let-bound-in-maker-reads-per-pin.vl`**

Repro:

    function mk(x) {
      let r = { f: x, g: () => x }
      return r
    }
    const a = mk(true)
    print(mk(7).g())
    // vl check: rc 0.  vl run: prints `7`.  Was: prints `true`

Want:

    7

#### Mechanism

[D2853](D2853.md)'s: the closure's lambda is shared by both instances and its banked return kind
is the first pin's. `makerRetObjLitOf` followed a returned `const` to its object literal so the
field closure is read per instance, but not a `let`, which may be reassigned. It now follows a
`let` whose declaration is the statement just before the return (`stmtPrecedesTail`), where
nothing can reassign it.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| `let` for `const` | runs, prints `true` then `7` | **yes** |
| the second pin (`mk(true)` only) | runs | **yes** |

#### Grading list

The RF grid's `mklet`, `mkletb` and `mkconst` cells (a maker by 10 field kinds, pairs), none
`OK → not OK`. A `let` with a statement between it and the return is still read at the shared
kind.
