#### Mechanism

`objLitNamesTwoRows` and `structIndexOfObjCtxGo` (emit_classify.vl) each walked every struct
row up to `sScanLim()` for every object literal, and looked up each of the literal's fields in
a row with the literal's field count. `repRowOfTyStruct` (emit_rep.vl), reached from the same
function, compared every row's canonical id through `repCanonId`. Those three were about 75% of
a guest profile of 2,000 functions that each build one nested inline record. Once they were
indexed, the type section's two pairwise row passes, `structEmitOrder` and `buildStructSupers`,
were the next 45%. Each compared every row with every row for a proper prefix.

The close indexes the rows, and every reader still applies its unchanged per-row test, in the
original order, to the candidates the index gives it:

- Per field name, the rows carrying it and the rows it comes first in (`sfnSync`). A literal's
  candidates are the rows holding its first field's name (`objLitNameCands`). A row's possible
  prefixes are the rows whose first field is its own (`structPrefixCands`). A row joins once
  its names are stored, and every reader takes the rows past the index as candidates too.
- Per canonical id, the rows whose own arena type (`sTyIx`) has it (`repRowOfTyStruct`'s
  `scn*`). The index is stamped on `tyMutEpoch`, as `repKeyMemo` is. A row joins in scan order,
  only when the scan reaches it, and only once its arena type is recorded. So every canonical id
  is first computed where the full scan computed it. A row the name rung answers is asked again
  on every scan, as before.

On the witness pair (2,000 against 500 functions), the fuel ratio went from 11.97 to 4.61.
Output is byte-identical: the compiler's fixpoint, sunpa's `game.wasm` (with and without
`-O3`) and all 4,532 `tests/cases` programs.
