### D1734 — a map read place is narrowed by `is` and NOT by `!= null`, while a list read place is narrowed by both

**closed 2026-09-06 · the decline was documented and its stated reason inverted the fact:
the `| null` a map read carries is manufactured by the READ, not held by the storage · 0
corpus cells**

Repro:

    const m: { [string]: i32 } = Map()
    m["k"] = 5
    if m["k"] != null { print(m["k"] * 2) } else { print(0) }
    // prints 10

#### Mechanism

`placeElemTy` is the checker's index twin of `placeFieldTy` and answered for arrays only, on
the stated reading that "a map read is already `V | null` whatever the key, so keying `m[0]`
would narrow a nullability the storage never dropped". The storage never HAD it: a map's
`mVal` is `V`, and `checkIndexNode` mints the `| null` for the miss. Proving the key present
is the narrowing, and it is the one the emitter's `emitNarrowedMapReadTail` already emits a
`ref.as_non_null` for under the `is` sense.

Three condition spellings reach three different collector arms — `!= null`,
the else of `== null`, and the else of `is null` — and the emitter needed a map rung in each;
`nonNullTy` is asked for the pushed spelling so a map whose value is ITSELF nullable narrows
to the value, not to `V | null`, which would leave the box unboxed.

#### Grading list

`tests/cases/maps/null-guarded-map-place-read.vl` carries the three spellings, the value reps
and the write. The HAZARD set is what a close owes: `m.delete("k")`, a mutating call and a
write between the guard and the read must each still refuse, and `m.delete("z")` must not —
the list place's own column is the precedent and none of its cells may move. Two value shapes
decline by design: `f64`/`i64`/`f32`, whose map miss is a numeric zero with no null to
recover from, and an OBJECT-shaped value, which is D1735.
