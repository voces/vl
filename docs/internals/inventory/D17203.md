### D17203 — an inferred-null binding read before a later write fills it with a different type keeps the read checked at the open hole, then emitted at the filled type

**check-clean invalid wasm · clause 1 · found by V4 verifying #9936 (LB2 item 3), ablated by IR-N4 · its module-scope join spelling is a price of #9936 (was a loud check reject) · owner IR-N4 · filed 2026-11-24 against master `6aabbd9ac`, the same before #9936 (`4e84cecc`) except the module-scope join**

Repro:

    type In = { v: i32 }
    type Out = { w: string, k: i32 }
    const rec: In = { v: 9 }
    function run(f: boolean) {
      let m = null
      const j = if f { m } else { rec }
      m = { w: "z", k: 4 }
      return j == null
    }
    print(run(true))
    print(run(false))
    // vl check: rc 0.  vl run: invalid module inside `run`, "type mismatch: expected (ref null
    // $0), found (ref $3); $0 is `Out` … $3 is `In`"

#### Mechanism

`let m = null` binds the open hole `mkNullableTy(-1)`, and the later write fills it in place
(`nhFillLinked`), so every read of `m` checked before the write is retroactively typed at the
filled `Out | null`. Its consumer was checked while the read was the hole, which is assignable to
anything, and nothing re-asks it at the fill. A `??` over the hole is re-asked there
(`fillCoalHoleNodes`: re-banked where it fits, else "annotate the binding"). Other readers are
not. Since #9936 the join of the hole with `In` is `In | null` and is not re-asked either. Before
it the join was the hole itself, filled to `Out | null`, which dropped `In`.
