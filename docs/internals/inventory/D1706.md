#### Mechanism

The seed built with `--names` names the recursion, which is a different pair from D1700's:

    0: vl!memberFieldCode   1: vl!memberNulVariantRow   2: vl!structIndexOfExpr
    3: vl!memberFieldCode   4: vl!memberNulVariantRow   5: vl!memberFieldCode   …

`memberFieldCode` resolves a `Member`'s receiver through `structIndexOfExpr`, which asks
`memberFieldCode` of the receiver's own receiver — and more than one arm of the walk asks the
same link, so a `.g.g.g…` chain is walked once per path that reaches it. Same shape as D1700's
intern doubling, one reader over, and the same trap: `allocation size too large`.

**A re-entrancy memo on `memberFieldCode` was tried and REFUSED, and profiling it is what
closed this row without one.** Keyed on `(memIx, fnIx)`, it made the ladder clean to 40, passed
all 3,059 `tests/cases` modules, and then the compiler could not compile itself. The named
backtrace of THAT failure names the frame, which is the step the guess about narrowing missed:

    0: vl!sidArrPut   1: vl!memberFieldCode   2: vl!memberNulVariantRow   3: vl!memberFieldCodeGo

The trap was inside the memo's own growth. `sidArrPut` grows an `i32[]` up to its key, the key
was a raw ARENA NODE INDEX, and the table was dropped and regrown per outer ask — on the
compiler's own source that is hundreds of thousands of entries rebuilt hundreds of thousands of
times. Not a staleness bug at all; a sizing one.

**And the row closes with no memo here.** D1705's indexed pair table makes the capture comparator
refute correctly at every depth, so the literal mints its own row and the access walk is never
asked the same link twice: the ladder is clean to 100 at both faces, and this row's own witness
prints `7`. The recursion is still unmemoised — what is gone is the caller that fed it the same
link repeatedly, which is D1713.

**Reachability moved twice, and the row says so rather than leaving it implied**: before D1700's
close the intern exponential trapped at depth 20, so this one was never reached; it then stood
