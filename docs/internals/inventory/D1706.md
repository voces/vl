#### Mechanism

The seed built with `--names` names the recursion, which is a different pair from D1700's:

    0: vl!memberFieldCode   1: vl!memberNulVariantRow   2: vl!structIndexOfExpr
    3: vl!memberFieldCode   4: vl!memberNulVariantRow   5: vl!memberFieldCode   …

`memberFieldCode` resolves a `Member`'s receiver through `structIndexOfExpr`, which asks
`memberFieldCode` of the receiver's own receiver — and more than one arm of the walk asks the
same link, so a `.g.g.g…` chain is walked once per path that reaches it. Same shape as D1700's
intern doubling, one reader over, and the same trap: `allocation size too large`.

**A re-entrancy memo on `memberFieldCode` was tried and REFUSED, and the price is the record.**
Keyed on `(memIx, fnIx)` and live only while an outer ask is on the stack, it made the ladder
clean to 40 — and the compiler could not compile itself: `vl build compiler/entry.vl` under
that candidate trapped, while the same source built by the previous seed was fine. That is the
L2 failure the bootstrap rule names, and it is why this is filed rather than fixed in the same
PR as D1700. `memberFieldCode` is flow-sensitive through `memIsNarrowed`, so a memo has to key
on the narrowing state too, or be a table the emit pass owns rather than a re-entrancy cache.

**Reachability moved with D1700's close**, and the row says so rather than leaving it implied:
before that close the intern exponential trapped at depth 20, so this one was never reached.
It now stands at 70.
