    function id(v) { return v }

#### Mechanism

The same as D15609's: `holeBindInstance` sees only the direct call `g(5)`, because the walk does
not follow `g` into the record literal, and so it pins `id` at `(i32) => i32`. D15609's fix
covers list literals only, the hand-on the elaboration forwards (`elabLitFwdTargets`).

Tried 2026-11-10: counting a field initialiser of the record literal as an open hand-on in
`holeBindArgListsHole` moves the program to the emit reject `a generic function taken as a
value reaches no call that fixes its type`. The elaboration forwards a hand-on only through list
literals, so the record needs its carrier there before the checker can leave the call open.
