### D1574 — one released `vl` was TWO COMPILERS, chosen by the current directory: a `./build/vl-compiler.wasm` outranked the seed inside the binary

**closed (fixed) — a DISTRIBUTION build (`--features embed-seed`) no longer consults the filesystem for a seed: `--compiler` → `$VL_COMPILER_WASM` (announced) → embedded, and the current directory is never a rung · was a tooling hazard with NO diagnostic, and the owner's own first failure of the week · a development build keeps `./build/vl-compiler.wasm`, which is how the repo's scripts drive a freshly built seed · reported by the glean session, VL-006, `~/glean/docs/vl-issues.md` · filed 2026-09-03 against master `4490423c`, landed on `292380ff`**

Repro (the FLOOR — any program compiles with ONE compiler now; the defect's own witness is a
shell transcript, below, and is gated by ci-embed-seed):

    function f(xs: i32[]) {
      let len = 0
      len = xs[0]
      len
    }
    print(f([6]))

#### Mechanism

`resolve_compiler_source` read `./build/vl-compiler.wasm` — **CWD-relative** — ahead of the
seed baked into the binary, so `dist/vl` picked up whatever a directory happened to hold.
The consumer's measurement:

> `vl seed --path` prints `build/vl-compiler.wasm` when run from inside `~/vl` and
> `embedded` from anywhere else. So `vl run x.vl` compiles with a different compiler
> depending on `cwd`, and a program that fails in one directory may pass in another.

`dist/vl seed | wc -c` read **1,832,652** inside `~/vl` (that checkout's on-disk seed, from
another branch) and **2,046,575** from `~/glean` (the embedded one). Two compilers, one
binary, no word about it — and the ABI check cannot help, because both seeds speak the same
generation. `cli-design.md` even documented the preference as a footnote to the ABI section,
which is how it survived: it was written down as a fact rather than read as a defect.
