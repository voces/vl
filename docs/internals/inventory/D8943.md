### D8943 — an un-annotated function handed to a generic `(T) => R` parameter has no monomorphization pin for `R`

**closed · runs, prints `4` · was loud emit reject, `emitProgram: monomorphize: unsupported argument type for `h` in a call to `apply`` · clause 2 · filed 2026-10-21 against master `30ff8d9b5` · closed by the checker reading `R` off the handed body at the bound `T` (`holeFnArgRetAt`, check_relate_core.vl) and the monomorphizer binding `R` from the arrow annotation's result (`monoBindArrowRet`, emit_mono.vl) · fixtures `closures/hole-fn-to-generic-fn-param-result.vl`, `closures/error-hole-fn-to-generic-fn-param-result-at-i32.vl`, matrix `hole-fn-to-generic-fn-param-result`**

Repro:

    function inc(a) { return a + 1 }
    function apply<T, R>(h: (T) => R, x: T): R { return h(x) }
    const r = apply(inc, 3)
    print(r)
    // vl run: emitProgram: monomorphize: unsupported argument type for `h` in a call to `apply`

#### Mechanism

Two halves. The checker left the call's result at the open `R`: nothing bound it, because the
handed function's own type is `(_) => _`. It now reads the handed body's result at the
parameter types the call bound, so `apply(half, 3)` is `f64` and refused at an `i32`
destination. The monomorphizer had no binding for `R` when it spelled `h`'s instance; it now
binds `R` to the result the handed function gives at the annotation's closed parameters.
