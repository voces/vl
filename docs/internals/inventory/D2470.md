### D2470 — a bare `Set()` with `.add` then a bound `.values()` passed check and refused at emit: `.keys()` scratch frame not reserved

**closed 2026-09-25 — the filed repro RUNS and prints `1` · was a loud emit reject of a type-valid program · design doc `collections-representation-design.md` §10 F2 (`critic-learn/v2.vl`, `s1.vl`) · filed 2026-09-25 against master `086466d1a`**

Repro:

    const s = Set()
    s.add("a")
    print(s.values().length)
    // was: emitProgram: .keys() scratch frame not reserved

#### Mechanism

A set's `.values()` is built by the key-list path (`emitMapKeys`), which needs the 6-slot
`mapKeysBase` frame. The reservation scan (`mfScan`) reserved it for an i32-keyed set (`-5`)
but deliberately not for a string-keyed one (`-2`), on the reasoning that `for v in s.values()`
also reaches the scan and walks without a list. The bound form does need the list, so the frame
is now reserved at both key reps; an unused frame costs six locals. The collect pass also forces
the string-list type for a set's `.values()` (it forced it only for `.keys()`), which the
annotated spelling `const s: Set<string> = Set()` needed.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the result bound or read (`for v in s.values()`) | ran | **yes** |
| an i32-keyed set (`s.add(1)`) | ran | **yes** — the string key |
| the annotation added (`const s: Set<string>`) | `string index access but string list type not collected` on `s.values()[0]` | no — the collect half |
