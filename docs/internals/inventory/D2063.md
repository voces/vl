### D2063 — f64 `%` is admitted in a getter as cost 0, and its lowering is a loop whose trip count depends on the operands' exponent gap

**runs today and must keep running until the contract closes: the defect is that `vl check` ACCEPTS it as bounded and data-independent, and the ruled close (owner, 2026-09-22, D-Q1) refuses f64 `%` in a getter, which the grader reports as MOVED · filed 2026-09-22 against master `31ea77721`, found by the Rust/systems lens of the getters/effects persona review (probes `p1_rem`, `p3_rem_*`)**

Repro:

    type R = new f64
    get m(self: R): f64 { (self as! f64) % 5e-324 }
    print((1.7e308 as! R).m)
    // vl check: rc 0; prints 0.  `__f64_rem__` is scaled repeated subtraction, so this one
    // read runs thousands of iterations; `(3.0 as! R).m % 1.5` runs a handful

#### Mechanism

`__f64_rem__` (`compiler/emit_sections.vl`) doubles the divisor up to the dividend and halves back
down, which is O(exponent gap), up to about 2 x 2098 iterations. The v1 contract admits `%`
because it is not on the deny list, and the #3039 amendment (I15) counts helpers like it as 0
because they are "bounded by the float format". Bounded is true; "never data-dependent", the
amendment's own invariant, is not. Re-measured for the synthesis: 200,000 reads of
`get m(self: R): f64 { (self as! f64) % 1.5 }` took 0.36 s at receiver `1.7e308` and a few
milliseconds at receiver `3.0`.

#### Grading list

The `% 1.5` pair above at both receivers; the same getter with an `f32` receiver; any constant
`%` in a constant-bounded loop once the amendment is built.
