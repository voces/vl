### D2435 — a declared `boolean` field's row takes an un-annotated literal's `i32` field, which shares its field code

**closed 2026-09-25 — the witness prints `7` then `true` · was check-clean silently wrong, printing `true` then `true`, clause 1 · the D2423 family, found by the #3147 review, filed 2026-09-25 against master `a277bf7b0` · fixture `tests/cases/objects/declared-row-literal-destination.vl`**

Repro:

    type Q = { k: boolean }
    const q: Q = { k: true }
    function main() { const r = { k: 7 }; print(r.k) }
    main()
    print(q.k)
    // vl check: rc 0.
    // vl run (as filed): prints true then true. Now prints 7 then true.

#### Mechanism

`i32`, `boolean` and a string literal set's atom all store as field code 0. A literal is matched to
a row by its field names and then each field's code, so `{ k: 7 }` took the declared `Q` row with
nothing in the code to refuse it, and `print` rendered its `7` as `Q.k`'s `boolean`. Against a
declared row, an equal code 0 is now asked of the row's own arena type (`declRowScalarFits`): a
primitive value refuses a different primitive, and it refuses a string literal set (`{ j: 3 }`
against `{ j: "a" | "b" }` printed `b`). A numeric literal set shares the `i32` rep and still fits.

#### Ablation

| ingredient changed | outcome (as filed) | needed? |

| `Q = { j: "a" \| "b" }`, `{ j: 3 }` | prints `b` | the same code-0 blindness |

#### Grading list

`bool-row-bool-param`: `function f(q: Q) { q.k }` over `f({ k: true })` must keep printing
`true`, since there the literal's own destination names the row.
