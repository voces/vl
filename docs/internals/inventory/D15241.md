### D15241 — a read of a container built wider, defaulted with `??` to an annotated parameter, joins two records

**open · loud check reject · `a ?? whose default is a parameter or an annotated binding, stored apart from the J a read of a container built wider holds, is not yet supported` · clause 2, capability: the literal raises goal-scoreboard's conceded-capability count by one until this row closes · probe `capability-probes/coalesce-fixed-default-built-read.vl` · was check-clean invalid wasm until the refusal, which is a placeholder for the converting copy of the read (`storeCoalescesResolve`) · the un-annotated parameter is D15318 · out of scope of [D15217](D15217.md) · graded CAPABILITY: the join is only read, so a converting copy of either side is unobservable; a write through the result is the design refusal · filed 2026-11-04 against master `2b449f004`**

Repro:

    type J = { f: i32 | null }
    function mk() { { f: 4 } }
    const m = Map()
    m.set("a", mk())
    const wm: {[string]: J} = Map()
    wm.set("a", mk())
    function pick(d: { f: i32 }) { (m.get("a") ?? d).f }
    print(pick({ f: 1 }))

Want:

    4

#### Mechanism

`m.get("a")` reads a record of `J`'s storage, and `d` is a parameter at its declared `{f: i32}`,
whose callers' records cannot be rebuilt. The `??` joins one of each storage. The program is
type-valid and the join is only read: a converting copy of either side at the join changes no
observable value, since nothing is written through it. Where the result IS written through
(`const b = m.get("z") ?? d; b.f = 9; d.f`), a copy would break `b` aliasing `d`, and that
spelling is the one that should refuse, as D15217 refuses an own-storage delivery of a built `d`.

**The refusal, and where the capability lives.** `storeCoalescesResolve` (store column, after the
record solve, over the write scan's join list) refuses the join where the default is a parameter
or an annotated binding stored apart from the read's record. It has to run there: when the checker
first visits the `??`, the build table has no build for the read yet (measured: `recBuiltReadTy`
answers -1 at `checkCoalesceBinNode`). Emit consults a recorded copy at every expression
(`emitExpr` → `coerceKindAt` → `recCopyRowAt`), so the capability is a producer in the same
post-solve place recording a copy of the read back to its own row (`recCopyTyIx`, `recCopyFrom`,
as D15246 does for a call), with the write-through spelling refused as a design rule.
