### D15911 — a `const` copy, inside a lambda, of a parameter holding a hole lambda's bundle, handed on, is refused by mono

**closed 2026-11-12, runs and prints `5` `2.5` · was loud emit reject · clause 2 · `emitProgram: monomorphize: unsupported argument type for \`a\` in a call to \`fw\`` · found closing [D15909](D15909.md) · filed 2026-11-12 against master `6976e1af` · closed in the elaboration: a copy inside a lambda nested in the function holds the record under that lambda's instances (`elabCopyRecordsNote`, `elabHandFromKeys`), and the callee's read of its parameter that initialises such a held copy is not a read other than a call (`elabReadInitsHeldCopy`, in `elabParamReadOtherThanCalled` under `elabBodyReadsOtherThanCalled`), which had left `fw`'s parameter with no bundle signatures at the call · fixture `tests/cases/closures/hole-lambda-bundle-param-copied-in-a-lambda-and-handed.vl`**

Repro:

    function lap(f) {
      f(2.5)
      f(3)
      return f
    }
    function take(b) {
      print(b(4))
      print(b(1.5))
    }
    function fw(a) {
      const k = () => {
        const v = a
        take(v)
      }
      k()
    }
    fw(lap((a) => a + 1))

Want:

    5
    2.5

#### Mechanism

The parameter's hand from the lambda runs (D15909), and so does a `const` copy in the function's
own body (D15902). The copy note holds a copy only in the parameter's own function
(`elabCopyRecordsNote`, `elabCopyInFn`); keying the copy at the lambda's instances instead did not
run, as `fw`'s parameter then gets no signatures through the copy, so mono refuses its call.

#### Ablation

| spelling | outcome |
| --- | --- |
| `take(a)` in the lambda | runs |
| `const v = a`, `take(v)` in `fw`'s body | runs |
| `const v = a`, `take(v)` in the lambda | refuses |
