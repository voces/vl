### D15431 — a function returning one of two record literals whose field holds different generics, handed to a hole parameter calling the field at two types, refuses at emit

**loud emit reject · clause 2 · with the split plan on and off · found beside D15430 · filed 2026-11-04 against master `a090a48b`**

Repro:

    function k<T>(x: T): T { return x }
    function k2<T>(x: T): T { return x }
    function get3(c: boolean) { if c { return { f: k, g: 7 } } return { f: k2, g: 8 } }
    function show(o) { print(o.f("s")); print(o.f(2)); print(o.g) }
    show(get3(true))
    show(get3(false))
    // vl check: rc 0.  vl run: emitProgram: a generic function taken as a value reaches no call that fixes its type

Want:

    s
    2
    7
    s
    2
    8

#### Mechanism

The tag decision never tries the set `{k, k2}`. A traced build (every `ftTry` logged) records no attempt for it. The only call through the set is `o.f(...)`, a call through a field of the hole parameter `o`, made in `show`'s instance. The decision's call list (`fnTagCalls`) has no such call. Neither do the elaboration's mint facts (`mintFactRows`), which record calls through a parameter bound to a set, not through a field of one.

The same literals called through a module binding (`const o = get3(true); o.f("s"); o.f(2)`) are tagged as `{k, k2}`. That spelling refuses only with the split plan off. One literal (`get3() { return { f: k, g: 7 } }`) runs. Two `const` records returned by `get3` and handed to `show` refuse the same way, at `a function-value call has no interned signature`.

The fix wanted is an elaboration fact for a call through a field of a parameter bound to a holder of a set, read by the decision as `mintFactRows` is read.
