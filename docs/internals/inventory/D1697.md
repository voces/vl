### D1697 — a LIST-OF-LIST element names no struct row, so the capture comparator has nothing to walk and a declared row takes the literal anyway

**closed 2026-09-06 — the comparator peels a CONTAINER key before looking for a row, and both
readers now reach it · filed against master `ad287fae7` + D1690 + D1694 + D1696/D1674 · the
capture preference's one remaining blind spot · residue D1700 · 0 corpus cells**

Repro:

    type U1 = i32 | boolean
    type U2 = string | boolean
    type A = { xs: U1 }
    type B = { xs: U2 }
    type H = { ys: B[][] }
    function as1(): A[][] { return [[{ xs: 7 }]] }
    const b = { ys: as1() }
    print(b.ys[0][0].xs)
    // vl check: rc 0.  vl run: rc 0, prints 7

Was: `invalid module — type mismatch: expected (ref null $type), found (ref $type)`. Taking one
container off printed `7` then too, which is what named the ingredient.

#### Mechanism

The capture preference refuses a declared row whose element ROW disagrees with the value's, and
it reaches that row by NAME: `structIndexByName(vn)` and `structIndexByName(dn)`. A ref-list
field whose element is itself a list records the key `A[]`, which names no struct row, so both
lookups decline and the comparator answers its lenient default — the same answer it gives a row
it cannot resolve, which is the contract that keeps it from refusing on ignorance.

So the blind spot is one container deep, not one nesting level: the walk into a nested-struct
field is depth-general (D1696), and the walk THROUGH a second list was not there at all.

**The close is three lines and one habit.** The comparator peels both keys with
`refArrElemKeyDeferred` before it looks for a row, and recurses on the elements — the key the
DECLARED path already uses for `A[][]`, so the two producers stay comparable. Where neither
peeled key names a row and neither is a container — a closure, a map, a nullable ref — the two
sides are both SPELLINGS of the same producer, so they are compared as such rather than
declining; that arm alone closes a closure, a map and a nullable-ref element, the last of which
was a loud `unknown struct field in field access` rather than invalid wasm.

**And the ARENA reader joins the same comparator here, which is what the separate audit of it
concluded.** Eight arena-path cells were built — a differing nested field set inline and named,
a box at depths 1, 2 and 3, a ref-list element differing by a box, the accepting side, and this
row's shape — and **only this one misbehaved**: `fieldElemDeclConflict` compares element ROW
NAMES, and two different rows have two different names, so at code 15 it is already at least as
strong as a structural walk. Its one blind spot is the same as the node reader's — an element
that names no row, where `declNominalOfTy` answers "" — so it takes the container-general
comparator on that arm instead of a copy of the walk.

**Two outcomes, one ingredient**, which is worth naming because the second is the loud one and
would otherwise look like a different row: with the two elements' member SETS differing the
module fails to validate, and with their FIELD SETS differing (`{p:i32}[][]` against
`{q:i32,tag:string}[][]`) it is a loud `emitProgram: unknown struct field in field access`.
Both need the same walk.
