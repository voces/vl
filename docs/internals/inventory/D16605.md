**closed 2026-11-15 · runs, prints `16777217` · was check-clean silently wrong, clause 1 · closed by taking a float for a radix literal in `numLitDstTy` only where the float holds its value exactly (`intLitMisfitAtFloat`), so the `??` default keeps its own type and the join widens and the element is refused as a binding is; `as` keeps the rounding reading through a cast-only entry (`numLitAdoptCastDst`, `numLitAdoptCastTails`, check_num_adopt.vl) · fixtures `tests/cases/numerics/radix-default-inexact-at-float-keeps-own.vl`, `tests/cases/numerics/error-radix-element-inexact-at-float.vl` · the element's refusal reads the list's types (`cannot assign i32[] to … f32[]`), as the decimal element's does, not the exactness sentence; the record field keeps its record-shape sentence · was ruling 4.1 (a radix literal in a float context is the value its digits spell, refused where the float cannot hold it exactly) and 4.3 (a literal that does not fit the typed value keeps its default and the join widens) · found by lane T's literal-adoption position matrix · filed 2026-11-15 against master `c8f0324da`**

Repro:

    const n: f32 | null = null
    print(n ?? 0x1000001)
    // PRINTS 16777216

Want:

    16777217

The element face, `const xs: f32[] = [0x1000001]`, prints `16777216` too; its want is a check
reject, `constant 16777217 is not exact at f32 — write it as a float literal to round it`, as a
binding and an `f32` argument give.

#### Mechanism

Not localised past the ablation. A binding and an argument check a radix literal's exactness at
the float destination and refuse an inexact one. At a list element, and as the default of a `??`
beside a typed float, the literal adopts the float without that check and the value is rounded.
