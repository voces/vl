### D3830 — two nested `<U>` generics of the same name in different functions share their `$N` instance names, so a call reaches the other one's instance

**closed 2026-10-08 by lane SC · was check-clean invalid wasm · found closing D3826 · filed 2026-10-08 against master `cab1ee907` · pins: `tests/cases/generics/same-named-nested-generics-keep-their-instances.vl`**

Repro:

    function outer(x: i32) {
      function inner<U>(u: U) { print(u) }
      inner(1)
      inner("a")
    }
    function first(x: string) {
      function inner<U>(u: U) { print(x) }
      inner(1)
      inner(2.5)
    }
    outer(7)
    first("s")
    // vl check: rc 0.  vl run: invalid module inside `first`, `expected (ref $type), found f64`

Want:

    1
    a
    s
    s

#### Mechanism

Each template named its later instances `inner$1`, `inner$2`, … by its own count, so both
templates minted an `inner$1`, and `first`'s renamed call resolved to `outer`'s. No capture
is needed. With D3826's per-enclosing-instance keying, the same collision printed a wrong
value instead of failing to validate (`p(true); q(2.5); p(3); q(false)` printed `0` for the
last call). An instance name another template's instance already carries is now skipped
(`monoInstNameTaken`, `emit_mono.vl`).
