### D1865 — dogfood: a map value reaches a union at the INLINE spelling of its type and refuses at an ALIAS for the same type

**loud emit reject · filed 2026-09-07 against master `678f578e3`**

Repro:

    type V = f64 | string | { [string]: V }
    type VMap = { [string]: V }

    function name(v: V): string {
      if v is f64 { return "number" }
      if v is string { return "string" }
      "object"
    }

    const m: VMap = Map()
    m["a"] = 1.0
    print(name(m))
    // vl check: rc 0.  vl run: emitProgram: a map value is not a supported union member — use a struct member instead

#### Mechanism

The two spellings name one type and disagree about its representation. Declare the same map
INLINE — `const m: { [string]: V } = Map()` — and the identical program runs and prints
`object`; give the type a name and the delivery into `V` refuses at emit. Nothing else moves:
the map is built the same way, written the same way, and the union it is delivered into is the
same union. So the refusal's own sentence is false of the feature it names — a map value IS a
supported union member, at one of the two spellings of its type — and the arm that fires is
reading the ALIAS rather than the shape behind it.

The message is what makes this worth a row rather than a note: "use a struct member instead"
tells an author to change their data model, when the fix that actually works is to delete a
`type` line.

It is `std:json`'s whole write path. `Json`'s object arm is `{ [string]: Json }`, so a program
that builds one and renders it — `toJson(m)` — hits this at the argument boundary the moment
the map's type is given a name, which is what anyone reading `std:json`'s header would write.
That is the write-side twin of D1864's read side: between them, a program can neither build a
JSON object nor read one back out of a parse result at the spellings a consumer reaches for.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the alias — `const m: { [string]: V } = Map()` | runs, prints `object` | **yes** |
| the delivery into the union — `print(m.size)` with the alias | runs, prints `1` | **yes** |
| the user union — the same shape over `std:json`'s `Json` and `toJson` | refuses identically | no |
| the map WRITE — the alias and the delivery with an empty map | refuses identically | no |

#### Grading list

The two running controls above are the row's boundary and must keep running: the inline
spelling, and the aliased map used without crossing into the union. `std:json`'s own path is
the second witness — `type JsonMap = { [string]: Json }` then `toJson(m)` refuses while the
inline spelling prints `{"bytes":2254088}` — and a close owes both, since the alias is what a
reader of that module's header would write. D1864 is the read-side row over the same two types
and must be graded beside this one: a fix that gives the alias its map rep may move both, and a
fix that special-cases this delivery moves neither.
