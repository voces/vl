#### Mechanism

`arrNewIntrKind`'s ladder has arms for an i32 list (`exprArray`), a ref list (`exprRefArray`),
a string list (`exprStringArray`) and a map, and none for an `f64` / `i64` / `u8` / `f32` list
— so what decides this cell is which of `exprRefArray`'s storage-class channels answers.
Its global channel is `globalIsRefArraySid` → `letIsRefArray`, which claims a wide-scalar list;
its parameter channel is `paramRefArray` → `nodeTyIsStructArray` / `annBareRefArrSlot` and its
local channel is `declaredRefArray` → `declaredKind(name) == "reflist"`, and neither of those
does. A local or parameter therefore reaches the ladder's `return 0` — the i32 list — and the
disassembly shows the wrong pair being built beside the right one: `fp` declares `(param i32
(ref $7))` and result `(ref $5)` over `$4 = (array (mut (ref null $7)))`, where `$7` is the
f64-list wrapper over `$6 = (array (mut f64))`, and its body returns `(struct.new $3
(array.new $0 (local.get $1) …))` — `$0 = (array (mut i32))` with its wrapper `$3`.

The generic wrapper the probe uses is SCENERY: the identical concrete helper
`function fp(n: i32, v: f64[]): f64[][]` is the same cell, so this is not a
monomorphization face and the pin is not an ingredient. What the storage class decides is
visible in one pair of programs — a helper whose fill is its own `f64[]` PARAMETER is
invalid, and a helper whose fill is a module-global `f64[]` read from inside the same
function runs.
