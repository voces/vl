### D4556 — an inline record nested in a declaration interns before the generic-application instances its fields name

**closed 2026-10-14 — the witness prints `1` · the inline shape's interner codes a concrete generic-application field `FC_STRUCT` keyed by its name, as `fieldTypeCode` already did for a declared field · fixture `tests/cases/generics/inline-record-field-holding-generic-application.vl` · was loud emit reject · clause 2 · filed 2026-10-14 against master `eb2603843`**

Repro:

    type B<T> = { v: T }
    type Obj = { inner: { q: B<i32>, r: i32 }, s: i32 }
    const o: Obj = { inner: { q: { v: 1 }, r: 2 }, s: 3 }
    print(o.inner.q.v)
    // vl check: rc 0.  vl run: struct field type `{q:B<i32>,r:i32}` has no struct-field rep

Want:

    1

#### Mechanism

`collectS` interns every inline field shape (`collectNestedFieldShapes` →
`internInlineShapeTyGo`) before `collectGenAliasShapes` interns generic-application
instances. `nameFieldCode` never codes an application, so `q: B<i32>` coded `-1`, the inline
shape was never minted, and the declared field holding it had no code. A declared field
escapes this through `fieldTypeCode`'s `nameIsGenAppDecl` rung, which keys the field by the
application's name; the inline interner, `variantNestedShapeOkTy` and
`collectShapeVariantFields` lacked that rung. Inside a generic alias (`{ q: B<T> }`) the same
shape was minted as a concrete row whose element `B<T>` is never interned ("nested-struct
field element type is not interned"); `shapeFieldsRideTyParam` now declines it as the generic
original's.
