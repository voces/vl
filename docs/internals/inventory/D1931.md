### D1931 — with a `std:` import in the graph, an operator whose BOTH operands are un-annotated parameters refuses, and the identical import-free program runs

**loud check reject · PRE-EXISTING, unmoved by [D1891](D1891.md)'s close on both seeds · filed 2026-09-08 against master `fbe0b0f01`**

Repro:

    import { toString } from "std:fmt"
    type Ord = new { x: i32 }
    function ">"(self: Ord, other: Ord): boolean { return self.x > other.x }
    const opO: Ord = { x: 12 }
    function mkval(): Ord {
      const r: Ord = { x: 24 }
      return r
    }
    function take(p, q) {
      if p > q { print(1) } else { print(0) }
    }
    take(mkval(), opO)
    // vl check: argument 2: operator '>' is not defined for Ord and Ord
    //           (the body of `take` applies '>' to this argument)
    // Delete line 1 and the same program prints 1.

#### Mechanism

Two un-annotated operands leave the operator undecidable in the body, so the comparison
defers and `validateBinCstrs` re-asks it at the call under the bindings. That works — the
import-free spelling runs — and stops working once any std module joins the graph. The
refusal names `Ord` on both sides and the operator IS declared for `Ord`, so the table is
being asked about the right type and answering no; the constraint reaching the call under
the import is not the one the declaration would satisfy.

This is [D1893](D1893.md)'s other half. That row's witness had ONE hole and is closed:
seeding the left hole from the declaration's `self` gives the solve an answer the import
cannot perturb. With BOTH operands holes there is no receiver to seed from, so the deferred
path is the only one and the import still changes its answer.
