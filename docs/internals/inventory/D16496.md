### D16496 — a join whose constant arm does not fit `i32`, beside an inner join of a typed `i32` arm and a literal arm, builds invalid wasm

**closed 2026-11-15 · runs, prints `3000000000` · was check-clean invalid wasm, clause 1 · `numLitAdoptJoin` (check_num_adopt.vl) leaves the tails of a nested join that keeps its own type (a tail typed other than the join's, and no literal) out of the adoption, so its literals stay at its width and it is converted whole · fixture `tests/cases/numerics/nested-join-wide-constant-arm.vl` · found by the independent oracle's arithmetic generator once it stopped emitting what the checker folds and refuses (fuzz cell `ar_s42_0050`) · filed 2026-11-15 against master `6f9bafb92`**

Repro:

    let v1: i32 = 5
    let c = true
    const x = if c { 3000000000 } else { if c { v1 } else { 1 } }
    print(x)
    // master: vl check rc 0; vl run: the emitted module failed to validate

Want:

    3000000000

#### Mechanism

The outer join is `i64`, because its constant arm does not fit `i32` (4.3, D3043).
`numLitAdoptJoin` adopted that type into every tail leaf `valueTailLeaves` yields, and it walks
through nested joins, so the inner literal `1` was built `i64`. `numLitJoinSpineSync` retypes a
nested join only when every tail it yields holds the type, and `v1` is `i32`, so the inner join
stayed `i32`. The emitter wrapped it in `i64.extend_i32_s`, and an `i64.const 1` arm sat inside
an `if (result i32)`. A nested join with a tail typed other than the outer type, and no literal,
now keeps its own type for all its tails.
