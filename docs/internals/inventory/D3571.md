### D3571 — an `if` nested in an `else` arm keeps its runtime arm's own type when the outer join parts it from a literal-adapted sibling, so the value reads at the wrong width

**check-clean silently wrong · clause 1 · open · found by the #3353 review (`w/nest.vl`) · the same on master `3b9319528` and with #3353 · filed 2026-10-03 against master `3b9319528`**

Repro:

    function run(q: i32 | null, r: i32 | null) {
      const x = if q != null { q } else { if r != null { r } else { 2.5 } }
      print(x / 2)
    }
    run(null, -3)
    // PRINTS -1

Want:

    -1.5

#### Mechanism

A prediction until a close confirms it. The inner `if` alone types `f64` (its `2.5` arm adapts
`r` by widening), and the outer `if` joins `q`'s `i32` apart from that `f64`. The inner arm's
`r` is then boxed at its own `i32` member of the outer union rather than at the inner join's
`f64`: the "literal inside a union chain boxes at its own type" rule of #3327 reaches the
runtime arm beside the literal, not only the literal.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| the inner `if` bound to a `const` first | prints `-1.5` | **yes** (the inline nested arm) |
| `q: f64 \| null` (the outer join does not part) | prints `-1.5` | **yes** (the outer union) |
| `else if r != null { r } else { 2.5 }` | prints `-1` | no (either spelling) |
