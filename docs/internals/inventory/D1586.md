### D1586 — `%` over two floats was a loud check reject because wasm has no `f64.rem`; the truncated remainder is a real operation and the compiler now computes it exactly

**closed 2026-09-04 · was a loud check reject (`operator '%' is integer-only, got f64 and f64`) · `%` leaves `binIntOnlyOp` and joins the arithmetic lattice; `emitBinExprNode`'s f32 and f64 slices call a once-per-module `__f64_rem__` intrinsic · 10 distilled-corpus classes move `loud check reject` → `runs`, 0 runs lost, 0 → silent · 54 of 54 position-matrix cells move `check refuses` → `RUNS` in both faces · owner ruling 2026-09-04, "`%` can follow Rust/JS" · filed 2026-09-04 against master `5328a781`**

Repro (prints `1.5`):

    function g(a: f64, b: f64): f64 { return a % b }
    print(g(5.5, 2.0))
    // was: [ERROR]: operator '%' is integer-only, got f64 and f64

#### Mechanism

`binIntOnlyOp` held ONE list — the bitwise ops, the shifts, and `%` — read by
`checkBinary`'s reject and by `binOpDefinedFor`'s pin mirror. The bitwise members are
there because they are about BIT PATTERNS and a float has none; `%` was there for a
different reason, stated in its own comment: wasm has no `f64.rem` instruction, and the
one-line `a - b * trunc(a / b)` identity is not `fmod`. That reasoning was correct about
the identity and wrong about the conclusion — the operation is meaningful, it just needs a
helper rather than an opcode.

`%` therefore leaves the family and takes an arm of its own in `binOpDefinedFor` (keeping
the operator-FIELD dispatch route the family's arm served it), and `checkBinary` reaches
the ordinary mixed-numeric lattice instead. `exprIsF64` / `exprIsF32` gain `%` in their
BinExpr arms so the result classifies at the operand width, `scanPrintUse` reserves
`gHelpF64Rem` for a module that needs it, and both float slices of `emitBinExprNode` call
`__f64_rem__` instead of reading an opcode table that has no entry.

The helper is the SCALED REPEATED-SUBTRACTION form, not the identity evaluated: double
`|b|` to the largest `|b| * 2^k <= |a|`, then halve back down subtracting where it fits.
Doubling and halving a binary float move only the exponent, and each subtraction lands in
Sterbenz's range (`t <= a < 2t` is the loop's invariant), so no rounding enters anywhere
and the answer is the exact remainder. `f32` rides the same helper: an f32 is exact in
f64, the remainder of two f32-representable values is itself f32-representable, so
promote / call / demote loses nothing — with the operands emitted AT f32 first, so a
literal re-encodes at f32.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the `f64` annotations (bare `5.5 % 2.0`) | the same reject before, the same value now | no — every float spelling |
| the direct spelling (a `<T>` pin instead) | `operator '%' is not defined for f64 and f64 (the call's argument types)` before, `0` for `7.5 % 1.5` now | no — D493's twin, closed by the same edit |
| `f64` replaced by `f32` | the same, one width down | no — one helper serves both |
| a float operand at all (`7 % 2`) | ran before, runs now, byte-identical | **yes** — the integer path is untouched |
| the float DIVISOR only (`5.5 % 2`) | widens to f64 and runs | no — the lattice decides, as it does for `+` |

#### Grading list

* **20 vectors against Python's `math.fmod`** (C `fmod` = the same truncated definition;
  Python's `%` is floored and is NOT the reference), printed through `std:fmt`'s
  `toString(f64)`: `5.5 % 2`, `-5.5 % 2`, `5.5 % -2`, `1e308 % 3`, `0.1 % 0.03`, `x % 0`,
  `inf % 2`, `2 % inf`, `-0.0 % 1`, `nan % 1`, plus ten seeded random pairs. **20 of 20
  identical**, including `1e308 % 3 = 2` and `0.1 % 0.03 = 0.010000000000000009`, both of
  which the identity gets wrong.

  (-0.0 % 1.0)` is `-Infinity`, `1 / (-4.0 % 2.0)` is `-Infinity`, `1 / (4.0 % 2.0)` is
  `Infinity`.
