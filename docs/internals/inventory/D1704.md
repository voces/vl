#### Mechanism

`anonValueFitsField`'s composite tail refuted five value codes by naming what each widens into
(`4→18`, `14→22`, `24→17`, `25→32`, `26→33`) and, since D1663, the three that name a heap
(`fieldCodeRefsElemHeapC`: 15, 5, 28). **Everything else fell to a terminal `true`.** Code 6 —
a STRING list — has no arm and names no heap, so a code-6 value fitted a code-5 row, and the
`(ref $stringList)` slot took a `(ref $structRefList)` value.

That default is the bare fall-through the ladder rule forbids: an anon row's codes are read off
its own literal, so a value fits its own code, the union box, or a widening an arm spells — and
nothing else. The tail now returns `false` and says so, which closes code 6 and every other
unnamed code in one line rather than growing a per-code list.

**Both faces, and the second needed its own arm.** With the string-list row DECLARED
(`const two: { us: string[] } = { us: ss1() }`) the collision runs the other way — the
un-annotated struct-list holder captures the declared row — and `declRowFieldFits` was lenient
on a differing code, because a declared field's code can differ from the value's through
adoption. No adoption turns a string list into a struct-ref list, so that pair is refuted too.

The family is narrow, and that is measured rather than assumed: of the pairs graded, only
5-beside-6 collided. 5-beside-4, 5-beside-25 (an f64 list), 6-beside-4 and a list beside a
plain scalar of the same backing all already ran, because each has an arm or an unequal
backing the earlier ladder catches.
