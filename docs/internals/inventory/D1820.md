### D1820 — the monomorphizer's replaced-template ledger is keyed by ARENA NODE INDEX and never cleared, so on a shared compiler instance one program's slot answers the next program's lookup and a per-pin clone is never minted

**closed 2026-09-06 — the pair compiles to the same bytes in either order · was check-clean
invalid wasm on the SECOND program of a shared instance, `struct.new[0] expected type (ref 0),
found local.get of type i32` · clause 1 · filed and closed 2026-09-06 against master
`d7786bc78`, found when [D1782](D1782.md)'s fixture turned [D1788](D1788.md)'s red in the same
test shard while each was green alone**

Repro:

    function o(n) {
      function k() { return n }
      const f = k
      return f()
    }
    print(o(2))
    print(o(2.5))
    function h(n) {

    // Compiled through ONE wasm compiler instance and followed by

#### Mechanism

`monoSlotOfLamNode` scans `fnStmts` for a node and, when the scan misses — which is exactly
what the D1046 arm arranges, since the first instance overwrites the template's slot — falls
back to `monoNamedTmplNode` / `monoNamedTmplSlot`. Those two were declared `const` and are
written but never cleared, while their key is an ARENA NODE INDEX and their value an `fnStmts`
SLOT: both are re-minted by every program.

Measured with a sticky probe at `monoLamNodeIsTemplateCore`, the same node in the same compile,
poisoned run against clean:

    clean   TPL k node=26 slot=6 caps=1 fnStmts=10   (twice — clone minted, fnStmts=12 next)
    dirty   TPL k node=26 slot=6 caps=1 fnStmts=10
            TPL k node=26 slot=3 caps=0 fnStmts=10   (no clone, fnStmts=11 next)

Slot 3 is the PREVIOUS program's row for node 26. In this program slot 3 is another function
with no captures, so the capture rung reads 0, the template test declines, and the per-pin
clone is never minted — `wasm-dis` of the two modules differs by exactly that one function and
its env struct, and the call that should reach it feeds an i32 to a `struct.new`.

The fix is the lifetime, not the lookup: the ledger resets per program beside `monoLamPinned`
and `monoLamShared`, which is what `emitProgram`'s own arena-index sidecar block already does
for every other node-keyed column.

**Two attributions were tried and both are refuted by measurement.** It is NOT [D1788](D1788.md)'s
reader family — with all fourteen `fnIndexOfInScopeSid` call sites reverted to the flat lookup
the pair still fails — and it is NOT [D1782](D1782.md)'s binding resolver: the pair fails on a
seed built from `origin/master` with neither change present. What [D1782](D1782.md)'s fixture
supplies is only a program that reaches the ledger and sorts before [D1788](D1788.md)'s in the
same shard.
