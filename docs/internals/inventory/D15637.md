### D15637 — [CLOSED 2026-11-10] a hole function called directly at one type and handed on inside a nested list literal to a callee that calls the element at another is refused by the checker

**closed 2026-11-10, runs and prints `5` then `s` · was loud check reject, clause 2, `argument 1: expected i32, got string (the call of a function value at the call's argument types)` · filed 2026-11-10 against master `7b499846` · closed in two steps: the elaboration forwards a list literal nested in another as the outer one lands (`elabLitFwdTargets`, emit_elab.vl), then the hole-instance walk counts a hand-on at any depth of nesting as an open call (`holeBindArgListsHole`, check_relate_core.vl), so the argument stays generic and each call takes its own instance, dispatched by tag · fixture `functions/hole-param-called-and-handed-on-in-nested-list.vl`**

Repro:

    function id(v) { return v }
    function call0(fss, x) { print(fss[0][0](x)) }
    function run(g) {
      print(g(5))
      call0([[g]], "s")
    }
    run(id)

Want:

    5
    s

#### Mechanism

The same as D15609's: `holeBindInstance` sees only the direct call `g(5)` and pins `id` at
`(i32) => i32`. D15609's fix counts a hand-on inside a list literal as open, but only one level
deep, because the elaboration forwards only that level (`elabLitFwdTargets`, D15566). Counting
the nested literal as well moves the program to the emit reject `a generic function taken as a
value reaches no call that fixes its type`, so the elaboration has to follow it first.
