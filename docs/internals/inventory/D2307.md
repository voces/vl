### D2307 — an operator declared on a `new` type whose body concatenates strings makes a sibling constructor function invalid wasm

**closed 2026-09-24 — the witness prints `x` · was check-clean invalid wasm · found while writing
`prefer-interpolation`'s user-operator fixtures · filed 2026-09-24 against master `ab942030b` · fixture
`tests/cases/objects/anon-field-string-concat-of-values.vl`**

Repro:

    type Widget = new { s: string }
    function mk(s: string): Widget {
      const r: Widget = { s: s }
      return r
    }
    function "+"(self: Widget, other: string): Widget {
      const r: Widget = { s: other + other }
      return r
    }
    print(mk("x").s)
    // vl check: rc 0.  vl run: invalid module — inside `mk`: type mismatch: expected i32, found (ref $type)

#### Close

[D2305](D2305.md)'s field code. The operator's `{ s: other + other }` is coded by
`anonFieldCodeSyn` whatever its annotation, and its `+` of two string values was coded as an
arithmetic `i32` field; the `{ s }` row that minted is the one `mk`'s literal of the same shape
then built into. With the `+` arm declining a string-typed concat, the row codes `s` as a string
and both functions agree. The cross-module spelling runs too.

#### Mechanism

Not yet located. The failure is in `mk`, which neither calls the operator nor concatenates;
the operator's body only has to contain a string `+`, and the operator never has to be used.
Declaring the operator before `mk` moves the failure into `+@Widget` itself. Measured on a seed
built from master `ab942030b`; the same program fails across modules (the type, `mk` and the
operator in an imported module).
