### D15019 — a function in two list literals, handed a hole parameter's function in one and another named function in the other, is invalid wasm

**closed 2026-11-03 · runs, prints `1 2.25`, with the split plan on and off · was check-clean invalid wasm, clause 1 · `ftLateArgOfSet` (check_fn_tag.vl) now decides the set of the list element called with the id together with the set handed, so an id goes only into a dispatch · fixture `tests/cases/closures/fn-in-two-lists-handed-hole-param-fn-and-named-fn.vl` · found ablating `closures/forwarded-hole-fn-to-list-element-value-param.vl` for D15018 · filed 2026-11-02 against master `ebd304ac`, pre-existing**

Repro:

    function add(a, b) { return a + b }
    function mul(a, b) { return a * b }
    function same(g, s) { print(g(s, s)) }
    function inner(h) {
      for f in [same] { f(h, 0.5) }
    }
    inner(add)
    function swap() {
      for f in [same] { f(mul, 1.5) }
    }
    swap()
    // vl check: rc 0.  vl run: the emitted module failed to validate inside `swap`:
    //   type mismatch: expected (ref $type), found i32

Want:

    1
    2.25

#### Mechanism

After the elaboration, `{mul}` was tagged on its own: `ftLateArgOfSet` takes an argument of a
call through a list element as an id when every member of the element's set takes the handed set
at that parameter, and `same` does in `swap`'s instance. The element's own set `{same}` stayed a
closure, declined for its holder in `inner`, so the call in `swap` went through the closure's one
signature and handed an `i32` id where it expects a ref. The element's set is now decided with
the handed one, so both are tagged or neither.
