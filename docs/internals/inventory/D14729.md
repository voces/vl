### D14729 — a hole lambda in a generic body, relayed to a hole function called at two types, takes an instance per type only through mono's flow pin

**runs today and must keep running · step 2 residue: `monoHoleGenFnPin`'s flow branch cannot take the elaboration's type, because the per-instance lambda fact is not in the elaboration · found ablating `monoHoleGenFnPin` · filed 2026-11-01 against master `cd15b5ebe`**

Repro:

    function two(a: i32, b: (n: i32) => i32) { b(a) }
    function twof(a: f64, b: (n: f64) => f64) { b(a) }
    function fwd(h, x, f) { return h(x, f) }
    function outerB(h, x) { return fwd(h, x, (n) => n * 2) }
    print(outerB(two, 3))
    print(outerB(twof, 1.5))

Want:

    6
    3

#### Mechanism

`outerB` hands the hole lambda `(n) => n * 2` to `fwd`, which hands it to `h`. Each instance
of `outerB` needs its own copy of the lambda, at `(i32) => i32` and at `(f64) => f64`.
`monoHoleGenFnPin` passes `monoFnPinAt` a flow type of -1 here, and that is what copies the
lambda per instance. The elaboration closes `h` at each call, but it does not carry that the
lambda inside the body is copied per instance. Pinning the flow branch at the elaboration's
type therefore gives one lambda at `(i32) => i32`, and the `f64` instance calls it through the
wrong signature.
