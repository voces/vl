### D3856 — at module scope, a `let` link of an alias chain ends the chain walk, so a lambda written into a later link has no peer signature

**closed (2026-10-08, lane SC) · was check-clean invalid wasm on #3447, a loud emit reject on master `cc1ee0a89` · `r0606` of the module-scope generator `gen3.py`, found in review of #3447 · filed 2026-10-08 against master `cc1ee0a89` · pins: `tests/cases/closures/module-let-alias-chain.vl`**

Repro:

    const x = "a"
    const c = (y) => y + "C"
    const e = (y) => y + "E"
    const g = (y) => y + "G"
    let d1 = c
    let d2 = d1
    function w5(): i32 { d2 = e; 0 }
    let d3 = g
    let i6 = 0
    while i6 < 2 { d3 = d2; i6 = i6 + 1 }
    print(d3(x))
    // vl check: rc 0.  vl run: invalid module inside `e`, `expected (ref $2), found i32`

Want:

    aC

#### Mechanism

D3847 taught `fieldValueFeOfIn` that a module-scope `let d1 = c` names `c`. `monoAliasChainLamFe`
reads that answer at every link past the first, and took a `let` with an answer as the end of
the chain, which it refused (only a `const` link may end it). So `e`, written into `d2` in a
function nothing calls, found no peer through `d2 → d1 → c`. Its body was lowered at the
hole's `i32`, though `d3`'s loop copies `d2` into the called link. A module-scope `let` link is
now walked on, with its writes checked like any other `let`'s. On master the same chain was a
loud `no interned signature`.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| module scope (the same lines in a function) | still invalid, inside `f`: there `d2` is a cell and the write a cell read, which is D3855 | no |
| the write `d2 = e` | runs | **yes** (the unpinned lambda) |
| the link `d2 = d1` (`let d2 = c`) | runs | **yes** |
