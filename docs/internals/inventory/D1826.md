#### Mechanism

D1671 stages a `?.` chain's base in `optRecvSlot` when it is not a re-readable place: the
first read tees the value in and every later one is a `local.get`. Four lowerings nest another
chain inside their own, and each SAVED the marker pair, marked, lowered, and RESTORED — which
put back `optRecvStagedSet` as it found it, `false`. The inner lowering had teed the value in
by then, so the restore threw away the fact that the slot was live and the next arm evaluated
the receiver again. One evaluation per re-entry: three for a two-link chain whose leaf is a
nested struct (its null test re-enters `emitOptChainValue`), two for a three-link scalar leaf.

The save/restore is now one pair, `optRecvStageSave`/`optRecvStageRestore`, and the restore
keeps the tee when both scopes stage the same base — the value is in the slot and the first
tee dominates every later read, which is the contract `emitOptRecvBase` already stated.
`wasm-dis` of the two-link witness reads **three `local.tee` before and one after**.

Not a hint and not a cost: the base is arbitrary code. A call that counts, a `pop()`, or a map
write runs once per link, so the program's OUTPUT is wrong.
