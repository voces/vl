### D2486 — a generic parameter typed `T` unioned with a concrete type has no monomorphization pin for any argument

**loud emit reject · clause 2 · found in review of #3157 against master `0a0d24ac9`, filed 2026-09-25**

Repro:

    function f<T>(x: T | string): boolean {
      if x is string { return true }
      false
    }
    print(f(1))
    // vl check: rc 0.  vl run:
    // emitProgram: monomorphize: unsupported argument type for `x` in a call to `f`

#### Mechanism

Not ablated to a rung. `x`'s declared type is a union of the type parameter and a concrete
member, `T | string`. Monomorphizing `f(1)` has to decide what `T` is from an argument whose
declared type is already a union, and whatever rung reads a call argument's type to bind `T`
cannot see through the union at all — it refuses before it can ask which arm matched. It refuses
identically for `f("s")`, an argument that IS the union's own concrete member, and identically
with the `is string` narrowing removed: this is not about narrowing, and not about which
concrete type is passed. A `T` unioned with anything concrete has no monomorphization pin for
any call.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the union (`x: T` alone) | runs, prints `false` | **yes** |
| the `is string` narrowing check | same refusal | no |
| calling with a string instead of `i32` (`f("s")`) | same refusal | no |

#### Grading list

D2487, the same monomorphization gap for a map-typed parameter (`{[i32]: T}`); both should close
together if the fix is at the argument-typing rung rather than the union shape specifically.
