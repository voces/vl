### D17577 — a closure returning a captured parameter delivered at its list's build row keeps the checker's result type, so its signature and its calls disagree

**loud emit reject · D17660's grading list · filed 2026-11-26 against master `fa5d6e86e` by SOUND**

Repro:

    type J = { f: i32 | null }
    function mk2() { return { f: null } }
    const dA: J = mk2()
    const src = [mk2()]
    const r = src.filter((y) => {
      const e = () => y
      print(e().f)
      const h = { w: y }
      return true
    })
    print(r.length)
    // vl check: rc 0.  vl run: emit error at `e().f`: field access receiver is not a struct

Want:

    null
    1

#### Mechanism

The filter callback is keyed at its list's build `J` (`#r.0`), and the read of `y` inside `e` is
stamped there (D17660's close). `e`'s result is still typed `{ f: null }`, and its closure signature
key (`cloSigKeyExt`) and result kind come from that type, while `fnRetRepTy` reads the stamped
return value as `J`, so `e()`'s receiver row resolves to none. Before D17660's close it was a
check-clean invalid module inside `e` (expected `{f:null}`, found `J`). The closure's result has to
be built at the row its return value is stored at, signature included.
