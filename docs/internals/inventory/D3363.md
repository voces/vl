### D3363 — a concrete join of `i32`, `f64` and `null` types differently depending on which arm comes first

**closed · runs, prints `true`, `false`, `3` · was a loud check reject, order-dependent · owner numeric-join ruling of 2026-09-30: the join is `i32 | f64 | null` in any arm order · found by the #3310 round-3 re-review (`rv3310r3/m/np_c1`–`np_c4`) · fixture `tests/cases/numerics/numeric-join-null-any-order.vl` · filed and closed 2026-09-30**

Repro:

    function g(a: i32, b: f64, k: i32) {
      const r = if k == 0 { a } else if k == 1 { b } else { null }
      print(r is i32)
      print(r is f64)
      print(r)
    }
    g(3, 1.5, 0)
    // vl check: `is` check type 'i32' is not a variant of f64 | null

Want:

    true
    false
    3

#### Mechanism

With the `i32` arm first the join widened to `f64 | null` (`i32` is assignable into the nullable
`f64`) and `is i32` refused; with the `f64` arm first the join kept both numbers. The ruling makes
both orders `i32 | f64 | null`: two runtime numbers join apart (`joinArmLit`), a `null`-only arm
adapts to nothing, and the generic spelling's emit refusal (`monoNulJoinMixesNumbers`) is gone,
since the pinned join is now the same set in every order.

#### Ablation

| --- | --- | --- |

| `a: i32 \| null` (`np_c4`) | the same refusal | no |
| `a: f64, b: i32 \| null` (`np_c3`) | runs, keeps both numbers | no |
