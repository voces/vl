### D14885 — a hole lambda delivered directly to a declared list beside its pass through an identity in an inferred-return function is pinned by rung B

**runs today and must keep running · refutation pin for deleting mono's rung B (`monoOpenFnFlowPin`) · found grading the D14884 coercion's holder positions · filed 2026-11-01 against master `c8c745179`**

Repro:

    function fw(f) { return f }
    const lam = (x) => x
    function deliver() { return fw(lam) }
    const xs: ((x: i32) => i32)[] = [lam]
    print(xs[0](3))

Want:

    3

#### Mechanism

`lam`'s one-member set is read twice. Inside `deliver` it is handed through `fw`, which needs the
set tagged (an id) so `fw`'s instance is keyed by it. In `[lam]` it is delivered straight into a
list of a declared function type, a holder the tag decision cannot coerce: the literal's value is
the name itself, not a delivery from an inferred-return call (`fvaInferredRetCall`). So the set
stays a closure, and `fw`'s parameter has no closed type. Rung B pins it from the flow table. Before
the change below, the program was refused with rung B disabled: `emitProgram: monomorphize:
unsupported argument type for f in a call to fw`.

#### Built: the one instance

The elaboration's fact about `lam` is that it is built at exactly one instance, the `(i32) => i32`
the declared binding delivers it at. The call `fw(lam)` cannot be keyed there when its row is
bound, because `fw`'s instance is enqueued, with `f` open, before `lam`'s instance exists. Once the
run has settled, `elabSoleRekey` keys each root call that hands back a hole lambda its row left
open at that lambda's one instance (`elabSoleInstFnTy`), and mono's existing elaboration arm pins
it. No mono rung is added. With rung B disabled the witness runs, and so do all three
`hole-lambda-through-*` templates, 48 of 48, the un-annotated map value included. With `lam` used
nowhere else (D14887), no instance exists and the program is refused, with rung B too.
