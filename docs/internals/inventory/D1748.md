### D1748 — writing through a literal-union key refuses at CHECK with `isn't supported yet`, while every read through the same key now runs

**loud check reject · `vl check` rc 1, `A K-keyed Map isn't supported yet — Map/Set keys must be string or i32` · clause 2: the message concedes it, and the identical key typed `string` writes fine · filed 2026-09-06 against `#2749`'s tree · the residue [D1724](D1724.md)'s close leaves, and the one refusal in that grid with a different channel · 0 corpus cells**

Repro:

    type K = "red" | "green"
    function take(a: K) {
      const m = Map()
      m[a] = 1
      print(m["green"] ?? 0)
    }
    take("green")
    // vl check: rc 1,
    // A K-keyed Map isn't supported yet — `Map`/`Set` keys must be `string` or `i32`

Read through the same key — `m[a]`, `m.get(a)`, `m.has(a)`, `m.delete(a)` — and all four print
correctly at [D1724](D1724.md)'s close. Only the write direction refuses.

#### Mechanism

Predicted, not probed. The refusal is a CHECK-level gate naming the map's declared KEY TYPE, and
its wording admits the gap. It fires where the checker can SEE the key type is `K`: the
annotated parameter and `Set.add`. Through a hole parameter the checker cannot, so the write
reaches the emitter and — since [D1724](D1724.md) — widens and runs, which is what shows the
capability exists and only the gate is missing.

**A literal union's members are strings**, so a `K`-keyed map is a string-keyed map whose keys
happen to be drawn from a fixed set; the key boundary already widens the atom to its member text
in both directions. What the gate owes is to admit a key type whose rep, after that widen, is
the `string` it names.
