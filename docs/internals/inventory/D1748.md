### D1748 — writing through a literal-union key refuses at CHECK with `isn't supported yet`, and the gate cannot be lifted alone: `.keys()` must move with it

**loud check reject · `vl check` rc 1, `A K-keyed Map isn't supported yet — Map/Set keys must be string or i32` · clause 2: the message concedes it, and the identical key typed `string` writes fine · filed 2026-09-06 against `#2749`'s tree, re-measured on `#2753`'s · the residue [D1724](D1724.md)'s close left · 0 corpus cells**

Repro:

    type K = "red" | "green"
    function take(a: K) {
      const m = Map()
      m[a] = 7
      print(m[a] ?? 0)
    }
    take("green")
    // vl check: rc 0.  vl run: rc 0, prints 7

Was: `A K-keyed Map isn't supported yet — Map/Set keys must be string or i32`, while every read
through the same key already printed correctly at [D1724](D1724.md)'s close.

#### Mechanism

The refusal is a CHECK-level gate naming the map's declared KEY TYPE, and its wording admits the
gap. `mapKeyRepTy` is the one home of which hash a key takes, and it answers -1 for a literal
union; every gate projects that answer. It fires where the checker can SEE the key type is `K` —
the annotated parameter and `Set.add`. Through a hole parameter the checker cannot, so the write
reaches the emitter and, since [D1724](D1724.md), widens and runs — which is what shows the
capability exists and only the gate is missing.

**Lifting the gate alone was BUILT, MEASURED and REFUSED, and the tree's own pin predicted it.**
`tests/cases/maps/error-newtype-over-unsupported-key.vl` says in as many words that admitting a
literal-union key "needs the key RENDER and `.keys()`'s element type to move together". Adding
`if tyIsLitUnion(k) { return TY_STR }` to `mapKeyRepTy` moves **six cells** from the refusal to
RUNS — the index write, `.set`, `Set.add`, two keys, an annotated `{[K]: i32}` map, the inline
spelling — and then **`m.keys()` on that map is check-clean invalid wasm**: `.keys()` is typed
`mkArrayTy(rt.mKey)`, so its element is the literal union, whose rep is the interned ATOM, while
the map stores the member STRINGS the boundary widened. Typing `.keys()` by the stored rep
instead fixes that cell and **loses a `runs`**: `m[m.keys()[0]]` becomes `map key must be K, got
string`. Neither route is free, so neither shipped.

**A third consequence the first route exposes**, worth recording because it is the shape both
routes run into: a member LITERAL directly in the key position (`m["green"]` on a `{[K]: i32}`
map) is refused `map key must be K, got string`, while the identical literal is accepted as a `K`
argument and a `K` binding. A bare literal defaults to its base type and nothing pushes the map's
key type back into the subscript.

#### Grading list

* The six ablation rows above, at both faces.
* **`m.keys()` and `m[m.keys()[0]]` on a `{[K]: i32}` map are the two cells any close must carry**,
  and they pull in opposite directions: typing `.keys()` by the DECLARED key makes the first
  invalid wasm, typing it by the STORED rep makes the second a check reject. A close needs the
  keys list to hold what the map stores AND to be indexable back into the map.
* `tests/cases/maps/error-newtype-over-unsupported-key.vl` — the standing pin that predicted
  this, and which a close must update rather than delete: its `K` case is the deliberate
  negative, and its stated condition ("the key RENDER and `.keys()`'s element type move
  together") is exactly what the measurement above confirms.
* The NUMERIC literal union is the same gate and the same message; a close should say whether it
  moves with the string half or needs its own widen (its rep is already the `i32` the map hashes,
  so it may need none).
