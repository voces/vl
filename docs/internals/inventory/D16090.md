### D16090 — a re-pointed `let` of un-annotated lambdas whose results differ is refused at the call, where declared functions dispatch

**closed 2026-11-14 · runs, prints `s` · was loud check reject, `cannot assign (i32) => string to (i32) => i32 (the body of \`f\` at the call's argument types)` · clause 2 · the lambda twin of [D16064](D16064.md) · filed 2026-11-14 against master `b53278055` · fixed by leaving a lambda written to a widened `let` to the calls through that binding (`letLamJudgedAtCall`), which dispatch on the lambda it holds and type the members' join, as they already did for declared functions · residue [D16095](D16095.md), [D16096](D16096.md) · fixtures `closures/written-let-of-lambdas-results-differ-dispatches.vl`, `closures/written-let-of-hole-lambdas-results-differ.vl`**

Repro:

    function run(c: boolean) {
      let f = (a) => a + 1
      if c { f = (_a) => "s" }
      print(f(3))
    }
    run(true)
    // vl run: prints `s`

Want:

    s

#### Mechanism

The write `f = (_a) => "s"` recorded a destination row, the lambda's type against the binding's,
which each later call through `f` re-asked at its argument types and refused. Declared functions
leave no such row. The row is now skipped at a call through the binding itself, whose members'
join types it (`holeSetCallRetOf`), unless a call typed before the lambda was checked used it
(`holeSetEarlyLamNote`). A binding handed to a named callee still asks the row there (D16096).
