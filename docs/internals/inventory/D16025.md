### D16025 — a union's row identity still rides its label: one union type can hold two rows that differ only in `null` position, and a declared alias is found by its label registration

**closed 2026-11-14 · runs, prints `7` · registration asks the type key alone (`unTyKeyHasRow`, emit_union_tykey): an alias and a spelling that places `null` elsewhere name the key's one row, and `unRowBySid` with its bind paths is deleted · 1 of 19,754 programs moves bytes with identical output, 0 `runs → not-runs`, and no type key holds two rows over 15,086 emitted programs · the identity half of [D16032](D16032.md) · filed 2026-11-14 against master `875f5c709`**

Repro:

    type A = { a: i32 }

#### Mechanism

No reader looks a union up by its label any more (D16032). The label index (`unRowBySid`) is
still how registration decides that a union already has a row, through three guards:
`unNameAdoptTyKeyRow` (emit_union_tykey), `monoPinMintedUnion` and `monoRegisterPinUnion`
(emit_mono), with `annAdoptRegisteredName` (emit_collect) rewriting an annotation to the
registered spelling. A probe over the 19,744-record population (`tests/cases` and the distilled
corpus, master `875f5c7`) found the label bound where the type key would decide otherwise in
3,242 programs at `unNameAdoptTyKeyRow`, 7 at `monoPinMintedUnion` and 22 rewrites. A sample of
400 of the 3,242:

| why the type key disagrees | programs | decisions |
| --- | --- | --- |
| the name is a declared union alias (`cUserTypes`), which adopt refuses unless it is bound | 399 | 599 |
| the key row exists, but `null` sits in a different position among its members | 24 | 458 |

So two rows can share one member multiset and differ only in where `null` sits, which breaks
step 7's "one row per type". A declared alias reaches its row through its declaration's label
registration, not through its type's key row; #7835 folds an alias to its base type's key, so why
adopt still needs the binding is part of this row.

#### Ablation

The repro is the `null`-position shape. Whether it lands on one row or two is decided by
registration order, so the program runs either way; the defect is the identity, not an output.

#### Grading list

The 24 null-shape programs and the 399 alias programs of the sample, re-graded after the null
position joins the row's typed identity (or the two rows merge) and aliases answer through their
type's key row; then `unRowBySid` and the three guards go, in a sweep-labelled PR.

#### Closed

Registration no longer consults the label. Every mint site asks `unTyKeyHasRow(ty)`: the
`registerInlineUnionGo` gates, the inferred and inferred-return mints, the array-literal element
mint, `registerValueUnionNameTy` and `monoRegisterPinUnion`. The alias exclusion and the
null-position test are gone with the adopt. A declared alias that matches its key's row is named
by that row and pushes nothing; `unRowBySid`, `unRowOfName`, `unNameBound`, `unNameBindRow`,
`unNameShareTyKeyRow`, `shareObjLitFieldUnionRows` and `annAdoptRegisteredName` are deleted.

A probe counting rows whose type key's first row is another row read 0 over the population on
both master and this change. Its control is D16000's repro with the type-key re-check removed,
where it reads 20. So the null-position shape never minted a second row in this population: the
type-key re-check ahead of `mintInlineUnion` caught it. What it changed was which decision the
label made, and that decision is gone.

Byte comparison over 19,754 programs (`tests/cases` plus distilled `cells/` and `named/`), master's
fixpoint seed against this one: 15,069 build to the same bytes, 4,684 give the same refusal, 1
differs. The one that differs is `tests/cases/literal-unions/coalesce-hole-call-litunion-join.vl`,
where one print ladder tests its tags in another order (`wasm-dis`), and all of its output lines
are identical.
