### D17001 — inside `is K[]` over a list arm stored apart from `K[]`, an element read at `K` is refused, where the ruling makes the value a `K[]`

**loud check reject · clause 2 · the in-arm half of the 2026-11-18 ruling (DECISIONS, "`is K[]` tests a list's contents"): inside the arm the value is a `K[]`, reads converting to `K` and a `K` write converting back, until a possible write · D16970 (numeric arms) and D16989 (record arms) made the test answer by contents but keep the arm at its own type beside `K[]`, so a read at `K` is refused · filed 2026-11-19 against master `917ae89e3` by lane F1**

Repro:

    type K = 1 | 2
    const a: u8[] = [1, 2]
    const q: u8[] | K[] = a
    if q is K[] { const k: K = q[1]; print(k) }
    // vl check: cannot assign i32 to 'k' of type K

Want:

    2

#### Mechanism

`listIsFitsAcrossReps` (numeric arms, D16970) and `listIsFitsAcrossRecs` (record arms, D16989)
keep the declared union in the then arm and push no element-read fact, because the arm's
storage (`u8[]`, or a `W` record list) is not a `K[]`'s: reading an element as `K` needs a
converting view of the arm (`rvEmitView` for records) that the emitter does not build for an
`is` arm. The test answers by contents; the arm's reads do not follow.
