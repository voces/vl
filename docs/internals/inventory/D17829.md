### D17829 — the elaboration types a nullable choice of a generic function as non-null, dropping its `null` arm

**loud emit reject · suspected clause 1 · `emitProgram: a generic function taken as a value reaches no call that fixes its type` · `vl check` rc 0 · filed 2026-11-28 against master `3b5582185` by COV-UNION (D17818's generic face, coordinator ruling)**

Repro:

    function id<T>(x: T): T { return x }
    function two() { return [1, 2].length }
    const h = if two() > 1 { id } else { null }
    const z: ((x: i32) => i32) | null = h

#### Mechanism

The checker types `h` as `((T) => T) | null`. The elaboration types the same binding as the
non-null `(i32) => i32` (`elabNodeTy` on the declaration), dropping the `null` arm. With D17818's
close taking this choice, mono holds `((i32) => i32) | null`, and `monoBindingAdoptInit` refuses
the disagreement as an internal error, so the elaboration guard in `monoCoerceChoiceBinding` (emit_mono.vl) keeps it at
master's refusal. The elaboration disagreeing with the checked type could build wrong elsewhere,
hence suspected clause 1. On master, the spellings with the `null` arm taken refuse loudly or run
correctly: a call through `h` ("union atom has no value box"), `h ?? lambda`, and a hand to a
nullable parameter refuse; `print(h == null)` prints `true`. None was seen wrong.
Pinned by `tests/cases/closures/error-nullable-choice-of-a-generic-function-at-a-nullable-function.vl`.
