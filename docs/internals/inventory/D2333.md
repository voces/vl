### D2333 — `__array_new__` stored its length in the one-slot array-intrinsic frame and re-read it after the fill, so an `__array_new__` in the fill replaced it

**closed 2026-09-24 — the witness prints `3` and `5`. Filed against master `816bda01e`, where it is check-clean silently wrong and prints `5` and `5`. Found by the D2331 sweep**

Repro:

    const a = __array_new__(3, __array_new__(5, 7).length)
    print(a.length)
    print(a[0])
    // PRINTS 3

#### Mechanism

`emitArrayNewIntr` stored the length in `arrNewScratchBase`, evaluated the fill, then read the
slot three times (`array.new` and the wrapper's `len` and `cap`). The frame is one i32 per
function, so an `__array_new__` anywhere in the fill stored its own length there first. The
length cannot ride the stack because `array.new` wants it above the fill, so a site now counts
the fills enclosing it (`arrNewFillDepth`) and a nested one stages its length in a lazy i32 slot
of its depth; the outermost keeps the frame's slot, so a program without the nesting emits the
same bytes as before. `std:array`'s `filled` is a call and was never affected.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the nesting in the fill (`__array_new__(__array_new__(3, 0).length, 5)`) | runs | **yes** |
| the intrinsic (`filled(3, filled(5, 7).length)`) | runs | **yes** |
| the inner length bound to a `const` first | runs | **yes** |
| the i32 fill (`0.5 + __array_new__(4, 1).length`) | still wrong | no |
| top level (inside a function, inside a generic) | still wrong | no |
