### D2946 — an element read off a generic list parameter pinned by an inferred `[null, true]` prints the niche's `i32`

**closed 2026-10-26 · was check-clean silently wrong, clause 1 · the un-annotated spelling of [D2943](D2943.md)'s witness · filed 2026-09-28 against master `8615a730d` · fixture `tests/cases/generics/hole-pin-inferred-nullable-bool-list.vl` · the explicit `h<T>(x: T[])` face is [D14200](D14200.md)**

Repro:

    function h(x) {
      print(x[0])
      print(x[1])
    }
    const v = [null, true]
    h(v)
    // vl check: rc 0.  vl run: prints `2` then `1`

Want:

    null
    true

#### Mechanism

Closed in `monoElabPin` (emit_mono.vl): the elaboration closes the parameter at
`(boolean | null)[]`, and the closed branch now pins at that type instead of declining to the
rep cascade. As filed: The checker hints that an annotation `(boolean | null)[]` on `v` is redundant, and
with it the program runs since [D2943](D2943.md). Without it the instance's pin is the inferred
list type, whose element the `boolean | null` niche test (`tyIsNulPrim`) does not recognise, so
`print` takes the `i32` import. The explicit `h<T>(x: T[])` prints `2` the same way, so the gap is
in the inferred pin, not the hole read.

| `h([null, true])` | prints `2` | no |
| `[true, null]` | prints `1` | no |
