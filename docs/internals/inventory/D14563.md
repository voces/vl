### D14563 — a `boolean | null` global's cell kind has two producers, storage and read side

**closed 2026-10-29 · runs, prints `true`, and must keep running · the global's storage kind came from `globalCellKind` (`i32`) and its read-side kind from `globalReadCellKind` (`nulbool`) · fixed: `letCellKind`, the one cell-kind producer locals and globals share, answers `nulbool` for a `boolean | null` binding, and `globalReadCellKind` is deleted; no file over 17,267 builds differently · found building Step 5 slice 1a (#5021) · filed 2026-10-27 against master `29a3201c5`**

Repro:

    let x: boolean | null = null
    x = true
    x = null
    print(x == null)

Want:

    true

#### Mechanism

A `boolean | null` local gets a `nulbool` cell, while a module global of the same annotated
type is stored as a niche-encoded `i32` cell by `globalCellKind` (`globalCellKindGo`'s
annotated arm). The nullability reader `exprNulKind` asks a read's cell kind through
`identCellVKind`, whose global arm goes through `globalReadCellKind`: that function reports
`nulbool` for an `i32` global that `letNulBool` claims, so that a write or a null-narrowed read
lowers as a nullable boolean. Answering `nulbool` from `globalCellKind` itself instead puts the
`null` initializer into the global section on a ref-kind path (emit_sections matches `nulbool`
as a ref cell), and the module fails to validate. This is D14434's question at module scope with an
annotation: one type, two cell kinds by scope. Its close is one cell-kind producer that the
global's storage, its reads and a local all read, and that close deletes `globalReadCellKind`.
