### D16364 — a function declared before a module-level `[]` that later top-level code pins reads the list at no element type

**check-clean invalid wasm · `type mismatch: expected (ref null $5), found (ref $3); $5 is list of i32-represented elements` · clause 1 · with the function declared after the push it runs; without the alias it trapped the compiler and runs since the hoisted container is kept · found grading `inferred-empty-list-scalar-elem.matrix.vl` (cell `two_instances`, un-annotated) · filed 2026-11-14 against master `b45a06ef`**

Repro:

    function one() {
      const v = xs
      print(v[0] + 1.0)
    }
    const xs = []
    xs.push(1.5)
    one()
    // vl check: rc 0.  vl run: invalid module inside `one`

Want:

    2.5

#### Mechanism

Pass 1.5 declares every module binding first, and a `[]` initializer as an open list. Pass 2
checked `const xs = []` again and minted a second open list, which `xs.push(1.5)` pinned, while a
body declared above read the first, never pinned. The binding now keeps the hoisted container
when both are still open (`letHoistedOpenCtn`), so a read of `xs` in such a body runs. The alias
still fails: `const v = xs` is read-only, so `defaultReadOnlyContainer` pins the shared row to
`i32` while the body is checked, before the top-level push. Deferring that default only moves
the refusal to the body's scope-close check. Both are check order, beside D16301.
