### D16780 — a generic or hole-parameter function relaying a non-generic maker's hole lambda, delivered at a function type returning `f64`, keeps the lambda's `i32` result

**loads then traps · `vl check` rc 0, `wasm trap: indirect call type mismatch` · clause 1 · a relay face of [D16753](D16753.md) beside [D16755](D16755.md) · routed to lane INIT (relay twins) · found by the maker/map/relay hunt · filed 2026-11-16 against master `6fb5ac348`**

Repro:

    function deliver() { return (a) => a + 1 }
    function wrap<T>(x: T) { return deliver() }
    const w: (a: i32) => f64 = wrap("s")
    print(w(3) / 8.0)
    // vl check: rc 0.  vl run: wasm trap, indirect call type mismatch

Want:

    0.5

#### Mechanism

Traced by lane INIT on branch `init-d16780-2` (stacked on #8601). Four steps, each one a probe result:

1. **Checker.** A relay with a type parameter or a hole parameter fails `fvaIsMaker`, so it is no relay and nothing notes `deliver()` at the delivered result. Fix on the branch: `fvaIsRelay` accepts any function with an open function result (`fvaOpenFnResult`). `fvaRelayTwinRows` still declines an instanced relay. After this, the maker row and the call note at `(a: i32) => f64` are made (`elabMakerTwinHeld` y, `elabMakerOpen` y).
2. **Mono guard.** `monoWalkIdentCall` skips the maker twin of a call inside an instanced body: `shared = twinMs < 0 && ctx >= 0 && monoCadInstOf(ctx) >= 0`. The call node is one node for every instance.
3. **Slot naming.** With the guard off, `monoMakerTwin` builds the twin, but as the template's first instance. `first` holds, so the twin takes the template's slot and name. The call keeps naming `deliver`, which emits as the root `deliver@1`. On the branch, a widened twin built while an instance is walked (`cadEncl >= 0`) never takes the slot. `wrap` then calls `deliver$1`.
4. **Open.** `deliver$1` still returns the root's `i32` lambda (`__lambda_0`). In the non-instanced relay ([D16770](D16770.md)) the twin's lambda is rebuilt at the twin's result (`elabTwinLamRet`). Built from inside `wrap`'s instance walk, it is not: the lambda's key is presumably looked up under the instance's path. This step is the mono/elab half still open.
