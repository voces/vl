### D3136 — a closure inside a module-scope `for` over box elements reads a narrowed loop variable as the box

**closed · the recording walk resolves a module-scope loop variable over box elements while it banks its closures' narrowing · fixture `tests/cases/closures/capture-walk-variable-literal-union.vl` · was check-clean invalid wasm · clause 1 · the second mechanism in [D3119](D3119.md)'s ablation · the same on master `07d414042` · filed and closed 2026-09-29 against master `07d414042`**

Repro:

    function show(k: string): string { return k }
    const zz: (string | i32)[] = ["b", 3]
    for e in zz {
      if !(e is i32) {
        const f = () => show(e)
        print(f())
      }
    }
    // vl check: rc 0.  vl run: invalid module inside `f`: type mismatch: expected (ref $type),
    // found (ref $type)

Want:

    b

#### Mechanism

A closure reads a captured box at the narrowing banked where it is written (`capNarrowRecord`),
and `capNarrowBuild` banks the module's narrowing before the start function exists. A
module-scope loop variable is a start-function local, so `exprUnion` and
`forInLoopVarUnionName`, which ask the live local table, did not see a box, the guard pushed no
narrowing, and `f` passed the box where `show` takes a string. The recording walk now keeps
the module loops it is inside (`cnModLoopPush`, `emit_classify.vl`), and both classifiers
answer a loop variable over box elements from it while the frame is the module. Inside a
function the frame's own re-bank after `buildLocals` already saw the box.
