#### Mechanism

`A_i = {l: A_(i-1), r: A_(i-1)}` shares each level's type twice, and the emitter SPELLS a record
type structurally to find its struct row: `structIndexOfObjCtxGo` asks `anonFieldCode` of each
object literal's fields, which asks `anonFieldElemName` and `anonUnionFieldName`, which render
the field's type with `tyToEmitNameAt` (`compiler/typecheck.vl`) and hand the spelling to
parsers that scan it (`shapeFieldParse`, `tyTopIndexOf`, `tyHasSepByte`,
`compiler/tyname.vl`). The spelling itself is exponential, not only the walk: a probe on
`nodeTyCanonObjName`'s answer read 1,785 characters at depth 8 and 28,665 at depth 12 (7 · 2^k),
so a memo per type index would bound the render's work and leave every consumer scanning a
2^depth-character string. At depth 14, 47% of a build's samples are in `tyToNameGo` and 26% in
`tyHasSepByte`. `nodeTyCanonObjName` declines past depth 16 (`tyDeeperThan`); the other callers
do not, which is where 18 traps.

**Plan (not built; one lane's round was not enough).** Row resolution must stop deriving a row
from a record's structural SPELLING. A declared record alias already has a row by name
(`structIndexOfTypeName` resolves `A7`), and the nominal face (`tyToNominalNameAt`) spells it
as `A7`; the fix is for `anonFieldElemName`, `anonUnionFieldName` and `declRowFieldFits` to ask
the row of the field's ARENA type — `structRowOfObjFieldSet` over the type index, memoised per
index — and to fall back to a spelling only for an anonymous shape, whose spelling is linear in
its source. That is the registry-by-key direction: the key is
the type, not its text. Grade it on this row's ladder at depths 16, 20 and 24, and on the
`d2780` cells; an anonymous nested literal (`{l: {l: …}}` written inline) is the case the
fallback keeps, and it is linear because its text is.

**Where the cost is, 2026-10-21.** A `--names` profile at depth 12 puts 185 of 227 samples
under `anonNestPolyPremint` → `structIndexOfObjCtx` → `anonFieldCode`, in its
`anonUnionFieldName`, `nodeTyName` and `anonFieldElemName` rungs and in `declRowFieldFits`,
each rendering the field value's type with `tyToEmitName`. Fuel at depths 6, 8, 10 and 12 reads
31,341,266 / 132,725,593 / 624,223,173 / 2,382,502,649, ×2 per level, so the render is
already linear in its own output and no memo over it can help. Testing `objVariantName` ahead of
`structIndexOfObj` in the premint moved nothing, because the main collect loop asks the same
literals' rows. Only the plan above, a row read off the arena type, removes it.


**After the row read, 2026-10-21.** The plan above landed for the struct-row rungs:
`anonUnionFieldName` declines a record before rendering it, `anonFieldCode` codes a record value
by whether its row resolves, and `anonFieldElemName` reads a DECLARED record's row off its arena
type (`structRowOfObjFieldSet`). Every build is byte-identical to master's. The cost fell
2.5–3.7x and still doubles per level (~1.9x), so the plan was necessary and not sufficient:

| depth | fuel before | fuel after |
| ---: | ---: | ---: |
| 8 | 132.7M | 49.7M |
| 12 | 2.38e9 | 0.78e9 |
| 16 | 26.7e9 | 10.5e9 |
| 20 | 335.7e9 | 134.8e9 |

Under `VL_COMPILE_GC=null`, depth 18 no longer traps (2.48 GB). A depth-20 profile names the
producers left, each walking or spelling the whole shared tree: `repIdOf` → `hcCanonObjId`
(~30%, memoised on the outermost type only, `emit_rep.vl`); the mono pin names
`monoNarrowedPinName` / `monoNicheWidenedPinName` / `monoDeclRecListPinName` via
`tyToEmitNameAt` (~24%); `collectAnnShapes` → `internArmFieldShape` / `internInlineShapeTy`
(~15–20%); and `ffInstCtx` → `tyToEmitNameAt` (~4%).
