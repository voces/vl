### D2552 — a function value inside a generic body keyed its `$fnsig` off the template's recorded type, which names the type parameter

**closed 2026-09-25 — the filed repro RUNS and prints `q` · was a loud emit reject, `emitProgram: function-value call arity has no interned signature`, and check-clean invalid wasm at a second instance · clauses 1 and 2 · found grading D2551's position grid · filed 2026-09-25 against master `a09d1f6bc` · fixture `tests/cases/generics/value-call-callee-pinned-per-instance.vl`**

Repro:

    function g<T>(r: T): T {
      const f = () => () => r
      const h = f()
      return h()
    }
    print(g("q"))

#### Mechanism

`cloCallSigKey` resolves a value call's `$fnsig` syntactically for a callee bound to a lambda
and otherwise from `sigKeyOfTy(nodeTyIxOf(callee))`. Inside a generic the callee's recorded
type is the template's, `() => T`, which keys nothing: at `T = i32` the arity fallback
happened to be right, at `string`/`f64`/`i64` it refused, and with two instances the second
called at the first's signature. The same holds for a function value handed to a generic as an
argument (`const f = () => r; return app(f)`), whose pin is keyed off the same type. The
instance walk (`monoPinFnValueTy`) now re-records every callee's and argument's function type
at the instance's binding, on a fresh node where the walk had not already rebuilt it, and a
rebuilt call records its own result type there too, since a value call's result is typed off
it (`f()()` at `f64` converted an `i32` result otherwise).

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| `T` bound to `i32` | runs (the arity fallback is the i32 signature) | **yes** |
| the callee bound to the lambda itself (`const h = () => r`) | runs | **yes** |
| `h` annotated (`const h: () => T = f()`) | runs | **yes** |
