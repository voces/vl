### D15860 — a returned bundle bound at one member's annotated type, before a holder of the same call called at the other, is refused at check

**closed 2026-11-12, runs and prints `5` `4` · was loud check reject, clause 2, `cannot assign (i32) => i32 to 'v' of type (f64) => f64 (the body of \`w\` at the call's argument types)` · found closing D15748 · filed 2026-11-12 against master `5e0a0ccf6` · closed in `bundleMemberFits` (check_assignable.vl): a call through a binding of the bundle names no function, so the member test now finds the bundle's signatures through the parameter its lambda is handed to · fixture `tests/cases/functions/bundle-bound-at-one-member-before-another-binding-runs.vl`**

Repro:

    function lap(f) {
      f(2.5)
      f(3)
      return f
    }
    function g() { return lap((a) => a + 1) }
    const v: (f64) => f64 = g()
    print(v(4))
    const w = g()
    print(w(3))

Want:

    5
    4

#### Mechanism

`v`'s constraint has no owner, so the re-check of `w(3)` judges it with the lambda's hole bound
at `w`'s argument, `i32`. It exists only once `v` is checked, hence the order dependence. The
D15146 member test (`bundleMemberFits`) accepts a destination one of the bundle's call signatures
fits, but it found those signatures through the parameters of the function the call names, and
`w(3)` names none. It now also follows the lambda the holes belong to, to the named function's
parameter it is handed to (`lap`'s `f`), whose calls (`f(2.5)`, `f(3)`) are the signatures.
