### D1675 — an un-annotated `Map()` carrier resolves its value row by rendered shape name, and that reader has no member-set test, so a union-box field takes the wrong box

**loads then traps · filed 2026-09-06 against master `bce33eae0` · D1689's residue at the
second reader · 0 corpus cells**

Repro:

    type U1 = i32 | boolean
    type U2 = string | boolean
    function u1(): U1 { return 7 }
    function u2(): U2 { return "hi" }
    function _firstHolder() {
      const first = { xs: u1() }
      print(first.xs)
    }

    // a value was not an instance of the type it was narrowed to

#### Mechanism

The row identity is already right here, which is what separates this row from D1689. The
probe, on the witness above:

    ROW 0 #anon0 [xs:16:<i32|boolean> ]
    ROW 1 #anon1 [xs:16:<string|boolean> ]
    LIT node15 -> row0 #anon0 lit-fields[xs:16:<i32|boolean> ]
    LIT node32 -> row1 #anon1 lit-fields[xs:16:<string|boolean> ]

Two rows, each literal on its own. What picks the wrong one is the OTHER reader: an
un-annotated map's value row is resolved from a rendered shape NAME through
`structIndexOfTypeName` and `shapeFieldTypeCompatK`, which carries per-code tightenings for
codes 0, 4, 15, 19, 5 and 28 and none for 16. `{ xs: string | boolean }` therefore matches the
first `{ xs: <box> }` row in the table — `#anon0`, over the other member set — and the box
written under one set is narrowed against the other's tags.

That the map value goes through this reader is measured, not read off the code path: adding
the codes 5 and 28 arm to `shapeFieldTypeCompatK` is what moved the same `map_value` cell of
the REF-LIST matrix template from refusing to `runs`, while this cell, whose code is 16, did
not move.

The comparator code 16 needs is a different shape from the one that arm takes.
`nestedStructNamesCompat` asks whether two type SPELLINGS denote one structure; a member set
is a set, and `i32|boolean` against `string | boolean` differs in membership and in spacing at
once — so this wants a set-aware test beside `mvValNamesCompat`, not another canon-key call.

Pre-existing and unchanged by D1689's close: both seeds trap identically. `_firstHolder` is
never called on purpose — its row is minted by the arena walk, so the collision needs no
second execution, and calling it would only add a second failure.
