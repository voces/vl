### D7443 — in an un-annotated generic, `??` over a `null`-armed join of a record union's tag finds no member set

**closed 2026-10-19 by lane L6 · runs, prints `b` · was loud emit reject · clause 2 · the instance's `??` reads its operand's members from the join's field read and the hole receiver's pin, at collect time and at the call's result · pin: `tests/cases/generics/coalesce-join-tag-in-instance.vl` · present on master `1c86d0f42` · filed 2026-10-19 against master `1c86d0f42`**

Repro:

    type N = { tag: "a" | "c", v: i32 } | { tag: "b" | "d", w: i32 }
    function mk(a: boolean): N | null {
      if a { return null }
      { tag: "b", w: 2 }
    }
    function take(a) {
      const v = a
      const c = if v != null { v.tag } else { null }
      print(c ?? "z")
    }
    take(mk(false))
    // vl check: rc 0.  vl run on master: emit error, `` `??` over this nullable value is not supported yet ``

#### Mechanism

`take` is a hole instance, so the `??` node is shared with the generic and records the
generic's hole type, not a literal union. `coalesceLitUnionFits` and `coalesceNulAtomToStr`
therefore asked `nulLitAtomTexts` of the operand `c`, and it found no members. It did not look
through a join whose other arm is `null`, and it did not read the body's own declaration of `c`
when no scope was open. With the members found, three later readers needed the same answer:

* `fRetLitAtom` and `fRetKind` are computed at collect time, where no narrowing is open, so
  `v.tag` under `v != null` has no variant row. The tag is read off the hole receiver's pin,
  whose every record arm stores it as a literal set (`holeRecvAtomFieldTexts`).
* The caller's widening of the atom result to its text read the callee's annotation, and an
  inferred result names none. It now asks the callee's returned expression.
* A module global bound to that result kept the result's i32, and `globalInitIsLitAtom`
  returned early for an un-annotated global, so a `: string` global copied the id unwidened.
