### D15186 — a map of hole-typed function values stored in a record field and read back is refused at emit

**closed 2026-11-04 · runs, prints `1.5` · was loud emit reject, `emitProgram: ref valtype with no interned shape`, `vl check` rc 0 · clause 2 · found closing [D15163](D15163.md) by the `captured-alias-of-hole-fn-map` matrix (its `struct_field_init` position, un-annotated face) · filed 2026-11-03 · closed by reading the function-set tag fact (`fnTagTyIsTagged`) through one helper, `mapStoredTyOf`: a map of a tagged set is stored as the `i32`-valued map, so the record's anonymous row codes the field and the map's own local finds the same shape · fixture `tests/cases/closures/hole-fn-map-in-record-field-runs.vl` · the list twin [D15187](D15187.md) is a different mechanism**

Repro:

    function half(a) { return a / 2.0 }
    const fnMap = Map()
    fnMap.set("b", half)
    const w = { f: fnMap }
    const v = w.f
    const g = v.get("b")
    if g != null { print(g(3)) }
    // Want: 1.5

#### Mechanism

The record `{ f: fnMap }` had no row: its anonymous mint asked `anonMapValName` for the map's value spelling, and a hole function type renders to `""`. The map's own local was the mono map only because the slot lookup on the same hole type missed. The set is tagged, so its values are `i32` member ids and the map is the `i32`-valued map; both now read that. The same map read through a plain local alias runs, and so does the record field read when the function is annotated.
