### D17858 — a function value's set tag is added to the row its type already has, in place, so two declarations sharing a row would share a set

**runs today and must keep running · refactor-blocking for S2b: under interning by structure, functions with one signature would share a row and `elabFnValNote` would union their sets; on master each declaration's binding row is its own (coordinator ruling) · filed 2026-11-28 against master `8109888ab` · owner COV-IS**

Repro:

    function a(x: i32) { return x + 1 }
    function b(x: i32) { return x * 2 }
    const fs = [a, b]
    print(fs[0](5))
    print(fs[1](5))
    // vl check: rc 0.  vl run: 6, 10

Want:

    6
    10

#### Mechanism

`elabFnValNote` (`check_elab_cap.vl`) records that a value of function type `t` is one of
declaration `d` by writing `elabFnSetTy[t] = fnSetIntern(fnSetUnion(elabFnSetTy[t], {d}))`: the
set rides on the row `t` the value already has, from a read of a named function (`typecheck.vl`,
the binding's row) or an anonymous lambda's own row. It is the one writer that tags a row after its
mint; the thirteen others mint the row they tag. The close mints the tagged row (the set id in the
key, the uJoin pattern) and stores it as the value's type, so nothing tags a row in place.
`fnTagSetTy` finds a set's row by the map's insertion order, which a copy-on-tag must keep exact.
