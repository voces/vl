### D3538 — `vl fmt` re-spells a method shorthand `add(x) { … }` in an object literal as `add: (x) => { … }`

**runs today and must keep running · open · a `vl fmt` re-spelling on a `vl check`-clean program, against the formatter's never-re-spell rule · pre-existing, the same on master `f6e17953b` · found 2026-10-03 while writing D3484's fixture · filed against master `1395b6cd4`**

Repro (runs, prints `3`; `vl fmt` must keep the method shorthand):

    const o = { add(x: i32) { return x + 1 } }
    print(o.add(2))
    // vl check: rc 0.  vl run: 3.
    // vl fmt prints:
    //   const o = {
    //     add: (x: i32) => {
    //       return x + 1
    //     },
    //   }
    //   print(o.add(2))

Want:

    3

#### Mechanism

The parser lowers a method shorthand to a `FieldInit` whose value is an anonymous function
(`parseObjLit` via `parseFuncTail`), and nothing on the node records which spelling the source
used, so the formatter prints every function-valued field as `name: (params) => { … }`. A
written return type survives (`add(x: i32): i32 { … }` becomes `add: (x: i32): i32 => { … }`).
The program's meaning is unchanged, which is why this is a formatter defect and not a clause-1
row, but it re-spells source the author wrote, which the formatter's rules forbid
(the formatter defect family). The fix needs the spelling banked at parse time and read by the
object-literal printer; not fixed here.

#### Grading list

`vl fmt` of the witness must print it unchanged apart from layout: `add(x: i32) { … }` stays a
method shorthand, with and without a return type, on one line and across several, and a
duplicate method name (now a check error, D3484) is not a reason to re-spell either.
