### D17854 — a list literal holding an un-annotated function beside `null` has no element rep

**closed 2026-11-28 · runs, prints `4` · was `emitProgram: the compiler cannot yet lower this statement (box pass)` · a join of the set's values admits `null` and a value already the set's `F | null` (`ftValuesOk`), and a holder's slot admits the set or its nullable (`ftTyIsSetOrNul`, read by `ftHoldKind` and `ftLitJoin`; check_fn_tag.vl), so the list is the nullable id's list; the binding face by #10833 · pins `closures/list-of-tagged-member-or-null-joins`, `closures/tagged-hole-function-or-null-bound-then-called` · the remaining faces are D17865 (a member name at the slot), D17866 (an annotated parameter), D17867 (an argument), D17868 (a written `let`), D17869 (an annotated nullable global), D17872 (a parameter handed `null`) · filed 2026-11-28 against master `06f4dfec2` by I8-PREP (found closing D17722, coordinator ruling)**

Repro:

    function inc(a) { return a + 1 }
    function two() { return [1, 2].length }
    const xs = [if two() > 1 { inc } else { null }]
    const f = xs[0]
    if f != null { print(f(3)) }
    // vl run: prints 4

Want:

    4

#### Mechanism

Not located. The list's element is `((_) => _) | null`, the nullable of a hole function that no
call through the list closes before the element is stored. The same list with `inc` annotated, or
with no `null` element, runs. The family's spellings refuse at different sites:

- the element read and called after a null test: `box pass`;
- the element handed to an un-annotated parameter that null-tests and calls it: `box pass` (was
  `monomorphize: unsupported argument type` before D17722);
- `[inc, null]` handed there: `convert i32 -> closure` (was `a generic function taken as a value
  reaches no call that fixes its type` before D17722);
- the element handed to a parameter annotated `((x: i32) => i32) | null`: `ref valtype with no
  interned shape`.

#### The nullable holder (COV-UNION, coordinator ruling)

The set is tagged, so its value is its id at every holder and its `F | null` is `i32 | null`
(`nulTagIdRepTy`), as a record field already stores it (D15560). A binding needed only that union's
registration. A list does not: the checker types the element name itself at the literal's element
type `((_) => _) | null`, and the tag decision compares an element's type against the set
(`ftHoldKind`, `ftLitJoin`, `ftIsS`, the leaf emission), so `inc` is never a leaf there. The ruled
fix is one predicate in check_fn_tag, "this element type is the set or the set's nullable", that all
of them read; the join delivers the null into the nullable reference (`[if c {inc} else {null}]`
reaching the IR verifier, rule 2, is the clause-1 control). The other faces:

- `call(if c { inc } else { null })` to an un-annotated parameter: `union atom has no value box`;
- `call(inc); call(null)`: `tag dispatch result rep`;
- `let g = null; g = inc`: `call of a non-declaration`;
- the binding beside an annotated `((x: i32) => i32) | null` of the same member, chosen by an
  `if` with `null`: `if arm coercion`; bound to the member directly
  (`const k: ((x: i32) => i32) | null = inc`): `call of a non-declaration`. The null is needed:
  the same pair with a non-null annotation `(x: i32) => i32`, or with no `null` on either side,
  runs, so this is the nullable holder, not the tagged-versus-closure join.
