### D14884 — a hole lambda returned through an identity from an inferred-return function is pinned by mono's rung B, not by the elaboration

**runs today and must keep running · refutation pin for retiring mono's rung B (`monoOpenFnFlowPin`) · filed 2026-11-01 against master `443394d44`**

Repro:

    function fw(f) { return f }
    const lam = (x) => x
    function deliver() { return fw(lam) }
    const v: (x: i32) => i32 = deliver()
    print(v(3))

Want:

    3

#### Mechanism

`deliver`'s return is inferred, so nothing at `fw(lam)`'s own position says which instance of
`lam` it carries. The only fact is the declared type of `v`, one return hop later. The
elaboration flows forward only (Decision 5), so it leaves `fw`'s parameter open, and rung B
pins it by reading that later destination. With rung B disabled the program is refused with
`emitProgram: monomorphize: unsupported argument type for f in a call to fw`.

#### The forward answer

Step 3's singleton function type. `deliver()`'s inferred result is `Fn#lam`, which flows forward
through the return unchanged, and the delivery to `(x: i32) => i32` is a coercion record that
instantiates `lam` at that destination. Rung B can be deleted once `Fn#d` reaches inferred
returns. Until then, keep it and narrow it to this shape (plus the un-annotated map value).

#### Ablation

| ingredient changed | outcome with rung B disabled | needed? |
| --- | --- | --- |
| `function deliver(): (x: i32) => i32` | runs (the elaboration pins it at the return) | **yes** (the inferred return) |
| `const v: (x: i32) => i32 = fw(lam)`, no `deliver` | runs | **yes** (the return hop) |
