### D16239 — a `for` over `.values()` of an un-annotated map of hole functions does not pin the functions it calls

**closed 2026-11-15 · runs, prints `4` · was a loud emit reject, `a function-value call has no interned signature — parameter 1 of type _ has no representation in the function-value ABI`, clause 2, `vl check` rc 0 · found ablating [D16237](D16237.md) · filed 2026-11-15 against master `55151b054` · closed by one classifier of what a `for` loop's variable reads (`cwLoopVarSource`, check_write_scan.vl), which the write scan's place paths and the elaboration's slot store both call, the latter in place of its own step choice · fixture `maps/map-values-walk-pins-hole-fns.vl`**

Repro:

    function inc(n) { return n + 1 }
    const m = Map()
    m["a"] = inc
    for g in m.values() { print(g(3)) }
    // vl check: rc 0.  vl run: emit error at the call, parameter 1 of type `_`

Want:

    4

#### Mechanism

Two producers each answered which place a `for` loop's variable reads. The check side's
`cwSlotPath` and `cwForInBinderOf` read a loop's first variable as `[]` below its iterable. The
elaboration's slot store (`eplEdgeAt`'s `CW_UP_ITER` arm) took `eplStepOfRecv` of the iterable and
picked the first or second variable itself. Neither had a step for a `.values()` iterable, so the
call pinned nothing in the map's value slot, and `inc` kept its open parameter. Adding the step on
the check side alone moved the bare-function face to `internal: a function slot pinned at one
signature has no one closed type the elaboration delivers it at` (`monoStoredSlotFnTy`): the two
answers disagreed.

`cwLoopVarSource` is now the one answer, read from the AST and the iterable's type:

- the receiver a variable is one step below, and the step: `e` for a list's or set's element, and
  `v` for a map walk's second variable or a `.values()` element;
- -1 for a variable that reads no place: a list walk's index, a map walk's key, `.keys()`.

The check side calls it with the node's final type, and the slot store with its instance's type of
the iterable. It also corrects a one-variable map walk (`for x in m`), whose `x` is a key that both
sides had read as the map's value.
