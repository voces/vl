#### Mechanism

Three readings of an instance's re-check built each arm at the widened list, while the instance's
own type of the `if` (its substitution, which keeps a join of fresh lists apart) is the union of the
two lists, and the emitter tags each arm by that union's members:

* The `if`'s two joins (`ifTailElseJoin`, `ifTailBankValTy`) took `joinArmLit` of the concrete
  arms, `f64[]` and `i32[]`, which widens to `f64[]` and adopts each arm there. A join the template
  kept apart (`tpJoinUnions`) now keeps two lists apart in the instance too (`ifArmsJoin`).
* A list literal delivered to a union destination chose its arm by its template type (`B[]`), which
  no instance member equals, then by fit, which `[2]` meets at `f64[]` first (`listMemberIn`,
  `arrLitFitsList`). They now read the instance's own type (`liveNodeTyOf`).
* A returned literal's union arm compared arena indices (`listArmIn`), which an instance's `i32[]`
  need not share with the union's; it now compares types.

Before the fix: D2760 made the join of `[a]` and `[b]` keep the two list types apart
as `A[] | B[]`. In an instance that binds the pair to two different number types, the list each
arm builds is read back as an empty one. The same join at `(i32, string)`, `(boolean, i32)`,
`(i32, i32)` or `(i32, i64)` runs.

Related spellings:
- `const x: A[] | B[] = if k { [a] } else { [b] }`, or the same join returned from the function
  (D2760's own spelling), at `(i32, f64)`: invalid wasm, `type mismatch: expected i32, found f64`
  inside `w`.
- `print(x[0])` in the repro: traps, `out of bounds array access`.
