### D3191 — a call-result function field shares an anonymous row with another signature's literal and is called at that literal's closure type

**closed · an anonymous row's closure field is shared only at one signature, so a literal whose closure has another signature keeps its own row, and a call through it has no other literal's closure to be typed by · fixture `tests/cases/structs/anonymous-records-with-field-functions-of-two-signatures.vl` · was check-clean silently wrong · clause 1 · found by the #3286 review (`rv3286-2159/h/c1.vl`) · the same on master `36d233f66` · filed and closed 2026-09-29 against master `36d233f66`**

Repro:

    const a = { v: 1, f: () => true }
    function mk(): () => i32 { return () => 11 }
    const xs = [{ v: 2, f: mk() }]
    print(xs[0].f())
    print(a.f())
    // printed true, then true, on master

Want:

    11
    true

#### Mechanism

D3190's close checks the closure `fieldClosureFeOfRecv` types a field call by against the
receiver's type, and when it disagrees, looks for a literal of the right signature among the
row's literals (`fieldClosureFeOfWant`). A `mk()` field holds no lambda that lookup can find,
so it fell back to `a`'s `() => boolean`. The row sharing was the cause: the second round of
#3286 lets a closure share an anonymous row's closure field only at that field's signature
(`anonValueFitsField`), so `{ v: 2, f: mk() }` mints its own row and the only closure the
walk reaches is its own. The fallback itself is unchanged, and still reachable where a row's
recorded field type is a hole, which `fnFieldTyFits` does not refute.
