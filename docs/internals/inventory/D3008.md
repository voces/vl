### D3008 — a `let` re-seated at a wider declared record is reassigned another own-type literal binding, which is built at its own record

**closed · was check-clean invalid wasm on master `b34730ad9` and on #3253 · a literal-bound name assigned into a `let` bound to a literal is delivered at the row that literal is built at (`rsAssignLitRow`) · fixture `tests/cases/objects/record-literal-widened-bare-store.vl` · a non-fresh record assigned there is [D3010](D3010.md) · found by the #3253 review grid · filed 2026-09-28**

Repro:

    type D = { v: f64 }
    const x: i32 = 3
    const c: {[string]: D} = Map()
    let o = { v: x }
    c["k"] = o
    const p = { v: 4 }
    o = p
    print(o.v)
    // vl check: rc 0.  vl run: invalid module — type mismatch

Want:

    4

#### Mechanism

`p`'s walk saw `o = p` and asked `rsElemAssignSafe`, which cleared an un-annotated `o` only for a list element. It now reads the row `o`'s own literal is built at, so `p` is re-seated at `D` with it. The check is syntactic on `o`'s side (`rsLetLitInit`), so neither walk evaluates the other mid-flight.

As filed: The map store re-seats `o`'s literal at `D`, so the `let o` slot holds `D`'s record. `p` is a second un-annotated literal whose only use is `o = p`, and nothing re-seats it at `o`'s row, so `local.set` gets `{v: i32}` where `D` is expected. The walk does not follow an assignment into a binding that was itself re-seated.
