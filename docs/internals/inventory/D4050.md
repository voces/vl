### D4050 — a list of records is refused as a `readonly` list of a narrower record type, though the element flow and readonly covariance each run

**loud check reject · clause 2 (the refusal says `type-valid … but not yet supported by codegen`) · found writing `docs/spec/types.md` (lane SPEC) · filed 2026-10-11 against master `1df3c8f91`**

Repro:

    type Animal = { a: string }
    type Cat = { a: string, z: i32 }
    const cats: Cat[] = [{ a: "c", z: 9 }]
    const view: readonly Animal[] = cats
    print(view[0].a)
    // vl check: rc 1, "an object value of shape Cat flowing into Animal (reached through
    // Cat[] into readonly Animal[]) drops the field `z`: type-valid (structural width
    // subtyping) but not yet supported by codegen"

#### Mechanism

The owner's container ruling (DECISIONS.md §"No implicit container widening", 2026-09-23)
makes a `readonly` list covariant and lowers it by the element-converting copy (D791). The
element-level width check that guards a list delivery does not consult that rule. It
refuses every field-dropping element flow reached through a list, whatever the
destination's mutability. Here the pair is a layout prefix: the dropped `z` sorts after
`a`, so the D3631 limit does not apply, and a single `Cat` already flows into an `Animal`
binding and runs. A copy of the list's spine that shares the element records is sound,
because writes through the view reach the same records.

#### Ablation

| variant | outcome |
| --- | --- |
| this witness | refused, message above |
| `const an: Animal = cats[0]` (one element, not a list) | runs, prints `c` |
| `const ys: readonly f64[] = xs` with `xs: i32[]` (storage-changing readonly covariance) | runs |
| destination `Animal[]` (mutable) | refused, same message (D4051 is its wording) |
