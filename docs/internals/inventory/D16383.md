### D16383 — a type-bound member call in a function nested in a generic body is refused when two instances need two modules

**loud check reject · clause 2 · open · the nested-function face of [D4033](D4033.md) · filed 2026-11-15 against master `83a90988d`**

Repro:

    // file: c.vl
    export type Circle = { r: i32 }
    export function grow(self: Circle, o: Circle): Circle { { r: self.r + o.r } }
    export function mk(r: i32): Circle { { r: r } }
    // file: d.vl
    export type Sq = { s: i32 }
    export function grow(self: Sq, o: Sq): Sq { { s: self.s * o.s } }
    export function mkS(s: i32): Sq { { s: s } }
    // file: entry.vl
    import { mk } from "./c"
    import { mkS } from "./d"
    function f<T>(x: T, y: T): T {
      const k = () => x.grow(y)
      k()
    }
    print(f(mk(2), mk(3)).r)
    print(f(mkS(2), mkS(3)).s)
    // vl check: "`.grow` in a function nested in a generic body reaches one module's `self`-function, and Sq needs another's (the body of `f` at the call's argument types)"

Want:

    5
    6

#### Mechanism

A lambda or named function nested in a generic body is cloned per instance with its body
shared (`monoCloneLambdaSubst`), and the rewrite lowers the member call in that shared body once
(`drwWalkMemberCall`), so every clone calls the first instance's `grow`. The pin refuses the second
module's (`tbNestedSiteMsg`), since letting it through emitted a wasm that failed to validate.
Closing it means pinning the member call per lambda clone, as `monoPinMemberCall` does for the
instance body.
