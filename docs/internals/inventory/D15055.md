### D15055 — `==` between two lists whose leaf elements are stored apart is refused as having no lowering

**closed · runs, prints `false` · was a loud check reject, clause 2 · one loop reads each operand at its own storage (`emitListEqXCore`, a compare frame per side) and compares each pair by value: two numbers at the wider width (D15090), two boxes through the staged union compare, a box against a number, a nullable record against a plain one field-wise · one list level; a list literal beside a list stored apart (D15091) and lists of lists stored apart (D15092) stay refused · matrices `xrep-*-eq` · filed 2026-11-02 against master `92b47e1f1`, closed 2026-11-03**

Repro:

    const a: (i32 | null)[] = [1, null]
    const b: i32[] = [1, 2]
    print(a == b)
    // was: vl check, "`==` over (i32 | null)[] and i32[] has no lowering: the two are mutually
    // assignable but store their elements differently"

Want:

    false

#### Mechanism

The list compare cores read both operands at one rep. An `i32[]` element is a plain `i32` and an
`(i32 | null)[]` element a union box, so no one core reads both, and the checker refuses the pair
(`glistLeafKey` differs, or the two answer different core tokens). The same holds for `f64[]`
against `f32[]`, for `(P | null)[]` against `P[]`, and for `(i32 | null)[]` against
`(f64 | null)[]`. `string[]` against `(string | null)[]` shares one rep and runs. The capability
is a cross-rep core: an element loop that reads each side at its own rep and compares the values
(a box's tag and payload against a plain scalar or record).

#### Grading list

* `f64[] == f32[]`, `(P | null)[] == P[]`, `(i32 | null)[] == (f64 | null)[]`: the same refusal.
* `string[] == (string | null)[]`: runs, and must keep running.
