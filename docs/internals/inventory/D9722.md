### D9722 — a call-bound `const` of a generic called directly at one type and listed beside the generic called at another refuses

**closed 2026-10-27 · runs, prints `8` · was loud emit reject, clause 2, `a generic function taken as a value reaches no call that fixes its type` · fixed by (γ) slice 1: `ys` is a list of the set `{id}` held by index only, so it holds the set's ids and `ys[0]("abc")` and `ys[1](2)` each call `id`'s instance at their own tuple; pinned by `tests/cases/closures/call-bound-generic-listed-beside-generic.vl` · found closing [D9652](D9652.md) · present on master `4fce2a127` · filed 2026-10-22 against master `4fce2a127`**

Repro:

    function id<T>(x: T): T { x }
    function mk() { return id }
    const c = mk()
    const ys = [c, id]
    const s = ys[0]("abc")
    print(s.length + ys[1](2) + c("ab").length + c("x").length)
    // runs: prints 8

Want:

    8

#### Mechanism

Not traced. From the ablation only: `c` called at one type and also listed takes two lanes in
the split (`fsLetSplitKeys`, fn_split.vl, D9594), one per call key and one for the listed
value. With `c` called at two types the program runs, so the lane the listed read takes seems
to be the one no call reaches when the direct calls share one key.
