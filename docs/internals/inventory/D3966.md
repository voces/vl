### D3966 — a literal argument called through a `let` of a generic written with a concrete function traps when the parameter is not the literal's default type

**closed 2026-10-10 by lane CK · now a loud check reject, by the owner's ruling C (D3960: the concrete write needs the binding annotated, and the annotated spelling runs) · was loads then traps · found in review of #3500 (`rv3500/r3`: `loc_i64`, `loc_f64`, `loc_strlitunion`, `num_int_into_i64`, `num_int_into_f64`, `num_into_nullable`, `name_litlet_widened`) · filed 2026-10-10 against master `56f77d80f`**

Repro:

    function inner<U>(u: U) { print("I"); print(u) }
    function cI64(n: i64) { print("L"); print(n + (1 as i64)) }
    function main() {
      let k = inner
      k = cI64
      k(5)
    }
    main()
    // vl check: rc 0.  vl run: wasm trap: indirect call type mismatch

#### Mechanism

Not located. The program is well-typed: `k` holds `(n: i64) => void` and `5` is an `i64` there.
The call still instances the seed `inner` at the literal's DEFAULT type (`i32`; `string` for a
string literal), so it is lowered as a call of `(i32) => void` through a slot holding `cI64`. The
same happens at `f64`, at `i32 | null`, at a literal union `"a" | "b"`, and for an un-annotated
literal `let` (`let s = 0; k(s)`), in a function body or above the module binding's declaration.
