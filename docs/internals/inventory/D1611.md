### D1611 — the same analysis matches a WRITE by name over the whole program, so a push to a same-named binding in another function refuses a covariant assignment that runs

**loud check reject · filed 2026-09-05 against master `6517412df` · open · a clause-2 violation, the other face of D1610's mechanism · ZERO corpus cells**

Repro:

    type Circle = { r: i32 }
    type Sq = { s: i32 }
    type Shape = Circle | Sq
    function decoy() {
      const b: Shape[] = []
      b.push({ s: 3 })
      print(b.length)
    }
    function f() {
      const a: Circle[] = [{ r: 7 }]
      const b: Shape[] = a
      print(b.length)
    }
    f()
    decoy()
    // vl check: rc 1 — "a Circle[] cannot be assigned to Shape[] here: the list is WRITTEN
    // THROUGH somewhere in this program". Nothing writes through `f`'s `b`.
    // Delete `decoy`, or rename its `b`, and the program runs and prints 1 then 1.

#### Mechanism

`cwWrites` walks `P.nodes` for every list write in the module and asks `cwHas(set, rn)` of the
receiver's ROOT NAME, where `set` is the alias closure built the same way. Neither side resolves
a name to a binding, so `decoy`'s `b` and `f`'s `b` are one name to the analysis. D793's refusal
then fires on `f`'s assignment, which no handle in the program writes through. The message says
"somewhere in this program", which is honest about the analysis and not about the program: the
sentence describes the ARM that fired, and grading it one scope per row is what separates the
design rule (a covariant list assignment that IS written through is refused) from the mechanism
(a name matched without a scope).
