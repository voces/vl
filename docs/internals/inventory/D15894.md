### D15894 — a `let` list literal binding returned by an inferred function is refused when the call is delivered as a list of a wider record

**closed 2026-11-12, runs and prints `3` · was a loud check reject, clause 2, the same on master · a module `let` every write of which is a list literal holds only literals (`recFreshDeclOf`), so a function returning it relays no existing list (`noRetFnRelaysList`, check_list_origin.vl) and the call is copied where it lands, as a literal `const`'s is (D2194's rule) · graded by the `return_inferred` cells of `scripts/capability-probes/matrix/let-reassigned-list-into-wider-list.matrix.vl` · fixture `tests/cases/soundness/let-list-returned-by-inferred-fn-delivered-wider-runs.vl` · found grading D15871 · filed 2026-11-12**

Repro:

    type D = { v: i64 }
    let q = [{ v: 3 }]
    function g() {
      return q
    }
    const v: D[] = g()
    print(v[0].v)

Want:

    3

#### Mechanism

D3340 builds an un-annotated list literal binding at the list a delivery wants. Through an
inferred function's result the `const` binding is followed to its literal, but the `let` is not, so
the call's result is judged at the binding's own type and refused.
