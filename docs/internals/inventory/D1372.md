**THE ROW'S OWN MECHANISM PARAGRAPH PREDICTED A REGISTRATION AND THE PREDICTION WAS WRONG.**
It said the kind-2 element "has to be REGISTERED (`registerInlineUnion`) before a slot can key
on it, and that registration is what the annotation walk performs", so a seventh niche rung
could not reach it. Measured: deleting the exclusion alone — no registration work — makes every
one of this row's cells run. `collectTyReachRegister`'s LetDecl arm already walks an
un-annotated binding's arena type, so `i32|null` is registered before the literal is classified;
what was missing was permission to key the slot at the kind `refArrElemKind` already answered.
An attribution read off the code path is a prediction, and this one cost nothing only because
the cheaper experiment was run first.

**AND THE SECOND HALF IS THE ONE THE ROW COULD NOT PREDICT — THE SCALAR CLASSIFIERS.** The
exclusion had a load-bearing SIDE EFFECT nobody had named: while `arrLitIsRef` declined a
nullable-box literal, `arrLitIsF64` / `arrLitIsI64` / `arrLitIsStr` claimed it, and the two
classifiers agreed by accident. Admitting it alone broke two corpus fixtures — `[887.5]`
delivered into an `(f32 | null)[] | boolean` arm went `runs -> loud emit reject` with
`f64 array literal but f64 list type not collected`, and `["a"]` into `(K | i32 | null)[]` with
the string twin. `collectA` interned the ref list while `emitArr`'s ladder still tested
`isF64Lit` ahead of `isRefLit`: one heap type each way. The rule already had a home —
`arrLitBoxElem`, which the scalar classifiers consult and which reads `TyUnion` only — so the
fix is to teach it the NULLABLE spelling of the same box (`arrLitNulBoxElem`). Two halves, and
the second is invisible to any witness this row filed: only the corpus fixtures reach it.

#### Mechanism

`arrLitNulRefElemName` refused a kind-2 element outright — `if refArrElemKind(an) == 2 {
return "" }` — on the reasoning that the rungs above it all name a NICHE (a nullable list, map,
closure, struct or variant), whose element is a `(ref null $X)` and whose slot the ref-list
layer already knows how to intern, while `i32 | null` is a BOX with a tag. The literal fell to
the i32 list default and a `(ref $box)` was stored into an i32 backing.

**THE EXCLUSION WAS NOT LOAD-BEARING, AND THE ONE INSTRUMENT THAT SAYS SO IS `refElemArrName`.**
That function is the single authority both spellings reduce through, and it re-groups an
element into `(elem)[]` on exactly two gates: a NICHE nullable (list / closure / map /
declared-struct / variant), or `isValueUnionName(elem)`. The second gate is the union box, and
it is the gate the ANNOTATED walk uses too — `parenUnionArrElemName` reaches it through the
same predicate. So the name this rung re-forms for `i32|null` is `(i32|null)[]`, the kind
`refArrElemKind` answers for it is 2, and both are character-for-character what the annotated
`(i32 | null)[]` spelling interns. Deleting the exclusion keys ONE row, not a second.

The niches the exclusion was protecting decline one line earlier, at `nameIsRefArray`: a
`boolean|null` or `string|null` element is NOT re-grouped (their `| null` is a sentinel or a
nullable ref, and `isValueUnionName` excludes both), so `refElemArrName` returns the un-grouped
`boolean|null[]`, whose `unionMemberCount(base) >= 2` makes `nameIsRefArray` false. Those two
still fall to their own list reps, unchanged.

The null-free union element is the discriminator that named the rep: `f(): i32 | string`
records a `TyUnion`, not a `TyNullable`, so it never reaches this rung at all and ran already.
