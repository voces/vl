### D2865 — a record literal beside an annotated `{ f: i32 | null }` record reads its boolean field as `null`

**closed · was check-clean silently wrong, the same on master `4dc94bd23` · the record-literal row scan refutes a declared `i32 | null` field for a `boolean` value (`declRowFieldKindFits`) · fixture `tests/cases/soundness/record-literal-beside-nullable-i32-record.vl` · found by the #3227 review · filed 2026-09-27**

Repro:

    const n: { f: i32 | null } = { f: null }
    const x = { f: true }
    print(x.f)
    // PRINTS null

Want:

    true

#### Mechanism

Not localised past the ablation. The `{ f: true }` literal is read through the
`{ f: i32 | null }` row's nullable `i32` niche, so the boolean is printed as that niche's null.

Localised by the close: `i32 | null` is a union-box field (code 16), which
`anonValueFitsField` lets every atom into on a declared row, so `{ f: true }` matched
`n`'s declared row by name and was boxed there, and the collect pass minted it no row of its own.
Nothing compared the literal's `boolean` with the row's `i32 | null`. The close compares the two
field types' layout kinds; `boolean` does not widen into `i32 | null`, so the literal gets its own
row. `{ f: 5 }` still builds at the `i32 | null` row, where the checker lets it go.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the nullable field (`{ f: i32 }`) | runs, prints `true` | **yes** |
| the boolean (`{ f: 5 }`) | runs, prints `5` | **yes** |
| `boolean \| null` for `i32 \| null` | runs, prints `true` | **yes** |

`function p(o) { print(o.f) }` with `p(n); p({ f: true })`, which prints `null` twice.
