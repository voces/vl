### D9914 — a `??` over an un-annotated parameter at a never-null `i32` pin returns the pin's value as an `f64`

**closed · runs, prints `2` · was runs but wrong value on #4413's head `c466bdf48`, clause 1 (master `8700f0727`: check-clean invalid wasm) · `vl check` rc 0 · found reviewing #4413 · filed 2026-10-22 against #4413's head `c466bdf48` · closed by this change, by typing a `??` over a hole at a never-null number pin as the pin, whatever the default's width (`coalDeadAtPin`, check_hole_pins.vl), and reading the `??`'s type in an instance off the instance before the program's pin bank (`coalResultTyOf`, emit_ty_canon.vl) · fixture `generics/hole-coalesce-join-operand-tp-list-literal.vl`**

Repro:

    function take(a) { return a ?? 1.5 }
    const z: i32 = 5
    print(take(z) / 2)
    // #4413's head prints 2.5

Want:

    2

#### Mechanism

At a never-null `i32` pin the default is dead and `take(z)` is `5`, so `/ 2` is integer division.
The pin substitution of the `HD_COAL` hole answered the pin only under a declared type parameter
([D2951](D2951.md)), so at a hole it joined the pin with the default and typed the call `f64`, and
#4413's result annotation (`monoHoleRetNumPin`) made the instance deliver that `f64`. A hole now
answers the pin at a number pin too, and the annotation is removed. Calls at `i32` and at
`i32 | null` then pin the hole apart, so the bank holds no one type for the `??` and every emit
site asks the instance first.

and `string` pins, which keep the join.
