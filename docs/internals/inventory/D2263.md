### D2263 — any `import` let a top-level `function` or `const` spelled as a compiler intrinsic silently replace it

**closed 2026-09-23 — now a loud check reject (`'__add_i32x4__' is a compiler intrinsic and cannot be redefined — every call to it lowers to instructions inline, so this definition would never run`) · was check-clean silently wrong: `vl check` rc 0 and the user's body ran in place of the intrinsic (the witness printed `3`, the intrinsic's answer is `6`) · the same program with the `import` line deleted was already refused with that message · filed against master `e4f244373` · fixtures `tests/cases/simd/error-redefine-simd-intrinsic-with-import.vl`, `tests/cases/intrinsics/error-redefine-intrinsic-with-import.vl`, `tests/cases/intrinsics/error-redefine-intrinsic-binding-with-import.vl`, `tests/cases/modules/err-intrinsic-name-decl/`**

Repro:

    import { hypotF64 } from "std:math"
    function __add_i32x4__(a: v128, _b: v128) { return a }
    const v = __splat_i32x4__(3)
    print(__extract_lane_i32x4__(__add_i32x4__(v, v), 0))
    print(hypotF64(3.0, 4.0))
    // vl check (as filed): rc 0.  vl run (as filed): 3, then 5 — the user's function won
    // the call. Without the import line: refused at the definition.

#### Mechanism

The reservation is `checkNotEmitterIntrinsic`, run by `checkFuncDeclNode` and the `LetDecl`
arm on the declared NAME. An `import` puts the program into module mode, and `modBuildRename`
renames every top-level declaration of every module to `<name>$m<N>` — declaration and call
sites alike — before `checkProgram` runs. The checker then sees `__add_i32x4__$m0`, which is
no intrinsic, and the call resolves to the renamed user function, so the direction is USER
WINS: the intrinsic becomes unreachable from that module and nothing says so. D1585 is the
same dodge for builtin TYPE names. The fix widens D1585's pre-rename screen
(`driver.modCheckReservedDecls`) to call the name-only half of the reservation
(`checkNotIntrinsicName`) on every top-level `FuncDecl` and `LetDecl` of every module. All 234
reserved `__…__` names were graded one per row in both faces: 234 disagreed before, 0 after.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the `import` line | refused at the definition (already, before the fix) | **yes** |
| the arity/type match with the intrinsic (`function __load_i32__()`) | still ran the user body | no |
| declaration before use (declared after the call) | still ran the user body | no |
| `function` (a top-level `const __trap__ = (x: i32) => x + 1`) | still ran the user body | no |
| the ENTRY module (the definition in an imported `./lib`) | still ran the user body | no |

#### Grading list

The 24 compiler `__…__` literals that are NOT reserved (`__str_concat__`, `__print_i32__`,
`__f64_rem__`, `__start__`, …) are accepted in both faces and a user definition of each runs
beside strings, maps, floats and `%` unchanged — consistent, not part of this row. A nested
`function __trap__` inside a function body was already refused in module mode (nested
declarations are not renamed). An `extern` name redefined was already refused in both faces.
The import-alias twin (`import { bump as __trap__ } from "./lib"`, whose call ran `bump`) was
ruled by the owner and closed as D2268.
