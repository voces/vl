### D3621 — importing a builtin by name was refused as "not exported" with no word that the name needs no import

**loud check reject (parse error), by design — the row was its message, fixed 2026-10-04: a builtin named in an import list is still refused, and the refusal now says it is a builtin that needs no import · sunpa SP-034 · fixture `tests/cases/intrinsics/error-import-builtin-name.vl` · filed 2026-10-04 against master `7eeb9e8c3`**

Repro:

    import { sqrt } from "std:math"
    print(sqrt(2.0))
    // vl check: "sqrt" is not exported by "std:math" — `sqrt` is a builtin and needs no
    // import; remove it from this list

#### Mechanism

`modVisit` (`compiler/driver.vl`) refuses every imported name the target module does not
export, at the name's token, with one sentence. A builtin (`print`, `Map`, `Set`,
`fromCodePoint`, the numeric intrinsics `sqrt`/`abs`/`floor`/`min`/`max`/… and the emitter
intrinsics) is in scope in every module, so no module exports it, and `std:math` exporting
`powF64`, `sinF64` and friends makes reaching there for `sqrt` natural. The import stays an
error — the module design has no "import a builtin" form, and accepting one would make the
list say the name came from a module it did not. The refusal now appends the builtin note
when `isBuiltinCallName` (`compiler/typecheck.vl`, the predicate `builtinShadowMsg` already
used for "the builtin `x`", now shared) answers true. A name that is not a builtin keeps the
bare sentence; a module that does export a builtin's name is unchanged.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the name being a builtin (`sqrt` → `hypot`) | the bare "not exported" sentence | **yes** |
| `std:math` as the source (a local `./lib` that does not export it) | the same note | no |
| the import (call `sqrt` directly) | runs, prints `1.4142135623730951` | **yes** |
