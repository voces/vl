### D14574 — a read's `let` declared in an enclosing frame is classified at the asking frame

**closed 2026-10-28 — runs today and must keep running · the program printed right before and after; the defect was the binding storage column holding a row for `t`'s `k` keyed on the closure `() => k`, with its initializer classified there · closed by the slice in which a read's `let` belongs to the frame whose body declares it · filed 2026-10-28 against master `10c0b75f4`**

Repro:

    type K = "a" | "b"
    function t(ks: K[], kn: K | null) {
      for e in ks {
        const k = kn ?? e
        const f = () => k
        print(f())
      }
    }
    t(["a", "b"], null)

Want:

    a
    b

#### Mechanism

Return inference for `() => k` (`computeRetInference`) asks `exprIsLitAtom` of the read `k` with
the closure as the frame, before the closure's captures are recorded, so the capture channel
does not answer. The `let` channel then took the asking frame as the binding's owner
(`readLetOwnerOf`), and `letBindIsNulAtom(k, closure)` classified `kn ?? e` at the closure.
There `kn` is not a parameter of the frame being asked, so the parameter channel answered
`false` while `kn`'s type and annotation are both the `K | null` niche. The output stayed right
because the coalesce falls through to `e`. The parameter-read shadow (`VL_REP_SHADOW=1`, the
literal-atom Ident arms against the rep of the parameter's type) is what saw it: two
disagreeing lines in `closures/capture-walk-variable-coalesce`.

The close: `readLetOwnerOf` walks from the asking frame up its enclosing frames (`fnParent`) to
the one whose body holds the declaration or a copy minted from it, and answers -1 for a module
global or a module-scope block binding. The asker fallback is deleted. With it went
`readLoopVarIsLitAtom` and both of its arms (the walk variable "asked outside its frame's
emission", D3169): on the corpus no case is left for them, and D3169's own fixture prints the
same without them on the base as well.
