### D3865 — a function-scope `let` alias of a module-scope hole lambda, reassigned to a second module-scope hole lambda nothing else calls, leaves the second at its `i32` default

**closed (2026-10-08, lane SC) · was check-clean invalid wasm · found by the rv3449b function-scope written-alias probes (5 of 15 programs fail on master) · filed 2026-10-08 against master `09e133eb4` · pins: `tests/cases/closures/fn-scope-alias-of-module-lambda.vl`**

Repro:

    const c = (y) => y + "C"
    const e = (y) => y + "E"
    function mk(x: string) {
      let d = c
      d = e
      print(d(x))
    }
    mk("a")
    // vl check: rc 0.  vl run: invalid module inside `e`, `expected (ref $2), found i32; $2 is string`

Want:

    aE

#### Mechanism

Peer pinning, and the one-signature check from D3857, find the writes that store a lambda by
resolving each write's names in the lambda's own frame. A module-scope lambda's frame is the
module, so a write inside a function (`d = e` in `mk`) was resolved at module scope. There `d`
is no binding, so the write was never seen: `e` took no peer signature and was emitted at the
hole's `i32` default. Each of those three sites now resolves a write at module scope in the
function that holds it (`monoTopFrameOf`). The `f64` spelling, which validated and then trapped
on the `i32`-default call, is D3859; the same change closes it.
