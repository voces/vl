### D15215 — a record literal holding another function's record result, delivered to a wider record, is built at its own record

**closed 2026-11-04 by lane destringify, runs, prints `4` · was check-clean invalid wasm, clause 1 · `recFnBuiltAtDst` built `w`'s literal at `K` by stamping its reps (`recordRepTyAdopt`) and delivered none of its field values, so `mk()` stayed at its own row in a `J`-stored field; `recLitFieldsDeliver` now delivers each field value at the destination's field through `recAdoptNote`, as the literal written at `K` delivers it · fixture `soundness/record-literal-holding-call-built-at-wider-record-runs.vl` · matrix `returned-literal-holding-call-into-wider-record` · named set `d15215-literal-field-call` · found grading the nested-field defect step5 handed the destringify lane · filed 2026-11-04 against master `b4bdefff0`**

Repro:

    type J = { f: i32 | null }
    type K = { j: J }
    function mk() { { f: 4 } }
    function w() { { j: mk() } }
    const k: K = w()
    print(k.j.f ?? 0)

Want:

    4

#### Mechanism

`w`'s literal is built at `K` where `k` delivers it, but its field `j` is `mk()`'s result, which
`mk` builds at its own record `{f: i32}`; the field is stored at `J`'s storage and handed a record of
`{f: i32}`. A single delivery is enough, so this is not the two-site rule (`recSitesLandAt`): the
build of `w` at `K` does not reach the call inside its literal.

#### Ablation

| --- | --- | --- |

| a second binding `const y = w()` beside `k` | still invalid | no |
| `k` read through `y: K = w()` beside `k` | still invalid | no |
