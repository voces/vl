### D1897 — a `string | null` element pinned at both `T[]` and `T` delivers a nullable string where the instance wants a non-null one, silently

**check-clean invalid wasm · `type mismatch: expected (ref $type), found (ref null $type)`
in the module's top-level code · `vl check` rc 0 · clause 1 · filed 2026-09-07 against master
`1a67d7811` as the one element type [D1896](D1896.md)'s close does not move · 0 corpus cells**

Repro:

    function mkS(i: i32): string | null {
      if i == 0 { return null }
      "a"
    }
    function two<T>(xs: T[], t: T): i32 { return 1 }
    const rs = [mkS(1)]
    print(two(rs, mkS(2)))
    // vl check: rc 0.  vl run: the emitted module failed to validate

#### Mechanism

The same instance shape as [D1896](D1896.md) — one generic carrying both `T[]` and a bare `T`
— at a `string | null` element, which is a NICHE rather than a shape row, so D1896's binding
fix (the pin no longer carries grouping parens) does not reach it. The instance is minted and
its signature validates; what does not is the ARGUMENT delivery in the caller, which hands a
`(ref null $string)` to a parameter the instance declared non-null.

Annotating either argument fixes it, and each alone is enough: `const rs: (string | null)[]`
runs, and `const t: string | null = mkS(2)` passed as the second argument runs. So the two
faces disagree about the REP while the checker agrees about the TYPE, which is the
annotate-everything shape — but here the un-annotated face is SILENT rather than loud, so it
is a clause-1 violation and not a capability gap.

Not measured: whether the same delivery is wrong for a `string | null` RETURN at the pin
rather than an argument, and whether the nullable-map element that D1896's close moved from
silent to running was the same delivery or a different one.
