#### Mechanism

The record-row class is `repKeyOf(ty, "row")`, the key behind `repRowId`, which `buildStructTwins`
keys heap twins on through `slotCanonId`. It first keyed 31 pairs apart that share a row. The row
mode now spells a record's fields in layout order (`fieldNameOrder`), a nullable record field as
its record (both store a `ref null` to one row), and a union's members in one order, which closes
26 of them at no byte cost (0 movers over `tests/**` and the distilled corpus).

The 5 that remain are arms of one union whose discriminant is a literal set in one arm and
`string` or another set in the other (`kind: K` against `kind: string`). D1023/D1050 lay them at one
row because they are members of one union; the type of either arm alone does not say so. Deduping
literal members in the key is not the fix: the key spells every string literal `string`, so
`"a" | "b"` and `"z"` differ only by member count, and deduping merged 15 pairs that build at two
rows, which was measured and reverted.

**And the key's SIZE grows with record sharing.** `repKeyOf` spells a referenced record inline at
each place it is reached, so a diamond of records (`D_n` holding `D_{n-1}` twice) has a key that
doubles per level, capped at 262,144 characters. Warming every declared record's class before the
elaboration failed `tests/vl_scaling_shape_test.ts` on all five diamond-depth axes (fuel ratio 4.4 to
7.1 against bars of 2.5 to 4.45), so the class is computed only when a reader asks. A reader that
asks per record on a hot path needs a fixed-size identity first: `repRowId`'s hash-consed id within
one compile, or a memoised structural hash.
