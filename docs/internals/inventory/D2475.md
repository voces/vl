### D2475 — a `self`-function named after a member its receiver type already has is never called, and nothing says so

**closed 2026-09-25 — now a loud check reject at the declaration: "`get` is already a method of `{[i32]: i32}`, so `m.get(…)` would never call this function — rename it" (code `self-fn-shadowed`) · owner ruling 2026-09-25 (collections Q6, generalised): a `self`-function the member-call order can never reach is an error (DECISIONS.md, "A self-function the resolution order can never reach is an error") · filed 2026-09-25 against master `0a0d24ac9` from the critic witness `p7.vl` · fixtures `tests/cases/methods/error-self-fn-shadowed-by-method.vl`, `tests/cases/methods/error-self-fn-shadowed-by-field.vl`, `tests/cases/methods/self-fn-not-shadowed-controls.vl`**

Repro:

    function get(self: {[i32]: i32}, k: i32): i32 | null { 42 }
    const m: {[i32]: i32} = Map()
    m[1] = 7
    print(m.get(1) ?? -1)
    // vl check, filed: rc 0.  vl run: prints 7 — the built-in `get`, never the function's 42

#### Mechanism

`recv.name(args)` resolves in a fixed order (`checkMemberCallNode`): a built-in method arm of
the receiver's kind (list, map/set, string), then a field of the receiver type (a callable one
is called), then a `self`-function in scope. A `self`-function whose name an earlier rung
already owns for every receiver its `self` admits is dead code, and the declaration was
accepted without a word. Worse, the emitter's UFCS rewrite did not ask about built-ins at all,
so for a list, a set or a string it called the function the checker had not typed: on master
`function push(self: i32[], x: i32) { print(99) }` made `xs.push(1)` print `99` and leave the
list empty, `function pop(self: Stack): i32` over `type Stack = i32[]` was check-clean invalid
wasm, and `function add(self: Set<i32>, …)` ran the function while `s.has(1)` read `false`
(that half is [D2476](D2476.md)).

The close: `checkFuncDeclNode` asks `selfFnShadowRung` of every named function whose first
parameter is `self`. It answers from the same tables the member-call arms use
(`listMethodNames`, `mapMethodNames`, `strMethodNames`; `length`/`size` excluded, since they
are member reads and their call spelling does reach a function) and from `tyFieldTyOf`, after
aliases, newtypes and string-literal receivers. A type-parameter `self` is never refused. A
`Set<T>` is its own type (#3158) with its own table: `add`/`has`/`delete`/`keys`/`values` are
members and refused, `get`/`set` are not and stay legal; a map, boolean-valued or not, is the
reverse for `add`/`get`/`set`.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the name matching a built-in method (`get` → `lookup`) | the function runs, prints 42 | **yes** |
| the receiver kind owning that name (`self: i32`) | the function runs | **yes** |
| the annotation on `m` (inferred from `Map()`) | same refusal | no |
| the call itself | same refusal (it is the declaration) | no |
| a field instead of a method (`type P = {x: i32}`, `x(self: P)`) | same refusal, `field` | no |
