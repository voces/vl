### D15108 — a function-valued composite parameter takes no pin type from the elaboration: a generic function value has no closed type at its read

**runs today and must keep running · structural: the named decline of the composite-pin fact (the elaboration's per-call pin type for a composite parameter, D15107 class B) · the elaboration's walk type of a read holding a generic function value is -1, so `monoElabCompositeTy`'s "the type holds a function" decline stays, and `monoPinTyParamComposite` keeps deriving these pins · 14 of the 1,519 `@run` files declaring a type parameter or a nested function, measured 2026-11-03 · filed 2026-11-03 against master `ff23f8a99`**

Repro:

    function idg<T>(t: T): T { return t }
    function app<T>(g: (x: T) => T, v: T): T { return g(v) }
    let f = idg
    const c = idg
    print(app(f, 3))
    print(app(c, 4))
    print(app(c, "s"))

Want:

    3
    4
    s

#### Mechanism

`app`'s parameter `g: (x: T) => T` is a composite annotation that holds a function. At `app(f, 3)` the argument reads a binding of the generic `idg`, whose type stays open (`<T>(T) => T`) until mono pins it at the call's binding, so the elaboration has no closed type for the read (`elabWalkTy` is -1). Mono's pin type is `(i32) => i32`, built by `monoPinTyParamComposite` from the binding. Every other composite parameter's pin type equals the argument's type closed under the instance, which the elaboration answers.
