### D15263 — a nested generic that captures only a closed value gets one elaboration key for every enclosing instance, which mono builds once per frame

**runs today and must keep running · parked: the fix needs a capture fact produced by the checker or the elaboration · structural: in `generics/nested-generic-capture-callers-that-run.vl`, `shadowOther<T>(_x: T, k: string)`'s nested `inner<T>(u: T)` reads `k` and no outer type variable, so the elaboration keys it once per binding (`ek5` at `i32`, `ek6` at `string`), while mono, which builds a capturing nested generic per enclosing frame, records each key at two instances (`10#i32` and `10#^20i32`) · found by the slot probe while sizing [D15106](D15106.md) · filed 2026-11-04 against master `ccfdb7a33`**

Repro:

    function shadowOther<T>(_x: T, k: string) {
      function inner<T>(u: T) {
        print(k)
        print(u)
      }
      inner(3)
    }
    shadowOther(true, "K")
    shadowOther(2.5, "L")

Want:

    K
    3
    L
    3

#### Mechanism

Measured with a probe on `monoNestedCallFrame`, 2026-11-04. Mono keys a nested generic that
captures anything by the enclosing instance's slot (`^<slot>`), and it has to: the two frames
print `K` and `L`. `shadowOther(true, "K")`'s instance takes the template's own slot, so its
`inner` has no frame segment; `shadowOther(2.5, "L")`'s is slot 20. Every call site agrees, so
this is not the call path choosing the frame.

The elaboration's parent rule (`elabParentForAt`) keys a nested declaration under an enclosing
instance only when it reads a type variable on that instance's chain, or for an anonymous lambda
with an untyped parameter. `inner<T>` redeclares `T` and reads only the closed value `k`, so it
gets no parent, and one key serves both frames. `viaOwnLambda`'s `inner`, in the same file, reads
`T` through `x` and does not collide.

#### Options

1. The elaboration reads `captureNamesOf` (emit_classify.vl) in `elabParentForAt`, and keys a
   declaration that captures a value bound in an open encloser under that encloser's instance.
   Refused: the capture fact's only producer is emit-side, and reading it from the elaboration
   inverts the stage order.
2. The checker or the elaboration produces the capture fact, and both the elaboration's parent
   rule and mono's frame keying read it. A larger design, for a payoff today of 2 collisions in
   1 file (of 124 in 52, plan on and plan off alike).
