#### Mechanism

Traced to emit; the deciding line is not yet found. The same defect needs no map:

    function inc0(a) { return a + 1 }
    const xs: ((a: f64) => f64)[][] = []
    const inner = [inc0]
    xs.push(inner)
    print(xs[0][0](6))

That loads, then traps with `indirect call type mismatch`. `xs[0] = inner` in place of the push runs,
as do `[inner]`, an annotated parameter, and a pushed literal (`xs.push([inc0])`). So the defect is a
push of a BINDING holding a container of an un-annotated function.

The checker and the elaboration agree for both spellings, by probe (2026-11-12):

- `fvaAdapt` and `fvaValueRowWalk` walk the push and the index write alike. Both bank `inc0` at
  `(f64) => f64` through `fvaValueRowAt`, outside `inferQuiet` (q=0, m=0).
- `recordRepTyAdopt` adopts only the read of `inner`, for both.
- `elabDrainHoleRows` drains the same rows (`?inc0.0 = f64`) and enqueues instance key 0 for both.

The emitted modules differ. For the index write, `inc0` is `(param f64) (result f64)`. For the push,
the same instance is emitted as `(func $inc0)`: no parameters and an empty body. The closure
trampoline for `[inc0]` is `(structref) -> ()` and tail-calls it. That is the empty closure row
`(()=>void)`, the row D14782 showed for a hole-function list whose element keys no closure signature.
So the gap is where emit picks the closure signature, and the instance, of the hole function inside
`inner`'s literal. An index-write delivery reaches that choice, and a push argument does not.
`arrLitRowTyIn` is not on that path; it is never asked for these literals.

For maps, `fvaValueRowWalk` also has no `TyMap` arm.
