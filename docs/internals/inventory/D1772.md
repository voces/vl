#### Mechanism

**The filed mechanism was wrong and the probe refuted it.** The row said `mapFindShapeOfNodeTy`
resolves the shallow map's shape, one container short. It never runs at all. Instrumented at
[D1758](D1758.md)'s pair, against the shallow struct-valued map that runs as the control:

    nested   [KIND let=36 ini=35 annRep=covered isMap=1] [CAP fe=3 name=held b=36 kind=map]
    shallow  [KIND let=26 ini=25 annRep=null    isMap=1] [CAP fe=2 name=held b=26 kind=map]
             [SHAPE ini=25 valName=[{n:i32}] valTyIx=43 FIND=0 MINTwould=1 mvLen=2]

No `SHAPE` line for the nested cell. `letInitProjKind` takes `annRepKindOf`'s answer when the
rep descriptor covers the node and falls to `nodeTyIsMap` when it does not; its companion
`letInitProjMapShape` declined **every node the descriptor covered** (`if annRepKindOf(ini) !=
null { return -1 }`). A nested map IS covered — the descriptor answers `"map"` for it — and a
struct-valued shallow map is not, so the two arms of one pair split the same domain on
opposite predicates. The pair was `("map", -1)`, and -1 is the MONO map: a different layout,
over a value carrying the nested map's own `$mapStruct` (slot 0, `kind=6`, `heap=16`).

The fix is the gate, not a new arm: the companion asks whether its twin answered `"map"`,
so the two cannot disagree about which route produced the kind. That is the pairing the
code's own comment already demanded — "a `"map"` cell whose shape stays -1 is the mono map,
which is a different layout and not half a fix".
