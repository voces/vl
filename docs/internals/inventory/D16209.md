#### Mechanism

The checker types `f(__add)`, with `f` a `const` value-`if` of two hole relays, as an open hole,
so it accepts any destination: `const z: string = __pick(true)` checks clean too. An existing
join of a call through a function set (`holeSetCallRetOf`) would type it, but it declines for two
reasons. The argument `__add` carries no set, since `elabFnValNote` records none for a type with a
type variable. Inside `__pick`, `f` carries no set either. The emitted value is an `i32` that an
un-annotated map stores at the hole's guess.

Both facts exist in the slot-store class graph, where `f`'s members are `{__ap2, __ap3}` and the
argument's are `{__add}`. That graph is built during elaboration, after check. Stage 6 switches
the check-side readers to the classes. The row closes there, with
`distilled/named/d16209_map_single.vl` and `d16209_map_sum.vl` as its acceptance cells. A narrower
interim fix, `elabFnValNote` recording a declared hole function's own singleton set, was declined:
stage 6 would delete it.
