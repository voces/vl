### D2271 — a nest of if-expressions in the then arm was classified once per path, so its compile cost doubled per level

**closed 2026-09-23 — the witness prints `1` at depth 16 and at depth 60, each under 0.1 s · was exponential in the nest depth on master (~1.8^depth: depth 16 took 0.32 s) and on #3094's first head (depth 13 took 3.4 s and 1.49 GB, depth 16 was a compiler trap `allocation size too large`) · fixed by `ifExprRefKind` answering null for a join the checker typed as a bare number or boolean, and remembering its answers for the rest of one outermost query · found in review of #3094 · filed against master `6bfe5e770` · scaling pair `if-expression nesting depth` in `tests/vl_scaling_shape_test.ts`**

#### Mechanism

`ifExprRefKind` classifies a join from its deciding arm by asking a ladder of predicates. Two
of them (`exprStringArray` and `exprRefArray`) have an `IfStmt` arm that asks `ifExprRefKind`
of that arm again, so an inner join was classified once per asking path: at least two per
level. #3094 moved `exprF32Array` onto `exprListRep`, which has an `IfStmt` rung too and
allocates a `RepDesc` on each ask, so the base grew and memory ran out. There are two fixes.
First, a join whose raw recorded type is a bare `i32`/`i64`/`f64`/`f32`/`boolean` answers
null before any predicate runs; the raw type is used, not a pin, so a generic body's
hole-typed join is not claimed. Second, answers are memoised per (join, function) during one
outermost query and cleared when it returns. That covers list, string and struct nests,
which the scalar exit does not reach. `exprListRep` keeps the same discipline one level down
(D2275): its answers are memoised per expression for one outermost query, indexed by node and
stamped with the query's generation, so a nested join's arms are classified once per query.
