### D9020 — an un-annotated lambda calling an un-annotated function, delivered at a function type returning `f64`, loads and traps at the call

**closed · runs, prints `4` · was loads then traps, `vl check` rc 0, `wasm trap: indirect call type mismatch` · clause 1 · found closing [D9011](D9011.md) · filed 2026-10-21 against `31c154cea` · closed by giving a hole lambda's instance the scalar result of the concrete function type the checker typed it at (`monoLamCheckedScalarRet`, emit_mono.vl) · fixture `closures/hole-lambda-relaying-i32-at-f64-fn-type.vl`, matrix `hole-fn-lambda-relaying-i32-at-f64-fn-type`**

Repro:

    function inc0(a) { return a + 1 }
    const f: (a: i32) => f64 = (a) => inc0(a)
    print(f(3))
    // vl check rc 0, vl run prints 4 (was: wasm trap: indirect call type mismatch)

#### Mechanism

The checker types the lambda at `(i32) => f64` and records its widened `f64` return under the
lambda's node. Its parameter is still a hole, so the monomorphizer instances it, and the first
instance takes the template's `fnStmts` slot (`monoMakeInstanceFirst`) with no return
annotation. The emitter then looks up the inferred return under the instance's node, finds no
row, and classifies the tail `inc0(a)` as `i32`. The function and its trampoline are emitted
`(result i32)` while the call site's `$fnsig` is `(structref, i32) -> f64`. `(a) => a + 1` was
not instanced, because its body makes no generic call, so it kept the `f64` row. With the
lambda's parameter annotated there is no instance. The fix is `monoMakeInstanceRet`: when the
template's checked type is a concrete function type, and its scalar result differs from the
return expression's type, the instance takes that result as its annotation.
