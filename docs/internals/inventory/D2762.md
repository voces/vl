### D2762 — two single-field record literals of different field types, handed straight to one un-annotated parameter that reads the field, share one row

**closed 2026-09-27 · was check-clean invalid wasm (clause 1), and the lone-literal face silently wrong, on master `1df19732b` · the review's `h2` cell and its `f64`, reversed-order and bound-local-return twins · filed 2026-09-27 against master `f6db92e0d`, from the #3181 review · fixtures `tests/cases/objects/record-literal-to-hole-param-string-beside-i32.vl`, `tests/cases/objects/record-literal-to-hole-param-reads-its-own-field-type.vl`**

Repro:

    function g(o) { o.v }
    print(g({ v: "s" }))
    print(g({ v: 3 }))
    // vl check: rc 0.  vl run: prints `s` then `3`.
    // Was: invalid module in the top-level code — expected (ref $type), found i32

Want:

    s
    3

#### Mechanism

A literal handed to an un-annotated parameter records the parameter's hole (`{v: ?g.1}`) as
its context type, and that context is what `anonRowTyIx` banks as the row's type. Three readers
trusted it:

- `structIndexOfObjCtxGo`'s adoption rung sent every literal whose context differs from its own
  type to the row with that context, so both literals built at the first one's row. A context
  that still names a hole is not a record of another type; the rung now skips it.
- A field read in the instance formatted by the row's field type, which is the hole and reads as
  `i32`, so `p({ f: true })` printed `1`. The monomorphizer now records an instance parameter
  pinned at an anonymous row to the argument's own record type (`monoAnonParamPinTy`) when the
  argument is an object literal, or when the argument's type agrees kind for kind with the type
  the row was minted from (`anonRowKindsAgree`). `exprIsBool` reads that first.
- `anonRowScalarFits` could not tell a hole-typed row's `boolean` field from an `i32` or literal-set
  one, so a later literal of another kind joined it. The row now keeps the minting literal's own
  type beside it (`sAnonOwnTy`), read only for that comparison, never as the row's identity.

The own-shape rule #3220 tried (recording the literal's own type as the row's type) is not
used: it made a constructor's shared literal adopt a concrete row type, and D2850's rows are not
reintroduced. A constructor's `i32` or `boolean` pin no longer takes a literal-set row
(`instParamAtomFits`); where no other row fits it is D2850's loud refusal instead of a member
printed for a number.

| ingredient removed | outcome | needed? |
