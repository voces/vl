### D2762 — two single-field record literals of different field types, handed straight to one un-annotated parameter that reads the field, share one row

**closed 2026-09-27 by D2841's fix · was check-clean invalid wasm on master `7323baf55` · the review's `h2` cell and its `f64`, reversed-order and bound-local-return twins · filed 2026-09-27 against master `f6db92e0d`, from the #3181 review · fixture `tests/cases/structs/anon-row-code0-kinds.vl`**

Repro:

    function g(o) { o.v }
    print(g({ v: "s" }))
    print(g({ v: 3 }))
    // vl check: rc 0.  vl run: invalid module in the top-level code — expected (ref $type), found i32

#### Mechanism

Not localised past this: `g` is instantiated twice (`g` and `g$1`), and both instances take the
`{v: string}` row as their parameter and result, while the second call builds `{ v: 3 }` at
that row too — `struct.new $0 (i32.const 3)` into a string field. The `{v: i32}` row is never
interned. The anonymous-row machinery (`anonLeaf…`, the `??`-family folds keyed on a field-name
set) is the suspect: every ingredient that separates a working neighbour from this one is a
reason for the second literal to be resolved by its field NAMES alone.

Localised by D2841: a literal handed straight to an un-annotated parameter recorded the
parameter's open hole as its anonymous row's type (`anonRowTyIx`), so the row knew only its
field names. The row now records the literal's own shape when its context type is a hole.
