### D14845 — a hole lambda pushed onto a list of hole functions, called through it at two function types, leans on the split plan for a copy per type

**runs today and must keep running · runs only because the split plan copies the list per call type; with the split plan and the D6210 rung off it refuses at emit (`a function this call reaches through a list or join is already taken at another function type by an earlier call through it`) · γ's backlog gap (c), named by `docs/internals/closure-at-delivery-2026-11.md` and not covered by it · without the split plan since 2026-11-03: a lambda literal whose one position is a list element (a `push` or an index store, `ftArmOnlyLams`) may call its own parameter and still be an id, and a dispatch arm's lambda callee is resolved before mono's open-parameter refusal, so each call through the list reaches the lambda's own instance; a lambda that captures a written binding stays a closure and keeps the refusal with the plan off · pin `tests/cases/closures/lambda-list-element-called-at-two-function-types.vl` · filed 2026-11-01 against master `3e36a3c26`**

Repro:

    import { toString } from "std:fmt"
    function cat(a, b) { return a + b.toString() }
    function snd(_a, b) { return b }
    function apply2(g) { print(g("x", 2)) }
    const gs = [apply2]
    gs.push((g) => {
      print(g("z", 5))
    })
    for f in gs { f(cat) }
    for f in gs { f(snd) }

Want:

    x2
    z5
    2
    5

#### Mechanism

A lambda element has one rep in the list, so one closure, built at the first call's function type. The second call through the list wants it at another type, which the element path refuses (`monoElemTakenSig`). A named element would be the set's id and dispatch per call; a lambda is no id here.
