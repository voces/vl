### D2386 — an inferred list literal of a local closure's calls is not collected when a sibling function nests a same-named string function

**loud emit reject · `vl check` rc 0, then `emitProgram: array literal but list type not collected`, clause 2 · found in review of #3135 (D2289), the same on its base · filed 2026-09-25 against master `02cce0b14`**

Repro:

    function b() {
      function w() { "hi" }
      print(w())
    }
    function a() {
      const w = () => { 3 }
      const xs = [w(), w() + 1]
      print(xs[1])
    }
    b()
    a()
    // vl check: rc 0.  vl run: emit error, "array literal but list type not collected"
    // (on master the same program reads "index access but list type not collected")

#### Mechanism

A prediction until a close confirms it. The collect pass decides the literal's list type by
reading its elements' call results through a resolver with no position, which answers `b`'s nested
string `w` for `a`'s closure: the pass collects a string list while emission, positioned by #3135,
builds an `i32` one. It is not the collect-pass twin `emit_collect.fnIndexOfInScopeChainSid`: that
function's only callers are the default-argument fill and the direct-call lowering, neither of
which types a list. The annotated spelling runs, so the gap is the inferred element type.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| the binding annotated `const xs: i32[] = …` | runs, `hi`, `4` | **yes** |
| `b`'s nested `w` returning `5` instead of a string | runs, `5`, `4` | **yes** |
| the literal `[w(), w()]` (no arithmetic) | still refuses | no |
| the literal `[w() + 1]` (one element) | still refuses | no |
