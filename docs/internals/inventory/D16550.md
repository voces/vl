### D16550 — a call whose result stores `void` passes check and builds an invalid module

**closed 2026-11-15 · now a loud check reject (`` `void[]` stores `void`, which has no value: no list element, map key or map value can be `void` ``), the refusal DECISIONS rules for a `void` element · was check-clean invalid wasm, clause 1 (`expected i32, found (ref $type)`), and a loud emit reject for a generic's `U[]` · fixed in `checkCallNode` (`check_calls.vl`) · fixture `tests/cases/arrays/error-void-result-list-from-call.vl` · found by lane R2 · filed 2026-11-15 against master `3fad4b753`**

Repro:

    const r = [1, 2].map((x) => print(x))
    // vl check: `void[]` stores `void`, which has no value: no list element, map key or map value can be `void`

#### Mechanism

DECISIONS ("`void` is a real type in the lattice", point d) rules `void` non-storable: no
`void[]`. The checker enforced it on a written annotation (`voidStoreCheck`) and on a list
literal's element (`voidValueSlotErr`), but a type that stores `void` can also be formed by a
call: `.map` over a callback whose result is `void`, or a generic's `U[]` at a void `U`. That
type reached the emitter, which built an `i32` list over the callback's empty result. A call
whose result stores `void` is now refused at the call with the annotation's own sentence.
