### D1471 — an UN-ANNOTATED param gives an empty-collection hole nothing to pin from, so the argument builds the i32 default while the body reads another rep

**check-clean invalid wasm · filed 2026-09-03 against master `f0c824a7` · found as the one cell
of D1470's 38-cell position matrix that is SILENT on both seeds**

Repro (`vl check` rc 0; `vl run` reports the module failing to validate inside `take`:
`Invalid input WebAssembly code … type mismatch: expected i32, found f64`):

    function take(a) {
      const v = a
      v[0] = 1.25
      print(v[0] + 0.25)
    }
    take(__array_new_default__(3))

#### Mechanism

`constrainEmptyExpr(arg, at, expected)` at the argument boundary pins the argument's open holes
FROM the parameter's type — and an un-annotated param is a `TyVar`, which pins nothing. The
callee's `v[0] = 1.25` then pins the PARAM's own element to `f64` (the ordinary index-write pin),
so the body lowers f64 reads and stores while the argument, still unpinned, builds the i32 list
default. Two rows, one call.

The body re-check itself is not missing — it EXISTS and it works. A typed argument through the
same bare param (`take([1, 2])`) is a loud `cannot assign f64 to i32`, raised against the body
of `take` at the call's argument types. What slips through is the UNPINNED hole: the re-check
accepts an f64 store into an element nothing has committed, and that element then takes the
i32 default.

It is the BOUNDARY, not the value and not the intrinsic. Annotating the param (`a: f64[]`) runs;
handing over an argument that is already typed (`take([0.0, 0.0, 0.0])`) runs even with the param
left bare; and a read-only body (`print(v[0])`) runs, printing `0`, because nothing demands the
f64 rep on either side. The bare `[]` spelling is the same defect with a different validator
sentence (`expected i32, found f64`), which is what says the intrinsic is scenery here.
