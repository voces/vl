### D2341 — a closure written under a narrowing of a shared cell read the cell at its declared type

**closed 2026-09-24 — the witness prints `4`. Was check-clean invalid wasm (`type mismatch:
expected i32, found (ref $type)` inside `g`), found building D2339, filed against master
`90c3ba566`. Fixture `tests/cases/closures/capture-by-reference.vl` (`narrowed`)**

Repro:

    function main() {
      let x: i32 | null = 3
      const w = () => { x = 5 }
      if x != null {
        const g = () => x + 1
        print(g())
      }
    }
    main()
    // prints 4

#### Mechanism

`x` is written by a closure, so it lives in a shared cell and every read is `x[0]`. The
emitter narrows the index place `x[0]` under `x != null`, which is how the maker's own reads
unbox. A closure takes the narrowings live where it is written through `capNarrowRecord` /
`capNarrowSeed` (`compiler/emit_classify.vl`), which banked only keys equal to a free name,
and the free name here is the cell `x`, not `x[0]`. The closure read the cell's `i32 | null`
element where the checker had typed `i32`. They now also bank and replay the `c[0]` key of a
cell `captureBoxRewrite` made (`cboxCellNames`). The checker already refuses a later write that
would retire a narrowing a closure captured, so the replay is sound. D2339 made the defect
common: any narrowed read, inside a closure, of a binding assigned after the capture.
