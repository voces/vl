### D3175 — a hole's field function from an inline record literal is called with no function type again when the body also reads another field of the literal

**check-clean silently wrong · clause 1 · the continuation of D3142, found by the #3283 review (`rv3283-3186/w/w3.vl`, `w6.vl`) · the same on master `934f169f4` · filed 2026-09-29 against master `934f169f4`**

Repro:

    function F(z) {
      print(z.v)
      const g = z.f
      print(g())
    }
    F({ v: 3, f: () => true })
    // prints 3, then 1

Want:

    3
    true

#### Mechanism

Not localised past the ablation. D3142's close binds the literal's own record type where it
differs from its anonymous row only at function fields the row holds as `_`. A body that reads a
second field of the same literal leaves the binding at the row again, so `g` has no function
type at the pin. The likely cause is the row holding `_` at a field the close does not admit
(`monoObjDiffersInFnFieldsOnly` declines it), unconfirmed. The second read has two faces: a
second function field `z.h()` traps where the result is `f64` or `i32 | null`, while the data
field `z.v` refuses those results loudly.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| no `print(z.v)` (`{ v: 3, f: … }`, `g()` only) | prints `true` (D3142) | **yes** (the second read) |
| `const r = { v: 3, f: () => true }` then `F(r)` | prints `3`, `true` | **yes** (the literal argument) |
| `print(z.h())` over `{ f: () => true, h: () => 1 }` | prints `1`, `1` | no |
| that, with `f: () => 2.5` or `(): i32 \| null => null` | prints `1`, then indirect call type mismatch | no (the trapping face) |
| `z.inner.f` over `{ inner: { f: () => true } }` | prints `1` | no |
| `print(z.v)` with `f: () => 2.5` | loud emit reject, no interned signature | no (the loud face) |
