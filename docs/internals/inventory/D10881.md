### D10881 — a generic returning a record whose `(T | null)[]` field holds a bare `null` refuses the `null` at a `string` pin

**closed 2026-10-23 — the filed repro RUNS and prints `2` · was a loud emit reject, `emitProgram: bare null needs a struct-typed context` · clause 2 · found by lane C3 writing the type-parameter fields of `shapeFieldsRideTyParam` · filed 2026-10-23 against master `ec57e9a8e` · fixture `tests/cases/generics/record-nullable-type-param-list-field-literal.vl`**

Repro:

    function f<T>(x: T): { g: (T | null)[] } { return { g: [x, null] } }
    print(f("s").g.length)
    // vl check: rc 0.  vl run: emitProgram: bare null needs a struct-typed context

Want:

    2

#### Mechanism

The list literal's element classifiers (`arrLitIsStr`, the string, `i32` and index-store
predicates in `emitArrStr`, `emitArrI32` and `emitIdxStoreValue`) read the node's type from the
template, where the element is `T | null`, not `string | null`. So the literal fell through to
the struct-typed `null` arm. They now read the type at the instance (`arrElemIsNulStrAt` and
`arrElemInstTyAt`, which gains a type-variable leg through `nodeTyInOf`). With the instance
reading its own rep, `monoNicheNulListCheck` no longer refuses the `string` and `boolean`
instances (D2525). A literal union of strings and a function type are still refused at the list
result (`tests/cases/generics/error-nullable-type-param-list-niche-litunion.vl`). The record-field
spelling of the literal union is D10934.

#### Ablation

| the result is the list itself, `(T \| null)[]`, at `string` | refuses as `a nullable-string list element has no rep` | no |

#### Grading list

The list-result spelling `function f<T>(x: T): (T | null)[] { return [x, null] }` with
`print(f("s").length)`, which refuses with a different sentence while its concrete twin
`const g: (string | null)[] = ["s", null]` runs; and the bound spelling, `const g: (T | null)[]
= [x, null]` returned as `{ g: g }`, which refuses the same way.
