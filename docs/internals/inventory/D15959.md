### D15959 — the owner-ruled reference-identity operator `===` is unbuilt, and the parser's refusal contradicts the ruling

**loud check reject · parse error · filed 2026-11-12 against master `2bb5d2f2a`**

Repro:

    type A = { x: i32 }
    const a: A = { x: 1 }
    const c: A = { x: 1 }
    print(a === c)
    // vl run: parse error, "VL has no `===`; `==` is already strict — write `==`"

#### Mechanism

`strictEqTail` (compiler/parser.vl) treats a third `=` after `==` as a JavaScript reflex,
consumes it and reports that VL has no `===`. The owner ruled on 2026-09-01
(`docs/identity-design.md` §0, DECISIONS A15) that `===`/`!==` is reference identity over
reference reps, a check error on scalars and `string`. No lowering exists, so the operator is
refused at parse and the message names a rule the design reversed.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `a == c` | runs, prints `true` (structural) | **yes** |
| operands `1 === 1` | the same parse error, where the ruling owes a check error | no |

#### Grading list

The identity design's §0 acceptance list (ROADMAP A15), and the `==`-on-views ruling
(open-rulings `width-view-equality`), whose identity counterpart is `===`.
