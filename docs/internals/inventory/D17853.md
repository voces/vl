### D17853 — a nullable over a generic application minted in the application's fill is read as another row than the signature's equal nullable

**runs today and must keep running · refactor-blocking, reader not yet found: under S2a's interning without the application in the nullable's key, the witness is refused with a depth-limit delivery error at its first `cons` call; on master the two nullables are two rows · filed 2026-11-28 against master `498410d70` · owner COV-IS**

Repro:

    type L<T> = { head: T, tail: L<T> | null }
    function cons<T>(h: T, t: L<T> | null): L<T> { return { head: h, tail: t } }
    function len<T>(l: L<T> | null) {
      let n = 0
      let c = l
      while c != null {
        n = n + 1
        c = c.tail
      }
      return n
    }
    const xs = cons(1, cons(2, cons(3, null)))
    print(len(xs))
    // vl check: rc 0.  vl run: 3

Want:

    3

#### Mechanism

The fill of `L<T>` mints `L<T> | null` for the field `tail`; the signature's `t: L<T> | null`,
resolved after, is that same row once rows intern by structure. Ablation on S2a: interning off
for nullables, or for a nullable whose inner is an application row, runs; the seen-stack and the
fresh-scope marks are not the reader. Counters put it in `substTyDeep`: one such nullable comes
back unsubstituted because its inner application row does, after `substCyclicApp` declines it.
The reader must be found before S2a lands, even though the application identity in the key
(D17852's close) masks it. The use-site answer is S2c's, with records.
