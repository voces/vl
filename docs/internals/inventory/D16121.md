### D16121 — a function read back through a map of maps is called at a signature no stored value was instanced at, when that call is the only one

**loud emit reject · `` emitProgram: a function-value call has no interned signature — no function value of type `(f64) => f64` reaches this call to intern its signature `` · clause 2 · the same program runs once the function is called through its own map first, or held in a list or record instead · filed 2026-11-14 against master `1b5ee549`**

Repro:

    function half(a) { return a / 2.0 }
    const m4 = Map()
    m4.set("a", half)
    const mm = Map()
    mm.set("k", m4)
    const f = mm.get("k")
    if f != null {
      const g = f.get("a")
      if g != null { print(g(5.0)) }
    }

Want:

    2.5

#### Mechanism

`m4`'s slot finds no pin (`monoStoredSlotFnTy`, `elabSlotUncalled`), because the only call reaches
`half` through `mm`'s value. The elaboration does not alias `mm`'s value slot to `m4`'s slot the
way it aliases a list element or a record field to it. `m4` closes at the uncalled default, and
the read-back call names a signature no stored value was instanced at. A `for` loop over `mm`
reaches a related refusal: the loop variable's own value reads keep their open type, because a
loop variable is no binding `monoReadLetFrame` resolves.

#### Containment, 2026-11-14

With a lambda of the call's signature elsewhere in the program, the read-back call found a
`$fnsig` and trapped on `indirect call type mismatch`, which is clause 1, instead of refusing.
D15941's pin let that through. `monoPinMapSlot`'s map-of-maps arm now declines when a stored
map's functions are uncalled (`monoStoredMapFnsUncalled`, through nested maps) and a value of the
outer map is read for its own values (`monoMapValuesRead`). That spelling refuses loudly again.
This row's close is what lets it run.
