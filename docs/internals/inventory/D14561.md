#### Mechanism

`vl check` over a directory ran its roots on a worker pool (`check_root_workers`,
scripts/vl-host/src/main.rs), and the pool stayed on under `$VL_FUEL` on purpose. Each
retired worker's fuel was added to the run's total. Each worker serves a root from the
module checks it already holds (`wiStat`, compiler/driver.vl), and which roots a worker
holds depends on which ones the schedule gave it first. Three default runs with
`VL_CHECK_STATS=1` served 203, 202 and 204 roots. The second run declined one root for
`demand` and re-checked its 84 modules. The result did not depend on the schedule, but the
cost did.

The close: `compile_pool_allowed` is now the one predicate for `vl test`'s compile pool and
`vl check`'s root pool. Neither runs under `$VL_FUEL` or a guest profile, so one store
checks every root, and the pooled fuel sum is deleted. The `[fuel]` line is read before
`$VL_CHECK_STATS` asks the instance for its counts, so the two together read the same
fuel. `VL_CHECK_STATS` alone still reads the pool's schedule.
