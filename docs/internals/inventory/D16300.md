### D16300 — a `??` whose default is a literal of another storage builds an invalid module when the call that binds its result comes before the function's declaration

**check-clean invalid wasm · clause 1 · found from [D12455](D12455.md)'s witness while mapping the open clause-2 rows onto architecture items · filed 2026-11-14 by lane J against master `089d6e0b`**

Repro:

    const a: boolean[] | null = null
    const y = pc(a)
    function pc(xs: boolean[] | null) { xs ?? [1] }
    print(y.length)
    // vl check: rc 0.
    // vl run: invalid module, `the emitted module failed to validate`.

Want:

    1

#### Mechanism

Not yet located. With `pc` declared first, the default `[1]` adopts the `??`'s `boolean[]` side and
the program prints `1`. With a `const` binding the call's result before `pc` is declared, the
binding's type is settled before `pc`'s body is checked, and the literal is built at its own `i32[]`
storage beside the `boolean[]` side, so the two arms of the `??` disagree in the module. An order
dependence, which DECISIONS.md's declaration-order independence rules out.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `pc` declared before the call | runs, prints `1` | **yes** (the order) |
| `print(pc(a).length)`, no binding (generic `pc`) | check reject, the owed `??` join | **yes** (the binding) |
| default `[]` instead of `[1]` | runs, prints `0` | **yes** (a literal of another storage) |
| `a: i32[] \| null` (one storage) | runs | **yes** |
| `pc<T>(xs: T[] \| null)` generic | invalid module the same way | no |
| inside a function `p` calling `pc` (D12455's neighbour) | invalid module the same way | no |

#### Grading list

The generic spelling (`pc<T>`) and the spelling inside a caller `p(t: boolean, c: boolean)` with
`let a` written under `if c`, both with `pc` declared after the call. With `pc<T>` declared first,
the call keeps its owed check reject.
