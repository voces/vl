### D9631 — a list literal holding an un-annotated parameter and arithmetic of it with a wider literal has no list type at emit

**closed · runs, prints `3.5` · was loud emit reject, `vl check` rc 0, clause 2 · CAPABILITY: `function f(x: i32)` prints `3.5` · found closing [D9620](D9620.md) · filed 2026-10-22 against master `54fb716a1` · closed by keeping a parameter's hole and its arithmetic beside an `f64` or `i64` operand apart in the list's join (`paramArithHole`, `tpOpenJoin`, check_tp_join.vl), so each re-joins at the pin, and by typing that arithmetic `f64` at an integer pin (`binArithPinTy`, check_union_mint.vl) · fixture `generics/hole-param-list-literal-mixed-width.vl`, matrix `hole-element-list-literal` 0 → 66 of 66 · with [D9632](D9632.md) closed, [D9680](D9680.md), [D9681](D9681.md) and [D9682](D9682.md) filed open**

Repro:

    function f(x) {
      const xs = [x, x + 1.5]
      print(xs[1])
    }
    f(2)
    // vl run: emitProgram: index access but list type not collected

Want:

    3.5

#### Mechanism

In the hole-typed body `x` is a hole and `x + 1.5` a derived hole over it. `tpOpenJoin`
kept two distinct parameters apart as a join each pin re-joins, but declined a derived
hole, so `joinTys` fell back to assignability and typed the list `_[]`, the element type
of `x`. At the `i32` pin that list is `i32[]` while its second element is `f64`, and the
emitter collected no list type for it. The derived hole also pinned at `i32`, since the
arithmetic recorded only an `i64` operand beside a hole. The literal now records its
`f64` too (with whether it adopts an `f32` pin), so the pin reads the arithmetic at `f64`
and the list at `(i32 | f64)[]`, as the `x: i32` spelling does.
