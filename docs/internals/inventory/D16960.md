### D16960 — an un-annotated parameter pushed onto a list of a record that stores a field differently is refused: the fresh argument is not built at the list's record

**loud check reject · clause 2 (the argument is a fresh literal, which the design builds at the record it is delivered to; the refusal is the shared-record rule applied to the parameter) · open · found grading D16958's parameter chain (`rec-adopt-chain-param.matrix.vl`) · filed 2026-11-18 against master `665aeae36` by lane F2**

Repro:

    type J = { f: i32 | null }
    function put(ys: J[], q) {
      ys.push(q)
      return 0
    }
    const xs: J[] = [{ f: 4 }]
    put(xs, { f: 9 })
    print(xs[1].f ?? 0)
    // vl check: rc 1, "{f: i32} is not J: they store field `f` differently (`i32` into `i32 | null`), and a record is shared, not copied, so only a fresh record widens. A write through the J would break the {f: i32}. Build the source as `J`, or copy it with a literal `{ f: q.f }`"

Want:

    9

#### Mechanism

The un-annotated `q` is instanced at its argument's own type, `{f: i32}`, and the body's
`ys.push(q)` then delivers a parameter, not a fresh record, into `J`, which the shared-record
rule refuses. Adoption builds a fresh literal at the record it is delivered to only where the
delivery and the literal meet in one scope (a binding's initialiser, a push of the binding); it
follows no edge from a parameter back to the call's argument. Binding the parameter to a `J`
local instead of pushing it runs, so the refused edge is the element store of a parameter.
