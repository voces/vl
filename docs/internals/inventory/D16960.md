### D16960 — an un-annotated parameter pushed onto a list of a record that stores a field differently is refused: the fresh argument is not built at the list's record

**closed 2026-11-18 by lane F2 · runs, prints `9` · was a loud check reject, clause 2 · closed by pinning an un-annotated parameter that a `.push` or `.set` stores into a closed record element to that element in the template, as a binding of it at the record already pins it (`bmParamAtClosedRecord`, `check_member_call.vl`), so each call's fresh literal argument is delivered to the record parameter and built there · pin: `tests/cases/records/unannotated-param-pushed-onto-declared-record-list.vl` · found grading D16958's parameter chain · filed 2026-11-18 against master `665aeae36` by lane F2**

Repro:

    type J = { f: i32 | null }
    function put(ys: J[], q) {
      ys.push(q)
      return 0
    }
    const xs: J[] = [{ f: 4 }]
    put(xs, { f: 9 })
    print(xs[1].f ?? 0)
    // vl check: rc 1, "{f: i32} is not J: they store field `f` differently (`i32` into `i32 | null`), and a record is shared, not copied, so only a fresh record widens. A write through the J would break the {f: i32}. Build the source as `J`, or copy it with a literal `{ f: q.f }`"

Want:

    9

#### Mechanism

A binding `const j: J = q` pins the hole `q` to `J` in the template, so each call delivers its
literal to a `J` parameter. A store into a container (`bmArgOk`, `check_member_call.vl`) instead
deferred a hole argument to a per-call method demand, re-asked at each argument's own type
`{f: i32}`. That delivered the parameter, not the fresh literal, into `J`, and the record solve
refused it at the pass end as a shared record.
