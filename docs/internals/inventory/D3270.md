### D3270 — a METHOD member of a type literal cannot name its parameters, though a function type now can (a ruling question)

**loud check reject · raised at the PARSE stage, `(parse error)` · open, awaiting an owner ruling · found 2026-09-29 beside PL-060 (owner ruling A1) · filed 2026-09-29 against master `569caa36c`**

Repro:

    type Shape = { area(scale: f64): f64 }
    function area(self: f64, scale: f64) { self * scale }
    function total<T: Shape>(s: T) { s.area(2.0) }
    print(total(3.0))
    // vl check: expected `)` but found `:` — the member's argument list takes types only

Want:

    6

#### Mechanism

`parseMethodMemberTail` reads the member's argument list with `parseTypeName` alone, while the
function-type arm of `parseTypeAtom` now takes an optional `name:` per parameter
(`parseFnTypeParam`). A method member is a call shape with the receiver implicit, so the same
documentation-only reading would apply: the names never enter the member's spelling
(`f(A,B):R`), all or none. Not landed with A1 because the ruling names function TYPES, and a
method member is a sibling construct, not a function type (`{f: () => string}` demands a
closure, `{f(): string}` only that the call types). Recommendation: accept the names under
A1's rule, discarding them from identity exactly as `(fn: i32) => i32` does.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `{ area(f64): f64 }` | runs, `6` | **yes** (the name) |
| `{ area: (scale: f64) => f64 }` (a function-typed FIELD) | parses; a different contract (a closure field) | no |
