### D15639 — a hole function called directly at one type and handed on in a `const` record to a callee that calls the field at another is refused by the checker

**loud check reject · clause 2 · `argument 1: expected i32, got string (the call of a function value at the call's argument types)` · the literal written as the argument runs since [D15638](D15638.md) · found closing D15638 · filed 2026-11-10 against master `20775a7d`**

Repro:

    function id(v) { return v }
    function call0(r, x) { print(r.f(x)) }
    function run(g) {
      print(g(5))
      const r = { f: g }
      call0(r, "s")
    }
    run(id)

Want:

    5
    s

#### Mechanism

`holeBindArgListsHole` follows a record literal only where it is the call's argument, so the
hand-on through `r` is not an open call and `holeBindInstance` pins `id` at `(i32) => i32`.

Tried 2026-11-10: following the `const` too (and forwarding through it in
`elabRecLitFwdTargets`) runs this repro, but when the function is instanced at two sets
(`run(dbl)` then `run(neg)`, every call at `i32`) the elaboration keeps no per-instance slot
fact for the record, so the binding stays a record of closures while the parameter becomes a
set: invalid wasm in a program that runs today. The list spelling has that fact
(`elabListParamSource`); the record needs its own before the checker can leave the call open.

#### Ablation

| spelling | outcome | needed? |
| --- | --- | --- |
| the literal as the argument, `call0({ f: g }, "s")` | runs, `5` `s` | **yes** |
| a list, `const fs = [g]` with `fs[0](x)` | runs, `5` `s` | **yes** |
