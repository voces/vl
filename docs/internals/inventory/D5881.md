### D5881 — an un-annotated lambda handed to a call through an un-annotated function parameter cannot infer its parameter

**closed 2026-10-17 by lane L3 · runs, prints `6` · was loud check reject · clause 2 · a lambda handed to a call of a hole callee, directly or on through a forwarder, types its parameters as holes and is pinned where the call binds the callee, at the parameter types of the function it is delivered to (`pinHoleLambdaArgs`, `monoHoleLamArgPin`); the spellings still refused are [D5931](D5931.md), [D5932](D5932.md) and [D5934](D5934.md) · pins: `tests/cases/functions/hole-lambda-through-hole-callee.vl` · found closing [D5842](D5842.md) · filed 2026-10-17 against master `60c4d1c43`**

Repro:

    function two(a: i32, b: (n: i32) => i32): i32 { b(a) }
    function outer(h) { return h(3, (n) => n * 2) }
    print(outer(two))
    // vl check: rc 1, cannot infer a type for parameter `n`

Want:

    6

#### Mechanism

From the ablation only. A lambda argument takes its parameter types from the parameter it is
delivered to. `h` is a hole, so the call `h(3, ...)` has no parameter type for the lambda while
`outer` is checked, and nothing re-types the lambda when `outer` is called with `two`.
[D5842](D5842.md)'s close seeds a lambda at a hole from a call that binds the hole, which this
call does not.
