### D17820 — one hole parameter handed two storages of a function at different reps reads both at one, and the call traps

**loads then traps · `wasm trap: indirect call type mismatch` · clause 1 (`vl check` rc 0) · open · one storage handed to the same parameter runs once D17817's close lands (#10744) · filed 2026-11-28 against master `186ae23a9` · owner I8-PREP · mechanism: instance per argument storage rep (coordinator ruling)**

Repro:

    function dbl(a: f64): f64 { return a * 2.0 }
    const g = (a) => a + 1
    const xs = [g, dbl]
    function walk(ys) { const v = ys[0]; print(v(3)) }
    walk(xs)
    const one = [g]
    walk(one)
    // vl check: rc 0.  vl run: wasm trap: indirect call type mismatch (in `walk`)

Want:

    4
    4

#### Mechanism

`xs` stores its members at `dbl`'s `(f64) => f64`; `one` stores `g` alone at another closure
signature. `walk` has one instance for both arguments, so its read of `ys[0]` and the call through
it take one storage's rep, and the other's closure is called at a type it was not built at. The
close keys the hole parameter's instance by its argument's storage rep, as the monomorphizer keys
an instance by type (coordinator ruling 2026-11-28): no converting copy at the call, which would
break aliasing, and no unifying of the two storages, each decided at its declaration.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the second call, `walk(one)` | runs, `4` (with #10744) | **yes** (two storages) |
| `one` as `[g, dbl]`, the same set | runs | **yes** (two reps) |
| `g` stored in a record field `{ f: g, h: dbl }` read by a second hole parameter, beside `xs` | the same trap | no (another holder kind) |
