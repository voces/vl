### D14760 — a fresh record literal handed to a type parameter is not built at the storage the instance delivers it to, so it is refused where the direct and hole spellings run

#### Mechanism

The literal is fresh, so the direct call `{ y: 2, x: 9 }.poke()` builds it at `V` and runs, and
so does a hole parameter (`function h(v) { v.poke() }`), whose instance takes the rep its argument
is built at (`callBindAdoptReps`, D14532). A type parameter's argument is built at its own type
`{y: i32, x: i32}`, so at the pin the delivery into `V` is a shared record stored differently and
is refused.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the type parameter (a hole `function h(v)`) | runs `1` | **yes** |
| the method spelling (`const r: V = v` in the body) | still refuses | no |
| `x`'s union in `V` | runs | **yes** |
| the literal (an annotated `{y: i32, x: i32}` source) | refuses, which is right: it is shared | **yes** |

A fresh BINDING (`const i = { y: 2, x: 9 }; g(i)`) runs in the method spelling since the pin asks
the caller's argument rather than the parameter (`pinArgOfParamRead`): the record solve builds the
binding at `V`, and the instance takes it as `T`'s rep. The inline literal, which the pin may not
stamp, and the binding spelling `const r: V = v`, refused by the instance's re-check, are left.
