### D3584 — a list index whose type is a type parameter is never re-asked at the pin, so `g<i64>(1)` indexes with an `i64`

**now a loud check reject 2026-10-03, naming the call · was check-clean invalid wasm, clause 1 · found by the #3357 review (D3539's binder reached it from a destination) · filed and closed by lane FZ against master `030a90e52` · fixture `tests/cases/generics/error-index-type-param-not-i32.vl`**

Repro:

    function g<T>(x: T): string {
      const s = ["a", "b", "c"]
      return s[x]
    }
    print(g<i64>(1))
    // master: vl check rc 0, vl run "invalid module … expected i32, found i64"
    // now: "array index must be i32, got i64 (the call's argument types)"

#### Mechanism

The index rule (`array index must be i32`) is `assignable(idxTy, i32)`, and `assignable`
answers true for a type variable, so the body admits `s[x]` and nothing asks again once `T` is
bound. Every other operation on a hole has a deferred constraint for this purpose; the index
had none. It now records one (`noteArgCstr` with the `ACF_INDEX` form) whenever the index type
carries a type variable, and `validateArgCstrs` refuses it at each call whose binding is not
`i32`, in the direct spelling's words. A hole parameter (`function h(x)` called with `1.5`) is
the same row and is fixed by the same constraint.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the type parameter (`x: i64` directly) | check error | **yes** |
| the non-`i32` binding (`g(1)`) | runs, prints `b` | **yes** |
| the explicit type argument (`g(1.5)`, `g("q")`) | same invalid module | no |
