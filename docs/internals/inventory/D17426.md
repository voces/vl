### D17426 — a hole function that reads its parameter through `?.` and returns it, delivered wider, emits an invalid module

**check-clean invalid wasm · clause 1 · `vl check` rc 0, `vl run`: invalid module inside `g` · legacy's bytes · filed 2026-11-25 by lane S1 against master `c59738bbd`, found by D17047's grid**

Repro:

    type A = { d: i32 | null }
    function g(v) {
      print(v?.d)
      return v
    }
    const c: A = g({ d: 5 })
    print(c.d ?? -1)
    // vl check: 0 errors.  vl run: invalid module, inside `g`

Want:

    5
    5

#### Mechanism

Narrowed 2026-11-25 by SOUND: since D17047's close the parameter and its literal are adopted at `A`, and the `?.` read itself builds `A`'s boxed field. The value is still handed on at the literal row's field type: `print(v?.d)` calls `__print_i32__` with the box, and `const z = v?.d` / `v?.d ?? -1` fail the same way, while `v.d` and `v?.d == null` run. So the `?.` read's recorded type is not refreshed when its receiver is adopted, where a `.` read's is.


D17047's spelling with `?.` in place of `.`. D17047's fix admits a `.` field read before the
hand-back, but admitting `?.` there alone does not make this run: another site still builds the
parameter at the literal's own row. `?.` on an annotated `v: A`, or an un-annotated `c`, runs.

Traced 2026-11-25 by SOUND: `g`'s instance is checked at the literal argument's own type, so
`v?.d` types `i32` there (the template types it as a hole), while D17047's close stores the
parameter at `A`'s row, whose `d` is a box. A `.d` read is emitted at its stored row (#10001) and
runs; the `?.` read builds `A`'s box and hands it on under the checker's `i32`. Either the instance
is keyed at the adopted record (checker), or the `?.` read is emitted at its stored row as `.d` is
(emitter; legacy's is frozen, so the IR's claim).

#### Grading list

`print(v?.d ?? 0)`, and a `?.` read nested in an `if` condition.
