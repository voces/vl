Repro:

    function f(): string {
      let v: string[] | null = ["a"]
      const q = () => { v = v }
      q()
      "x"
    }
    print(f())
    // vl check: rc 0.  vl run before the close: invalid module inside `q`: type mismatch: expected i32, found (ref null $type)

#### Mechanism

The closure's value is its tail write to the boxed cell, `v[0] = v[0]`. `cboxYieldTail` leaves
the tail alone, since the value's type is the cell's, so the write lowers as store-then-re-read
and the closure's result kind comes from `criClassify` on the right side: a synthetic `v[0]`
read with no recorded type. No classifier names a nullable `string[]` or `f64[]` element from
that node, so the result defaults to `i32` (disassembly: `(func $q … (result i32))`) while the
re-read pushes `(ref null $list)`. An `i32[] | null` cell classifies and runs. On master a later
`if v != null { v.length }` refused first, loudly; the D2393 close lifted that refusal and left
this one visible.

The un-annotated tail was one face of a wider gap: the closure value ABI had no token for a
nullable distinct-backing scalar list, so `(): string[] | null => …` refused loudly and
`() => { v }` refused as `bare null needs a struct-typed context`. The close records a
lambda's inferred `T[] | null` return (`IR_RUNG_NUL_LIST_RET`, as a named function's already
was) so `synthRetAnnots` pins it, gives the five nullable scalar lists result and parameter
tokens (`P E J G H`, `emit_rep.vl`, and their annotation twins in `annParamKind` and
`annRetKind`), and lets `exprNulScalarListKind` read a value call's result kind, so
`const got = q()` narrows with `got != null`. A function type's parameter lists are now forced
by name as its result's were (`forceCloResultListTypes`): `const g: (f64[]) => i32 = …` in a
program that builds no `f64[]` was check-clean invalid wasm on master, and the nullable
parameters would have been the same.
