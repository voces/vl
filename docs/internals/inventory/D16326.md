### D16326 — `x is 1 | "a"` over an `i32 | string` answers `false` for the numeric member

**closed · runs, prints `true` then `true` then `false` · was check-clean silently wrong, clause 1 · found closing D4082 · filed 2026-11-15 against master `5683d3b2c` · fixed 2026-11-15: a test of a literal set over two bases is minted as one test per base (`litSetSplitBuild`, check_annot_resolve.vl), `{ const $ls = x; $ls is 1 || $ls is "a" }`, each part a set the test's lowering answers whole; an open operand is bound as it reads, so a hole parameter's pins test the same way. Matrix `mixed-literal-set-is-over-scalar-union`: every one of 64 cells printed the wrong answer, all 64 run. Fixture: `tests/cases/narrowing/literal-set-over-two-bases-runs.vl`**

Repro:

    function h(x: i32 | string) { return x is 1 | "a" }
    print(h(1))
    print(h("a"))
    print(h(2))

Want:

    true
    true
    false

#### Mechanism

Disassembled: the test reads the box's tag once, compares it with the string arm's, and then
compares the payload with `"a"`. Nothing tests the `i32` arm against `1`, so a literal
set over two scalar bases is answered for its string members only: the string-membership
rungs read the tested type's members through `tyLitMemberTexts`, which answers string
members alone.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the string member (`x is 1 \| 3`) | runs | **yes** |
| the numeric member (`x is "a"`) | runs | **yes** |
| a third member (`x is 1 \| "a" \| "b"`, `x is 1 \| 3 \| "a"`) | wrong output, the same | no |
| the order (`x is "a" \| 1`) | wrong output, the same | no |
