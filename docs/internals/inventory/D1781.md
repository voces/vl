### D1781 — a monomorphized instance calling its own per-pin clone of a nested function resolved the callee through the FLAT name map, so it adopted the template's return kind

**closed 2026-09-06 — the witness prints `2` then `9000000000` · was check-clean invalid wasm,
`the emitted module failed to validate inside \`o$1\`: type mismatch: expected i32, found i64`
· clause 1 · filed and closed 2026-09-06 against master `be5a79fd2`, found by
[D1780](D1780.md)'s fix converting one invalid module into another · fixture
`tests/cases/generics/nested-capture-per-pin-clone.vl`**

Repro:

    function o(n) {
      function k(x: i32) { return n }
      return k(1)
    }
    print(o(2))
    print(o(9000000000))
    // vl check: rc 0.  vl run: prints 2 then 9000000000.

#### Mechanism

With [D1780](D1780.md)'s clone minted, the instance and the clone are two lifted functions
named `k`, and the clone is re-parented to the instance. Every return-kind classifier that
resolves a called name reached it through `fnIndexOfSid`, a flat name→index array that answers
the FIRST same-named slot — the template. `fnIndexOfInScopeSid`, which walks the frame chain,
already sat beside it. Probed with a post-monomorphize dump of `fRetKind`: for the f64 witness
the clone reads `[k s=2 ret=f64]` while the instance reads `[o$1 s=3 ret=i32]`.

Two symptoms share the root, and which one shows depends on whether the outer return carries a
synthesized annotation: with none, the instance's own SIGNATURE is stale (`$o$1 (result i32)`
over an f64 body); with one, the signature is right and the BODY carries a spurious widening
(`i64.extend_i32_s` over an already-i64 call). Six readers were converted, each graded by a
witness of its own kind: `exprIsF64`, `exprIsI64`, `exprIsF32`, `tailIsF64NoLocal` (the
`$fnsig` half, which decides the f64-template/i32-instance direction), `fnRetArraySid` and
`fnRetF64ArraySid`. The remaining flat sites were left alone: converting them blind is what
this row's own history warns against.
