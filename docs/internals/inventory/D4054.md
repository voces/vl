### D4054 — an existing wider record bound, returned or assigned at a narrower record type is refused as a codegen gap

**open · loud check reject · clause 2 (the refusal says `type-valid … but not yet supported by codegen`) · found re-grading `docs/spec/types.md` §T4.6 against D3992 (lane SPEC) · filed 2026-10-11 against master `98a4ed71b`**

Repro:

    type Animal = { b: string }
    type Cat = { b: string, a: i32 }
    const c: Cat = { b: "tom", a: 1 }
    const an: Animal = c
    print(an.b)
    // vl check: rc 1, "an object value of shape Cat flowing into Animal drops the field `a`:
    // type-valid (structural width subtyping) but not yet supported by codegen"

Want:

    tom

#### Mechanism

D3992 closed width subtyping into a declared record PARAMETER by making that parameter
generic, so an existing `Cat` is passed to `function nm(x: Animal)` as it is. A binding, a
return and an assignment have no such route, and D3992's own ablation table records the
binding as "loud check reject (kept)". These positions still accept the value only when
every dropped field's name sorts after every kept one. Here `a` sorts before `b`, so the
value is refused.

#### Ablation

| variant | outcome |
| --- | --- |
| this witness | refused with the codegen-gap sentence |
| fields `a` kept, `z` dropped (the dropped name sorts last) | runs, prints `tom` |
| `function nm(x: Animal): string { x.b }` with `nm(c)` | runs, prints `tom` (D3992) |
| `function f(c: Cat): Animal { c }`, the return position | refused, same sentence |
| `let an: Animal = { b: "x" }` then `an = c` | refused, same sentence |

#### Grading list

The three positions in the ablation table: binding, return and assignment. Also re-grade
D4050, a list of the wider record into a `readonly` list of the narrower one, which reaches
the same refusal through a container.

#### Ruling needed (2026-11-12)

Escalated to the owner; until it rules, the refusal stands as filed and the rows D4021–D4023
(an existing `A = {k, x, y}` or `B = {s, x, y}` handed to `Pos = {x, y}`, written through it)
are the same family.

What runs today, on master `c0d6666d`:

| spelling | outcome |
| --- | --- |
| `Animal = { a: string }`, `Cat = { a: string, b: i32 }`, `const an: Animal = c` | runs; `an.a = "x"` then `print(c.a)` prints `x` |
| `const c = { b: "tom", a: 1 }` (a fresh literal binding) | runs, built at `Animal` (D15093) |
| `const an: Animal = mk()`, `function mk(): Cat` | the same refusal |

Mechanism: fields are laid out sorted by name (D622), and a narrower record shares a wider one
only where its fields are a layout prefix of the wider record's, which makes it the wider
struct's wasm supertype. `{b}` is not a prefix of `{a, b}`. An existing record cannot be rebuilt
at the narrower type, since copy-on-delivery is rejected (DECISIONS "Record covariance", B), and
no subtype edge relates the two structs.

The options put to the owner:

* (a) Lay a record out so each declared narrower record it flows into is a prefix. It serves one
  chain; two narrower records that share no prefix (a diamond) conflict.
* (b) A view: the narrow handle carries the wide record and its field positions (or a getter and
  setter per field), a new rep for every read and write through a narrow type. DECISIONS
  "Record covariance" already names a view (C) as the eventual direction.
* A contract: rule that a narrower view must be a layout prefix, refuse the rest with the
  shared-record wording, and re-status these rows as design. This makes structural width
  subtyping of an existing record a declared-order rule.
