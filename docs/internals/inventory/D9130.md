Repro:

    function fst<T>(xs: T[]): T { return xs[0] }
    function lst<T>(xs: T[]): T { return xs[xs.length - 1] }
    function app<T>(g: (x: T[]) => T, v: T[]): T { return g(v) }
    let f = fst
    if [1].length > 0 { f = lst }
    const g = f
    print(app(g, [1, 2, 3]))

#### Mechanism

A `.map` callback follows the alias to the written `let`
(`monoCoerceAliasOfWrittenLet`, emit_mono.vl), but the hand to a generic's arrow parameter
coerced a written `let` only when the argument named it directly (`monoHandWrittenLet`).
The refusal came one step earlier than that. `monoCallGenFnToTyParamArrow` decides whether a
call binds `T` from its value arguments before it pins the arrow parameter, and it did so only
for a direct read of the `let` (`monoWrittenGenLetFrame`). For the alias `T` was still unbound
when `g` was pinned, so the substituted parameter type was empty and the argument had no type.

The close is `monoHandLetRead`. It follows a chain of un-annotated aliases to the written
`let`, one hop per alias and at most `MONO_ALIAS_CHAIN_MAX` hops. A non-`const` alias counts
only if nothing writes it after its initializer. Both sites use it: the pre-bind gate, and the
arrow branch of `monoPinTyParamComposite`, which then coerces the `let` the alias reaches. A
generic function named directly, or through an alias of a `const`, still takes the
open-function-value path it took before.
