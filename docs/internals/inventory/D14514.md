### D14514 — a function's list of literals delivered at two readonly lists that store a field differently is refused, though a readonly destination widens

**open · loud check reject · clause 2 · CAPABILITY: a `readonly` destination is where the design permits a list to widen · found closing [D14510](D14510.md), where master `4e04cd6de` accepted it and emitted a module that fails validation · filed 2026-10-27 against master `4e04cd6de`**

Repro:

    type Circle = { r: i32 | null }
    type Tag = { r: string | null }
    function sink(x: readonly Circle[]) { print(x.length) }
    function sink2(x: readonly Tag[]) { print(x[0].r == null) }
    function mkcall() {
      const cc = [{ r: null }]
      return cc
    }
    sink(mkcall())
    sink2(mkcall())
    print(1)

Want:

    1
    true
    1

#### Mechanism

D14510's close refuses, in the list-result arm of a call delivery, a function whose calls land
its one list on two storages (`recSitesLandApart`, `recRefuseAtOwnRow`, check_fit_rules.vl).
That rule is right for a mutable `Circle[]`, where a container never widens. A `readonly`
destination is covariant, so each call could be served as a read-only view of the list built at
its own row; the arm refuses it all the same, as `{r: null}[] is not readonly Circle[]`.

The same refusal names `readonly Circle[]` as the fix for the mutable spelling
(`objShapeReadonlyFixErr`), pointing the author at a type this row refuses.

#### Grading list

The binding spelling shares it: `const a = mkcall()`, `sink(a)`, `const b = mkcall()`,
`sink2(b)` refuses at both bindings with the same sentence (it was invalid wasm on master
`4e04cd6de` too). With one delivery only (`sink(a)` and no `sink2`) it runs and prints `1`.
