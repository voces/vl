### D6524 — an un-annotated hole lambda read out of a list has no function-value signature when the read is copied into a binding, or when the lambda was called at another type

**closed 2026-10-18 by lane L1 · runs, prints `3` · was a loud emit reject · clause 2 · a call through an un-annotated binding initialised by a list element read is keyed as the element read it copies (`cloElemCopyInitOf`, `cloIndexCalleeSigKey`) · pins: `tests/cases/closures/hole-lambda-list-element-copied-into-binding.vl`, `scripts/capability-probes/matrix/hole-lambda-list-element-copied.matrix.vl` · found closing [D6470](D6470.md) · filed 2026-10-18 against master `d9c8431e5`**

Repro:

    const h = (u) => u
    const fs = [h]
    const g = fs[0]
    print(g(3))
    // vl check: rc 0.  vl run: emitProgram: a function-value call has no interned signature — parameter 1 of type `` has no representation in the function-value ABI

Want:

    3

#### Mechanism

The flow table already instanced `h` at `i32` through `g`, so the lambda was built; the call
site had no key. `cloCallSigKey` keys a callee `fs[0]` through the list's element resolvers, and
a callee `g` through the name ladder, which follows a copy of another name but not of an element
read, and the arena type of `g` still names the hole. A callee binding with no annotation whose
initializer is an index read now takes the key of that read. Inside a function body the name
ladder's call-result rung already answered, so only the module-scope spelling refused.
