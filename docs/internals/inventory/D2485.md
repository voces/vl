### D2485 — `.length` on a generic function's list-of-closures parameter has no lowering the emitter can classify

**loud emit reject · clause 2 · found in review of #3156 against master `0a0d24ac9`, filed 2026-09-25**

Repro:

    function f10<T>(x: T[]): i32 { x.length }
    print(f10([(z: i32) => z + 1]))
    // vl check: rc 0.  vl run:
    // emitProgram: '.length' on a receiver the emitter cannot classify as a list, string, map or set

#### Mechanism

Not ablated to a rung. `x`'s generic element type `T` monomorphizes to a closure type here, and
`.length`'s emit arm classifies its receiver by concrete kind (list/string/map/set) before
lowering — inside this generic instance a closure-element receiver is apparently not classified
as a list at all, so it falls through to the emitter's default refusal. The same call over a
concrete `((i32) => i32)[]` (no generic) and the same generic instantiated at `T = i32` both
run, so it is specifically a closure-typed generic instance the classifier misses. An explicit
type argument on the call fails identically to the inferred spelling, so — unlike D2484 —
explicit vs. inferred is not the ingredient here.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the generic (`function f10(x: ((i32) => i32)[]): i32 { x.length }`, no `<T>`) | runs, prints `1` | **yes** |
| `T` monomorphized to `i32` instead of a closure type | runs, prints `3` | **yes** |
| an explicit type argument on the call (`f10<(i32) => i32>(...)`) | same refusal | no |

#### Grading list

D2484's list-of-closures matrix, since both share a generic instantiated at a closure element
type; a fix to one should be checked against the other's witness too.
