### D2832 — a generic if-join of two DIFFERENT list types takes one arm's list rep for the join, so the other arm is delivered into the wrong list

**check-clean invalid wasm · clause 1 · the same on master `9f11c9c9f` · found by the #3215 round-2 review (`rv3215g/p3/a4.vl`, `b6.vl`, `c1.vl`) · filed 2026-09-27**

Repro:

    function no(): boolean { false }
    function f<T>(xs: T[], ys: string[]) { const r = if no() { ys } else { xs }; print(r.length) }
    f([1.5], ["a", "b"])
    // vl check: rc 0.  vl run: invalid module inside `f` — expected (ref $type), found (ref $type)

#### Mechanism

At the pin `T = f64`, the arms are `string[]` and `f64[]`. That join is two list types (#3211's
rule keeps `T[]` apart from a concrete list), so no single list rep holds it. `emitIfExpr`'s
blocktype asks `ifExprRefKind`, which reads the THEN arm alone, and lowers the other arm into
that rep. #3215 made the binding's own classification refuse a disagreeing join
(`ifArmsAgreeOnListRep`), which turned the spellings with the concrete list in the ELSE arm
loud (`rv3215g/p3/b4`, `c2`, `c3`). The blocktype, the flipped arm order and the inline
`(if … ).length` still lower one arm's rep. The build item is to join two lists as their
union box, as #3211 does for a two-list return set, or to refuse.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `f([1.5], …)` → `f(["q"], …)` (the arms agree) | runs, prints `1` | **yes** |
| the arms swapped (`if no() { xs } else { ys }`) | loud emit reject | **yes** (the then arm decides) |
| `const r = …; r.length` → `(if … ).length` | still invalid | no |
| `if no() { [1] } else { [t] }` at `T = string` | still invalid | no |
