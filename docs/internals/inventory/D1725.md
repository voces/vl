### D1725 — a LIST LITERAL over a hole parameter takes its element rep from nothing, so an atom prints its interned id and a string refuses for want of a collected list type

**check-clean silently wrong · `vl check` rc 0, `vl run` prints `0` where `green` is expected · clause 1 · filed 2026-09-06 against master `5530f6132` · residue of [D1545](D1545.md), and the row that records that close's price · 0 corpus cells**

Repro:

    type K = "red" | "green"
    const src: K[] = ["green", "red"]
    function take(a) {
      const xs = [a]
      print(xs[0])
    }
    take(src[0])
    // PRINTS 0
    // want: green

Annotate the parameter `a: K` and the same program prints `green`, at both seeds.

#### Mechanism

Predicted, not probed. `const xs = [a]` has to name the list's ELEMENT to collect a list type
for it, and the only source is the parameter — which, being a hole, carries no annotation the
literal collector reads. Two reps fall through it in opposite directions: an atom-repped `a`
builds the i32 list, so `xs[0]` is the raw id and `print` is merely wrong; a string-repped `a`
reaches `emitProgram: string array literal but string list type not collected`, because no
string list was ever collected for the module.

**The string face is pre-existing and is not about literal unions at all** — `function take(a)
{ const xs = [a] }` called with a bare `"green"` refuses identically on master. That is what
makes this one row rather than two: the list-literal collector asks the hole parameter for an
element rep and gets nothing, and each rep then fails in its own way.

**This row is [D1545](D1545.md)'s price.** That close gives an inline litunion hole parameter the
`string` rep its spelling always softened to, so the inline face moves out of the atom half
(`runs 0`) and into the string half (the standing refusal above) — a clause-1 wrong value
becoming the loud floor its own rep already had. The alias face is unmoved and is this row's
witness.
