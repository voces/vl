### D3444 — a record a function with no declared result builds is refused into a record that stores its integer as `f64`, where the same call runs into `i64` or `f64 | null`

**loud check reject · clause 2 · open · the same on master `afb0ecc08` · found by the #3322 review (`rv3322-6397`) · the outcome depends on a reading of the record-covariance ruling, recorded below · filed 2026-09-30 against master `afb0ecc08`**

Repro:

    type W = { f: f64 }
    function mk() { { f: 4 } }
    const w: W = mk()
    print(w.f / 8)
    // vl check: "{f: i32} is not W: they store field `f` differently (`i32` into `f64`), and a
    // record is shared, not copied, so only a fresh record widens. ..."

#### Mechanism

The record-covariance ruling ("A, with C eventually", DECISIONS.md "Record covariance: only a
fresh value widens") lets a record widen into one that stores a field differently only when it
is fresh. DECISIONS.md records one reading past the ruling's words: a call of a function with
no declared result that returns only fresh records is fresh, because the distilled corpus
depends on it (598 behavioural classes). Under that reading `mk()` is fresh, and at `i64` and
`f64 | null` the call is accepted and runs with the right value. At `f64` and `f32` it is
refused, for a reason that is not the ruling's: `recFloatBuiltElsewhere` (`compiler/typecheck.vl`)
refuses a record a function built with an integer where the destination stores a bare float,
because the emitter has no conversion for it. That refusal replaced invalid wasm, and it reuses
the existing-record wording ("only a fresh record widens") for a value the same rule calls
fresh. At `f32` the refusal is the plain "cannot assign {f: i32} to 'w' of type W". The
annotated twin, `function mk(): { f: i32 }`, refuses all three widths, and that is the ruling
applied as written: a declared result is an existing record, and a function's result is never
adopted.

**Which outcome the ruling wants.** It depends on the recorded reading. If the reading stands,
`mk()` is fresh at every width. Then `f64` and `f32` should run like `i64` does, and this row is
a clause-2 capability gap. The fix is a build of the call's literal at the destination's storage,
or a converting copy at the delivery; since nothing else holds a fresh value, the copy cannot be
observed. If the owner rejects the reading, the call is an existing record at every width, and
`i64` and `f64 | null` should be refused as the twin is. That would also refuse the 598 corpus
classes the reading was kept for. Recommendation: keep the reading, and close this row by
building at the destination. Either way, the width of the field must not decide whether the
call is fresh. The row carries no `Want:` block until the reading is confirmed; under the
reading, the witness prints `0.5`.

#### Grading list

- All three widths (`f64`, `i64`, `f64 | null`) plus `f32`, in both the un-annotated and the
  declared-result spelling. After a close they must agree with each other the way the ruling
  says.
- The `if` and `match` join faces, which are emit refusals today.
- D3351, the join face of a fresh function result when a record of its own fields is
  declared.
