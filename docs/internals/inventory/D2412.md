### D2412 — a value-position write to a wider name that cannot move ahead of its statement still re-reads the name at its storage rep

**check-clean invalid wasm · clause 1 · pre-existing on master `a277bf7b0` · filed 2026-09-25
against `a277bf7b0`, the residue of [D2398](D2398.md)'s close**

Repro:

    let a: f64 = 1.5
    function k(): i32 { 3 }
    function h(p: i32, q: i32) { p + q }
    print(h(k(), a = 5))
    // vl check: rc 0.  vl run: invalid module, type mismatch: expected i32, found f64

#### Mechanism

[D2398](D2398.md)'s close moves a value-position write `a = e` ahead of its statement as
`const v = e; a = v` and reads `v` (`assignValueSpill`, `emit_rewrite.vl`). It moves only a
write every operand before which is a literal or a name the write leaves alone, since moving
it past anything else would reorder an evaluation. A write after a call or after a callee a binding
holds, among named arguments (which run in parameter order, D2343), under the right of `&&`,
`||` or `??`, or in a `while` condition (re-evaluated every iteration) stays where it is and lowers as store-then-re-read, which pushes the name's storage rep (`f64`) into a
position typed at the value's (`i32`). The fix is to spill the operands before it too, in
order, and for a `while` condition to move the write into the loop head.

#### Ablation

| ingredient removed | outcome on `a277bf7b0` plus [D2398](D2398.md)'s close | needed? |
| --- | --- | --- |
| the call before it (`h(3, a = 5)`) | prints `8` | **yes** |
| the widening (`let a: i32`) | runs | **yes** |
| a `while` condition for the call (`while (a = next()) > 0`) | still invalid wasm | no: a second position |
| the right of `&&` for the call (`b && (a = 5) == 5`) | still invalid wasm | no: a third position |

#### Grading list

The three spellings above, each with `let a: i64`, `let a: i32[] | null` from an `i32[]`, and
`let a: S | null` from an `S`; and [D2398](D2398.md)'s six position templates, which must
keep running.
