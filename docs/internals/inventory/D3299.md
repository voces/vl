### D3299 — a write of an un-annotated parameter to a declared record's nullable field does not narrow the field, so reading through it is refused

**loud check reject · clause 2 · pre-existing, the same on master `e70102886` · found by the NF2 lane's write grid (`pw/wr_V_annB`) · filed 2026-09-29 against master `e70102886`**

Repro:

    type O = { n: i32 }
    type R = { v: O | null }
    function put(b: R, a) {
      b.v = a
      print(b.v.n)
    }
    const r: R = { v: null }
    put(r, { n: 5 })
    // vl check: member access '.n' on non-object O | null

Want:

    5

#### Mechanism

A write narrows a declared record's field to the written value's type, and an inference hole is
neither non-null nor assignable-checked in the body, so the write to `b.v` leaves the field at
`O | null`. The same write to a HOLE receiver's field narrows to the hole (D3287's
`holeFieldWriteTy`), and the pin then re-asks the read against what `a` was pinned to; the
declared-receiver arm has no such rung. The fix is to narrow to the hole there as well, which is
sound only because reads off a parameter hole are re-asked at the pin.

#### Ablation

| ingredient changed | outcome on master | needed? |
| --- | --- | --- |
| `a: O` annotated | prints `5` | **yes** (a hole value) |
| `function put<X>(b: R, a: X)` | prints `5` | **yes** (an inference hole, not a type parameter) |
| `function put(b, a)`, both holes | prints `5` | **yes** (a declared receiver) |
| `b.v = { n: 5 }` instead of `a` | prints `5` | **yes** |
