### D4842 — a hole lambda called at one type and copied through written `let`s into a capture cell called at another is refused, because one binding holds one signature

**closed 2026-10-15 · runs today and must keep running · was loud emit reject · clause 2 · closed by L1 step 6 (`monoBindingsAtPin` gives each reassigned binding the flow table's pin; the cell store delivers at the cell's `e` pin) · in the multi-pin family of `fn-value-flow-design.md` §(g): `c` is pinned at `string` by its own call and at `i32` through `d3` · found by lane SC's step-5 candidate that delivers a capture cell's store at the cell's pin (it runs this witness and refuses `binding-copied-through-uncalled-chain`) · filed 2026-10-15 against `de595e3a5` (#3814's head)**

Repro:

    function chain(x: string, n: i32) {
      const c = (y) => y + y
      const g = (y) => y
      print(c(x))
      let d2 = c
      d2 = g
      let d5 = c
      d5 = d2
      let d3 = g
      function w8(): i32 { d3 = d5; 0 }
      w8()
      print(d3(n))
    }
    chain("a", 4)
    // vl check: rc 0.  vl run: rc 0, prints aa 4
    // (was: the reassigned function binding `d3` holds functions called at more than one argument type)

Want:

    aa
    4

#### Mechanism

`monoBindingSigConflict` gives each reassigned binding one closure signature, met over the
values written to it. Flow-insensitively `d3` can hold `c` (through `d5`'s initializer), so
`c` is wanted at `string` by its own call and at `i32` by `d3(n)`, and the meet is empty.
Delivering the cell store `d3 = d5` at the cell's `e` pin (`monoDeliverAtPin`) instead of
coercing it makes a per-signature instance of the hole lambda and the witness runs, but the
same delivery refuses `tests/cases/closures/binding-copied-through-uncalled-chain.vl`, which
the binding model runs today. Retiring the binding model is step 6; whether a value pinned at
two signatures gets two instances is the §(g) decision.
