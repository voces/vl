### D14485 — a negated number literal in a returned object literal is refused at a float field the bare literal is built at

**closed 2026-10-27 · runs, prints `-3.5` · was loud check reject, clause 2, `cannot assign {v: i32} to 'wd' of type F` · filed 2026-10-27 against master `fe512788b` · fixed: `recLitFits` (check_fit_rules.vl) asks `cexLitPeel` whether a field is a number literal, so `-7` is one as `7` and `(7)` are; `exprIsNumLit` is deleted and `isFloatLitExpr`, `intLitLexemeOf` and `crRhsNonNull` read `cexLitPeel` · pins: `tests/cases/soundness/record-fresh-call-negative-literal-at-float-destination.vl`**

Repro:

    type F = { v: f32 }
    function d() { return { v: -7 } }
    const wd: F = d()
    print(wd.v / 2)

Want:

    -3.5

#### Mechanism

D3444 builds a single-call function whose returns are all object literals at the record its
call is delivered to. When the delivery's own type refuses (`{v: i32}` into `{v: f32}`),
`recLitFits` decides: a field is accepted when it is a number literal and the field stores a
number. It tested `nodeAt(cwPeel(fx)) is NumLit`, which peels parentheses only, so `-7` was an
expression rather than a literal there. The same refusal held for a nested record field and at
an argument position (`take(d())`). The direct spelling `const wd: F = { v: -7 }` ran.

Five functions answered "is this a number literal under parentheses and negations":
`cexLitPeel`, `exprIsNumLit`, `isFloatLitExpr`, `intLitLexemeOf` and `crRhsNonNull`'s
`crNegLit` (one negation only). `recLitFits` was a sixth with parentheses only. All now read
`cexLitPeel`.
