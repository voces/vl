### D5712 — an f64 destination refuses `??` over a nullable i32 whose default literal only fits i64

**closed 2026-10-17 by lane L3 · runs, prints `2` · was loud check reject · clause 2 · an `i64` join is admitted into a bare `f64` when every leaf is an integer literal up to 2^53 or an `i32`, `f32` or `f64` value (`f64ExactJoinLeaves`, `check_num_adopt.vl`), so the `if` join, a `match` join, a return, an assignment, a list element and an argument run too, while a join with an `i64` value leaf is still refused · pins: `tests/cases/numerics/f64-wide-literal-join.vl` · filed 2026-10-17 against master `bb4448de7`**

Repro:

    function pick(n: i32): i32 | null { if n > 1 { return n } return null }
    const v: f64 = pick(2) ?? 9000000001
    print(v)
    // vl check: i64 doesn't fit in f64 — the conversion is lossy and must be made explicit with `as` (write `x as f64`)

Want:

    2

#### Mechanism

The `??` joins `i32` with the literal `9000000001` to `i64` before the destination is read, and
the delivery then judges `i64 → f64`, which is lossy for an i64 in general. Under the numeric
join ruling (DECISIONS.md, 2026-09-30, extended to `??` 2026-10-03) a literal operand adapts
and a delivery converts when it is exact for every member: here the members are an `i32` and
one literal, both exact in f64, and `const v: f64 = 9000000001` alone runs. Un-annotated, the
element is `i64` and runs (`tests/cases/unions/coalesce-out-of-range-default-element.vl`).

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the default `5` instead | runs | **yes** |
| the binding un-annotated | runs (i64) | **yes** |
| the destination `i64` | runs | **yes** |
| `const xs: f64[] = [pick(2) ?? 9000000001]` | still refused (`cannot assign i64[] to 'xs' of type f64[]`) | no |
| `if c() { pick(2) } else { 9000000001 }` into `f64` | still refused | no |

#### Grading list

The list element, the `if` join and the binding above, each into `f64`.
