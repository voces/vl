### D14942 — a hole function handed through a hole parameter to a named function that calls its own parameter at two types is refused at emit

**closed 2026-11-02 · runs, prints `1` then `s` · was loud emit reject, `cannot take the generic function \`id\` as a value`, with the split plan on and off · clause 2 · the tag decision now lets a call through a hole parameter hand a set's id when the sets the calls through that parameter go through hold only named functions, each taking the set at that position (`ftParamSetsTake`) · pins: `tests/cases/functions/named-fn-through-hole-param-calling-generic-at-two-types.vl` · filed 2026-11-02 against master `2ce0b824`**

Repro:

    function id(a) { return a }
    function lap(g) {
      print(g(1))
      print(g("s"))
    }
    function use(k) { k(id) }
    use(lap)
    // vl check: rc 0.  vl run: emitProgram: cannot take the generic function `id` as a value

Want:

    1
    s

#### Mechanism

`lap` is a named function, so its one-member set is tagged and `k(id)` dispatches to `lap`
directly; `lap`'s calls through `g` then need `id`'s set tagged too. The tag decision refused it
at `ftCtxOk`: the argument `id` of `k(id)` was accepted only when the callee was a binding,
element or field holding the set (`ftLateArgOfSet`), never a parameter. A parameter's calls go
through the sets `mintParamSetsOf` records, and when each member is a named function taking
`id`'s set at that position the id is what every member reads, so `id`'s set is tagged and each member calls
its instances directly. The lambda spelling is bundle-lam's and is served by the bundle-typed
closure parameter (closure-at-delivery item (d), slice 1).
