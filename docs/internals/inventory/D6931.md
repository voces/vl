### D6931 — a hole function called by name and also handed to a parameter that only aliases it is refused at emit

**closed 2026-10-19 by lane L1 · runs, prints `2` then `5` · was loud emit reject · clause 2 · CAPABILITY: the same value, inert and called by name, already ran as a module binding and as a list read for its length; only the parameter and the returned-unread positions refused. The parameter is pinned at `() => void` and takes the closure of the instance the calls build, which nothing calls there; a closure's representation is the same for every signature, so the pin is never observed. Compared through the alias, it still refuses (D4551) · pins: `tests/cases/closures/hole-fn-called-by-name-and-aliased-by-param.vl`, `tests/cases/closures/error-called-hole-fn-param-alias-compared.vl` · found closing [D6912](D6912.md) · present on master `43f22053c` and at #4153's head · filed 2026-10-19 against master `2dcd6d29f`**

Repro:

    function inc(x) { x + 1 }
    function run(f) {
      const k = f
      print(2)
    }
    run(inc)
    print(inc(4))
    // vl check: rc 0.  vl run: emitProgram: cannot take the generic function `inc` as a value — a function value carries ONE signature, and parameter `x` is un-annotated (it would default to i32). Call sites pin `inc` at (i32)

Want:

    2
    5

#### Mechanism

From the ablation only. The inert-parameter stub served only a function no call instances, since
a called function has a body the stub would replace. Once `inc(4)` instances it, the argument
took the ordinary value pin, which refuses a hole function its call sites pin at one type
rather than adopting that type.

Graded on master `9379b4491` before the fix. Every row calls `inc` by name unless it says otherwise.
