### D4843 — a hole lambda called through a capture cell, then written back into that cell directly, is refused as not settled

**closed 2026-10-15 · runs today and must keep running · was loud emit reject · clause 2 · closed by L1 step 7 (a cell's write the store's pin already renamed to its instance is taken at that instance's signature) · found by the mutate-then-read probes of lane SC's L1 step 6 (refused before and after it) · filed 2026-10-15 against `bf9a09dd4` (#3815's head)**

Repro:

    function f(n: i32) {
      const c = (y) => y + 1
      const g = (y) => y * 2
      let d = c
      print(d(n))
      function w(): i32 { d = g; 0 }
      w()
      d = c
      print(d(n))
    }
    f(5)
    // vl check: rc 0.  vl run: rc 0, prints 6 6
    // (was: the captured binding `d` is written with a function value whose type at this binding is not settled)

Want:

    6
    6

#### Mechanism

The cell store `d = c` is delivered at the cell's `e` pin, which pins the hole lambda `c` and
renames the write's value to the lambda's lifted name. The second call `d(n)` then coerces the
cell again (`monoCoerceWrittenCell`), re-taking every write. The renamed value no longer
resolves as a hole lambda by binding (`monoLamValueFe` follows names in scope), so
`monoCellValueTake` fell through to the node's still-open type and refused it. The take now
reads a lambda's lifted or instance name (`monoLamInstanceNamed`) and compares that slot's
signature with the cell's type: equal is taken, different is the one-signature refusal.

The same re-take refused `tests/cases/closures/binding-copied-through-uncalled-chain.vl` when a
store of a value read through another cell (`d3 = d5`) was delivered at the cell's pin, so the
same change lands that delivery (§(f) step 7, case (a)).
