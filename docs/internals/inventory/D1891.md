### D1891 — an operator overload is decided by the LEFT operand alone, so a hole parameter on the left with a resolved type on the right never reaches the operator table

**loud check reject · 4 of 99 `operator_vs_call` pairs, every one at the `argument` position · filed 2026-09-07 against master `f3cac5fe5`**

Repro:

    type Ord = new { x: i32 }
    function "<"(self: Ord, other: Ord): boolean { return self.x < other.x }
    const opO: Ord = { x: 4 }
    function mkval(): Ord {
      const r: Ord = { x: 3 }
      return r
    }
    function take(p) {
      if p < opO { print(1) } else { print(0) }
    }
    take(mkval())
    // vl check: 9:6: comparison expects numeric operands, got _ and Ord

#### Mechanism

An index or arithmetic operator is a free function dispatched on its `self` parameter's type
(DECISIONS.md B14), and the resolution reads the LEFT operand to pick the arm. When the left
operand is an un-annotated parameter its type is still the hole `_`, so no arm matches and
the ladder falls through to the numeric arm, which reports. The hole is never a candidate for
the operator's `self`, so the call site's binding — which would have given it `Ord` — is
never consulted.

The `_` in the message is the tell: the refusal is not "no such operator for `Ord`", it is
"the left operand has no type yet". Both halves of the message are printed by the arm that
fired, not by the operator table.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the parameter is un-annotated (`take(p: Ord)`) | runs, prints `1` | **yes** |
| the operator (`ltOrd(p, opO)`, same body) | runs, prints `1` | **yes** |
| the operator, via UFCS (`p.ltOrd(opO)`) | runs | **yes** |
| the hole is on the LEFT (`opO < p`) | runs, prints `0` | **yes** |
| the right operand has a type (`take(p, q)` with both holes) | runs, prints `1` | **yes** |
| the `new` brand on `Ord` | still refuses | no |
| the operator is `<` (also `>` `<=` `>=` `+` `-` `*` `/` `%`) | all nine refuse | no |
| the parameter is generic (`take<T>(p: T)`) | refuses, `got T and Ord` | no |

#### Grading list

`opO < p` and the two-hole `p < q` run today and must keep running — a fix that resolves the
left hole must not lose the spellings that already work. The generic-parameter twin
(`take<T>(p: T)`, `got T and Ord`) is the same mechanism at a type variable and should move
with it. [D1892](D1892.md) is the bracket operators' version of the same question and refuses
in the EMITTER instead, so this row's close does not cover it — re-grade `p[4]` before
claiming it does. [D1893](D1893.md) is the case where the hole DOES resolve and the operator
is still not found.
