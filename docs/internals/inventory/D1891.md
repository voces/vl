### D1891 — an operator overload is decided by the LEFT operand alone, so a hole parameter on the left with a resolved type on the right never reaches the operator table

**closed 2026-09-08 — the witness prints `1` · was a loud check reject, 4 of 99 `operator_vs_call` pairs, every one at the `argument` position · clause 2 · filed 2026-09-07 against master `f3cac5fe5` · 81 of 81 cells (9 operators x 9 positions) move `check` to `runs`, 0 lost · [D1893](D1893.md) closes with it · fixtures `tests/cases/operators/overload-through-hole-parameter.vl` and `…-two-hole-and-asymmetric.vl`**

Repro:

    type Ord = new { x: i32 }
    function "<"(self: Ord, other: Ord): boolean { return self.x < other.x }
    const opO: Ord = { x: 4 }
    function mkval(): Ord {
      const r: Ord = { x: 3 }
      return r
    }
    function take(p) {
      if p < opO { print(1) } else { print(0) }
    }
    take(mkval())
    // vl check: 9:6: comparison expects numeric operands, got _ and Ord

#### Mechanism

An index or arithmetic operator is a free function dispatched on its `self` parameter's type
(DECISIONS.md B14), and the resolution reads the LEFT operand to pick the arm. When the left
operand is an un-annotated parameter its type is still the hole `_`, so no arm matches and
the ladder falls through to the numeric arm, which reports. The hole is never a candidate for
the operator's `self`, so the call site's binding — which would have given it `Ord` — is
never consulted.

The `_` in the message is the tell: the refusal is not "no such operator for `Ord`", it is
"the left operand has no type yet". Both halves of the message are printed by the arm that
fired, not by the operator table.

Measured at the decision point, printing what the resolver receives:

    a_hole_left    op='<' lt=_/HOLE     rt=Ord/TyObj  lookupAsked=no    REFUSES
    b_hole_right   op='<' lt=Ord/TyObj  rt=Ord/TyObj  lookupAsked=yes   runs
    c_hole_both    op='<' lt=_/HOLE     rt=_/HOLE     lookupAsked=no    runs (deferred)
    d_annotated    op='<' lt=Ord/TyObj  rt=Ord/TyObj  lookupAsked=yes   runs

`b`'s right operand is already `Ord` and not a hole, which names the asymmetry exactly: the
lookup's own trailing `assignableExpr(rightIx, rt, expected)` is what seeds a hole on the
right, and it only runs once the LEFT is an object. Closed by recording the mirror flow —
`noteHoleFlow(lt, opSelfParamTy(op))` — from the same declaration, with `opSelfParamTy` split
out of `opSelfFnTy` so the two sides read one `self` type. It flows to `self` and not to the
other operand, which is why an asymmetric `"*"(self: Sca, k: i32)` keeps its own answer, and
`noteHoleFlow` is inert outside the parameter solve, so no diagnostic elsewhere can move.
