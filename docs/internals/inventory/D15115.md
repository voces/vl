### D15115 — two records of one shape holding one un-annotated function, called at `boolean` then `i32`, print the second as a boolean

**open · check-clean silently wrong, prints `true` then `true` · clause 1 · pre-existing on master `eb6c23665` · `print` chose its sink from `exprIsBool`, whose field-call arm asks `fieldCloCallIsBool`; that asks `fieldClosureFeOfRecv` which closure the field holds and reads the slot's `fRetBool`, and the slot it answers is `g`'s `boolean` instance, though the checker typed `b.f(3)` `i32`; the same shape as D15114, so the fix goes the same way: a field call whose checked type has no hole takes that type · found grading D15113 · filed 2026-11-04**

Repro:

    function g(a) { return a }
    const a = { f: g, n: 1 }
    const b = { f: g, n: 1 }
    print(a.f(true))
    print(b.f(3))

Want:

    true
    3

#### Ablation

| spelling | outcome |
| --- | --- |
| the witness (bound) | prints `true`, `true` |
| the same two literals unbound | prints `true`, `true` |
| `i32` first, then `boolean` | runs |
| the two records of different rows (`n: 1` and `n: "x"`) | runs |
| either call alone | runs |

#### Mechanism

The checker's facts are right: `b.f(3)` is typed `i32`. `exprIsBool`'s `Call` arm reaches the
field-closure branch (`drwFieldClosure`), and `fieldCloCallIsBool` resolves `b.f` through
`fieldClosureFeOfRecv` to slot 0, `g`'s instance at `boolean` (`fRetBool` 1), so `print` uses the
boolean sink. The reader decides from the resolver's slot, not from the call's checked type or the
elaboration's stamp.
