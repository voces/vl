#### Mechanism

The checker types the `??` as `T[]`, so the call is `string[]` at `T := string`, and the
instance declares a `string[]` result while the fallback `[1]` is built as an `i32` list. The
same function with `xs: string[] | null` spelled out types the `??` as `string[] | i32[]` and
runs, as does the return-set join of `[t]` beside `[1]` (D2783): the `??` result type does not
go through the join that keeps a type parameter's list apart from a concrete one: the `??` arm
answers the left's non-null type whenever the default is assignable to it, and `T[]` accepts
`i32[]` through `T`.

The emitter now refuses a `??` typed as the operand's one list where the operand and the default
are stored as different lists at the instance, which is the loud refusal this program had before
`2bbc5c412`. A list literal default of numbers that fit (`[1]` at an `f64` or `f32` pin, `[1]` at
`i64`) is built at the operand's element and keeps running; a string, record, fractional-into-
integer or `i64`-into-`i32` literal, and any non-literal default (a variable, a second type
parameter's list), has no converting copy and is refused. The operand's storage is read from its
classifier, never from a wrapper type index, since an unused list type's index is a placeholder
that can equal a used one's. Typing the `??` apart
(`T[] | i32[]`) is the clause-1 close, and #3214 tried it for five review rounds: it needs every
body read of such a join to be re-asked at the pin, which is [D2843](D2843.md).
