### D2062 — the getter walk refuses string `==` but not `is "literal"`, which lowers to the same looping `__str_eq__`

**closed · the filed repro RUNS and prints `true`, now admitted at a stated cost of 1 step (the literal's length) · `self.name == "z"` is admitted the same way, so both spellings agree · the owner's string-literal ruling · filed 2026-09-22 against master `31ea77721`, found by the compiler-engineer lens of the getters/effects persona review (probes `h2`, `h8`)**

Repro:

    type N = new { name: string }
    get isZ(self: N): boolean { self.name is "z" }
    const n: N = { name: "z" }
    print(n.isZ)
    // vl check: rc 0; prints true.  The body of `N.isZ` is one `call $__str_eq__`,
    // which answers unequal lengths before its loops, so the compare walks at most one
    // character.  At filing `self.name == "z"` was refused while this was admitted at 0

#### Mechanism

The getter body walk (`gwWalk` in `compiler/typecheck.vl`) is an allow-list by node kind plus a
hand-written deny list by operand type for `==`. Its `IsExpr` arm walks only the tested object
and never asks what the literal test lowers to, so a string literal pattern reaches `__str_eq__`
unseen. Verified for the synthesis by `wasm-dis` on a `--names` build: `$N.isZ@2` calls
`$__str_eq__`. The wider cause is that the operator cost list is written beside the emitter's
lowering, not derived from it.

#### Grading list

`self.name is "z" || self.name is "y"` (two calls); a literal-union field tested with `is` (must
stay accepted, since that compare is an `i32`); the `==` control above, which must stay refused.

#### Close

The owner ruled (2026-09-23) that a compare with a string LITERAL is bounded, and costs the
literal's length in steps (D2061's budget), provided the lowering pre-checks length and never
walks past the shorter operand. `emitStrEqFnCode` (`compiler/emit_sections.vl`) does: after the
`ref.eq` fast path it compares `a.len` with `b.len` and returns 0 when they differ, and only then
walks `n = a.len` elements. With equal lengths that is the literal's length.

The emitter did need one change, found by the new body-shape test
(`tests/vl_getter_body_shape_test.ts`): `s is "ab" | "z"` built each literal that appeared
nowhere else in the program as a FRESH string (`array.new_fixed` + `struct.new`) at every test,
because `collectStrPool` pooled only `StrLit` nodes and the `is` lowering mints its literal at
emit time. That is an allocation inside a getter, which the contract forbids, and a per-test
allocation everywhere else. `collectStrPool` now also pools the literals an `is` tests a `string`
or `string | null` against, appended after the `StrLit` pass so a program whose literals were
already pooled keeps its bytes. Of the 57 corpus programs spelling `is "…"`, 44 are
byte-identical, 9 do not build on either seed, 3 shrank (61, 100 and 11 bytes; same output), and
the fourth is this row's own new fixture.

Admitted, each costing its literal's length: `s == "lit"`, `"lit" != s`, a value whose TYPE is one
string literal (`const Z: "z" = "z"`), and `s is "a" | "b"`, whose cost is the SUM of the
literals' lengths — the lowering tests each literal in turn with its own `__str_eq__` call, and
more than one can pass the length check. `x is "z"` over `string | null` calls `__str_eq__` too
and is charged the same; over a literal union it is an `i32.eq` on the tag (disassembled) and
costs 0. Still refused: two runtime strings (`self.name == self.other`), the ordering compares
(`<` against a literal was not part of the ruling), and a literal reached through an UN-annotated
`const`, which widens to `string` — D2120. `startsWith`/`endsWith` are std functions, which a
getter cannot call at all yet, so the ruling's clause for them has nothing to admit today.
