### D14491 — what a function whose tail is an assignment returns is decided by two syntactic walks, not read off the checker's return type

**open 2026-10-27 · runs today and must keep running · a second producer, not a wrong answer: `fnAssignRetTarget` (emit_classify.vl) walks a straight tail and `ifTailAssignTarget` → `armAssignTarget` (emit_local_scope.vl) walks an `if`/`match` tail, and each decides whether the function returns the assigned cell. Both now carry the same number-literal decline (D14490), while the checker has already typed the function's return · filed 2026-10-27 against master `1810bc326`**

Repro:

    let g: f64 = 0.5
    function arm(c: boolean) { if c { g = 5 } else { g = 7 } }
    function one() { const v = 9; g = v }
    print(arm(true) / 2)
    print(one() / 2)

Want:

    2
    4

#### Mechanism

The checker types an assignment at its right side, so both functions return `i32`. The emitter
reuses the target cell as the return (store, then re-read and unwiden). Whether it may is
answered twice, once per tail shape, and #4964 added a rule (decline a literal right side) to
one walk only, which was D14490. The question is whether the return can be built from the
checker's return type at the one site that lowers the tail's value. Then a cell at another
width is re-read through the checker's type, and neither walk has to decide anything.
