#### Mechanism

Probed against the D7183 close. The split plans every function the call reaches at the union of
their keys (`fsPlanHoles` through `fsListGroupPars`), so `apply3`, which calls `g` at `i32` only,
keeps one parameter while `apply2` gets two, and the elements no longer share a function type. The
element read is then refused at the type-parameter floor. A close gives a function that never
reads a split slot that slot anyway, typed from its siblings, as `monoElemParamTys` already does
for a parameter its body never reads.

Re-probed 2026-10-20 (lane L1, closing [D7763](D7763.md)): the retype stops in `monoElemParamTys` at
`apply2`, whose `g` still has two pinned parameter lists (`fnFlowDeclPathAgreedPinTys` false).
The split has therefore not given `apply2` a slot per type at all; the close is in the split
plan (`fsPlanHoles` declining the list group), before the emitter.
