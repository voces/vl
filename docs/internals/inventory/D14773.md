### D14773 — a `null[]` write or result an instance builds at `T = null` carries no rep stamp of the cell it lands in

**runs today and must keep running · refutation pin for deleting `nullOwnAt`'s D4671 floor: with it gone the witness's module fails to validate inside `put` (`expected i32, found nullref`) · D14640's family, step 4 / mono per-instance work · filed 2026-11-01 against master `7aa71dbba`**

Repro:

    function put<T>(self: T[], v: T) { self[0] = v }
    function id<T>(x: T): T { return x }

#### Mechanism

A `null` landing in a `null[]` cell is stamped with the rep type of the `(boolean | null)[]`
list that cell rides (`stampNullUnitCell`, check_fit_rules.vl, D4771), so `nullOwnAt` builds
the sentinel 2 from the stamp. Inside an instance at `T = null` the write is a node mono mints in
the clone (`self[0] = v` rewritten, std's `insert`), which the checker never checks, and an
instance's returned value (`id<T>` at `T = null`, reached through `filled`) is delivered to
the return storage mono chose. Neither carries a stamp, so `nullOwnAt` still takes the
destination's `nulBool` seed there: the floor's last uses, beside D14640's.
