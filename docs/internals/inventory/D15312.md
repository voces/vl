### D15312 — a `??` default for a read built wider, placed in a list or record literal, is built at the literal's own row

**closed 2026-11-04 by lane destringify, runs, prints `4` · was check-clean invalid wasm, clause 1 · the store column built a `??` join at the read's record only where it initialises a binding; `storeLetsResolve` now also takes a binding's list or record literal, and `storeLitHeldAt` builds it at its own type with each slot that holds such a join (or a binding of one) at the held record, through nested literals · fixture `soundness/built-read-default-in-literal-runs.vl` · named set `d15312-join-in-literal` · a default held in a binding inside the literal is refused at check (D15313) · found grading D15240 · filed 2026-11-04 against master `ddb0573bc`**

Repro:

    type J = { f: i32 | null }
    function mk() { { f: 4 } }
    const m = Map()
    m.set("a", mk())
    const wm: {[string]: J} = Map()
    wm.set("a", mk())
    const xs = [m.get("a") ?? { f: 1 }]
    print(xs[0].f ?? 0)

Want:

    4

#### Mechanism

The store column builds a `??` join at the read's record where it initialises a binding
(`storeHeldAt`), but a list or record literal holding the join is typed at the default's own row
and its element is stored there. A literal default, a held one and a call behave the same. Through a
binding (`const b = m.get("a") ?? d; const xs = [b]`) it is an emit refusal instead.
