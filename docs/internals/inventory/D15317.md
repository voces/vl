### D15317 — a function built at a read's record by one `??` default's delivery and adopted there by another's is two decisions about one build

**closed 2026-11-04 by lane destringify · runs, `4` and `1` · each default alone ran · found closing D15311 · filed 2026-11-04 against master `5f65fde96`**

Repro:

    type J = { f: i32 | null }
    function mk() { { f: 4 } }
    const m = Map()
    m.set("a", mk())
    const wm: {[string]: J} = Map()
    wm.set("a", mk())
    function mk2() { { f: 1 } }
    function mk4() { mk2() }
    const dA = mk2()
    const bA = m.get("a") ?? dA
    const b = m.get("z") ?? mk4()
    print(bA.f ?? 0)
    print(b.f ?? 0)

Want:

    4
    1

#### Fix

Three readers each made a second decision about one build (D15317's PR):

* The record solve's `recQueuedLandingOf` read each `??` default's queued pair at the join's own
  type, while the store column delivers it at the read's record; with `mk2` called at two sites it
  judged them apart. It now reads the default where the store column lands it.
* The store column resolved bindings in check order, so `const d = mk4()` read its build before a
  later `?? d` delivered it; each `??` join is now held first.
* Emit's union-arm pin (D4555) pinned `mk4` at `{f: i32}` once the re-check typed `read ?? dA` as
  `{f: i32} | J`; its guard now reads a call or `??` leaf the store column stamped.

#### Mechanism (as filed)

Not yet ablated past the grid below. `mk2` is decided twice: the held one-level default `dA` is
adopted at the read's record J with `mk2`'s build (D15240), while the inline `?? mk4()` delivers
`mk4` at J and hands its build on to `mk2` (D8143). The two decisions about one function's build do not
meet, and the join's operands arrive at two rows. The same shape as
the assignment stamp's two producers that #6255 collapsed into one (D15282): whoever picks this up
should start there, with one decision about `mk2`'s build that both defaults read.
