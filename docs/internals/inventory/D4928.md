### D4928 — a list narrowed by `is K[]` is delivered as `K[]` and later written through its wider type

**closed · now a loud check reject · was check-clean silently wrong value (clause 1) · related to D4771 (`is` over a list tests every element) and D4926 (the narrowing outliving a write) · filed 2026-10-15 against master `23dcd80be`**

Repro:

    type K = 0 | 1
    const b: i32[] = [0, 1]
    let k: K[] = []
    if (b is K[]) { k = b }
    b[0] = 5
    const e: K = k[0]
    print(e)
    // vl check: 'b' is narrowed by `is` only for reading its elements; it is still declared
    // i32[] and a later write may widen it, so it cannot be delivered as K[]. Copy it with
    // 'b.map((x) => x)'

#### Mechanism

Inside the guard `b` reads as `K[]`, and the assignment delivered that same list object into a
binding whose declared type is `K[]`. The binding outlives the guard, so a store through `b`'s
declared `i32[]` after the `if` changed what `k` holds without any narrowing for D4926's
retirement to end. A narrowed list is only safe to read at the narrowed element type, never
to deliver at it.

#### Close

Owner ruling (c) on #3792, for string and numeric literal unions alike: inside `if (v is K[])`
the element reads of `v` narrow to `K`, and `v` itself is never delivered as `K[]`. A binding,
assignment, argument, return or record field (also nested in an object or list literal) whose
destination the declared type does not fit, but the element-narrowed type would, is a check
error that names the `map` copy. A closure capturing `v` reads its elements at the declared
type unless the closure is a callback the call keeps. String literal unions now narrow element
reads too (`s is S[]` reads `s[i]` as `S`), retired by writes exactly as D4926 retires numeric
ones. List `as` conversion is deferred (ROADMAP A-LISTAS).
