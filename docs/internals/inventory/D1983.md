### D1983 — an f32 plus a parenthesised f32-plus-literal-product is check-clean invalid wasm

**check-clean invalid wasm · clause 1 · PRE-EXISTING, found incidentally while writing SIMD S3's geometry fixture · filed 2026-09-22 against master `a8a104432`**

Repro:

    const ay: f32 = 2.0
    print(ay + (ay + 0.5 * 2.0))
    // vl check: rc 0.  vl run: the emitted module failed to validate — type mismatch:
    //   expected i32, found f64

#### Mechanism

Not localised. The checker types the whole expression `f64`: annotating the binding
`const r: f32 = ay + (ay + 0.5 * 2.0)` is refused with `f64 doesn't fit in f32`. So a
product of two float literals is a HARD f64 to the checker once it sits inside a
parenthesised f32 sum, while the emitter's f32/f64 classification of the same tree
disagrees and lowers one operand at the wrong width. The un-nested spelling agrees in
both halves and runs.

#### Ablation

| spelling | outcome |
| --- | --- |
| `ay + (ay + 0.5 * 2.0)` (witness) | invalid wasm |
| `const r = ay + (ay + 0.5 * 2.0)` | invalid wasm |
| `ay + 0.5 * 2.0` (no outer add) | runs, `3` |
| `ay + ay + 0.5 * 2.0` (no parens) | runs, `5` |
| `ay + (ay + 1.0)` (no product) | runs, `5` |
| `ay + (ay + h * 2.0)`, `h: f32` | runs, `5` |
| `ay: f64` | runs, `5` |

#### Grading list

The three rows that run must keep running, and the checker's answer for the annotated
`f32` binding must agree with whatever width the emitter picks.
