#### Mechanism

**The producer was never wrong.** `narrowVariantFor("__m[\"k\"]")` banks the TESTED ARM for an
index path exactly as it does for a bare name — measured, not read: an emit-time probe at the
`.size` site prints `exprMap=1 key=[__m["k"]] variant=[{[string]:i32}]
mapOfPlace=[{[string]:i32}] atom=[] mrs=0 atomKind=-1`. The whole-union reading this row
carried before the close was the OUTER `!= null` narrowing, which does bank
`{[string]:i32}|i32`, and the inner `is` push shadows it.

The hole is the CONSUMER. `emitNarrowedMapReadTail` asked `mapReadNarrowedAtomKind` and, for
`-1`, left whatever `emitMapGetUnionBox` had pushed — the box. A map is not a value atom, so
that question answers `-1` for it, while `exprMap` (through `narrowedMapOfPlace`) had already
called the read a map: the classifier and the lowering disagreed, and `.size`'s
`struct.get $mapStruct 5` read the box. `emitPlaceNarrowContainerUnbox` — the payload read plus
`ref.cast` that D1014 built for the member place and `emitIndex`'s ref-list rung already
took — is what the map read never called. The fixed module is +7 bytes at that site, one
`struct.get` and one `ref.cast`, and the sequence is the bound control's own.

`mapReadNarrowedContainer` is the new gate, so the four classifiers that must stop calling the
read a box (`exprUnion`, `unionNameOfExpr`, `letNulMapReadUnionBox`) and the lowering that
opens it read ONE predicate. `letNulMapReadUnionBox` is the load-bearing one: without it the
binding inside the arm keeps a union-box cell while the init now delivers a map.
