### D1984 — a local `dot` that cannot take the receiver still blocks type-bound UFCS, so `v.dot(w)` on an F32x4 is refused in any module with its own `dot`

**loud check reject · clause 2 · filed 2026-09-22 against master `4d64edc73`, found by the std-api review of SIMD S3**

Repro:

    import { f32x4 } from "std:simd"
    type V2 = { x: f64, y: f64 }
    function dot(self: V2, o: V2): f64 { return self.x * o.x + self.y * o.y }
    const a = f32x4(1.0, 2.0, 3.0, 0.0)
    print(a.dot(a))
    print(dot({ x: 1.0, y: 2.0 }, { x: 3.0, y: 4.0 }))
    // vl check: 'dot' is not imported — … add `dot` to the existing import { … } from "std:simd"

#### Mechanism

Type-bound resolution (#3005) is FALLBACK-ONLY: it asks the receiver type's home module only
when ordinary resolution finds no `dot` in the caller's scope. Here the scope has a `dot`,
it just cannot accept an `F32x4`, so the fallback never runs. The message then suggests
adding `dot` to the import, which collides with the local declaration (`Duplicate binding
"dot"`). `import { dot as dotF32x4 }` plus `a.dotF32x4(a)` works (prints `14`) and is what
`std:simd`'s header tells a caller today. The fix is for the fallback to run when the
in-scope candidate's `self` does not accept the receiver, and for the message to suggest an
aliased import.

#### Grading list

The same program with `cross` and `normalize`; a local `dot` whose `self` IS an `F32x4`
(must keep resolving to the local); a `std:buffer` method shadowed the same way.
