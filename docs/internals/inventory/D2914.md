### D2914 — an adopted object-literal list read at its own `{ f: i32 }` type is invalid wasm

**check-clean invalid wasm · clause 1 · the same on master `1f092d569` · found by the #3235 review · filed 2026-09-27 against master `1f092d569`**

Repro:

    const i: { f: i32 } = { f: 4 }
    type I = { f: i64 | null }
    const il = [{ f: 7 }]
    const ic: I[] = il
    const z = il.map((e) => e.f)
    print(z[0])
    // vl check: rc 0.  vl run: invalid module in the top-level code

Want:

    7

#### Mechanism

Not localised past the ablation. D2881 builds `il` at `I`'s row, which its declared destination
names, but the checker still types `il` as `{f: i32}[]`. The direct reads the D291 ladder
already converts (`il[0].f`, `il.length`, `for e in il`) run. A read that hands an element on
at the literal's own type does not convert it, and neither does a copy of the list. Before D2881
the same programs were invalid one line earlier, at the adopting binding.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the adopting binding (`const ic: I[] = il`) | runs | **yes** |
| the `{ f: i32 }` record | runs, prints `7` | **yes** |

#### Grading list

Each of these beside the same four prelude lines is invalid wasm:
`function show(r: { f: i32 }) { print(r.f) }` with `show(il[0])`; `const cp = [...il]` with
`print(cp[0].f)`; `function first<T>(xs: T[]): T { xs[0] }` with `print(first(il).f)`; and a
function that binds `il`, adopts it into `I[]` and returns `il`.
