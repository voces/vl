### D14930 — a re-pointed `let` of a generic listed inside a function called at two instances runs only through `monoPinListElems`

**runs today and must keep running · waits on the flow-sensitive-read backlog item (owner ruling B, 2026-11-02) · step 4 (γ) family C of `monoPinListElems`' flat path · with that pin cut to return early the witness is a loud emit reject (`a function value's signature is not known at this call`), so the pin is the only producer of each instance's element signature · capture-cell join territory ([D14425](D14425.md)) · pins: `tests/cases/closures/written-let-in-list-called-in-two-instances.vl`, `written-let-in-two-element-list-called-in-three-instances.vl` · found ablating family W · filed 2026-11-02 against master `ea74167bd`**

Repro:

    function other<V>(v: V) { print(v) }
    function g<T>(x: T) {
      let k = other
      k = (n) => { print(n) }
      const fs = [k]
      fs[0](x)
    }
    g(3)
    g("s")

Want:

    3
    s

#### Mechanism

`k` is a `let` first bound to a generic and re-pointed to a hole lambda, so it is a capture cell
holding one function per instance. The list literal `[k]` reads that cell, and the checker types
the list at `k`'s open signature. Only the flow-table pin `monoPinListElems` reads gives each
instance's list its closed element type. The fix is the per-instance join of a written `let`, not a
closed signature for the list.

#### Ablation

| ingredient removed (pin cut) | outcome | needed? |
| --- | --- | --- |
| the second instance (`g(3)` only) | runs | **yes** |
| the re-point (`k = (n) => ...`) | runs | **yes** |
| the list (`k(x)` directly) | runs | **yes** |
| the type parameter (`function g(x)`) | emit reject | no |
| the generic initialiser (`let k = (n) => ...` first) | runs | **yes** |

#### Ruling (2026-11-02): B, backlogged

Owner ruling: a read of a `let` takes the type of the most recent write in scope, so `[k]` after
the re-point reads the lambda's type. It is backlogged as ROADMAP.md §"Backlogged: ruled, waiting to be built", flow-sensitive reads of a `let`, with this row and
[D2660](D2660.md) as its witnesses, and this row waits on it. DECISIONS.md §"A read of a `let`
takes its most recent write's type".

#### Findings (2026-11-02, before the ruling)

Three measurements, from the attempt to close it at the let-write join:

- The checker has no read-after-assignment typing for any type: `let x: i32 | string = 1; x = "s"; const y = x; y.length` refuses, `y` reading the union. A read of `k` after its in-frame re-point taking the lambda's type is a new, flow-sensitive rule, pending the owner's ruling beside D2660 (the same question from the null side).
- Every read of `k` takes the binding's type, `elabFnLetTy` (`check_statements.vl`), a clone of the initialiser's signature `(V) => void` (`other`'s own `V`) carrying the union set, so `[k]` is `((V) => void)[]` with `V` never bound; at the refusal the call reads the first instance's `(i32) => void` and its signature key has no parameters.
- Re-pointing the join's parameters at the written lambda's, where a parameter is the generic initialiser's own type variable, did not move the witness with `monoPinListElems` cut.
