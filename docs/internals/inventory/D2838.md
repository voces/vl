### D2838 — an `i32[]` value `??` an `f64[]` literal types `f64[]` but builds no element-converting copy

#### Mechanism

The `i32` twin of [D2274](D2274.md). The `??` of an `i32[]` value and the `[2.5]` literal is typed
`f64[]`, which is right for the literal, but the value arm reaches the join as the `i32` list with
no element-converting copy, so the two arms are two list wrappers. A return set of `[t]` beside
`[2.5]` runs, since both are literals built at the joined type (D2716). Whether the join owes a
converting copy or the checker owes a refusal is the open ruling D2274 already names.

#### Grading list

The attack grid's direct twins `*_mix_f_i_*`, `*_mix2_f_i_*` and `*_coal_f_i_*` (a `??` inside a
function returning it), and D2274's own repro.

The generic spelling is out of the checker's reach: inside `function h<T>(xs: T[] | null)` the
`??` joins `T[]` with the literal, and only the pin `T := i32` makes the stored lists differ. The
emitter refuses it there (`coalListDefaultClash`, D2799): a `??` typed as its operand's one list
whose default is stored as another list and is no numeric literal that fits, which also covers an
`i64` literal into an `i32` list, `R[] | null ?? ["d"]`, and a variable or second type parameter's
list beside `T[]` (the #3214 final review's `gvar`/`gtwo` cells, invalid on master `7323baf55`).

#### Ruling needed

The emitter could build the join as asked, with the D965 converting copy at each arm whose
list is stored differently. That copy is the one DECISIONS.md §"No implicit container
widening" retired for a mutable destination, since a write through `q` would not reach `a`
and nothing at the `??` says a copy was made. The join's result is a fresh mutable list, so
the ruling's reason applies to it as it does to `const b: f64[] = a`, which already refuses.
Until the owner rules, the checker refuses (`listJoinWidenCheck`, typecheck.vl) at each
`if`, `match`, `??` and inferred return set whose joined list stores some level of an arm's
list differently. A list literal arm is exempt, since it is built at the joined type.

**Question:** does a value join of a list with a differently stored list (a) refuse, as a
delivery into a mutable `f64[]` does, (b) type as the union `i32[] | f64[]`, as a join of two
maps of different storage does (D2666) and a join of `string[]` with `[1]` does, or (c) build
a converting copy?

This is the question [D2728](D2728.md) already asks for the return set, whose author recommends
(b); the refusal here holds either answer open, since both (a) and (b) refuse `q[0]` on this
repro. It covers a reference-element pair too: `string[]` beside `[1, "a"]` refuses, with
`.map((x): i32 | string => x)` as the copy.

**Recommendation: (a).** It is the rule every other delivery of a mutable list follows, the
message names two fixes that build (`.map((x) => x as f64)` on the arm, or building the source
as `f64[]`), and it moves no running program. (b) is sound and copy-free, but it retypes every
literal pair beside it unless the literal exemption is kept, and a read like `q[0]` would then
refuse as `not on every member`. (c) is the hidden copy the aliasing ruling rejected.
