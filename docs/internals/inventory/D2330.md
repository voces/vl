### D2330 — a function-value call nested in another's arguments at the same signature made the outer call run the inner closure's code, with no trap

**closed 2026-09-24 — the witness prints `17`. Found while grading D2329 (plumb PL-036); filed
against master `1c1e796f8`, where it is check-clean silently wrong and prints `4`.**

Repro:

    const a = (x: i32) => x + 1
    const b = (x: i32) => x * 10
    const c = (x: i32) => x - 3
    print(c(b(a(1))))
    // prints 17

#### Mechanism

This is D2329's mechanism with the signatures matching. The single `callRefSlot` held the
innermost callee by the time each outer call read its function id, so `call_indirect` passed
the signature check and ran `a`'s code three times, with each call's own env: `a(a(a(1)))` is
`4`. Nothing traps, so only a wrong value shows it. Closures that share one lambda's code and
differ only in their env (`mk(1)`, `mk(10)`) came out right by accident, because the env is
read before the arguments. Callback specialization also hid it wherever a literal lambda was
passed straight to a parameter, since those calls became direct calls. The D2329 fix covers
this row too.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the nesting | runs | **yes** |
| distinct lambda code (closures of one `mk`, different envs) | runs, right by accident | **yes** |
| a call that stays indirect (a literal lambda passed straight to a parameter is specialized to a direct call) | runs | **yes** |
| a bare nested argument (the inner calls inside a `.map` callback, or in `a(1) + a(2)`) | still wrong | no |
