### D1890 — an f64 target has no contextual-literal rule, so an integer literal past the i32 range refuses there while the same literal adopts the strictly LESS precise f32

**closed 2026-09-07 — the witness prints `2147483648` · was a loud check reject at 7 delivery positions plus mixed arithmetic · clause 2 · filed 2026-09-07 against master `4b36f61b1` · fixtures `tests/cases/numerics/f64-literal-adopt-positions.vl` and `…-boundary.vl` · the union-box half is [D1930](D1930.md)**

Repro:

    const a: f64 = 2147483648
    print(a)
    // vl check (before): 1:16: i64 doesn't fit in f64 — the conversion is lossy and
    // must be made explicit with `as` (write `x as f64`).
    // `const a: f32 = 2147483648` ran, and still does.

#### Mechanism

An integer literal types `i32` while it fits and `i64` once it does not, and the only
implicit route into an `f64` slot was the widening lattice's `i32 -> f64` edge
(`numWidensName`, `compiler/typecheck.vl`). So the flow site saw an `i64` VALUE and took the
lossy-edge rejection, which is right for a value and wrong for a literal: the f32 target does
not rely on the lattice at all, it has its own exactness-gated adoption predicate
(`isF32AdoptingLitExpr`, `docs/internals/contextual-f32-literals-design.md`), and that
predicate reads the LEXEME, so it spans the whole integer range. f64 was never given the twin
— the `i32 -> f64` edge covered every literal anyone tried, and the literals it does not cover
are exactly the ones between 2^31 and 2^53, every one of which f64 holds exactly.

Closed by `isExactF64IntLitExpr` over `intLexemeIsExactF64` (53 significand bits against the
f32 flavour's 24), granted where `dstAdmitsPrim(dstTy, "f64")` and at `binOpType`'s and the
comparison's literal-adopt arms. The exactness walk and the destination walk are each ONE
function taking the width, so the two grants cannot drift apart the way this row is the
evidence they can.

#### Grading list

`const a: f32 = 2147483649` and `const a: f32 = 16777217` must keep refusing — the f32
predicate is exactness-gated and the f64 twin is too, so `const a: f64 = 9007199254740993`
(2^53 + 1) still refuses at all thirteen positions while `9007199254740992` (2^53) runs. The
mixed-arithmetic spelling `mkF64() + 9000000000` is the second face and was NOT fixed by the
assignment site alone — it needed `binOpType`'s arm, and the comparison needed its own. The
union/nullable destination was the thirteenth cell and needed an emitter change:
