#### Mechanism

`dupScanRun` (compiler/emit_sections.vl, D1595) runs the scratch-detection sweep with the scope
stack empty, so a name bound in many blocks resolves to its `dupSlotBias`-th slot, and the bias
climbed one slot position at a time while any later slot was of another rep class. D2090 skipped
a bias whose whole tuple of classes (one per multiply-bound name) matched an already-swept one.
That holds while few names vary. In generated x86 code, `m`, `x`, `y`, `c`, `v` and `b` are each
bound hundreds of times per function and each flips between `i32` (`const m = 16`) and `i64`
(`const m = rax + 8`) on its own schedule, so almost every position produced a new tuple and the
function body was swept once per position. The guest profile of `chunk_466` read `dupScanRun` at
41.7% of the compile, inclusive.

#### Fix

`dupScanIndex` now lays out each name's class REPRESENTATIVES (the first slot of each
`localRepKey`) rather than all its slots, so the bias walks classes. A frame is swept
max(classes of one name) times, at most a handful. Same-class slots already classify alike, which
is D2090's own premise, and each class of each name is still visited, which is what D1595
requires. Byte identity: the three plumb chunks at `-O` and without it, the self-compile fixpoint,
and 11,138 programs built by master's seed and this one (`tests/cases`, `tests/fixtures`, `std`,
`compiler`, every distilled and named corpus cell) to the same bytes or the same refusal. `tests/vl_scaling_shape_test.ts` axis `same-named locals of several
reps` (five names on periods 2, 3, 5, 7 and 11) reads 4.10 on master and 1.10 after.
