### D14489 — which print imports a module needs is guessed by a syntax pre-scan, not recorded where the print is emitted

**open 2026-10-27 · runs today and must keep running · a second producer, not a wrong answer: `scanPrintUse` (emit_sections.vl) decides the `__print_f64__` / `__print_f32__` / `__print_i64__` imports from TypeRefs, number literals, `as` targets and read literal-valued assignments, guessing from statement position whether a value is read, while the emitter knows exactly which print call it builds · filed 2026-10-27 against master `39b871e68`**

Repro:

    let h: f32 = 1.0
    h = 0.5
    const y = (h = 0.1)
    print(y)

Want:

    0.1

#### Mechanism

Imports precede every function index, so the module cannot add one once emission has begun,
and the pre-scan reserves them ahead of time from the syntax. Each new way a value reaches a
print at a width the program never spells has to be taught to the scan as well. The witness
is one: the assignment's value is read at its literal's f64 type in a program that spells
only f32. If the scan misses one, `print` falls back to `__print_i32__` over an f64 operand,
which is check-clean invalid wasm. If the scan over-reserves one (a store-only `m["a"] = 1.5`), the import is unused. The
question is whether the print imports can be reserved at the emission site instead (a
deferred import table with indices fixed up afterwards, or a checker fact naming each print
call's operand width), so the scan is deleted rather than taught.

#### Progress

The pre-scan no longer reads syntax. It reserves a width for every node whose recorded type
holds that scalar at any depth, so the statement-position guess and the per-construct arms
are gone, and the witness runs on that basis. The scan is still a second producer: what
remains open is reserving the import where the print is emitted.
