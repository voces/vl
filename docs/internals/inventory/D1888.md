### D1888 — a bare `null` at a GENERIC call's argument has no struct-typed context, while the same `null` at a concretely-typed parameter runs

**loud emit reject · clause 2 · 11 of the 18 disagreements in a 1,600-pair `pinning` sample
(seeds 301-304, 800 programs each) · filed 2026-09-07 against master `6f76e471a` by the day-one
sampler's new multi-parameter pin, which is what first delivered a bare `null` into a generic
argument at all**

Repro:

    type Rec = { name: string, n: i32 }

    function pass<T>(x: T): T { return x }

    function make(): Rec | null { return pass(null) }

    const v = make()
    if v is null { print(0) } else { print(v.n) }
    // vl check: `Checked 1 file, no errors.` rc 0
    // vl run: emitProgram: bare null needs a struct-typed context
    // Should print 0; the same `null` through a concretely-typed parameter does.

#### Mechanism

**Found by the two-parameter pin, minimal at ONE.** The sampler reaches this by binding the
SECOND hole of `pass2<A, B>` to the value's own `null` alt; the grammar's one-parameter pin
only ever wrapped the delivered value, so no plan before it wrote a bare `null` into a generic
argument. Reduced, the second parameter is not an ingredient — `pass<T>(null)` refuses the
same way, and so does a bare `null` in the FIRST hole of the two-parameter form.

The neighbouring spelling runs: `function take(x: Rec | null): Rec | null` called as
`take(null)` prints `0`. So the hole is what loses the context, not the `null`.

Sixty-nine filed rows cite this sentence and all but three are CLOSED; the one open sibling,
[D1832](D1832.md), is a `null[]` LITERAL whose element type has no non-null member at all —
a different mechanism, and its witness needs no generic.
