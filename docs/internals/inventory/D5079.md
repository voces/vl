### D5079 — a record field holding a written `let` of a generic, in a generic function, has no signature

**closed 2026-10-16 — now prints `5 t` · was loud emit reject, `vl check` rc 0, clause 2 · the pinned type of a field read a generic's instances share is kept per instance (`monoFieldReadTys`, keyed by the read and the instance), with the field's initializer left open there, and the call keys its signature from it, through a `const` alias of the read too · a call through the field from a closure in the generic is D5112 · found grading D5061's generic-frame position · filed 2026-10-16 against master `502f8daa8` · pin: `tests/cases/closures/record-field-written-let-in-generic-frame-two-instances.vl`**

Repro:

    function k<T>(x: T): T { return x }
    function use<U>(u: U): U {
      let g = k
      g = k
      const r = { q: g }
      return r.q(u)
    }
    print(use(5))
    print(use("t"))
    // vl check: rc 0.  vl run: emit error, a function-value call has no interned signature

Want:

    5
    t

#### Mechanism

D5061's close types a field read `r.q` at the slot's pinned function type, and declines in a
generic function's frame: `use`'s two instances share the read node, so typing it at one
instance's `(i32) => i32` makes the other instance's call invalid wasm (measured before the
decline). A `const` alias does not need the read typed, because the slot-read rewrite turns the
call into a direct call of `k` in each instance. A written `let` has no one function to rewrite
to. A fix types the read per instance, which the shared node cannot hold, or proves the frame has
one instance.
