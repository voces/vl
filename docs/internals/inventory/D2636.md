### D2636 — `vl run` has no way to supply an `extern let` / `extern const` global, so a program that declares one can only run after a hand-linked build

**closed 2026-09-26 by `vl run --extern NAME=VALUE` (owner ruling 2026-09-26, flag name ruled the same day) — a host CLI gap, not a miscompile: the witness runs, and the behaviour is graded by `tests/vl_extern_global_test.ts` · plumb PL-046 (reported by plumb) · filed 2026-09-26 against master `50c627ce4`**

Repro:

    function add(a: i32, b: i32): i32 { a + b }
    print(add(2, 3))
    // runs, prints `5`. With `extern let CTXB: i32` added at the top, master's `vl run` stopped
    // at load with "extern global `CTXB` is declared but `vl run` provides no globals" and had no
    // flag to supply it, although nothing reads `CTXB`. Now `vl run p.vl --extern CTXB=0` prints
    // `5`, and without the flag the refusal names it: "extern `CTXB` is not supplied — pass
    // --extern CTXB=<value>".

#### Mechanism

`register_extern_imports` in `scripts/vl-host/src/main.rs` refused every `global` import in the
`extern` namespace. The refusal is right without a value (a zero nobody set is what the extern
contract exists to prevent), but the CLI offered no way to give one, so plumb's tests that
import `src/rt.vl` needed `vl build`, a hand-written WAT, `wasm-as` and `wasm-merge` before
`vl run`. The close defines each declared global from its `--extern` value, typed by the
import: an integer (decimal, or `0x` hex, signed or as the unsigned bit pattern) for `i32`/`i64`
(so `boolean` too), a float for `f32`/`f64`. A value of the wrong kind or out of range, a
malformed or repeated `--extern`, and one naming no declared global are each refused, naming it.

#### Grading list

Refusing only a global the program actually reads is the owner's longer-term goal, recorded as
ROADMAP Track C `C-extern-read`; today every declared extern global needs a value.
