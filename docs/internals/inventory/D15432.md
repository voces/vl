#### Mechanism

The tag decision declines `{id, dbl}` at the hand `viaHole(f)` (`ftCtxOk` → `ftHoleParamOf`), because `ftParamStored` counts the parameter listed in a literal that `ys.push(...zs)` copies element by element (D15131). The set stays closures, and `f`, called at `string` and handed to an `i32` slot, wants two signatures, which only the split plan's copies give. Lifting that clause tags the set and builds invalid wasm: the copy's adapter (`fvaListSetCopy`) is built at the template, where `zs`'s element is a closure, and receives an id in `viaHole`'s instance (`expected (ref $5), found i32` inside `__lambda_0`). The direct `ys.push(a)` runs without the plan, since `a` is delivered to the closed slot type at the call (an escape the adapter dispatches). Closing it needs the copy's adapter built per instance at the element the instance holds.

Measured 2026-11-04 (patch not landed): the copy's lambda returning an explicit eta closure, `($e) => ($c0: i32): i32 => $e($c0)`, in place of `$e` when the source element is a hole, is harmless with the clause kept and runs this witness, D15131's, a two-set spelling and an `f64` slot with the clause lifted. It still traps (`indirect call type mismatch` in `viaHole`) when one instance of `viaHole` holds the set's id and another a closure (`viaHole(f)` beside `viaHole((x: i32) => x * 3)` or `viaHole(id)`), which is the shape D15130's guard keeps. Lifting the clause therefore wants the elaboration's fact that every instance of the parameter holds the set, rather than the syntactic `ftParamStored`: the per-instance row of closure-at-delivery-2026-11.md, `(creation site, instance, closed signature) → fe`, with the copy's adapter as the creation site. It waits on that row rather than a producer of its own.
