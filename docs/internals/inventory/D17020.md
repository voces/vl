### D17020 — the name section never names the `__log__` decoder, so a backtrace through it shows `<wasm function N>`

**closed 2026-11-19 · runs, prints `105` and `-7`, and `--names` now names the decoder `__log__` · fixed in emit_sections.vl `emitNameSection`/`nameMapCount`: the decoder's entry is written at `gMemLogIdx`, between the init functions and the runtime helpers, and counted · the index was right; the row was never written · filed 2026-11-19 against master `58c91fe76`**

Repro:

    __memory_grow__(1)
    __store_i32__(0, 0)
    __store_i32__(4, 105)
    __store_i32__(8, 0)
    __store_i32__(12, -7)
    __log__(0, 16)
    // vl build --names: every function named but the decoder, which disassembles as `$N`

Want:

    105
    -7

#### Mechanism

`emitNameSection` writes the namemap in index order: the imports, the user functions, the start
function, each init function, then `nameHelpers()`'s runtime helpers. The `__log__` decoder sits
at `gMemLogIdx`, between the init functions and the helpers, and no step wrote it; `nameMapCount`
did not count it either, so the map stayed well-formed and the decoder simply had no name.
`runtimeFnNames` (a per-module artifact's name table) does name it, which is why a search there
finds the name and the module does not. The index was correct, so no other function could be
named in its place.
