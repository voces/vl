### D1862 — two sibling module-level blocks binding one closure name, where either closure returns VOID, emit a malformed start function

**CLOSED 2026-09-07 — the call statement's drop decision asks whether the callee's `$fnsig` is void, and it asked by NAME with no position; positioned at the callee's own arena node (D1751's key, this reader) it answers per block. Was: check-clean invalid wasm · pre-existing, identical before and after D1861 · the filed axis was wrong, and the re-measurement is below: the capture is not an ingredient, and neither is the map**

Two sibling blocks at module scope each bind a closure called `f`. If either closure's result
is VOID and either is called, the start function's byte stream loses its stack:
`type mismatch: expected a type but nothing on stack`. `vl check` returns 0.

**The row was first filed as a captured-MAP defect, from D1861's price cell, and that framing is
retired.** A witness with NO capture at all fails identically, every capture type fails
identically, and a value-returning pair of the same shape runs. What the two spellings differ by
is the closure's RESULT, not what it closes over.

Repro:

    if true {
      const f = () => { print(1) }
      f()
    }
    if true {
      const f = () => { print(2) }
      f()
    }
    // vl check: rc 0.  vl run: invalid module — the emitted module failed to validate
    //   inside the module's top-level code: type mismatch: expected a type but nothing on stack

#### Mechanism

The `Ident` arm of the call-STATEMENT ladder decides whether to `drop` what the call left. For a
closure-VALUE callee it asked `calleeReturnsVoid(name, fnIx)` — a name and a frame, no position
— which reaches `calleeCloSigKeyAt(sid, fnIx, -1)`. D1751 made that resolver DECLINE on a name
two sibling module blocks bind rather than pick the first, so the key came back `""`,
`sigKeyRetIsVoid("")` is false, and a void call took a `drop` with nothing to drop. The reader is
now positioned at the callee's own arena node, so it answers per block.

Two earlier hypotheses were refuted with an instrument VALIDATED by a control that makes it fire
— an unconditional probe in `emitCloCall` prints `PROBE emitCloCall REACHED ckey=[>v]` on all
seven closure-call shapes, so the two silences below are readings and not a mute probe. The
signature key resolves correctly at both spellings through the POSITIONED path
(`cloCallSigKey` already threads it), and the emitter never takes the `fnSigIdxForArity`
fallback. What was wrong was one UNpositioned reader, and the same probe printed it:
`name=f fnIx=-1 atIx=-1 fe=-1 key=` for the shared name against
`name=f1 … atIx=7 fe=0 key=>v` for the distinct one.

#### Ablation

Every row is `vl check` rc 0; "invalid" is check-clean invalid wasm.

| spelling | outcome |
| --- | --- |
| the witness — two blocks, shared name, void block body | **invalid** |
| `() => print(n)` — a void EXPRESSION body | **invalid** |
| no capture at all in either closure | **invalid** |
| the captures are i32 / a list / a string / a struct / a map | **invalid**, identically |
| three siblings of one name | **invalid** |
| only the FIRST block's closure is called | **invalid** |
| only the SECOND block's closure is called | **invalid** |
| one void and one value-returning closure, either order | **invalid** |
| `let` bindings rather than `const` | **invalid** |
| both closures return a VALUE (`() => 1`, `() => { return 1 }`) | runs |
| the two closure names made distinct | runs |
| one block only | runs |
| neither closure is called | runs |
| the two blocks made two FUNCTIONS | runs |
| the two sibling blocks put INSIDE one function | runs |

Needed: the MODULE frame, two sibling blocks, one shared closure NAME, a VOID result on at least
one of them, and at least one call. Not needed: a capture, the capture's type, the map, `const`
vs `let`, which of the two is called, or the body being a block rather than an expression.
