### D1862 — sibling module-level blocks reusing one CLOSURE name share an env row, and a captured map in them is check-clean invalid wasm

**check-clean invalid wasm · found 2026-09-07 while closing D1861 · pre-existing on master `678f578e3` at five of six spellings; D1861's fix moved the sixth from a loud emit reject to this same silence, which is the price it names**

D1751 closed the sibling-module-block shared-env-row family for the bindings it was filed
against. A captured MAP is still in it, and the axis is the CLOSURE's name, not the map's:
two sibling module-level blocks that each declare a closure called `f` share one env row, so
the second block's capture reads the first's field. Renaming either closure fixes it, and
renaming only the MAP does not.

Repro:

    if true {
      const c1: {[string]: f64} = Map()
      const f = () => {
        c1.set("b", 3.5)
        print(c1.get("b") ?? 0.0)
      }
      f()
    }
    if true {
      const c2: {[string]: f64} = Map()
      const f = () => {
        c2.set("d", 1.5)
        print(c2.get("d") ?? 0.0)
      }
      f()
    }
    // vl check: rc 0.  vl run: invalid module — the emitted module failed to validate
    //   inside the module's top-level code: type mismatch: expected a type but nothing on stack

#### Mechanism

The env row is keyed on the closure's NAME within the module frame, so two sibling blocks
declaring `f` intern one row and the second block's field layout is the first's. D1861's fix
made the map's SHAPE resolve correctly at both blocks, which is why the one cell that used to
refuse loudly (`map values must be i32 / boolean`, the mono assumption firing) now reaches the
env row and is silent with the other five. Nothing about the map is wrong; the row it is stored
in belongs to another closure.
