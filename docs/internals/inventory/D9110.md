### D9110 — a function-typed parameter named like a module function refuses as a `.map` callback

**closed · runs, prints `30` · was loud emit reject, `emitProgram: unsupported .map/.filter element type` · `vl check` rc 0 · clause 2 · found closing [D9073](D9073.md) · filed 2026-10-21 against master `713f2c17d` · closed by resolving an identifier callback by scope, so a parameter, binding or capture shadows the module function of its name (`cbIdentNamesFn`, `mfCallbackCloKey`, emit_classify.vl; `emitMfCallbackValue`, wasmEmit.vl) · fixture `closures/fn-param-shadows-module-fn-callback.vl`**

Repro:

    function k(x: i32): i32 { return x + 1 }
    function h(k: (x: i32) => i32): i32 { return [3].map(k)[0] }
    print(h((x: i32): i32 => x * 10))
    // master: vl check rc 0, vl run: emitProgram: unsupported .map/.filter element type

#### Mechanism

The `.map` / `.filter` result kind came from the callback's lifted function (`mfCallbackFe`,
scope-aware) or, failing that, a closure value's signature key (`mfCallbackCloKey`); the key
reader and the emitter's `emitMfCallbackValue` asked `fnIndexOfAt` / `fnIndexOfNode`, which see
the module's functions and block-local ones but not a parameter, `let` or capture on the frame
chain. A parameter named like a module function was therefore taken as that function: no
closure key, and the callback built as a direct reference to the wrong function. Both now ask
`cbIdentNamesFn`, which resolves the name with `fnIndexOfInScopeAt`, the reader the checker's
scoping agrees with.
