### D9682 — an un-annotated parameter bound at `i64` computes `x + 1.5` at `f64`, where `x: i64` refuses the mix

**closed · now a loud check reject, refused by the checker as the direct spelling is, "argument 1: operator '+' mixes i64 and f64 (the body of `f` applies '+' to this argument)" · was check-clean silently wrong, printing `5000000001.5`, clause 1 · found closing [D9631](D9631.md) · filed 2026-10-22 against master `abe12f20f` · closed with [D9802](D9802.md): the pin asks the direct spelling's pair rule, with the operator's node so a literal adapts as it does there (`binCstrPairRefusal`, check_relate_core.vl) · fixtures `numerics/error-pin-numeric-pair-mixes.vl` and `numerics/pin-numeric-pair-controls.vl`**

Repro:

    function f(x) { x + 1.5 }
    print(f(5000000000))
    // was: PRINTS 5000000001.5

#### Mechanism

The body is checked once with `x` a hole, where a float literal beside it is accepted, and at
an `i64` pin the arithmetic computed at `f64` (since [D9631](D9631.md), `binArithPinTy` types
it `f64` explicitly). The direct spelling refuses the mix, since a fractional literal cannot
adapt to `i64`. The pin asked only whether `+` is defined over numerics; it now re-asks the
direct spelling's pair rule, so the two spellings agree.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| the argument `2` (an `i32` pin) | runs, prints `3.5`, as `x: i32` does | **yes** |
| the annotation `x: i64` | check refuses | **yes** |
| the literal `1` | runs, prints `5000000001`, as `x: i64` does | **yes** |

#### Grading list

A lambda `(x) => x + 1.5`, a `<T>(x: T)` body at `i64`, `-`, `*` and `/`, and an `i64` pin
through a list literal (`[x, x + 1.5]`): each refuses, and the three controls above still run.
