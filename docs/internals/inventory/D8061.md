### D8061 — a hole called at `i32` and at `f64` has its `i32` call's result typed `f64` at an annotated destination

**loud check reject · clause 2 · CAPABILITY: the same program without the annotation runs and prints `4 3` · found closing [D7841](D7841.md) · present on master `370ba120c` · filed 2026-10-20 against master `370ba120c`**

Repro:

    function add(a, b) { return a + b }
    function p(g): i32 {
      print(g(1.5, 2.5))
      return g(1, 2)
    }
    print(p(add))
    // vl check: return type mismatch: expected i32, got f64 (the return of `p` at the call's argument types)

Want:

    4
    3

#### Mechanism

Traced 2026-10-20, not fixed. At the pin, `holeFnArgInst` (check_relate_core.vl) instances the
handed hole function at ONE signature, built from every call the body makes of the parameter,
so `g := add` becomes `(f64, f64) => f64`. The re-check then types each `g(...)` from the
`HD_RET` arm of the same file, which substitutes the call's own arguments only for an open
foreign generic signature (`holeCallRetAt`) or a function read out of a hole (`holeOpenFnRetAt`);
otherwise it returns that one instance's `fnRet`, `f64`. The un-annotated spelling is consistent
with this and not with the emitter's split: `const r = p(add)` then `print(r / 2)` prints `1.5`,
so `g(1, 2)` is computed as `f64` there too. A close types each call at its own arguments, which
needs `p` instanced per call type on the emit side, and changes the VALUE TYPE of the
un-annotated spelling (`f64` to `i32`), so it is a `runs → runs` change in printed values and
has to be read against the numeric-join ruling before it lands.

#### Ablation

| spelling | outcome | needed? |
| --- | --- | --- |
| the witness | loud check reject | — |
| no `: i32` on `p` | runs, `4 3` | **yes**: the annotated destination |
| `const r: i32 = g(1, 2)` in a void `p` | loud check reject, `f64 doesn't fit in i32` | no: any annotated destination |
| no `g(1.5, 2.5)` call | runs | **yes**: two call types |
