**closed 2026-10-20 by lane L1c · runs, prints `4 3` · was loud check reject · clause 2 · CAPABILITY: the same program without the annotation ran · each call of a hole is now typed at its own arguments, so the un-annotated spelling's `g(1, 2)` is `i32` too and `r / 2` after it prints `1` where master printed `1.5`, an intended change of output (no tests/cases program or corpus cell carried that spelling) · pins: `tests/cases/closures/hole-fn-called-at-f64-and-i32-returns-i32.vl`, `hole-fn-called-at-f64-and-i32-unannotated-per-call.vl`, `hole-fn-called-at-f64-and-i32-delivered-to-i32.vl`, matrix `hole-fn-called-at-f64-then-i32-open` · found closing [D7841](D7841.md) · present on master `370ba120c` · filed 2026-10-20 against master `370ba120c`**

Repro:

    function add(a, b) { return a + b }
    function p(g): i32 {
      print(g(1.5, 2.5))
      return g(1, 2)
    }
    print(p(add))
    // vl check: return type mismatch: expected i32, got f64 (the return of `p` at the call's argument types)

Want:

    4
    3

#### Mechanism

Traced. `genFnHoleInstance` (check_relate_core.vl) builds one instance of the handed function
from all the hole's calls, and `genFnHoleCallBind` absorbed a later call whose argument was
assignable to an earlier binding: `(1, 2)` fits `(f64, f64)`, so both calls took the `f64`
instance. The call order reversed already split, because `f64` does not fit an `i32` binding.
A call that would bind any type variable differently now declines the shared instance, so each
call is typed at its own arguments through the per-call path, which the emitter's split plan
already instances.
