### D1603 — a compound assignment read the element it was about to pin, so the store banked the operator floor's `TyErr` as the element type

**closed 2026-09-04 · was check-clean invalid wasm at an f64 or f32 element, a loud emit reject at a string one, a loud check reject wherever the compound assignment was the function's tail, and at i32 a program that ran with `<error>[]` recorded for the binding · a store's own right-hand side now pins the open element from the value operand · found in [D1600](D1600.md)'s residue, reported by the `glean` consumer as VL-046 · the deferred-pin family is [D1591](D1591.md)**

Repro:

    const seen = []
    const count = []
    const seconds = []
    function note(name: i32, dt: f64) {
      for i in 0 to seen.length - 1 {
        if seen[i] == name {
          count[i] += 1
          seconds[i] += dt
          return
        }
      }
      seen.push(name)
      count.push(1)
      seconds.push(dt)
    }
    note(7, 0.5)
    note(7, 0.25)
    print(count[0])
    print(seconds[0])
    // was: vl check rc 0, then exit 70 — the emitted module failed to validate inside
    //   `note`: type mismatch: expected i32, found f64
    // now: 2 / 0.75

#### Mechanism

**A compound assignment is its own first read.** `count[i] += 1` desugars to
`count[i] = count[i] + 1` with the target node shared between the read and the write
(`mkCompoundAssign`), so the read runs while the element is still open. `checkIndexNode`
answers `arrElemValueTy(-1)` — the in-band `-1` an unpinned element reads back as — and the
binary arm's floor turns that into `TY_ERR` with no diagnostic, deliberately: it is
[D1462](D1462.md)'s guard against indexing `T.tys` with `-1`, and its silence is what keeps
`print(xs[0])` from reporting the open element twice. The `=` arm above it then pins
`arrT0.aElem = rt` from that `TY_ERR`, so the row stops being open, the later `count.push(1)`
does not re-pin it, and `flushUninferred` has nothing to grade. What the program does next
depends only on the element type the push would have named: an i32 tally runs, because a row
nothing pinned lowers as the i32-list default, and every other element type disagrees with that
default — f64 and f32 by producing a module the engine refuses, string by reaching
`emitProgram: string array literal but string list type not collected`. Where the compound
assignment is the body's TAIL, the `TY_ERR` is also the return type, so every element type is
`cannot infer a return type`.

The close names the row an index store is about to pin, for the length of that store's value
only (`asgOpenElemRow`), and a read of the SAME row inside the value pins the element from the
value operand (`asgReadElemPin`) — the answer the plain `xs[i] = v` spelling already took. The
read's own recorded node type is patched with it, for `arrDefOperandElemPeek`'s reason
([D1566](D1566.md)): `checkNode` banked the `-1` a moment ago and the emitter reads that entry.
Keying on the receiver's arena ROW rather than on the shared node is what makes the hand-written
spelling `count[i] = count[i] + 1` — two nodes, one row — take the same pin.

The i32 witness's module is **byte-identical** before and after (2,264 bytes, element
`(type $0 (array (mut i32)))`): where the guess happened to match, only the recorded type moved.

**Residue.** A compound assignment into an un-annotated `Map()` still records
`{[string]: <error>}` for the carrier. It is refused at BOTH faces — `m[k] += 1` reads
`V | null`, and the annotated spelling gets the same `operator '+' is not defined for i32 | null
and i32` — so no diagnostic-free program can show the token, and the two faces differ only in
how the message renders the unpinned value. Whether `m[k] += 1` should be a spelling at all (it
needs a `??` today) is a design question this row does not answer.
