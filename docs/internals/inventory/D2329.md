### D2329 — a function-value call nested in another's arguments overwrote the outer call's closure slot, so the outer `call_indirect` checked the inner callee against the outer signature

**closed 2026-09-24 — the witness prints `a!`. Reported by plumb as PL-036
(`~/plumb/docs/vl-issues.md`, repro `~/plumb/out/repro/pl036.vl`); filed against master
`1c1e796f8`, where it loads then traps with `indirect call type mismatch`. Not a regression from
#3111: archive builds of `ac25508bd` and its parent `51f7bb8ab` trap the same way. D2330 is the
same mechanism at a matching signature, where it runs the wrong closure without a trap.**

Repro:

    const lo = (x: i32) => "a"
    const set = (e: string) => e + "!"
    print(set(lo(1)))
    // prints a!

#### Mechanism

`emitCallRef` (and `emitCapturedCall`, the capturing nested-function twin) stashes the callee
closure in `callRefSlot` so it can read the env (field 0) before the arguments and the
function id (field 1) after them. There was one `callRefSlot` per function, so a
function-value call in the arguments stored its own closure there. The outer call then read the
inner closure's id and `call_indirect`ed it at the outer call's `$fnsig`. Where the two
signatures differ the engine traps. Plumb's PL-036 (`set(lo(o))`, `(O) => string` inside
`(string) => void`) is this case. The void `if` bodies, the loop and the captures in plumb's
program were all incidental. A call now takes `callRefSlot` only at nesting depth 0. A call
inside another's arguments gets a lazy-frame slot keyed by its depth (`callRefNestSlot`,
`liBack` 23, `(ref null $cloStruct)`), so siblings share one slot and no inner call can write
an enclosing call's slot.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the nesting (`const x = lo(o)` then `set(x)`) | runs | **yes** |
| different signatures for the two callees | runs, but calls the wrong closure (D2330) | for the trap |
| the `for` loop, the early `return`, the enclosing function | still traps | no |
| the captures of `w` (both lambdas) | still traps | no |
| the void `if` body (a block `{ if … }`, a `: void` annotation, a string result) | still traps | no |
| `lo` as a lambda (a declared `function lo`, called directly) | runs | **yes** |

#### Grading list

`tests/cases/closures/nested-value-call-arguments.vl` (plumb's shape, a `match` body through
function-typed parameters, sibling arguments, capturing nested functions, struct-field
closures) and `tests/cases/closures/nested-value-call-same-signature.vl` for D2330. On master
both graded the 64-cell matrix on the setter's body (`if` expression, `{ if }` block, `match`,
`{ match }` block) × annotated or inferred × captured or not × flat or in a loop × called
directly or through a function-typed parameter: 64 of 64 trapped. All 64 print `32 a1` / `true`
after the fix. On master, the workaround is to bind the inner call to a `const` first. A block
body or a `: void` annotation on the lambda does not avoid the trap.
