### D5611 — a generic handed to an un-annotated parameter that is called at two signatures has no single instance

**closed 2026-10-17 by lane L1 · runs, prints `x 3` · was loud emit reject · clause 2 · option A: the split plan gives a hole parameter called at two argument-type keys one parameter per key, and each call hands its argument once per key · pins: `functions/generic-fn-value-hole-forwarded-at-two-types.vl` and six siblings · [D6090](D6090.md), [D6091](D6091.md), [D6092](D6092.md) · found closing [D5402](D5402.md) · filed 2026-10-17 against master `7fe51e77c`, re-graded on the merged pin driver against master `5aa033e26`**

Repro:

    function same<T>(k: T): T { k }
    function take(a) {
      print(a("x"))
    }
    function take2(a) {
      print(a(3))
    }
    function mid(a) {
      take(a)
      take2(a)
    }
    mid(same)
    // vl check: rc 0.  vl run: emitProgram: a function-value call has no interned signature — the callee has no function type to key a signature from

Want:

    x
    3

#### Mechanism

From the ablation only. A function value carries one signature, and `mid`'s hole is reached by
pins at two: `(string) => string` and `(i32) => i32`. The pin driver `monoHoleGenFnPin` takes
the flow table's pin only when the argument's read has exactly one closed pin (D5612's close).
With two it declines, and the forwarded value stays open. Closing this needs either the hole
instanced once per pin (one `mid` per signature) or the program refused at `vl check`. That is a
rank-2 question, not a gap in the driver.

Re-graded after [D5751](D5751.md)'s close, unchanged. That close gives a const hole lambda one
flow walk per call, which a hole function like `mid` already had. It does not reach this row:
the one `mid(same)` call still reaches two closed pins.

#### Options

The question: is `mid`'s hole `a`, bound to the generic `same`, still generic, so that each
call through it instances `same` at its own signature? Or is it one function value with one
signature, so the checker owes a refusal at the second call?

**Existing rulings already decide it: `a` stays generic (option A).** No owner ruling is
needed, and the rest of this section is the implementation brief. Four rulings decide it,
and the checker already agrees:

- **An un-annotated parameter is a type parameter.** DECISIONS.md §"An unbounded `<T>` is
  an ENTIRELY OPEN HOLE" (owner, 2026-09-03) says an explicit `T` and a hole are one thing.
  So `mid(a)` is `mid<A>(a: A)`.
- **Each call is checked at its own type arguments** (spec T9.1). `mid(same)` binds `A` to
  the type of `same`, which is the generic function type `<T>(k: T) => T`. `take` and
  `take2` bind their holes to the same type.
- **A binding of a generic keeps the generic type, and calls through it stay generic.**
  This is ruling C, D3960 (owner, 2026-10-10, "what TypeScript does"), in spec T9.3 and
  S2.5. `const h = same; h("x"); h(3)` runs (row s16 below). A parameter is a binding, and
  no ruling makes a parameter monomorphic where a `let` is not.
- **A binding called at several types holds one closure per type, and is delivered by
  value.** This is D3975 (owner, 2026-10-15), DECISIONS.md §"A reassigned function binding
  called at several types holds one closure per type". It is the rep for the multi-source
  case. fn-value-flow-design.md §(e) already gives the one-source case: "two or more pins,
  one source, no writes: each read gets the instance at its own pin".
- **`vl check` already accepts the witness.** It also refuses the one wrong spelling: with
  `a: (k: string) => string` (s02), `take2(a)` is refused at the call. So the typing half
  is in place. The emit refusal is clause 2 by construction.

##### Option A: the hole stays generic (implied by the rulings above)

```vl
function same<T>(k: T): T { k }
function mid(a) { print(a("x")); print(a(3)) }
mid(same)          // prints x, then 3
```

- **Meaning.** A hole that receives a generic function holds a generic function. Each call
  through it is a call at that call's types, as through `const h = same`.
- **Runs:** s00, s05, s07, s09, s10, s11, s15, and the pinned
  `error-generic-fn-value-inferred-hof.vl`, which then prints `3 4 3 4`.
- **Still refused:** s02 at check, which is correct. s01 does not parse. Option A needs no
  new syntax. A written rank-2 annotation would be a separate surface question, and nothing
  asks for one yet.
- **Other languages.** C++ behaves the same way: a template parameter bound to a generic
  lambda `[](auto k) { return k; }` is called at two types. A VL hole is a per-instance
  template, so this is the closest analogue. TypeScript gives the same result only with an
  annotation, `a: <T>(k: T) => T`. An un-annotated `a` is `any` there, or an error under
  `noImplicitAny`.
- **Implementation (lane L1/SC, one binding per call).** No checker change.
  - `monoHoleGenFnPin` (D5612's driver) declines at two or more closed pins today. With
    two or more, it hands the class to the multi-pin path.
  - **One source, no writes** (s00, s05, s07, s10, s11). This is fn-value-flow-design
    §(e)'s rule. The class's source is known at every read, so each call through the hole
    lowers to the source's instance at that call's pin. The value carries only the
    source's environment, and a top-level function has none. No record is built.
  - **Two or more sources, or a written binding** (s09, s15). This is the D3975 record,
    `{src, c1…cn}`, built where the value is delivered into the hole class. `mid(same)` and
    `mid(other)` each build one, filled at every pin of the class. A call at pin `i` reads
    field `i`.
  - **Delivery into a concrete slot** inside the hole's body (for example
    `useI(a: (k: i32) => i32)`) takes that pin's instance by value. This is D3975's
    by-value rule, and s12 already runs it for a direct delivery.
  - Two messages go away with the refusal: s10's `unsupported argument type`, which has no
    source position, and s11's `No call site pins`.
- **"Must not slow ordinary calls."** Only a class with two or more closed pins changes. A
  one-pin class takes today's path through D5612's driver, so its output is byte-identical.
  The one-source case allocates nothing. The multi-source case allocates one record per
  delivery into the class, and only in programs master refuses. The proof is the one D3975
  asked for: `difftree.sh --identity` differs only on programs master refused.
- **The lambda question.** A hole lambda is generic under spec S2.5, so `mid((k) => k)`
  (s06) asks the same question with a lambda in place of `same`. Its check refusal is
  older than every ruling here, and its fixture states a mechanism ("gives the emitter
  nothing to monomorphize against"), not a contract. Under option A it is a clause-2
  candidate. That belongs to a follow-up for L3 (checker legality), not to this row.

##### Option B: a hole bound to a generic is one monomorphic value

```vl
mid(same)   // refused: `a` is called at (string) => string and at (i32) => i32,
            // and a function value has one signature. Annotate the parameter, or pass `same` twice
```

- **Meaning.** Let-polymorphism only, as in OCaml (`let mid a = (a "x", a 3)` is a type
  error) and Kotlin (a generic function reference fixes its type arguments where it is
  taken).
- **Runs:** s03, s08, s12 and s13, as they do today.
- **Becomes a check reject:** s00, s05, s07, s09, s10, s11 and s15. That is a DESIGN
  refusal written in the checker by lane L3.
- **Against.** It contradicts ruling C. `const h = same; h("x"); h(3)` would run, but
  passing `h` to a parameter that does the same thing would be refused. That makes a
  parameter less generic than a `let`, which no ruling says. It also contradicts the
  2026-09-03 ruling: `mid<F>(a: F)` (s05) would have to refuse what `T9.1` checks per call.
  It reverses the checker's current acceptance. And it adds a checker pass that unifies
  every demand made through a hole across forwarders, which the flow table already does
  emit-side.

##### Option C: generic for one source, refused for two

- **Meaning.** s00 runs, but s09 (`mid(same); mid(other)`) is refused, so the record is
  never needed.
- **Against.** D3975 already chose the record for the same class shape, a binding that may
  hold two functions and is called at two types. The checker cannot count sources: that
  is a flow-table fact. So this refusal would be emitted at emit, which makes it clause 2
  by construction, or the checker would grow a second copy of the flow table.

##### Recommendation

Option A, as already decided by the 2026-09-03 hole ruling, ruling C (D3960) and D3975.
Build it in L1/SC as the multi-pin arm of `monoHoleGenFnPin`. The one-source case comes
first and allocates nothing. The D3975 record follows for multi-source classes. This row's
witness and s05, s07, s09, s10, s11 and s15 are the grading list, plus the pinned
`error-generic-fn-value-inferred-hof.vl`, which flips to runs and has to become a runs
fixture.
