### D8220 — a wrapper returning a direct call of a function widening `i32` to `f64` is accepted at an `i32` binding

**closed 2026-10-20 by lane L1 · now a loud check reject (`f64 doesn't fit in i32`) · was check-clean invalid wasm · clause 1, present on master `be738c9f0` · fixtures `tests/cases/soundness/error-hole-wrapper-of-widening-call-at-i32.vl` and `tests/cases/functions/hole-wrapper-of-widening-call.vl` · filed 2026-10-20 against master `be738c9f0`**

Repro:

    function half(a) { return a / 2.0 }
    function w(x) { return half(x) }
    const r: i32 = w(3)
    print(r)
    // vl check: f64 doesn't fit in i32 — the conversion is lossy and must be made explicit with `as`

#### Mechanism

D8161 takes a direct call's result from the callee's body at the bound arguments
(`holeLamRetAt`). `w`'s body re-derived at `i32` reaches `half(x)`, a direct call inside a
body, and `holeCallNodeTy` (`check_relate_core.vl`) answers it with the call's recorded type
`T` rather than re-deriving `half` at `x`'s bound `i32`. Closed there: `holeCallNodeTy`
answers a direct call of an un-annotated function by `holeDirectCallRetAt`, which re-derives
the callee at the call's argument types through `directHoleBodyRet` (moved from
`check_calls.vl`), so `w(3)` is `f64` at every level of wrapper.
