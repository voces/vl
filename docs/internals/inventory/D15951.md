### D15951 — a read of a `let x = null` inside a callback run in its call, with a write that fills the hole after the call, is delivered as the hole and builds invalid wasm

**check-clean invalid wasm · clause 1 · pre-existing on master `403a522d5` · one open cell of the flow-sensitive-read matrix (the callback position of the null face) · filed 2026-11-12 against master `403a522d5`**

Repro:

    function take(s: string | null): i32 { if s == null { return 1 } else { return 0 } }
    function main() {
      let x = null
      const ys = [1, 2].map((e) => e + take(x))
      x = 5
      print(ys[1])
    }
    main()
    // vl check: rc 0.  vl run: the emitted module failed to validate inside `__lambda_0`

Want:

    3

#### Mechanism

Not traced. The callback runs inside `.map`, before `x = 5`, so under the ruling its read of `x`
is `null` (DECISIONS.md, "A read of a `let` takes its most recent write's type").
`crCallbackKeeps` keeps a guard narrowing in the same position (`if x is string { [1,
2].map((e) => e + x.length) }` with `x = 2` after it runs). The `null` row from the declaration does not
reach the read: it is typed at the binding's hole, delivered to `string | null` while the hole is
open, and built at the filled `i32 | null` box. The end-of-check judgement of such deliveries
(`judgeNullHoleDeliveries`) does not see it either.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| `x = 5` | runs, `3` | **yes**, the fill after the call |
| the callback (`take(x)` in `main`) | runs, `1` | **yes** |
| the `null` row for an `is string` guard over an `i32 \| string` | runs | **yes**, the `null` face |

#### Grading list

* A block-bodied callback, `(e) => { const y: string | null = x; … }`.
* `.filter`, and a generic higher-order function whose parameter is only called.
