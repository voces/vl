### D15951 — a read of a `let x = null` inside a callback run in its call, with a write that fills the hole after the call, is delivered as the hole and builds invalid wasm

**closed 2026-11-12 · was check-clean invalid wasm under the flow-reads face · the cell read now delivers its `null` at the destination's rep · filed 2026-11-12 against master `403a522d5`**

Repro:

    function take(s: string | null): i32 { if s == null { return 1 } else { return 0 } }
    function main() {
      let x = null
      const ys = [1, 2].map((e) => e + take(x))
      x = 5
      print(ys[1])
    }
    main()
    // was: vl check rc 0, then the emitted module failed to validate inside `__lambda_0`

Want:

    3

#### Mechanism

The callback runs inside `.map`, before `x = 5`, so under the ruling its read of `x` is `null`
(DECISIONS.md, "A read of a `let` takes its most recent write's type"), and the checker keeps
that narrowing in the callback (`crCallbackKeeps`). `x` is written after a closure captures it,
so it lives in a shared cell, and `captureBoxRewrite` respells the closure's read as `c[0]`. The
null delivery (`emitNullReadAtDst`) answered only an `Ident` read, and asked the destination of
the respelled node, which records none. So the `c[0]` read pushed the cell's `i32 | null` union
box into a `string | null` parameter.

`emitIndex` now delivers a cell read narrowed to `null` as the name read does, and
`emitNullReadAtDst` asks the destination of the read the node respells (`nodeSrc`).
