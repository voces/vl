### D15462 — a value `if` joining an un-annotated parameter with a named function traps when the named function's arm runs

Repro:

    function inc(x) { x + 1 }
    function dbl(x) { x * 2 }
    function go(k: boolean, f) {
      const h = if k { dbl } else { f }
      print(h(1))
    }
    go(true, inc)

Want:

    2

#### Mechanism

As filed: the value `if` joins the parameter `f`, whose type is an open hole, with the named function `dbl`.
The join keeps the hole beside the function type (`_ | ((i32) => i32)`) instead of binding the
hole to it, so the instance of `go` types `h` at the parameter's closure signature while the `dbl`
arm delivers a value of another one, and the indirect call through `h` traps. With an annotated
`dbl` the same join reaches the checker, which refuses the call: `called value is not a function
(_ | ((i32) => i32))`, a clause-2 refusal of the same program.

#### Close

Two readers of the same join. In the template the `if` value is open (`_ | ...`), so
`monoCoerceIfArms`, which instances a hole-function arm at the join's closed function type
(D10797), never ran, and `dbl` was built as an uncalled stub, `(structref) -> void`, while the
call through `h` was `(i32) => i32`. It now falls back to the instance's type of the value
(`elabWalkTy`). The annotated face was the checker's join of the parameter's bare hole with
`(i32) => i32` into a union nothing can call; it now joins as the hole, which each instance
pins. Both changes: 0 movers over the `tests/cases` corpus with the split plan on and off.
