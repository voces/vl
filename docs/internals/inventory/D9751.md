### D9751 — an assignment to a module `let` with a module-scope `for … in` loop variable of the same name lowers the value at the loop variable's type

**closed · runs, prints `2.5` `2` · was check-clean invalid wasm, `vl check` rc 0, clause 1 · found writing the [D9681](D9681.md) fixture · filed 2026-10-22 against master `60aaa08c0` · closed by passing a loop variable over in the flat slot scan once the scope stack is authoritative, as a block-scoped binding already was, so every `declared*` classifier sees the same binding `localIndexOf` does (`flatScanSkips`, emit_struct_order.vl) · fixture `scope/module-let-shadowed-by-loop-variable.vl`, matrix `module-let-shadowed-by-loop-variable` (8 → 64 of 64) · with [D9750](D9750.md) closed**

Repro:

    let w = 1
    w = 2
    for w in [2.5] {
      print(w)
    }
    print(w)
    // vl run: invalid module — type mismatch: expected i32, found f64

Want:

    2.5
    2

#### Mechanism

A module `let` read only in top-level code lowers to a start-function local, beside the loop
variable's own local. The store `w = 2` targets the module binding's slot, but the value is
lowered at the loop variable's type: the disassembly is `local.set $3 (f64.const 2)` into the
`i32` local. The assignment's target classifiers (`exprIsF64` and the list and union seeds in
`emitAssignIdent`, wasmEmit.vl) appear to answer by name from the start function's flat
binding table, where the later loop variable is found. Reads of `w` before and after the loop
are correct.

Traced at the close: the classifiers ask `declaredSlotOf`, which tries the scope stack and then
scans the frame's flat slot table by name. That scan passed over a block-scoped binding whose
block had closed (D1597) but not over a loop variable, while `localIndexOf`'s own scan
(`declaredSlotLive`) passed over both. So outside the loop the store went to the module
binding's slot and the classifier typed it as the dead `f64` loop variable. The defect was
wider than filed: a read alone (`print(w)` after the loop, with no assignment), a
parameter shadowed by a loop variable in its function, and a loop inside a function over a
module binding all broke the same way; each is in the fixture. The assignment's own lowering
(`emitAssignGlobal`) still classifies its target by name, through the same scans, which now
agree with the resolver.
