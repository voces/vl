### D2993 — a generic reader of a record's `LS | null` field refuses to print it

**loud emit reject · clause 2 · identical on master `4dc94bd23` and on #3250 · found by the #3250 review grid · filed 2026-09-28**

Repro:

    type LS = "a" | "b"
    function rd(o) { print(o.v) }
    const l: LS | null = null
    const q = { v: l }
    rd(q)
    // vl check: rc 0.  vl run: emitProgram: print of a literal-union atom whose type carries no member texts

#### Mechanism

Not localised past the review grid. `rd`'s instance for `q` reads `o.v` as a literal-union atom,
but the type it asks for the member texts carries none, so `print` refuses. #3250's one lost
run is this row. The #3250 review found that on master, with a sibling declared `LS | null`
record, this reader printed `b` for a `null` field, which was unsound. #3250 builds the literal
at its own record, so it now refuses here instead.

#### Grading list

A sibling refusal of the same field: `?.` over a map read of an `LS | null` field,
`const m: {[string]: { v: LS | null }} = Map()`, `m["k"] = { v: "b" }`,
`print(m["k"]?.v ?? "none")`, which refuses `emitProgram: \`?.\` over a map read supports only
i32/boolean fields` on master and on #3250. Without the `??`, the `?.` refuses instead with
`a standalone \`?.\` has no rep for a map or closure leaf field`.
