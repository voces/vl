### D7660 — wasmtime's copying collector collects instead of growing while a growing live set nears a semispace, so a retained list of 2,000,000 strings costs 36 collections and about 10x its CPU

**runs today and must keep running · cost row: a live set approaching half the GC heap triggers a collection storm (36 collections at 2,000,000 retained strings on the 256 MiB default, 72 at 4,000,000), cause in wasmtime 49.0.2, no config remedy · filed 2026-10-20 against master `b56512057`**

Repro:

    import { toString } from "std:fmt"

    const xs: string[] = []
    let i = 0
    while i < 2000000 {
      xs.push("key" + toString(i))
      i = i + 1
    }
    print(xs.length)
    // vl check: rc 0.  vl run: prints 2000000 after 36 collections, 2.9 CPU-s.
    // VL_GC_HEAP=512M: 1 collection, 0.64 CPU-s.

Want:

    2000000

#### Mechanism

wasmtime 49.0.2's `Collector::Auto` is the copying (Cheney semispace) collector. When an
allocation fails, `retry_after_gc_async` (`store/gc.rs`) calls `should_collect_first`, which
collects first whenever `last_live + bytes_needed < capacity / 2`. The `capacity` there is the
WHOLE heap, both semispaces. `collect_and_maybe_grow_gc_heap` also compares against the full
capacity. So when a collection is chosen, it frees only `semispace - live`. The heap doubles
only after a collection fails to make room for the pending allocation, and until then each
collection copies about a semispace of live data. With the run default `RUN_GC_HEAP_INITIAL`
of 256 MiB (a 128 MiB semispace), the storm starts at about 1.9M retained `"key" + toString(i)`
strings. It comes back at the next doubling, at about 4M. Raising `$VL_GC_HEAP` only moves the
cliff. The host can do nothing between the collection and the allocation:
`GcHeapOutOfMemory::new` is crate-private, `gc_heap_capacity` is not on `StoreContextMut`, and
a `ResourceLimiter` can only veto growth. The seed's remedy, `SeedGcHeadroom` (an epoch check
plus a balloon allocation that forces the grow-first branch), works on user programs too. A
prototype on this row's commit took the witness from 36 collections and 2730 CPU-ms to 4 and
430. Its epoch check costs every loop back-edge, though: +22% on `bench/recursion/fib`, +59% on
`algorithms/lambda-hot` and +66% on `arith/i32-accum`. That is the price
`docs/internals/perf/gc-heap-policy-2026-09.md` §2 rejected, measured again. The upstream ask
is `docs/internals/perf/wasmtime-copying-heap-growth-issue.md`: grow when a collection leaves
the semispace mostly full.

The ingredient is a retained live set that grows toward a semispace. Strings reach it first
because each costs about ten times a two-field record. Concatenation, `toString`, `-O` and the
element type are not ingredients. Without retention, the same strings never storm. Neither
heap size nor the DRC collector is a remedy: refcount is still slow here, uses twice the
memory, and is 8x slower on `binarytrees`.

#### Grading list

Re-run this row's ablation table on a wasmtime that grows instead of collecting when the
survivor fills the semispace. Then re-measure `bench/algorithms/binarytrees` (53 collections)
and `bench/arrays/push-growth` (12), which share the policy. Re-measure the epoch tax on
`fib`, `lambda-hot` and `i32-accum` before any host-side `SeedGcHeadroom` for user stores is
proposed again.
