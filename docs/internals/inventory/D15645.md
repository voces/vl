### D15645 — the result of a function that hands a hole function, in a list or record literal, to a callee calling it at `f64` is left untyped by the checker

**closed 2026-11-10, runs and prints `6` · was check-clean invalid wasm, clause 1, `the emitted module failed to validate inside the module's top-level code: … type mismatch: expected i32, found f64` · found writing D15640's matrix · filed 2026-11-10 against master `1fc9a771` · closed in the checker: a call whose result stays open because a generic argument is handed on inside a list or record literal reads that result with the argument at the instance the element or field call in the callee takes (`holeLitFwdRet`, `holeBindLitForward`, check_relate_core.vl), pin-quiet, so the argument the elaboration binds stays generic and its dispatch is unchanged; `const b: string = both1(dbl)` is now refused as `f64`, as `c1([dbl], 2.5)` is · `c1` reads the set id and calls `$dbl` directly in the repro's `--names` build · fixtures `functions/hole-in-literal-handed-to-hole-callee-result.vl`, `functions/hole-in-literal-called-at-two-types-result.vl`, `functions/error-hole-in-literal-handed-to-hole-callee-result.vl` · residue: a result joining two calls at different types, [D15648](D15648.md)**

Repro:

    function dbl(v) { return v + v }
    function c1(r, x) { return r[0](x) }
    function both1(g) { return c1([g], 2.5) }
    const b = both1(dbl)
    print(b + 1)

Want:

    6

#### Mechanism

Before the close, `vl check` accepted `const b: string = both1(dbl)` too (it refuses `c1([dbl], 2.5)` there as
`f64`), so the checker gives `both1(dbl)` an open type, and the emitter, which builds `f64`,
has no conversion to the type the reader assumed. It opened in `holeBindForward`, which counted a
hand-on inside a literal as an open call (D15609), so no instance of `g` was found to read the
result at.

#### Ablation

| `c1({ f: g }, 2.5)` calling `r.f(x)` (record for list) | still invalid wasm | no |
