### D16099 — a call's result holding an un-annotated function, handed straight to a generic `(x: T) => R` parameter, is refused at emit

**closed 2026-11-14 · runs, prints `6` · was loud emit reject · clause 2 · ``emitProgram: monomorphize: unsupported argument type for `g` in a call to `app``` · found grading [D16093](D16093.md) · filed 2026-11-14 against master `e5bfe3d6c` · fixed in the checker: a type parameter an earlier argument bound to an inference hole (the call result's own open parameter) takes a later argument's closed type (`bgInferHole` in `bindGenWalk`), and a call argument's functions are read from its type's set (`holeFnArgDecls`), so `R` closes; before, the call's result stayed open (`const q: boolean = app(pick1(true), 3)` passed check) · fixtures `generics/call-result-hole-fn-handed-to-generic-param.vl`, `generics/error-call-result-hole-fn-generic-result-misused.vl`**

Repro:

    function inc(a) { return a + 1 }
    function dbl(a) { return a * 2 }
    function app<T, R>(g: (x: T) => R, v: T): R { return g(v) }
    function pick2(c: boolean) { return if c { dbl } else { inc } }
    print(app(pick2(true), 3))
    // vl run: prints `6`

Want:

    6

#### Mechanism

Ablated: a choice is not needed. `app(pick1(true), 3)`, with `pick1` returning `inc` alone, is
refused the same way, and `const g = pick1(true); app(g, 3)` runs. The call result's type is
`inc`'s open signature, so binding `g: (x: T) => R` against it bound `T` to that signature's own
parameter hole before `v: 3` could fix it. The result `R` then stayed open: the checker accepted
any use of the result, and the monomorphizer found no pin for `g`.
