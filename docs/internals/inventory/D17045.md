### D17045 — a maker returning a fresh hole lambda, held in a `const` and called at two signatures, has no interned signature

**closed 2026-11-26 · was loud emit reject: a function-value call has no interned signature · clause 2 · fixed by family C's C1 with D16845 · fixture `tests/cases/closures/maker-lambda-held-at-two-signatures.vl` · `vl check` rc 0 · the function-body spelling refuses the same · neighbours: [D15144](D15144.md) (the lambda is the maker's parameter; runs), [D16295](D16295.md) (the maker captures a hole parameter) · found by lane IR-N6 grading the holderRecord slice · filed 2026-11-21 against master `f1b142006`**

Repro:

    function mk() {
      return (x) => x
    }
    const id = mk()
    print(id(4))
    print(id("ab"))

Want:

    4
    ab

#### Mechanism

`mk` returns a lambda it creates, with an un-annotated parameter, so the call `mk()` yields one
closure whose parameter is still a hole. The `const` holding it is called at `i32` and at
`string`. D15144 gave a returned bundle *parameter* a record holding one closure per signature,
but a lambda created in the maker's own body gets no such record. The holder's call then reaches
emit with a parameter of type `_`. Today's refusal: `emitProgram: a function-value call has no
interned signature — parameter 1 of type \`_\` has no representation in the function-value ABI`
at `print(id(4))`.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |

| the holder: `print(mk()(4))` | runs, prints `4` | **yes** |
| the hole: `(x: i32) => x` with one call | runs, prints `4` | **yes** |
| the top level: the same lines in a function body | still refuses | no |
