### D1599 — the `no method` diagnostic knew the replacement and did not say it; the method twin of D1590

**fixed — now a loud check reject that ENDS by naming the method it wanted:
`; did you mean '.<name>'?`, a name that resolves on the receiver today · was the same
refusal, one clause short · diagnostics only: emitted wasm byte-identical, distilled
corpus 0 classes moved, 0 `runs → not-runs`, 0 `→ silent` · reported by glean as VL-045 ·
credit to glean for the report · filed 2026-09-04 against master `f3dfb648`**

Reported by the language's first external consumer: `~/glean/docs/vl-issues.md` §VL-045.
Its own words — "`s.charAt(i)` does not exist; `s.slice(i, i + 1)` is the substitute.
Minor, but the error (`no method '.charAt' on string`) does not name the alternative,
which is the same shape of complaint as VL-039 and VL-040: the checker knows the fix and
does not say it." VL-039 is D1590, this diagnostic's `unknown type` sibling.

**THE DECISION: `charAt` DOES NOT BECOME A STD EXPORT.** `slice(i, i + 1)` and
`charCodeAt(i)` already exist, std has no deprecation story, and a name close to
permanent is not the fix for a message that already knows the right one. The deliverable
is the message.

Repro (before: the first line only; now: the whole line):

    const s = "hello"
    const i = 1
    print(s.charAt(i))

    // BEFORE: 3:9: no method '.charAt' on string
    // NOW:    3:9: no method '.charAt' on string; did you mean '.slice(i, i + 1)'?

#### Mechanism

The checker's `no method '.<prop>' on <type>` message is built at exactly three call
sites in `compiler/typecheck.vl` (`grep "no method '\."`): the string arm and the array
arm of `checkCallNode`, and `validateUfcsCstrs`' generic fallback for a deferred UFCS
receiver constraint. `methodSuggestFor` (kind-dispatched on `T.tys[recvTy]`) and its
suffix wrapper `methodDidYouMean` add a `; did you mean '.<name>'?` to each, from two
sources in order: a small newcomer map per receiver kind (exact, case-folded — `charAt`
names a call with DIFFERENT ARGUMENTS, so its entry stores the whole shape,
`slice(i, i + 1)`, not a bare name), then an edit distance (`tyEditDist`, D1590's own
budget) over the intrinsic names for that kind plus every in-scope self-function the
receiver could dispatch to (`selfFnNamesFor`, mirroring `ufcsCallTy`'s lookup without its
arity gate).

**A FOURTH SITE, FOUND BY RUNNING THE PLAINEST PROGRAM THE BRIEF NAMED.** The brief's map
row (`put`→`set`, `containsKey`→`has`, `size`→`length`) assumed a Map's failed call
reaches one of the three "no method" sites. It does not: `m.put(1, 2)` on a `{[string]:
i32}` answers `unknown property \`put\` on {[string]: i32}` — a fourth, map-only message
at a fourth call site, and the newcomer map's own row would have been dead code without
wiring it there too. A Set (`mSet == 1`) skips the newcomer map entirely rather than
offering `.set`/`.get`/`.keys`, which `checkCallNode`'s own Set arm refuses.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the newcomer map (`s.silce(0, 1)` instead of `charAt`) | `did you mean '.slice'?` — the distance rung answers | no |
| the call-shape entry (`charAt` mapped to a bare `slice` instead of `slice(i, i + 1)`) | suggests a call with the wrong arity | **yes** |
| `selfFnNamesFor` (an imported `toUpperAscii`, typo'd `toUpperAscci`) | no suggestion — the distance rung has nothing to search | **yes** |
| the Set/Map split (`.put` on a real `Set()`) | wrongly suggests `.set`, which the Set arm refuses | **yes** |
| a NEAR name in scope (`"hello".zorptastic()`) | bare `no method '.zorptastic' on string` | **yes** |
