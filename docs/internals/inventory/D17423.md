### D17423 — a `null`-typed compare with an assignment of `null` on one side, against anything but a bare `null`, emits an invalid module

**closed 2026-11-24 by lane S1 · now runs, `true` · was check-clean invalid wasm, clause 1 (`type mismatch: expected i32, found nullref`) · legacy's `eqRouteOf` asks `nulNoneEqRoute`, which takes an assignment of `null` typed `null` as the unit, so the compare is `emitNulNoneEq`'s: each side for its effect, then the constant · pin: `tests/cases/soundness/null-pair-compare-assignment-side.vl` · filed 2026-11-24 by lane S1 against master `cea354ff6`, found writing the `null test of null` matrix**

Repro:

    function n(): null { return null }
    function g() {
      let s: string | null = "a"
      print((s = null) == n())
    }
    g()
    // vl check: 0 errors.  vl run: invalid module, `type mismatch: expected i32, found nullref`

    true

#### Mechanism

Legacy's `null`-typed pair compare (`emitNulNoneEq`) runs each side for its effect through
`emitNulNoneForEffect`, and an assignment of `null` on one side leaves a value of the wrong type
where the compare's `i32` answer is expected. Read by a route probe: the compare did not take the
`nulNone` route at all. `nulNoneEqSides` asks `exprIsNulNone`, which has no arm for an assignment,
so the pair fell to `numeric` and wrote `i32.eq` over two nullrefs.
