### D1512 — two `__array_new_default__` holes that meet at a plain `=` record a LINK, and the one defaulting site that never read it pinned `i32` under an `f64` slot

**closed 2026-09-03 — the witness runs and prints `1.5` · was check-clean invalid wasm (`vl
check` rc 0, `Invalid input WebAssembly code … type mismatch: expected (ref $type), found (ref
$type)`) · clause 1 · fixed by giving `checkArrayNewDefaultElems` the same hole-link consult
`arrDefHoleToI32` already had, through one shared `arrDefPinHoleElem` · found by the
`local_assign` matrix position added in #2479 (D1500), whose first sweep over the 21 standing
templates named exactly this cell**

Repro (before: `vl check` rc 0, then the engine refuses the module; now: prints `1.5`):

    function la() {
      let v = __array_new_default__(3)
      v = __array_new_default__(3)
      v[0] = 1.25
      print(v[0] + 0.25)
    }
    la()

#### Mechanism

`__array_new_default__(n)` returns an array row whose element is a HOLE, because
`array.new_default` promises the element's zero and says nothing about which element — the
destination pins it later (D1470). When BOTH sides of a store are still open, `constrainEmptyD`
cannot pin either from the other, so it records the pair with `noteHoleLink`; the pair is read
back at defaulting time by `holeLinkElemOf`. There are TWO places a hole is defaulted, and only
one of them read the link: `arrDefHoleToI32` (scope flush, consults the partner) and
`checkArrayNewDefaultElems` (program end, reached for `i32` unconditionally). A hole that is not
a BINDING never reaches the flush — and `v = __array_new_default__(3)` delivers the intrinsic
straight into an assignment, so its row is a bare call row. The link from that row to `v`'s was
recorded and thrown away; `v[0] = 1.25` pinned `v`'s row to `f64`, the call row took `i32`, and
the emitter built both.

The two reps, from `wasm-dis` on the pre-fix module. The `let` lowers the f64 list
(`(type $4 (array (mut f64)))`, struct `$5`), the assignment the i32 one
(`(type $0 (array (mut i32)))`, struct `$3`), into the same `(ref $5)` local:

    (local $0 (ref $5))
    (local.set $0 (struct.new $5 (array.new_default $4 …)))   ;; let v  = …  f64
    (local.set $0 (struct.new $3 (array.new_default $0 …)))   ;; v      = …  i32

The ANNOTATED face has one rep because the annotation takes `constrainEmptyD`'s other arm
(`d.aElem >= 0`), pinning both rows in place: `struct.new $1` over `(array (mut f64))` at both
sites, and no i32 array type in the module at all. After the fix the un-annotated face emits
that identical pair — 1943 bytes down to 330, the whole i32 list family gone.

Second half of the same fix: the arm that defaulted also SKIPPED the grade, so an element a
partner supplies was never asked for its zero. Pinning and grading now happen in that order, one
path, so a partner resolving to `string[]` or a nested list is refused by `elemHasZero` the way
the direct spelling is instead of reaching the emitter.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the reassignment (`let v = __array_new_default__(3)` alone) | runs `1.5` | **yes** |
| the intrinsic on the RHS (`v = [1.0, 2.0, 3.0]`) | runs `1.5` | **yes** |
| the intrinsic on the LHS (`let v = [1.0, 2.0, 3.0]`) | runs `1.5` | **yes** |
| the f64 element (`v[0] = 7`, `print(v[0] + 1)`) | runs `8` | **yes** |
| the f64 demand after the store (`print(v[0])` only) | runs `0` | **yes** |
| the store AFTER the reassignment (`v[0] = 1.25` moved before it) | runs `0.25` | **yes** |
| the annotation left on (`let v: f64[] = …`) | runs `1.5` | **yes** |
| the anonymity of the second row (`const w = …` then `v = w`) | runs `1.5` | **yes** |
| the function scope (module scope, or a bare block) | still invalid wasm | no |

The last two rows are the mechanism in one line. Naming the second hole makes it a BINDING, and
a binding is flushed through `arrDefHoleToI32`, which reads the link — the same program with the
same two holes and the same link runs the moment one of them has a name. And the position is not
the ingredient: module scope fails too, with `expected (ref null $type)` for the nullable global
slot, which is why the fix is at the defaulting site and not in `emitAssign`.

      function f() {
        let a = __array_new_default__(3)
        let b = __array_new_default__(3)
        let c = __array_new_default__(3)
        b = a
        c = b
        c[0] = 1.25

  Silent on BOTH seeds, identically. `holeLinkElemOf` is ONE HOP by design, and `flushUninferred`
  walks the pending bindings in declaration order — so `a` is asked before `b` has resolved,
  finds `b` still open, and takes `i32` while `b` and `c` land on `f64`. The chain is not
  all-open (`c` is pinned), so `i32` is not the honest answer here the way the one-hop note says
  it is for a chain nothing ever pinned. Needs its own id: the fix is a fixpoint over the pairs
  or a transitive walk with a visited set, neither of which this row's shared pin point touches.
