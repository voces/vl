### D3559 — an export list with no `from` is scanned as a re-export from the specifier ""

**closed 2026-10-03, now a loud check reject that names the re-export to write, reported by the module graph at the parse stage as `(parse error)` · was a loud check reject reading `Unsupported import specifier ""` · sunpa SP-014, lane EX · filed 2026-10-03 against master `fae55dec2` · fixtures `tests/cases/modules/err-export-list-*/`, `err-module-path-missing/`, `err-reexport-path-missing/`, `reexport-std-kept-import/`**

Repro:

    import { sinF64 } from "std:math"
    export { sinF64 }
    print(sinF64(0.0))
    // was: Unsupported import specifier "" — supported: relative paths (`./`, `../`) and `std:` modules; …
    // now: `export { sinF64 }` names an imported binding; re-export it with `export { sinF64 } from "std:math"`

#### Mechanism

`modScan`'s re-export arm (`driver.vl`) walked from the closing brace to the next STRING
token, bounded by the line, and pushed one import edge per listed name with whatever it found.
With no `from` there is no string, so the edge carried the specifier `""`, which no resolver
accepts, and `modVisit` reported the bare-specifier sentence at the `export` keyword. The
import arm had the same hole for `import { x } from` with nothing after `from`. The
`impSpecChar` column now records what stood in the specifier slot (`SPEC_STRING`, `SPEC_CHAR`,
`SPEC_ABSENT`, `SPEC_NO_FROM`), and `modVisit` gives each of the last two its own sentence. For
`SPEC_NO_FROM` it looks the name up among the module's own imports and, when found, spells the
re-export of that same binding (`import { sinF64 as s }` + `export { s }` suggests
`export { sinF64 as s } from "std:math"`). A local `export { … }` list stays refused:
modules-design §2.1 rejects it ("a second place to keep in sync"), so no semantics were added.
Whether an export list may name imports, together with SP-020's two questions (does a
re-export bind locally; is an import beside it a duplicate), is open in modules-design §2.1.1.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the `import` of `sinF64` | same empty-specifier refusal (now: the declaration-site sentence) | no |
| `std:` as the source (`./lib`) | same refusal | no |
| the list's `from` keyword, keeping `from` with no path | same refusal (now: `missing module path`) | no |
| a path string after `from` | runs | **yes** |

#### Grading list

`export { a, b as c }` naming two imports (one diagnostic per name, the alias carried), the
same list in a middle module of three, `export { foo }` of a local declaration, `export {
nothing }` of an undeclared name, `import { x } from` with no path, and the suggested spellings
themselves: each re-export suggested above, kept beside its original import, runs.
