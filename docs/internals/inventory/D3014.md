### D3014 — a hole `for`-in over a list literal of the parameter at a boxed or nullable pin binds the loop variable as a bare `i32`

**closed 2026-09-28 — the witness prints `2` · was check-clean invalid wasm · clause 1 · the monomorphizer re-makes a hole-typed for-in list literal at the instance type (`monoHoleIterLitCopy`), as `monoHoleListLitCopy` already did for a binding's · 252 invalid and 16 trapping cells of a 2,880-cell hole/`<T>` grid move to `runs`, 0 lost; the LU3 grid's `S_forinlit_h` row, 115 invalid and 52 trapping cells, runs · fixture `tests/cases/generics/hole-for-in-over-parameter-literal-at-nullable-pin.vl` · filed 2026-09-28 against master `59cf3b639`**

Repro:

    function f(x) {
      for e in [x] { print(e) }
    }
    const v0: i32 | null = 2
    f(v0)
    // vl check: rc 0.  vl run: invalid module, expected i32, found (ref $type)

Want:

    2

#### Mechanism

A hole instance shares its template's expression nodes, so the literal `[x]` keeps the recorded
type `T[]` over the hole's variable, and every list classifier answers the unpinned `i32` list:
the literal builds an `i32` backing around the parameter's box. A binding escapes this because
the monomorphizer annotates it and re-makes its literal at the instance type
(`monoHoleListLitAnn`, `monoHoleListLitCopy`); a for-in iterable had no such rung. It now does
(`monoHoleIterLitCopy`). The same literal in any other expression position (`[x].length`,
`[x][0]`, `[x].filter(…)`) is still invalid, and is [D3066](D3066.md).

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `const l = [x]` then `for e in l` | prints `2` | **yes** (the literal iterable) |
| `function f<T>(x: T)` | prints `2` | **yes** (the hole) |
| a non-null `i32` pin | prints `2` | **yes** |
| a `1 \| 2 \| null` or `f64 \| null` pin | invalid wasm | no (the same defect) |
| a `string \| null` pin at `null` | wasm trap, null reference | no (the niche twin) |
| `print([x].length)` | invalid wasm | no ([D3066](D3066.md)) |
