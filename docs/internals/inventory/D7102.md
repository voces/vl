### D7102 — a written `let` of generics that a closure writes, or that is written with a lambda, is refused when a list read of it is called at one type and the `let` at another

**loud emit reject · `vl check` rc 0 · clause 2 · CAPABILITY: the same program with no closure writing `k` runs (`tests/cases/closures/hole-fn-written-let-in-list-then-rewritten-and-delivered.vl`) · found closing [D3978](D3978.md) · the same on master `6ca1ebc5c` · filed 2026-10-19 against master `6ca1ebc5c`**

Repro:

    function inner<U>(u: U) { print("I"); print(u) }
    function other<V>(v: V) { print("O"); print(v) }
    function main() {
      let k = inner
      const flip = () => {
        k = other
      }
      const fs = [k]
      k = inner
      fs[0](3)
      k(true)
    }
    main()
    // vl check: rc 0.  vl run: the reassigned function binding `k` holds functions called at more than one argument type

Want:

    I
    3
    I
    true

#### Mechanism

The let plan gives each call type of a written `let` its own slot and renames every write to
write each slot; it cannot rename a write inside a closure other than the binding's own, nor give
a write of an un-annotated lambda one instance per slot. Splitting such a binding at a list read
was check-clean invalid wasm (`expected structref, found i32`), so `fsReachKey` keeps the read
on its own slot for any binding in `fsReachOwn` — closure-written, lambda-written, or a copy of
either — and the plan refuses as master did.
