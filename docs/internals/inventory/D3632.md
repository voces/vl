### D3632 — a call through a copy of a copied closure resolves the copied name unpositioned, so a sibling block's binding picks the signature

**closed 2026-10-04 · was check-clean, then a trap (`indirect call type mismatch`) · filed and closed by lane LF against master `221c7954f`, from the #3376 review's generator · fixture `tests/cases/scope/closure-copy-chain-in-sibling-blocks.vl`**

Repro:

    function k(): i32 { 7 }
    function q(): string { "loc" }
    function host() {
      {
        const f = k
        const g = f
        print(g())
      }
      {
        const f = q
        const g = f
        print(g())
      }
    }
    host()
    {
      const f = k
      const g = f
      print(1)
    }
    // master: vl check rc 0; vl run prints 7, then traps: indirect call type mismatch

Want:

    7
    loc
    1

#### Mechanism

`calleeCloSigKeyAt` (`compiler/emit_classify.vl`) keys a call through an inferred copy of
another closure binding (`const g = f`) by chasing the source name. The chase passed the name
alone (`calleeCloSigKey(src, fnIx)`, position -1). Unpositioned, the function's two `f`s are
ambiguous and the rung declines, so the module-scope block's `f` answered, and `g()` in the
second block was lowered with `k`'s functype over a value holding `q`. The chase now resolves the source at its own read
(`identCopySourceNodeAt`), as every other rung of the ladder is positioned (D2316).

#### Ablation

| ingredient changed | outcome on master |
| --- | --- |
| the module-scope block removed | runs |
| that block binds only `g` (`const g = k; print(g())`) | runs |
| that block binds `f` and calls it (`const f = k; print(f())`) | still traps |
| that block binds `f` and copies it to `h` | still traps |

#### Grading list

The single-module witness above, and the same shape inside a block-local function's frame
(`f1_fn_body_valcall2_*` in the #3376 review generator), which this close also moved from a
trap to `runs`.
