### D1676 — a standalone `?.` has no rep for an f64 or a nullable-list leaf, and its refusal names a set two of whose members run

**closed 2026-09-06 — the witness prints `1.5` · was a loud emit reject · filed 2026-09-05
against master `a0fa9533c` · found while closing D1670, whose fix made the call-receiver
spelling reach this layer · fixture
`tests/cases/expressions/optchain-standalone-leaf-reps.vl` · matrices
`optchain-standalone-f64-leaf` / `optchain-standalone-list-leaf`**

Repro:

    type B = { y: f64 }
    function mk(): B | null { { y: 1.5 } }
    const b = mk()
    const v = b?.y
    print(v ?? 0.0)
    // was: vl check rc 0, then emitProgram: a standalone `?.` supports only i32/boolean
    // and string leaf fields. Now prints 1.5.

#### Mechanism

`emitOptMemberValue` builds the `F | null` value of a standalone chain by dispatching on the
result's rep, and it carried arms for the nested-struct niche (code 15), the boxed scalar and
value union (code 16), the `i32 | null` box and the `string | null` niche. Two rep families
were missing and both were already spoken elsewhere in the same function:

* **A wide scalar leaf rides the SAME box.** `f64 | null` and `i32 | null` are one rep with a
  different tag, and the arm read `vbHeapIdxOfKind(0)` / `scalarTagOfKind(0)` — the kind now
  comes from the leaf's own code (`optChainLeafBoxKind`: 17 → f64, 23 → i64, 24 → f32).
* **A list leaf is the wrapper's own nullable ref**, the shape the code-15 arm already
  speaks one table over. `optChainLeafRefHeap` reads the field's storage heap off the same
  table `pushFieldStorage` writes, so the value this arm builds and the slot it was read
  from cannot name different types.

**The un-annotated face needed three CLASSIFIERS, not the arm.** With the arm built, an
annotated binding ran and `const v = b?.y` refused at `bare null needs a struct-typed
context` — the checker calls the annotation redundant (it agrees about the TYPE) while the
two spellings disagree about the REP. `exprNullableList`, `exprNulScalarListKind` and
`exprNullableRefArray` each carried a `Member` arm and no `OptMember` one, and so did
`refListElemNameOfExpr` and `exprEmittedRefListSlot` — the same family D1667 named, in five
more places. A `?.` read is the `.` read with the receiver's `| null` added, so where the
`.` arm asks for the nullable field code the `?.` arm asks for the non-nullable one too.

The refusal now names only what it still refuses: a MAP or closure leaf.

#### Ablation

One row per leaf type, standalone value position, both faces, proving the VALUE:

| leaf field type | before | after |
| --- | --- | --- |
| `i32`, `boolean`, `string` | runs | runs |
| `I \| null` (nested struct), `i32 \| string` (value union) | runs | runs |
| `f64`, `i64`, `f32` | **emit refuses** | **runs, right value** |
| `i32[]`, `boolean[]`, `string[]`, `f64[]`, `i64[]`, `f32[]`, `u8[]` | **emit refuses** | **runs, right value** |
| `i32[] \| null` | **emit refuses** | **runs, right value** |
| `S[]` (ref list), annotated | **emit refuses** | **runs, right value** (pinned on D1681) |
| `S[]` (ref list), un-annotated | emit refuses | still refuses — D1681 |
| `{[string]: i32}` (map) | emit refuses | still refuses, and the sentence says so |

**The sentence was false of two members it excluded**: a nested-struct leaf and a
value-union leaf both ran while it said "only i32/boolean and string".
