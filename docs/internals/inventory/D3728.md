### D3728 — a captured `let` assigned by a lifted function nested inside another lifted function keeps its heap cell

**runs today and must keep running · open · a cost row, no wrong value: the witness prints its Want, and the cell is the cost · residue of [D3664](D3664.md): `cloUnboxPick` admits only capturers nested directly in the binding's frame · filed by lane L2 against master `687b42dbe`**

Repro:

    function f(): i32 {
      let k = 0
      const outer = (d: i32) => {
        const inner = (e: i32) => { k += e }
        inner(d)
        inner(d)
      }
      outer(2)
      outer(3)
      k
    }
    print(f())
    // `outer` and `inner` are both lifted, and `k` is still a `struct.new` cell per `f` call

Want:

    10

#### Mechanism

`cuScan` refuses a binding named at depth two or more. Both functions lift, so the value could
travel as a parameter of `outer`, be handed to `inner`, written back into `outer`'s parameter and
returned from `outer` in turn: `outer` would have to count as a writer because a function nested
in it assigns the binding, and the write-back target inside `outer` is its own capture parameter,
which `localIndexOf` already resolves.
