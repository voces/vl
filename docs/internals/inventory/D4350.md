### D4350 — a string literal passed to `Set<K>.add` is not adapted to the literal-union element, so the call refuses

**closed 2026-10-13 — the witness prints `true` · `add`'s key argument takes the expression form `set` already took (`assignableExpr`, then `nomSlotAccepts`) · fixture `tests/cases/sets/litunion-key-literal-add.vl`, matrices `set-litunion-key-literal-add{,-generic}.matrix.vl` · was loud check reject · clause 2 · filed 2026-10-13 against master `d92163e47`**

Repro:

    type K = "a" | "b"
    const s: Set<K> = Set()
    s.add("a")
    print(s.has("a"))
    // was: vl check: add: expected K, got string

Want:

    true

#### Mechanism

`bmArgPred` (`compiler/typecheck.vl`) graded a `Map.set` key (`BM_SETKEY`) by the expression form,
which takes a member literal at the literal-union key (D1748), but let a `Set.add` key
(`BM_ADDKEY`) fall to the type-only `assignable`, where the literal had already widened to
`string`. `has` and `delete` (`BM_KEYMUST`) took the expression form all along. A bound `const k: K = "a"`
passed to `s.add(k)` runs, so the set itself and its atom rep are fine: only the literal's
adaptation at this call was missing.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the alias (inline `Set<"a" \| "b">`) | still refuses | no |
| the literal argument (`s.add(k)` over `const k: K`) | runs | **yes** |
| the method (`s.has("a")` as the first literal delivery) | runs | **yes** |

#### Grading list

The inline spelling `Set<"a" | "b">`, `s.has("a")` and `s.delete("a")` as the first literal
delivery, and a `Map<K, i32>` key written by literal.
