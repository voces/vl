### D2896 — a hole function's nested lambda aliased (`d = c`) and called at another type builds invalid wasm

**closed 2026-09-27 — the filed repro prints its four lines · closed by re-spelling a call through a `const` alias chain as a call through the lambda's own binding · found by #3231's review (`a7.vl`) · the same on master `8e10ef58b` · filed 2026-09-27 against master `8e10ef58b`**

Repro:

    function mk(x) {
      const c = (y) => y
      const d = c
      print(d(1.5))
      print(c(x))
    }
    mk("s")
    mk(true)
    // master: vl check rc 0.  vl run: invalid module inside `mk`

Want:

    1.5
    s
    1.5
    true

#### Mechanism

A call through `c` is instantiated per call ([D2854](D2854.md)); a call through `d` was not,
because `d`'s initializer is a name, not a lambda, so `d(1.5)` stayed a `call_ref` at the
signature of `c`'s first instance. `monoRespellLamAlias` now follows a chain of un-annotated
`const` aliases and, where it ends at an un-annotated `const` binding of a lambda that the call
reads unshadowed, re-spells the callee as that binding. A chain through anything else — a
parameter, a narrowed binding, a `let` — is left as written. Top level too: the same program
outside a function was a loud emit reject on master and now runs.

#### Ablation

| ingredient changed | outcome on master | needed? |
| --- | --- | --- |
| no alias (`c(1.5)` directly) | still invalid | no |
| one pin (`mk("s")` only) | still invalid | no |
| a concrete `x: string` | still invalid | no |
