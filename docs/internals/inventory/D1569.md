### D1569 — an INFERRED-empty list whose element is a non-i32 SCALAR minted no wrapper/backing pair: `collectA`'s empty-literal arm rescued three REF element kinds and no scalar one

**closed 2026-09-03 — the witness runs and prints `2.5` · was a loud emit reject on a `vl
check`-clean program (`emitProgram: f64 array literal but f64 list type not collected`, plus its
`i64` and `string` twins) · clause 2, the `const xs: f64[] = []` face already running · fixed by
giving that arm the SCALAR rung its three ref siblings had (`forceScalarListRep`, off
`nodeTyArrayElemRepName`) · matrix 29 -> 42 of 42 runs, 0 SILENT · found while grading the
compiler-trap witness the D1566 agent (#2498) recorded, which is a different thing entirely**

Repro (before: `vl check` rc 0, then `Error: emit error … f64 list type not collected`; now:
prints `2.5`):

    const xs = []
    xs.push(1.5)
    print(xs[0] + 1.0)

#### Mechanism

An empty `[]` names no element, so `arrLitIsRef` / `arrLitIsStr` / `arrLitIsF64` all decline it
by construction and the literal falls to the i32-list default. `collectA`'s empty-literal arm
carries RESCUES for that — one per element kind whose row the checker pinned but the program
never spells: a registered union, a nested array, and (D1511) a shape. Every one of them is a
REF element. A NON-i32 SCALAR element has no ref row to intern, only a wrapper/backing PAIR to
force (`fa64Used` / `ia64Used` / `fa32Used` / `ba8Used` / `slUsed`+`aUsed`), and no rung forced
it — the `TypeRef` walk that does mints from an `f64[]` SPELLING, and `synthEmptyListAnn`'s
synthesized one is produced a whole pass later. `emitArr` then read the threaded kind, took its
`isF64Lit` arm, and refused at its own floor.

**THE ONE RESCUE THAT EXISTED WAS A SYNTAX TEST.** The same pass held a hand-written arm for
`<recv>.push("<string literal>")` — an `is StrLit` check on the argument NODE. It fired for
`xs.push("s")` and for nothing else: `const s = "s"` then `xs.push(s)`, `xs.push(g())` and
`xs.push("a" + "b")` are the same program with the same recorded element and all three were
`string array literal but string list type not collected`. The replacement asks the ARENA for
the element the checker recorded, so every scalar rep and every pin form (a `push`, an index
store) are one rung; the syntax test is deleted, measured subsumed rather than assumed (the
600-cell grid, the corpus and `gate.sh` all move zero cells without it).

**BOTH REPS, OFF THE BYTES.** The fixed module declares `(type $4 (array (mut f64)))` with its
`(type $5 (struct (mut (ref $4)) (mut i32) (mut i32)))` wrapper, neither of which existed
before. And the proof that the two spellings now agree is stronger than a disassembly: the
INFERRED module is **byte-identical** to the annotated `const xs: f64[] = []` module, at 2,007
bytes, for the `push` face AND the index-store face.

**THE BRIEF'S WITNESS WAS A RUNTIME TRAP, NOT A COMPILER ONE**, and that is worth recording
because the two look alike in a terminal. `const xs = []` / `xs[0] = 5` / `print(xs[0] + 1)`
stores at index 0 of a ZERO-LENGTH list: `vl run` exits 1 with `wasm trap: out of bounds array
access` and no banner, and its `const xs: i32[] = []` face does exactly the same, before and
after. A compiler trap exits **70** with `vl: the compiler itself trapped while compiling …`;
graded on a fully `--names` seed the brief's witness still names `vl!<wasm function 4>`, because
the trapping module is the PROGRAM's. The f64 and string spellings of that same shape WERE this
row's defect, at emit.

The last six rows are the mechanism. A struct element and a nested-array element already ran —
those are the two rescues this arm had — and a string LITERAL push ran through the syntax test
while the same string in a variable did not. The arithmetic, the binding form, the scope and the
operand position are all scenery: what the defect needs is an empty literal whose element the
checker pinned to a scalar the program spells nowhere.

The 600-cell creation × value × pin × read × scope × binding grid moves **102 emit rejects to 0**
— 36 to `runs` and 66 to the program's own out-of-bounds trap, which is what its annotated face
already did — with **0 `runs` → not-runs**.
