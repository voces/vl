### D14228 — a `Set()` delivered to an inline or declared union arm's field cannot be stamped with the set it is delivered to

**runs today and must keep running · filed 2026-10-26 against master `8d0974164`**

Repro:

    const v: { seen: Set<string> } | i32 = { seen: Set() }
    if v is { seen: Set<string> } {
      v.seen.add("p")
      print(v.seen.length)
    }
    type A = { seen: Set<i32> }
    type B = { n: i32 }
    const u: A | B = { seen: Set() }
    if u is A {
      u.seen.add(9)
      print(u.seen.length)
    }
    // vl run: prints 1 twice; the `Set()` builds at the key its delivery recorded

Want:

    1
    1

#### Mechanism

A `Map()` call is a fresh literal and the checker stamps it with its destination's type
(`recordRepTyAdopt` → `repStamp`), which `emitMapNew` reads through `litRepTyAt`. A `Set()`
call is not stamped. Stamping it whole, at the destination, at a fresh `mkMapTy` of the
destination's key and value, or only when its own key is a hole, each turned this program into
check-clean invalid wasm: the stamp changes the record literal's box in the union arm. Also, a
`Set()` passed to `repStampableLit` runs one more `assignableExpr` (check_assignable.vl), and
that call has side effects.

So a `Set()` whose element is still a hole records only the key it is delivered to
(`setCtorKeys`, check_fit_rules.vl `setCtorKeyNote`), and `mapCtorKeyKind` reads that key.
The pin holds that record. The row closes when a `Set()` is stamped like a `Map()` and this
program still prints `1` twice.
