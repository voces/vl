**closed 2026-09-06 — the witness prints `1` then `1` · was check-clean invalid wasm,
`the emitted module failed to validate inside \`c$1\`: type mismatch: expected i32, found f64`
· clause 1 · filed against master `c30049d6c`, found writing [D1795](D1795.md)'s fixture — the
three-frame version broke while each frame alone ran; closed against master `5ef63bb50` ·
fixture `tests/cases/generics/nested-capture-sibling-frame-names.vl`**

Repro:

    function o(n) {
      function k(x: i32) { return n }
      function use(p) { return p(1) }
      return use(k)
    }
    function c(n) {
      function k(x: i32) { return x }
      function use(p) { return p(1) }

    print(c(2.5))

#### Mechanism

**The predicted rung was the wrong one, and three measurements refuted it.** The prediction was
[D1820](D1820.md)'s ledger colliding within one program rather than across two. Instrumenting
`monoSlotOfLamNode` prints `ledger=[]` at every visit in the broken program AND in the passing
control; its `scan=-1` fall-back fires identically in the control that runs; and the witness
still fails on a seed carrying [D1820](D1820.md)'s reset. The ledger is not involved.

What decides it is the instance-origin dump — the same program, only the nested names differ:

    BROKEN   INST use origFe=5 origNode=33   (c's own use)
             INST use origFe=3 origNode=13   (o's use — the OTHER frame)
    CONTROL  INST use origFe=5 origNode=33
             INST use origFe=5 origNode=33

At the second pin the callee resolves to the sibling frame's same-named helper.
`fnIndexOfInScopeSid` walks out from the instance's own frame, that frame declares none of its
origin's nested functions, the walk reaches -1, and it falls through to the flat
first-occurrence map. The fall-through is an in-band answer with nothing marking it a guess.
A one-line control settles it: declaring the sibling frame AFTER the called one makes the
witness run, because the flat map's first occurrence then happens to be the right one.

The repair is to the chain, not to the map. `fnInstOrigin` records the slot an instance was
cloned from, and the walk continues there when `fnParent` runs out — so an instance resolves a
name in the frame its body was written in. It resets with `fnParent`, per program, since
[D1820](D1820.md) is the same column's lesson one boundary over.

**Two narrower rules were built and refused.** Consulting the flat map only for module-scope
slots turns this into `emitProgram: identifier is not a parameter, local, or global` — a
refusal the design does not owe on a legal program — and it costs [D1795](D1795.md)'s two
argument cells, moving them `traps` -> `emit refuses`. Removing the fall-through outright is
worse: the scan is gated on `nestedNameBySid`, so a purely module-scope name never enters it
and the flat map is that name's only answer, across 32 call sites in two twins. And hopping to
the origin frame at `monoInstantiate`'s callee lookup alone fixes `origFe` and still
miscompiles, because the emit-side walk is a second reader missing the same way.
