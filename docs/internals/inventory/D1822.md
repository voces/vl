#### Mechanism

**The row was filed as a prediction and the prediction was WRONG in its load-bearing half.** It
read "the list channel has no arena rung beside its name test, which is why [D1864](D1864.md)'s
close does not reach it." `narrowedRefArrayOf` has exactly such a rung — `unMemIsRefElemArray`,
one line above `nameIsRefArray`, with a comment saying the arena leg can only reject and a shape
match re-asks the name. Measured at the `.length` floor with the narrowing live:

    alias   recv=[Ident:zq4] slot=1 v=[JsonArr] ty=66 unMemAtomKind=-1 refElemArr=1
                             valueAtomKind=-1 nameIsRefArray=0 narrowedRefArrayOf=[]
                             tyToEmitName=[(boolean|f64|string|Json[]|{[string]:Json}|null)[]]

So the arena rung had already answered YES and the name test vetoed it — the same shape as
[D1864](D1864.md), not a different one.

**And the position matrix found a SECOND classifier the reading missed.** With
`narrowedRefArrayOf` rendering the row, `.length` ran and the index read `r4[0]` still refused
`map op receiver is not a map`. The route is not `emitExpr`'s `Index` arm: a module-scope
`const v = r4[0]` is classified by `letNulMapReadUnionBox` → `mapReadMvSlot`, whose D1012 guard
is `if nameIsArray(narrowVariantFor(name)) { return -1 }` — a second name test over the same
banked alias. Without it the read claims the union's MAP arm over a receiver that is a list.

Both re-ask the arena row when the name test declines. The guard above each is what makes the
render safe, and the index one bound-tests its slot: `narrowSlotTy(narrowSlotOf(name))` on an
un-narrowed name reads index `-1` and TRAPS the compiler — measured, as 14 of the 22 grid cells
turning `rc=70` in one build.

takes an alias whose target the name test cannot parse — `Json[]`, over the recursive `Json`
union — for either name test to decline.
