### D2276 — `exprArray` claimed every non-ref literal, so a global `string[]` took the i32 list's fused `.get(i) ?? d`

**runs today and must keep running — the witness prints `b`, `z`, `b` on master and on this change · the global's two reads now lower the way the local's always did (the generic nullable read and `br_on_non_null`), one fixture's bytes change · `exprArray` is now `exprListRep(e) == "list"` (D2275 moved the other five) · filed against master `ba5378dd5`**

Repro:

    const ys = ["a", "b"]
    print(ys.get(1) ?? "z")
    print(ys.get(9) ?? "z")
    function f() {
      const zs = ["a", "b"]
      print(zs.get(1) ?? "z")

#### Mechanism

`exprArray` was wide. It answered true for any array literal that is not a ref list (`!arrLitIsRef`),
so string, f64, i64, f32 and u8 literals counted. It also accepted any concat whose left side was
not a string or ref list, and any global whose initializer was such a literal: `globalIsArraySid`
asks `letIsArray`, which asks `exprArray` of the initializer. Callers that must not see those
lists ask the narrower predicates first. The `xs.get(i) ?? d` fusion in `emitCoalesceGo` does not:
it takes `exprF64Array(recv) || exprArray(recv)`. So a module-global `string[]` got the fused
read, while a local one got the generic read, because `declaredKind` names it `strlist`. As a
projection, `exprArray` claims only what `exprListRep` names the i32 list, and the global lowers
the way the local does.

#### Ablation

| receiver of `.get(i) ?? d` | master | now |
| --- | --- | --- |
| module-global `string[]` bound to a literal | fused read | generic read |
| function-local `string[]` | generic read | generic read |
| module-global `i32[]` or `f64[]` | fused read | fused read |
