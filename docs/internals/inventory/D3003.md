### D3003 — a record literal nested in a literal stored at a wider declared record reads its re-seated field at the wider type

**closed · was check-clean silently wrong, identical on master `b34730ad9` and on #3253 · a field read narrows by the receiver's CHECKED record type (`memRecvIsRecord`), not by its syntax, so any handle whose storage is a wider record narrows back · fixture `tests/cases/objects/record-literal-widened-read-any-handle.vl` · found by the #3253 review grid · filed 2026-09-28**

Repro:

    type D = { v: f64 }
    type W = { d: D }
    const x: i32 = 3
    const c: {[string]: W} = Map()
    const o = { d: { v: x } }
    c["k"] = o
    print(o.d.v / 2)
    // PRINTS 1.5

Want:

    1

#### Mechanism

The mechanism is the ROW SCAN, not the map store: removed, `o.d.v / 2` still prints `1.5` on master, because `o` takes `W` as the first record of its field names and so builds its nested literal at `D`. `memReadNarrowOp` asked for a receiver that is itself an object-literal binding; it now asks the checker's type of any receiver (recovered through the binding or field a narrowed read names, `recvCheckedTyOf`) and narrows every scalar slot wider than that type.

As filed: The map store builds `o` at `W`, so its nested literal is built at `D` and `o.d.v` loads an `f64`. The checker types `o.d.v` as `i32`, so `/ 2` is an integer division, but the read classifies as `f64` and divides as one. #3253's read narrowing (`memReadNarrowOp`) takes only a receiver that is itself an object-literal binding, and `o.d` is a field read.
