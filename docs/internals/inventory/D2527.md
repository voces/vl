### D2527 — a written type argument naming a type of the calling module was not renamed by the module merge, so `mk<T>()` read "unknown type 'T'"

**closed 2026-09-25 — the filed repro RUNS and prints `4` · was a loud check reject of a type-valid program · clause 2 · found building `std:idtable` (collections Q4) · filed 2026-09-25 against master `ca544493e` · fixture `tests/cases/modules/type-args-name-importer-type/`**

Repro:

    // file: lib.vl
    export function mk<V>(): V[] {
      const s: V[] = []
      return s
    }
    // file: entry.vl
    import { mk } from "./lib"
    type T = { w: i32 }
    const t = mk<T>()
    t.push({ w: 4 })
    print(t[0].w)

#### Mechanism

When a program has more than one module, `driver.vl`'s merge renames each module's top-level
names to mangled ones, and rewrites every annotation (`modRwType`) to match. Explicit type
arguments (#3155) live in a side table keyed by the call node (`callTyArgsOf`), which
`modRwExpr`'s `Call` arm never visited, so `T` kept its source spelling while the declaration
became `T$m0`, and the checker's `resolveCallTyArgs` found no such type. An imported type
(`mk<Pt>()`) failed the same way, since its local name is also rewritten to the exporter's; only a
primitive (`mk<i32>()`), which no merge renames, resolved. The fix rewrites each type-argument
node as an annotation in the `Call` arm.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the second module (both in one file) | ran before the fix | **yes** |
| a primitive type argument instead of a declared type (`mk<i32>()`) | ran before the fix | **yes** |
| a type imported from `lib.vl` instead of one declared here (`mk<Pt>()`) | the same refusal | no |
| the generic being imported (a local `mk` in a two-module program) | the same refusal | no |
