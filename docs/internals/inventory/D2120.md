### D2120 — a string literal behind an un-annotated `const` compares as a runtime string in a getter

**closed 2026-09-23 by D2157 — the witness prints `true`: the `const` now has the literal's type, so the compare costs the literal's 2 steps · was a loud check reject, clause 2 · residue of D2062's close · filed 2026-09-23 against master `7cb12a61d`**

Repro:

    const K = "zz"
    type N = new { name: string }
    get isK(self: N): boolean { self.name == K }
    const n: N = { name: "zz" }
    print(n.isK)
    // prints true

#### Mechanism

D2062's close admits a compare against a string LITERAL, read as either a quoted literal node or
an operand whose type is one string literal (`gwStrLitLenOf`). An un-annotated `const K = "zz"`
widens to `string`, so the operand is neither, and the compare is refused as two runtime
strings. A local `const k = "z"` inside the getter behaves the same. Admitting it means reading
the binding's initializer: a local through the body walk's own locals, a module `const` through
its declaration.

#### Grading list

The module `const` above; a getter-local `const k = "z"`; the annotated `const K: "zz"`, which
must stay admitted; a module `let` holding a literal, which must stay refused (mutable state).
All four graded as listed on the close: the two `const` spellings and the annotated one run, and
the module `let` is refused for reading mutable state and for comparing a runtime string.
