### D1587 — `x as u8` refused a cast that is real: `u8` names a byte-sized RANGE, so the cast is the i64→i32 narrowing with 0..255 as its domain

**closed 2026-09-04 · was a loud check reject naming the store (D1583's message, which this supersedes) · `checkCastNode` admits `u8` after resolution fails and types the result `i32`; `numCastCanFail` gains four pairs; `emitNumExactTest` gains the 0..255 bounds · 60 of 60 trio-grid cells behave as the ruling states · 54 of 54 `as! u8` and 42 of 42 `as? u8` position-matrix cells move `check refuses` → `RUNS`, 0 silent · ZERO corpus cells · owner ruling 2026-09-04, "`x as u8` is fine, but it should follow the same logic as downscaling i64 to i32" · filed 2026-09-04 against master `5328a781`**

Repro (prints `200`, then `null`):

    const bytes: u8[] = []
    const v = 200
    bytes.push(v as! u8)
    print(bytes[0])
    const w = 300
    print(w as? u8)
    // was: [ERROR]: `u8` is a storage type, not a value type — a `u8[]` stores the low
    //      byte of an `i32`; push the `i32` directly (300 stores as 44), or `x & 0xff`

#### Mechanism

D1583 read `x as u8` as a request for a VALUE of type `u8` and answered, correctly, that
there is none: wasm has no 8-bit value type, `primTyOfName` deliberately withholds `u8`,
and `tsLeafTy` routes it to `storageTyLeafFail`. What that reading missed is that the
author is not asking for a `u8` value — they are asking for the CHECK the store does not
do. `bytes.push(v)` keeps the low byte and never complains; `bytes.push(v as! u8)` says
the value was supposed to be a byte already.

So `u8` is admitted as a cast target the same way it is admitted as an array ELEMENT — by
SPELLING, and only after `nameToTyAt` has failed, so a program declaring its own `type u8`
resolves first and is unaffected. The cast's result TYPE is `i32`; what the `u8` spelling
carries is the exactness DOMAIN. Those are two different names for one cast and the fix
keeps them apart (`numCastDomainName` / `asExprNumCastDomain`): the REP target decides the
conversion opcode and the `i32 | null` box row `as?` registers, the DOMAIN decides the
range test and the `as!` message. Collapsing them either loses the range or registers a
`u8|null` box that nothing builds.

Three sites had to learn the difference. The canon pass rewrites `n.asTy` to the
primitive spelling of the node's recorded type, which for a u8 cast is `i32` — it would
have erased the one string still carrying the domain, so it now leaves `u8` alone. The
emitter's PEEPHOLE lets `trunc(d) as! i32` skip the exactness test because
`i32.trunc_f64_s` enforces i32's range on its own, an argument that is false at 0..255, so
the peephole declines the `u8` domain. And a UNION operand is refused rather than routed
to the arm ladder, which would have handed back the arm's own `i32` with no range test at
all — `x as! u8` over an `i32 | null` holding 300 answering 300.

An `i32` SOURCE is new to this family (no other cast pair is integer-to-integer at the
same width) and rides the i64 path: `i64.extend_i32_s` is exact for every i32, the range
test is the same two compares, and `i32.wrap_i64` brings the proven byte back — one
instruction against a fourth scratch slot in every function of every module that casts.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the `u8[]` in the program entirely (`const b = v as? u8`) | the same `i32 \| null` | no — the cast stands alone |
| the suffix (`v as u8` at module scope) | `` `as u8` propagates null out of the enclosing function `` | no — the trio's own rule, `u8` quoted |
| `u8` replaced by `Bogus` | `` unknown type `Bogus` in `as` cast ``, unchanged | **yes** — the arm is name-gated |
| the operand's numeric-ness (`"x" as! u8`) | `` `as` supports numeric conversions only `` | **yes** — 0..255 is a range of numbers |
| the operand's non-union-ness (`x: i32 \| null`) | `` `as u8` narrows a number into 0..255, and i32 \| null is a union `` | **yes** — the arm ladder would skip the range test |
| the ANNOTATION position (`function f(b: u8)`) | `storageTyLeafFail`'s sentence, unchanged | **yes** — still no `u8` value |
| the cast (`bytes.push(v)` over 300) | runs, stores 44 | **yes** — the store's truncation is UNCHANGED by this ruling |

#### Grading list

* **The 60-cell trio grid** — {i32, i64, f64, f32} × {`as`, `as?`, `as!`} × {in range, out
  of range, fractional} × {function scope, module scope}. In range: all three spellings
  give the value. Out of range or fractional: `as?` and a bare `as` give `null`, `as!`
  traps with `as! u8 at L:C: not exact`. At MODULE scope the bare `as` is the trio's own
  refusal (`propagates null out of the enclosing function`), the other two behave as in a
  function. Every cell as stated.
* **`3.9 as! u8` traps and `200.0 as! u8` is 200** — the integrality half of the test is
  the same one `as! i32` applies, so a byte-sized fraction is still not exact.
* **Two position matrices**, `as-bang-u8-value` (54 of 54) and `as-q-u8-value` (42 of 42,
  12 discrimination positions skipped — `v is i32` over an `i32 | null` asks the nullable
  narrowing's question, not this cast's). Every cell `check refuses` → `RUNS`, 0 SILENT.
* **The store is unchanged and that is DELIBERATE**: `bytes.push(300)` still keeps the low
  byte (44), `bytes.push(-1)` still reads back 255, and whether the implicit `i32 → u8[]`
  store should REQUIRE the cast is not decided here. Both facts are now stated
  consumer-facing, next to each other, in `docs/guide/collections-design.md` §"What you
  write TODAY".
