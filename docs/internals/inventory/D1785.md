### D1785 — a negation RETURN annotation names no rep either, so an f64-returning function declared `: !string` is check-clean invalid wasm; the binding at the other end is transparent

**check-clean invalid wasm — `type mismatch` inside the function, `vl check` rc 0 · clause 1 ·
filed 2026-09-06 against master `57c8ae423` as the measured residue of [D1784](D1784.md),
which made the BINDING transparent and left the RETURN opaque · both spellings**

Repro:

    type N = !string
    function f(): N { return 1.5 }
    const v: N = f()
    print(v)
    // vl check rc 0; vl run -> the emitted module failed to validate inside `f`

#### Mechanism

Not probed beyond the ablation. [D1784](D1784.md) routed the BINDING classifiers through
`letRepAnnOf`, the one home for "the annotation node that names a rep", and a negation names
none. The function's RESULT valtype is decided by a different ladder with the same shape —
`retResultVKind` opens `if fn.fnRet >= 0 { return vtKindOfType(fn.fnRet) }` — so the result
byte is written from the negation while the body returns an f64. The binding `const v: N =
f()` at the other end is already transparent, which is why the failure is inside `f` and not
at the call.

The reason it is filed rather than folded into [D1784](D1784.md): `retResultVKind`'s own
comment says it reads "the same ladder `emitOneFuncType` writes the result byte from", so the
result position has more than one reader to move together, and the binding family's census
(`scripts/ann-shortcircuit-census.py`) does not cover it — a return annotation is not a
binding classifier.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |

| the alias, for an inline `function f(): !string` | same outcome | no |
| the binding at the call site (`print(f())`) | same outcome | no — the failure is inside `f` |
