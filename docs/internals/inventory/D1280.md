### D1280 — a `.pop()` INLINE in a `.push` ARGUMENT clobbers the push: the i32 face TRAPS, the string face silently drops the element

**closed by [D1592](D1592.md) · was: loads then traps (`wasm trap: out of bounds array
access`) · check rc 0 · clause 1 · found 2026-09-02 by the `string[]`-pop position matrix
built for [D1212](D1212.md), and PRE-EXISTING: identical on the pre-change seed**

Repro (prints `2`):

    const src: i32[] = [1, 2]
    const xs: i32[] = []
    xs.push(src.pop() ?? 0)
    print(xs[0])

* **HOISTING THE POP INTO A BINDING IS THE ONE-LINE CONTROL.** `const p = src.pop() ?? 0` on
  its own line, then `xs.push(p)`, prints `2` — the value is right and the push lands. Only
  the INLINE spelling fails, which is what makes this the shared list-op scratch frame and not
  the pop or the push alone.

* **THE ABLATION IS THE ARGUMENT, one ingredient at a time, everything else held.** All four
  of `xs.push(src[0])`, `xs.push(src.length)`, `xs.push(src.slice(0, 1).length)` and
  `xs.push(mk())` for a declared `function mk(): i32` run and land the element; only a
  `.pop()` — the list op that MUTATES its receiver and resolves it through
  `listOpRecvLocal`'s scratch frame — reaches the defect.

* **THE SECOND FACE IS A SILENTLY WRONG ANSWER, not a trap**, and it is the same ablation:

      const src: string[] = ["a", "b"]
      const xs: (string | null)[] = []
      xs.push(src.pop())
      print(xs.length)

  printed `0`. The push did nothing at all, `vl check` was rc 0 and the program exited 0; the
  hoisted spelling printed `1`. Both print `1` now.

* **IT IS NOT [D1212](D1212.md)'s** — the trap is identical on the pre-change seed, before the
  empty-pop guard existed, and the receiver here is never empty.

* **THE MECHANISM, NAMED WHEN [D1592](D1592.md) REACHED IT WITH A SECOND OP.** A list op whose
  receiver is not a bare LOCAL parks the wrapper ref in the frame's ONE `recvRef` slot, so the
  inner op overwrites the outer's receiver and the append lands on the INNER list — which is
  why hoisting the pop is the control and why only a `listOpRecvLocal` argument reaches it.
  `emitPush` now stages its receiver AFTER the value when `exprStagesListRecv` says the value
  stages one; source order is unchanged for every program that was already right. Both faces
  above run.
