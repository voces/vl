### D14757 — an un-annotated binding of a join of literal-bound consts is typed by their literal set but stored as a string

**closed · runs, prints `x`, `y`, and `M` is stored as the set's i32 atom · was a refutation pin for step 5's string-to-atom hook · closed by the column-G1 lane: an un-annotated `const` whose initializer's contextual type is a join of widening string literals stores that set's atom (`constBindsLitSet`, check_leaf_steps.vl, read by `bindCellGo`, `anyLitUnionUsed` and `litAtomWidenTexts`), and a `let` copying it stays the widened string · fixture `literal-unions/const-literal-join-stored-as-its-set.vl` · filed 2026-11-01 against master `8f56525b`**

Repro:

    const A = "x"
    const B = "y"
    function main(c: boolean) {
      const M = if c { A } else { B }
      print(M)
    }
    main(true)
    main(false)

Want:

    x
    y

#### Mechanism

The join's value leaves record the join's type, `"x" | "y"`, as their contextual type, and
`repOfTy` of that set is the i32 atom. The binding `M` is stored as a string (`(local $1 (ref
$0))`), so the arms must lower as strings, which today they do only because the delivery flag
is off. A reader that asks the contextual type turns each arm into an atom. The storage is the wrong
side (coordinator ruling, 2026-11-01): `const A = "x"` keeps its literal type, the join is the
set `"x" | "y"`, and the binding is to be stored as that set's atom.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the const reads (`if c { "x" } else { "y" }`) | the leaves' record widens to `string`, agreeing with the storage | **yes** |
| the binding's absence of annotation (`const M: "x" \| "y"`) | `M` is stored as the atom, agreeing with the type | **yes** |
