### D1693 — the pin re-asks the index / member / operator floor against the SUBSTITUTED parameter type, so a null-narrowing inside the body is invisible and the pin refuses what the direct spelling runs

**closed 2026-09-06 — every null-test spelling mints the hole's non-null face, so the pin
re-asks its floors against the narrowed type · filed against master `ad287fae7` · rides D691's
deferred constraint tables, but is NOT D691's family — its soundness argument fails here ·
residues D1698, D1699 · 0 corpus cells**

Repro:

    type A = { r: i32 }
    function ns1(): A[] | null { return [{ r: 4 }] }
    function take(a) {
      const l = a.xs
      if l != null { print(l[0].r) } else { print(0) }
    }
    take({ xs: ns1() })
    // prints 4 since the close; before it, `vl check` rc 1,
    // cannot index non-array A[] | null (the body of `take` at the call's argument types)

The DIRECT spelling of the same body — `const a = { xs: ns1() }` and the same two lines at
module scope — runs and prints `4`. So does the annotated parameter (`a: { xs: A[] | null }`).

#### Mechanism

**D691 is the machinery and its own witness still reproduces as filed**
(`function g<T>(x: T) { print(x.length) }` at `g(true)` → `member access '.length' on
non-object boolean (the body of 'g' at the call's argument types)`, re-run on
`83a3f2315`). What D691 built is a deferred constraint recorded when the receiver's type
carries a hole and re-asked at the pin against the substituted type, so a generic body meets
the same floor the direct spelling meets.

**Its soundness argument does not hold for this witness, and that is the whole row.** D691's
close rests on a measurement — "THE DIRECT SPELLING WAS ALREADY A POSITIONED REFUSAL AT EVERY
ONE OF THE SEVENTEEN" — which is what made reporting at the pin a lost refusal rather than a
lost capability. Here the direct spelling RUNS. The floor is asked about `a.xs`'s own recorded
type, `A[] | null`, while the body's flow analysis has already narrowed the receiver at the
read; the pin has no narrowing state, so it refuses a legal program.

The `??` spelling is the sharpest form: `const l = a.xs ?? []` gives `l` the type `A[]`, and
the pin still says `cannot index non-array A[] | null`. The sentence names a type the receiver
does not have at the read.

**And it is not the index floor alone.** Three floors lose the same narrowing, each with a
running direct control:

| body | pin's sentence | direct spelling |
| --- | --- | --- |
| `if l != null { print(l[0].r) }` | `cannot index non-array A[] \| null` | runs `4` |
| `if l != null { print(l.length) }` | `member access '.length' on non-object A[] \| null` | runs `1` |
| `if a != null { print(a + 1) }` over `i32 \| null` | `operator '+' is not defined for i32 \| null and i32 (the body of 'take' applies '+' to this argument)` | runs `5` |
| `if l != null { print(l[0]) }` over `string[] \| null` | `cannot index non-array string[] \| null` | runs `hi` |

A nullable STRUCT field read after the same narrowing (`if s != null { print(s.r) }` over
`A | null`) RUNS through the pin, so the member floor loses the narrowing for `.length` on a
nullable list and not for a field read on a nullable struct — the split is worth an ablation
before a fix picks a rung.

**The refusal's scope is honest about the UN-narrowed case**, which is why this is a narrowing
loss and not a bad message: `const l = ns1()` then `print(l[0].r)` refuses directly with
`cannot index non-array A[] | null`, and the same un-narrowed body through the parameter
refuses at the pin, correctly.
