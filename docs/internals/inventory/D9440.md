### D9440 — an un-annotated `Map()` whose one slot holds two different generic functions, called at two types, has no map value type

**loud emit reject · `vl check` rc 0 · `indexed-assignment target is not an array` · clause 2 · narrowed 2026-10-21 by lane-D9440: the same generic stored through the parameter now runs (fixture `closures/hole-fn-generic-map-stored-through-parameter.vl`, matrix `fn-value-generic-map-handed-open` 0 → 11 of 46) · found closing [D9310](D9310.md) · present on master `af839a093` · filed 2026-10-21 against master `af839a093`**

    function id<T>(x: T): T { x }

Want:

    id2

#### Mechanism

The read devirtualisation that closed D9310 (`monoFlowReads`, emit_mono.vl) rewrites a call
through a map slot to the name of the generic the slot holds, and only when every value
stored into the map, through the caller's own writes, its aliases and the stores of the
un-annotated functions it is handed to (`monoFlowMapVals`, `monoFlowMapHandOn`), names that
one generic. Here the slot holds `id` and `id2`, so no one name serves; the plan declines,
the slot is typed from its call pins (`monoStoredSlotFnTy`), which with two pins is -1, and
`fill`'s parameter is left with no map type, so its store refuses as a non-array target.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the second call's type (`r.f("s")`) | runs, `id2` and `2` | **yes** |
| `id2` in `fill` (stores `id`) | runs, `2` and `s` | **yes** |
| the parameter (`m["k"] = { f: id2 }` stored directly) | refuses, `unsupported map value type` | no |
| the record (`m["k"] = id`, `m["j"] = id2`, `r(2)`, `r("s")`) | refuses, `unsupported map value type` | no |
| the map (`[id, id2]`, `xs[0](2)`, `xs[1]("s")`) | refuses, `a list holding a generic function is called through its elements at more than one type` | no |

#### Grading list

The direct-store and two-key spellings above, and the list spelling `[id, id2]`, which
refuses with the list message.
