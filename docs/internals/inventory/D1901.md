### D1901 — a `return` inside a bare `{ … }` block is `expected i32, got void` at the ANNOTATED face, while the un-annotated face and the `if true` twin both run

**closed — `isStmtNode` gains the `Block` arm its `IfStmt` arm already had, so a bare block is a statement position rather than a value one · was a loud check reject at the annotated face only · found by the bare-block census, `scripts/block-census.py` · filed and closed 2026-09-07 against master `b803933d1`**

Repro (runs, prints `5`):

    function a2(): i32 {
      {
        return 5
      }
    }
    print(a2())

#### Mechanism

`isStmtNode` (`typecheck.vl`) answers "is this node a statement rather than a value-producing
expression", and the function-body tail walk reads it: a body whose last node is a statement is
genuinely void, one whose last node is a value has a value-return position. Its ladder named
`LetDecl`, `IfStmt`, `WhileStmt`, `BreakStmt`, `ContinueStmt`, `RetStmt`, `ForRange`, `ForIn`,
`TypeDecl` and `UnionDecl` — and fell through to `false` for a bare `Block`. So a body ending in
one was read as a VALUE position, the block's own type is void, and the declared `i32` did not
match it.

`drwBareBlock` (D1253) rewrites a bare `{ … }` into `if true { … }` before emission, and
`isStmtNode` answers TRUE for the `IfStmt` that produces — so the two spellings of one program
disagreed at the checker and agreed at the emitter. The arm makes the block answer as the `if`
already did.

**A bare block whose tail is a VALUE is a separate question and is NOT closed here.**
`function k() { { 5 } }` is void at both seeds while `function k2() { if true { 5 } }` yields
`5`, so the two spellings still differ for the value-block form. That is a language-design
question — whether a bare block is an expression at all, which the parser's `looksLikeObject`
already has an opinion about — and it is reported rather than decided.
