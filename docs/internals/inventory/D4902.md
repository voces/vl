### D4902 — a string-literal-union list literal delivered into `f64[] | K[]` is built as the numeric arm

**closed 2026-10-15 — now prints `1` · was check-clean invalid wasm, clause 1 · the union coerce classed the atom list as `i32[]` and, with no `i32[]` arm, widened it to the `f64[]` / `i64[]` arm; an atom list now keeps its own arm · pre-existing on master; the annotation names both arms · found closing [D4896](D4896.md) · filed 2026-10-15 against master `abb7359ea` · pin: `tests/cases/unions/atom-list-literal-into-numeric-list-union.vl`**

Repro:

    type K = "x" | "y"
    const a: f64[] | K[] = ["x"]
    print(1)
    // PRINTS 1 (was: constant expression required: non-constant operator: visit_f64_convert_i32_s)

Want:

    1

#### Mechanism

A string literal union is an atom held as an `i32` code, so the value ladder in
`emitUnionCoerceUnder` (`compiler/wasmEmit.vl`) classes `["x"]` as `i32[]` (kind 7). The
widening step that follows asks whether the union has an `i32[]` arm; `unionHasAtomTy` matches
only a primitive `i32` element, so a `K[]` arm does not count, and the step re-built the list as
the `i64[]` / `f64[]` / `f32[]` / `u8[]` arm, converting each atom id. At module scope that is a
non-constant initialiser; inside a function the box held the wrong list (`expected i32, found
(ref $type)`, exit 70). The `K[]` arm's own tag is kind 7 already (`unMemAtomKind` reads a
literal-union element as an `i32` leaf), so the fix is to not widen: an atom list
(`exprIsAtomList`, `compiler/emit_classify.vl` — typed `K[]` or `(K | null)[]`, or a literal
whose first element is an atom) is its own arm, as a boolean list is (D2796).

The pin covers the module binding, a return, an argument (and a `[1.5]` beside it), a record
field, reassignment, the arms reversed, a `(K | null)[]` arm, an `i64[]` arm, a `const k: K[]`
delivered by name (silently wrong before: `is K[]` answered false), a nullable union, and an
integer literal still widening to `f64[]`.
