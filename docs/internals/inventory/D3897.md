### D3897 — a hole lambda stored by `.set` into a map, and also called directly at another type, is refused where a list store of it runs

**closed 2026-10-09 by lane SC, with D3881 · runs · was a loud check reject, a valid program refused (clause 2) · found in review of #3471 · filed 2026-10-09 against master `995c7d82e` · pins: `tests/cases/closures/hole-lambda-set-into-map-then-called-directly.vl`, `tests/cases/closures/hole-lambda-in-list-and-map-and-called-directly.vl`**

Repro:

    const tw = (y) => y + y
    const ms: {[string]: (y: i32) => i32} = Map()
    ms.set("a", tw)
    print(tw("s"))
    const g = ms.get("a")
    if g != null { print(g(3)) }
    // vl check: set: expected (i32) => i32, got (string) => string (the body of `tw` …)

Want:

    ss
    6

#### Mechanism

`.set` checked its value through `bmArgOk`. That compares the lambda's type, as the direct call
pinned it (`(string) => string`), against the slot, a refusal that names a mechanism and not a
contract. `xs.push(tw)` and `m[k] = tw` instead ask whether the lambda's body can take the slot's
type (`assignableExpr`), and the monomorphizer then gives it an instance at each signature.
Closed by giving `.set` the same test, with D3881's delivery minting the instance.
