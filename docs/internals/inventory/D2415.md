### D2415 — a module-scope block's closure that shadows a module function is typed as the module function inside its own block

**closed 2026-09-25 · was check-clean invalid wasm · clause 1 · found grading D2384's module-scope position · filed 2026-09-25 against master `a277bf7b0`**

Repro:

    function w(): string { return "top" }
    if true { const w = (): i64 => { return 5 as i64 }
      const r = w()
      print(r + (2 as i64)) }
    print(w())
    // vl check: rc 0.  vl run (before the close): invalid module, inside the module's
    // top-level code: "type mismatch: expected (ref $type), found i64".  Now prints `7`, `top`.

#### Mechanism

`fnIndexOfInScopeAt` (`emit_classify.vl`), the positional answer to "does this name denote a
named function here", asked only the FUNCTION frame chain whether a binding shadows the name.
The start function has no frame, and a module-scope block's `const` lives in the module-local
table (`moduleLocalLetOf*`), which it never read, so inside the block `w()` resolved to the
module function: `fnRetStringSid` typed the call `string` and `r`'s cell took the string rep.
The close adds `moduleBlockShadowsAt`, asked at the outermost enclosing frame's own
declaration (so a closure written in the block sees it too), and a covering reader
`moduleLocalLetCoversAt` (`emit_base.vl`), because `moduleLocalLetOfAt` hands back a name's
sole binding without testing that it covers the position.
