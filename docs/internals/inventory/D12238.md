### D12238 — a lambda written into a list element holding a generic, called at a type it refuses from inside a generic body, still passes the checker

**loud emit reject · `vl check` rc 0 · `emitProgram: a lambda written into an element or field holding a generic function cannot take the type the calls through it give it — annotate its parameters` · clause 2 · DESIGN: the same lambda in a `let` inside the generic body is refused at check (`argument of type i32 flows into `l` expecting string`), and the top-level call is refused since [D12217](D12217.md) · emit_mono.vl `monoPinWrittenLam` · found closing D12217 · filed 2026-10-24 against master `84b98d149`**

Repro:

    function pick<A, B>(a: A, b: B): A { a }
    const fs = [pick]
    fs[0] = (x, y: string) => x
    function g<T>(v: T): T { fs[0](v, v) }
    print(g(1))

#### Mechanism

The hole-slot judge (`holeSlotFixedJudge`, check_relate_core.vl) judges a call through the
written element at the call's argument types. Inside `g` those types are `T`, a type parameter,
and the judge skips a parameter type that carries a type variable, since only an instance knows
it. The instance `g<i32>` calls the element at `(i32, i32)` while the lambda takes `string`, and
only the monomorphizer sees that instance. The close is to judge the call per instance, or to
refuse a type-variable argument against an annotated parameter it cannot always fit.
