### D16801 — the place classes share a non-generic function's returned record between its call sites, so each binding of it is delivered every binding's writes

**runs today and must keep running · refutation pin (slot store, D16768) · filed 2026-11-16 against master `a9ae9324`**

Repro:

    function id2(a) { return a }
    function id3(a) { return a }
    function id4(a) { return a }
    function mkD() { return { f: id2 } }
    const rd = mkD()
    rd.f = id3
    const sd = mkD()
    sd.f = id4
    print(rd.f(6))
    print(sd.f(6.5))
    // vl run: 6, then 6.5.

Want:

    6
    6.5

#### Mechanism

`mkD` returns one record literal, and the place classes give that literal one place, unioned into
every binding of a call's result. So `rd.f` and `sd.f` are one class: each is delivered `i32` and
`f64`. The delivery walk keeps the two bindings apart (`rd.f` at `i32`, `sd.f` at `f64`). The class
answer is a superset of what each binding holds; with the class-reading part D readers the module
differs from master's and the output and size do not
(`tests/cases/closures/fn-record-returned-to-two-bindings-one-written.vl`).

The coordinator's ruling (2026-11-16): the slot store stays context-insensitive, so this is a
graded, named mover, not an engine change. This row pins the program's output: a later change that
turns the shared class into boxing or a refusal fails it.
