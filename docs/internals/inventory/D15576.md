### D15576 — [CLOSED 2026-11-09] a hole parameter handed a generic, passed on to a generic's function parameter at one type and called directly at another, is typed at the first

**closed 2026-11-09, runs and prints `2` then `2` · was loud check reject, clause 2, `argument 1: expected i32, got string` · found closing [D10382](D10382.md) · filed 2026-11-08 against master `4a1d010d` · closed by leaving the hole unsolved when a direct call of it takes an argument the flow's function type does not: the probe records each call through a hole with its arguments' types (`holeCallName`, check_calls.vl) and the solve reads them beside `holeFlowsToTwoFns` (`holeCalledOtherwise`, check_fn_decl.vl) · fixture `closures/hole-param-passed-on-at-one-type-called-directly-at-another.vl`**

Repro:

    function id<T>(x: T): T { x }
    function run<U>(f: (x: U) => U, u: U): U { f(u) }
    function take(a) {
      print(run(a, 2))
      print(a("ab").length)
    }
    take(id)
    // vl check: argument 1: expected i32, got string

Want:

    2
    2

#### Mechanism

The parameter solve (`solveUnannotParams`, check_fn_decl.vl) takes the one function type the hole
flows into, `(i32) => i32`. D10382's rule leaves a hole unsolved only when it flows into two
different function types, and a direct call records no flow, so the direct call at `string` is
checked against the solved type.
