### D3893 — a nested generic called through a lambda parameter's hole with a value of the enclosing `T` is not checked at the enclosing pin

**closed 2026-10-09 by lane SC · now a loud check reject · was check-clean silently wrong · found in review of #3468 (`rv3468c-witnesses/a03u.vl`) · filed 2026-10-09 against master `c6ac0a1d2` · pins: `tests/cases/generics/error-hole-lambda-forwards-outer-value-to-nested-generic.vl` and four siblings, `tests/cases/generics/hole-lambda-forwards-outer-value-runs.vl`**

Repro:

    function a<T>(x: T) {
      function b<U>(y: U) { const n: i32 = y; print(n + 1) }
      const g = (q) => b(q)
      g(x)
    }
    a(true)
    // vl check: rc 0.  vl run: prints 2

Want:

    vl check: cannot assign boolean to 'n' of type i32

#### Mechanism

`b(q)` binds `U` to the lambda parameter's hole, and that constraint is re-recorded with the hole
under `a`. `g(x)` then binds the hole to `a`'s `T`, but a call that names no declaration re-recorded
nothing, so `a(true)` saw only the hole and left it undecided. A declared generic called the same
way (`b` at top level) had the same gap. Closed by a fourth substitution mode, `SUBST_HOLES`: a call
whose bindings are all inference holes, one bound to a type still holding a type variable, binds
the holes alone and re-records what it leaves undecided under the enclosing owner. A hole bound to
a concrete type re-records nothing, so a hole lambda called at several types per call is untouched.
