### D2833 — a generic join of two list types that a pin keeps apart is refused where no instance builds it as their union: an `is` operand, a list or record literal

**loud check reject · clause 2 · the concrete spelling runs · 114 cells of the D2832 grid (`uj/g1`: `is_inline`, `elem`, `field_is`, `nested_is`, and the `ct`-order bindings of a number or boolean list), 26 of which ran on master only because the arm that ran matched the template's one-list type · filed 2026-09-27 against master `0eae57b89`, found closing D2832**

Repro:

    function no(): boolean { false }
    function f<T>(xs: T[], ys: string[]) {
      if (if no() { xs } else { ys }) is string[] { print(1) } else { print(2) }
    }
    f([2.5], ["a", "b"])
    // vl check: rc 1 — at the call's argument types, the branches of an `if` or `match` in the
    // body of `f` join f64[] and string[]: no one list holds it where its value goes

#### Mechanism

D2832's close builds an apart join as the union box only where it is bound, assigned, passed,
returned or discarded (`tpIfMarkOk`), and refuses it at the call anywhere else. Every other
consumer lowers from the template's recorded one-list type, so on master these positions were
invalid wasm, or answered by that type whatever arm ran: this program printed `2`, and with
`xs` and `ys` swapped still `1`. Building them needs the instance to record the pinned union on
the join itself (an `is` operand, a list element, a record field, a nested arm), or to push the
`is` into the arms. A binding whose concrete list of numbers or booleans absorbed the
parameter's keeps the concrete type (a pin may store the two alike or widen one into the other),
so at a pin that keeps them apart its reads are refused by the re-check's type comparison.
