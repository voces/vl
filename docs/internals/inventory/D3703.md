### D3703 — `is` with an `f64` receiver against an integer literal compares at `i32`, and against an integer literal union folds to `false`

**check-clean invalid wasm · clause 1 · found grading [D3658](D3658.md)'s receivers · the same on master `111064dda` · filed 2026-10-05 against master `111064dda` · needs a ruling on the answer**

Repro:

    const e: f64 = 2.0
    print(e is 2)
    // vl check: rc 0.  vl run: invalid module, type mismatch (an `i32.eq` over an `f64`)

#### Mechanism

`emitNumLitEq` (wasmEmit.vl) picks the compare's width from the lexeme and asks only whether the
receiver is `i64`; an `f64` receiver against an integer lexeme gets `i32.const` and `i32.eq`. The
union spelling (`type U = 2 | 3`, or `e is 2 | 3`) never reaches it: `isNumRecvBaseName` gives
`f64` against the union's `i32` base, so the arm declines and `monoStaticIsResult`'s name fold
prints `false` without reading `e`. The two spellings of one question disagree.

The answer is a language question, not settled here. The checker refuses a float literal as a
type because float equality is not set membership (`-0.0 == 0.0`, NaN), and the same objection
applies to asking whether an `f64` is a member of an integer literal set, and the `f32` receiver
already refuses (below). Recommendation: refuse `is` of an `f64` receiver against an integer
literal or literal union at check time as the `f32` receiver is, naming `e == 2.0`, rather than
compare by `f64.eq`; the alternative is to compare by value, which makes `-0.0 is 0` true.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `const e: i64 = 2` | prints `true` (since D3658) | **yes** (an `f64` receiver) |
| `print(e is 2 \| 3)` | prints `false` | no (another wrong answer) |
| `const e: f32 = 2.0` | check reject, `` `is` check type '2' can never match a value of type f32 `` | **yes** (`f64`, not `f32`) |
