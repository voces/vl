### D2766 — a generic function whose returns join two list types at a pin is typed as one list at the call

**now a loud emit reject — was check-clean invalid wasm on master `876559d2f` · the #3207 review · filed 2026-09-26 against master `876559d2f`**

Repro:

    function h<T>(c: boolean, t: T) {
      if c { return [t] }
      [1]
    }
    const q = h(true, "s")
    print(q.length)

#### Mechanism

The checker types `h`'s result as `T[]`, so the call is `string[]`. At the pin `T := string`,
though, the returns join to `string[] | i32[]`, which is how the same function with `t: string`
spelled out is typed. #3207 builds the instance's result as that union.

It then refuses some uses that need one list, with the checker's sentence (`field 'length' is
not on every member of …`, `cannot index non-array …`). It does so only where it can SEE the
call: `.length` and an index on the call, or on an un-annotated binding of it, and the call or
binding passed to a generic `T[]` parameter ([D2772](D2772.md)). For a string pin, a discard,
an `is` test, a union annotation and a union parameter build and give the right values.

That is narrower than what the checker would refuse. Any other route to a one-list reader is
still invalid wasm ([D2783](D2783.md)): an alias, `for`, a `string[]` argument, binding or
return, a field, `push`, and so on. A record pin is invalid wasm inside the function whatever
the use ([D2782](D2782.md)). A nested generic's union beside a list is invalid wasm too
([D2784](D2784.md)). Two list types stored alike (`T := boolean` beside `i32[]`) are built as
the one list the checker types the call as, where `is` cannot tell them apart
([D2769](D2769.md)).

The open question: the checker, which types the call as one list, owes these refusals.
