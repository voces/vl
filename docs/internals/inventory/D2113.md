### D2113 — a for-in loop variable captured by a lambda inside a generic instantiated at two types builds the lambda at one instance's signature

**closed 2026-09-25 — the filed repro RUNS and prints `1` then `s` · was check-clean invalid wasm · 1 witness, identical on the seed before and after D2110 · filed 2026-09-23 against master `7b16d43ab`, found reviewing #3050 · closed by D2552 (a value call in a per-instance lambda clone keyed at the pin), fixture `tests/cases/generics/value-call-callee-pinned-per-instance.vl`**

Repro:

    function ap<T>(fs: ((T) => T)[], x: T): void {
      for f in fs { const h = () => { f(x) }; h() }
    }
    function pi(x: i32) { print(x); return x }
    function ps(x: string) { print(x); return x }
    ap([pi], 1)
    ap([ps], "s")

#### Mechanism

Not yet ablated. What is known: the same body run at ONE instantiation prints `1`, the
uncaptured loop variable (`for f in fs { f(x) }`) runs at both instantiations since D2110, and
a lambda capturing the whole list and looping inside it (`const q = () => { for f in fs { f(x) } }`)
runs at both too. So the ingredient is a loop variable CAPTURED into a lifted lambda whose
generic owner has two pins — the lifted lambda is likely shared between the instances, and its
env field or call signature is typed at one of them.
