### D2331 — a list `+` stored its left operand in the shared concat frame before evaluating its right one, so a `+` nested in the right operand overwrote it

**closed 2026-09-24 — the witness prints `6`, `1` and `2`. Filed against master `816bda01e`, where it is check-clean silently wrong: `d` is `3 3 4 5 6`, length 5, and `d[5]` traps. Found by the #3115 review; the same class as D2313 and D2329/D2330**

Repro:

    const a = [1, 2]
    const b = [3]
    const c = [4, 5, 6]
    const d = a + (b + c)
    print(d.length)
    print(d[0])
    print(d[1])
    // PRINTS 6

#### Mechanism

`emitListConcatI` (the i32 list) and `emitListConcatG` (every other rep) evaluated the left
operand, stored it in slot `bA + 0` of the function's one concat frame for that rep (LEQI, or the
rep's LCAT frame), and only then evaluated the right operand. A concat of the same rep inside
the right operand runs the same lowering against the same frame, writes its own left operand to
`bA + 0`, and the outer concat then copied the inner one's left operand where its own belonged.
Both operands are now evaluated onto the stack and stored `B` then `A`, the order the compare
cores already used, so no user code runs between a frame write and its read. `+=` on a list and
the generic path go through the same two functions.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the nesting on the right (`(a + b) + c`) | runs | **yes** |
| the inner concat behind a call (`a + cat(b, c)`) | runs | **yes** |
| the inner concat bound to a `const` first | runs | **yes** |
| the inner concat at another rep (`a + [(["x"] + ["y"]).length]`) | runs | **yes** |
| the i32 rep (string, f64, i64, f32, u8, bool, struct, nested, nullable list) | still wrong | no |
| a statement position (`xs += b + b`, a struct field, a `for`-in source) | still wrong | no |
