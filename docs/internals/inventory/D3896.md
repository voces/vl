### D3896 — a nested generic returned through an enclosing `(T) => void` annotation is called at the enclosing pin's type without its demand being checked

**closed 2026-10-09 by lane SC · now a loud check reject · was check-clean silently wrong · found in review of #3468 (`rv3468d-witnesses/a_ret_bad.vl`) · filed 2026-10-09 against master `995c7d82e` · pins: `tests/cases/generics/error-nested-generic-returned-at-outer-function-type.vl` and three siblings, `tests/cases/generics/nested-generic-delivered-at-outer-function-type-runs.vl`**

Repro:

    function a<T>(x: T): (T) => void {
      function b<U>(y: U) { const n: i32 = y; print(n + 1) }
      return b
    }
    a(true)(true)
    // vl check: rc 0.  vl run: prints 2

Want:

    vl check: cannot assign boolean to 'n' of type i32

#### Mechanism

A generic delivered by name as a value to a function type is instantiated there, and its deferred
constraints are checked at that type's bindings (`genFnValueCstrs`, D3080). That path asked only a
top-level declaration and skipped a destination holding a type variable, so a nested `b` returned
at `(T) => void` had its `U := T` never checked anywhere. Closed by resolving a nested generic by
scope there too, binding only its rows (`SUBST_NESTED`), and letting a destination typed by the
enclosing function's parameters through. The constraints it leaves undecided are re-recorded under
the enclosing owner and checked at `a(true)`, at a return, a typed binding and a list element alike.
Only the demands of `b`'s own body are bound at a delivery: a constraint recorded elsewhere in
`a`'s body that names `b`'s type (another delivery, `const g: (n: i32) => void = b`) is a second
use, bound afresh at its own destination (`nestCstrOutside`).
