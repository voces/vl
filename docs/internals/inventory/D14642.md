### D14642 — a numeric literal `is` test compares at the literal's lexeme width, not the receiver's

**closed · runs, prints `false`, `false`, `false`, `false`, `true` · was check-clean invalid wasm, clause 1 · `emitNumLitEq` takes its compare from the receiver's width (`exprScalarWidth`): `i64` compares at `i64`, `i32` at `i32` where the value fits, and any other receiver never holds the literal · fixture `literal-unions/numeric-literal-is-at-receiver-width.vl` · filed 2026-10-28 against master `70326a63e`**

Repro:

    const y: f64 = 2
    print(y is 2)
    function g<T>(x: T) { x is 2 }
    print(g(2.0))
    print(g("s"))
    function w<T>(x: T) { x is 5000000000 }
    print(w(2))
    print(w(5000000000))

Want:

    false
    false
    false
    false
    true

#### Mechanism

`emitNumLitEq` built the literal at the width its lexeme fits (`i32.const` for `2`,
`i64.const` past 2^31) and compared it with the receiver, whatever the receiver's type. An
`f64` receiver (direct, or a type parameter pinned at `f64`), a `string` pin, and an `i32` pin
tested against a literal past 2^31 each fed the compare a value of another valtype. The checker
already refuses `f32 is 2` and `f64 is 3000000000` as never matching, and answers
`f64 | string is 2` false.
