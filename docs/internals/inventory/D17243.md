#### Mechanism

`readRepOf` (`emit_classify.vl`) keys its memo on node, function, pass generation, type epoch,
local-frame generation and table lengths. `readRepGo` also reads `elabNodeTyAt` through
`identReadAtomKindAt` → `readAtomAgreed`. In the repro, one function (fn 47), logging every ask of
`readRepOf(r)`, shows the leak:
- claimless: `elabNodeTyAt(r)` stays 361 (`K[] | string[]`) and every answer is `union`;
- the claim attempt: it moves 361 → 358 → 359 and back to 361. At 359 the memo misses and stores
  `atom9`, and every later ask at 361 hits that stale `atom9`.

The key moves on the way into the arm and not on the way out.

In this repro the claimless build never leaves 361, so no legacy-only ask sees the divergent
context. A legacy path that asks `readRepOf` for the same node inside and outside an arm's
elaboration in one function would be served across them.
