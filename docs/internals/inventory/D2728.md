### D2728 — an inferred return joins a returned list LOCAL into a wider list type the annotated spelling refuses

**now a loud check reject, the ruling still open · `i32[] is not f64[]: this join would hold both, and a container never widens implicitly` at `return s`, the same sentence at all three cells (the refusal D2838 added at every join position until the ruling below is taken) · was check-clean invalid wasm · needs a ruling · three cells (`i32[]` into `f64[]`, `string[]` into `(i32 | string)[]`, and the same through `id<T>`) · identical on master · filed 2026-09-26 against master `90b63b840`**

Repro:

    function f(c: boolean) {
      if c { return [1.5] }
      const s = [2]
      return s
    }
    print(f(false)[0] / 4.0)
    // vl check: rc 1 at `return s`.  Was: vl check rc 0, vl run invalid module inside `f`.

#### Mechanism

With `: f64[]` written on `f`, `vl check` refuses `return s`: "i32[] is not f64[]: a container
never widens implicitly". Un-annotated, the return join widens `i32[]` and `[1.5]` to `f64[]`
anyway and accepts, so the existing `i32` list is returned through an `f64[]` result. The
refusal the annotated spelling gives is a design rule, so the un-annotated program is not one
the design permits as written. Ruling asked: should an inferred return's join keep a returned
LIST VALUE at its own type (the result is then `f64[] | i32[]`, which today refuses as "an
inferred return of this shape is not yet supported by codegen"), or refuse the second `return`
as the annotated spelling does? Recommendation: the union, since a fresh literal `[2]` in the
same position is legitimately `f64[]`, and refusing would make the two spellings of one value
disagree.
