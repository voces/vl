Repro:

    function sum(xs) {
      let t = 0
      let i = 0
      while i < xs.length { t = t + xs[i]; i = i + 1 }
      return t

    print(sum([1.5, 2.5]))

Want:

#### Mechanism

A literal `let` is re-typed by its deliveries and stores only within its literal's kind: an
integer literal widens to `i64`, never to a float. Each call instantiates `sum` at its argument
type, so at `f64[]` the store `t = t + xs[i]` is an `f64` into an integer binding and is refused,
and the diagnostic lands at the CALL. The same body at `i32[]` runs.

#### Grading list

The owner's answer decides this row: either an integer literal `let` in a generic body may join
to a float at an instance (and the witness prints `4`), or the refusal stands and its sentence
names the binding `t` and the annotation that fixes it, not only the call.

The sentence half is done (lane N, 2026-11-15): the refusal at the call now names the binding as
the same store outside a generic body does, `cannot assign f64 to i32 — \`t\` on line 2 has no
annotation, so its literal defaulted to \`i32\`; annotate it: \`let t: f64 = …\` (the body of
\`sum\` at the call's argument types)`. Whether the literal may join to the float is with the
owner (B′'s "Within kind" against ruling 4.3's one rule for every join form).

The owner ruled the join (2026-11-15). Integer-only stores keep the integer widening
(`let t = 0; t = t + big` with `big: i64` is `i64`), and a float that does not hold the literal
exactly keeps the refusal: `let t = 16777217; t = f` with `f: f32` is still `cannot assign f32 to
i32`, and the generic at `f32[]` is `constant 16777217 is not exact at f32`.
