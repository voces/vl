### D2066 — a type with a getter satisfies no bound that reads the property, and the refusal offers a fix the getter already is

**closed 2026-09-22 — now a loud check reject that names the getter and the method that would satisfy the bound · diagnostics quality and a false guide sentence · filed 2026-09-22 against master `31ea77721`, found independently by six lenses of the getters/effects persona review (Swift, C#/Kotlin, TypeScript, compiler-engineer, beginner, minimalist) · fixtures `tests/cases/getters/getter-refusal-shape.vl`, `tests/cases/getters/getter-method-alternative.vl`**

Repro:

    type Color = new i32
    get r(self: Color): i32 { ((self as! i32) >> 16) & 255 }
    function red<T: { r(): i32 }>(t: T): i32 { return t.r() }
    print(red(0x123456 as! Color))
    // vl check, filed: Color does not satisfy `{r():i32}`: no `r(): i32` — the bound needs a
    // field of that type or a `r(self: Color, …)` function in scope at this call
    // vl check, closed: Color does not satisfy `{r():i32}`: `r` on Color is a getter, and a
    // getter does not satisfy a bound yet — take a `Color` parameter instead, or declare `r` as
    // a method, `function r(self: Color): i32`, which satisfies it

#### Mechanism

`docs/guide/getters.md` said generic code that wants a readable `x` "asks for the method
`{ x(): f32 }` instead". A getter refuses `v.x()`, so it does not satisfy a method bound; by
ruling it does not satisfy a field bound `{ r: i32 }`; and the same-name rule refuses a method
`r` beside the getter. The un-annotated `function red(t) { return t.r }` is refused too
(`expected {r: _}, got Color`), so a getter-bearing type reaches no generic or inferred helper
that reads the property. The message repeated the false "or a `r(self: …)` function in scope"
fix, and here the named function exists, in getter form. Whether a getter should satisfy
`{ readonly r: i32 }` is owner question Q4; this row is the message and the guide sentence,
which were wrong under any answer.

#### The close

Refusing stays the ruling (F2: a getter never satisfies a structural type). Every place the
refusal is raised now says why and what to write instead:

- A bound member the receiver answers with a getter (`checkBounds`, via `getterFnFor`) is
  refused as "`r` on Color is a getter, and a getter does not satisfy a bound yet — take a
  `Color` parameter instead, or declare `r` as a method, `function r(self: Color): i32`", ending
  "which satisfies it" for a method bound and "and bound on `{ r(): i32 }`" for a field bound.
  A method does satisfy the method bound (`getter-method-alternative.vl` runs it).
- An un-annotated parameter's inferred record demand appends "`r` on Color is a getter, and the
  parameter's inferred type is a record with a field `r`, which a getter does not satisfy;
  annotate the parameter as `Color`" (`getterDemandNote`). This reaches std's `F32x4` through
  `function hx(v) { return v.x }`.
- A member read through a nullable getter result after a null test appends "`.q2` is a getter,
  and a null test does not narrow a getter read; bind it to a local first: `const q2 = n.q2`,
  then test `q2 != null`" (`getterNarrowNote`).
- The guide states the limitation and gives the method alternative with a runnable example.

`cs.map(r)` stays refused as `undeclared identifier`: a getter is never looked up by name
(§D3a rule 1), and that is unchanged.
