#### Mechanism

An un-annotated parameter is a hole the call pins from the argument, through `monoArgPinName`
and then `monoArgTyName` — a long ladder over the argument's SHAPE, ending in a set of NAMED
loud floors. Those floors are correct as floors: the `"i32"` catch-all above them is the
defect, since a wrong pin becomes the instance's parameter annotation and mints a wrong
instance silently. What two of them lacked was a channel.

Every arm above the floors resolves a BINDING — an annotated local, a param, a global, a call
with a concrete return. An if-expression is none of those, so it arrived at
`exprNullableStruct`'s floor with a type the checker had recorded and no way to spell it. An
instrumented build printed the floor's own inputs:

    PROBE nulstruct floor tyName=[{msg:string}|null] pin=[{msg:string}|null]

`monoAnnPinName` — the one pin membership list — already claimed that spelling. The floor was
discarding an answer the ladder had. [D1516](D1516.md) gave the UNION floor exactly this
question one line above, and its comment names the pattern: "the union floor owes the arena one
question first, exactly as the struct floor below already asks it".

A second floor answers the same way. `exprRefArray`'s non-literal leg — "only a literal
argument names its element type cheaply; other shapes have no channel here" — refused
`__array_new__(2, [0, 6])` while its own probe read
`PROBE refarray floor tyName=[i32[][]] pin=[i32[][]]`. Both floors now ask, and both still
return `""` where the membership list declines, so a pin that cannot name its type is still a
loud refusal rather than a wrong instance.

Binding the argument first does not launder it: the `Ident` arm recurses into the initializer
and propagates the floor's `""` deliberately ("a refusal propagates"), so one rung serves both
spellings.
