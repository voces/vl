### D1755 — an if-EXPRESSION value pins an un-annotated parameter with a type the monomorphizer declines, and binding it first does not launder it

**loud emit reject · 10 cells of the discovery pass's un-annotated-parameter group · filed
2026-09-06 against master `40334c8cf` · found by the 2026-09-06 discovery pass**

Repro:

    type E = { msg: string }
    function mkA(ok: boolean): E | null {
      if ok { return null }
      return { msg: "a" }
    }
    function mkB(ok: boolean): E | null {
      if ok { return null }
      return { msg: "b" }
    }
    function truthy() { 1 == 1 }
    function falsy() { 1 == 2 }
    function take(a) {
      const v = a
      if v != null { print(v.msg) } else { print("null") }
    }
    take(if truthy() { mkA(falsy()) } else { mkB(falsy()) })
    // vl check: rc 0.  vl run: emit error,
    // emitProgram: monomorphize: unsupported argument type for `a` in a call to `take`

#### Mechanism

The pin for an un-annotated parameter is taken from the argument's type, and an if-expression
whose arms are nullable refs carries a type the monomorphizer's argument ladder has no arm for.
The same callee accepts a plain call of the same nullable-ref type, so the parameter being a
hole is not the ingredient — the if-expression's own type is.

Binding the if-expression first and passing the local refuses identically, so this is the type
the pin reads and not the syntactic position of the argument. Annotating the parameter runs,
which places the whole defect on the pin.

The message is the monomorphizer's, so the refusal names an internal ladder rather than a
capability; every one of the ten cells is `vl check` rc 0, and every one has a neighbouring
spelling that runs.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the un-annotated parameter (`take(a: E \| null)`) | runs, prints `a` | **yes** |
| the if-expression, for a plain call (`take(mkA(falsy()))`) | runs, prints `a` | **yes** |
| the argument position, bound first then passed | still refuses | no |
