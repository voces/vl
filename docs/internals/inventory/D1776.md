### D1776 — a comment written INSIDE a list literal is reflowed out of it, and `vl fmt` re-emits it after the whole declaration, where it documents the next statement

**closed 2026-09-06 — the witness runs and `vl fmt` reproduces it byte for byte · was a `vl fmt` comment RELOCATION on a `vl check`-clean program · fixed by giving `arrayLiteral` the verbatim anchor `ifExpr` already takes for the same reason**

Repro (runs, prints `4`):

    const c = [
      1, 2,
      // the second row
      3, 4,
    ]
    print(c.length)
    // vl check: rc 0.  vl run: 4.
    // vl fmt: `const c = [1, 2, 3, 4]`, then a BLANK line, then `// the second row`,
    //         then the next statement — the comment now sits above `print`.

#### Mechanism

The witness RUNS, and the status line says so, for [D1647](D1647.md)'s reason: the defect is
in a tool the witness grader does not drive.

`arrayLiteral` rendered each element through `expr` and handed the items to `wrapList`, and
neither step reads the comment table. A comment inside the brackets is therefore still
PENDING when the literal is finished, so the next `emitLeadingComments` — the statement
printer's, at the following statement — emits it there. The list's own rows are gone by then,
so nothing records which row the comment was written against.

Two things make this worse than a cosmetic move. The comment ends up attached to a DIFFERENT
construct, which is the failure mode `docs/internals/comment-style.md` exists to prevent; and
the rule the owner ruled in #2814 re-flows a scalar list into a filled table, so the rows the
comment annotates are re-cut on the same pass that ejects it.

The fix is the anchor the printer already has: `sliceSpanFallback` reproduces a construct
from source and calls `markVerbatim` on its span, so the placement helpers skip the comments
inside it rather than re-emit them. `ifExpr` takes it for exactly this reason ("a comment
cannot ride the inline form"). `arrayLiteral` now tests `commentInCharSpan` over its own span
first, and every row — the commented one included — stays where it was written.

#### Ablation

Every row is `vl check` rc 0 and prints the same value before and after.

| ingredient removed | `vl fmt` behaviour | needed? |
| --- | --- | --- |
| the comment (`[1, 2, 3, 4]` alone) | reflowed, nothing to lose | **yes** |
| the comment moved AFTER the `]` (a trailing comment on the statement) | stays put | **yes: inside the brackets** |
| the multi-row spelling (the comment on the same line as an element) | still ejected | no |
| the top-level position (the same literal inside a function body) | still ejected | no |
| the element type (strings, booleans, structs) | still ejected | no |

Needed: a comment whose start offset lies inside the literal's own `[` … `]` span. Not
needed: the row shape, the element kind, or the depth the literal sits at.

#### Grading list

* The four fixture shapes the layout rule owns — filled, uniform rows kept, ragged rows
  filled, a one-line list unchanged — none of which may start reproducing itself verbatim.
* `vl fmt` idempotence over the whole tree: a verbatim slice must be its own fixed point.
* [D1777](D1777.md) — a comment inside an OBJECT literal and inside a call's argument list,
  both of which take the same `wrapList` path and are NOT covered by this fix. The anchor
  must not widen to them by accident, and it must not narrow away from lists when they land.
