Repro:

    //   the LITERAL, not the read. Now prints 42.

#### Mechanism

The literal's classifier receives the SAME inputs for both spellings. A probe in `collectU`'s
array-literal loop prints, for the annotated `(i32 | null)[]` and for the bare `[42, null]`
alike:

    PROBE arrlit ty=(i32|null)[] elemTy=i32|null infer=[] nulNum=[i32|null]

`infer=[]` is `arrLitInferUnionElemName` declining, because it reads `TyUnion` and `i32 | null`
is recorded as `TyNullable` — the same split D1372 already named on the classifier side. So
the loop minted no row for either spelling, and the ANNOTATED one is saved by its annotation
(`collectInlineUnions`), which the un-annotated one does not have.

`nulNum=[i32|null]` is the answer that was there all along: `nulNumScalarUnionName` is the
producer the `.pop`/`.get` loop immediately below already uses, which is exactly why
`elems.get(0) ?? 0` ran and a program spelling BOTH ran — `.get` registered the row the
subscript then found. The registration is now the literal's, so it no longer depends on what
else the program happens to spell.

The `??` was never an ingredient: a bound copy read through a `!= null` guard refused
identically. `boolean` and `string` elements have niches, need no box, and ran throughout.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |

| the subscript (`elems.get(0) ?? 0`) | printed `42` — `.get` registered it | **yes** |

| the `null`'s position (`[null, 42]`) | refused too | no |
| the nesting (`[[42, null]]`) | refused too | no |
