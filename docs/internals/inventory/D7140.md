### D7140 — a hole-function list's `for` loop variable called with a generic function is refused, though the element call beside it takes the same generic

**closed 2026-10-19 by lane L1 · runs, prints `3 4 3 4 3 4` · was loud emit reject · `vl check` rc 0 · clause 2 · CAPABILITY · the split's exact value-flow question now follows a `for` loop variable to its calls, and a call several list elements reach is handed its argument once · pins: `tests/cases/closures/hof-in-list-called-by-index-and-loop-var.vl` · found closing [D7101](D7101.md) · the same on master `8e787a973` · filed 2026-10-19 against master `8e787a973`**

Repro:

    function add(a, b) { return a + b }
    print(add(1, 2))
    print(add(1.5, 2.5))
    function apply2(g) {
      print(g(1, 2))
      print(g(1.5, 2.5))
    }
    const fs = [apply2]
    fs[0](add)
    for f in fs { f(add) }
    // vl check: rc 0.  vl run: emitProgram: cannot take the generic function `add` as a value — a function value carries ONE signature, and parameters `a`, `b` are un-annotated

Want:

    3
    4
    3
    4
    3
    4

#### Mechanism

The split asks the value-flow question in its exact mode, which lost a `for` loop variable,
so `apply2` was not split per call type and `add` reached the value floor. With the loop
variable answered, the split reaches the call `f(add)` once per call it makes and hands its
argument once.
