### D2197 — `for x in xs` over an un-annotated parameter is refused, though indexing the same parameter compiles

**loud check reject · clause 2 · every element type tried · filed 2026-09-23 against master `0c117d0c3`**

Repro:

    function total(xs) {
      let t = 0
      for x in xs { t = t + 1 }
      t
    }
    const a: i32[] = [1, 2, 3]
    print(total(a))
    // vl check rc 1: for-in expects an array, a map or a string, got _

#### Mechanism

An un-annotated parameter is a hole (`_`) that each call pins to the argument's type, and the
function is specialised per call. `xs.length` and `xs[i]` record a demand on the hole and the pin
satisfies it; the `for`-in head instead asks for a concrete array, map or string at the moment
the body is checked, before any call has pinned the hole, and refuses. The same body written
with a `while` loop over `xs[i]` runs for `i32[]`, `f64[]` and `Circle[]` arguments (the
readonly-only rule's `unannotated-list-param-no-widening-runs.vl` uses that spelling).

#### Ablation

| spelling | outcome | needed? |
| --- | --- | --- |
| the witness | check reject | — |
| `while i < xs.length { … xs[i] … }` | runs | the `for`-in: **yes** |
| `function total(xs: i32[])` | runs | the hole: **yes** |
| an `f64[]` or `Shape[]` argument | check reject | element type: no |

#### Grading list

The witness at an `i32[]`, `f64[]`, `(i32 | string)[]` and `Shape[]` argument, and the same
loop over a map argument.
