### D16931 — a `for` over a local joining two hole parameters is refused by the generic check: the join of two holes is a union of holes, which the loop does not treat as a hole

**loud check reject · clause 2 · found grading [D16897](D16897.md)'s step 2b against the `ug_k_s` named cells · filed 2026-11-17 against master `abf14795b`, pre-existing**

Repro:

    function g(a0, a1, k: i32) {
      const r = if k == 0 { a0 } else { a1 }
      let n = 0
      for e in r { n = n + 1 }
      print(n)
    }
    const x0: i32[] = [1, 2]
    const x1: string[] = ["y"]
    g(x0, x1, 0)
    g(x0, x1, 1)
    // vl check: rc 1, "for-in expects an array, a map or a string, got _ | _"

Want:

    2
    1

#### Mechanism

The template's check types `r` as the join of two holes, a `TyUnion` of `TyVar`s. The `for`
check derives a per-pin binding (`HD_ITER1`/`HD_ITER2`) only when the iterable is itself a
`TyVar`, so a union of holes falls to the not-iterable refusal before any pin re-checks the
loop at the instance's `i32[] | string[]`, where D16897's per-arm walk would lower it.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |

| `r[0]` in place of the loop | runs (D16897 step 2a) | **yes** (a `for`) |
| `for e in a0` (one hole, no join) | runs | **yes** (the join) |
