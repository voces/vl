### D16931 — a `for` over a local joining two hole parameters is refused by the generic check: the join of two holes is a union of holes, which the loop does not treat as a hole

**closed 2026-11-25 by SOUND · runs, prints `2` `1` · was a loud check reject (clause 2), "for-in expects an array, a map or a string, got _ | _" · the `for` check derived per-pin loop bindings only for a bare hole iterable; a union of holes now binds each variable to the join (`joinTys`) of its members' `HD_ITER1`/`HD_ITER2` holes, so each instance checks and walks its own union of lists (D16897), and an instance whose join is not iterable still refuses there · pinned by `tests/cases/generics/for-in-over-join-of-two-hole-params.vl` (count, sum, index, concatenation) · found grading D16897's step 2b · filed 2026-11-17 against master `abf14795b`**

Repro:

    function g(a0, a1, k: i32) {
      const r = if k == 0 { a0 } else { a1 }
      let n = 0

    }

Want:

    2

#### Mechanism

The template's check types `r` as the join of two holes, a `TyUnion` of `TyVar`s. The `for`
check derives a per-pin binding (`HD_ITER1`/`HD_ITER2`) only when the iterable is itself a
`TyVar`, so a union of holes falls to the not-iterable refusal before any pin re-checks the
loop at the instance's `i32[] | string[]`, where D16897's per-arm walk would lower it.
