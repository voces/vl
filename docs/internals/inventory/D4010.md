### D4010 — a generic written into a list element is instanced at a call the checker should have refused, so an ill-typed program runs

Repro:

    function inner<U>(u: U) { print("I"); print(u) }
    function plus<V>(v: V) { print(v + 1) }
    function main() {
      const fs = [inner]
      fs[0] = plus
      fs[0](true)
    }
    main()
    // vl check: operator '+' is not defined for boolean and i32 (the call's argument types)

#### Mechanism

`fs[0] = plus; fs[0](true)` is ill-typed (`plus` adds `1` to its argument), and `vl check`
accepts it because the call through the list element is never re-checked against the values
written into it. #3508 re-checks a call through a written `let`; a list element is not covered. `plus` prints `true + 1` as `true`. Before #3517 the call reused another instance and trapped with an indirect-call type
mismatch; #3517 instances every written generic at the call's argument types, so the ill-typed
instance is now built. At `boolean` (and at a type-variable name collision) it runs and prints
garbage; at `string` it fails to validate. Closed in the checker: an un-annotated list
literal holding a generic function value is marked as #3508 marks a `let`, whatever its keyword.
A write through an element, `fs[i] = g`, records `g` as an owner, and a call through an element,
`fs[i](…)`, re-asks every owner's deferred constraints at the call's argument types. As for a
`let`, the re-ask is flow-insensitive: a write after the call is re-asked too. A concrete
function written to an element is not refused, unlike a written `let`. A write through an alias
of the list, or through `push`, is not seen. Both of those spellings refuse at emit today
(`a function-value call has no interned signature`), so neither is silent.
