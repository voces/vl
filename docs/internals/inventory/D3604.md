### D3604 — a lambda created above a later local named like a numeric builtin captured the local instead of calling the builtin

**closed 2026-10-04 · was a loud emit reject (`call to unknown function`) of a check-clean program, clause 2 · filed and closed by lane SC against master `c473889d1` · fixture `tests/cases/scope/builtin-call-in-lambda-above-later-local.vl`**

Repro:

    function f(x: f64) { const g = () => floor(x); const floor = 0.25; print(g()) }
    f(2.5)
    // master: vl check rc 0, vl run "emitProgram: call to unknown function" at 1:45

Want:

    2

#### Mechanism

`capScan` (`compiler/emit_classify.vl`) decides what a lambda captures. In callee position a
numeric intrinsic's name is exempt from capture unless an enclosing frame binds it, and that
question went to `parentBindingFrameOf`, which looked the name up in the frame's whole body. So
the later `const floor` counted as a binding of the call above it: the lambda captured `floor`,
and the emitter, finding a captured `f64` where a function was called, refused. The checker
resolves the call to the builtin, because the `const` is not in scope there. The question now goes
to `parentBindingFrameAt`, which asks `parentLetReadAt` whether a body `let` covers the reading
node. A binding the plan cannot place keeps the old answer. `capRecord` asks the same positioned
question for an identifier, so a lambda above a later local named like a module function or
global no longer captures that local either.
