### D2254 — a map read keyed by a call, with a nullable `??` default, emits an invalid module

**check-clean invalid wasm · `vl check` rc 0, then the emitted module fails validation
inside the module's top-level code, clause 1 · found while extending the D2247 value-type
grid to a computed map key · filed 2026-09-23 against master `3330dcaa3`**

Repro:

    const m: {[string]: i32} = Map()
    m["b"] = 7
    const d: i32 | null = null
    function key(): string { "b" }
    const r7 = m[key()] ?? d
    print(r7 ?? -1)
    // vl check: rc 0.  vl run: invalid module,
    // "type mismatch: expected i32, found (ref $type)"

#### Mechanism

The same map (`{[string]: i32}`, value type excludes null) and the same nullable default
run correctly at a LITERAL key (`m["b"] ?? d`): the D2247/D2248 rewrite
(`emit_rewrite.vl:670`) desugars `m[k] ?? d` into `if m[k] != null { m[k] } else { d }`, but
only when the key is `exprReReadable` — duplicating a `Call` key would evaluate `key()`
twice. A call key declines the rewrite, so the read falls to the same FUSED
single-evaluation lowering D2253 reaches from the other side (`emitMapGetOr` /
`emitMapValDefault`'s scalar arm, `wasmEmit.vl:7652`), which does not correctly deliver a
NULLABLE default as the map's raw scalar kind.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the key being a call (`key()` replaced by the literal `"b"`) | runs | **yes** |
| the default `d`'s nullability (`i32` instead of `i32 \| null`) | runs | **yes** |

#### Grading list

D2253 — the two rows are the same fused-path defect reached by different guards (map value
already nullable vs. an un-re-readable key), and the mechanism paragraph there is the fuller
account. A fix should re-grade both this row's literal-key ablation and D2253's non-nullable-
map ablation, which must keep running.
