### D2520 — a generic's member call through a local copy of its parameter, or from inside a closure, is not dispatched per instance

**loud check reject · clause 2 (on master it printed the function's value) · filed 2026-09-25 against master `54fcaf5d8` while fixing [D2517](D2517.md) · fixture `tests/cases/generics/error-member-call-not-per-instance.vl`**

Repro:

    function slice(self: boolean | string, a: i32, b: i32): string { "fn" }
    function f<T>(x: T) {
      const y = x
      print(y.slice(0, 2))
    }
    f(true)
    f("hello")
    // master: prints fn, fn (the string instance should print he)
    // now: `.slice` on string is its built-in method, not the `slice` in scope, and this call cannot pick it per instance from inside a closure or through a local — call it on the generic's own parameter

#### Mechanism

[D2517](D2517.md)'s per-instance pick happens in `monoPinBinOps`, which knows an instance's
receiver type only for the generic's own parameters (`monoPinnedOperandTy`) and does not walk
into a lambda body. A call whose receiver is a local bound from the parameter, or which sits in
a closure, is still rewritten to the `self`-function once for every instance (`drwWalk`), so an
instance whose built-in or field should take it ran the function. The checker now marks such
sites when it types them (`ufcsSitePinnable`) and refuses them at a pin where a built-in or field
would take the call; a pin the function takes still runs. Closing it means substituting the
instance's type bindings into the receiver's recorded type (a local) and re-dispatching inside
the per-instance lambda clone (a closure).

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the local (`x.slice(0, 2)`) | prints fn, he | **yes** |
| the string instance (`f(true)` alone) | prints fn | **yes** |
| the local, closure instead (`const g = () => print(x.slice(0, 2))`) | the same refusal | no |
| the built-in, a field instead (`{ run: … }` receiver, `y.run(2)`) | the same refusal, naming the field | no |
