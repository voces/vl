### D17110 — an assignment-as-value operand after another reorders that operand's read past its store, invisibly where the read is of another cell

**closed 2026-11-24 · runs, prints `mk` `5` `2.5` · the IR's claim was a byte mismatch with legacy's output, the armed shadow's `fail a claimable function did not match`, shipped as the claim · fixed with D17109's guard in ir_build.vl, which declines the claim (`short-circuit closure argument`, `store after an operand`) · found by lane IR-N11 in `assignment value unwiden`'s sweep · filed 2026-11-24 against master `334f6958`, pre-existing**

Repro:

    function mk() {
      print("mk")
      return 2.5
    }
    function m() {
      let f: (f64) => f64 = (x) => x * 2.0
      let b: f64 = 0.5
      print(f(b = mk()))
      print(b)
    }
    m()

Want:

    mk
    5
    2.5

#### Mechanism

D17109's reorder where the earlier operand reads a cell the store does not write. Here that is a
closure local's callee read (`reRead` arm, mismatch `bytes: call at 0x20 vs 0x10`), or the
string literal before `show(x = 0xfffffffe)` (`lit` arm, `bytes: call at 0x23 vs 0x42`). A
shipped build emitted the IR's reordered bytes, and the output matched only because nothing
earlier observed the store. D17109's witness is the same reorder made visible.

#### Ablation

| ingredient | outcome | needed? |
| --- | --- | --- |
| the earlier operand reads the stored cell | wrong value (D17109) | **yes**, for invisibility |
| the earlier operand a temp | refused or unlowered | **yes**: a variable or immediate |
