#### Mechanism

`fnSlotAssignable` (check_relate_core.vl) refused a function-slot result whose rep differs from
the slot's, and `f64[]` and `f64[] | null` lower to different reps. A function value cannot take
the slot's result as its own, as a lambda written at the slot does. The result side now admits
`T` at `T | null` (`fnSlotRetAssignable`); a parameter stays invariant. Every delivery that passes
`assignableExpr` reaches `fvaAdapt`, which already built [D4351](D4351.md)'s adapter
`(p…): R => f(p…)` for any pair whose reps may differ. A function inside a container is still
refused loudly there. A join typed at the destination hid its tails' own types from `fvaAdapt`,
so each tail is now adapted, at a declared destination and at an un-annotated join's own type;
an un-annotated list literal's elements likewise ([D9882](D9882.md)). A function carries no
runtime tag, so `v is (i32) => f64[]` over a value of the widened type stays refused.
