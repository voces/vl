### D15531 — a second generic written by a helper into an un-annotated map already holding one, read back at two types, reaches no instance

**closed 2026-11-06 by lane mrec-row · runs, prints `id2`, `7`, `id2` and `w` · was loud emit reject, `indexed-assignment target is not an array`, `vl check` rc 0 · clause 2 · closed by taking a member's write through a callee's parameter into a held map of the set as that member's leaf (`fnTagMapWriteLeavesOf`, check_elab_cap.vl), the map twin of D14648's list rule, gated so the write lands only in maps of the set · fixture `closures/generic-written-into-map-holding-another-through-param-two-types.vl` · blocker (3) of `closures/hole-fn-generic-map-stored-through-parameter.vl`'s map-pin hits (architecture-target-2026-10.md §3.4) · filed 2026-11-06 against master `9dfa5874`**

Repro:

    function id<T>(x: T): T { x }
    function id2<T>(x: T): T {
      print("id2")
      x
    }
    function bare(mm) { mm["k"] = id2 }
    const h = Map()
    h["k"] = id
    bare(h)
    const hr = h["k"]
    if hr != null {
      print(hr(7))
      print(hr("w"))
    }
    // vl check rc 0.  vl run: emit error: indexed-assignment target is not an array

Want:

    id2
    7
    id2
    w

#### Mechanism

`h` holds `{id}` from its own write and `{id, id2}` once `bare`'s write lands in it, so its value
is a set of two generics. D15492 admits a helper's write into a holder of a wider set, but only
where the set is decided for every holder the helper is handed. Here the read of the wider set is
called at two types, so mono cannot pin one generic per map and the tag rule leaves the set
untagged; the store `mm["k"] = id2` then reaches emit with no rep for its map.
