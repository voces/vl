### D3060 — `.filter` keeps the element as re-read after its callback, not the value the callback tested

**closed 2026-09-28 — the witness prints `1,2,` · was check-clean silently wrong · clause 1 · `emitMapFilter`'s filter step reads the element once into a stash slot (`listIdxValSlot`) and hands that value to both the callback and the store · 100-cell grid (filter/map/reduce/mapIndexed × index store, push, pop × i32, f64, string, record and two view receivers) plus 11 receiver cells: every index-store cell right on plain lists and views; the length-changing cells are [D3068](D3068.md) · fixture `tests/cases/arrays/filter-keeps-the-element-its-callback-tested.vl` · filed 2026-09-28 against master `3a71bb1f9`**

Repro:

    const h: i32[] = [1, 2]
    let out = ""
    for e in h.filter((e) => {
      h[0] = 9
      return e > 0
    }) {
      out = out + "\{e},"
    }
    print(out)
    // PRINTS 9,2,

Want:

    1,2,

#### Mechanism

`emitMapFilter`'s filter step reads element `i` twice: once to pass to the callback, and again
(`emitMfElem`) to store it when the callback answers true. A callback that writes the list
between the two reads makes the result hold a value the predicate never saw. **The defined
semantics is the tested value** (as JavaScript's `filter` does): the element is read once per
step, and a callback's write reaches only the elements read after it. A read of a LATER element
already sees the write, for a plain list and for a `readonly` view alike (D3028), so the fix is
one stash of the element before the callback, shared by both reads. A callback that changes
the source's LENGTH is a separate question, [D3068](D3068.md).

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| the callback writes `h[1]` instead | prints `1,9,`, right | **yes** (the element under test) |
| no write in the callback | prints `1,2,` | **yes** |
| the list a `readonly i64[]` view of `h` | prints `9,2,` too | no |
