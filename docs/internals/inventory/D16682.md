### D16682 — the lossy-number hint says "write `x as i32`", which a function returning `i32` then refuses; a return position gives no hint at all

**closed 2026-11-16 · now a loud check reject whose note names `x as! i32` / `x as? i32` (and `x as% i32` from an integer) where the bare `as` would be refused, the bare `as` elsewhere, and a returned value gets the note too (`lossyAsNote`, check_mismatch_notes.vl) · first-error quality · lane AE conversion audit · filed 2026-11-16 against master `6356d3e7d` · fixture `numerics/error-lossy-hint-names-working-spelling.vl`**

Repro:

    function f(u: f64): i32 {
      const k: i32 = u
      return k
    }
    print(f(3.0))
    // was: f64 doesn't fit in i32 — the conversion is lossy and must be made explicit with `as` (write `x as i32`)
    // was, after it: `as i32` propagates null, which the enclosing function cannot return (it returns i32) — …

#### Mechanism

`letAssignMsg`'s lossy arm (check_mismatch_notes.vl) names the bare `as` whatever the
conversion and the enclosing return. For a float-to-integer (or narrowing integer) conversion the
bare spelling propagates `null`, so in a function whose return cannot carry it the hint's own
spelling is the next error; the hint should name `as!` / `as?` (and `as%` for an integer) there.
`return u` in the same function says only `return type mismatch: expected i32, got f64`, without
the lossy note the binding position gives (`checkRetStmtNode`, check_statements.vl); `floor(u)` and
`x / 2.0` returned as `i32` read the same.
