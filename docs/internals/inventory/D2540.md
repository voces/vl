### D2540 — `for k in t` over any struct (including `IdTable`) always suggests a `{[string]: i32}` map, wrong advice for an i32-keyed table that already has `.ids()`

**loud check reject · message quality · found while reviewing `std:idtable` (#3168) · filed 2026-09-25 against master `a09d1f6bc`**

Repro:

    import { IdTable } from "std:idtable"
    type Tex = { w: i32 }
    const t = IdTable<Tex>()
    t.set(1, { w: 2 })
    for k in t { print(k) }
    // vl check: rc 1, "a struct's fields are not a sequence, so `for … in IdTable<Tex>` has
    // nothing to iterate — use a map (`{[string]: i32}`) for keyed iteration, or read the
    // fields by name"

#### Mechanism

`checkForInNode`'s `TyObj` arm (`typecheck.vl`) refuses `for … in` over any struct with one
fixed sentence, always naming `{[string]: i32}` regardless of what struct it is. The refusal
itself is correct by design (a nominal record's fields have no shared type to bind a loop
variable to) — but for `IdTable<V>`, which is itself a struct under the hood, the canned
suggestion is wrong twice over: it is keyed by `i32`, not `string`, and it already ships the
right answer (`t.ids()`, a `for id in t.ids()` walk), which the generic message cannot know to
name.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| `IdTable` — a plain unrelated struct (`type Pt = { x: i32, y: i32 }`, `for k in p`) | the same sentence, same wrong `{[string]: i32}` mention | no — the message is generic, not `IdTable`-specific |
| the `for … in t` spelling, replaced by `for id in t.ids()` | runs, prints `1` | **yes** — the correct alternative already exists |

#### Grading list

Every struct type this message fires for; the fix is either an `IdTable`-specific carve-out
naming `.ids()`, or dropping the concrete map spelling from the generic sentence so it stops
asserting a key type it has not checked.
