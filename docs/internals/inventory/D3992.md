### D3992 — a record wider than a function's declared record parameter was refused as needing a field-dropping conversion

**closed 2026-10-11 by lane CK · runs · was loud check reject · clause 2 · found by the diderven consumer (`DV-400`) · filed 2026-10-11 against master `e5128703a` · pins: `tests/cases/objects/width-record-into-declared-param-runs.vl`, `tests/cases/objects/error-width-record-param-still-checked.vl`, `tests/cases/objects/error-width-record-param-body-checked-at-declared-type.vl`**

Repro:

    type Pos = { x: f64, y: f64 }
    type A = { k: i32, x: f64, y: f64 }
    function mv(p: Pos) { p.x += 1.0 }
    const a: A = { k: 1, x: 2.0, y: 3.0 }
    mv(a)
    print(a.x)
    // vl check: an object value of shape A flowing into Pos drops the field `k`: type-valid (structural width subtyping) but not yet supported by codegen

Want:

    3

#### Mechanism

The program is legal: the record-covariance ruling refuses an existing record into a type that
WIDENS one of its fields, since a store through the wider type would break the source's own; a
width difference changes no field's type, so the shared value keeps every invariant. Its wasm
layout is its own field list, though, so `A` cannot be passed where `Pos` is laid out. A call
that passes a wider record to a top-level function's parameter of a declared record type now
makes that parameter generic (`f<__W0>(p: __W0)`) and the program is re-checked
(`wsApplyPending`), so each instance takes its argument's own layout, as an un-annotated or
generic parameter already did. Every call is still held to the declared type, the body is checked
at it, and a function whose body refused something, an exported one, one read as a value, or one
whose declared type appears elsewhere in its signature keeps the refusal.
