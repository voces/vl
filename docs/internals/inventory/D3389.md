### D3389 — a module-scope `??` over a record if-join, delivered to a record that stores a field differently, builds invalid wasm

**closed 2026-11-01 (`repStampableLit` and `recordRepTyAdopt` in `compiler/check_fit_rules.vl` see through a `??`: each operand is built at the destination, and a value `if` on the left is stamped there too, since the emitter types the join's result from its stamp) · runs, prints `70` · was check-clean invalid wasm · clause 1 · fixture `tests/cases/structs/coalesce-over-record-join-delivered-at-wider-record.vl` · the bound-first un-annotated spelling is a different family, [D14872](D14872.md) · `q23` of the #3312 review's second round (`rv3312r2-q8m4/q/`) · filed 2026-09-30 against master `4ff12b994`**

Repro:

    type I = { f: i32 }
    type J = { f: i32 | null }
    type H = { h: J }
    const x: i32 = 3
    const b: J = (if x > 0 { { f: 5 } } else { null }) ?? { f: 6 }
    b.f = null
    print(b.f ?? 70)
    // vl check: rc 0.  vl run: invalid module inside the module's top-level code: type mismatch: expected (ref null $type), found (ref null $type) (exit 70)

Want:

    70

#### Mechanism

Every record here is a fresh literal, so the ruling admits the program. The join
bound first and annotated (`const o: J | null = if …; const b: J = o ?? { f: 6 }`) runs, and so
does the join with no `??`. Inside a function the same binding was invalid wasm too: both
literals were built at the record the join was typed at (`{f: i32}`) rather than at `J`, because
the rep stamp did not look through a `??`. An un-annotated `const o = if …` bound first fails
without the `??` too, which is D14872.
