### D3389 — a module-scope `??` over a record if-join, delivered to a record that stores a field differently, builds invalid wasm

**check-clean invalid wasm · clause 1 · `q23` of the #3312 review's second round (`rv3312r2-q8m4/q/`) · filed 2026-09-30 against master `4ff12b994`**

Repro:

    type I = { f: i32 }
    type J = { f: i32 | null }
    type H = { h: J }
    const x: i32 = 3
    const b: J = (if x > 0 { { f: 5 } } else { null }) ?? { f: 6 }
    b.f = null
    print(b.f ?? 70)
    // vl check: rc 0.  vl run: invalid module inside the module's top-level code: type mismatch: expected (ref null $type), found (ref null $type) (exit 70)

Want:

    70

#### Mechanism

Not traced. Every record here is a fresh literal, so the ruling admits the program. The join
bound first and annotated (`const o: J | null = if …; const b: J = o ?? { f: 6 }`) runs, and so
does the join with no `??`. Inside a function the same binding is invalid wasm too (re-graded on
master `fb695dcc`): both literals are built at the record the join was typed at (`{f: i32}`)
rather than at `J`, and an un-annotated `const o = if …` bound first fails alike.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| inside a function | still invalid wasm (re-graded on `fb695dcc`) | no |
| the join bound first to a `J \| null` | runs, `70` | **yes** (in place under `??`) |
| the write `b.f = null` removed (print `b.f ?? 70`, want `5`) | same invalid wasm | no |
