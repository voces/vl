### D14543 — a loop variable's loop is found by two finders, because an instance shares read nodes with its template

**closed 2026-10-29 · runs today and must keep running · one finder, `frameElemLoopOfRead`, asks the plan by DECLARATION (`parentLoopOfDecl`), which a shared read node cannot miss, and walks the body only where the plan has no row; `frameElemLoopAtRead` is deleted · a second producer, not a wrong answer: `frameElemLoopOfRead` walks the frame body and `frameElemLoopAtRead` reads the frame's loop plan, for one fact · filed 2026-10-27 against master `3aa75082e`**

Repro:

    function h<T>(x: T, y: T) {
      for e in [1, 2].filter((e) => e > 5) { print(e) }
      for e in [x, x].slice(0) { print(e) }
    }
    const bt: boolean | null = true
    h(bt, bt)

Want:

    true
    true

#### Mechanism

Both finders answer the same question: which `for … in` loop of a frame has, as its first
variable, the declaration a read names (`fiDecl1 == identDeclOf(read)`, emit_capture_frames.vl).
`frameElemLoopAtRead` asks the frame's cached plan (`parentLoopAt`, emit_base.vl), whose rows are
post-order node ranges. A mono instance's body can hold a read node it SHARES with its template,
and that node's index lies outside every range of the instance's copy. So the plan answers -1,
and the instance prints the element's `i32` rep (`1`) instead of `true`.
`frameElemLoopOfRead` walks the body (`modLoopHolding`, `nodeSubtreeHas`), so it finds a shared read.

Which finder serves which callers:

| finder | callers |
| --- | --- |
| `frameElemLoopOfRead` (walk) | the two former `loopVarForIn` sites in emit_classify.vl |
| `frameElemLoopAtRead` (plan) | `readLoopNodeOf` (emit_local_scope.vl), and through it `readLoopElemKind`, `readIsLoopBox` and `readLoopVarIsLitAtom` |

Routing the walk's callers through the plan turns the witness and two cases red
(`generics/for-in-generic-call-result-at-pin.vl`, `generics/for-in-over-mixed-reads-at-pin.vl`).

#### Deletion

One finder survives, decided by which fix is right:
- either an instance gets its own read node for every read in its body, so the plan's ranges own them;
- or the plan indexes shared nodes.

Then the other finder is deleted.

Landed as a third option: the read names its declaration (`readLoopVarDecl`), and the
declaration, unlike the read node, belongs to the instance's copy, so the plan's declaration
index (`parentLoopOfDecl`) finds the instance's loop. A full-tree comparison over 17,265 files
found no output or module that differs.
