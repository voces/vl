### D5612 — a generic handed to an un-annotated parameter the checker leaves unbound is not instanced at the call the body makes

**closed 2026-10-17 by lane L1 · runs, prints `3` · was loud emit reject · clause 2 · with no checker binding at the call, the hole takes the one signature the flow table pins the argument at past it (`monoHoleGenFnTy`, `fnFlowDeclPinTys`) · pins: `tests/cases/closures/generic-hole-fn-value-pinned-past-hole.vl` · found closing [D5402](D5402.md) · filed 2026-10-17 against master `7fe51e77c`**

Repro:

    function add(a, b) { return a + b }
    function apply(g, x, y) { return g(x, y) }
    print(apply(add, 1, 2))
    // vl check: rc 0.  vl run: emitProgram: cannot take the generic function `add` as a value — a function value carries ONE signature, and parameters `a`, `b` are un-annotated (they would default to i32). No call site pins `add`, so there is no inferred signature to adopt — annotate the parameters, or call `add` directly by name

Want:

    3

#### Mechanism

From the ablation only. `apply` is itself a hole function, instanced per call, and the checker
binds no type for `g` at `apply(add, 1, 2)`: `g`'s signature is fixed only by the instance's own
call `g(x, y)`. `monoHoleGenFnTy` read only the checker's binding, so the hole had no pin and
the refusal's "no call site pins `add`" was the visible floor.

The close: when the binding is open and the argument names a generic, the hole takes the one
closed pin the flow table carries downstream of the argument (`fnFlowDeclPinTys`), and the
generic is instanced at it. Two calls at different types (`apply(add, 1, 2)`,
`apply(add, 1.5, 2.5)`), an alias of `add`, string operands and a declared generic all run.
