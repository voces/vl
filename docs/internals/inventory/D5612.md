**closed 2026-10-17 by lane L1 · runs, prints `3` · was loud emit reject · clause 2 · with no checker binding at the call, `monoHoleGenFnPin` instances the generic's own signature at the one closed pin the flow table carries past the argument (`monoHoleGenFnFlowTy`, `fnFlowDeclPathPinTysOf`) · pins: `tests/cases/closures/generic-hole-fn-value-pinned-past-hole.vl` · found closing [D5402](D5402.md) · filed 2026-10-17 against master `7fe51e77c`**

#### Mechanism

From the ablation only. `apply` is itself a hole function, instanced per call, and the checker
binds no type for `g` at `apply(add, 1, 2)`: `g`'s signature is fixed only by the instance's own
call `g(x, y)`. The hole pin read only the checker's binding, and the D5530 flow pin delivered
only a generic that declares type parameters, by NAME, with a `void` return. So `add` had no
pin, and "no call site pins `add`" was the floor.

The close is one pin driver, `monoHoleGenFnPin`. It takes the checker's binding, and failing
that the generic's own signature instanced (`bindGenWalk`, `substTyDeep`) at the one closed pin
the flow table carries for the argument's read, frame-aware through `monoDeclPathPins`. Both
paths deliver the same way. Two calls at different types, an alias of `add`, string operands
and a declared generic all run.
