### D4017 — a binding of a generic function delivered to a concrete function parameter is held at that type, so a later use at another type is refused

**closed 2026-10-17 by lane L1 ([D5290](D5290.md)) · runs, prints `I 1 I s` · was loud check reject · an alias carrying a generic's own signature is bound afresh at each delivery and not parked (`tyIsForeignGenericSig`) · pins: `tests/cases/closures/generic-fn-value-demand-other-generic-same-tyvar-name.vl` · clause 2 · found in review of #3531 (`rv3531/i08`, `i08b`, `i08c`) · filed 2026-10-11 against master `5d4cd14dc`**

Repro:

    function id<T>(x: T): T { print("I"); return x }
    function call2(f: (x: i32) => i32, g: (x: string) => string) { print(f(1)); print(g("s")) }
    function main() {
      const h = id
      call2(h, h)
    }
    main()
    // vl check: argument 1: expected (i32) => i32, got (string) => string

Want:

    I
    1
    I
    s

#### Mechanism

Not located. Under ruling C a binding seeded with a generic keeps the generic type, and a call
through it at any type is accepted. A delivery is not treated the same way. The first delivery
into a concrete function parameter binds the binding's type variables, and every later use at
another type is checked against that binding. The checker owns this. Lane CK's #3508
re-checks calls through a written binding but not deliveries, and the witness grades the same
with #3508 applied.
