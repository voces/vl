### D12880 — a lambda pushed onto a list of hole functions from inside a hole function, capturing its hole parameter, reaches the generic-function floor

**closed 2026-10-25 by lane L1 · runs, prints `2 9` · an element of a list of hole functions reads the hole parameters of the function it is nested in at the one type every instance so far binds them to (`monoOneInstHoleBinds`), and a lambda clone too open to carry a type answers its result through its template (`monoLamCloneTmpl`, emit_mono.vl) · pin: `tests/cases/closures/hole-lambda-on-hole-fn-list-capturing-hole-param.vl` · `add` called at two value types stays this refusal, since its one lambda would need two instances · a hole function whose instance the walk reaches only after the loop is [D12940](D12940.md) · was loud emit reject · `vl check` rc 0 · clause 2 · CAPABILITY: the same program with `add(k: i32)` runs · found closing [D12800](D12800.md) · filed 2026-10-25 against master `d015bc7dd`**

Repro:

    function snd(a, b) { return b }
    function apply2(g) { print(g("x", 2)) }
    const fs = [apply2]
    function add(k) { fs.push((g) => { print(g("z", k)) }) }
    add(9)
    for f in fs { f(snd) }
    // vl check: rc 0.  vl run: emitProgram: a generic function is passed to a function value whose parameter type names a type parameter this closure does not bind

Want:

    2
    9

#### Mechanism

The list's elements are `apply2`, the lambda as written and `add`'s instance's clone of it
(D12800). The call through the loop types them at the top-level frame, where `k` is `add`'s
type variable `?add.0`: the lambda's parameter `g` took its pins from `g("z", k)` with
`?add.0` unbound, and the clone carries no type at all, since `monoCloneLambdaSubst` records a
clone's type only when it is closed and `g` is still a hole. Both now resolve: `?add.0` binds
from the instance rows (`monoHoleSubN`) when every instance agrees on it, and the clone's
result is read off its template under that binding.
