### D4884 — an `if` of two list literals bound to a local in a generic body builds a union box where an `f64` list is expected

**closed 2026-10-26 — now prints `3` `2` · was check-clean invalid wasm, clause 1 · the monomorphizer annotated the instance's copy of `v` with the apart join `f64[] | i32[]` while the elaboration types the `if` as `f64[]`, the one list the literal adapts to at the pin; the copy now takes the elaboration's list · found by L2 §13.30, beside D4883 · filed 2026-10-15 against master `5be21bb0a` · pin: `tests/cases/generics/type-param-list-join-literal-arm-adapts.vl`**

Repro:

    function h<T>(t: T, b: boolean) {
      const v = if b { [t, t] } else { [1, 2, 3] }
      print(v.length)
    }
    h(2.5, false)
    h(2.5, true)
    // vl check: rc 0.  vl run: prints 3 then 2

Want:

    3
    2

#### Mechanism

At `T := f64` the checker kept the template's join apart as `T[] | i32[]` (D2832), and
`monoApartJoinAnn` annotated the instance's copy of `v` with that join at the pin,
`f64[] | i32[]`. The elaboration types the `if` at that instance as `f64[]`, since the literal
`[1, 2, 3]` adapts to the pin, and reads of `v` follow it. The two disagreed: a read used the
union box as a list and failed validation, and once the copy's declaration read its
annotation's type, `v` was stored as a box the `f64[]` read saw as empty (`0` `2`). The
annotation now reads the elaboration's type for the join instead of substituting the
template's, so the storage, the literal's build and the reads all name `f64[]`. The same holds
at `T := i64`.

The mirror spelling with the literal first (`if b { [1, 2, 3] } else { [t] }`) still fails
validation, and its annotated twin `const v: T[] = …` is refused by the checker at the pin.
Neither moved with this fix.
