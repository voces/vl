### D4884 — an `if` of two list literals bound to a local in a generic body builds a union box where an `f64` list is expected

**check-clean silently wrong value · prints `0` `2` · clause 1 · found by L2 §13.30, beside D4883 · filed 2026-10-15 against master `5be21bb0a` · it failed validation until the monomorphizer's copy of a declaration read the type of the annotation it was given (2026-10-26)**

Repro:

    function h<T>(t: T, b: boolean) {
      const v = if b { [t, t] } else { [1, 2, 3] }
      print(v.length)
    }
    h(2.5, false)
    h(2.5, true)
    // vl check: rc 0.  vl run: prints 0 then 2

Want:

    3
    2

#### Mechanism

At `T := f64` the instance's copy of `v` carries a synthesized annotation `f64[] | i32[]`, so
`v` is stored as a union box holding the `else` arm's `i32[]`, while the read `v.length` is typed
`f64[]` and reads as an empty list (`v[0]` traps out of bounds). Before the copy read that annotation's type, the
read took `v` as the `f64[]` list the initializer's elaboration names and used the box as a list,
which failed validation. Both outcomes come from the annotation: the join is `f64[]` once the
literal `[1, 2, 3]` adapts to the pin, so a one-list annotation is predicted to fix both.

Not yet ablated past the table below. Both arms are fresh list literals, so the join at
`T := f64` is `f64[]` and each literal should be built at it, as the direct spelling does. The
local's `if` join is re-typed at the pin outside the return-set path D4862 fixed. Possibly one
family with D4883; that is a prediction until one fix moves both.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| the direct spelling `t: f64` | runs, `3` `2` | **yes** (the type parameter) |
| `T := i32 \| null` | a loud emit reject (D4883) | **yes** (the `f64` pin) |
| `print(v[0])` added | prints `0`, then traps out of bounds at `v[0]` (was invalid wasm) | no |
