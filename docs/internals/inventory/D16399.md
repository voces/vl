### D16399 — `==` over a record whose field is a union and a record whose field is a member of it is refused when the union side is on the left

**closed 2026-11-15 · runs, prints `true` · was loud check reject, clause 2 (`{f: A | B} isn't equatable (a field is not value-comparable)`) · fixed by judging a pair that compares field by field per field pair (`recEqFieldWise`, `check_ty_relate.vl`), as the bare compare is · fixture `tests/cases/structs/eq-union-field-vs-member-field.vl` · found grading D16395's matrix · filed 2026-11-15 against master `68cf81051`**

Repro:

    type A = {a: i32}
    type B = {b: string}
    const x: {f: A | B} = {f: {a: 1}}
    const y: {f: A} = {f: {a: 1}}
    print(x == y)

Want:

    true

#### Mechanism

`eqRefusals` (`check_ty_relate.vl`) asked whether the LEFT operand's record is equatable as a
whole, and `isEquatable` holds a general union not value-comparable. So `{f: A | B} == {f: A}`
was refused, while `{f: A} == {f: A | B}` passed and ran through D16394's field-wise compare,
which tests the arm as a bare `A | B == A` does. By the rule the coordinator settled from the
owner's ruling (2026-11-15), a union compared with a member is legal inside a record as it is
bare. A pair compared field by field is now judged per field pair. A field that has no value
equality (a map, a function) is still refused, now by that field's own sentence.
