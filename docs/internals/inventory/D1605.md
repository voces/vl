### D1605 — a monomorphized `__array_new__` fill had no element name, and the slot-0 clamp handed it the first-interned ref row

**closed 2026-09-04 by reading the fill's type off the INSTANCE's own annotation
(`instAnnTyNameOfExpr`) and by making the `__array_new__` emit site take the STRICT slot ·
was check-clean invalid wasm whenever one generic `T[]` constructor was pinned at two
different ref elements, and at several single pins too · 23 of 82 grid cells moved
SILENT→runs, 0 runs lost · filed 2026-09-04 against master `a42a776e`**

Found by #2572 while adding `filled(n, v)` to `std:array`; the consumer ask behind that
export is glean's R8 (VL-019). `scripts/capability-probes/generic-array-new-struct-then-nested.vl`
is the standing witness and now runs.

Repro (before the fix: `vl check` rc 0, then `the emitted module failed to validate inside
`filled$1`: type mismatch: expected (ref null $type), found (ref $type)`; now: prints `-1`
then `0`):

    type Node = { count: i32, symbol: i32 }
    function filled<T>(n: i32, v: T): T[] { return __array_new__(n, v) }
    const nodes: Node[] = filled(2, { count: 0, symbol: -1 })
    const rows: i32[][] = filled(2, [0, 0])
    print(nodes[1].symbol)
    print(rows[1][0])

#### Mechanism

`monoCloneBody` rebuilds only an instance's statement SPINE — "every leaf expression, a
nested lambda included, is shared". So the `__array_new__(n, v)` call node and its fill
node are the same arena nodes for every instance, and their recorded type is still the
template's `T`. `refListElemNameOfExpr`'s kind-3 arm had exactly two channels for the
element name: `structIndexOfExpr(fill, fnIx)`, which is instance-aware but answers only
for a named struct, and `tyToEmitName(nodeTyIxOf(fill))`, which is instance-BLIND. For any
instance whose element is not a named struct the arm therefore answered `""`,
`rlSlotByName("")` returned -1, and **`refListSlotOfExpr` clamped that miss to slot 0** —
a real row, the first ref element the module interned. `emitArrayNewIntr` then read
`rlBackIdx[0]`/`rlWrapIdx[0]` and built the list at another element's heap types.

The instrumentation is the whole story in two lines. Tracing the failing pair (an
`emitFail`-channel note appended per visit and flushed once at the end of `emitProgram`,
since `emitFail` keeps only the first message):

    TABLE [0]Node/k1/b5/w6 [1]i32[]/k4/b7/w8
    EMIT fn=41 call=13 name='Node' strict=0 slot=0 paramAnn='Node'
    EMIT fn=46 call=13 name=''     strict=-1 slot=0 paramAnn='i32[]'

Same `call=13` twice, once per instance; the second resolves no name, clamps to 0, and
`paramAnn` — the instance's own parameter annotation — is the channel that knows. The
disassembly says the same thing: `$1` has signature `(param i32 (ref $4)) (result (ref $8))`
and a body reading `struct.new $6 (array.new $5 …)`, which are `$0`'s (the `Node`
instance's) types.

The ORDER in the headline is a consequence, not the mechanism: with the nested list
interned first the clamp lands on the right row by luck, which is why nested-then-struct
ran and either pin alone ran. Two nested-list elements in either order (`i32[][]` then
`string[][]`) fail identically, and so do two SEPARATE generic functions, neither of which
an order-shaped story explains.

The fix adds `instAnnTyNameOfExpr` — the instance's own parameter, else local `LetDecl`,
annotation — as a rung BELOW the existing `nodeTyIxOf` channel, so no answer that already
resolved changes. This is D941's channel (`monoArgTyName`'s fourth one) asked by the
element-name resolver; D1470's technique, reading the pin off the CALL node, does not
transfer, because the call node is shared by every instance and carries `T`. With the
name channel working, the emit site takes `refListSlotOfExprStrict`, so an element that
still does not resolve refuses through the arm's existing loud floor instead of borrowing
row 0 — the hazard `refListSlotOfExprStrict`'s own contract names (D791).
