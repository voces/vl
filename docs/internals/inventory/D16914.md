### D16914 — a record of two list fields of different un-annotated functions builds an invalid module

**closed 2026-11-16 by lane AE — the witness prints `4` · mono pinned the record at the elaboration's slot fact, which closes every function field to a signature, so a field holding a tagged set (`{inc0}`, called through) lost its tag in the record's row while its literal and reads stored the set's ids: `monoPinObjFields` (`compiler/emit_mono.vl`) now keeps such a field's tagged type and builds the record from its fields, and a `let`'s writes agree with it (`monoLetWritesAt`) · fixture `tests/cases/closures/record-of-two-hole-fn-list-fields-one-called.vl` · was: check-clean invalid wasm · clause 1 · found by lane AE grading the D16834 position matrix · filed 2026-11-16 against master `6cd505a50`**

Repro:

    function inc0(a) { return a + 1 }
    function dbl(a) { return a * 2 }
    const r = { f: [inc0], g: [dbl] }
    print(r.f[0](3))
    // vl check: rc 0 (one warning, `r.g` never read).  vl run: invalid module, type mismatch in the top-level code

Want:

    4

#### Mechanism

The set called through (`{inc0}`) is tagged, so the field's literal builds an `i32` list of ids and
its reads load one; the other set is not. `monoPinFieldContainers` pins the record's open field
(`g`) and types the record at the elaboration's slot fact, which closes `f` too, to a closure list;
the record's row was minted from that type, so the literal stored an id list into a closure-list
field.
