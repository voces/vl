### D16813 — a `let` holding two hole functions pins both at the first one's call type, so a later call of the other at another type is refused

**loud check reject · `vl check` rc 1, `cannot assign (f64) => f64 to (i32) => i32 (the body of `hid` at the call's argument types)` · clause 2 · order dependent: with the two calls swapped it runs · found by the hof oracle fuzz (`ho_s10_0036`, seed 10) · filed 2026-11-16 against master `5692931a4`**

Repro:

    function hid(x) { return x }
    function kid(x) { return x }
    let g4 = hid
    g4 = kid
    print(kid(1.5))
    print(hid(100))
    // vl check: rc 1, cannot assign (f64) => f64 to (i32) => i32 (the body of `hid` at the call's argument types)

Want:

    1.5
    100

#### Mechanism

Not located yet. The refusal is raised for the `BND_LET` demand that the store into `g4` records
(`check_assignable.vl`, the "body of `…` at the call's argument types" arm). That demand is re-checked
when each call's arguments retype a callee body. `g4` is never called, but writing `kid` into it
apparently fixes its function type at `kid`'s first call, `(f64) => f64`. When `hid`'s body is
then retyped at `hid(100)`, the demand finds `(i32) => i32` against that type. Whichever function
is called first decides the type.

| `let g4 = gid` with `g4 = hid` (the generic first) | runs | **yes** |
