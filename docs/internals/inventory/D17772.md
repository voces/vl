#### Mechanism

Traced to the edge, not fixed (COV-CALL, 2026-11-28, time-boxed). The reject is not the
checker's own pass: it is raised in the elaboration's quiet re-check of an instance of `apN`
(`elabCapLive`, emit_elab.vl) and reported as the program's error by `elabErrorNote`. `apN` is
enqueued from the root callback notes (`elabCbRoot*`, noted by `.map`'s arm in
check_member_call.vl) at `?apN.0 = ((_) => _)[]`, the right element, and again from the
"callback at the set's rep" loop (`elabSetRepTy`) at the `() => void` stub, since no member
instance exists yet there; the instance whose re-check fails is keyed at the element and reads
`r[0]` as `i32`. The only set tagged is `{inc7}`, by the check, from the annotated `.map(ap)`;
`inc6` and `inc7` carry distinct types and sets (`elabFnValNote`), so it is no type-keyed
collision. Muting the callback-rep keys' diagnostics (as `elabReprKeys` are) does not move it.
The likely mechanism (coordinator, 2026-11-28) is that stub enqueue: an instance keyed before
its set has a member instance, the "stub as an instance key" family of D17741; that row's close
re-grades this one.

#### Close (CENSUS, 2026-11-28)

The stub enqueue was not it. The annotated `.map(ap)` tags `{inc7}`, so `fnTagEtaAgain` restarts
the check, and `initChecker` empties the type arena. `elabCbNote`'s root rows
(`elabCbRoot*`, check_elab_cap.vl) survived the restart, and `elabCapReset` runs once per
compile. So the first walk's `?apN.0 = ((_) => _)[]` (row 377) was enqueued after the restarted
walk had re-minted row 377 as `i32[]`. The restarted walk notes the root again at its own row,
382. Statement order only decides which type lands on the stale index. A probe of the element
field (the control: the same probe on the failing repro shows `direct=340` at the note and
`direct=0` at the enqueue, with no `tyPinElem` write between) found no in-place write.
