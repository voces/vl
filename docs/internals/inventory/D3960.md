### D3960 — a `let` seeded with a generic function accepted a concrete function and was then called at another type

Repro:

    function inner<U>(u: U) { print("I"); print(u) }
    function q(n: i32) { print("Q"); print(n) }
    function main() {
      let k = inner
      k = q
      k(true)
    }
    main()
    // vl check: rc 0 before the fix.  vl run: prints `Q` then `1`; with `k("s")` it traps, indirect call type mismatch

#### Mechanism

`let k = inner` binds `k` at `(U) => void`, and a type parameter is gradual, so the write
`k = q` of an `(i32) => void` was accepted and every later call through `k` was checked against
`(U) => void` at whatever type it passed, while the binding held `q`. The owner ruled (option C,
TypeScript's): a `let` whose un-annotated initializer is a generic function, or an un-annotated
lambda, keeps that generic type. A generic of compatible shape may be written to it, and calls
through it stay generic; a concrete function written to it is refused at the write, whatever
the calls (`fsbNoteStore`), with a fix that annotates the binding to hold that type
(`generic-binding-concrete-write`, applied by `check --fix`). The rule needs no ordering: an
un-annotated alias of such a binding is one too, and a write to a module binding above its
declaration is refused when the declaration marks it (`fsbMark`).
