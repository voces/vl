#### Mechanism

Re-derived 2026-10-16 on master `ed42d37ad`; the fold named when the row was filed is not the
cause. `buildVariantTwins` does fold the unrolled arm onto the rolled one, and the repro still
refuses with no `next` field at all (third cell below). The defect is the read of a field that
every arm shares, when one arm stores it as an interned atom (a multi-member string literal
union, `"a" | "b"`) and another stores it as a string (a lone literal `"end"`, softened, or
`string`). The checker types `n.kind` as `"a" | "b" | "end"`, an atom rep.
`sharedUnionFieldPlan` sees the mixed storage codes and `sharedFieldArmsBoxable` declines, so
the read falls to the floor in `emitMem`. A close needs that plan to read at atom rep and
convert each string arm to its atom over the read type's members.

Minimal witness, inline and un-annotated:

    function f(n: { kind: "a" | "b", v: i32 } | { kind: "end" }): i32 { if n.kind == "end" { return 100 } 1 }
    print(f({ kind: "end" }))
    // vl run: field access receiver is not a struct

With a declared alias the message is `field access but no struct type declared`.
