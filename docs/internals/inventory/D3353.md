### D3353 — an uninitialized function-typed `let` traps the compiler when a closure-valued alias asks for its source

**closed 2026-09-30 (`anonLeafFnValueTargetGo` and `anonLeafFnValueNames` in `compiler/emit_collect.vl` read a binding with no initializer through its assignments alone) · was compiler trap · filed 2026-09-30 against master `455e553ca` · fixtures `tests/cases/functions/uninit-function-let.vl`**

Repro:

    type Box = { f: (i32) => i32 }
    function apply(g: (i32) => i32, v: i32): i32 { g(v) }
    function h(n: i32): i32 {
      let y: (i32) => i32
      y = (x: i32) => x * n
      const b: Box = { f: y }
      const c = () => y(2)
      let z = y
      z = y
      apply(y, 1) + b.f(3) + c() + z(5)
    }
    print(h(4))
    print(h(1))
    // vl check: rc 0.  vl run: the compiler itself trapped (out of bounds, unwrapParen)

Want:

    44
    11

#### Mechanism

`anonLeafFnValueTargetGo` (`compiler/emit_collect.vl`, reached from `collectAnonShapes`) walks
every node that binds a name and reads `unwrapParen(n.letInit)` of each `LetDecl`, which for a
`let` with no initializer indexes the arena at -1 and traps. The walk already reads the
binding's assignments through its `BinExpr` arm, so a binding with no initializer is skipped.
Guarding `unwrapParen` itself instead cost 0.34% of plumb-shape guest fuel, since every
classifier calls it. It is reached before the emitter's own refusal of such a local (D3256), so
on master this program trapped rather than refusing.
