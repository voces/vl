#### Mechanism

D16764 instances a lambda written at the call, whose parameter is annotated at the element type,
at the receiver's build: the mono pass records the build on the annotation, so the parameter is
laid out there. The lambda's result is still the checker's (`elabRetOf` takes the closed result
of a non-generic declaration), so a `map` result holding the parameter, or a record built from
it, would be laid out at the annotated record. `recCbTakesBuild` keeps refusing those. A named
function or a `const`-held lambda is not keyed at the build for an annotated parameter
(`elabCbAtBuild` takes only a lambda at the call), so they are refused too.

#### Findings (parked, 2026-11-16)

- **Named or `const`-held function.** It waits on D3992's declaration rewrite: an instance clone
  of the function at the build. D16764's route records the build on the parameter's annotation
  node, which is safe only for a lambda written at the call (one use). On a named or held
  function, the annotation is shared, so the build would leak to every other caller.
- **Identity or record `map`.** Lifting the refusal for `(y: { f: null }) => y` builds a module
  that fails to validate. The lambda takes `J` but returns the narrow struct; mono records the
  closure signature `J → J`, but the function's own functype result is not derived from it.
  A rung in `frsRecordedRetCore` (`fn_ret_shadow.vl`: an annotated parameter handed back
  returns where it is laid out) had no effect, so the trace stops there. Read next: where the
  function result row is chosen (`fRetKind`, `cloRetValSlot`), against mono's records.
