### D2853 — a record's function-valued field built in a hole-parameter function reads back in the first instance's format at every pin

**closed 2026-09-27 · was check-clean silently wrong, clause 1, on master `1df19732b` · found by the #3220 round-3 review (`r3_fn/loc_true_7_*`) · filed 2026-09-27 · fixture `tests/cases/closures/record-closure-field-bound-in-maker-reads-per-pin.vl` · residue [D2862](D2862.md)**

Repro:

    function mk(x) {
      const r = { f: x, g: () => x }
      return r
    }
    const a = mk(true)
    print(mk(7).g())
    // vl check: rc 0.  vl run: prints `7`.  Was: prints `true`

Want:

    7

#### Mechanism

The closure field's lambda is shared by both instances of `mk`, so its banked return kind
(`fRetBool`) is the first pin's. `fieldCloCallIsBool` already reads a field closure's result
per instance, by following the receiver to its maker instance and reading the returned object
literal's field through that instance's pinned parameters. It read only a maker whose return
expression is the literal itself; `return r` over `const r = { ... }` fell through to the shared
`fRetBool`. The maker's returned `const` is now followed to its object-literal initializer
(`makerRetObjLitOf`).

The same grid found the literal-set face: `mk(k).f` with `k: K` printed `0`. A record with a
function field keeps its plain identifier fields as `i32` slots with no atom table, so the read
never claimed an atom. `exprIsLitAtom` now claims a plain `i32` slot whose read the checker types
as a string literal-set alias; that slot can only hold the atom id.
