### D15063 — a `const` of an `if` choosing two functions, pushed onto a list of its set and called, is re-typed at the slot's closed type and held as a closure where the list holds its ids

**closed · runs, prints `6` · was check-clean invalid wasm · clause 1 · fixture `tests/cases/closures/choice-of-functions-stored-into-list-of-its-set.vl` · found closing D15060 · filed 2026-11-02 against master `dd9349ae`**

Repro:

    function inc0(a) { return a + 1 }
    function dbl0(a) { return a * 2 }
    const b = true
    const fs = [dbl0]
    const g = if b { inc0 } else { dbl0 }
    fs.push(g)
    print(fs[1](5))
    // vl check: rc 0.  vl run: the emitted module failed to validate in the top-level code: expected (ref $2), found i32

Want:

    6

#### Mechanism

The tag decision tags the choice's set and holds the list's elements as its ids. The
monomorphizer then met the read `g` delivered at the list slot's closed function type and, as for
any binding of an `if` choosing open functions (`monoCoerceChoiceBinding`), re-typed the binding
and the `if` at that closed type. The closed type carries no set, so the binding's cell became a
closure while the push stored it as an id. Closed: a choice whose set is tagged is delivered as
it is. A list literal holding `g` never reached that coercion, which is why it ran. The same
re-typing made a tagged choice delivered to a closed function type (`const h: (x: i32) => i32 =
g`, or `apply(g)`) invalid wasm inside the adapter; that spelling runs too, fixture
`choice-of-functions-in-list-of-its-set-delivered-at-closed-type.vl`.
