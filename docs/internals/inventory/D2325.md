### D2325 — a closure-typed PARAMETER shadowed by a same-named block-local `const` resolves the parameter's signature inside the shadow's own block

**CLOSED 2026-09-24 — `calleeCloSigKeyAt`'s loop-variable/parameter/anon-leaf rungs
(`loopVarCloSigKey`, `paramCloSigKey`, `anonLeafCloBindSigKey`) matched by bare name with no
position check and ran BEFORE the positioned rungs; a block-local `const g` of the same name
as a parameter or loop variable never got the chance to shadow it. `monoBakeCallback`'s
direct-call rewrite (`emit_mono.vl`) had the identical unconditional-by-name shape. And
`parentLetOfAt` itself (D2316) had a second gap: when a name has exactly ONE tracked
`LetDecl` in the function it answered unconditionally, without checking whether the reader's
position falls inside that LetDecl's own block — sound for D2316's "two sibling LetDecls"
problem, unsound the moment a PARAMETER or loop variable (which `parentLetOfAt` does not
track at all) shares the name.**

Repro:

    function f(g: () => f64): string {
      let out = "\{g()}"
      {
        const g = () => "inner"
        out = out + "|" + g()
      }
      out
    }
    print(f(() => 1.5))
    // vl check: rc 0.  vl run (pre-fix): invalid module — the emitted module failed to
    //   validate inside `f$m0`: type mismatch: expected (ref null $type), found f64
    // Expected: 1.5|inner

#### Mechanism

Three independent rungs answered "what does the name `g` denote here" without ever asking
WHERE `here` is:

1. `paramCloSigKey(fnIx, name)` scans `fnIx`'s params and matches by bare name — it runs
   before `identFnTypeAnnNameAt`/`identClosureFeAt`/`identCopySourceAt`, the only rungs that
   already took a position (D2316), so a param match always won even when the actual call sat
   inside a block whose `const` of the same name should have shadowed it.
2. `loopVarCloSigKey`/`anonLeafCloBindSigKey` are the same shape: name-only, unconditional,
   ahead of the positioned rungs.
3. Even fixing the ordering (skip these three rungs when a block LetDecl shadows the
   position) needed `parentLetOfAt` itself to grow a bounds check it did not have: for a name
   with no tracked DUPLICATE `LetDecl`, it returned the sole binding regardless of `atIx`,
   because that was safe under D2316 (a checker-validated program never asks about a position
   outside a LetDecl's own block unless something ELSE — a param, a loop var — is also in
   scope there, and `parentLetOfAt` only tracks `LetDecl`s). A parameter is exactly that
   "something else": `parentLetOfAt(fn.fnBody, sid, atIx)` had never been asked to fail for a
   position outside the block of a name's only `LetDecl`.

`monoBakeCallback` (the monomorphizer's concrete-callback-specialization pass) carried the
identical bug on a separate tree walk: it rewrites a call `g(...)` to a direct call to the
baked callback whenever the callee's `Ident` spells the param's name, with no shadow check —
so a block-shadowed `g()` inside a baked clone was ALSO rewritten to call the outer param's
function, producing check-clean invalid wasm (or, once the param path above was fixed,
`emitProgram: field access receiver is not a struct` / an `indirect call type mismatch`
trap) at the shadowed call site.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the name collision (`g`/`h` instead of `g`/`g`) | runs | **yes** |
| the differing return kind (both closures return `f64`) | runs (same classification, harmlessly) | **yes** |
| the block (shadow moved to a sibling top-level `const` in the same scope) | check rejects, `redeclared g` — a different, unrelated diagnostic | **yes** |
| the call site made a monomorphized "baked callback" clone (`f(() => 1.5)` inlines the argument) | still fails, in the SEPARATE `monoBakeCallback` mechanism, once the `calleeCloSigKeyAt` rung is fixed alone | **yes**, its own ingredient |
| annotating the shadow's type | no change — the unpositioned rung fires before any annotation is even consulted | no |

#### Grading list

The matrix in `tests/cases/closures/param-shadow-*.vl` (param shadowed in a plain block, a
loop body, if/else arms, match arms; the param read again after the shadow closes; a `for g
in closures` loop variable shadowed inside its body; a nested closure defined inside the
shadow's block capturing the shadow vs. one defined outside capturing the param; every
adjacent (param kind, shadow kind) pairing over i32/f64/string/struct/list) must all keep
running and print the values each case is built to distinguish.
`param-shadow-loopvar.vl` and `param-shadow-nested-capture.vl` pass even on the PRE-FIX
compiler — loop variables resolve through `scopeSlotOf` (live-slot based, already positioned)
and captures resolve through `capturedBindingFrameOf` (frame-based, already positioned), not
through the three name-only rungs this row fixes; they stay in the matrix as controls, not
because they discriminate this defect. D2316's own fourteen-case matrix
(`tests/cases/closures/sibling-fn-blocks-*.vl`) and its two other fixtures must keep running
unchanged — this row narrows three EARLIER rungs and closes a gap in the shared
`parentLetOfAt` primitive; it does not change D2316's own duplicate-block resolution.

See D2326 for the analogous, still-open gap in the value-union member-set ladder
(`unionNameOfIdentSid`/`unionDeclTyIxOfIdentSid`/`startBlockLetRowOfSid`), which shares this
row's shape (an unpositioned name-only match ahead of, or instead of, a positioned one) but
was left unfixed here because closing it needs threading a reader position through roughly
thirty call sites across two files, a larger and riskier change than this row's.
