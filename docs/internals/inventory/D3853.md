### D3853 — a nested generic that redeclares its enclosing function's `T` has its body's constraints checked at the enclosing function's pin

**closed 2026-10-08 by lane SC · runs · was a loud check reject, a valid program refused (clause 2) · found in review of lane SC (#3444, `rv3446-probes/h/e4_valid.vl`) · filed 2026-10-08 against master `5b2ec9f85` · pins: `tests/cases/generics/nested-generic-redeclaring-type-parameter.vl`, `tests/cases/generics/error-nested-generic-redeclaring-type-parameter.vl`**

Repro:

    function a<T>(x: T) { function b<T>(y: T) { const n: i32 = y; print(n + 1) }; b(1); print(x) }
    a(true)
    // vl check: rc 1, `cannot assign boolean to 'n' of type i32 … (the body of `a` at the call's argument types)`

Want:

    2
    true

#### Mechanism

The checker records a deferred constraint for each assignment of a type-parameter value
(`const n: i32 = y`) and validates it at the pins of the function that OWNS it. Only a
registered top-level declaration owns constraints (`cstrOwnerStack` in `checkFuncDecl`), so
`b`'s constraints are owned by `a`. At `a(true)` they are substituted by NAME, `T → boolean`,
and `b`'s own `T` is read as `a`'s. With `b<U>` nothing names `U` at `a`'s pin, so the
constraint is left open and the program runs. The monomorphizer tells the two apart since
D3840 (#3444), but this refusal fires earlier, in the checker. A fix needs the constraint to
carry which declaration's `T` it names: a nested generic's own constraints should be validated
at its own pins. Simply making `b` an owner would also skip `a`-owned constraints that `b`'s
body records about `a`'s `T` through a capture, and those are refusals the design owes.

Closed by binding each nested generic's type parameters per declaration, not per name:
- Each type-parameter row of a generic nested in another function, both the signature's rows and
  the body's, records its declaration node (`tvNestOf`). The constraint de-duplication
  (`tyEqSameHoles`) keeps two declarations' rows of one name apart.
- A call names its declaration by scope: the function or alias its callee resolves to
  (`lookupFnDeclNode`, `lookupFnAliasNode`), never the rows in its parameter types. A call to a
  nested generic (`SUBST_NESTED`) binds only that declaration's rows and the holes. Every
  constraint it changes and leaves holding a type variable is re-recorded under the enclosing
  owner, so each call is checked again at the enclosing pin with that call's binding.
- A declared callee's pin (`a(true)`) leaves nested rows unbound (`SUBST_DECLARED`). The one
  exception is a nested generic its enclosing body reads as a value: a read whose type holds that
  declaration's rows, not just its name. Such a generic binds by name there, as before, and only
  at that pin, never at another nested generic's call.

The index demand was a separate table keyed by the bare name: D3884. D3081 is this row's
earlier filing.
