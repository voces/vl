### D3853 — a nested generic that redeclares its enclosing function's `T` has its body's constraints checked at the enclosing function's pin

**loud check reject · a valid program refused (clause 2) · found in review of lane SC (#3444, `rv3446-probes/h/e4_valid.vl`) · filed 2026-10-08 against master `5b2ec9f85`**

Repro:

    function a<T>(x: T) { function b<T>(y: T) { const n: i32 = y; print(n + 1) }; b(1); print(x) }
    a(true)
    // vl check: rc 1, `cannot assign boolean to 'n' of type i32 … (the body of `a` at the call's argument types)`

Want:

    2
    true

#### Mechanism

The checker records a deferred constraint for each assignment of a type-parameter value
(`const n: i32 = y`) and validates it at the pins of the function that OWNS it. Only a
registered top-level declaration owns constraints (`cstrOwnerStack` in `checkFuncDecl`), so
`b`'s constraints are owned by `a`. At `a(true)` they are substituted by NAME, `T → boolean`,
and `b`'s own `T` is read as `a`'s. With `b<U>` nothing names `U` at `a`'s pin, so the
constraint is left open and the program runs. The monomorphizer tells the two apart since
D3840 (#3444), but this refusal fires earlier, in the checker. A fix needs the constraint to
carry which declaration's `T` it names: a nested generic's own constraints should be validated
at its own pins. Simply making `b` an owner would also skip `a`-owned constraints that `b`'s
body records about `a`'s `T` through a capture, and those are refusals the design owes.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the shadowing (`function b<U>(y: U)`) | runs, `2` and `true` | **yes** |
| the call `a(true)` | checks clean | **yes** (the pin) |
| the call `b(1)` | still refused | no |
| `a(5)` for `a(true)` | runs (`i32` is assignable) | **yes** (a pin the constraint rejects) |
| the annotation on `n` | runs | **yes** (the constraint) |
| an annotated return in its place (`function b<T>(y: T): i32 { y }`) | still refused, `return type mismatch` | no, a second spelling |
