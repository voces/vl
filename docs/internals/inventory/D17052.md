### D17052 — `x is S[]` for a string literal set `S` over `i32[] | string[]` answers each arm inverted

**closed 2026-11-22 by lane IR-N1 · runs, prints `false` then `true` · `listIsAcrossRepsPlan` skips an arm that shares a string literal list's tag only because both store `i32` lists (`listArmTagCollides`, `emit_plan_union.vl`); it never fits (D16047), and the plan answers · fixture `tests/cases/unions/is-string-literal-list-over-int-list-arm.vl`; matrix `is-list-*` (24 templates) · was check-clean silently wrong, clause 1 · filed 2026-11-22 against master `2934a520`**

Repro:

    type S = "a" | "b"
    function mk(c: boolean): i32[] | string[] {
      if c { return [3] }
      return ["b", "a"]
    }
    print(mk(true) is S[])
    print(mk(false) is S[])
    // PRINTS true then false

Want:

    false
    true

#### Mechanism

The `listAcross` rung (`emitListIsAcrossReps`, planned by `listIsAcrossRepsPlan`) writes this
test. An `S[]` list stores its atoms as an `i32` list, so `S[]`'s box tag (`listIsArmTag`) is the
`i32[]` arm's tag. The likely cause is that the `i32[]` arm is planned as `S[]` itself, fitting by
the tag alone, which answers `true` for `[3]`. Why the `string[]` arm's string test answers
`false` for `["b", "a"]` is not yet located. Not ablated past the table below.
