### D2759 — a call through a local binding is resolved to a function of the same name nested in another frame, so the monomorphizer checks the wrong arity

**closed 2026-09-27 — the repro RUNS and prints `6` then `13` · was a loud emit reject, `monomorphize: wrong number of arguments calling \`ap\``, the same on master `f6db92e0d` · filed 2026-09-27 against master `f6db92e0d`**

Repro:

    function s1(xs: i32[]): i32 { xs.length * 3 }
    function one() {
      function ap(g) { g([1, 2]) }
      print(ap(s1))
    }
    function two() {
      const out = [7]
      const ap = (k, g) => g(out) + k
      print(ap(10, s1))
    }
    one()
    two()

#### Mechanism

`monoWalk` resolved the callee of `ap(10, s1)` with `fnIndexOfInScope`, the positionless form.
With no nested `ap` on `two`'s own frame chain it takes the flat answer, `one`'s nested `ap`,
and a positionless lookup lets only a PARAMETER on the chain shadow that answer (D2289), not the
`const ap` binding. The one-parameter nested function was then instantiated for a two-argument
call. Closed by asking the positioned form (`fnIndexOfInScopeAt`, the reading identifier as the
position) at the call, in `monoFnFeOfIdent` and at a callback argument, so a binding in scope
at the call shadows the namesake, and the call falls to the binding's own lambda. Not D2749's
mechanism: that one is the instance's frame, this one is the callee's resolution.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the nested `function ap` in `one` | runs | **yes** |

| the nested function moved to the top level | runs — the chain's binding scan sees it | **yes** — only an off-chain namesake |
