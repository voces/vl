### D2921 — a `boolean | null` read inside a hole function off a list or a lambda prints its sentinel

**closed 2026-09-28 — the filed repro prints `null` · was check-clean silently wrong, clause 1, the same on master `e91e04a8f` · closed by reading a shared node at the hole instance's own binding in `exprNulBool` · filed 2026-09-27 against master `a41bd80e8`**

Repro:

    function F(x) {
      const xs = [x]
      print(xs[0])
    }
    const n: boolean | null = null
    F(n)
    // vl check: rc 0.  vl run: prints `true`

Want:

    null

#### Mechanism

A hole instance shares the generic body's nodes, whose recorded type is the hole's type variable, so a classifier reading that type sees the template's `i32` rep. An explicit `<T>` instance re-types those nodes at the pin (`monoPinRetype`) and a hole instance did not. `monomorphize` now banks each hole instance's binding (`monoHoleSubRow`), and `holeOperandTyOf` reads a shared node at it without banking a pin. `exprNulBool` asks it, so the niche prints through `[x][0]`, `.map`, `.filter` and a lambda.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `print(x)` without the list | runs, `null` | **yes** |
| the value `true` | runs, `true` | **yes** (a null, or `false` through `.map`) |
| `[x].map((e) => e)` with `false` | prints `0` | no |
