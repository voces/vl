### D1673 — an `__array_new__` f32 fill is D1669 one column over: the annotated destination runs, the inferred one is invalid wasm, the generic pin refuses

**check-clean invalid wasm · filed 2026-09-05 against master `55f25c3e7` · found while closing
D1669 · clause 1 at the inferred spelling, clause 2 at the pin**

Repro:

    function f(): f32 { 7.5 }
    const xs = __array_new__(2, f())
    print(xs.length)
    // vl check: rc 0.  vl run: exit 70, the emitted module failed to validate inside the
    // module's top-level code: type mismatch: expected i32, found (ref $type)

#### Mechanism

`arrNewIntrKind` answers 6 here — the destination's own inferred `f32[]` names the kind, so
`emitArrayNewIntr` builds the `fa32TypeIdx` backing and the `fl32TypeIdx` wrapper. The cell the
value is stored into is classified by a different reader, which does not see the f32 list and
types the global as the i32 list: two heap types for one value.

At a GENERIC pin the same value refuses loudly instead, and for a different reason:
`arrNewKindOfElemVKind` returns -1 for `f32` by hand, so `arrNewNamedKind` names nothing and the
emitter's own floor fires (`__array_new__ fill names no element rep, and its destination names
none either`). That exclusion is deliberate and its source comment says so — "`-1` for `f32`,
whose FILL the emitter still refuses" — alongside a second guard in `emitArrayNewIntr` whose
comment records that the identical wiring for the f32 pair once produced invalid wasm. Both are
clause-2 refusals of a program `vl check` accepts.

D1669 is the i64 column of the same table and is closed; this row is what is left when the same
three spellings are written at `f32`.

#### Ablation

| spelling | outcome |
| --- | --- |
| `const xs: f32[] = __array_new__(2, f())` | runs, prints `2` |
| `const xs = __array_new__(2, f())` | **check-clean invalid wasm** |
| `const xs: f32[] = __array_new_default__(2)` | runs, prints `2` |
| the same fill at a generic `T[]` pin | loud `fill names no element rep` |
| the i64 column of every row above | runs (D1669) |

#### Grading list

`exprF32Array` and `exprU8Array` lack the `__array_new__` arm `exprI64Array` gained in D1669
(kinds 6 and 5); adding one is likely part of the fix but is NOT it on its own, since the
`arrNewKindOfElemVKind` exclusion has to lift first and its comment claims the wiring was
tried. The `u8` column has no witness at all — `u8` is a storage type, so the checker refuses
`function b(): u8` by design.
