Repro:

    function f(): f32 { 7.5 }
    const xs = __array_new__(2, f())
    print(xs.length)
    // was: vl check rc 0, then exit 70, expected i32 found (ref $type). Now prints 2.

#### Mechanism

Two readers, one value, and they disagreed about its REP while agreeing about its TYPE — the
checker calls the call `f32[]` at every spelling, including the pin.

`arrNewIntrKind` answers 6 for the inferred binding, off the destination's own recorded type,
so `emitArrayNewIntr` builds the `fa32TypeIdx` backing and the `fl32TypeIdx` wrapper. The CELL
is chosen by `letIsF32Array`, which falls through to `exprF32Array` for an un-annotated init —
and `exprF32Array`'s `Call` arm lacked the `__array_new__` rung that `exprI64Array` (kind 4),
`exprF64Array` (1), `exprStringArray` (2), `exprRefArray` and `exprArray` each carry. The
binding therefore claimed no list kind at all: the module's own bytes put `xs` in a bare `i32`
local while `array.new $fa32` pushed the wrapper into it.

At a GENERIC pin the fill is a PARAMETER, so only `arrNewFillAnnKind`'s substituted annotation
names it — and `arrNewKindOfElemVKind` excluded `f32` by hand, so nothing named the kind and
the emitter's own floor fired. Its comment said the identical wiring for the f32 pair had
produced invalid wasm. What differed is that there was no f32 arm in `emitArrayNewIntr` to
reach: D1470 built one for `__array_new_default__` and left the fill's guard standing above it.

#### Grading list

The `__array_new__ f32 fill — f32-element arrays are not supported yet` literal is deleted, not
narrowed: with the element kind lifted, an f32 fill never reaches that fall-through, and a
float LITERAL fill cannot either — it types f64, and the checker refuses it against an `f32[]`
destination. The `fill names no element rep, and its destination names none either` floor above
it STAYS and names the contract: it still refuses a fill whose kind genuinely nothing names
(D1630's union-typed fill).

`exprU8Array` still lacks the same arm (kind 5). It has no witness by design — `u8` is a
storage type, so the checker refuses `function b(): u8` and no `__array_new__` fill can be one.
