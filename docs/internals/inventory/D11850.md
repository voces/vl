### D11850 — a user string-literal type spelled `#lu<N>` is rendered as the N-th inline literal union

**loud check reject with the wrong type in its message · filed 2026-10-24 against master `4341ada61`**

Repro:

    function pick(u: "x" | "y"): i32 { 1 }
    print(pick("x"))
    const l0: "#lu0" = "c"
    // vl check: rc 1, `cannot assign string to 'l0' of type ""x" | "y""`; want `of type "#lu0"`

#### Mechanism

`inlineLitUnionUnhide` (`compiler/check_types.vl`, reached from `demangleMsg`) replaces
every `#lu<digits>` in a finished message with the members of the inline union that key
names in `cUserTypes`, including text that came from a user's string literal. The program's
own literal is indistinguishable from the internal name once both are in the message text.
The same substitution reaches the incremental check: `skBankNow` refuses to bank a message
holding `#` or `$`, but it reads the text after the substitution, so it banks
`""x" | "y""`. A served check then replays that row even when the current program's tables
would render something else. For example, after an edit that removes lib's only inline
literal union, the whole check says `"#lu0"` and the served check still says `""x" | "y""`.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the inline union `"x" \| "y"` | message reads `"#lu0"` | **yes** |
| the `#` in the literal (`"lu0"`) | message reads `"lu0"` | **yes** |
| a second literal `"#lu1"` with no union 1 | that row reads `"#lu1"` | no (only an existing key) |

#### Grading list

The served-check sequence: lib declares `const u: "x" | "y" | null = null` inside a private
function and main holds `const l0: "#lu0" = "c"`; check, edit lib's union to `i32 | i64`,
check again with check-skip armed. Since the whole check reads `"#lu0"`, the served check
must read the same.
