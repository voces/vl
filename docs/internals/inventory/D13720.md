**closed 2026-10-25 by lane L1 · runs, prints `3` and `2.25` · a lambda or nested function declared inside another function is walked once per walk of its enclosing function, so a captured hole function resolves to the pin of the enclosing function's own instance: `ffInstCtx` keys a nested function's instance by the calling walk as well as its own bindings, for a function the checker records inside another (`fnDeclParent`), in fn_flow_shadow.vl · pin: `tests/cases/closures/captured-hole-fn-handed-on-two-generics.vl` (the lambda, a named nested function at three generics, two levels deep, a `let` lambda, a returned result, the annotated face, the enclosing parameter alone annotated) · a hole function parameter handed on to a generic at two types is still loud, filed as [D13860](D13860.md) · was loud emit reject · `vl check` rc 0 · clause 2 · CAPABILITY: the same call made directly in the enclosing function runs, so does the lambda calling the captured function itself, and so does either call alone · found by lane L1 closing [D13660](D13660.md) · present on master `3e3b18500` and after lane L1's D13660 PR · filed 2026-10-25 against master `36bb58995`**

Repro:

    function add(a, b) { return a + b }
    function mul(a, b) { return a * b }
    function apply2(g, s) { print(g(s, s)) }
    function outer(h) {
      const run = (x) => { apply2(h, x) }
      run(1.5)
    }
    outer(add)
    outer(mul)
    // vl check: rc 0.  vl run: emitProgram: cannot take the generic function `mul` as a value

Want:

    3
    2.25

#### Mechanism

The function-value flow table walks each instance of a generic in its own context, keyed by
its type bindings. The lambda's instance at `x: f64` was keyed by its own bindings only. So
the walk of `outer(mul)` found it already walked from `outer(add)`'s context, and the captured
`h` reached only `add`. With no flow pin for `mul`, the mono pass fell to `(i32, i32) => i32`
and refused. A named nested function took the same path.
