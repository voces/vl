### D8060 — a fallible `as` over a hole call's result is not judged by the checker and is refused at emit

**loud emit reject · `vl check` rc 0 · clause 2 · the checker owed the refusal: binding the call's result as `const x: f64` first is a loud check reject, `as i32` propagates null, which the enclosing function cannot return · found closing [D7841](D7841.md) · present on master `370ba120c` · filed 2026-10-20 against master `370ba120c`**

Repro:

    function add(a, b) { return a + b }
    function p(g) {
      print(g(1.5, 2.5) as i32)
    }
    p(add)
    // vl check: rc 0.  vl run: emitProgram: bare null needs a struct-typed context

#### Mechanism

Traced 2026-10-20, not fixed. The design refuses this program: the direct spelling's check
error is the answer, not a lowering. A cast over a hole operand is parked by `noteCastDemand`
(check_demands.vl, called from `checkCastNode` in check_operators.vl) and re-asked at the pin by
`holeCastPinCheck` / `castPinAdjudicate`, which raise the propagation refusal. `noteCastDemand`
parks only an operand that is a direct read of a hole PARAMETER (`castOperandIdent`); a hole
CALL's result is a derived `HD_RET` hole and is never parked, so no pin asks, `vl check`
returns 0, and the emitter has nowhere to put the null. A close parks a cast whose operand type
is an `HD_RET` hole and adjudicates it from the substituted operand type. That is a change to
check_demands.vl and check_operators.vl. The grading list's spellings run today: `as!` over
`g(1.5, 2.5)` prints `4`, and `as? i32 ?? -1` prints `-1` over `g(1.5, 2.25)` and `4` over
`g(1.5, 2.5)`.
