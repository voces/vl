### D4532 — a fused `>>` closing two generic applications swallows the comma after it

**closed — a duplicate of D2534, closed by the same change: the type-argument loop in `compiler/parser.vl` reads its `,` through `atTypeCont` · graded by `tests/cases/generics/nested-application-close-before-separator.vl` · filed 2026-10-13 against master `a8efc18f3` · was loud check reject (parse error), 1 cell**

Repro:

    type R = { a: i32 }
    type F = { parts: Map<string, Map<string, R>>, rc: i32 }
    const f: F = { parts: Map(), rc: 1 }
    print(f.rc)
    // vl check: expected `}` but found `rc`

#### Mechanism

The type-argument loop in `compiler/parser.vl` (the `<` arm of the type-name parser)
decides whether another argument follows with `peekKind() == "COMMA"`. When the inner
application closes on a fused `>>`, `expectTypeGt` consumes the whole token and leaves the
outer `>` owed in `pendingGt`; the outer loop then still reads the NEXT token, the field or
parameter separator, as one more type argument's comma, eats it, and stops on the
`pendingGt > 0` trailing-comma arm. The enclosing list then finds `rc` where it wanted `,`.
Testing `pendingGt` before the comma (as `atTypeCont("COMMA")` does) is the likely fix.
