### D2370 — an i32-keyed map lookup went through a murmur mix and four entry-parallel arrays, and a delete-free module still kept `live` and `hashes` for every entry

**closed 2026-09-24 — the witness prints `499500`; PL-037 item 5 (`~/plumb/docs/vl-issues.md`),
the `map` kernel of `bench/vs-rust` at 2.83–3.02× Rust before and 1.06–1.28× after (three
interleaved `--reps 15` rounds each). A performance row, not a wrong answer: every program
printed the same thing before and after. Filed against master `f9c3f41e2`**

Repro:

    const m: {[i32]: i32} = Map()
    for i in 0 until 1000 { m[i * 2654435761 as% i32] = i }
    let s = 0
    for i in 0 until 1000 { s = s + (m[i * 2654435761 as% i32] ?? 0) }
    print(s)
    // prints 499500

#### Mechanism

A lookup called `__map_probe_i32__(index, hashes, live, keysBack, key)`, which ran the murmur3
finalizer (two multiplies, three shift-xors) and then, per probed slot, read `index[slot]`,
`hashes[entry-1]`, `live[entry-1]` and `keysBack[entry-1]` — four bounds-checked loads over
four arrays — before the caller re-read `index[slot]` and then `vals[entry-1]`. `-O` had
already scalarised the map struct, so the `struct.get` chain was not the cost; the loads and
the mix were. Each insert also grew and stored `live` and `hashes` even in a module with no
`.delete(…)`, where nothing ever reads either.

An i32-keyed map's index is now an array of (key, entry) pairs, placed by Fibonacci hashing
(`fbMapSlotOf`: the top bits of `key * 0x9e3779b9`), so a hit or a miss is decided from one
cache line of the index alone; `hashes` stays empty for it and resize rehashes from the pairs
(`__map_resize_i32__`). A deleted pair's entry becomes `-1`, a probe marker the probe skips only
in a module that deletes. In a module that never deletes (`gMapDeletes` false — the scan that
already decides the `seqs` fields), no map grows or reads `live`; `keys()`, `values()` and the
`for`-in walk take every entry as live. `__map_compact__` clears the index in place with
`array.fill` when its size is unchanged, which is a steady churn's case, instead of allocating a
fresh one per compaction.

A string-keyed map keeps the entry-number index and its `hashes` gate. The pair layout was
built and measured for it too and lost: `bench/collections/map-string` went 440 → 542 ms in V8
and ~0.80 → ~0.90 s under `vl run`. The index doubles to 2 MB at 100k keys, and FNV's low bits
put a run of sequential keys (`key0`, `key1`, …) in nearby slots under `hash & mask`, which
Fibonacci placement scatters; `hash & mask` over the pairs only won back half of it.

#### Ablation

Hand-written wasm variants of the kernel at `n = 200000`, run in one V8 process, ns per unit
of `bench/vs-rust` (a noisy box, so read the ratios within a row, not across rows):

| variant | outcome | needed? |
| --- | --- | --- |
| the old layout, dropping the `live` test, then the `hashes` gate | 14.4 → 12.0 → 10.0 | **yes** — the loads |
| pairs placed by murmur `& mask` instead of Fibonacci | 9.4 against 4.9 on the kernel's keys, 11.1 against 10.6 on random keys | **yes** — placement |
| a module with `.delete` | pairs still decide; one `entry > 0` test per key match | no |
| growth at a 3/4 or a 3/8 load factor instead of 1/2 | 5.9 and 7.0 against 4.6; 11.5 and 14.0 against 11.0 on random keys | 1/2 kept |

#### Grading list

`tests/cases/maps/pair-index-against-reference.vl` (a deleting module) and
`pair-index-insert-only-against-reference.vl` (a delete-free one) are randomized differential
fixtures against a flat reference, over key families chosen to hash badly — sequential,
negative, multiples of 2^20 and 2^26, the extremes, and 128 multiples of the multiplier's
inverse, which all share one home slot. Seven sabotaged compilers (the probe without the
deleted-pair test, the string probe without its live test, compaction or resize placing at the
wrong slot, a mis-recorded pair key, compaction not clearing the reused index) each fail at
least one of them. The D2315 walk-mutation fuzz, the D2280 churn fixtures and
`churn-sliding-window-every-rep.vl` run unchanged.
