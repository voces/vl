### D9080 — a `const` bound to an `if` choosing between two generic or un-annotated functions refuses when handed to a generic parameter or `.map`

**closed · runs, prints `3` · was loud emit reject, ``monomorphize: unsupported argument type for `g` in a call to `app` `` · `vl check` rc 0 · clause 2 · found closing [D9005](D9005.md) · filed 2026-10-21 against master `8f0df7360` · closed by delivering a read of a never-written binding of such an `if` as that `if`: the recogniser follows the binding (`monoArgIsOpenFnChoice`, `monoIfBindingWalk`) and the value coercion instances its arms where the read is delivered (`monoCoerceChoiceBinding`, emit_mono.vl) · fixture `closures/fn-choice-bound-as-callback.vl`, matrix `fn-choice-bound-as-list-callback-result`**

Repro:

    function idg<T>(t: T): T { return t }
    function kg<T>(t: T): T { return t + t }
    function app<T>(g: (x: T) => T, v: T): T { return g(v) }

    const h = if c { idg } else { kg }

#### Mechanism

The inline `if` was coerced arm by arm wherever it was delivered: recognised as riding a
callee's type parameters by `monoArgIsOpenFnChoice`, and instanced by
`monoCoerceFnValueName`'s `IfStmt` arm. A name bound to the same `if` is an `Ident` naming
neither a generic nor an alias of one, so the recogniser declined it and the coercion found no
generic to instance. `monoArgIsOpenFnChoice` now follows a never-written, un-annotated binding
to its initializer, and `monoCoerceFnValueName`'s `Ident` arm hands such a read to
`monoCoerceChoiceBinding`, which coerces the binding's `if` at the delivered type through the
same `IfStmt` arm and records that type on the binding and the read. The binding holds one
value, so a delivery at a second function type is refused ([D9121](D9121.md)).
