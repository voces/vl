### D1583 — `x as u8` said `unknown type \`u8\``, which is the one thing that is not true: it is a STORAGE type, and the conversion the author wanted is what the store already does

**now a loud check reject that NAMES THE STORE (fixed; the program stays illegal — there is no `u8` value to cast to — and the message is what changed) — `checkCastNode`'s unresolved-target arm gains a `u8` case (`u8CastText`), `storageTyLeafFail`'s twin at the one position whose remedy differs · was a loud check reject naming the wrong reason · 4 of 4 `as u8` positions carry it, `as Bogus` unchanged · ZERO corpus cells · reported by the glean session, VL-037, `~/glean/docs/vl-issues.md` · filed 2026-09-04 against master `9ba97704`**

Repro (`vl check` reports `` `u8` is a storage type, not a value type — a `u8[]` stores the low byte of an `i32`; push the `i32` directly (300 stores as 44), or `x & 0xff` to make the truncation explicit ``):

    const bytes: u8[] = []
    const v = 300
    bytes.push(v as u8)

#### Mechanism

`u8` is a STORAGE type by design: wasm has no 8-bit VALUE type, but WasmGC has packed
`i8` array elements, so `u8[]` is a real `(array (mut i8))` while every value crossing its
boundary is an `i32`. `primTyOfName` deliberately does not answer for `u8`, and
`tsLeafTy` / `nameToTyReal` route it to `storageTyLeafFail`, which banks the
annotation-position sentence. `checkCastNode` does not read that bank — its unresolved
target falls to a hand-built `unknown type \`u8\` in \`as\` cast`, and that sentence is
false in the way that matters: `u8[]` is spellable and `std:fs`'s `readFile` answers one,
so the name plainly names something. The reporter read it as the language accepting a
widening it would not let you write down.

The fix is a second sentence, not a second rule, because the REMEDY differs by position.
In an annotation the answer is "write `i32`". In `x as u8` there is nothing to write: the
store already truncates to the low byte, so `bytes.push(v)` IS the conversion, and
`v & 0xff` is the same thing said out loud. The message names both. It is reached only
when the name did not resolve, so a program declaring its own `type u8` is unaffected,
and it is gated on the NAME, so `as Bogus` keeps its own wording.

The truncation numbers in the message are measured, not asserted: `bytes.push(300)` reads
back **44** and `bytes.push(-1)` reads back **255** on this seed, which is what
`u8-packed-list.vl` and `error-u8-literal-range.vl` already pin from the other side.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the `push` position (a `u8[]` literal element, an index write, a bare binding) | the same message | no — every `as u8` position |
| the `u8[]` in the program entirely (`const w = v as u8`) | the same message | no — the cast is refused on its own |
| `u8` replaced by `Bogus` | `unknown type \`Bogus\` in \`as\` cast`, unchanged | **yes** — the arm is name-gated |
| the cast (`bytes.push(v)`) | runs, stores 44 | **yes** — the working spelling is the message's own remedy |
| the cast replaced by `v & 0xff` | runs, stores 44 | **yes** — the second spelling the message names |
| the position is an ANNOTATION (`function f(b: u8)`) | `storageTyLeafFail`'s sentence, unchanged | **yes** — two positions, two remedies |

#### Grading list

* **4 `as u8` positions** — `push` argument, `u8[]` literal element, index write, bare
  binding — all four carry the new message with a position; the `as Bogus` control and
  the annotation-position message are byte-identical to before.
* **The truncation the message claims**: `bytes.push(300)` -> 44, `bytes.push(-1)` -> 255,
  `bytes.push(v & 0xff)` -> 44, and `(v >> 24) & 0xff` over `0x41424344` -> 65 / 66.
* The docs half: `docs/guide/collections-design.md` §"What you write TODAY" now states
  that a `u8[]` store keeps the low byte and that `as u8` is not a cast to write — nothing
  consumer-facing said either before (the fixtures did, from the inside).
