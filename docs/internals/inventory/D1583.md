### D1583 — `x as u8` said `unknown type \`u8\``, which is the one thing that is not true: it is a STORAGE type, and the conversion the author wanted is what the store already does

**SUPERSEDED BY D1587 and closed there — the row stands as the record of a message that was accurate about the TYPE and wrong about the REQUEST · `x as u8` is now a real cast (the i64→i32 narrowing with 0..255 as its domain), so the remedy sentence below is retired along with `u8CastText` · was a loud check reject naming the wrong reason, then a loud check reject naming the store, and is now a loud check reject only at module scope, where the trio's own rule applies · ZERO corpus cells · reported by the glean session, VL-037, `~/glean/docs/vl-issues.md` · filed 2026-09-04 against master `9ba97704`**

Repro (`vl check` reports `` `as u8` propagates null out of the enclosing function, and there is none here — at module scope, use `as!` to trap or `as?` to take a nullable ``):

    const bytes: u8[] = []
    const v = 300
    bytes.push(v as u8)

#### Mechanism

`u8` is a STORAGE type by design: wasm has no 8-bit VALUE type, but WasmGC has packed
`i8` array elements, so `u8[]` is a real `(array (mut i8))` while every value crossing its
boundary is an `i32`. `primTyOfName` deliberately does not answer for `u8`, and
`tsLeafTy` / `nameToTyReal` route it to `storageTyLeafFail`, which banks the
annotation-position sentence. `checkCastNode` does not read that bank — its unresolved
target falls to a hand-built `unknown type \`u8\` in \`as\` cast`, and that sentence is
false in the way that matters: `u8[]` is spellable and `std:fs`'s `readFile` answers one,
so the name plainly names something. The reporter read it as the language accepting a
widening it would not let you write down.

THE REMEDY THIS ROW SHIPPED WAS "WRITE NOTHING", AND THE OWNER RULED OTHERWISE (D1587,
2026-09-04). `x as u8` is not a request for a `u8` VALUE — it is a request for the CHECK
the store does not do, and it is now the same exact-or-fail narrowing `x as i32` is, with
0..255 as the domain and an `i32` as the result: `bytes.push(x as! u8)` traps on a
non-byte, `x as? u8` yields `i32 | null`, and a bare `x as u8` propagates the null. The
store is UNCHANGED — `bytes.push(v)` still keeps the low byte — so the two spellings this
row's message named are still legal and still truncate; what changed is that a third
spelling now exists and says something the other two cannot.

What survives from this row: `u8` is still a STORAGE type at every ANNOTATION position
(`storageTyLeafFail`), the arm is still reached only when the name did not resolve (a
program declaring its own `type u8` is unaffected), and it is still gated on the NAME, so
`as Bogus` keeps its own wording.

The truncation numbers in the message are measured, not asserted: `bytes.push(300)` reads
back **44** and `bytes.push(-1)` reads back **255** on this seed, which is what
`u8-packed-list.vl` and `error-u8-literal-range.vl` already pin from the other side.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the `push` position (a `u8[]` literal element, an index write, a bare binding) | the same message | no — every `as u8` position |
| the `u8[]` in the program entirely (`const w = v as u8`) | the same message | no — the cast is refused on its own |
| `u8` replaced by `Bogus` | `unknown type \`Bogus\` in \`as\` cast`, unchanged | **yes** — the arm is name-gated |
| the cast (`bytes.push(v)`) | runs, stores 44 | **yes** — the store's truncation, unchanged by D1587 |
| the cast replaced by `v & 0xff` | runs, stores 44 | **yes** — the explicit spelling of the same truncation |
| the position is an ANNOTATION (`function f(b: u8)`) | `storageTyLeafFail`'s sentence, unchanged | **yes** — the value position is still refused |

#### Grading list

* **4 `as u8` positions** — `push` argument, `u8[]` literal element, index write, bare
  binding — all four now take D1587's trio; the `as Bogus` control and the
  annotation-position message are byte-identical to what this row shipped.
* **The truncation the message claims**: `bytes.push(300)` -> 44, `bytes.push(-1)` -> 255,
  `bytes.push(v & 0xff)` -> 44, and `(v >> 24) & 0xff` over `0x41424344` -> 65 / 66.
* The docs half: `docs/guide/collections-design.md` §"What you write TODAY" states that a
  `u8[]` store keeps the low byte — nothing consumer-facing said so before (the fixtures
  did, from the inside). D1587 replaced this row's second claim there, that `as u8` is not
  a cast to write, with the trio it now is.
* Fixtures: D1587 replaced this row's `tests/cases/arrays/error-u8-cast-names-the-store.vl`
