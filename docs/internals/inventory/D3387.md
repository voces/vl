### D3387 — a store of a float intrinsic over a literal `let` bounded the target by the intrinsic's first-pass `f64`, so an `f32` use of the target conflicted

**closed · fixture `tests/cases/numerics/literal-binding-float-intrinsic.vl` · was a loud check reject (`` `y` takes its type from its uses, and they conflict … f64 … f32 ``) · the #3311 review's `rv3311b-x4m/w/f2.vl` and the #3308 review's `a = sqrt(a)` · filed and fixed 2026-09-30 against master `4ff12b994`**

Repro:

    function tf32(x: f32) { print(x / 3) }
    function f() {
      let x = 0.5
      let y = 0.5
      x = -1.1
      y = abs(x)
      tf32(y)
    }
    f()
    // was: vl check refused `y`; with `y = x` in place of `y = abs(x)` it printed -0.36666667461395264

Want:

    0.36666667461395264

#### Mechanism

The literal-binding solve reads a store's tree through `lbiLeaves`, which stops at a call and
takes the call's type as a typed leaf, a lower bound on the target. A float intrinsic's type is
its operands' width, and on the first pass every float literal `let` is still its `f64` default,
so `abs(x)` bounded `y` below by `f64` before `x` had a type, and `y`'s `f32` use then had no
type satisfying both. #3311 made an integer intrinsic's operands forward-only edges (`LBI_EDGE_FWD`)
for the same reason. Now every intrinsic whose result is its operands' width (`lbiIntrArgs`)
is read through: its typed leaves bound the target, its own first-pass type bounds nothing, and
a candidate operand is an edge. A float candidate's edge is two-way (`lbiIntrEdge`), as a copy
is, because a float binding's answer only falls below `f64` through an `f32` upper bound, which
an extra upper bound never widens; forward-only would leave `x` at `f64` and `y`'s `f32` still
refused. An integer operand's edge stays forward-only, since its width is the value (`clz`).
