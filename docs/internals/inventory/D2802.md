### D2802 — a generic's `v != null` refuses at a pin that cannot be null

**closed 2026-09-27 — the filed repro RUNS and prints `a` · was a loud emit reject · clause 2 · found by #3208's review (`gPr` `gnnar` cells) · closed by folding the null test of a pinned parameter whose pin proves non-null to its constant in the instance rewrite (`monoDeadNullTest`), the direct twin's dead null test · filed 2026-09-27 against master `b586b6063` · fixture `tests/cases/generics/pin-non-null-dead-null-test.vl`**

Repro:

    type LS = "a" | "b"
    function k<T>(v: T) {
      if v != null { print(v) } else { print(v) }
    }
    const x: LS = "a"
    k(x)
    // vl run: emitProgram: bare null needs a struct-typed context

#### Mechanism

`v != null` over a type parameter is admitted by the checker. The direct spelling
(`v: LS`) is a dead null test the emitter folds to a constant (`deadNullTestOperand`), but an
instance's nodes carry the generic's `T`, which proves nothing, so the compare reached the
niche dispatch and the `null` operand had no nullable rep to be built at. `monoPinBinOps`, which
already rewrote `??` over a pin that excludes null (D512), now rewrites `==`/`!=` against a
bare `null` over a pinned parameter that `tyProvesNonNull` to the boolean it always yields.
A nullable pin (`i32 | null`) is untouched and still tests the value. Once the instance built,
a second leak showed: the monomorphizer's quiet re-check of an instance body
(`monoRecheckBegin`) restored every table but the lint findings, so a generic called at a pin
that proves non-null warned `v != null is always true here` at its body — a claim about one
pin. The re-check now truncates those findings with the rest.
