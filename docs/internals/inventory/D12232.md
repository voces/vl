### D12232 — a generic handed to two parameters of one type parameter, called at two types, is refused when the function may return either parameter

**loud emit reject · `vl check` rc 0 · `emitProgram: monomorphize: a generic function handed to two parameters of type `F` in a call to `mid` is called at two types, and `F` takes one` · clause 2 · CAPABILITY: the same function returning only `a1` runs ([D6425](D6425.md)), and the program is well-typed · emit_mono.vl, the `monoTyParamOnlyBareParams` refusal in the type-parameter binding loop · pin: `tests/cases/functions/error-generic-fn-value-two-type-param-params-read-elsewhere.vl` · found surveying emit refusals for L3 family (d) · filed 2026-10-24 against master `84b98d149`**

Repro:

    function same<T>(k: T): T { k }
    function take(a) { print(a("x")) }
    function take2(a) { print(a(3)) }
    function mid<F>(a: F, a1: F, c: boolean): F {
      take(a)
      take2(a1)
      if c { return a }
      a1
    }
    mid(same, same, false)

#### Mechanism

`mid`'s two parameters share `F`, and `same` is called through them at `string` and `i32`. The
type-parameter split (`fsTyParamReadSplits`, fn_split.vl) gives the second parameter a type
parameter of its own when `F` is read nowhere else, or when every `return` and tail value is
that one parameter (D6425). A result that may be either parameter has no single new type
parameter to take, so the split declines and the binding loop refuses. With the result unused
at the call, nothing observes which `F` the result has.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| `if c { return a }` | runs, prints `x 3` | **yes** |
| the result used (`const u = mid(same, same, true); print(u(1))` added) | still refuses | no |
