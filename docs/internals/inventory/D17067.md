### D17067 — unary `-` and `~` refuse a `never` operand that every binary operator takes as a bottom

**closed 2026-11-23 by lane IR-C1 (#PRNUM) · now runs, `2.5` · was loud check reject · `unTyOfArg`: unary `-` and `~` over a `never` operand are `never`, as the binary operators are (D14420) · pin: `tests/cases/soundness/never-operand-of-unary-runs.vl` · matrix: `-` and `~` 64 of 64 check refuses → 64 of 64 runs · filed 2026-11-23 against master `53f48d792`**

Repro:

    function fail(): never { __trap__() }
    function w(c: boolean, x: f64) {
      if c { return x }
      return -fail()
    }
    print(w(true, 2.5))
    // vl check (before #PRNUM): unary '-' expects a numeric type, got never

Want:

    2.5

#### Mechanism

`unTyOfArg` (`check_operators.vl`) requires a numeric operand for `-` and `~` and names `never` as
the type it got. The binary operators return `never` for an operator over a `never` operand before
their operand checks (D16006, D14420), because the operator can have no value. The unary ones had
no such arm, so a refusal the design does not owe fired. `!` already took `never`.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `!fail()` | runs | **yes** (`-` or `~`) |
| `-fail()` at `i32`, `i64`, `f32`, `f64`, `boolean` | refused at each | no (any type) |
| `fail() - 0` | runs | **yes** (unary) |

#### Grading list

- `~fail()`, and `-fail()` delivered into a typed binding (`const y: f64 = -fail()`).
