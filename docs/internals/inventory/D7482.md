### D7482 — comparing a delivered generic with the generic's name fixes its type parameter, so a later delivery at another type is refused

**closed 2026-10-23 by lane L1 · runs, prints `true 1` · was loud check reject · clause 2 · CAPABILITY: without the comparison both deliveries run, printing `2` · the comparison binds `two`'s `T` at `i32` for the rest of the module, which no ruling asks for · found closing [D7382](D7382.md) · present on master `1c86d0f42` · filed 2026-10-19 against master `1c86d0f42`**

Repro:

    function two<T>(x: T): i32 { return 1 }
    const p: (x: i32) => i32 = two
    print(p == two)
    const r: (x: string) => i32 = two
    print(r("a"))
    // vl check: cannot assign (T) => i32 to 'r' of type (x: string) => i32

Want:

    true
    1

#### Mechanism

`p == two` has an operand typed `(x: T) => i32`, so `checkBinExprNodeReal` recorded a deferred
binary-op constraint (`binNoteHoleCstr`) over `two`'s own `T`, owned by no call. Every later
`genericFnAssignable` consults owner-less constraints, so the delivery at `string` failed
`(x: i32) => i32 == (x: string) => i32`. Fixed by `binOperandHoleInScope` (check_operators.vl):
a function-typed operand whose type variables are neither inference holes nor type parameters
in scope is a generic value's own signature and records no constraint. Pins:
`tests/cases/generics/generic-fn-compared-then-delivered-at-another-type.vl` and
`generic-fn-compared-in-function-then-delivered-at-another-type.vl`.
