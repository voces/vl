### D16050 — an array of a literal union with more than one base is no value atom in a union, so its union-box code depends on the spelling, not the type

**runs today and must keep running · 2 programs of the sweep population (D3491, D4199) plus 4 spellings ablated below · filed 2026-11-13 against master `71a04133`**

Repro:

    type D = 9000000000 | 1
    function f(x: D[] | string) {
      if x is string { print(x) } else { print(x.length) }
    }
    f([1, 9000000000])
    f("s")
    // vl run: 2, s. The union row banks the `D[]` member at value-atom code -1 ("not a value
    // atom"), where `(1 | 2)[]` banks 7 and `(9000000000 | 9000000001)[]` banks 10.

Want:

    2
    s

#### Mechanism

A union member's box ABI code is banked by `valueAtomKind` over the member's canon render
(`recordUnMemTys`, `msFreeSlicePush`, emit_rep.vl). For a list member the code follows the
render's element spelling. `litUnionArrayElemOf` claims an alias element only when
`nameIsLitUnionType` says it is a literal union, and that test holds only for one base, as the
render shows. An element alias whose literals span two bases (`i64` and `i32`, or `i32` and
`string`) is claimed by no arm, so the member banks -1. A type-derived code (the element's
literals each ride their base) would answer per base. The programs run, so the -1 is consistent
everywhere it is read; the defect is that the code is a fact about the spelling.

#### Ablation

Each program is the repro's shape, with `D` replaced. "Banked" is the code `valueAtomKind`
gives the list member; measured with a probe at the producer.
