#### Mechanism

The key was not what failed. D9006's split gave `app(f, [7, 8])` and `app(f, u)` a `let`
each, and the emitter pins each split `let` once per instance of `both`, as it does for two
`let`s written by hand. The refusal came from the instance plan that runs in the same plan
pass, D6322's copy of a module function called at two keys when an ask sits inside it. The ask
here is `f`, so `both` was copied per call key. A copy is a fresh parse of the original source,
so it carries none of the let plan's new slots. It holds the one `f` with both hands, and the
written-let refusal fired again on the APPLY build. The direct-call spelling, `f([7, 8])` and
`f(u)`, failed the same way.

The close leaves out of that copy any body whose `let` the let plan gave more than one slot
(`fsLetSplit`, `fsPlanInstances`). Keying the split on the instance as well was not needed,
because each instance already reads its own slots. Splitting after monomorphization would
mean a second split mechanism inside the emitter for a case the existing plan already covers.
