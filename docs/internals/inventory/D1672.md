#### Mechanism

Two independent halves, one per face, and neither is the field WRITE the row named — the
write can be deleted from the annotated cell and it refuses identically.

**A union arm has no `sNames` row of its own**, so the row a code-15 nested-struct field
stores through is minted on demand by `internArmFieldShape`, and only
`collectNestedFieldShapes` asked for it — a walk over `TypeDecl` field ANNOTATIONS.
An inferred holder has no annotation to walk, so `anonFieldCode` answered -1 for the field
(instrumented: `si=-1 code0=-1 tn=[{x: i32}] arm=-1 elem=[]` — the render is structural, so
the `armFieldStructRow` rung never sees the arm's name), the literal was refused a row, and
`emitObjLitNode`'s middle rung boxed it because the program declares a union. `{f: 1}` beside
the same union runs, and so does `{f: p}` with a `type W = { f: P }` in the file: the arm in
the field is the ingredient, exactly as filed. The same mint is owed by an INLINE-SHAPE
annotation (`const w: {f: P} = …`), whose field texts nothing descended either.

**The annotated cell's kind and its readers read different sources.** A code-15 field read is
nullable-classified by design (the slot is a `(ref null $S)`), so `globalCellKind` gives
`const v: P = w.f` the `nulvariant` niche off its initializer — while
`exprNullableVariant`'s and `nulVariantIdxOfExpr`'s global legs re-derived the answer from
the ANNOTATION alone, which names the non-null arm. Instrumented at the floor:
`li=40 gk=[nulvariant] gs=0 annVi=0 nulVar=1` beside `evi=-1 nvi=-1`. The struct twin has
shared one predicate (`globalIsNulRefSid` → `letIsNulRef`) throughout, which is why the plain
`type S = {x: i32}` control runs; the variant twin never got it.
