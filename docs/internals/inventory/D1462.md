### D1462 — arithmetic on an UNRESOLVED array-element hole traps the COMPILER instead of diagnosing it: two lines, no intrinsic

**closed — now a loud check reject, the same sentence `print(xs[0])` already gave · `cannot infer a type for 'xs' — add a type annotation`, `vl check` rc 1 · the element is GENUINELY under-determined (five element types satisfy `xs[0] + 1`), so a stated diagnostic is the answer, not a lowering · fixture `tests/cases/types/open-element-operand-diagnoses.vl`**

Repro (was a wasm backtrace; now the binding's own diagnostic):

    const xs = []
    print(xs[0] + 1)

    // [ERROR]: cannot infer a type for 'xs' — add a type annotation
    //   const xs = []
    //               ^
    //   at d1462.vl:1:13

* **THE ARITHMETIC IS THE WHOLE INGREDIENT.** `print(xs[0])` on the same binding is
  `cannot infer a type for 'xs' — add a type annotation`, which is the right answer. Adding
  `+ 1` — an operand that *narrows* the element toward numeric — replaces the diagnostic with
  a crash.

* **THE INTRINSIC IS SCENERY, WHICH IS WHY THIS IS NOT THE PROBE'S ROW.** The probe
  (`autofixed-redundant-return-annotation.vl`) routes through
  `function mk(len: i32) { return __array_new_default__(len) }`. Deleting the function and the
  intrinsic — a bare `[]` — traps identically, at the same address. The element hole is the
  subject; how it was created is not.

* **A COMPILER TRAP IS WORSE THAN EVERY OUTCOME THIS INVENTORY GRADES.** The user gets a wasm
  backtrace naming a function number in a compiler they did not build. It is the same class as
  [D1440](D1440.md), found the same day by the `--fix` work: an unguarded read on a `-1` hole
  index. That row's fix guarded one reader; this is a second, and the pair is the argument for
  auditing the family rather than the site.

* **IT IS NOT THE PROBE'S CAPABILITY QUESTION.** The probe asks whether an un-annotated
  `__array_new_default__` binding should infer its element type — genuinely underdetermined,
  since `print(zs[0])` narrows to "printable" and no further. That question stands open and is
  recorded on [D1091](D1091.md)'s taxonomy as the 3-edit "type exists nowhere else" category.
  This row is only the crash, which is answerable regardless of how that question is ruled.

* **THE GRADER READ THIS ROW AS `check_reject` BOTH BEFORE AND AFTER THE FIX, AND THAT IS
  THE HOLE WORTH NAMING.** `vl check` exited 1 for the crash and exits 1 for the diagnostic,
  so `check-filed-witnesses.py` graded the trap `as filed` alongside every honest refusal —
  it has no outcome for "exited 1 without saying anything". A row that prints a function
  number to the user is not the same defect as one that names a rule, and only this sentence
  separated them. Worth its own outcome word if a second lands.

#### Fix — three bound tests, and the placement is the whole difficulty

`arrElemValueTy` hands back the in-band `-1` for an element nothing has pinned, and
`T.tys[-1]` is an out-of-bounds array access inside the CHECKER. D1500's rule applies
verbatim — *a table read whose index came from a reader with an in-band "no answer" value
must be bound-tested* — and it needed three sites, none of them D1500's or D1440's:

| site | what it received | guard |
| --- | --- | --- |
| `checkBinExprNodeReal`, the operator-dispatch arm (`T.tys[lt]`) | `lt = -1` from `xs[0]` | `if lt < 0 { return TY_ERR }`, placed AFTER the `=` arm |
| `checkBinExprNodeReal`, the `??` arm (`T.tys[lt]`) | same | the same guard covers it |
| `checkIsExprNode`, the soundness gate | `objTy = -1`, and `baseTy = ot.nInner = -1` for `mkNullableTy(-1)` (an unpinned `Map()` read) | `objTy >= 0` on the arm, `if baseTy < 0 { return TY_BOOL }` inside it |

**THE PLACEMENT IS LOAD-BEARING AND A TOP-OF-FUNCTION GUARD IS WRONG.** `xs[i] = v` PINS the
open element from the RHS in place, and `lt` is that open `-1` while it does so — an early
return would delete the inference, and `const xs = []` / `xs[0] = 5` / `print(xs[0] + 1)`
would stop checking. That cell is in the position grid below and stays `ok`.

#### Ablation — the element is under-determined, measured not assumed

`xs[0] + 1` is satisfied by **five** element types, so nothing in the program decides it:

| annotated spelling | outcome |
| --- | --- |
| `const xs: i32[] = [1]` | runs `2` |
| `const xs: i64[] = [1]` | runs `2` |
| `const xs: u8[] = [1]` | runs `2` |
| `const xs: f32[] = [1.5]` | runs `2.5` |
| `const xs: f64[] = [1.5]` | runs `2.5` |
| `const xs: string[] = ["a"]` | type error |

And the ANNOTATED face of the witness itself — `const xs: i32[] = []` / `print(xs[0] + 1)` —
is `vl check` rc 0 and a runtime out-of-bounds trap in the USER's module (`vl!<wasm function
4>`), which is the program's own bug. The inferred face now matches it wherever the element
gets pinned at all.

#### Price

One cell moved compiler-trap → **loud emit reject**, not to `runs`: `const xs = []` /
`print(xs[0] ?? 1)` / `xs.push(3)`, where the pin arrives on a LATER line than the read, now
reaches `emitProgram:` &nbsp;`?? over this nullable value is not supported yet`. Its annotated
twin (`const xs: i32[] = []`) builds and traps at runtime. Loud→loud, no `runs` lost; the
residue is the check-ORDER question (a read typed before the pin that follows it), not this
row's.
