### D1648 — a QUOTED operator declaration printed unquoted, and `"<"` before a `<T>` list fused into `<<`: the declaration printer took the name from the node, not the source

**closed 2026-09-05 — the witness runs · was a `vl fmt` round-trip failure (rc 3, `formatter produced invalid output — file left unchanged`) on a `vl check`-clean program, and a silent re-spelling of every other quoted operator · fixed by printing the name token's own source text in `functionHeader` · found by the whole-tree `vl fmt` sweep of #2664, where it was the one file left at rc 3**

Repro (before: `vl fmt` rc 3 and the file left unchanged; now: rc 0 and byte-identical output.
The program itself prints `true` at both — this is the formatter, not the checker. `T` is
scenery: its only job is to put a `<` immediately after the name):

    type P = { x: i32 }
    function "<"<T>(self: P, other: P): boolean { return self.x < other.x }
    const a: P = { x: 1 }
    const b: P = { x: 2 }
    print(a < b)

#### Mechanism

`function "+"` and `function +` name the same function (`parseFuncHead` strips the quotes and
stores the bare operator), so by the time the formatter runs, `FuncDecl.fnName` is `<` and the
source spelling is gone from the node. `functionHeader` rebuilt the header from that name:
`"function " + node.fnName` → `function <`. An INDEX operator escaped, because its name is
re-minted with its receiver (`[]@F32View`) and `opDeclOpOf` recognises the `@` form and
re-quotes it — the one operator family the printer had a spelling for.

For nine of the ten free binary operators the unquoted output still re-parses, so the damage
is a silent re-spelling. For `<` it is not: the printer emits `function <` and the
type-parameter list's own `<` follows immediately, and `<<` lexes as one token. There is no
legal unquoted spelling of that declaration — `function <<T>(…)` written by hand does not
parse either (rc 2) — so the quotes are the only faithful rendering.

The header now takes the name from `declNameTokOf`'s token when one is stamped. A token's
`text` is its raw source span, quotes included, so the source spelling round-trips exactly:
quoted stays quoted, bare stays bare, and `"[]"` is unchanged.

#### Ablation

`vl fmt` over stdin, all twenty spellings, graded against master's fixpoint and the
candidate's. `printed` is what the header emitted (read from a build with the round-trip gate
lifted).

| declaration | before | after |
| --- | --- | --- |
| `function "<"<T>(…)` | **rc 3**, printed `function <<T>(…)` | round-trips, quoted |
| `function "<"(…)` | rc 0, printed `function <(…)` — quotes dropped | round-trips, quoted |
| `function "+"<T>(…)`, `"-"`, `"*"`, `"/"`, `"%"`, `"^"`, `">"`, `">="`, `"<="` | rc 0, quotes dropped (9 of 9) | round-trips, quoted (9 of 9) |
| the same nine, no type parameters | rc 0, quotes dropped | round-trips, quoted |
| `function +<T>(…)` and the other nine bare spellings | round-trips unchanged | round-trips unchanged |
| `function <<T>(…)` written bare | rc 2 — does not parse | rc 2 — does not parse |

Two ingredients, and only their conjunction breaks the round trip: the QUOTED spelling (which
the printer dropped in 10 of 10 rows) and an operator that ends in `<` followed by a
type-parameter list. The bare spellings are the control and are unmoved in all ten rows; the
bare `<`-with-type-params row is the proof that the quotes are load-bearing rather than
decorative.
