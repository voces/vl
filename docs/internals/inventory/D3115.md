### D3115 — a `<T>` function's nested list literal of its parameter builds invalid wasm at any pin but `i32`

**check-clean invalid wasm · clause 1 · open · found grading lane MT against the #3274 review's `B_nested`/`B_2d` shapes · the same on master `f14a8cca2` · filed 2026-09-28 against master `f14a8cca2`**

Repro:

    function f<T>(x: T) {
      const l = [[x]]
      print(l.length)
    }
    f(2.5)
    // vl check: rc 0.  vl run: invalid module

Want:

    1

#### Mechanism

Not localised past the ablation. The outer literal's row is chosen for an element whose own
element is the type parameter, and at any pin whose list is not the plain `i32` list the inner
list built and the outer row's element disagree. The hole spelling `function f(x)` builds the same
literal correctly, and binding the inner list first (`const i = [x]; const l = [i]`) runs, so it
is the nested literal's in-place element that is read at the template's type.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `f(3)` | prints `1` | **yes** (a non-`i32` pin) |
| `f("s")` | invalid module | no |
| `const i = [x]; const l = [i]` | prints `1` | **yes** (the literal in place) |
| `function f(x)`, the hole spelling | prints `1` | **yes** (the `<T>` spelling) |
| `const l: T[][] = [[x]]` | invalid module | no |
| a `: i32` return with `return l.length` | invalid module | no |
