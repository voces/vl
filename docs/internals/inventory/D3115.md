### D3115 — a `<T>` function's nested list literal of its parameter builds invalid wasm at any pin but `i32`

**closed · the per-frame collect pass mints the `string[]`, `f64[]` or `i64[]` row a nested literal's element keys at the instance's pin, and a loop variable over it, or a binding of one, reads its element at the pin · fixture `tests/cases/generics/generic-nested-list-literal-pin.vl` · was check-clean invalid wasm · clause 1 · the union and nullable-scalar pins are [D3154](D3154.md) · found grading lane MT against the #3274 review's `B_nested`/`B_2d` shapes · filed 2026-09-28 against master `f14a8cca2`, closed 2026-09-29 against master `b1794003a`**

Repro:

    function f<T>(x: T) {
      const l = [[x]]
      print(l.length)
    }
    f(2.5)
    // vl check: rc 0.  vl run: invalid module

Want:

    1

#### Mechanism

A collection gap. The frameless collect pass keys the outer literal's element row by the
template's leaf, `i32[]`, so the `f64[]` row the instance's inner list builds was never minted.
The emitter's frame-aware `arrLitElemNameIn` does see the `f64[]` leaf, but it takes that row
only if it exists, so it fell back to the `i32[]` row and stored an `f64` list into an `i32`-list
backing. A program that spells `f64[][]` anywhere mints the row and runs. A `for` over the
result then bound its loop variable at the template's element, which read a `boolean` as `1`
and a literal union as its atom id.
