### D3771 — an error type reaching an inferred return is reported again as "cannot infer a return type", in the function and in every caller and importer that infers from it

**closed, now a loud check reject with the root cause alone (lane DX) · filed 2026-10-06 against master `e2443d6b2`**

Repro:

    // file: terrain.vl
    export function height(x: f64) { return nope(x) }
    // file: entry.vl
    import { height } from "./terrain"
    function above(x: f64) { return height(x) + 1.0 }
    function twice(x: f64) { return above(x) * 2.0 }
    const xs = [1.0, 2.0].map((x) => height(x))
    print(twice(1.0))
    print(xs.length)
    // master: undeclared identifier 'nope', then "cannot infer a return type" for
    // 'height', 'above', 'twice' and the lambda ''

#### Mechanism

`finishInferredReturn` refuses a return that saw only error types (`inferSawErr`) unless the
function's own parameters or a bare `{}` explained it. Two kinds of error type reach it. One is
minted beside a diagnosed error, and the refusal is then its echo, in the function and in every
caller and importer whose return infers from it. The other is a recursive cycle's, which no
diagnostic explains: a call whose callee's return is still pending yields an error type
silently. The fix tells the two apart by where the error type came from, not by whether some
error was raised. `inferCycleFns` records each function a cycle reached (a cycle break, a call to
a pending callee, or a call to a function already in the set), the return pre-pass included. That
function's refusal is raised firm. Every other one goes into `T.diags` under the pending code
`NO_BASIS_PENDING`, so a speculative rollback discards it like any other diagnostic, and
`noBasisFlush` keeps it only when no other error stands. A firm raise of the same refusal makes a
pending one firm.
