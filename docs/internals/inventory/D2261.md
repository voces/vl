### D2261 — a `??` whose left operand is the `null` type is typed `null`, not the default's type

**closed 2026-09-29 (the `??` arm of the binary checker answers the default's type for a left operand that is only `null`; `emit_rewrite` folds a literal `null ?? d` to `d`) · was a loud check reject, and at a literal `null` on the left a loud emit reject of a check-clean program (`{ c: null ?? 3 }`: `ref valtype with no interned shape`), both clause 2 · found in PR #3089's review (D2227); the literal spelling again in the #3299 review grid · filed 2026-09-23 against master `7d369c028` · fixture `tests/cases/operators/coalesce-null-literal-left.vl`**

Repro:

    function f() { 1 == 2 }
    const y: string = (if f() { null } else if f() { null }) ?? "s"
    print(y)
    // was: vl check: type error, "cannot assign null to 'y' of type string"
    // now: prints s

Want:

    s

#### Mechanism

The checker's `??` arm answered the default's type only when the left operand is a `TyNullable`.
A left operand whose type IS `null` (a `TyPrim`) fell past it to the hole-deferral tail, which
answered the left type, `null`. It now answers the default's type. A literal `null` on the left
also reached the emitter's nullable-`??` lowering, which refused it at a binding and had no
shape for a record field typed `null`; the rewrite pass drops the operand, which has no effect.

#### Ablation

| ingredient changed | outcome on master | needed? |

#### Grading list

`null ?? "s"` passed as a `string` argument, `n() ?? 4` bound to an annotated `i32`, the
un-annotated chain used as a `string`, and `n() ?? 6` un-annotated plus one: all run. The
literal `null ?? d` at a nested field, a binding, a print argument, a typed argument, a generic
argument and a closure result, with `i32`, `f64`, `string`, list and record defaults and a
side-effecting default call: all run with the right value. `null ?? null` stays `null`.
