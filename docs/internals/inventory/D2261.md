### D2261 — a `??` whose left operand is the `null` type is typed `null`, not the default's type

**loud check reject · `cannot assign null to 'y' of type string` · clause 2 (the program is well typed: `null ?? d` is `d`) · found in PR #3089's review (D2227) · filed 2026-09-23 against master `7d369c028`**

Repro:

    function f() { 1 == 2 }
    const y: string = (if f() { null } else if f() { null }) ?? "s"
    print(y)
    // vl check: type error, "cannot assign null to 'y' of type string"

#### Mechanism

The checker's `??` arm (`typecheck.vl`, the `op == "??"` branch of the binary checker) answers
the default's type only when the left operand is a `TyNullable`. A left operand whose type IS
`null` (a `TyPrim`, not a `TyNullable`) falls past that arm to the hole-deferral tail
(`mkDerivedHole(HD_COAL, …)`), which ends up answering the left type, `null`. The checker's own
`tyExcludesNull` already says `null ?? d` is exactly `d`. A prediction from reading the arm, not
yet confirmed by a probe of the rung's input.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the `if` chain (a bare `null ?? "s"` instead) | same error | no |
| the chain replaced by a call of a function returning only `null` (`n() ?? "s"`) | same error | no |
| the annotation on `y` (un-annotated, then `y + "!"`) | `operator '+' is not defined for _ \| null and string` | no, it moves |
| the `null` type on the left (an else-less `if f() { null }`, a `TyNullable`) | still refuses, `cannot assign string \| null`, through the other arm | unclear, re-grade at the close |

#### Grading list

`null ?? "s"` passed as a `string` argument; `n() ?? 4` bound to an annotated `i32`; the
un-annotated spelling used as a `string`.
