### D3530 — a two-width literal union is refused delivery into a nullable float (`f64 | null`), where its non-null spelling and `i64 | null` both run

**loud check reject · clause 2 · open · found by lane LC closing D3523 (`map_value` of the `litunion-mixed-width-into-f64` and `-coalesce-i64` matrices) · the same on master `f6e17953b` · filed 2026-10-03 against master `f6e17953b`**

Repro:

    type D = 9000000000 | 1
    function g(): D { 1 }
    const z: f64 | null = g()
    print(z)
    // vl check: "cannot assign D to 'z' of type f64 | null"

Want:

    1

#### Mechanism

`litNumUnionConverts` (D3523) admits a literal box into a numeric primitive only. A nullable
destination lowers as a box too, and a box-to-box delivery converts by retagging members
(`recordWidenRetag`, `widenTargetOf`), whose table widens `i32` into `i64` or `f64` and `f32`
into `f64`, but has no `i64` into `f64` row: for a variable that conversion is lossy. A box of
literals holds its wide member under the `i64` tag, so the retag owes a conversion that is exact
only because the member is a constant. Admitting the nullable destination without that row
printed `null` for the program above in lane LC's draft, which is why it was held back. The
fix is the row: a retag from `i64` to `f64` (and to `f32`) recorded only for a literal box
whose `i64` members `intLexHeldBy` the destination. The map-value position of the matrices is
this delivery, because a map read is `V | null`.
