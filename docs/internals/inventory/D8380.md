### D8380 — an inferred-return function handing back a generic identity's record literal, delivered into a record union and also read at the literal's own type, returns the bare row into the union

**closed 2026-10-20 · runs, prints `4` `4` · was check-clean invalid wasm · `vl check` rc 0 · clause 1 · when the record adoption keeps an inferred-return function at its own row, each literal it returns through a generic identity is built at the landing (`recIdentityLeavesAt`, `check_fit_rules.vl`), so the identity's instance is pinned there · pins: `tests/cases/generics/inferred-return-identity-literal-also-read-at-own-type.vl` and its annotated twin · matrix `inferred-return-identity-literal-also-read-at-own-type` · present on master `cd64d5faa` and `1e05c7e3c` · found closing [D8341](D8341.md) · filed 2026-10-20 against master `cd64d5faa`**

Repro:

    type J = { r: i32 | null }
    function idn<T>(v: T): T { v }
    function deliver() {
      return idn({ r: 4 })
    }
    const v: J | string = deliver()
    const q = deliver()
    print(q.r)
    if v is J { print(v.r ?? 0) } else { print(0) }
    // vl check: rc 0.  vl run: invalid module, "expected (ref null $5), found (ref $6)": the union box expected, the `{r: i32}` row found

Want:

    4
    4

#### Mechanism

`deliver` is built once, at `{r: i32}`, since its second call site reads it at the literal's
own type, and the union delivery at the first site stores that bare `{r: i32}` ref with no
box and no conversion to `J`. The checker accepts the first site as a fresh record delivered
to the wider `J` (spelling `deliver(): { r: i32 }` refuses there, "only a fresh record
widens"), but with two sites at two types nothing builds the record at `J` for the first.
With the literal returned directly (no `idn`) the same two sites run, printing `4` twice:
`deliver` is then built at `J` and the second site reads `J`. The pin that decides it is the
checker's or mono's adoption of the fresh return, outside the emit-collect lane; a relative of
[D8301](D8301.md), a literal-building function delivered into two records of different storage.

Traced further by lane mono-rows (2026-10-20): the fix is not in `emit_mono.vl`. The no-`idn`
spelling builds `deliver` at `J` because the checker retypes the returned literal
(`recordRepTyAdopt`, reached through `check_assignable.vl`'s fresh-record adoption), and mono
only reads that rep. Through `idn` the literal is an argument of a generic call, and no
adoption retypes it, so `deliver`'s return stays `{r: i32}`. Mono cannot pin `idn` at `J` on its
own: `deliver` is not generic, so `q`'s read is of the same single build. The close is in the
checker's adoption of a literal handed back through a generic identity.

The fix, measured 2026-10-20. With `idn` removed, the checker does not retype the literal.
A `recordRepTyAdopt` probe was checked against a control that fired, and on this spelling it
fires on nothing. `deliver` is built at `J` only because emit's name scan picks the declared
row. So the prediction that the direct case is retyped by `recordRepTyAdopt` was wrong.

Through `idn`, the two sites land apart from each other, one landing queued at `J` and one
un-annotated. `recFnBuiltAtDst` therefore declines, and `recAdoptNote` falls through to
`recAdPushDecl`, which only records the function as kept. Mono then pins `idn`'s instance at
the literal's own row.

The fix adds one step at that fall-through. It stamps each literal returned through an
identity at the landing, which is what the single-site D8341/D8021 path already does.
Direct leaves are left to emit's scan, so the direct spelling does not move.

The new matrix runs 62 of 62 cells. On master `1e05c7e3c`, 35 of them are invalid wasm:
31 in the annotated face and 4 in the un-annotated face (`return_annotated`,
`struct_field_assign`, `array_element_assign` and `array_push`).
