### D2161 — a class-keeping list widening SHARES the list, so a `null` written through the wider handle reaches the narrower one

**now a loud check reject by design at the DELIVERY · closed 2026-09-23 by the owner's ruling: only a readonly list is covariant, so `C[]` into a mutable `(C | null)[]` is refused at every position, and `readonly (C | null)[]` is the spelling that shares the list · was loads then traps, then a check reject at the write by [D2060](D2060.md)'s rule · clause 1 (soundness) · 5 element kinds, every delivery position · filed 2026-09-23 against master `b52b14e83`**

Repro:

    type C = { n: i32 }
    function clear(xs: (C | null)[]) { xs[0] = null }
    const a: C[] = [{ n: 1 }]
    clear(a)
    print(a[0].n)
    // was: vl check rc 0, vl run: wasm trap: null reference
    // now: vl check rc 1 at `clear(a)` — C[] is not (C | null)[]: a container never widens
    //   implicitly, and only a readonly list is covariant

#### Mechanism

`assignable` is covariant in a list's element, and the element-storage rule
(`containerElemClassDiffers`) admits a widening whose element keeps its storage class with no
copy: a `C` and a `C | null` element are the same nullable reftype, a `boolean | null` the same
`i32` with a sentinel. So both handles alias one list, the wider one accepts a store the
narrower one's type forbids, and the narrower one's reader sees it. This is Java's covariant
array hole. The written-through check (D821, `covarWriteThrough`) fires only where the two
handles need DIFFERENT element storage, which is exactly the case this one is not. Under the
2026-09-23 ruling (DECISIONS.md §"No implicit container widening") the widening itself is what
is unwanted; `readonly (C | null)[]` is the spelling that keeps the pass sound.

**The close.** The ruling took the second of the two shapes below. `listWidenWalk`, run at the
one seam every delivery shares after the storage floor, refuses any list whose element
`assignable` widens (`listElemWidens`) unless the destination is `readonly`, through nullables,
unions, nested lists, record fields and function types. It keys on each list's ORIGIN: a list
literal, or a `const` bound to one whose contents nothing stores into, is built at the type it
flows into and is exempt, while the lists inside it are judged by their own expressions
([D2194](D2194.md) is the one origin still taken on trust). Two containers cannot take a view:
a MAP, which has none, refuses a list value or key whose element differs, and a view of a union
or nullable element reached from a mutable list (a view stored back through the map may view a
narrower list); a list shared at its own element type (`string[]` into `readonly string[]`)
passes. A RECORD value is shared, not rebuilt, so a list field whose element differs is refused
even into a `readonly` field ([D2100](D2100.md) is the rebuild that would lower it). The message
names only fixes that build — `readonly` for the whole destination when this checker accepts
it, a `.map` copy except for [D2193](D2193.md)'s elements, and the source's own type to declare
it at — and `tests/vl_widen_hint_test.ts` applies every printed fix and checks the value it
delivers. A readonly copy under `| null` or nested in another list is [D2196](D2196.md).
Fixtures: `tests/cases/arrays/error-list-widening-*.vl`, the readonly twin
`list-widening-readonly-destination-runs.vl`, and `maps/readonly-view-same-element-runs.vl`.

**Out of scope, with witnesses.** A record whose field widens WITHOUT a list inside
(`{x: i32}` into `{x: i32 | string}`, [D2100](D2100.md)/[D2160](D2160.md)) is the record rule's
([D2060](D2060.md)). A map value that widens without a list inside (`{[string]: C}` into
`{[string]: C | null}`) shares its entries and runs read-only; a write through the wider map is
refused by D2060's rule, so it is sound, and it is left as it stands.

Before the ruling, the list kept its element storage, so it was shared, and D2060's analysis (which follows every
handle a covariant delivery creates and refuses a store the source's slot type cannot hold) now
covers it: each ablation row that writes `null` is a check reject at the delivery, the row that
writes a value of the narrow type (`{ n: 7 }`) and a read-only delivery still run. What stays the
owner's is whether the widening should be refused even where nothing writes.

#### Ablation

| element pair (write `null` through the wide handle, read the original) | outcome |
| --- | --- |
| `C[]` into `(C \| null)[]` (the witness) | trap: null reference |
| `i32[][]` into `(i32[] \| null)[]` | trap: null reference |
| `boolean[]` into `(boolean \| null)[]`, `print(a[0])` | prints `true` — the sentinel read as a boolean |
| `K[]` into `(K \| null)[]` (`K = "a" \| "b"`, holding `"a"`) | prints `b` |
| `string[]` into `(string \| null)[]` | loud emit reject `bare null needs a struct-typed context` |
| any of these, writing a value of the NARROW type (`{ n: 7 }`) | runs; the write is seen through both handles |
| the parameter declared `readonly (C \| null)[]` | loud check reject at the write |

#### Grading list

Each ablation row at the grid's nine positions (binding, argument, return, assignment, struct
field, element, push, global init, global assignment). A close has two honest shapes, and the
owner picks: refuse the widening at the write (D821's rule extended to a shared storage), or
refuse the implicit widening itself and make `readonly` the only covariant spelling. The second
costs running programs — `elem-storage-class-widening-runs.vl` pins five of them.
