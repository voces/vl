### D2161 — a class-keeping list widening SHARES the list, so a `null` written through the wider handle reaches the narrower one

**now a loud check reject at the write, by [D2060](D2060.md)'s write rule (the grading list's first shape); the owner's choice between that and refusing the widening itself is still open · was loads then traps · clause 1 (soundness) · 5 element kinds, every delivery position · filed 2026-09-23 against master `b52b14e83`**

Repro:

    type C = { n: i32 }
    function clear(xs: (C | null)[]) { xs[0] = null }
    const a: C[] = [{ n: 1 }]
    clear(a)
    print(a[0].n)
    // was: vl check rc 0, vl run: wasm trap: null reference
    // now: vl check rc 1 at `clear(a)` — the assignment on line 2 writes a widened element

#### Mechanism

`assignable` is covariant in a list's element, and the element-storage rule
(`containerElemClassDiffers`) admits a widening whose element keeps its storage class with no
copy: a `C` and a `C | null` element are the same nullable reftype, a `boolean | null` the same
`i32` with a sentinel. So both handles alias one list, the wider one accepts a store the
narrower one's type forbids, and the narrower one's reader sees it. This is Java's covariant
array hole. The written-through check (D821, `covarWriteThrough`) fires only where the two
handles need DIFFERENT element storage, which is exactly the case this one is not. Under the
2026-09-23 ruling (DECISIONS.md §"No implicit container widening") the widening itself is what
is unwanted; `readonly (C | null)[]` is the spelling that keeps the pass sound.

The list keeps its element storage, so it is shared, and D2060's analysis (which follows every
handle a covariant delivery creates and refuses a store the source's slot type cannot hold) now
covers it: each ablation row that writes `null` is a check reject at the delivery, the row that
writes a value of the narrow type (`{ n: 7 }`) and a read-only delivery still run. What stays the
owner's is whether the widening should be refused even where nothing writes.

#### Ablation

| element pair (write `null` through the wide handle, read the original) | outcome |
| --- | --- |
| `C[]` into `(C \| null)[]` (the witness) | trap: null reference |
| `i32[][]` into `(i32[] \| null)[]` | trap: null reference |
| `boolean[]` into `(boolean \| null)[]`, `print(a[0])` | prints `true` — the sentinel read as a boolean |
| `K[]` into `(K \| null)[]` (`K = "a" \| "b"`, holding `"a"`) | prints `b` |
| `string[]` into `(string \| null)[]` | loud emit reject `bare null needs a struct-typed context` |
| any of these, writing a value of the NARROW type (`{ n: 7 }`) | runs; the write is seen through both handles |
| the parameter declared `readonly (C \| null)[]` | loud check reject at the write |

#### Grading list

Each ablation row at the grid's nine positions (binding, argument, return, assignment, struct
field, element, push, global init, global assignment). A close has two honest shapes, and the
owner picks: refuse the widening at the write (D821's rule extended to a shared storage), or
refuse the implicit widening itself and make `readonly` the only covariant spelling. The second
costs running programs — `elem-storage-class-widening-runs.vl` pins five of them.
