### D3760 — a getter read after a fresh `const` is checked does not count as a use of it, so a write through the getter's result leaves the const's narrowing standing

**closed 2026-10-06 by lane GN — the filed repro RUNS and prints `true` · was loads then traps (`cast failure`), clause 1, and a check-clean silently wrong `false` when the field is a nullable record, and a loud check reject when the narrowing is an `is` test · found in review of #3399 · filed 2026-10-06 against master `b05991d98` · fixture `tests/cases/soundness/getter-alias-write-ends-place-narrowing.vl`**

Repro:

    type H = new { f: i32 | null }
    get me(self: H): H { self }
    function g(): boolean {
      const p: H = { f: 4 }
      const q = p.me
      if p.f != null {
        q.f = null
        return p.f == null
      }
      false
    }
    print(g())
    // vl check: rc 0.  vl run: wasm trap, cast failure

Want:

    true

#### Mechanism

D2584's sole-reference rule lets a write through another name skip a fresh `const` whose name its
root uses only as a receiver. A getter hands its receiver on, so `x.p` counts as a use when it reads
a getter. `crValUseEnter` (typecheck.vl) decided that from `getSiteFnOf`, which the checker
fills as it checks each site. It asks when the `const` is declared, and the root's sites after the
declaration are not checked yet. So `p.me` on the next line was not a use, `p` was recorded as the
only holder of its object, and `q.f = null` did not retire `p.f`. The emitter then read `p.f` at the
narrowed `i32` and the cast trapped. The close counts `x.p` as a use whenever some getter is named
`p`. The getter registry is filled when the declarations are hoisted, before any body is checked.
#3399 cached the walk but kept the old reading of the bank, so the defect predates it.
