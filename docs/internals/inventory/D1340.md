#### Mechanism

`arrLitNulRefElemName` (D1270) claims a literal whose recorded element is a `TyNullable`
only when the ref-list layer can NAME the re-formed array — `nameIsRefArray(refElemArrName(nen))`.
`refElemArrName` re-groups the element in parens for exactly three niches, and its own header
says so: a nullable LIST, a nullable MAP and a nullable CLOSURE. A nullable STRUCT is
deliberately excluded there ("value-union / nullable-struct elements keep their existing
(munged-name) kind"), so `S | null` munges to `S | null[]`, `nameIsRefArray` reads a
multi-atom element and answers false, and the literal falls through to the i32 default exactly
as before.

So this is TWO missing halves, not one, and that is why it was not closed with its eight
siblings. `refElemArrName` needs a nullable-STRUCT arm, and the exclusion is load-bearing for
its NEIGHBOUR: re-grouping a value-union element (`i32 | null`) turns it from "not a ref array"
into kind 2, a real behaviour change on the annotated path. And the name the inferred literal
would key must be the NOMINAL `S|null` that `refArrShapeKind`'s `structIndexByName` rung
resolves — `tyToEmitName` renders a `TyObj` structurally (`{a:i32}|null`), which resolves no
struct row, so the two producers would name different rows for one element.
