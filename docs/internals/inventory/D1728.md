### D1728 — an if-EXPRESSION joining a hole parameter's atom with a member literal builds the string join over the atom slot, and is check-clean invalid wasm

**check-clean invalid wasm · `vl check` rc 0, `vl run` exit 70 · clause 1 · filed 2026-09-06 against master `5530f6132` · residue of [D1545](D1545.md), whose close fixed the INLINE face of this same join and left the alias one · 0 corpus cells**

Repro:

    type K = "red" | "green"
    const src: K[] = ["green", "red"]
    function take(a) {
      const b = if a == "green" { a } else { "red" }
      print(b)
    }
    take(src[0])
    // vl check: rc 0.  vl run: invalid module,
    // type mismatch: expected i32, found (ref $type)

Annotate the parameter `a: K` and the same program prints `green`, at both seeds.

#### Mechanism

Predicted, not probed. The two arms disagree about the rep and nothing reconciles them: the
`then` arm is the parameter, an interned i32 atom, and the `else` arm is a member LITERAL, which
lowers as a string ref. `exprIsLitAtom`'s `IfStmt` arm claims the join only when BOTH arms are
atoms — its own header says a mixed atom/string join types `string` instead and widens at the
seam — so the binding takes the atom slot from the first arm while the second stages a
reference into it. The direction of the message says which end won: `expected i32, found (ref
$type)`.

**The annotated DESTINATION is a check reject, not a fix**: `const b: K = if …` answers `cannot
assign string to 'b' of type K`, so the checker already knows the join is a `string` — the
emitter is the half that does not.

**[D1545](D1545.md)'s close moved the inline face out of here.** With the inline set repped as
`string`, both arms of the same join are strings and it runs; the alias face keeps the atom in
one arm and is what this row is.
