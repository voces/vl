### D16744 — a `for` loop over an un-annotated list parameter of functions with different results calls each element at one signature and traps

**closed 2026-11-16 · runs, prints `4` `1.5` · fixed by lane AE4: the elaboration reads a `for` loop whose element is only ever called (directly, through a `const` or unwritten `let` copy, as the root of an element chain, or as the list an inner such loop walks) as an element read of the list parameter, so the call mints its fact and the set is tagged · was check-clean trap, `indirect call type mismatch` · clause 1 · fixture `tests/cases/closures/hole-fn-list-param-walked-by-for.vl` · found closing [D16742](D16742.md) · filed 2026-11-16 against master `7de99c68a`**

Repro:

    function inc0(a) { return a + 1 }
    function half(a) { return a / 2.0 }
    function run(xs) { for x in xs { print(x(3)) } }
    run([inc0, half])
    // vl check: rc 0.  vl run on master: prints 4, then wasm trap: indirect call type mismatch

Want:

    4
    1.5

#### Mechanism

The tag decision tags a set held in a list parameter only where every instance's calls through
it have a fact (`ftHoldCtxOk`'s hole-argument rule, `mintSetPartial`). The elaboration notes a
call's fact when its callee is the parameter or an element chain off it (`elabMintFactAt`), and
marks the set partial for any other read of the parameter (`elabMintHandedIn`). A `for` loop's
list is such another read, so the set was partial and stayed a list of closures. The closure call
then went through one signature, `(i32) => i32`, and `half`'s `f64` adapter trapped. The `while`
spelling `xs[i](3)` was already a callee chain and ran.
