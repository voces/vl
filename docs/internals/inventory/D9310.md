### D9310 — a generic function held in an un-annotated `Map()`, or in a record held as its value, called at two types has no map value type

**loud emit reject · `vl check` rc 0 · `unsupported map value type` · clause 2 · found closing [D9065](D9065.md) · present on master `cf1b1a8d3` · filed 2026-10-21 against master `cf1b1a8d3`**

Repro:

    function id<T>(x: T): T { x }
    const m = Map()
    m["k"] = { f: id }
    const r = m["k"]
    if r != null {
      print(r.f(2))
      print(r.f("s"))
    }
    // vl check rc 0.  vl run: emit error: emitProgram: unsupported map value type (no rep for a union-member struct, ...)

#### Mechanism

Partly traced. The map's value type is taken from the parameter types its calls pin on the
stored slot (`monoPinMapSlot` and `monoStoredSlotFnTy`, emit_mono.vl), and one slot holds
one closed type: with two pins the slot reads -1, so the value keeps its open signature. A
list literal holding the same record (`const xs = [{ f: id }]`, `xs[0].f(2)`,
`xs[0].f("s")`) runs, printing `2` and `s`, because fn_split.vl copies a `const` list
literal once per call type; a map written by `.set` or an index after its `Map()` has no
such copy. Re-graded 2026-10-21 by lane-D9311: still as filed, and the fix belongs in that
per-type split rather than in the map's slot.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the second call's type (`r.f(5)`) | runs | **yes** |
| the record (`m["k"] = id`, `r(2)`, `r("s")`) | same refusal | no |
| the binding (`m["k"]?.f(2) ?? 0`, `m["k"]?.f("s") ?? "none"`) | same refusal | no |
| the map (a list literal) | runs, `2` and `s` | **yes** |
