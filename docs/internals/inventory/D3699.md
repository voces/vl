### D3699 — inside brackets a negative integer match pattern was read as a subtraction from the previous arm's body

**closed 2026-10-05 — the witness prints 20 · was a parse error on master (`expected an expression but found GT`) for a `vl fmt`-clean program · by `negArmPatternAt` in `parser.vl`: a line-leading `-` whose run reads as an integer pattern followed by `=>` never continues the line · found while grading D3698, whose spaced `- 1 =>` arm at statement level would otherwise have regressed the same way · filed and closed by lane SR against master `56af0f07e` · fixture `tests/cases/match/negative-integer-pattern-in-call-argument.vl`**

Repro:

    const x = -1
    print(
      match x {
        1 => 10
        -1 => 20
        _ => 30
      },
    )

Want:

    20

#### Mechanism

D1581's bracket gate lets any line-leading binary operator continue inside an open `(`, `[`
or object-literal `{`, `-` included, and a `match` block does not reset `brDepth` (only
`parseBlock` does). So inside `print(…)` the arm body `10` met the next line's `-1`, continued
into `10 - 1`, and the arm's `=>` was then read as `=` and a stray `>`. At statement level
the tight `-1` stayed a new arm. D3698 made a SPACED `- 1 =>` continue at statement level
too, which would have broken it there as well. No continued expression can be followed by
`=>` after an integer-pattern run, so the guard only turns a parse error into the arm.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the enclosing `print(` (statement-level `match`) | 20 on master | **yes** |
| the `-` (pattern `1`) | 20 on master: a NUMBER cannot continue | **yes** |
| the earlier arm (negative pattern first) | 20 on master: no body before it | **yes** |
| an or-pattern `-1 \| -2` in place of `-1` | still a parse error on master | no |
