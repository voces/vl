### D15934 — a program whose check stops before the record solve's pass end makes the next program on the instance skip a refusal

**closed · now a loud check reject, as checked alone · was check-clean (exit 0) when checked after such a program in one `vl check --batch`, a cross-program leak · filed 2026-11-12 against master `6a2ef29f` · closed the same day: the record solve's per-pass queues (`recOwnSrc`, `recKept*`, `recListLits`, the apart and wide-function lists, `recOwnRefused`) are emptied when a pass starts as well as at its end (`recPassQueuesReset`, check_program.vl) · test `tests/vl_check_json_test.ts` "a program after one whose check stopped early keeps its refusal" · the intermittent native-align failure of `soundness/error-literal-binding-built-wider-stored-beside-own-literal.vl`**

Repro:

    // vl check --batch a.vl b.vl, with VL_JOBS=1
    // a.vl:
    function id(a) { return a }
    const lap = (g) => {
      const x = g(1); return x.toString()
    }
    function use(k) { return k(id) }
    print(use(lap))
    // b.vl:
    type J = { f: i32 | null }
    const o = { f: 4 }
    const wideJ: J[] = [o]
    const m = Map()
    m.set("b", { f: 5 })
    m.set("a", o)
    // vl check: b.vl refused, `set: expected {f: i32}, got J`, as it is alone

#### Mechanism

The record solve's queues are node-indexed and were emptied only in `recRunPending`, near the
pass end. `a.vl`'s check stops before it, on the unimported UFCS call in the lambda's
instance, and leaves its entries behind. In `b.vl` the refusal of `m.set("a", o)` skips any
use `recOwnRefused` lists, and `a.vl`'s entry named the same node index. Native-align's batch
waves split files across workers dynamically, so the pair met only on some runs.

| `VL_JOBS=1` (files spread over workers) | refused or not, by schedule | no |
