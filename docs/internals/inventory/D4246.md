### D4246 — a list holding a written `let` of generics inside a function, called through its element at two types, builds invalid wasm

**closed · runs, prints `z` `1` · was check-clean invalid wasm, clause 1, then a loud emit reject from 2026-10-12 (lane SC) until [D9791](D9791.md)'s close · found in round 2 of the review of #3578, grading `rv3578/cells3` (`ret2_idg_list_fn`, `ret2_idh_list_fn`) · filed 2026-10-12 against master `f6ee50929` · pins: `tests/cases/closures/list-of-written-let-in-function-called-at-two-types.vl`, `tests/cases/closures/list-of-written-let-in-function-called-at-literal-union.vl`**

Repro:

    function idg<T>(t: T): T { return t }
    function main() {
      let x = idg
      x = idg
      const y = [x]
      print(y[0]("z"))
      print(y[0](1))
    }
    main()
    // vl check: rc 0.  vl run, before D9791's close: a list holding a generic function is called through its elements at more than one type

Want:

    z
    1

Since [D9791](D9791.md)'s close, a written `let` whose every write names `idg` is listed as
`idg` itself is, so each element call takes its own instance.

#### Mechanism

Inside a function the checker adapts the write `x = idg` to a lambda `($fp0: string) => idg($fp0)`
at the type of the list's first element call, and leaves the `let`'s own type generic. The
monomorphizer followed a written `let` only when every write named a declared generic, so it saw
no generic in `[x]`, did not pin the list, and the second call passed an `i32` to the `string`
adapter. A write that is the checker's adapter around a declared generic is now read as naming
it (`monoAdapterCallee`), so the list is pinned and refused at two types as D3977's list is.
