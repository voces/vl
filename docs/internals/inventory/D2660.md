### D2660 — a generic `T` bound from a list and from a `let x = null` hole that a later write fills builds invalid wasm

**closed 2026-11-12 · runs, and prints `2` · a read of `x` before `x = 5` is `null`, its most recent write's type (flow-sensitive reads, owner ruling B, 2026-11-02) · contained earlier the same day as a loud check reject (`judgeNullHoleDeliveries`), which still refuses the loop-head spelling · before that the module failed to validate (clause 1) · pre-existing on master `979323f83` · found by the #3188

Repro:

    function link2<T>(xs: T[], v: T) { xs.push(v) }
    function main() {
      const xs: (string | null)[] = []
      let x = null
      link2(xs, x)
      x = 5
      xs.push("s")
      print(xs.length)
    }
    main()
    // first: vl check rc 0, then the emitted module failed to validate inside `main`
    // then: the delivery of `x` at the call was refused at check
    // now: runs

Want:

    2

#### Mechanism

Not traced. `T` binds to `string | null` from `xs` and to the open hole of `x`, and the call
checks while `x` is still the `null` type, so the pair agrees. The later `x = 5` fills `x`'s hole
with `i32`, and nothing re-asks the call: the instance was built for `string | null`, while `x`
now lowers as an `i32 | null` box, so the argument at the call is the wrong rep. The annotated
twin (`const x: i32 | null = null`) is refused at the call (`argument 2: expected string |
null, got i32 | null`), which is the answer this spelling owes too. Unlike D2506's refusal, the
open hole here is the argument binding itself, not an element inside it.

#### Minimal witness (2026-11-02, master `5a736baa`)

No generic, list or call is needed. Every delivery of a read of an un-annotated `let x = null`
made before a later write fills its hole is judged at `null`:

    let x = null
    const y: string | null = x
    x = 5

`vl check` rc 0, then invalid wasm (`expected (ref null $0)` against the `i32 | null` box). The
same at `xs.push(x)` and at `xs[0] = x` into a `(string | null)[]`. With `x = "s"` as the fill, or
no fill, it runs; with `let x: i32 | null = null` the delivery is refused (`push: cannot add
i32 | null to (string | null)[]`). So it is flow typing, not the record-covariance rule (D2996):
the binding's type is the join of its writes, `i32 | null`, while a read before the filling write
keeps the initialiser's `null`, and nothing re-asks the deliveries made at that read once the
hole fills. The answer this spelling owes is the annotated twin's refusal.

#### Containment (2026-11-12)

A delivery of a read of a `let x = null` made while the hole is open is recorded with its
destination (`noteNullHoleDelivery`, from `constrainEmptyExpr`), and judged once checking ends at
the type the hole was filled with (`judgeNullHoleDeliveries`). The binding is stored at that
type, so a destination that cannot take it is refused, with the annotated twin's verdict. The
judgement is static, so a loop back-edge cannot make it unsound: `while … { const y: string |
null = x; x = 5 }` is refused too, where it was invalid wasm. A fill the destination accepts
(`x = "t"`, or a `i32 | null` destination with `x = 5`) runs as before, and so does a hole
nothing fills.

#### Ruling (2026-11-02): B, backlogged

Owner ruling: a read of a `let` takes the type of the most recent write in scope, so `x` read
before `x = 5` is `null` there and the delivery is sound. That is a new, flow-sensitive rule; it
is backlogged as ROADMAP.md §"Backlogged: ruled, waiting to be built", flow-sensitive reads of a `let`, with this row and [D14930](D14930.md) as its witnesses. This row
waits on it. DECISIONS.md §"A read of a `let` takes its most recent write's type".

#### Close (2026-11-12): flow-sensitive reads

The declaration `let x = null` installs an assignment narrowing of the closed `null` type, so a
read before the first write is `null` rather than the hole the write fills in place. `link2(xs,
x)` then binds `T` to `string | null`, and the argument is delivered as that null
(`emitNullReadAtDst`, `wasmEmit.vl`). A loop-head read still takes storage, because the body's
write retires the row before the loop (`crLoopPreRetire`), and so it is still refused
(`tests/cases/inference/error-null-let-read-at-loop-head-before-a-filling-write.vl`). Refactor
note: `docs/internals/refactor-notes/2026-11-12-flow-reads-design.md`.
