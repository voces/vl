### D1582 — the map TYPE is spellable and nothing said so: `Map` in a type position answered `unknown type 'Map'`, a message whose remedy is a spelling nobody can guess

**now a loud check reject that NAMES THE SPELLING (fixed; the program stays illegal — `Map` is not a type name — and the message is what changed) — `builtinCtorTyLeafFail` banks a hint on the `unkTyClash` wire at both leaf ladders and at the generic-alias door, so `Map`/`Set` in ANY annotation position now names the index-signature spelling and the constructor · was a loud check reject that conceded nothing · diagnostic grid 8 of 8 positions, `runs` unchanged 10/20 (a message change moves no cell) · ZERO corpus cells · reported by the glean session, VL-033, `~/glean/docs/vl-issues.md` · filed 2026-09-04 against master `9ba97704`**

Repro (`vl check` reports `` `Map` is not a type name — `Map()` is the constructor and the map TYPE is spelled `{[K]: V}`, e.g. `{[string]: i32}` for field 'index' ``):

    type S = { names: string[], index: Map }
    print(1)

#### Mechanism

`Map`/`Set` are CONSTRUCTOR names — `checkCallNode` recognises `Map()` and answers
`mkMapTy`, and `emit_base.isBuiltinFnName` deliberately lets a program declare its own.
Neither is a TYPE name: `primTyOfName` and `declaredTyOfName` know nothing of them, so
`Map` in a type position fell off the end of both leaf ladders (`tsLeafTy` for the
spelling tree, `nameToTyReal` for the rendered name) and got the generic
`unknown type 'Map'`. Honest and useless — the remedy is `{[string]: i32}`, and nothing
in the tree told a reader that. The reporter concluded a map could not be a struct field
at all and fell back to a hand-rolled open-addressed table in `i32[]`.

The fix is `storageTyLeafFail`'s twin. `builtinCtorTyLeafFail(name)` banks the hint on
`unkTyClash`, the override wire `unknownTyText` already prefers, so all six raise sites
report it without gaining an arm. It is reached from three doors, not one: the two leaf
ladders, and `applyGenAliasArgs`, which is where `Map<string, i32>` — the spelling a
consumer reaches for first — enters instead. And it sits AFTER the declared-name rung at
both ladders, so a program declaring `type Map = …` keeps it. The wording ends in the
EXAMPLE because two of the six sites append their own clause (`… for field 'index'`,
`… in union 'U'`).

Two companions, same reasoning: `docs/guide/collections-design.md` gains a "What you
write TODAY" table putting the type spelling and the constructor in one place (the rest
of that document is design vocabulary and calls `Map()` uncommitted), and the LSP
completion detail for `Map` stopped saying `() => Map`, which named a type that does not
resolve.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the field position (a binding / param / return / union member) | the same hint | no — every annotation position |
| the bare spelling (`Map<string, i32>`) | the same hint, via a DIFFERENT door | **yes** — the alias-application arm needed its own hook |
| `Map` replaced by `Set` | the set spelling `{[K]: boolean}` | no — the same mechanism |
| `Map` replaced by an ordinary unknown name (`Bogus`) | `unknown type 'Bogus' for field 'f'`, unchanged | **yes** — the hint is name-gated |
| the program DECLARES `type Map = { a: i32 }` | resolves, runs | **yes** — the hint is after the declared rung |
| the position is `x is Map` / `x as Map` / a match pattern | still `unknown type 'Map' in 'is'` | those three build their message by hand and were left alone — `is` over a map type is not a thing the right spelling makes work |
