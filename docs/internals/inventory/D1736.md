### D1736 — a `while` condition narrows its body for `!= null` and NOT for `is`, so the loop spelling of a guard the `if` accepts is refused

**loud check reject · filed 2026-09-06 against master `6de9fd11a` · found as the two
`is_in_while` cells that refuse on both seeds of D1719's template · 0 corpus cells**

Repro:

    type A = { r: i32 }
    type M = i32 | A
    function st(): A { return { r: 8 } }
    function pick(b: boolean): M { if b { return st() } return 7 }
    const v: M = pick(true)
    while v is A { print(v.r)
      break }
    if !(v is A) { print(0) }
    // vl check: rc 1,
    // field 'r' is not on every member of M — narrow with `is` first (i32 is not an object)

#### Mechanism

Not D1734's family: no map, no place, and the receiver is a bare name. `checkWhileStmtNode`
collects the condition's facts like an `if`, then keeps only those whose narrowed type is
exactly `nonNullTy(lookup(name))` — a null strip — and only for bare names.

**The restriction is DELIBERATE and its comment says so**: "Only a null strip re-narrows
(never an `is T` pin), and only bare names (property paths can alias)", on the reading that
the body is "re-tested every iteration". That reason does not separate the two: `v is A` is
re-tested at the top of each iteration exactly as `v != null` is, and the write-retire
machinery covers a body that assigns. So the row is a bounded DESIGN question — is the pin
unsound across the loop's re-execution barrier, or only unimplemented — and not a hole.

The message is the same one D1730 names: it tells the author to narrow with `is` first, in a
program whose condition IS an `is`. That half is shared; the mechanism is not.

#### The ruling's premise is REFUTED by measurement, 2026-09-06

The owner ruled (a) on 2026-09-06 — the pin is the null strip's twin, "retired by a write to
the receiver exactly as `!= null` is". **Built, and the price lands on WORKING code.** With
`checkWhileStmtNode`'s null-strip filter dropped and the emitter's `narrowStripNullOnly` with
it, all four cells run — and `tests/cases/unions/paren-is-narrow.vl` stops compiling:

    let x: i64 | boolean = 6000000000
    while (x is i64) { n = n + 1
      x = true }
    // cannot assign boolean to i64

That is `runs -> not-runs` on a corpus program, the one movement the gate refuses on.

**A narrowed binding's type is also what it ACCEPTS, and that lands differently on the two
guards.** For a null strip the assignment the narrow forbids is `e = null` — the one that
would falsify the fact, which is the soundness the guard is for. For an `is T` pin it is the
one that FLIPS the variant, and a flip is how a loop over a union makes progress. The
retirement does not *cover* the write; it *refuses* it, and for a loop that is termination.

**The `if` spelling is not the oracle for this axis**, which is where the row's own ablation
misled: `if v is A { v = 7 }` rejects the flip too, and an `if` arm needs no flip to finish.
`tests/cases/loops/while-body-is-guard-not-narrowed.vl` is the standing contract fixture that
states exactly this and names `paren-is-narrow.vl`'s `whileParen` as the price — it was
written before the ruling and predicted the failure verbatim. The property-path restriction
falls out of the same contract, so the `if`/`while` disagreement there is designed too.

What a close would now need is not the pin but a rule that lets the FLIP through — a narrowing
whose write contract admits an assignment that leaves the guard's own scope — and that is a
larger design question than this row asked.
