### D1641 — `[] as u8[]` refuses at the numeric-only `as` arm, and the message does not say the cast is what is wrong

**fixed — now a loud check reject that ENDS by naming the spelling that works: `` `as`
supports numeric conversions only; write `[]` — an empty array literal takes its element
type from its destination `` · was the same refusal, one clause short · diagnostics only:
emitted wasm byte-identical over all 3,002 corpus modules, `compile(candidate, master
source)` reproduces master's fixpoint byte for byte · found by glean, VL's first external
consumer · filed 2026-09-05 against master `df312ed6b`**

Repro:

    function f(m: u8[], off: i32): u8[] { if off < 0 { return [] as u8[] } m.slice(off, off + 2) }
    const b: u8[] = [1, 2, 3, 4]
    print(f(b, 0 - 1).length)
    print(f(b, 1).length)
    // BEFORE: `as` supports numeric conversions only
    // NOW:    `as` supports numeric conversions only; write `[]` — an empty array literal
    //         takes its element type from its destination

#### Mechanism

`as` is numeric-only by design, so the refusal is CORRECT and this is not a capability
gap — the program is ill-typed and the checker owes the diagnosis. What the row asked for
is the diagnosis's second half. An empty array literal takes its element type from its
DESTINATION, so the cast the author reached for is not merely unsupported, it is
unnecessary: deleting `as u8[]` makes the same program run. The message said what `as`
does not do and left the reader looking for a different cast spelling, which is the one
thing that cannot work.

`checkCastNode`'s numeric refusal now appends `emptyArrCastHint`, which answers only when
the operand is an `ArrayLit` with no elements AND the resolved target is a `TyArray` —
both halves, because the advice is false without either. It is a SUFFIX, so a consumer
matching the `` `as` supports numeric conversions only `` prefix keeps matching, and it is
built the way `tyDidYouMean` is (D1590's house style): one function returning the clause
or `""`, not a table.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| `as u8[]`, leaving a bare `return []` | runs, prints `0` then `2` | **yes** |
| the parameter and return annotations (`function f(m: u8[], off)`) | still refuses, same message | no |
| the annotation AND the cast together | runs, prints `0` then `2` | — |

BOTH FACES REFUSE and BOTH FACES RUN once the cast goes, so the destination's element
type reaches the empty literal with or without the annotation. Nothing about the
inference is at issue; only the wording was.

#### Grading list

The two controls above — the annotated and un-annotated `return []` — run today and must
keep running; they are the evidence that the suffix's advice is true. The message is also
unchanged where the operand is NOT an empty array literal, since the suffix would be false
advice there: `"x" as i32`, `xs as u8[]` over a non-empty list VALUE, and `[1, 2] as u8[]`
over a non-empty LITERAL all keep the bare sentence, asserted by equality rather than by
substring — a corpus `@error` directive matches a prefix and therefore cannot see an
absence.
