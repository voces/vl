#### Mechanism

The multi-value step (`multivalue.rs`) passes a record argument as its fields when the
callee uses the parameter field-only. It is the same "record" the step returns as
multi-value: 1 to `MV_RECORD_MAX_FIELDS` (8) fields, each `i32`, `i64`, `f32` or `f64`,
never written. The bound was set for results, where past the return registers each field
is a store and a load through a return area (DECISIONS.md, D3625). A parameter has no such
area. Its fields are ordinary arguments, and a reference field (`more: f64[]`) is a valid
argument too, because the field is immutable and reading it early reads what a later
`struct.get` would. sunpa's game-side `Item` has 17 fields, one of them a list. Its anim-side
`Item` (`animItem(c: Item, …)`) has about 35 numeric fields, and `newState(c, …)` also takes
it whole. Binaryen inlines a small consumer and Heap2Local removes the box then. sunpa's
`emit` and `animItem` are too large for that.

**Ruling asked.** Should a field-only parameter take apart a record of any width, and one
with immutable reference fields, while the result bound stays 8 numeric fields? The
recommendation is yes, up to a parameter bound near wasm's practical argument limits (for
example 64). A call then copies more arguments, but it allocates nothing and does not
collect. `Num` would need to carry a reference type, which is the larger part of the work.

headers (2.8 a frame each), `modelItem` 10,938 of each (1 a frame).
