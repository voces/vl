#### Mechanism

The multi-value step (`multivalue.rs`) passes a record argument as its fields when the
callee uses the parameter field-only. It is the same "record" the step returns as
multi-value: 1 to `MV_RECORD_MAX_FIELDS` (8) fields, each `i32`, `i64`, `f32` or `f64`,
never written. The bound was set for results, where past the return registers each field
is a store and a load through a return area (DECISIONS.md, D3625). A parameter has no such
area. Its fields are ordinary arguments, and a reference field (`more: f64[]`) is a valid
argument too, because the field is immutable and reading it early reads what a later
`struct.get` would. sunpa's game-side `Item` has 17 fields, one of them a list. Its anim-side
`Item` (`animItem(c: Item, …)`) has about 35 numeric fields, and `newState(c, …)` also takes
it whole. Binaryen inlines a small consumer and Heap2Local removes the box then. sunpa's
`emit` and `animItem` are too large for that.

**Ruling asked.** Should a field-only parameter take apart a record of any width, and one
with immutable reference fields, while the result bound stays 8 numeric fields? The
recommendation is yes, up to a parameter bound near wasm's practical argument limits (for
example 64). A call then copies more arguments, but it allocates nothing and does not
collect. `Num` would need to carry a reference type, which is the larger part of the work.
(Decided by the coordinator, 2026-10-06: yes, with the bound measured.)

sunpa `frame-alloc` under `feet-test` (10,938 frames): `shadow` 30,219 `Item` and 30,219 list
headers (2.8 a frame each), `modelItem` 10,938 of each (1 a frame).

#### Close (lane RA)

A record ARGUMENT is now 1 to `MV_ARG_MAX_FIELDS` (64) fields, each a number or a reference
the step can spell; a RESULT keeps `MV_RECORD_MAX_FIELDS` (8) numeric fields. A reference
field is passed on as the reference, so the callee reads the same object (the fixture grows
the list between two reads of it). The never-written rule is unchanged. A twin takes at most
`MV_TWIN_MAX_PARAMS` (128) parameters: a function's record parameters, in order, are taken
apart only while its own parameters plus their fields stay within it, so every twin of it does
(`tests/fixtures/opt-multivalue/twin-param-cap.vl`: seventeen 64-field records, which would
have given one twin 1,088). The step's output is validated, and a rewrite that does not
validate is dropped with the input kept (`$VL_MV_FAULT=1` proves that path).
A slot for a non-null reference field in a scalarized local is declared nullable and each
read re-asserts it, since a set need not dominate a read in wasm's block-scoped sense.

**The bound, measured** (DECISIONS.md, "`-O` takes a record argument apart up to 64 fields"):
an N-field `f64` record built per call at two sites and passed to a callee too large to inline
that reads every field, 6M calls, step off → on:

The gain holds near 1.5x on V8 through 64 fields and falls past it; it never reverses up to

parameters).

**What it did not reach in sunpa.** The game-side `Item` is written (`item.height = …` in
`frame`), so `shadow`'s `Item` stays a box: D3765 asks whether a record built fresh at the
call may be taken apart although its type is written elsewhere. `modelItem`'s `Item` is
pushed into the draw list, so it is a real box. The anim-side `Item` (36 fields, never
written) was the one this reached: `animItem`'s argument, 1 a frame.

**One refinement the first cut needed.** A record whose reference field can hold a struct
nothing writes (a value union's box, `{ tag, payload }`) stays whole for a callee of at most
`ESCAPE_INLINE_MAX_BYTES`: the escape step inlines such a callee and `--heap2local` then
removes both boxes, where taken apart here the payload box is still allocated. Without it,
sunpa's `sound.vl` `add` made 12,800 more boxes, through a `toString` twin of a string
interpolation that was no longer inlined.
