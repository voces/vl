#### Fix

A bare vector map value is a scalar value kind, `MVK_V128`, beside `MVK_F32`: its vals column is the
flat `v128` list (`fl128`/`fa128`), a miss reads as the `v128 | null` box (`mapTyScalarBoxKind`
answers the vector atom), and `mvValLowersTy` admits it, so an un-annotated record field holding
such a map gets its row. `tyNestsV128`'s map arm then stops counting a bare vector value, and
names a vector-list value instead, which still has no rep (the `{[string]: v128[]}` spelling below
is now a check refusal, not an emit one). Graded by `v128-map-value.matrix.vl`: 90 of 90 run.

#### Mechanism (at filing)

Not traced. The check gate (`v128NestMsg`, reached from `check_annot_resolve.vl` and
`check_demands.vl`) refuses a vector held by a map or by a list inside a list, though a list of
vectors, a record field, a `v128 | null` list element and a `v128 | null` map value all lower.
The message names "an array" too, which one list level contradicts. A map whose value is a list
of vectors escapes the gate and reaches the emitter, which has no element rep for that list row.
