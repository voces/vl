#### Mechanism

A write inside a nested block retires the narrowing IN PLACE — which is what stops a falsified
fact resurrecting at that block's `}` — and re-narrows only within the block it sits in. So the
code below the `if` read the DECLARATION, whatever the arms had left the name at. The emitter
agreed (`retireNarrowFor` is in place, `pushNarrowRep` unwinds with the block), which is why the
symptom was a refusal rather than a rep disagreement.

The missing piece is the JOIN, the shape `daJoinArms` already runs for definite assignment.
`checkIfStmtNode` now folds a per-write ledger — the type each write left the name at, the type
it held before, and the scope depth it ran at — into one end type per arm: a write at the arm's
OWN statement depth runs whenever the arm does and replaces what came before, a deeper one is
conditional and joins. The surviving arms' end types join, a diverging arm contributes nothing,
and an absent else contributes the type the `if` was entered with. The result is banked at the
`if` node and the emitter pushes the same member, selecting it out of the DECLARED member set so
box tags stay positional however the join's own arena row is spelled.

**THE ROW'S FIRST WITNESS COULD NOT HAVE SHOWN THIS.** It was
`if x is i64 { if c { x = true }; if x { … } }` — one arm, no else. On the path where `c` is
false `x` is still an `i64`, so the sound join IS `i64 | boolean` and `if x` is refused with the
join exactly as it was without one. Re-graded before building, and re-filed above; the original
is kept as `error-narrow-arm-join-one-armed.vl`, where it pins that the join is sound rather
than generous.

#### Grading list

The seven ablation rows and both fixtures, plus the two refusals the close must not weaken:
`soundness/narrowed-write-in-loop-body-rejected.vl` and
`soundness/index-place-narrowing-barred-across-a-loop.vl` — a nested `while` still meets the
re-execution barrier, with its own sentence, and the narrowing then STANDS for the reads after
the loop rather than joining. That is the rule [D1736](D1736.md) kept deliberately, and the join
must not fold it in.

The join reads BARE NAMES only. A property path's fact is an `npKeys` overlay entry the arm's
scope already popped, so joining one needs the overlay's own fork/join — filed as
[D1849](D1849.md).

**And the ledger has to record EVERY write, not only the retiring ones** — measured, and the
first cut of this close got it wrong. With only retiring writes recorded, both arms writing the
same member still joined to `i64 | boolean`: the FIRST arm's in-place retirement widens the name
to its declaration, so the SECOND arm's flip is a write the (now wide) narrowing admits, retires
nothing and recorded nothing. A regrader of this row should write both arms and check the join
is the member, not the declaration; the "did it retire" answer lives in its own column, because
the post-guard residual must still drop only on a falsifying write.
