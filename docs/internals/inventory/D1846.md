### D1846 — a write in a NESTED block retires the narrowing rather than re-narrowing across it, so the reads after that block are at the declared type

**loud check reject · filed 2026-09-07 against master `678f578e3` · the limit
[D1736](D1736.md)'s close pinned in `tests/cases/unions/narrow-write-flips-variant.vl`'s
`innerBlock` row rather than lifted · clause 2 · 0 corpus cells**

Repro:

    function f(x: i64 | boolean, c: boolean) {
      if x is i64 {
        if c { x = true }
        if x { print(1) } else { print(2) }
      }
    }
    f(3, true)
    // vl check: rc 1, if-condition must be boolean, got i64 | boolean

#### Mechanism

D1736's rule gives a write two effects with two different lifetimes, and only one of them
crosses a block. `retireNarrowingsForWrite` writes the DECLARED type back IN PLACE at
`lookupDepth(nm)` — so the retirement outlives the inner block, which is what stops a
falsified narrowing resurrecting at its `}` — and shadows the written member in the CURRENT
scope, which the inner block's `popScope` unwinds. The emitter is the same shape by
construction: `retireNarrowFor` marks slots in place while `pushNarrowRep` is a stack push
`restoreNarrow` unwinds at the same `}`. Both halves therefore read at the declaration after
the block, and agree — the refusal is a lost capability, not a rep disagreement.

The missing piece is a control-flow JOIN. On the path where `c` is false the value is still an
`i64` and on the path where it is true it is a `boolean`, so the sound answer after the block
is `i64 | boolean` for a read that demands one member and the union for one that does not.
Today both get the union, which is why `print(x)` after the same write RUNS and prints `true`:
`print` takes the box, so only a read that demands the member is refused.

**A `while` nesting is a different rule and must not be folded in.** `if x is i64 { while n > 0
{ x = true … } … }` is refused by the re-execution barrier with its own sentence (`'x' was
narrowed by a guard OUTSIDE this loop …`) and the narrowing then STANDS for the reads after
the loop. That refusal is deliberate and D1736 kept it; this row is the `if` nesting only.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the nesting (`x = true` at the guard's own level) | runs, prints `1` | **yes** |
| the demanding read (`print(x)` instead of `if x`) | runs, prints `true` | **yes** |
| the `if` nesting, made a `while` (`while n > 0 { x = true … }`) | refuses, but as the loop barrier, and the narrowing stands | **yes** |
| the guard's kind (the same nesting inside `while x is i64`) | refuses identically | no |
| the condition (`if true { x = true }`, always taken) | refuses identically | no |
| the sibling arm (`if x > 1 { x = false } else { x = x - 1 }`) | refuses, `operator '-' is not defined for i64 \| boolean and i32` | no |

#### Grading list

The six ablation rows, `tests/cases/unions/narrow-write-flips-variant.vl`'s `INNER-BLOCK` row
(the `print(x)` spelling, which runs and must keep running) and
`tests/cases/soundness/narrowed-write-in-loop-body-rejected.vl` (the barrier, which a close
must not weaken). The recovery a caller has today is a re-test — `if x is boolean { … }` after
the inner block runs and prints `1` — so a close is graded on removing the re-test, not on the
program compiling at all.

A close needs the join, not another in-place write: the checker would have to carry each arm's
end-state for the name and meet them at the block's `}`, and the EMITTER would have to reach
the same answer from the same place, or a read after the block lowers at an arm's rep the
value may not have. That is the same fork/join shape `daJoinArms` already runs for definite
assignment, over types rather than assignedness.
