### D2534 — a nested generic application closed by `>>` before a comma is a parse error: the lexer's shift token is not split inside a type

**closed — the type-argument loop in `compiler/parser.vl` reads its `,` through `atTypeCont`, so while a `>>`/`>>>` still owes a `>` the list is closed and the separator stays with the enclosing list · graded by `tests/cases/generics/nested-application-close-before-separator.vl` (field, parameter, `>>>`, outer application, function type, call type arguments) · refiled as D4532 on 2026-10-13 · was loud check reject, parse error, clause 2 · found by #3168's review · filed 2026-09-25 against master `15be0d1b8`**

Repro:

    type GB<T> = { v: T }
    type H = { t: GB<GB<i32>>, n: i32 }
    const h: H = { t: { v: { v: 3 } }, n: 1 }
    print(h.t.v.v + h.n)

#### Mechanism

`GB<GB<i32>>` inside a record field type lexes its two closing brackets as one `>>` shift token,
and the field-type parser does not split it, so the field list reads `expected '}' but found 'n'`.
Spelled `GB<GB<i32> >` the same program prints `4`. A type position has no shift operator, so the
parser should split `>>` (and `>>>`) into closers there, as TypeScript and Java do.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| a space between the closers (`GB<GB<i32> >`) | runs, prints `4` | **yes** |
| the following field (`type H = { t: GB<GB<i32>> }`) | not graded | — |
