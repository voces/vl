### D16783 — an element of a list a kept maker's build stores at a wider record, read through a loop variable or a callback parameter and handed to an annotated narrower record, builds a module that fails to validate

**check-clean invalid wasm · clause 1 · `type mismatch: expected (ref $2), found …` at the hand-off · `for … of` loops and `filter`/`map` callbacks · found by lane WIDTH grading `annotated-callback-over-built-list.matrix.vl` for D16764 · filed 2026-11-16 against master `29cd46b32`**

Repro:

    type J = { f: i32 | null }
    function mk2() { return { f: null } }
    const dA: J = mk2()
    const src = [mk2()]
    function show(z: { f: null }) { print(z.f) }
    for y in src { show(y) }
    // vl check: rc 0.  vl run: invalid module, type mismatch

Want:

    null

#### Mechanism

`dA`'s delivery keeps `mk2` building at `J`, so `src` stores its elements at `J`. An element read
by index (`show(src[0])`, `show(src[i])`) is a built-container read: `recAnnArgTakesRep` instances
`show` at `J` (D14532) and it runs. A loop variable, or an un-annotated callback parameter that
the elaboration instances at the build (`elabCbAtBuild`), holds the same `J` element, but neither
is recognised as a built-container read. The checker raises no refusal and the emitter hands a `J`
struct to a parameter laid out at `{ f: null }`. An annotated binding does the same
(`const z: { f: null } = y` in the loop).

| the call, the element bound annotated instead (`const z: { f: null } = y`) | invalid module | no |
| the loop, an un-annotated `filter` callback calling `show(y)` instead | invalid module | no |
