### D3918 — a local lambda inside a generic, named like a top-level generic function, is read as that function when delivered

**closed 2026-10-09 by lane SC · runs · was check-clean invalid wasm · found in review of #3484 (`rv3484/m/m08_shadow_bind`; m09 and m10 are the controls) · filed 2026-10-09 against master `09d7de908` · pins: `tests/cases/generics/local-binding-shadowing-module-generic-delivered-as-value.vl`**

Repro:

    function b<U>(y: U) { print(y) }
    function a<T>(x: T) {
      const b = (t: T) => print("local")
      const h: (t: T) => void = b
      h(x)
    }
    a(2.5)
    a("s")
    // vl check: rc 0.  vl run: the emitted module failed to validate inside `__lambda_5`: expected (ref $type), found f64

Want:

    local
    local

#### Mechanism

The checker's function-value adapter (`fvaAdapt`) builds a wrapper lambda for a generic function
named as a value. A delivery whose destination names the enclosing `T` is re-checked later, at
the instance's types, and that deferred re-check runs outside the function's scopes: the name
`b` then resolved to the module generic, not the local `const b`. So an adapter calling the module
`b` was built, rewriting the delivery in place, and the second instance read the first's.
Closed: the declaration a name resolves to is banked the first time it reaches `fvaAdapt`, which
is in its own scope, and the deferred re-check reads the bank (`fvaNameDecl`). A parameter or a
reassigned `let` named like the generic is fixed the same way.
