### D15316 — a `??` default the record solve pins at a built read's record joins as a union, which a list or record literal slot built at that record cannot hold

**closed 2026-11-11, runs and prints `4` · was open · closed by the fresh-call copy (`recFreshCallCopy`, `recHeldFreshCopy`, check_fit_rules.vl): a maker called more than once keeps its own record, and a delivery whose destination stores a field differently copies the call there, so no other delivery reads it at another row · graded by `scripts/capability-probes/matrix/kept-maker-delivery.matrix.vl` · found closing D15313 · filed 2026-11-04 against master `23c9f7db8`**

Repro:

    type J = { f: i32 | null }
    function mk() { { f: 4 } }
    const m = Map()
    m.set("a", mk())
    const wm: {[string]: J} = Map()
    wm.set("a", mk())
    function mkd() { { f: 1 } }
    const dl = mkd()
    const xs = [m.get("a") ?? dl]
    print(xs[0].f ?? 0)

Want:

    4

#### Mechanism

A `const` of a call and a `let` are adopted at the read's record J: the call's function is built
there and its other calls share that build (D15240), and a `let`'s later writes must land there
too. The adopted binding is typed J, so `m.get("a") ?? dl` joins as `{f: i32} | J` (D15314), and the
literal slot the store column builds at J (`storeSlotHeldAt`, D15312) has no conversion from that
union. Without the refusal, emit refused the list element ("a value that fits `J` may be stored as
another arm") and built the record field invalid. A `const` of a literal is built at J while it
keeps its own type, so its join is one record and it runs (D15313).

#### Measured attempt (parked 2026-11-04)

With the refusal lifted, three changes were tried on master `c80b7e33d` plus #6270, each graded
on the grid below; none moves a cell to `runs`:

1. A default already typed at the read's record counts as delivered there, and
   `storeLetsResolve` admits a `??` typed as a union, so the store column records the join as
   held at J. Necessary, not sufficient: nothing moves.
2. One reader of that record (`coalHeldRecordTy`) consulted by `exprUnionBin`,
   `structIndexOfExpr`, `letStoreHeldTy` and a `br_on_non_null` rung at the top of
   `emitCoalesceGo`. Still invalid wasm: the join is lowered as
   `if (ref.is_null …) struct.new <box> …` by four sites that box a `??` from its union node type
   and ask none of those classifiers: a module global's initialiser, a local's initialiser, the
   union coerce of a join delivered into a list element, and a record field initialiser. The
   bound-first spelling moved from the cross-tag refusal to invalid wasm.
3. The literal slot keeping the join's union row instead of J: no change, since the list's element
   type is J independently.

**Hypothesis for whoever resumes it:** when the store column holds the join at J, the checker
could type the `??` node itself as J, the fact owned at its producer; every lowering then follows
the node type and none needs a held-fact reader. Answer first whether that typing is sound for the
pinned defaults, i.e. whether every value of the join is stored at J (the map's values are built
wider; a `const` of a call is adopted there with its function; a `let`'s writes land there).
