### D4963 — a list narrowed by `is K[]` under a type parameter is delivered as `K[]`

**closed 2026-10-15 · now a loud check reject · was check-clean silently wrong, clause 1 · pin: `tests/cases/soundness/list-element-narrowing-type-param-delivery-reject.vl` · the type-parameter face of [D4928](D4928.md), which refuses the same delivery from a list declared at a concrete type · filed 2026-10-15 against branch `d4934-empty-arm-push` over master `e2efbc0af`**

Repro:

    function pushOne(xs: f64[]) { xs.push(1.5) }
    function g<V>(v: V[]) {
      if v is f64[] { pushOne(v) }
      print(v.length)
    }
    const e: i32[] = []
    g(e)
    // vl check: 'v' is narrowed by `is` only for reading its elements; it is still
    // declared V[] and a later write may widen it, so it cannot be delivered as f64[]. Copy it
    // with 'v.map((x) => x)' (was: PRINTS 0)

#### Mechanism

D4928's check refuses delivering a list narrowed by `is K[]` at `K[]`, since the narrowing
covers element reads only (owner ruling #3792). A receiver declared at `V[]` is not refused,
so the `g(e)` instance hands `pushOne` the arm's fresh empty `f64[]` and the push is lost,
while an `f64[]` argument has the push land in the caller's list and prints `1`. The right
answer is the refusal D4928 gives, which is why this row has no `Want:` block.

#### Close

`narListDeliveryErr` (typecheck.vl) now asks that the narrowed list's declared type fit the
destination at every instantiation: a declared type holding a type parameter fits a concrete
destination only at some instances, so the delivery is refused as D4928 refuses a concrete
declared type, in every position and inside a closure in the arm. A `V[]` destination is still
accepted. The bare-`V` and un-annotated face is [D4981](D4981.md).
