### D16887 — `__array_new__`'s fill keeps its own type where a literal of the same value takes the destination's element type

**closed 2026-11-16 · runs, prints `2` · was loud check reject, `null[] is not (string | null)[]`, clause 2 · fixed in check_calls.vl and wasmEmit.vl: a scalar, string or `null` fill assignable to the union or nullable element of the list the call is delivered to (`callDstTyOf`) is built at that element, and the emitter boxes it there (`emitArrNewFillAt`); the redundant-annotation hint knows the annotation supplies it (check_redundant_annot.vl) · an integer fill at a float element stays refused (D3539's ruling B′) · pin: `tests/cases/intrinsics/array-new-fill-at-union-element.vl` · found closing [D3549](D3549.md) · filed 2026-11-16 against master `bc6546163`**

Repro:

    const xs: (string | null)[] = __array_new__(2, null)
    print(xs.length)
    // was: vl check rc 1, null[] is not (string | null)[]

Want:

    2

#### Mechanism

`__array_new__`'s checker rule typed the list as the fill's own type (`null[]`, `i32[]`), and the
container rule then refused the widening, where the literal `[null, null]` is built at the
destination's element type. A generic wrapper (`filled<T>`) binds `T` from the destination
(D3539) and so never reached the gap.
