#### Mechanism

The refusal site reads `monoArgPinName`'s answer and asks `nameIsArray` of it. Printed at the
site, the un-annotated face hands it `i32[][]|null[]` while `tyToEmitName` of the very same
node reads `(i32[][]|null)[]` — so the arena renderer was right all along and the mono
argument reader built a different name.

It builds one at exactly one place, by CONCATENATION: `arrLitElemName(ix) + "[]"`, the
array-literal channel. `arrElemRender` is "the one home of the array-element grouping rule,
shared by all three renderers", and this site is not one of the three. A nullable element has
two top-level atoms, so a bare `[]` binds into its last arm and spells a type the program never
wrote. The close gives that site the rule (`arrLitElemSuffixed`, grouping on
`splitUnionAtoms` > 1), which is the same string the arena render produces.

**It is not the poisoned hole pin.** `pinnedHoleTyOf` / `holePinTys` have zero readers in
`emit_mono.vl`; their three readers are in `emit_classify.vl`, none on this path. The campaign
re-keying that table and this close do not touch the same code.

**And the `redundant` hint was right — the monomorphizer was wrong.** D1835's fixture declared
three hints and said its annotations were rep-load-bearing despite them. With the grouping
rule in place, dropping the annotations behaves identically, so the checker's reading of the
TYPE and the emitter's reading of the REP now agree and the hint needs no exemption. The
fixture's note is corrected rather than the hint retired.
