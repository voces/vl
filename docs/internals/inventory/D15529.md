### D15529 — [CLOSED 2026-11-08] a list of a hole parameter, pushed and handed on whole, its element called at two types, refuses its `.length`

**closed · runs, prints `2` then `5` · was loud emit reject (`emitProgram: '.length' on a receiver the emitter cannot classify as a list, string, map or set`) · filed 2026-11-06 against master `3866dd5f` · closed by tagging the parameter's one-member set when the list it fills is pushed with its reads and handed whole**

Repro:

    function id<T>(x: T): T { x }
    function use(ys) { print(ys.length) }
    function take(a) {
      const xs = [a]
      xs.push(a)
      use(xs)
      print(xs[0]("abc").length + xs[0](2))
    }
    take(id)

Want:

    2
    5

#### Mechanism

[D15010](D15010.md)'s witness with a push. Without the push the `monoFlow*` chain gate renames each
call through `xs[0]` to `id` and the program runs; with it, `xs[0]` is a literal index into a list
written after its build, so the gate declines (the element at an index can move), the list is built
as closures of one signature, and the `.length` refusal D15010 had stands. The right answer is `2`
then `5`.

Want:

    2
    5

#### Fix

`elabListParamSource` takes a list as its parameter's holder when every other read of it is a push
of that parameter's reads or a positional hand to a named function's un-annotated parameter. The
push is then no closure store (`ftParamStored`), no call through an element
(`ftChainCallsComplete`) and no partial delivery (`elabPushOntoParamList`), so `{id}` is tagged:
the list holds its id, `use` takes it at that list's type, and each call through `xs[i]` is a direct
call of `id` at its own arguments. The slot-write spelling `xs[0] = a` still refuses: [D15567](D15567.md).
