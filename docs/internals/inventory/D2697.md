### D2697 — a later same-named list binding delivered to a `Circle[]` annotation reads the earlier sibling's union-box storage

**check-clean invalid wasm · `type mismatch` inside `f`, the same on master `1be1363d9` and after D2685 · filed 2026-09-26 from the #3196 review's generated program 230**

Repro:

    type Circle = { r: i32 }
    type Sq = { s: i32 }
    type Shape = Circle | Sq
    function f(n: i32) {
      if n == 0 {
        const out = [{ r: 1 }, { s: 7 }]
        print(out.length)
      }
      if n == 2 {
        const out = [{ r: 5 }, { r: 3 }]
        const c: Circle[] = out
        print(c[0].r)
      }
    }
    f(0)
    f(2)
    // vl check: rc 0.  vl run: invalid module, type mismatch inside `f`; should print 2 then 5

#### Mechanism

Not yet located; the ablation says what it needs. Two same-named sibling bindings in one
function, the first a mixed literal (union-box element storage), the second an all-`Circle`
literal delivered to a `Circle[]` annotation. Renaming the second binding runs, so the
second binding's delivery resolves `out` to the FIRST binding somewhere — a prediction to
check: a reader keyed by name through `parentLetOf` (which answers the first binding) rather
than `parentLetOfAt`. It is not the destination scan of [D2685](D2685.md)/[D2696](D2696.md):
neither binding has a union-box destination, and the program fails identically before and
after them.
