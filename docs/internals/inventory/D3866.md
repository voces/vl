### D3866 — the value of a function-scope assignment `d = both`, where `both` takes a WIDER parameter than `d`'s function type, keeps `both`'s own signature, and calling it traps

**closed (2026-10-08, lane SC) · now a loud check reject, `argument 1: expected A, got {k: string, w: string}` · was loads then traps · check-clean, `indirect call type mismatch` at the call · found by the rv3458 review of #3457/#3458 (pa/c5.vl) · filed 2026-10-08 against master `fd225840b` · pins: `tests/cases/functions/assignment-of-wider-function-value.vl`, `tests/cases/functions/error-assignment-of-wider-function-value-called-wide.vl`**

Repro:

    type A = { k: "a", v: i32 }
    type B = { k: "b", w: string }
    const both = (p: A | B): i32 => { if p.k == "a" { p.v } else { 7 } }
    let d: (p: A) => i32 = (p: A): i32 => 0
    const g = () => { d = both }
    const r = g()
    print(r({ k: "b", w: "z" }))
    // vl check: rc 0 (one unused-parameter warning).  vl run: rc 1, `wasm trap: indirect call type mismatch`

Want:

    vl check: argument 1: expected A, got {k: string, w: string}

#### Mechanism

The checker accepts `d = both` because a function of a wider parameter is assignable to a
narrower function type, and its delivery rewrite (`fvaAdapt`) replaces the right side with an
adapter lambda at `d`'s signature, `(p: A) => both(p)`. The assignment expression still yielded
the right side's type, `(A | B) => i32`, while the value it now held was the adapter: `r` was
called at the wide signature and reached a function of the narrow one. Where the delivery
rewrote the right side, the expression's type is now the place's, which the value is. Of the
two sides the grading list names, this takes the refusing one: `r` is `(p: A) => i32`, as a
typed `r` or a lambda literal on the right already are, so `r` with a `B` is refused at the
call and `r` with an `A` runs. Converting back to the wide signature at the value would need
the original `both` beside the adapter, which the rewrite does not keep.

#### Grading list

The `i32 | string` spelling is refused at the checker while the record-union one is accepted:
the two disagree about whether a wider parameter may be assigned into a narrower function
type, which is a design question the close has to settle before it picks a side (accept and
convert at the assignment's value, or refuse as the literal and the typed `r` already do).
The reviewer also reported a trap with a plain module-level `let` and no capture cell; that
did not reproduce on `fd225840b` in the shape `d = both; print(d(...))` (runs, `3`), so it is
not claimed here. Programs that run today and must keep running: `{ d = both; d }`,
`g()` as a statement then `d(...)`, `const r = d`, and passing `both` as an argument to a
function whose parameter is `(p: A) => i32`.
