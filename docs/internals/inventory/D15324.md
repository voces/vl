### D15324 — a literal holding a holder's record, read once through a copy and once through its place at the other signature, refuses at emit

**closed 2026-11-04 by this PR (lane bundle) — the repro now RUNS and prints the Want below: a call through a `const` copy of a field is a use of that field at the call's instance, so the adoption no longer pins the field at one signature. Was: loud emit reject · clause 2 (`emitProgram: a function returning a parameter called at two signatures is called where its result is not used at one of them`) · found closing [D15323](D15323.md) · filed 2026-11-04 against master `55102709c`**

Repro:

    function lap(f) {
      const _a = f(2.5)
      const _b = f(3)
      return f
    }
    const u = lap((a) => a + 1)
    const w = { f: u }
    const v = w.f
    print(v(4))
    print(w.f(1.5))

Want:

    5
    2.5

#### Mechanism

Measured with a probe build on the field spelling. When the slot fact is noted, `w` carries an
annotation `{f:(f64)=>f64}`, one closure type rather than the record, and the slot fact declines an
annotated binding, so neither `w`'s slot nor the holder `u` gets a fact. The producer is the
checker's record adoption: `recAdPinLet` (check_rec_rows.vl) replaces `w`'s node with one annotated
at the adopted type. A probe that logged every writer of a binding's annotation (each
`.letType =` in emit_collect, emit_mono and emit_rewrite, `mkLet`, and the two node rebuilds in
check_num_lit_state and check_rec_rows) logged that one writer for `w` and no other.

The adoption's demand comes from `holeFieldCallAdopt` (check_calls.vl, D13969): a call through
`recv.field` at a closed instance builds `recv`'s records with the field at that instance. Two
calls through the place give two demands at two instances, which disagree, so nothing is adopted.
A call through a copy `const v = w.f` gave no demand, so `w.f(1.5)` alone pinned `w` at
`{f:(f64)=>f64}`. The adoption was wrong because one of the field's two uses was invisible to it.
A call through an un-annotated `const` copy of a field (`holeFieldCopyOf`) now registers the same
demand, and the field spellings run. The list rows are a different mechanism: no annotation is
written, and no slot candidate is noted for the read in `[u]`. They are [D15325](D15325.md).

This fix lands with [D15326](D15326.md), and neither is safe alone. D15326 alone makes the
store honour the one-signature pin, so an i32 call through the copy runs through the f64 member:
`lap((a) => a / 2)` with `v(3)` printed `1.5`, check-clean and wrong. This fix alone sends the
copy-only spelling into D15326's gap, a runs → not-runs. Together the divergence prints `1`, and
the pin carries that program.

#### Ablation

| spelling | outcome |
| --- | --- |
| `{ f: lap((a) => a + 1) }` stored directly | runs |
| the copy called at both signatures, `v(4)` and `v(1.5)` | runs |
| both calls through the place, `w.f(4)` and `w.f(1.5)` | runs |
| a list, `const xs = [u]; const v = xs[0]`, then `v(4)` and `xs[0](1.5)` | the same refusal |
| the list with both calls in one interpolation, `"\{v(4)} \{xs[0](1.5)}"` | runs |
| the field with both calls in one interpolation, `"\{v(4)} \{w.f(1.5)}"` | the same refusal |
