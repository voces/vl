### D12231 — a list element holding a hole function, handed to a hole parameter that calls it at two types, is refused at emit

**loud emit reject · `vl check` rc 0 · `emitProgram: cannot take the generic function `add` as a value — a function value carries ONE signature` · clause 2 · CAPABILITY: `apply2(add)` runs, and so does `const h = fs[0]; apply2(h)` · emit_mono.vl `monoHoleTwoPinsFail` (its `monoArgTyFail` fallback serves the call-result spelling) · found surveying emit refusals for L3 family (d) · filed 2026-10-24 against master `84b98d149`**

Repro:

    function add(a, b) { return a + b }
    function apply2(g) {
      print(g(1, 2))
      print(g(1.5, 2.5))
    }
    const fs = [add]
    apply2(fs[0])

#### Mechanism

The split plan gives `apply2` one copy per type its parameter is called at, but only when the
argument names the function (an identifier, or an alias the flow table follows). An element
read `fs[0]` is neither, so `monoHoleGenFnPin` finds no pin while `monoHoleGenTwoPins` is set,
and `monoHoleTwoPinsFail` refuses with the generic-value sentence. A call result handed the
same way (`function pickIt() { add }; apply2(pickIt())`, with `add` a `<T>` generic) refuses
with `monoArgTyFail`'s `unsupported argument type for `f``; which of its callers fires there is
not yet measured. A `<T>` generic in the list
(`function add<T>(a: T, b: T): T`) refuses earlier with `a function-value call has no interned
signature`.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the list (`apply2(add)`) | runs, prints `3 4` | **yes** |
| the second type (`g(1.5, 2.5)`) | runs, prints `3` | **yes** |
| the element read inline (`const h = fs[0]; apply2(h)`) | runs, prints `3 4` | **yes** |
| the hole parameter (`fs[0](1, 2)` and `fs[0](1.5, 2.5)` directly) | runs, prints `3 4` | **yes** |

#### Grading list

The call-result spelling `apply2(pickIt())`; a record field `apply2(r.f)`; the `<T>` generic in
the list at `i32` and `string`.
