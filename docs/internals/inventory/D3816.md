### D3816 — a `string | null` narrowed inside a `??`'s left operand reached a call argument with the arm's raw-read seeds still set, so a `string` parameter got the nullable ref

**closed 2026-10-08 by lane SC · was check-clean invalid wasm · filed 2026-10-07 against master `dfe8e92b3` (found by lane OV) · pins: `tests/cases/expressions/coalesce-arm-narrowed-string-argument.vl`**

Repro:

    function describe(self: string): string { "string " + self }
    function f(n: string | null): string { n?.describe() ?? "none" }
    print(f("nn"))
    print(f(null))
    // vl check: rc 0.  vl run: invalid module, `expected (ref $type), found (ref null $type)` inside `f`

Want:

    string nn
    none

#### Mechanism

Not the optional call: the written-out guard `(if n == null { null } else { describe(n) }) ?? d`
fails the same way. A `string | null` `??` emits its left operand with the raw-read seeds set
(`coalesceNulStrArmCtx`), so the arm's own nullable strings stay `(ref null)`. Those seeds are
ambient and reached the call arguments inside the arm: the direct call reassigned
`nulString` from its parameter but left `rawNullRead` set, and the value and captured calls
reassigned neither, so the narrowed `n` was handed to a `string` parameter unrecovered. Each
argument now takes both seeds from its parameter alone (`wasmEmit.vl`). A record or list
receiver never hit this: their recovery is at the argument, not at the read.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the `??` (bind `const r = n?.describe()`, then `r ?? "none"`) | runs | **yes** |
| the optional call (`(if n == null { null } else { describe(n) }) ?? "none"`) | still invalid | no |
| the `string` receiver (`A \| null`, `i32[] \| null`) | runs | **yes** |
| the module boundary (one file) | still invalid | no |
| the function wrapper (module scope `print(n?.describe() ?? "none")`) | still invalid | no |
