### D2112 — a `for` over a `(F | null)[]` list of function values binds a non-null closure, so a null element traps

**closed 2026-09-22 — the witness prints `none` then `101` · was loads then traps (`wasm trap: null reference` on the first null element), clause 1 · filed 2026-09-22 against master `7b16d43ab`, found beside D2110 · fixture `tests/cases/closures/function-list-call-statement.vl`**

Repro:

    function a(x: i32) { return x + 100 }
    const table: (((i32) => i32) | null)[] = [null, a]
    for f in table {
      if f != null { print(f(1)) } else { print("none") }
    }

#### Mechanism

`forInElemKind` answered `closure` for every closure-element ref-list slot, nullable or not,
and the for-in emitter recovers a `closure` element with `ref.as_non_null`. Every other niche
element (`nulstruct`, `nullist`, `nulreflist`, …) asks `rlElemIsNulNiche` first and binds its
nullable kind; the closure arm alone did not. It now answers `nulclosure`, which
`declareForInLocals` and the emitter treat as the ref-list walk without the recovery, so the
body's `f != null` test sees the null. With a void element the same loop was also D2110's
invalid wasm, which is why the void spelling read as silent rather than a trap.
