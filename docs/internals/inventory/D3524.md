### D3524 — `==` inside a generic body pinned at `i64 | f64` passes the check and has no operator at the emitter, where the direct spelling is refused at check

**loud emit reject · clause 2 · open · found by the #3343 review's `g7` grid (`j7_k*_std`) · the same on master `f6e17953b` · filed 2026-10-03 against master `f6e17953b` by lane LC**

Repro:

    import { includes } from "std:array"
    function mx(k: i32): i64 | null { if k == 0 { return null }
      9000000000 }
    const x = mx(0)
    const xs = [x ?? 2.5]
    print(includes(xs, x ?? 2.5))
    // vl check: rc 0.  vl run: "emitProgram: a numeric union member pair has no operator type"

#### Mechanism

`x ?? 2.5` over `i64 | null` joins `i64 | f64`. The direct `a == b` over that union is refused
at check by `numUnionBinTy` (`mixes the members i64 and f64; narrow with is or convert with
as`), because the `i64`/`f64` pair has no exact common type (`numPairOpTy` answers -1). A
generic body (`includes`, or any `eq<T>(a: T, b: T) { a == b }`) defers the operator to its
pin, and the pin mirror `binOpDefinedFor` → `numUnionPinOk` only asks that each member is
numeric, so it admits the pair; the emitter's dispatch then finds no operator type. Not the
operator table D3512 changed (that was the softening of literal operands). The pin mirror
cannot simply call `numPairOpTy`: that rule needs the operand NODES for a literal's adoption
(`f32 + 1`), and a pin has only types, so a direct port would refuse `T = f32 | i32` with a
literal operand that runs today. Recommendation: refuse at the pin with the direct spelling's
message for a pair of two concrete members neither of which widens to the other (`i64`/`f64`,
`i64`/`f32`), leaving literal-adoption pairs to the instance check — a refusal the design
already owes at the direct spelling, so the close is hygiene, not a new rule.

The same pin mirror holds a second, related gap. An operator over a two-width literal union in
a generic body (`function op<T>(x: T) { -x }`, `x * 2`, `x + 1`, `x < 2` at `T = 1 |
9000000000`) stays refused at the pin, as on master, because `binOpDefinedFor` keeps
`softenLitTy` rather than the operand softening D3512 gives the direct spelling. Softening there
was tried in lane LC's first draft: `-x` became invalid wasm (the instance's `T` operand is not
read as the literal box at the node), and `x * 2` under `: T` passed the pin while returning an
`i64` as `T`, hidden only by an emit refusal. The close owes both: the pin admits the operator
only where its `i64` result fits the destination (an un-annotated return may take it; an
annotated `: T` return or a `T`-typed store may not), and the instance resolves the operand's
box as `njMembersOf` does. Witness of that half:

    type U = 1 | 9000000000
    function op<T>(x: T) { -x }
    const u: U = 9000000000
    print(op(u))
    // check: "unary '-' expects a numeric type, got U (the body of `op` negates this argument)"
    // want: -9000000000

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `function eq<T>(a: T, b: T): boolean { a == b }` over `mx(): i64 \| f64` | same emit refusal | no (std is scenery) |
| `a == b` written directly over `i64 \| f64` | check refuses, `mixes the members i64 and f64` | **yes** (the generic pin) |
| `mx` returning `i32 \| null` | runs, `true` | **yes** (an `i64` member beside `f64`) |
| `xs.indexOf(...)` without the import | check refuses, names the import | no |
