### D4064 — an `import` of a name the module also re-exports from the same module gets no duplicate-import warning

**open · missing warning (no outcome word fits: `vl check` rc 0 and the program runs, so it grades as runs today and must keep running) · found writing `docs/spec/modules.md` (lane SPEC) · filed 2026-10-11 against master `98a4ed71b`**

Repro:

    // file: m2.vl
    export function f(): i32 { 3 }
    // file: m1.vl
    import { f } from "./m2"
    export { f } from "./m2"
    export function h(): i32 { f() }
    // file: main.vl
    import { h } from "./m1"
    print(h())
    // vl check: rc 0, no warning.  vl run: rc 0, prints 3

Want:

    3

#### Mechanism

Owner ruling R2 (A), 2026-10-04: under R1 a re-export already binds its name locally, so an
`import` of the same name from the same specifier is redundant and gets the
duplicate-import warning with a `--fix` that removes the import. The `duplicate-import`
lint compares `import` statements with each other only, and never sees the re-export.
`docs/internals/modules-design.md` §2.1.1 records std's eight instances (`std:args` 1,
`std:env` 4, `std:process` 3), which the ruling cleans up in the same change.

#### Ablation

| variant | outcome |
| --- | --- |
| `import { f }` beside `export { f } from` the same specifier | no warning (wrong) |
| two `import { f } from "./m2"` | warns, "Duplicate import `f`" (right) |
| `export { f } from "./m2"` alone, `f()` used locally | runs, no warning (right) |

#### Grading list

The repro should keep printing `3` and carry one duplicate-import warning on the `import`,
whose fix deletes it. std's eight instances go in the same change.
