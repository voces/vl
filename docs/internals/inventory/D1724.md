### D1724 — an ATOM-repped literal-union value is refused as a MAP KEY, while the identical value typed `string` is accepted

**loud emit reject · filed 2026-09-06 against master `194d1f8d2` · found by the spelling x use

clause 2: `vl check` returns 0 and every member of the union is a string · 0 corpus cells ·

Repro:

    type K = "red" | "green"
    function take(a: K) {
      const m = Map()
      m["green"] = 1
      print(m[a] ?? 0)
    }
    take("green")
    // vl check: rc 0.  vl run: emit error,
    // emitProgram: map key is not a string

Annotate the same parameter `a: string` and the identical program prints `1`.

#### Mechanism

Predicted, not probed. A literal union's members are strings and the ALIAS spelling's rep is the
interned i32 atom; the map-key gate asks for the string rep and the atom is not one. Every other
consumer either widens the atom to its member text or compares atoms directly — the key gate is
the one that does neither, so it refuses rather than widening. The fix is the widening the
`print` path already performs (`litAtomWidenTexts`), applied at the key boundary; probe the
gate against this failing witness before writing it.

**The row is about the REP, not the spelling.** Every ablation that keeps the value an atom
still refuses; the two that soften it to `string` — the declared `string` and the INLINE member
set — both run. That also makes the row's separation from [D1545](D1545.md)/[D1717](D1717.md)
sharper than "a different family": those two closed by giving the inline hole parameter the
`string` soften it always had, so `inline/hole/mapidx` moved emit-reject → runs with them, and
what is left refusing is exactly the atom.
