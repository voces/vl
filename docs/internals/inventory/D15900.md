#### Mechanism

The tag plan refuses the set in `ftHoldCtxOk` (check_fn_tag.vl): the call's result holds the set's
ids and is delivered to `v`'s closed closure type. The record solve stores both alike before
tagging, so no rule builds `deliver`'s returned literal at `v`'s type, and a converting copy is no
answer: a call result need not be fresh (coordinator ruling, 2026-11-27). The literal positions run
since `ftLitStampedAt` reads the record solve's stamp on a list literal built at closures; a
binding written into another (`b = a`) runs since `recLitPlaceBuiltTy` builds a list literal where
its binding's one read is delivered. The call result needs the same edge through a function's
return: its returned literal built where its one call is delivered.

Closed by the missing third step: `monoRetFnListTy` re-stamped the returned literal at the joined
tagged result (D15226), so the literal's build and the result rep fell back to the id list. Parked
2026-11-27 (COV-CLOS-2) after one attempt. Building the returned literal at the call's
annotated type (`recLitPlaceBuiltTy` through the function's one returned value and one call) and
reading such a call as holding what that literal holds (`ftHolderCoerced`) gets past the tag plan.
But the function's result rep stays the set's id list. With the global `xs` the emit then refuses
`global initializer coercion`, and with `xs` local, a program that runs today
(`function main() { const xs = [{ f: id }]; … const v: … = deliver() … }`) refuses `convert record
-> record`, a runs -> not-runs. The function's result has to move to the closure rep with its
literal: the D14385 build-the-result-at-the-destination question, not a converter.
