### D9005 — an `if` expression choosing between two functions, handed to a generic higher-order parameter, is not instanced at the callee's pin

**closed · runs, prints `3` · was loud emit reject, `emitProgram: monomorphize: unsupported argument type` for `g` · `vl check` rc 0 · clause 2 · found closing [D9001](D9001.md) · filed 2026-10-21 against master `f0249c64f` · closed by the monomorphizer treating an `if` whose arms name generic or un-annotated functions as an argument that rides the callee's type parameters (`monoArgIsOpenFnChoice`, emit_mono.vl) · fixtures `closures/fn-choice-as-callback.vl`, `closures/fn-choice-unannotated-as-callback.vl`, matrix `fn-choice-as-list-callback-result` · the same choice bound to a `const` first is [D9080](D9080.md)**

Repro:

    function idg<T>(t: T): T { return t }
    function kg<T>(t: T): T { return t + t }
    function app<T>(g: (x: T) => T, v: T): T { return g(v) }
    const c = [1].length > 0
    print(app(if c { idg } else { kg }, 3))
    // vl run: emitProgram: monomorphize: unsupported argument type for `g` in a call to `app`

#### Mechanism

The monomorphizer binds a generic's arrow parameter from an argument naming a generic or
un-annotated declaration, or an open binding of one (`monoPinTyParamComposite`); an `if`
expression was none of these, so the parameter stayed open and the call refused. It now
counts an `if` whose arms each name a function, at least one of them open, as such an
argument (`monoArgIsOpenFnChoice`), pre-binds the type parameters from the value arguments
(`monoCallGenFnToTyParamArrow`), and the existing `IfStmt` recursion in
`monoCoerceFnValueName` / `monoValueRetAt` takes each arm's instance at that pin.
