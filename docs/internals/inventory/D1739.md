### D1739 — concatenating two literal unions is refused as `not defined for string and string`, because the string-concat gate needs ONE operand to be the `string` prim and neither is

**closed 2026-09-06 — the `+` gate's operand test softens at both homes, and the pin's IMPLICIT return records the constraint its explicit twin already did · filed against master `15baeb884`, closed against `04ee488e0` · 11 cells · the residue [D1732](D1732.md)'s close leaves · 0 corpus cells**

Repro:

    type K = "red" | "green"
    const src: K[] = ["green", "red"]
    function take(a: K, b: K) { print(a + b) }
    take(src[0], src[1])
    // vl check: rc 1,
    // operator '+' is not defined for string and string

Make either operand a real `string` and it runs: `b: string` prints `greenred`, and so does
assigning `b` to a `string` local first.

#### Mechanism

`checkBinary`'s `+` arm gates string concat on `isStringTy(lt) || isStringTy(rt)` — at least
one operand being the `string` PRIM — and only then tests mutual assignability. Two literal
unions are `TyUnion`s of `TyLit`s, so neither satisfies the gate; the arm is skipped entirely,
the arithmetic tail softens both to `string`, and the numeric test fails. The message renders
the SOFTENED pair, which is why it reads as a contradiction: the softening that makes the
message say `string and string` happens one line after the gate that could have used it.

**The numeric twin is the control.** `type N = 1 | 2` with `a + b` prints `3`, because the
arithmetic tail *does* consult `softenLitTy`. Only the string gate reads the unsoftened pair.

#### The close, and the price the first table could not see

Softening the gate's operand test at both homes — one shared `concatsAsStr(ty)` =
`isStringTy(softenLitTy(ty))`, read by `checkBinary`'s `+` arm and by `binOpDefinedFor`'s
mirror — moves **eleven cells to `runs` and loses none** over a 23-cell table:

| moves | five annotated spellings (`K + K`, module scope, two inline sets, two bare literal types, two different aliases), three PIN spellings (two holes, one hole, an inline set through a hole), and three result cells |
| --- | --- |
| holds | both numeric-litunion controls still print `3`; every mixed pair (`K + N`, `K + i32`, `K + boolean`, `N + string`) still refuses, matching the plain `string + i32` precedent, which refuses too |
| proves the result type | `const s: string = a + b` runs, `(a + b).length` prints `8`, and `const s: K = a + b` refuses `cannot assign string to 's' of type K` — the concatenation is a `string`, never the union |

Rendering the refusal's operands BEFORE the arithmetic tail softens them also makes the
remaining messages name what the user wrote: `K and N` rather than `string and i32`. One
fixture asserts the old wording.

**And then it introduces a clause-1 miscompile.** `tests/cases/generics/error-litunion-concat-pin-order.vl`
is the control that caught it, and it is the only thing in the tree that did:

    type K = "a" | "b"
    function addT<T>(a: T, b: T): T { a + b }
    function g(a: K, b: K): string { addT(a, b) }
    // at the close: vl check rc 0, and the module fails to validate inside `addT`
    // — type mismatch: expected i32, found (ref $type)

At `T = K` the body now concatenates to `string` while the declared return is `T` = `K`, which
reps as the interned atom. **The DIRECT spelling refuses this** — `function f(a: K, b: K): K`
reports `return type mismatch: expected K, got string` — so the pin loses a refusal the direct
spelling makes, which is [D1732](D1732.md)'s divergence one level out: at the RETURN rather
than at the operator.

#### The third mechanism, and it is not the one this row predicted

`mkBinOpRetTy`'s deferral and `substHoleTy`'s `HD_BINOP` concat answer were both built, and the
row said the remaining work was that "the return constraint does not reach that answer". It is
not that it fails to reach it — **no return constraint is recorded at all**. Instrumented at
the pin's constraint loop, with a fixture that is known to record one as the control:

    error-declared-return-hole-vs-body-at-pin.vl   RETCSTR fires 4x     (the control)
    addT<T>(a: T, b: T): T { a + b }               RETCSTR fires 0x     (this row's witness)

Written with an EXPLICIT return the same generic records and resolves it correctly:

    RETCSTR got=56[_] -> 5[string]  want=53[T] -> 43[K]  gHole=0 wHole=0

and refuses `return type mismatch: expected K, got string`. So the deferral and the `HD_BINOP`
arm were right; what was missing is one rung above them. `checkRetStmtNode` records the pair on
the passing side — its own comment says why, "the check above is vacuous whenever a side is a
hole" — and the IMPLICIT return, the bare tail expression `checkFuncDeclNode` checks with the
same `assignableExpr`, had no such `else`. A generic whose body is a tail expression therefore
carried no return constraint into any pin. It records one now, arm for arm with its twin.
