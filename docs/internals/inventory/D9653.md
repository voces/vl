#### Mechanism

A hole parameter called at two types is split into one parameter per call type (D5611).
`fsHoleKeys` (fn_split.vl) collects the keys from each read of the parameter, and it accepts a
read only when that read is a call, a forward to another hole, or a copy into a binding read
at one key. The read `a` in `[a]` is a list element, which is none of these, so `hsBad` is
set, no split is planned, and `monoPinHoleParam` (emit_mono.vl) refuses. Running it needs a
new kind of plan. Its keys would come from the `xs[k](...)` calls of an un-annotated `const`
list whose every read is a literal-index call. `fsApply` would then rewrite the list literal
once per lane, or each `xs[k]` callee to that lane's parameter name. The plan today only
renames an `Ident`. (traced 2026-10-22, lane-D9652)
