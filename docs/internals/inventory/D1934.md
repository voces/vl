### D1934 — with a `"+"` operator overload declared anywhere, a string `+` on a name shadowed across scopes by a ref-typed binding is check-clean invalid wasm

**closed 2026-09-08 — the witness prints `hi!` · was check-clean invalid wasm, clause 1 · found by the day-one sampler's operator × modules_split cross, in the SINGLE-file face (the split/cross-module face always ran) · fixture `tests/cases/operators/operator-decl-no-hijack-shadowed-string-concat.vl`**

Repro:

    type Vec = new { x: i32 }
    function "+"(self: Vec, o: Vec): Vec {
      const r: Vec = { x: self.x + o.x }
      return r
    }
    const n: Vec = { x: 3 }
    if true {
      const n = "hi"
      print(n + "!")
    }
    // vl check: rc 0.  vl run: the emitted module failed to validate — Invalid input
    // WebAssembly code: type mismatch: expected (ref $type), found (ref $type)
    // (the compiler itself prints "this is a bug in vl, not in your program")

#### Mechanism

Declaring any `"+"` operator overload routes every `+` through the operator-dispatch lowering
(`dispatchRewrite`). Its gate was `structIndexOfExpr(n.binLeft) >= 0 || nodeTyIsObj(n.binLeft)`
— and `structIndexOfExpr` resolves an identifier by NAME (`declaredStructIndex`), so the
block's `string` `n` colliding with the module `const n: Vec` returned the Vec's struct row.
`osi >= 0` was true for a string operand, the string `+` rewrote to `"+"(n, "!")`, and the Vec
operator applied to two strings emitted a `(ref $type)` where another `(ref $type)` was
expected. `vl check` returned 0; the module failed wasm validation at the concat.

Closed by gating the free-operator dispatch on the operand's own OBJECT type
(`nodeTyIsObj(n.binLeft)`) rather than on the name-resolved `osi`: a user `"+"` receiver is
always an object, so a string or scalar left operand takes the built-in. The `osi`-based
field-closure dispatch below it (a struct carrying a `"+"` closure field) keeps `osi`.

The operator need not be for the shadowed type: an overload on an unrelated type triggers it
just the same, because it is the PRESENCE of an operator that changes how `+` is lowered. It
is a single-file defect; the sampler's `modules_split` cross assembled the ingredients (an
operator record, a block with a string frame, a colliding name) and its `single` face is where
it fires — the `split` face runs, because moving the module `n` behind the import boundary
breaks the shadow.

#### Grading list

The eight ablation rows are controls: each removes one ingredient and must keep RUNNING (or,
for the two marked "no", must keep being INVALID until the fix, then run). `no_collision` — a
`"+"` operator plus a block string concat with NO name collision — runs today and must keep
running; it is the sharpest control, isolating the shadow as the trigger. A fix is the string
`+` at the inner use reading the block binding's rep rather than the outer name's; grade it by
this witness reaching `runs` (printing `hi!`) while `no_collision` stays `runs`.
