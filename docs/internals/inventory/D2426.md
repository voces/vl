### D2426 — an un-annotated lambda handed to a type-parameter arrow parameter has no monomorphization pin

**closed · clause 2 · found grading D2344, filed 2026-09-25 against master `a277bf7b0`**

Repro:

    function ap<T>(f: (T) => T, x: T): T { return f(x) }
    print(ap((v) => v + 1, 3))
    // vl check: rc 0.
    // vl run: emit error, emitProgram: monomorphize: unsupported argument type for `f` in a
    // call to `ap`.

#### Mechanism

A checker order, not a monomorphizer gap. `checkCall` seeds a function literal's parameter
types from the substituted parameter type, but checked arguments in source order, so the
literal arrived while `T` was still unbound and `v` was typed as the variable `T` itself.
`monoArgFnTypeName` reads the literal's recorded type, found a type variable in it, answered
"" and the rung refused. `checkCall` now checks an argument whose parameters are still open
after the value arguments when its parameter rides a type variable (`lambdaLastOrder`), so
`x` binds `T = i32` first and the literal is seeded `(i32) => i32`, the type the annotated
spelling already had. The same order is D2425's second route.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `(v: i32) => v + 1` | runs, prints 4 | the un-annotated lambda: **yes** |
| `ap` concrete, `f: (i32) => i32` | runs, prints 4 | the type parameter: **yes** |
| named arguments, either order | same refusal | no |
| `T` bound to `string` (`(v) => v + "b"`, `"a"`) | same refusal | no |
| `ap(3, (v) => v + 1)` over `ap<T>(x: T, f: (T) => T)` | runs | the argument order: **yes** |
