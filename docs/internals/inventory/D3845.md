### D3845 — a hole lambda called through a `let` alias that a closure captured and that is written after, so every read goes through its capture cell `d[0]`, keeps its `i32` parameter default

**closed 2026-10-08 by lane SC · was check-clean invalid wasm · found in review of #3441 (`l3`) · filed 2026-10-08 against master `52c8e492d` · pins: `tests/cases/closures/hole-lambda-alias-chain-and-cell.vl` · residue [D3846](D3846.md)**

Repro:

    function f(x: string) {
      const c = (y) => y + "C"
      const e = (y) => y + "E"
      let d = c
      const g = () => d(x)
      print(g())
      d = e
      const r = g()
      r
    }
    print(f("a"))
    // vl check: rc 0.  vl run: invalid module inside `c`, `expected (ref $2), found i32`

Want:

    aC
    aE

#### Mechanism

A `let` a closure captures and that is written after the capture is boxed by the rewrite: `let
d = c` becomes `let d = [c]`, each read `d[0]`, each write `d[0] = e`. A call through it is
then `d[0](x)`, whose callee is no identifier, so no alias resolution saw it and `c` was never
instantiated. The monomorphizer now reads a call through such a cell (`monoCellReadName`,
`monoCellLamFe`), and `monoAssignedPeerFe` reads `d[0] = e` as `d = e`. A write is attributed
in the frame it sits in, the lambda's own or a function lifted out of it at any depth (a
nested `function flip() { d = e }`, whose write the rewrite spills through a temporary), and
never to a namesake elsewhere (`monoFrameHolds`, `monoFrameOfNode`, `monoLamValueFe`). Only the
rewrite's own cell is read through, one with no source position: a list the program wrote
(`let d = [c]`, reassigned `d = [e]` or grown) keeps the loud refusal it had
(`tests/cases/closures/error-hole-lambda-user-list-reassigned.vl`), as does a cell with any
write whose value is no hole lambda. The reviewed
spelling ending in a bare `d(x)` tail is [D3846](D3846.md), whose return is inferred void.
