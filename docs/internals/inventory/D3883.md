### D3883 — a nested generic returns or stores its enclosing function's `T` as its own type parameter, and the value is read at the wrong type

**closed 2026-10-08 by lane SC, with D3853 · now a loud check reject · was check-clean silently wrong · found closing D3853 (lane SC) · filed 2026-10-08 against master `a1c9be3c4` · pins: `tests/cases/generics/error-outer-type-parameter-returned-as-nested-one.vl`**

Repro:

    function a<T>(x: T) {
      function b<U>(y: U): U { x }
      print(b(1))
    }
    a(true)
    // vl check: rc 0.  vl run: prints 1

Want:

    vl check: return type mismatch: expected U, got T

#### Mechanism

Not located. A type variable is assignable to any type in a generic body, and the flow of `x: T`
into `U` is recorded as a deferred constraint. It can only be decided where both are bound, and
no single pin binds both. `a(true)` binds `T` and leaves `U` open, and `b(1)` binds `U` and leaves
`T` open. So neither pin refuses it, and the instance returns `a`'s boolean as `b`'s `i32`.

Closed by D3853's re-recording: `b(1)` binds `U` to `i32`, so the return constraint becomes
`T` against `i32`, re-recorded under `a`, and `a(true)` refuses it.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| `U` named `T` (shadowing) | still prints `1` | no |
| a `const q: U = x` in place of the return | still prints `1` | no |
| `a(1)` for `a(true)` | prints `1`, which is right | **yes** (the pins differ) |
