D937 wired five sites for the inferred nullable-map return and restricted all of them to the
`i32`-valued shape. That restriction was correct when it shipped and is the interesting part of
this row, because **it outlived its reason without anyone noticing**.

* **THE STATED REASON, and why it expired.** D937's own words: the return-site seed hardcoded
  `pendingMapSlot = -1`, the MONO `$mapStruct`, so rendering a name the emitter could not then
  lower "would lift this floor without lowering the value — `{[string]: string} | null` would
  pass `check` and then fail in the emitter, trading a clean refusal for a worse one". True at
  the time. But the SIGNATURE side already resolved a non-mono shape through
  `inferredRetMapSlot` — its own comment records gaining the `nulmap` arm — so the seed only
  ever had to ask the same home instead of assuming. Two sites disagreed about whether the
  shape was known, and the narrower one set the capability's bound.

* **THE ANNOTATED TWIN RAN THROUGHOUT for every value type**, which is what makes this a
  capability gap rather than a design rule, and what should have prompted the check earlier: a
  restriction whose annotated spelling works is a restriction on the INFERENCE path only.

* **THREE SITES, the same three D937 named.** The renderer (`nullableRetName`) drops the
  `i32` test and keeps the arena one — a string-KEYED map that is not a Set. The classifier
  (`buildFnMap`) drops it too. The return-site seed asks `inferredRetMapSlot(fnPos)`.

* **THE CHANNEL WITNESS HAS NOW MOVED FOUR TIMES, and this row moved it twice.** D937 moved it
  from the i32 map to a `string`-valued one; this close takes that spelling too, so it moves
  again to `i64[] | null`. What remains on this literal is the DISTINCT-BACKING scalar list
  (`i64[]`, `f64[]`, `f32[]`, `string[]`), whose inferred nullable return has no renderer arm —
  every annotated twin runs, so that half is a capability gap on the same footing this one was.
