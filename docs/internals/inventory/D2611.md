### D2611 — a value of a union of numeric types is accepted where one of its wider members is expected, and the box is passed as that number

**closed · runs, prints `14` · was a loud check reject, clause 2 (and invalid wasm past the checker,
clause 1, on master `e289f84d7`, before #3184 refused it) · closed 2026-09-30 by the numeric-join
lane, with D3450 · fixture `tests/cases/numerics/numeric-union-delivery.vl` · filed 2026-09-26,
found by the narrowed-write grid of D2609**

Repro:

    function useF(v: f64) { print(v * 2.0) }
    function src(): i32 | f64 { return 7 }
    useF(src())
    // vl check: argument 1: expected f64, got i32 | f64.  Wanted: prints `14`

Want:

    14

#### Mechanism

`assignable` accepted a union when every member is assignable, and `i32` widens to `f64`, so
`i32 | f64` was assignable to `f64`. No delivery position converts the value box: the argument,
the binding and the return passed the box where an `f64` is expected, and the module failed to
validate. #3184 made the arm join keep a numeric member as its own (D2627), which put many more
programs into that shape, so `assignable` now refuses a numeric union into a numeric primitive
it only widens to. The lowering is now `emitNumUnionConvert`: unbox by tag and convert each
payload at `emitExprAsF64`/`AsI64`/`AsF32`, the seam the delivery positions already call for a
number destination, and `assignableExpr` admits the delivery when every member converts exactly
(`numUnionConverts`, D3450).
