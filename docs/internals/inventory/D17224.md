### D17224 — an inferred result's statement returns deliver no record join into a maker's result, so the built record is refused

**closed 2026-11-25 by IR-N5 on branch `legacy-inferred-return-record-delivery` · now runs, prints `null` then `7` · was a loud emit reject at 4:14 (an invalid module before #9997): `adoptRetLits` now queues each returned value's delivery to the inferred result (`recPend`), as `assignableExpr` does for a written one · clause 2 · filed 2026-11-24 against master `bf61bf508` by IR-N5**

Repro:

    function mk2() { return { f: null, g: 7 } }
    function pick(m: boolean) {
      if m { return { f: 1, g: 7 } }
      return mk2()
    }
    print(pick(false).f)
    print(pick(true).g)
    // vl check: rc 0.  vl run: prints the Want block below

Want:

    null

#### Mechanism

With a written result `: { f: i32 | null, g: i32 }` the same program runs: the check delivers the
result's row into `mk2`, whose result is then built at the join's row (`(ref $0)` in the
disassembly), so no conversion is owed. An inferred result joins the `return`s at
`{ f: i32 | null, g: i32 }` but makes no such delivery (`noteRetJoinValues` re-joins only a
`tpJoinUnions` result), so `mk2` keeps its literal row and emit's record-join audit refuses the
branch. A local `const t = { f: null, g: 7 }` returned is the same: the binding is not typed at
the join.
