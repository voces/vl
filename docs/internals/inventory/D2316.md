### D2316 — two sibling blocks inside a FUNCTION binding one closure name resolve the FIRST block's signature, not the caller's own

**CLOSED 2026-09-24 — `parentLetOfSid`, the function-scope table every closure-signature
reader chases a binding through, was first-wins with no duplicate-name handling at all; two
sibling blocks binding one name collapsed onto the first block's `LetDecl` for every caller,
function-scoped, regardless of which block the actual call sat in. `moduleLocalLetOfAt`
already solved this at MODULE scope for D1751; `parentLetOfAt` is its function-scoped twin,
threaded through the closure-resolution ladder (`identClosureFeAt`, `identFnTypeAnnName*`,
`identCopySource*`, `calleeCloSigKeyAt` and its `calleeRetKind*`/`calleeReturns*`
callers)**

Two sibling blocks inside one function each bind a closure named `g` with a different return
type. `vl check` returns rc 0; the emitted module fails validation because the second block's
call is classified with the first block's return kind.

Repro:

    function f(): string {
      let out = ""
      {
        const g = () => 1.5
        out = "\{g()}"
      }
      {
        const g = () => "s"
        out = out + g()
      }
      out
    }
    print(f())
    // vl check: rc 0.  vl run: invalid module — the emitted module failed to validate
    //   inside `f$m0`: type mismatch: expected (ref $type), found f64

#### Mechanism

`calleeCloSigKeyAt` — the resolver every closure-call classifier (`calleeRetKindAt`,
`calleeReturnsF64At`/`StringAt`/`I64At`/`StructIdxAt`, `identClosureFeAt`,
`identFnTypeAnnName*`, `identCopySource*`) eventually reaches — resolves a bare (unannotated)
closure binding by finding its `LetDecl` through `parentLetOfSid(fn.fnBody, sid)`. That
reader's underlying table (`plScanStmt`'s walk, feeding the dense `plSidVal`/`plSidGen`
arrays) recorded ONE arena index per name, first-write-wins, with no notion of "this name has
more than one binding" at all — unlike the module-scope table (`mllMap`/`mllDup`/`mllOwner`)
D1751 built. So every caller asking "what does `g` denote here", regardless of which of the
two blocks it was actually asking from, got the FIRST block's `LetDecl` — the f64 closure —
and classified the second block's `g()` call as f64-returning. The call itself still invoked
the right (string-returning) function at runtime (value flow is scope-slot based, not
name-resolved), so the classifier's answer and the actual bytecode disagreed and the module
failed to validate.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the name collision (`g1`/`g2` instead of `g`/`g`) | runs | **yes** |
| the differing return type (both `() => 1.5`) | runs (same value classified twice, harmlessly) | **yes** |
| the second block (one block alone) | runs | **yes** |
| the sibling blocks moved to two functions | runs | **yes** |
| annotating both bindings' types | still invalid (the annotated rung has the same unpositioned reader) | no |

#### Grading list

The fourteen-case matrix in `tests/cases/closures/sibling-fn-blocks-*.vl` (param types,
each pairwise return-type combination over i32/f64/string/struct/list/nullable, nested
blocks, a block inside a loop, if/else arms, match arms, module level, a capture reused by
name in a sibling block, and a closure name reused for a non-closure value) must all keep
running and print the DIFFERENT value each case is built to distinguish. D1751's and D1862's
own fixtures (module-scope sibling blocks) must keep running unchanged — this row's fix adds
a function-scoped table, it does not touch the module-scoped one. D1935 (a field-source
capture's `nulstruct` classification lost under a duplicate block-local name) shares this
row's mechanism (`letInitCellKind`'s closure-return chain resolving by bare, unpositioned
name) and is closed by the same fix — see D1935.md.
