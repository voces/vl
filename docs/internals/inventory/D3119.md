### D3119 — a closure capturing a `for-in` variable over a literal-union list reads the atom as a string ref

**check-clean invalid wasm · clause 1 · found grading lane NB's position grid (`lit__capture__walk`) · the same on master `cc890c9f4` · filed 2026-09-28 against master `cc890c9f4`**

Repro:

    type K = "a" | "b"
    const zz: K[] = ["b"]
    for e in zz {
      const f = () => e
      print(f())
    }
    // vl check: rc 0.  vl run: invalid module inside `f`: type mismatch: expected (ref $type),
    // found i32

Want:

    b

#### Mechanism

Not localised past the ablation. The loop variable holds the `i32` atom, and the lifted
closure `f` reads its capture as a string ref. The same capture of a `K` parameter, or of a
`K` bound inside a `while` loop from `zz[i]`, runs, so the loop variable's capture type is
the suspect (compare [D2258](D2258.md), a loop-variable capture typed from the wrong rep).

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `string[]` in place of `K[]` | runs | **yes** (the literal union) |
| `print(e)` in the loop, no closure | runs | **yes** (the capture) |
| `zz[i]` bound in a `while` loop and captured | runs | **yes** (the `for-in` variable) |
| `e: K` a parameter, captured | runs | **yes** |
| the loop inside a function | the same invalid module | no |
| `const c = e`, then `() => c` | the same invalid module | no |
| `const f: () => K = () => e` | the same invalid module | no |
| `() => e == "b"` | the same invalid module | no |
| `zz: (K \| i32)[]` at module scope, `e` narrowed by `!(e is i32)`, then `() => show(e)` | invalid module inside `f` | no; with `string` for `K` also invalid, with a record arm `emitProgram: field access but no struct type declared`, and inside a function it runs, so the narrowed walk may be a second mechanism |
