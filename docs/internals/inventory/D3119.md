### D3119 — a closure capturing a `for-in` variable over a literal-union list reads the atom as a string ref

**closed · a capture of a `for-in` variable, or of a bare copy of one, asks the loop's iterable whether it holds an atom, and a module-scope loop over box elements is resolved while its closures' narrowing is recorded ([D3136](D3136.md)) · fixture `tests/cases/closures/capture-walk-variable-literal-union.vl` · was check-clean invalid wasm · clause 1 · found grading lane NB's position grid (`lit__capture__walk`) · the same on master `cc890c9f4` · filed 2026-09-28 against master `cc890c9f4`, closed 2026-09-29 against master `07d414042`**

Repro:

    type K = "a" | "b"
    const zz: K[] = ["b"]
    for e in zz {
      const f = () => e
      print(f())
    }
    // vl check: rc 0.  vl run: invalid module inside `f`: type mismatch: expected (ref $type),
    // found i32

Want:

    b

#### Mechanism

The env field was right (`captureValKind` types a loop variable off `forInElemKind`, an `i32`
atom), but the closure's read asked `capturedIsLitAtom`, which resolves a capture through
`capturedBindingOf` — and a loop variable has no declaration node, so the answer was "not an
atom" and `f` compared and returned the capture as a string ref. `capturedLoopVarIsLitAtom`
(`emit_classify.vl`) is the loop channel: it follows `captureLoopCopySrc` to the loop variable
a bare copy names, then asks `forInVarIsLitAtom` of the iterable in the walking frame, the one
predicate `declareForInLocals` now flags the loop's own slot with. The narrowed module-scope
walk in the ablation's last row was the second mechanism, filed and closed as
[D3136](D3136.md).
