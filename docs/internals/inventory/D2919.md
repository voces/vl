### D2919 — a generic call on a hole list literal's element prints a `boolean` pin as `1`

**closed 2026-09-28 — the filed repro prints `true` · was check-clean silently wrong, clause 1, the same on master `e91e04a8f` · closed by reading a shared node at the hole instance's own binding in `exprIsBool` and in the generic-call pin (`monoArgTyName`) · filed 2026-09-27 against master `0284dc2a8`**

Repro:

    function id<T>(t: T): T {
      return t
    }
    function h(x) {
      const l0 = [x]
      print(id(l0[0]))
    }
    h(true)
    // vl check: rc 0.  vl run: prints `1`

Want:

    true

#### Mechanism

A hole instance shares the generic body's nodes, whose recorded type is the hole's type variable, so a classifier reading that type sees the template's `i32` rep. An explicit `<T>` instance re-types those nodes at the pin (`monoPinRetype`) and a hole instance did not. `monomorphize` now banks each hole instance's binding (`monoHoleSubRow`), and `holeOperandTyOf` reads a shared node at it without banking a pin. `exprIsBool` asks it, and so does `monoArgTyName` before its rep cascade, which named the element `i32`. The lambda chain closes through `exprIsBool` too. [D2931](D2931.md) is the same symptom through a lambda argument's signature key.

#### Ablation

| ingredient changed | outcome | needed? |

| `h<U>(x: U)` | runs, `true` | **yes** (the hole) |
