#### Mechanism

**Two rungs, and the first alone changes nothing an error message can show.** `.pop()` /
`.get(i)` over a value-union ref list already yields the `{tag, payload}` box
([D1825](D1825.md) built that arm). What was missing is the reader half:

* `globalCellKind` had no module-scope twin of the local ladder's `letPopUnionBoxElem` arm, so
  the un-annotated global's cell was the `i32` fall-through and the binding was PROMOTED to a
  start-function local on that answer (`globalPromotable` admits only numeric scalars);
* `exprUnion` had no arm for the read at all, so `emitUnionCoerce`'s "already a union value"
  pass-through declined and every box-typed destination boxed the box again.

`wasm-dis` on the second of those is what names it — the box built a second time, as the
union's f64 member, around the box the read had already built:

    (global.set $global$71
     (struct.new $4
      (i32.const 6)
      (block (result (ref (exact $7)))
       ...
       (struct.new $7
        (f64.convert_i32_s
         (if (result (ref $4))

Adding only the cell rung makes the message IDENTICAL while the mechanism changes underneath
it: `expected i32, found (ref $type)` is what a box in an i32 local prints AND what
`f64.convert_i32_s` applied to a box prints. Reading the unchanged message as "the cell is
still i32" is what a whole lane spent itself on — the disassembly is what separates them.

**The memo was not the mechanism.** Instrumented at the memo itself — one sink row per
`globalCellKind` call carrying name, answer, hit-or-`Go`, `gckGen` and `emitPassGen`, flushed
after `emitProgram` — the witness's `_t` reads

    GO  ix=6035 nm=_t k=i32 gen=3 pass=35 depth=0
    HIT ix=6035 nm=_t k=i32 gen=3 pass=35 depth=0    (x3)

one `Go` and three hits of it, all at one generation and one pass. There was no earlier
committed answer to be stale, and the annotated face already answered `union` at the same call
while failing identically — which is what pointed at the destination rather than the cell.
