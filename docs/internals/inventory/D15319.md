### D15319 — an unbound `??` over a read of a container built wider, defaulted to a generic identity of a fresh literal, joins two storages

**closed 2026-11-04 by lane destringify · runs, `4` · the same join bound to a `const` ran · found closing D15318 · filed 2026-11-04 against master `019d4cdd8`**

Repro:

    type J = { f: i32 | null }
    function mk() { { f: 4 } }
    const m = Map()
    m.set("a", mk())
    const wm: {[string]: J} = Map()
    wm.set("a", mk())
    function id<T>(d: T): T { d }
    print((m.get("a") ?? id({ f: 1 })).f ?? 0)

Want:

    4

#### Fix

The store column's general `??` arm (`storeHeldAt`) was reached only from a binding, return or
write holding the join, so a join nothing holds never had its default delivered at the read's
record. `storeCoalescesResolve` now holds each such join itself, unless its default is a fixed
parameter or binding (D15241's refusal). The scope was wider than this row: on master `0fe0103c8`
and `dd6fb84da` every unbound record default was invalid wasm, the plain literal
`(m.get("a") ?? { f: 1 }).f` included, so the ablation row below that reads `runs` did not hold
there; a maker call, a relay, a held `const` of a literal or a call, a hole identity, and a local
assignment of the join all run now.

#### Mechanism (as filed)

Not yet ablated past the grid below. Bound to a `const`, the join is held at the read's record by
the store column (`storeHeldAt`), which builds the identity's literal there (D3442); a join no
binding initialises is never visited by it, so the read is emitted at J and the identity's result
at its own row.

#### Ablation

| --- | --- | --- |
| the identity (`?? { f: 1 }`) | runs | **yes** |
| the inline join, bound first (`const b = m.get("z") ?? id({ f: 1 })`) | runs | **yes** |
| a held literal argument (`const lit = { f: 1 }; … id(lit)`), bound | runs | no |
