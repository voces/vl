### D16493 — pinning a generic's function-typed parameter asks the write-scan index about a lambda minted after it was built, and the compiler traps

**compiler trap · clause 1 · open · `vl check` rc 0 · `vl run`: "the compiler itself trapped" in `cwIxReadPastBuild` (check_write_scan.vl), from `elabModuleLam` ← `elabHeldFnTy` ← `monoArgPinTyAt` ← `monoPinTyParamComposite` · every neighbouring spelling is [D16412](D16412.md)'s refusal · found by the independent oracle's higher-order generator (fuzz cells `ho_s3_0015`, `ho_s9_0097`) · filed 2026-11-15 against master `d31ab4440`**

Repro:

    function hid(x) { x }
    function gid<A>(x: A): A { x }
    function app<A, B>(f: (x: A) => B, x: A): B { f(x) }
    function compose<A, B, C>(f: (x: A) => B, g: (x: B) => C): (x: A) => C { (x: A) => g(f(x)) }
    print(hid("a"))
    print(compose(gid, hid)(5))
    print(app(gid, 7))
    // master: vl check rc 0; vl run: the compiler itself trapped

Want:

    a
    5
    7

#### Mechanism

`monoPinAnnotatedParam` pins `compose`'s `f`/`g` from the argument's held type, which
`elabHeldValTy` reaches through `elabHeldFnTy`; that asks `elabModuleLam` whether the held lambda
sits at module level, and `elabModuleLam` reads `cwIxParent` through `cwIxCovers`. The lambda it
asks about was minted after the write-scan index was built (an instance made by the earlier
`app(gid, 7)` or `hid("a")` instantiation), and `cwIxCovers` traps on such a read by design rather
than answer from a column that cannot describe the node. The fix is the reader's: answer for a
minted node from its origin, or not ask.
