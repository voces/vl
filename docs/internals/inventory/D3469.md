### D3469 — a `?.` call on a local a type-parameter write left nullable is typed without its `| null`, and its guard reads the receiver as the hole

**closed 2026-11-15 — the filed program RUNS and prints `null` · was a loud emit reject, `emitProgram: callee is not a function name`, the same on master `660af42ff` · clause 1 until 2026-11-01 · the `opt-call-on-type-param-write` matrix runs 84 of 84 cells, 0 before · filed 2026-10-02 against master `c17016a1e`**

Repro:

    function g<T>(x: T) { let s: {[string]: i32} | null = null; s = x; const ff = () => s?.has("k"); print(ff()) }
    const v: {[string]: i32} | null = null
    g(v)
    // vl check: rc 0.  vl run: prints null (was: emit reject, "callee is not a function name")

Want:

    null

#### Mechanism

`s = x` narrows `s` to an `HD_TVW` hole whose pin reads the declaration or its non-null member.
Three readers disagreed about it. `checkOptCallNode` wrapped the call's `| null` only for a
`TyNullable` receiver, so the template typed `s?.has` as `boolean`. It also resolved the method on
the hole, so a string, list, self-function or closure-field method fell to the field-read demand
and was refused at the pin. And `drwWalkMemberCall`'s guard cloned the receiver at `nonNullTy` of
the hole, which is the hole itself, so the arm's `has`/`get` met an unresolved receiver. The fix
reads the declaration's non-null face (`writeLandNestedTy`) in both the checker and the guard. It
wraps `| null` when the write-land read admits `null`, and every instance of that call wraps it too
(`optCallLandWraps`), so a closure lowered at the template's rep agrees with its caller.
