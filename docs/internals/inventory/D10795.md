### D10795 — a hole-function list element past 0 whose own calls pass other types than element 0's is refused an un-annotated lambda

**loud emit reject · `vl check` rc 0 · clause 2 · CAPABILITY: a neighbouring spelling runs (the ablation) · found closing [D10793](D10793.md) · present on master `cf38fa028` · filed 2026-10-23 against master `cf38fa028`**

Repro:

    function apply2(g) { print(g(1, 2)) }
    function apply3(g) { print(g(1.5, 2.5)) }
    const gs = [apply2, apply3]
    gs[1]((a, b) => a + b)
    // vl check: rc 0.  vl run: emitProgram: monomorphize: unsupported argument type for `g` in a call to `apply3`

Want:

    4

#### Mechanism

The checker types `gs[1](...)` through the list's element type, which is element 0's. The
lambda's bind therefore names `apply2`'s parameter, and `apply3`'s is left unbound. D10793's rung
pins the lambda from the element's own calls of `g` (`fnFlowCallPathAgreedPinTys`). But the
fn-flow class merges the parameters of every element in the list, so `(i32, i32)` and
`(f64, f64)` disagree and the lookup returns nothing. When the elements' calls agree on one type,
the rung pins and the program runs. What is missing is a pin scoped to the one element that the
constant index names.
