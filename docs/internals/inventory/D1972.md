### D1972 — `__trap__()` does not end a path, so a guard arm that traps does not narrow the code after it

**loud check reject · design question, not yet ruled: whether a trapping call is a path terminator · residue of D1970's grid (every `__trap__` cell) · filed 2026-09-22 against master `a8a104432`**

Repro:

    type IoError = { msg: string }
    function f(x: i64 | IoError): i64 {
      if x is IoError {
        __trap__("io")
      }
      x * 2
    }
    print(f(3 as i64))
    // vl check: rc 1, `operator '*' is not defined for i64 | IoError and i32`

#### Mechanism

`stmtAlwaysExits` recognises only `return`/`break`/`continue` and the compound statements built
from them. `__trap__` is an ordinary void call to the checker, and VL has no `never`-returning
user function, so no call is a terminator. Admitting one needs a ruling first: the intrinsic
only (and whether a user binding named `__trap__` shadows it), or a `never` return type that
any function can declare. Either answer must reach the same predicate, so the checker, the
emitter and the unreachable-code lint move together.

#### Grading list

Both return spellings; the `__trap__()` and `__trap__("reason")` arities; the lint's
unreachable-code warning after a trap.
