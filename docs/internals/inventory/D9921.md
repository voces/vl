### D9921 — a lambda whose un-annotated result is `null` refuses, even uncalled

**closed · runs, prints `true` · was loud emit reject, `vl check` rc 0, `emitProgram: bare null needs a struct-typed context`, clause 2, CAPABILITY · found closing [D4672](D4672.md) · present on master `8700f0727` · filed 2026-10-22 against master `8700f0727` · closed with [D9565](D9565.md): the suspect was right, a lambda published no inferred-return row when its result was the `null` unit, so `buildFnMap` never gave it `nulnone`; it now records one keyed by its node (`inferRetPublishNullOnly`, check_inferred_return.vl), and a declared function's row goes through the same `recordInferRetNullOnly` (check_fit_rules.vl) · fixture `closures/lambda-null-result-inferred.vl`, matrix `fn-value-lambda-result-null` 0 → 48 of 48**

Repro:

    const v = (x: i32) => null
    print(v(1) == null)
    // vl check: rc 0.  vl run: emitProgram: bare null needs a struct-typed context

    true

#### Mechanism

Not localised past the ablation. Since [D4672](D4672.md) the `null` type has a `$fnsig` token
(`Z`), and a declared function whose inferred return is `null` gets the `nulnone` return kind
from the checker's inferred-return row (`buildFnMap`, emit_collect.vl). The lambda's body is
emitted with no such kind, so the bare `null` reaches the struct-null floor. The suspect is
the inferred-return row a lambda is looked up by (`inferRetRowByNode`), which the ablation
does not reach.
