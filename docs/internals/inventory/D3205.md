### D3205 — a function read through a declared row's `H | null` field of a literal whose field is present is called at `i32` in a hole or generic instance

**closed · a hole read through a nullable record reads its non-null face at the pin, in the emitter's pin read and in the substitution · fixture `tests/cases/generics/hole-nested-nullable-record-field-call.vl` · was check-clean silently wrong · clause 1 · pre-existing, the same on master `94670f728` · found by the NF lane's grid (`n0153_bool_NR_hole_bound_fn_lit`) · filed and closed 2026-09-29 against master `94670f728`**

Repro:

    type R = { v: i32, h: { f: () => boolean } | null }
    function F(z) {
      const g = z.h.f
      print(g())
    }
    F({ v: 7, h: { f: () => true } })
    // PRINTS 1

Want:

    true

#### Mechanism

The checker pins `z` at the literal, whose `h` is present, so the program is well-typed. The
emitter's instance lays the literal out at the declared row `R` it matches, whose `h` is
`{ f: () => boolean } | null`, and the result of `g()` is read off `?ret.?fld.f.?fld.h.z`:
`holePinReadAt` (and, for `<Z>`, `substHoleTyReal`) looked `f` up on the nullable record, found
no field, and the result fell to `i32`. Both now read a nullable record at its non-null face.
The checker cannot be fooled by this: a read through a pin that is really `| null` is refused
by its own `memCstrTy` row (D3204).

#### Ablation

| ingredient changed | outcome on master | needed? |
| --- | --- | --- |
| `type R` removed | prints `true` | **yes** (a declared row claims the literal) |
| `R`'s `h` not nullable | prints `true` | **yes** |

| `v` removed from `R` and the literal | prints `1` | no |
| `function F<Z>(z: Z)` | prints `1` | no |
| `const r: R = …; F(r)` | prints `1` (now refuses, D3204) | no |
