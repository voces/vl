#### Mechanism

The multi-value step takes a record apart only when no `struct.set` anywhere can reach its
type (`multivalue.rs`, `scan`). The rule protects values that may be aliased: a producer's
result can be a stored record, and reading its fields early would miss a later write. A
`struct.new` that is itself the argument has no alias. Its only reference is the parameter,
and a field-only parameter reaches nothing but `struct.get`s and other field-only
parameters, so no `struct.set` can name that object while the call runs. Its fields are the
`struct.new`'s operands for its whole life. That argument holds for a fresh argument and for
a scalarized local set only from fresh records. It does not hold for a producer's result, a
merge arm that reads a stored record, or a result twin's exit.

sunpa's game-side `Item` is written in `frame` (`item.height = …`, `item.roll = …`, on the
actor's own item before it is emitted), so `shadow`'s literal is boxed: 30,602 `Item`s and
30,602 list headers under `feet-test` (2.8 a frame each).

**Decision asked.** The coordinator's brief for D3754 kept "only never-written records
qualify, the same as today", on the row's claim that sunpa's items are never written. They
are written. The recommendation is to let a fresh `struct.new` argument, and a local set only
from fresh records, be taken apart whatever writes its type elsewhere. That is a separate
predicate from the per-type rule, which producers, merges and exits keep. It is about 30
lines in `plan_context` and the field-only-local fixpoint.
