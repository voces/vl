### D15251 — a string-literal `is` in a hole or generic function builds a string compare on an operand its instance pins at a non-string

**closed 2026-11-04 by lane column-G1 · runs, prints `true` then `false` · was check-clean invalid wasm, clause 1 (`expected (ref $string), found i32` inside the instance), and a positionless loud emit reject with the `i32` instance alone · found probing [D15250](D15250.md) · filed 2026-11-04 against master `80e3a45b` by lane column-G1**

Repro:

    function h(v) { v is "x" }
    print(h("x"))
    print(h(3))
    // vl run: true, then false.
    // Was: vl check rc 0, then the emitted module failed to validate inside `h$1`.

#### Mechanism

A number-literal test lowers only where the operand's base is the literal's (`emitIsTestNumLit`),
but a string-literal test, inline, a set or a named set, lowered the string compare at every
instance: `emitIsTestLitArms` and `emitLitMemberEq` never asked whether the instance's operand
could be a string. `monoStaticIsResult`, which answers `is string` there, is never reached for a
literal test.

#### Fix

`litIsPinNever` (`compiler/wasmEmit.vl`), ahead of the literal paths: where the tested type is a
literal or a literal set and the operand is typed at a type parameter or a hole, the operand's
type at the instance (`instanceReadTyOf`) is compared member by member with the tested members
through the checker's `assignable`, both ways. With no member related, the test is `false`
there, and a receiver that is not a re-readable place is still evaluated (D12070).
`tests/cases/generics/is-string-literal-at-non-string-instance.vl`, the two
`is-string-literal-at-non-string-instance` matrix templates and the named set
`d15251-is-string-literal-instance` hold the shapes.
