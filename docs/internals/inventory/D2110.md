### D2110 — a `for f in fs` loop variable is a storage class the function-value callee resolver had no rung for, so a void element's call statement dropped nothing

**closed 2026-09-22 — the witness prints `a` then `b` · was check-clean invalid wasm (`vl check` rc 0, then `type mismatch: expected a type but nothing on stack`), clause 1 · filed 2026-09-22 against master `7b16d43ab`, found by a sibling lane probing indirect calls · fixture `tests/cases/closures/function-list-call-statement.vl`**

Repro:

    function a(): void { print("a") }
    function b(): void { print("b") }
    const fs: (() => void)[] = [a, b]
    for f in fs { f() }

#### Mechanism

`emitCallStmt`'s `Ident` arm decides whether to `drop` a function-value call's result by
asking `calleeReturnsVoidAt`, which reads `calleeCloSigKeyAt`: narrowed arm, parameter,
annotated or inferred `LetDecl`, lifted-closure binding, copy source, capture owner. A for-in
loop variable is none of those — it has no declaration node — so the ladder answered `""`,
`""` reads as "returns a value", and the statement emitted `call_ref` of a `>v` functype
followed by `drop`. The CALL itself was right: `cloCallSigKey` falls back to the callee's
arena type, which the void question never reached. The same missing rung also let a generic
instance call its loop variable at the GENERIC's arena signature (`(T) => T`), which is a
second face: `expected i32, found (ref $type)` inside `runG$1`. Fixed by two rungs: the loop
variable keys through its iterable's element slot exactly as `fs[i]` does (`loopVarCloSigKey`,
from the SCOPED slot's `localLoopIter`, or D1142's `captureLoopVarIterOf` when the frame
captures the name), and a positioned last rung reads the callee node's own `TyFunc` — the key
the call is lowered with — so the void answer and the emitted `call_ref` cannot disagree.

The loop-variable rung must read the scope stack (`scopeSlotOf`), not `declaredSlotOf`: the
latter falls back to a whole-frame scan by name, and review of the first candidate showed a
call to an OUTER binding after the loop closed (`const f: (i32) => void = a; for f in vs {…};
f(9)`) keyed at the element's signature — `indirect call type mismatch` at run time, where the
base printed `1 1 9`. The fixture carries that shape at module scope and in a function.

#### Ablation

A 1,496-cell grid (11 signatures × named / lambda / capturing / mixed elements × 9 access forms ×
module / function × annotated / inferred list) plus 47 hand cells; every cell prints values
proving which element ran, in which order. Before this row the void signatures ran only
through an index (`fs[i]()`, `fs[k]()`) and a module-scope copy binding; every for-in spelling,
a struct field, a parameter, a returned list and a loop variable captured by a closure in an
ordinary function were silent. A loop variable captured inside a GENERIC instantiated at two
types is not covered: it is invalid wasm on both seeds (D2113).

| rung removed (seed rebuilt) | outcome |
| --- | --- |
| neither (the fix) | 1,496 / 1,496 grid + 47 / 47 hand cells run |
| the loop-variable rung | 24 grid cells silent (`const g = f; g()` in a function), 5 generic hand cells silent or `no interned signature` |
| the positioned arena rung | map pair `for k, h in m { h(k) }` silent (the second name has no `localLoopIter`) |
| scoped lookup (`declaredSlotOf` instead) | a call to an outer same-named binding after the loop traps or is invalid wasm (runs on base) |
