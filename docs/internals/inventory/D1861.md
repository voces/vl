### D1861 — a map declared in a MODULE-LEVEL BLOCK and captured by a closure: check-clean invalid wasm at a string key, a loud emit reject at an i32 key

**check-clean invalid wasm · found 2026-09-07 by B6a's position matrix (`i32-keyed-map-in-container.matrix.vl`, the six `*_capture` cells) · pre-existing on master `50054e1eb` · the SAME shape inside a function body, or at module scope with no block, RUNS at both key reps**

The capture's env field takes the map at the wrong type. At a STRING key the module validates
nothing and the engine refuses it — `type mismatch: expected i32, found f64` inside the closure
— which is a clause-1 violation `vl check` cannot see. At an i32 key the emitter reaches
`emitProgram: map key is not a string` first, because the receiver's shape has already resolved
to the string-keyed mono, so the same defect wears a loud message on one face and none on the
other. Neither is about the KEY: the key rep only decides which of the two symptoms the author
gets.

Repro:

    if true {
      const c: {[string]: f64} = Map()
      c.set("a", 2.5)
      const f = () => {
        c.set("b", 3.5)
        print(c.get("b") ?? 0.0)
      }
      f()
    }
    // vl check: rc 0.  vl run: invalid module — the emitted module failed to validate
    //   inside `f`: type mismatch: expected i32, found f64

#### Mechanism

A module-level block's bindings live in the START function's frame, and the closure's capture of
one resolves through a different leg from a function body's. `mapShapeOfExpr`'s captured-map arm
walks `parentBindingOf` and `letMapShapeOf` off `fnStmtsPosOf(fnIx)`, which the start frame does
not present the way a `FuncDecl` frame does, so the shape falls to the mono `-1` — the
string-keyed struct — whatever the binding's declared key and value were. The three block kinds
the matrix names (`if`, `while`, bare) all reach it.
