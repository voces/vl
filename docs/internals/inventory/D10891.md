#### Mechanism

Traced 2026-10-25 on the L6 D2 branch. The `.map` is not the ingredient; the list literal is.
Any use of `[x]` at the instance refuses (see the ablation rows below). The array-literal
classifiers that decide a literal's rep are frameless: `arrLitIsRef`, `arrLitElemName` and
`arrLitElemKind` read `nodeTyIxOf`, the template node's own type. A `<T>` function is cloned
per instance, so its nodes carry the pinned type. A hole function's instances share the
template's nodes, and their types live only in the per-frame bank (`nodeTyInOf(ix, fnIx)`,
`bankInstanceNodeTys`). So `[x]` classifies as the i32-list fallback. The frame-aware
`exprStruct(elem, fnIx)` in that fallback (wasmEmit.vl) then sees a `P` element and refuses
with `struct array elements are not supported`. The `.map` spelling refuses earlier, at its
source row. This is not a type-keyed row question: the fix is to make the literal classifiers
take `fnIx`, the way `arrLitElemNameIn` already does for a nested scalar leaf (D2798).
