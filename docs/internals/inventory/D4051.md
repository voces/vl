### D4051 — a mutable list of records delivered as a list of a narrower record type is refused as a codegen gap, though the container ruling refuses it by design

**loud check reject · clause 2 by wording only: the refusal concedes type-validity for a program the design forbids · found writing `docs/spec/types.md` (lane SPEC) · filed 2026-10-11 against master `1df3c8f91`**

Repro:

    type Animal = { a: string }
    type Cat = { a: string, z: i32 }
    const cats: Cat[] = [{ a: "c", z: 9 }]
    const animals: Animal[] = cats
    animals.push({ a: "dog" })
    print(cats.length)
    // vl check: rc 1, "an object value of shape Cat flowing into Animal (reached through
    // Cat[] into Animal[]) drops the field `z`: type-valid (structural width subtyping) but
    // not yet supported by codegen"

#### Mechanism

DECISIONS.md §"No implicit container widening" (owner, 2026-09-23) refuses a MUTABLE wider
list whether or not the element's storage changes. A write through the wide list would
reach the narrow one; here, an `Animal` without `z` would be pushed into `cats`. The
refusal is correct, but its sentence is not. The element-level width check fires before
the container rule. It says the program is type-valid and waiting on codegen, so the
program counts as a capability gap, and the message offers neither fix the ruling names.
The sibling flows print the ruling's message. For `i32[]` into `f64[]` it reads: "a
container never widens implicitly, and only a readonly list is covariant … Declare the
destination `readonly f64[]` … or copy it with `.map(…)`".
