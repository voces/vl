### D3979 — a generic function written into a `let` or a list element and called reuses an instance another call already made, at that call's type

**closed 2026-10-11 by lane SC · runs · was check-clean silently wrong · clause 1 · pins: `tests/cases/closures/written-let-of-generics-called-after-another-instance.vl`, `tests/cases/closures/list-element-written-with-generic-after-another-instance.vl`, `tests/cases/closures/error-written-let-of-generics-called-at-two-types.vl` · found in review of #3505 (`rv3505/r7/y01`–`y04`; `x01`, `x05`, `x06` through #3505's pin) · filed 2026-10-11 against master `50ab2d601`**

Repro:

    function inner<U>(u: U) { print("I"); print(u) }
    function other<V>(v: V) { print("O"); print(v) }
    function main() {
      inner(3)
      let f = other
      f = inner
      f(true)
    }
    main()
    // vl check: rc 0.  vl run: printed I 3 I 1

Want:

    I
    3
    I
    true

#### Mechanism

`f` keeps the generic type of its seed `other` (ruling C), so the call `f(true)` has no concrete
type, and nothing instanced the generic written into `f` at the call's type: `inner` was read as a
value with no instance of its own, which resolved to the `i32` instance `inner(3)` had made. A call
through a written, un-annotated `let` every value of which names a declared generic now takes the
instance its arguments give the seed, and each value written is instanced at that type
(`monoCallWrittenLet`); a second call type is the binding conflict, refused. A list written through
an element (`fs[0] = inner`) and called through one is pinned as D3977 pins it, and each value
written takes the element type. A binding with a lambda written in keeps master's path (one lambda
body serves every enclosing instance).
