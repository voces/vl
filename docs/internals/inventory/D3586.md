### D3586 — a write to a list's `.length` passed `vl check`, then the emitter refused it (sunpa SP-023)

**closed 2026-10-03 — now a loud check reject (`` `length` is read-only; to empty a list use `xs.clear()` or `xs = []` ``), spanned on `.length`, for `=`, `+=` and `-=` on a list (a generic `T[]` included), a map, a set (the hint names `m.clear()`) and a string (no hint) · a record's own field named `length` stays assignable · `xs.length++` was already a parse error · fixtures `tests/cases/lists/length-is-read-only.vl`, `tests/cases/lists/record-length-field-assignable.vl` · was a loud emit reject (`emitProgram: field assignment but no struct type declared`) · clause 2, the checker owed the diagnosis · owner decision 2026-10-03: `length` is read-only · filed 2026-10-03 against master `030a90e52`**

Repro:

    let xs: i32[] = [1, 2, 3]
    xs.length = 0
    print(xs.length)
    // vl check (before): rc 0.  vl run: emit error, "field assignment but no struct type declared".

#### Mechanism

`checkMemberNode` answered `.length` on a list, a map or a string as an `i32` whether the
member was being read or written, so `xs.length = 0` typed as an ordinary `i32` store. The
emitter's field-assignment arm handles only struct receivers and refused it. The checker
already knows a member is an assignment target (`getWriteTarget`, used to refuse a write
through a getter), so the fix asks that question on the three built-in `.length` arms.
