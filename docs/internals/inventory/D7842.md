#### Mechanism

Probed against the D7183 close. An instrumented build shows the retype in `monoOpenCallAtElems`
declining (an element's result at the planned types is not found) after a second plan round,
so the callee keeps its open type and is refused. The `for` spelling calling twice runs, so the
difference is the `if` join's arms once the first call has coerced them (not traced further).

Re-probed 2026-10-20 (lane L1, closing [D7763](D7763.md)): the decline is in `monoElemParamTys` at the
`apply2` arm, whose `g` still has two pinned parameter lists (`fnFlowDeclPathAgreedPinTys`
false). With the second call the split gives `apply2` no slot per type, so the plan
(`fsPlanHoles`, or the asked calls `fsAskOpenCallPars` collects) declines before the emitter.

The close found two causes instead, both in the status line: the by-name plan's drop of
`apply3`'s parameter, and the second call reading an arm the first call had already instanced.
