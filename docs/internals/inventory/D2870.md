### D2870 — a list literal returned beside a string, with no return annotation, builds invalid wasm

**closed 2026-09-27 — the repro RUNS and prints `1.5` · was check-clean invalid wasm inside `g`, the same on master `8e10ef58b` · closed by holding an inferred union-box return at the box (`fnCheckedRetIsUnionBox`) · fixture `tests/cases/functions/infer-list-return-beside-string.vl` · found by the #3225 review · filed 2026-09-27 against master `93b93319e`**

Repro:

    const a: i32[] = [3]
    function g(k: boolean) {
      if k { return [...a, 2.5] }
      "z"
    }
    const v = g(true)
    if v is f64[] { print(v[0] / 2.0) } else { print(v) }
    // vl check: rc 0.  vl run: invalid module inside `g`

Want:

    1.5

#### Mechanism

`g`'s checker-inferred return `f64[] | string` is recorded as a value-union box, and
`buildFnMap` seeds its result kind `union` from that row. The body built the box correctly,
but `criClassify` then read each `return`'s own expression and let an `f64list`, `strlist` or
`reflist` fact outrank `union` (`retKindPri` ranks every list but `i32[]`'s above it), so the
signature declared the list while the body returned the box. A tail `if` never reached that
walk, and an `i32[]` arm ranks below `union`, which is why both ran. The close holds a
function whose row names a union box (`inferRetRungIsBoxedUnion`, not a literal-union alias's
atom) at `union`, as `fnCheckedRetIsMapUnion` already did for a map arm. A record arm beside a
string list (`string[] | C`, a struct-union row) was the same mechanism and closes with it.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| a plain literal (`[3.0, 2.5]`) | still invalid | no |
| the list bound first (`const l = [3.0, 2.5]; … return l`) | still invalid | no |
| the string arm (`[0.5]` instead of `"z"`) | runs | **yes** |
| an `i32[]` list (`[3, 2]`) | runs | **yes** |
| a tail `if` instead of `return` | runs | **yes** |
