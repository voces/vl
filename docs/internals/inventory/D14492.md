### D14492 — an `__array_new_default__` element is an in-band `-1` on the row, so a read of it records a snapshot

**open 2026-10-27 · runs today and must keep running · a second kind of "open", not a wrong answer: the read's recorded type is a peeked `i32` written by hand, not a variable the pin resolves · filed 2026-10-27 against master `f1332ea4d`**

Repro:

    function storeAfter() {
      let a = __array_new_default__(3)
      print(a[0] + 1)
      a[0] = 1.5
      print(a[0])
    }
    storeAfter()

Want:

    1
    1.5

#### Mechanism

An unpinned `__array_new_default__` element is `TyArray.aElem = -1`. It is a sentinel on the
row, not an arena type, and a pin mutates the row in place (`arrDefPinHoleElem`,
`asgReadElemPin`, `resolveHoleLinks`). The array node's recorded type follows the pin because
it is the shared row. A read of the element has nothing open to record, though: no `Ty` names
"the element of row R", and `hdMint` declines a base that is not a `TyVar`. So
`arrDefOperandElemPeek` (check_demands.vl) and `asgReadElemPin` (check_narrow_flow.vl) each
write the peeked default as the read's type with `nodeTySet`. The operator over that read is
then typed off a snapshot rather than derived from the element.

#### Close condition

The element becomes a body-scoped inference variable: one binding per declaration, not per
instance, so gradual generics, the owner-keyed `holePinSet` and instance cloning never see it
as hole-generic. Its solution lives in the same substitution store as a call pin's
per-instance bindings, so there is one resolution path. The read and the operator then record
`HD_ELEMV`/`HD_BINOP` over it unchanged. A `Ty` variant pointing into a storage row is
rejected: it would be a second kind of "open".

Deletes: the `nodeTySet` peek in `arrDefOperandElemPeek` and in `asgReadElemPin`, plus the
`aElem < 0` sentinel sites the change reaches.
