### D16390 — radix-pattern arithmetic at a float destination wraps at 32 bits

**closed · runs, prints `4294968295` · was check-clean silently wrong · clause 1 · bucket (f) · closed 2026-11-15 by lane N under the owner's ruling on spec question 4.2 (DECISIONS.md, "At an `f64` the use's width is 64"), which reverses D14990's `f64` clause: a radix tree at an `f64` destination (`litTreeWideTy`) or beside an `f64` operator peer (`radixTreeF64Pair`, read by the checker and `numPairOpTy`) computes at 64 bits and converts · fixture `numerics/radix-tree-at-f64.vl` · matrix `radix-tree-at-f64.matrix.vl` · 1 DISAGREE verdict of the 2026-11-15 oracle-fuzz triage (`ar_s27_0068`) · filed 2026-11-15 against master `3d526470a`**

Repro:

    let x: f64 = 0xFFFFFFFF + 1000
    print(x)
    // PRINTS 999 (filed)

Want:

    4294968295

#### Mechanism

Arithmetic over a radix pattern is not folded: the pattern is its bit pattern at its use's width
(DECISIONS.md, "Exact constant arithmetic"). An `f64` destination has no integer width, and the
bare pattern reads there as the number it spells (`let x: f64 = 0xFFFFFFFF` prints `4294967295`).
In an operation, though, the pattern computes at 32 bits and wraps before the conversion: `+ 1000`
and `* 2` wrap, while `- 1` and `0x80000000 + 1`, which stay inside 32 unsigned bits, do not. An
`f64` holds every one of these values exactly, as the decimal spellings show.

#### Ablation

| spelling | outcome |

| `0xFFFFFFFF - 1` at `f64` | prints `4294967294` |
| `0x80000000 + 1` at `f64` | prints `2147483649` |
| `f(0xFFFFFFFF + 1000)` for `f(x: f64)` | prints `999` |
