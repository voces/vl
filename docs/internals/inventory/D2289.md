### D2289 — a call to a local closure `w` is classified by a SIBLING function's nested `function w`

**closed 2026-09-24 — the witness prints `7`, `hi` · was check-clean invalid wasm, clause 1 · found by
the PL-033 fixture ([D2285](D2285.md)) running in company · filed 2026-09-23 against master `2d8341305`;
still open after #3111 and #3114 · fixtures `tests/cases/closures/sibling-nested-fn-name-vs-local-closure.vl`,
`tests/cases/closures/local-closure-shadows-top-level-fn.vl`,
`tests/cases/closures/out-of-scope-local-leaves-generic-fn-callable.vl`**

Repro:

    function a() {
      const w = () => { 7 }
      print(w() + 0)
    }
    a()
    function b() {
      function w() { "hi" }
      print(w())
    }
    b()
    // vl check: rc 0.  vl run: invalid module, `a` fails validation: expected (ref $type), found i32

#### Close

As predicted, a reader outside D1966's emission-only guard: `exprIsStrConcat` asks
`fnRetStringSid`, which resolves the callee through `fnIndexOfInScopeSid`. Its scope-chain walk
found no `w` declared on `a`'s chain and then returned the flat map's answer, `b`'s nested `w`,
a function no read in `a` can name. The same flat answer is wrong when it is a top-level
`function w` (review round 1). The walk now declines the flat answer, nested or top-level, when
a binding of `w` is IN SCOPE at the call: a parameter of any frame on the chain, or a block
`let` or loop variable whose scope covers the callee identifier (`chainShadowsAt`, positioned by
the callee node the `fnRet*Sid` readers now pass). Review round 2 showed a frame-wide test was
wrong: a closed block's `const w`, a later `const w` or an ended `for w` made a generic
`function w<T>` unresolvable there, and a generic has no fallback (9 cells, invalid wasm). The
parameter, reassigned-`let`, lambda-parameter and captured spellings run, and so do all nine
generic cells (`tests/cases/closures/out-of-scope-local-leaves-generic-fn-callable.vl`).

#### Mechanism

Both lifted bodies are right: `w@2` returns `i32`, `w@7` returns the string. The call
`w() + 0` in `a` is classified by the NAME `w`, which resolves to `b`'s nested function, so
the `+` lowers as a string concatenation over an `i32`. D1966 taught `fnIndexOfSid` that a
sibling frame's nested function is not the binding when the current body has a local of that
name, but only during emission (`emitCurFnIx >= 0`); the classifier that picks the `+`'s
operator may run outside that guard and resolve through the flat name map. Declaration order
does not matter (swapping `a` and `b` is still invalid). Which reader answers is a
prediction, not a finding.
