### D2788 — an `if` joining two tagged record literals is refused where a discriminated union is declared

**loud check reject · clause 2 · identical on master `781f68091` · filed 2026-09-27 from the #3209 review**

Repro:

    type Ci = { kind: "c", r: i32 }
    type Sq = { kind: "s", w: i32 }
    type Sh = Ci | Sq
    function g(sel: i32) {
      const s: Sh = if sel == 0 { { kind: "c", r: 1 } } else { { kind: "s", w: 2 } }
      if s is Ci { print(s.r) } else { print(s.w) }
    }
    g(0)
    g(1)
    // vl check: cannot assign {kind: string, r: i32} | {kind: string, w: i32} to 's' of type Sh

#### Mechanism

The design permits it: each arm alone is assignable to `Sh`, and `const s: Sh = { kind: "c",
r: 1 }` runs. The `if` is typed from its arms before the destination is consulted, and an
un-annotated record literal softens its literal field `"c"` to `string`, so the join is a union
of two records whose `kind` is `string`, which is no longer an arm of `Sh`. The fix is to check
each tail against the destination (contextual typing of a value `if`), as the arms' own
literals would be.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the `if` (`const s: Sh = { kind: "c", r: 1 }`) | runs | **yes** |
| the literal discriminant (`Sh` over arms of different field sets) | not graded | — |
| same field sets (`{ kind: "a", v: i32 } \| { kind: "b", v: string }`) | the same refusal, since D2731 against the joined `{kind: string, v: i32 \| string}` | no |

#### Grading list

The `match` spelling, and a `return` of the `if` from a function declared `: Sh`.
