### D3033 — a union whose arms share field names is refused at emit even when a literal discriminant tells them apart

**closed 2026-10-12 by lane CK (the D4056 build) · runs, prints `s` · was a loud emit reject · the `assignTags` face in the grading list runs too · pins: `tests/cases/unions/record-arms-same-field-literal-discriminant.vl` · found by the #3259 review · filed 2026-09-28**

Repro:

    type X = { t: "x", a: i32 }
    type Z = { t: "z", a: string }
    type U = X | Z
    const u: U = { t: "z", a: "s" }
    if u.t == "z" { print(u.a) }
    // vl check: rc 0.  vl run: emitProgram: union `U` cannot be discriminated — variants `X` and `Z` have the same field names but different field types

Want:

    s

#### Mechanism

`assignTags` (`emit_collect.vl`) keys each arm's tag on `variantSig`, its field-name signature,
and refuses a pair that shares one unless the pair is layout-equal or differs only in a literal
set of one storage (`variantLitDiscriminable`, `variantLitRepUnifiable`). Arms that differ in a
NON-discriminant field's type fall through to the refusal, although `t` tells them apart and the
checker accepts the narrowing. The refusal names a mechanism, not a design rule. The `assignTags`
face is the same pair with a literal SET in the discriminant (`t: "x" | "y"` beside `t: "z"`),
which reports `one tag while their literal discriminant at field \`a\` is laid out two ways`: it
names the non-discriminant field and calls itself a compiler bug.
