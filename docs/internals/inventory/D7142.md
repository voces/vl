### D7142 — a list of a generic-initialized, lambda-written `let` called at a type parameter of its own generic frame is invalid wasm

**now a loud emit reject · was check-clean invalid wasm · `vl check` rc 0 · clause 1 made loud, not run · pins: `tests/cases/closures/error-written-let-in-list-called-in-two-instances.vl` · found closing [D7103](D7103.md) · the same on master `8e787a973` · filed 2026-10-19 against master `8e787a973`**

Repro:

    function other<V>(v: V) { print("O"); print(v) }
    function g<T>(x: T) {
      let k = other
      k = (n) => { print("L"); print(n) }
      const fs = [k]
      fs[0](x)
    }
    g(3)
    g("s")
    // vl check: rc 0.  vl run: emitProgram: a function value's signature is not known at this call — the type it was given takes fewer parameters than the call passes
    // (on master `8e787a973`: the emitted module failed to validate inside `g`: type mismatch: expected structref, found i32)

Want:

    L
    3
    L
    s

#### Mechanism

Two, found by ablation and probed at the call's signature key.

1. With one instance (`g(3)` alone), the key the call through `fs[0]` takes is the list
   slot's, `>v`. The slot is named `() => void` after the pruned `other` stub. In the instance,
   `fs`'s element type is still open: the flow pins agreed at `T`, which is a type variable,
   and [D7103](D7103.md)'s close answers only a call type free of them. The call passes one
   argument to a key that takes none, so the emitter now refuses it at the call. That makes
   this row loud. It does not run.
2. With two instances and no list (`k(x)` directly), both instances share one lifted
   `$__lambda_0` at `i32`, so `g("s")` loads and then traps
   (`indirect call type mismatch`). That is [D7181](D7181.md).
