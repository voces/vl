### D2978 — a hole value at a nullable literal-union pin prints its atom id

**closed 2026-09-28 — the filed repro prints `b` · was check-clean silently wrong, clause 1, the same on master `8615a730d` · closed by reading the niche at the instance's pin: `exprNulLitUnion` and a new `nulLitAtomTexts` ask `holeOperandTyOf` (of the read, of an element's receiver, of a parameter's or local's declaration, of a named call's return), and `anyLitUnionUsed` counts a `(K | null)[]` element · filed 2026-09-28 against master `264fd86f1`**

Repro:

    type LS = "a" | "b"
    function k(v) {
      const l = [v]
      print(l[0])
    }
    const x: LS | null = "b"
    k(x)
    // vl check: rc 0.  vl run: prints `0` on master `4dc94bd23`

Want:

    b

#### Mechanism

A hole read typed at a `LS | null` pin is the `i32` atom niche (`-1` for null). Two things kept
`print` off its member-or-`null` chain. `exprNulLitUnion` read only the node's recorded type,
which is the hole's variable, so nothing claimed the read and `print` took the `i32` import. And
where something did claim it, the texts came from `nodeNulLitUnionMemberTexts`, which reads the
same recorded type, so the arm refused (D2807's message). A third ingredient hid the
element spelling: `anyLitUnionUsed` never counted a `(K | null)[]` element, so a program whose only
literal union sat there skipped every atom classifier.
