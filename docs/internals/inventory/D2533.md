### D2533 — a generic whose inferred return is `(V | null)[]` hands the checker a list it lets `+` read as `V`, and the instance is invalid wasm

**closed 2026-09-25 — the filed repro is now a loud check reject, `operator '+' is not defined for i32 | null and i32`, the refusal its non-generic twin makes · was check-clean invalid wasm · clause 1 · found by #3168's review · filed 2026-09-25 against master `15be0d1b8` · fixtures `tests/cases/generics/error-inferred-nullable-type-param-list-arith.vl`, `inferred-nullable-type-param-list.vl`**

Repro:

    function pair<V>(x: V) { [x, null] }
    print(pair(5)[1] + 1)

#### Mechanism

`pair`'s return is inferred from `[x, null]`, a `(V | null)[]`. At the call the checker reads
`pair(5)[1]` at a type `+` accepts with an `i32`, although the element is `i32 | null`; the
non-generic twin (`function pair(x: i32) { [x, null] }`) is refused with "operator '+' is not
defined for i32 | null and i32". The instance then feeds the boxed element to an `i32` add:
`expected (ref null $type), found (ref $type)`. The checker owes the non-generic refusal at the
instance.

The mechanism is the join, not the instance: `joinTys` collapses mutually assignable sides, and
`null` is assignable to a declared type parameter until an instance binds it, so `[x, null]`
typed `V[]` and every instance lost its `null`. `joinTyParamNull` now keeps `V | null` when one
side is a declared type parameter and the other `null` (a `?`-named inference hole is left
alone). `pair(5)[1] == null` then prints `true` where master refused it, and
`const q: (i32 | null)[] = pair(5)` runs where master refused it as an aliasing copy. At a
string or a record instance the un-annotated face is a loud emit reject (`bare null needs a
struct-typed context`, `a nullable-{w:i32} list element has no rep`) where master's was a loud
check reject; the annotated `(V | null)[]` face keeps D2525's boundary.
