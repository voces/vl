### D14824 — a generic handed to two lambda consumers runs only through the split plan: the tag decision on its set does not settle

**runs today and must keep running · the split plan copies the consumer per instance; without it (inc3 retires it) this is a loud emit reject, `monomorphize: `g` is called at two instances of the function handed to it in a call to `__lambda_0`` · inc3's lambda shape L1, fixture `tests/cases/functions/hole-call-let-lambda-at-two-instances.vl` · the named-consumer twin is closed by G2e (`elabKeyCallsHandSet`), which leaves lambda consumers out because the decision oscillates · filed 2026-11-01 against master `799f73cb`**

Repro:

    function id(a) { return a }
    let lap = (g) => {
      print(g(1) + 1); return g("s")
    }
    print(lap(id))
    let one = (g) => g(1) + 1
    print(one(id))

Want:

    2
    s
    2

#### Mechanism

Without the split plan, `lap`'s two-type call through `g` runs only when `id`'s one-member set is
tagged, so `lap` takes an id and calls each instance directly. `one(id)` binds its parameter to
one instance, which makes the set partial in `elabMintFacts`. Exempting that pin as G2e does for
a named consumer makes the decision oscillate: round 1 tags `{id}`, round 2 refuses it at
`ftCtxOk` on `one(id)`, and the run ends in "the tag decision after the elaboration did not
settle". The refusal in round 2 sits beside how a lambda consumer read as a value is instanced.
