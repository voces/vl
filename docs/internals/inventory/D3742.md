### D3742 — a store between two open `[]` bindings records a hole link, and the uninferred flush refuses the side the link would have pinned

**loud check reject · clause 2 (graded CAPABILITY, not design: a use pins the binding through the store) · the `global_assign` un-annotated cell of every `lk-empty-*` matrix · lane UA · filed 2026-10-06 against master `42c4d4c10`**

Repro:

    let a = []
    let b = []
    b = a
    b.push(4)
    print(a.length)
    // vl check: cannot infer a type for 'a' — an empty array literal has no element type
    // until it is used; use it where its type is known, or annotate the binding

#### Mechanism

`b = a` between two open list rows cannot pin either, so `constrainEmptyD` records the pair
(`noteHoleLink`, D1470) and leaves both open. `b.push(4)` then pins `b`'s row to `i32`. The
link is only ever consulted for an `__array_new_default__` row (`arrDefHoleToI32` →
`arrDefPinHoleElem` → `resolveHoleLinks`); `flushUninferred` asks `unresolvedHole` of `a`'s own
row, finds it open, and refuses. The two rows must hold one element type at run time (they
alias one list object after the store), and the program fixes that type by a use, which is
what D1470's diagnostic asks for, so the refusal is owed to the missing propagation, not to
the design. This is the shape the reviewer's `global_assign` cell has
(`let __a = []; let __b = []; __b = __a; const v = __b; v.push(4)`); the
binding-initialiser spelling (`const b = a`) shares one row and already runs.

Recommendation, not applied in this lane (brief: grade, do not fix): run `resolveHoleLinks()`
at the head of `flushUninferred`, and make the propagation refuse a link whose two rows were
pinned to different elements (`a` pushed a string, `b` an `i32`) at the store, in the store's
words. No owner ruling is needed: the literal-binding ruling (B′) types a `let` by its
deliveries and stores, and D1470 already treats a store link as binding the two rows.
