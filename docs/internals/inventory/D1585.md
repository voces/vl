### D1585 — an exported user `type` named after a built-in type DODGED the reserved-name refusal, because the merge renames the declaration before the screen reads it

DECLARATION, in every module, exported or not, and `u8` joins the reserved set · was `runs` at
every module spelling while the single-file twin was already refused · a deliberate
`runs → not-runs`, priced in the grid below and confined to programs that declare a type named
after a built-in type · distilled corpus 0 classes moved, 0 `runs → not-runs`, 0 `→ silent`
(no corpus cell declares one) · filed 2026-09-04 against master `4df75852`**

Repro (before: prints `7`; now: refused at `lib.vl:1:13`):

    // file: lib.vl
    export type f64 = { x: i32 }

    // file: main.vl
    import { f64 } from "./lib"

    const a: f64 = { x: 7 }
    print(a.x)

    // NOW: lib.vl:1:13: a `type` declaration may not take the built-in type name `f64`
    //      — every annotation resolves that name to the primitive, so the declaration
    //      can never be referred to; rename it

#### Mechanism

**THE MERGE RENAMES THE DECLARATION BEFORE THE SCREEN READS IT — the module BOUNDARY was
never the ingredient.** `checkProgram`'s pass-0 reserved-name screen does walk the
dependency's `type` declaration: the merge concatenates every module's statements into ONE
`Program` and hands that to the checker. But `modRwStmt`'s `TypeDecl` arm has already run
`n.tdName = modTypeRenamed(n.tdName)`, so the name the screen tests is `f64$m1`, and
`primTyOfName("f64$m1")` is `-1`. The entry module's own declaration renames to `f64$m0` and
dodges identically the moment an `import` puts the program into module mode — a single-file
`type string` is refused, and the same line in the same entry file is not.

**AND THE PREDICATE HAD TWO COPIES THAT DISAGREED.** The screen asked `primTyOfName`, which
deliberately withholds `u8` (the storage type is reachable only as an array element), while
the merge's own copy of the same question — `driver.modNameIsBuiltinTy`, added by D1571 —
included it. So `type u8 = { x: i32 }` was accepted in a SINGLE file too, which is why this
row's close is not only about modules. `typecheck.isBuiltinTyName` is now the one home and
both readers ask it.

The fix is two functions and one call site: `modCheckBuiltinTyDecls` runs in `modCompile`'s
existing pre-rename per-module window (beside `modCheckDupBindings`, step 2b) and raises
through `tErrBuiltinTyDecl`, which the single-file screen also calls — so message, channel
(`T.diags`, a type error at both faces) and anchor are shared rather than duplicated. The
anchor moved to the declaration's NAME token in both faces: the `nodeToks` anchor is a struct
alias's closing brace, a line or more below the name the message tells the reader to rename.
The merge's rename machinery is UNTOUCHED, so `modBuiltinTyTargets` still serves the one
declaration this rule does not reach — a GENERIC alias (`type u8<T>`), whose declared name is
`u8<T>`, a name no annotation resolves on its own.
