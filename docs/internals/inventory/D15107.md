### D15107 — mono builds separate instances for one elaboration type at two record representations, which the elaboration key does not carry

**runs today and must keep running · structural: two mono instances record ONE elaboration key, so a reader mapping a key back to its instance is ambiguous (per-instance identity, `docs/internals/per-instance-identity-2026-11.md`) · measured by a probe in `elabSlotNote` over the 1,519 `@run` files declaring a type parameter or a nested function: 78 files note one key at two slots, 33 by this mechanism and 45 by the other row's · filed 2026-11-03 against master `de3bfa8b8`**

Repro:

    type C = { r: i32 }
    type S = { s: i32 }
    type U = C | S
    type D = { r: i32 }
    type V = D | S
    function ap<T>(x: T): T { x }
    const c: C = { r: 1 }
    const d: D = { r: 2 }
    print(ap(c).r)
    print(ap(d).r)

Want:

    1
    2

#### Mechanism

Both calls elaborate `ap` at one key (`T={r:i32,}`); `C` and `D` are members of different unions, so they take different representations, and mono keys `ap` by the pin spelling of each (`C`, `D`). The same split occurs at a nullable field, a `Set` against its boolean map, a closure against a named function type spelling, a list rep, and an enclosing pin prefix (45 files).

#### What the record classes wait on

A record's representation is decided by `collectS`, which runs after the elaboration (`elabRun`
precedes the emit passes), so the elaboration key cannot name it. The decision has four inputs:

1. the record's shape: field names and types, in `fieldNameOrder`'s order (pure check);
2. its union memberships, from the variant tables `collectU` builds (derived from checked declarations);
3. each field's type code (`fieldTypeCode`, `internArmMapSlotsNamedBy`), a function of the field's
   type computed against the emitter's interned arms and map slots;
4. `unifyMixedLitRepArms` (D1050), which re-lays a mixed-spelling pair after both tables are built.

1 and 2 move ahead of `elabRun` as they are; 3 moves if a field's code is read from its type
alone; 4 depends on the order the tables were built, the order D15098 also hits. One up-front
pass from checked types, run before `elabRun`, produces all four: it registers every declared
record's row before any field is coded (D15098) and names each record's representation before the
elaboration keys on it. Classes A and the two nominal G files read it.

The delivered arm alone (class B) needs none of this: it is a type the check gives the argument,
keyed only where the body tests a type variable, as mono's composite path already keys it.

The composite-pin files of classes B and G, the `#lit` alias file and the nullable literal union closed without a change to the elaboration key: in each, the elaboration already held one instance, and mono split it by deriving a fact of its own that disagreed with one the elaboration had. A union pin's exact type and literal-union mark repeated what the key's bindings fix (D15109, #6085); a literal argument's spelling named its base where the substituted union holds its type (#6093); a type-testing instance was demanded at its pin's rep binding before its exact one (#6077); and a record literal pinned at its own type where the elaboration stamps it at the parameter's record (D14140). The pattern to look for next is a mono derivation where an elaboration fact exists, before adding an entry to the key.
