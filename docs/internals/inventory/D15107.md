### D15107 — mono builds separate instances for one elaboration type at two record representations, which the elaboration key does not carry

**runs today and must keep running · structural: two mono instances record ONE elaboration key, so a reader mapping a key back to its instance is ambiguous (per-instance identity, `docs/internals/per-instance-identity-2026-11.md`) · measured by a probe in `elabSlotNote` over the 1,519 `@run` files declaring a type parameter or a nested function: 78 files note one key at two slots, 33 by this mechanism and 45 by the other row's · filed 2026-11-03 against master `de3bfa8b8`**

Repro:

    type C = { r: i32 }
    type S = { s: i32 }
    type U = C | S
    type D = { r: i32 }
    type V = D | S
    function ap<T>(x: T): T { x }
    const c: C = { r: 1 }
    const d: D = { r: 2 }
    print(ap(c).r)
    print(ap(d).r)

Want:

    1
    2

#### Mechanism

Both calls elaborate `ap` at one key (`T={r:i32,}`); `C` and `D` are members of different unions, so they take different representations, and mono keys `ap` by the pin spelling of each (`C`, `D`). The same split occurs at a nullable field, a `Set` against its boolean map, a closure against a named function type spelling, a list rep, and an enclosing pin prefix (45 files).

| --- | --- | --- |
