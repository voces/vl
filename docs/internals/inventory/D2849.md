### D2849 — a list literal around a generic call, inside a generic body, loses its type when the call is cloned per instance

**closed as `runs` · the repro prints `s` · `monoCloneGenericCalls` re-made the literal around each cloned generic call with no recorded type, so `arrLitIsRef` read no element and built the `i32` list around a list; a re-made list literal now keeps its template's type, which the pin substitutes · was check-clean invalid wasm · clause 1 · reserved by the coordinator from the #3214 round-3 grid (`arr_coal_*`, the `??` is scenery) · the same on master `1df19732b` · filed 2026-09-27 against master `1df19732b` · fixture `tests/cases/generics/list-literal-around-generic-call-in-generic-body.vl`**

Repro:

    function pc<T>(xs: T[]) { xs }
    function k<T>(t: T) {
      const xs = [pc([t])]
      print(xs[0][0])
      0
    }
    k("s")
    // was: vl check rc 0, then invalid module inside `k` (expected i32, found (ref $type))

Want:

    s

#### Mechanism

Each instance of a generic body gets its own copy of every call to a generic
(`monoCloneGenericCalls`, emit_mono.vl), and every node on the path to the call is re-made. The
re-made nodes had no entry in the checker's type table. A list literal's rep is read off its
recorded type (`arrLitNestedElemName`), so the literal holding the cloned call fell to the
`i32` list and stored the inner list's ref in it. Only the list literal takes the template's
type: a cloned call is typed by its instance, and giving it the template's type moved 18 cells of
the round-3 grid from loud to invalid (`idv(p(t, c))`). A literal whose call reaches a `??` over a
type parameter's list with a boolean default at a number pin, or a number default at a boolean
pin, is refused instead (`monoLitReachesPinDefaultClash`): built, it would print
[D2816](D2816.md)'s value.
