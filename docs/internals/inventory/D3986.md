### D3986 — a hole lambda written to a `let` of a generic through a binding of it is not re-checked at the call

**closed · now a loud check reject, `operator '+' is not defined for boolean and i32` · was check-clean silently wrong · clause 1 · the error channel reports the lambda's instance at `boolean`, and the direct spelling `f(true)` is refused with the same message, so the refusal is the design's · found closing D3968 (`h4`) · filed 2026-10-10 against master `56f77d80f`**

Repro:

    function inner<U>(u: U) { print("I"); print(u) }
    function main() {
      let k = inner
      const f = (x) => { print(x + 1) }
      k = f
      k(true)
    }
    main()
    // vl check: operator '+' is not defined for boolean and i32

#### Mechanism

Not located. D3968 re-asks, at each call through such a binding, the body constraints of a lambda
written to it in place. A lambda written through a binding (`const f = …; k = f`) shares its
holes with every other use of `f`, so re-asking the enclosing body's constraints over them at the
call's types refused valid programs (`gen4/r053`); that spelling is left unchecked. The emitter
reads `x + 1` at the hole's `boolean` binding as `substHoleTyReal` answers it, the operand
itself, so the call printed `true` (it printed `2` before L2's binary-operator hole read); it prints
`2` again since the hole instance's elaboration types a hole operand. The checker still owes
the reject.
