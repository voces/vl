Repro:

    function f(): string {
      let c: (i32 | f64)[] = [1, 2.5]
      const k = () => { c = [3.5, 4] }
      k()
      "\{c.length}"
    }
    print(f())
    // vl check: rc 0.  vl run before the close: invalid module inside `k`: type mismatch: expected (ref null $type), found (ref $type)

#### Mechanism

An assignment is an expression yielding its right side, and the checker typed it at the right
side's own type: `f64[]` for `[3.5, 4]`. But the store builds that literal at the place's type,
`(i32 | f64)[]`, so no value of the assignment's recorded type exists. Every position that uses
the value disagreed with the store. A closure whose tail writes a boxed cell yields through
`const t = e; v = t; t` ([D2285](D2285.md)), which built `t` as an `f64[]` and stored it into
the `(i32 | f64)[]` cell. The same write used as a value, `const r = (c = [3.5, 4])`, re-read
the target under the `f64[]` type. The checker now types an accepted assignment at the place's
type (`asgYieldsPlaceTy`, `typecheck.vl`) when a value of the right side's type could reach the
place only through an adapter, so the right side is a literal built there, or when the two are
one type in another member order. The list classifiers read such an assignment's rep off its
target.
