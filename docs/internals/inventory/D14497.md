### D14497 — a read of an open list element records its type before a later store pins the element, and keeps it after

**check-clean invalid wasm · also a loud emit reject (`??`) and a loud check reject (`needs a type annotation`) at two sibling spellings · blocks the operand slice of architecture-target §3.1: the operator's width read off the operands' recorded types traps the compiler on two `tests/cases` files that run today · filed 2026-10-27 against master `67905160e`**

Repro:

    function g() {
      let a = __array_new_default__(3)
      const y = a[0] + 1
      a[0] = 1.5
      print(y / 4)
      print(a[0] + 1)
    }
    g()
    // vl check: rc 0.  vl run: inside `g`, type mismatch: expected i32, found f64

Want:

    0.25
    2.5

#### Mechanism

A list whose element is still open (`[]`, `__array_new_default__`) has its element decided by
the first store or `push` in source order. That store pins the element in place, writing the
row's `aElem` at one of the eleven `.aElem = ` sites in `check_*.vl` (`idxStoreHolePin`,
`asgReadElemPin`, `arrDefPinHoleElem`, the push pins in `check_member_call.vl`, …). A read
checked earlier has already banked its type in `nodeTyIx`. That is either `-1`, or the `i32`
default `arrDefOperandElemPeek` peeks for an operator operand, and a dependent node (the `+`,
the `const y`) is typed from it. The pin updates the row but none of those entries, so each one
is a second producer of the element's type, and a stale one. Two sites already patch their own
read after the fact (`asgReadElemPin` and `arrDefOperandElemPeek`, each through `nodeTySet`).
Every other read and its dependents stay stale. Today's emitter mostly re-derives a
number operator's width from the list's current row (`exprIsF64` and friends), so most of these
programs run, and the ones that do not are the reads whose stale type reaches a binding or a
coalesce.

#### Grading list

The two sibling spellings in the ablation table (the `??` read and the un-annotated `const x =
s[0]`). The three `tests/cases` files named in the last row, on the operand slice. The ordering
controls of `tests/cases/intrinsics/array-new-default-operand-hole.vl`, where a later store
still decides the element and an earlier one is untouched.
