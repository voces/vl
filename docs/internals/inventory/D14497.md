### D14497 — a read of an open list element records its type before a later store pins the element, and keeps it after

**closed · now a loud check reject, `'y' takes its type from an element of 'a' whose type is not decided yet; annotate 'a' or 'y'` · DESIGN (coordinator ruling 2026-10-27, "later-decided element binding"): a binding commits a type, and an element that a later statement decides cannot be committed earlier without a dependency walk, so binding such a read without an annotation is refused at check time; a read consumed in place (an operator, a unary, `??`, a store into a declared place) waits for the pin and runs · was check-clean invalid wasm, with a loud emit reject (`??`) and a loud check reject (`needs a type annotation`) at two sibling spellings, filed 2026-10-27 against master `67905160e` · closed by one producer: open-element reads and the operators over them are banked in check order and typed once, after the last pin, by `resolveOpenElemReads` (check_operators.vl); the two `nodeTySet` patches and `arrDefOperandElemPeek` are deleted · the in-place spellings that now run are pinned by D14498 (`??`) and D14499 (a store into a declared place)**

#### Mechanism

A list whose element is still open (`[]`, `__array_new_default__`) has its element decided by
the first store or `push` in source order. That store pins the element in place, writing the
row's `aElem` at one of the eleven `.aElem = ` sites in `check_*.vl` (`idxStoreHolePin`,
`asgReadElemPin`, `arrDefPinHoleElem`, the push pins in `check_member_call.vl`, …). A read
checked earlier has already banked its type in `nodeTyIx`. That is either `-1`, or the `i32`
default `arrDefOperandElemPeek` peeks for an operator operand, and a dependent node (the `+`,
the `const y`) is typed from it. The pin updates the row but none of those entries, so each one
is a second producer of the element's type, and a stale one. Two sites already patch their own
read after the fact (`asgReadElemPin` and `arrDefOperandElemPeek`, each through `nodeTySet`).
Every other read and its dependents stay stale. Today's emitter mostly re-derives a
number operator's width from the list's current row (`exprIsF64` and friends), so most of these
programs run, and the ones that do not are the reads whose stale type reaches a binding or a
coalesce.

#### Grading list

The two sibling spellings in the ablation table (the `??` read and the un-annotated `const x =
s[0]`). The three `tests/cases` files named in the last row, on the operand slice. The ordering
controls of `tests/cases/intrinsics/array-new-default-operand-hole.vl`, where a later store
still decides the element and an earlier one is untouched.

#### Close

Graded on the closing build: the repro and `const x = s[0]` read before `s.push(3)` both refuse
with the message above, from the one site in `checkLetDeclNodeIn`. The three `tests/cases` files
and `storeAfter` run. `s[0] ?? 7` read before the push runs, printing `2.5` (D14498). A store
`y = a[0]` or `y = s[0]` into a declared `f64` before the pin, which trapped the compiler on
`67905160e`, runs (D14499). Nested operators and a unary over the read (`(a[0] + 1) * 2`,
`-a[1]`) run.

The ruling covers bindings. An un-annotated function that returns a later-decided read is a
second place a type is committed, and it is not routed to this refusal: `function h() { return
a[0] + 1 }` called after `a[0] = 1.5` reads `h` as returning `void` (`print expects a value, got
void`). On `67905160e` that spelling ran by accident: the peek typed the return `i32` and the
emitter re-derived `f64`, and the same function bound through `const r = h()` was check-clean
invalid wasm.
