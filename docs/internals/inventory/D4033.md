### D4033 — a type-bound member call at a type-parameter receiver is refused at each instance

**loud check reject · clause 2 · found in the #3538 review (lane DV, D4030) · filed 2026-10-11 against master `98a4ed71b`**

Repro:

    // file: c.vl
    export type Circle = { r: i32 }
    export function grow(self: Circle, o: Circle): Circle { { r: self.r + o.r } }
    export function mk(r: i32): Circle { { r: r } }
    // file: entry.vl
    import { mk } from "./c"
    function f<T>(x: T, y: T): T { x.grow(y) }
    print(f(mk(2), mk(3)).r)
    // vl check: no field 'grow' on Circle (the body of `f` at the call's argument types)

Want:

    5

#### Mechanism

Not yet located. `grow` is not imported, so `x.grow` can only resolve type-bound, through the
module that declares the receiver's type (`docs/internals/type-bound-ufcs-design.md`). That
resolution runs for a concrete receiver but not when the body is re-checked at an instance's
argument types, which falls through to the field lookup and its message. The design doc does
not exclude a type-parameter receiver, and the same call at the concrete type runs, so this
is a capability gap, not a design rule.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the type parameter (`f(x: Circle, y: Circle): Circle`) | runs, prints 5 | **yes** |
| type-bound resolution (`import { mk, grow }`) | runs, prints 5 | **yes** |
| the member call (`x.r` in a generic body) | runs | **yes** |

#### Grading list

The same body over a second type whose module also declares `grow` (two instances, two
modules), and the element receiver `xs[0].grow(xs[1])` in `g<T>(xs: T[])`.
