### D9370 — records holding un-annotated functions of different results, written into a map or pushed onto a list, or read back through a binding, are not judged at check, where the same pair read in place from a list literal is

**loud emit reject · `vl check` rc 0 · `unsupported map value type` · clause 2 · found closing [D9311](D9311.md) · present on master `6bd8e96aa` · filed 2026-10-21 against master `6bd8e96aa`**

Repro:

    function inc0(a) { return a + 1 }
    function half(a) { return a / 2.0 }
    const m = Map()
    m.set("a", { f: inc0 })
    m.set("b", { f: half })
    const r = m.get("b")
    if r != null { print(r.f(3)) }
    // vl check rc 0.  vl run: emit error: emitProgram: unsupported map value type (no rep for a union-member struct, ...)

#### Mechanism

Partly traced. `const l = [{ f: inc0 }, { f: half }]` read as `l[1].f(3)` is refused by
`vl check` (`cannot store 'half' in 'l[].f': … must return one type`), because the read's
slot path `l[].f` is followed from the call. A call through a record bound first
(`const r = …; r.f(3)`) or through `?.` does not reach the slot's writes, so the
disagreement reaches the emitter. The list spellings fail the same way, with
`cannot take the generic function … as a value`: the literal list read through a binding,
and a record pushed onto the list (`l.push({ f: half })`).

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the `inc0` write | runs, `1.5` | **yes** |
| the record (`m.set("a", inc0)`, `x(3)`) | loud check reject ([D9311](D9311.md)) | **yes** |
| the map (`const l = [{ f: inc0 }, { f: half }]`, `const r = l[1]`, `r.f(3)`) | same family, `cannot take the generic function` | no |
| the binding, on a list literal (`l[1].f(3)`) | loud check reject | **yes** |

#### Grading list

The map's `?.` read (`print(m["b"]?.f(3) ?? 0)`), the index write (`m["a"] = { f: inc0 }`),
and the pushed list (`const l = [{ f: inc0 }]`, `l.push({ f: half })`, `print(l[1].f(3))`).
