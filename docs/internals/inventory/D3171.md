### D3171 — a string literal passed beside a literal-union function value to an un-annotated function reaches the function's `K` parameter as a string

**now a loud check reject · the argument handed to a hole callee is recorded as a demand on the callee's parameter (`HD_PARAM`) and re-asked at each call that pins it; a literal written as that argument is held to the parameter in its context, as a direct call holds it, and a hole-bound argument at its base type · fixtures `tests/cases/generics/error-hole-callee-argument-at-pin.vl`, `tests/cases/generics/hole-callee-literal-argument-at-pin.vl` · was check-clean invalid wasm · clause 1 closed; the literal-through-a-binding witness needs a ruling · filed 2026-09-29 against master `a0b9acaf8`**

Repro:

    type K = "a" | "b"
    function H(h, v) {
      return h(v)
    }
    print(H((x: K) => x, "b"))
    // vl check: rc 0.  vl run: invalid module inside `H`: type mismatch: expected i32, found
    // (ref $type)

Want:

    b

#### Mechanism

Not localised past the ablation. The hole `v` is pinned at the literal's own type, a string ref,
while `h`'s parameter is the `K` atom, so `h(v)` inside the instance hands the string to an `i32`
parameter. Nothing converts the member to its atom where the two holes meet.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `const k: K = "b"`, then `H((x: K) => x, k)` | runs | **yes** (the literal argument) |
| `function H<V>(h: (V) => V, v: V)` | runs | **yes** (the holes) |
| `function H<V>(h, v: V)`, only `h` a hole | the same invalid module | no |
| `(x: string) => x` | runs | **yes** (the literal union) |
| `(x: K) => x == "b"`, a `boolean` result | the same invalid module | no |

#### Grading list

The witness, the `K | null` parameter twin, and the instance passers of the `fnparam` grid
(`F<Z, V>(g: Z, v: V)` and `F(g, v)` forwarding to `H`).

#### Close and the open question

`checkCallNode`'s hole-callee arm checked each argument and minted a return hole, and recorded
nothing linking the argument to the callee's parameter, so `H((x: i32) => x + 1, "s")` was
check-clean invalid wasm and `H((x: K) => x, true)` printed `b`. Each argument is now a deferred
demand on a new derivation, `HD_PARAM` (parameter `j` of calling the hole), which the pin
resolves to the pinned function's parameter. A literal written as the argument (`h("a")`,
`h(1)`, `h({ d: "n" })`) is held at its literal type (`holeCalleeArgTy`), which is the
parameter-context rule the direct call applies; a first round held it at its base type and
refused programs the direct spelling runs. On the HF grid (224 cells, eight parameter types
across seven argument spellings and four call shapes) 56 cells that ran all printed a wrong value
and now refuse, 76 invalid and 3 trapping ones refuse, and no correct run is lost. Over the
#3287 review's 1,155-cell `hf` set every refusal but two shapes is one the direct twin makes: the
witness below, and `H(g-taking, (y) => y * 10)`, which master refuses too.

The witness itself now refuses: `v` binds at the literal's base type (`string`), as every hole
does, and a `string` does not fit `K`. **Ruling asked:** should a literal argument to an
independent hole be typed by a demand only the call discovers (then `v` binds `K`, as
`H<V>(h: (V) => V, v: V)` binds it, and `"b"` runs), or stay at its base type, so the witness is a
design refusal? Recommendation: keep the refusal. It matches `const s = "b"; H(f, s)`, which must
refuse, and the shared-parameter spelling that means "the same type" is one annotation away.
