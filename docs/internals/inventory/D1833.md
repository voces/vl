### D1833 — a payload clause after a NON-TYPE match pattern refuses as the arrow's token cascade, not as one sentence naming the rule

**CLOSED 2026-09-07 — now a loud check reject, raised at the PARSE stage so `vl check` reports it as `(parse error)`: ONE sentence, anchored at the `{`, echoing the pattern as the source spells it, after which the clause is consumed so the arm still parses. Was: 10 diagnostics for `"a"{}`, `"a"{x}`, `0{}` and `-1{x}`, 7 for `_{}` and 13 for an or-arm carrying two of them, none of which said a clause needs a variant type. FILED COUNTS CORRECTED — "2 for `"a"{}`, 3 for `_{}`" was a `head -8` truncation of the CLI's four-line diagnostic blocks read as the whole output, not a measurement**

A payload clause reads a VARIANT'S fields, so it is meaningful only after a type pattern. After a
string literal, an integer literal or `_` the arm is already committed to `=>`, so the `{` used to
be reported as a missing `=` and then a missing `>` — the arrow's words about the wrong token —
and the recovery then lost the rest of the arm. The author was told to insert `=` where a `{` had
to be DELETED. B21.2's own refusals name their rule; this was the one clause position that did not.

Repro:

    type K = "a" | "b"
    function g(k: K): i32 {
      match k {
        "a"{} => 1
        _ => 2
      }
    }
    print(g("b"))
    // vl check: rc 1 (parse error), ONE diagnostic
    //   a payload clause binds a variant's fields, so it cannot follow a literal / `_` /
    //   an integer pattern — write `"a" =>`   at 4:8, the `{`

#### Mechanism

`parseMatchPattern`'s literal and `_` arms sit BEFORE `matchPatStartsType()` and return their
pattern node directly; only the type-atom arm called `parseMatchPayload`. A `{` after a non-type
pattern was therefore left for the arrow's `expect`s. The fix gives those four arms
`refuseMatchPayloadHere(pat)` — one sentence at the `{`, then `skipBracedRun()` consumes the
balanced clause so the arrow reads `=>` — and NOT the ladder's fall-through arm, where the cursor
has advanced one token and need not be at a clause at all: skipping there turned `({x}) => 1` from
4 diagnostics into 11, which is how that arm earned its exclusion.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the clause (`"a" => 1`) | runs, prints 2 | **yes — the clause is the subject** |
| the non-type pattern (`A{} => 1` over a struct union) | B21.2's own sentence, unchanged | **yes — the pattern kind is the second ingredient** |
| the clause's emptiness (`"a"{x}`) | was 10 diagnostics, now the same one sentence | no |
| `"a"` for `_` | was 7, now one sentence naming `_` | no |
| `"a"` for `0` / `-1` | was 10, now one sentence naming `0` / `-1` | no |

#### Grading list

All four pattern kinds with an empty AND a non-empty clause, the or-arm that carries one on each
member (two sentences, one per member), and the three refusals that must not move — B21.2's
`` `Stop{}` ``, the nested `` `p: {}` ``, and the nested TYPE pattern. The corpus file is
`tests/cases/match/payload-binding-non-type-pattern-errors.vl`, whose `@error-at` directives pin
the anchor COLUMN, and its controls live in `payload-binding-nest-parse-errors.vl`.
