### D1833 — a payload clause after a NON-TYPE match pattern refuses as a token cascade, not as one sentence naming the rule

**loud check reject (parse error) · found 2026-09-07 while banning the empty top-level clause (B21.2) · pre-existing, identical under the merge-base seed and the B21.2 branch · 2 diagnostics for `"a"{}`, 3 for `_{}`, 10 for `0{}` and 10 for `"a"{x}` — none of which says a clause needs a variant type**

A payload clause is only meaningful after a TYPE pattern: it reads that variant's fields. After a
string-literal pattern, an integer-literal pattern or `_`, the parser never reaches
`parseMatchPayload` at all — the arm has already committed to `=>`, so the `{` is reported as a
missing `=` and then a missing `>`, and from `0{}` onward the arrow's recovery loses the rest of
the arm and the cascade runs to end of input. Every message is true of the token stream and none
is about the rule the author broke: the author is told to insert `=` where a `{` must be DELETED.
B21.2's own refusals (`` `Stop{}` binds nothing — write `Stop` `` and the nested `` `p: {}` ``
twin) each name their rule; this is the one clause position that does not.

Repro:

    type K = "a" | "b"
    function g(k: K): i32 {
      match k {
        "a"{} => 1
        _ => 2
      }
    }
    print(g("b"))
    // vl check: rc 1 (parse error)
    //   expected `=` but found `{`
    //   expected `>` but found `{`

#### Mechanism

The literal and `_` arms of the match-pattern ladder return their pattern node directly and sit
BEFORE `matchPatStartsType()`; only the type-atom arm calls `parseMatchPayload`. So a `{` after a
non-type pattern is left for the arrow's `expect`s, which report what THEY wanted rather than
what the `{` is. Nothing tests for a clause in that position, which is why the message set is the
arrow's and not the clause's — and why the cascade's length depends on whether the clause body
happens to re-sync the arrow (`{}` does, `{x}` does not).

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the clause (`"a" => 1`) | runs, prints 2 | **yes — the clause is the subject** |
| the non-type pattern (`A{} => 1` over a struct union) | one sentence, `` `A{}` binds nothing — write `A` `` | **yes — the pattern kind is the second ingredient** |
| the clause's emptiness (`"a"{x} => 1`) | same class of cascade, 10 diagnostics | no |
| the `"a"` spelling, for `_` | 3 diagnostics, same shape | no |
| the `"a"` spelling, for `0` | 10 diagnostics, same shape | no |

#### Grading list

The close must re-grade all three non-type pattern spellings (`"a"{}`, `0{}`, `_{}`) with an
empty AND a non-empty clause after each, and must leave B21.2's two sentences and the nested
clause's sentence unchanged — `tests/cases/match/payload-binding-nest-parse-errors.vl` is the
file that holds all three.
