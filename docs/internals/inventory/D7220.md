### D7220 — a one-literal record field and the same field at a one-literal alias are one type, but rep apart: a `string` and an atom

**closed 2026-10-19 by lane L6 · runs, prints `circle` · was check-clean invalid wasm · clause 1 · a string-literal record field reps as its one-member set's interned atom whichever way it is spelled, so both spellings share one struct row (owner ruling `one-literal-union-rep`); the `utkStructText` guard stays, since the union box site still resolves a member by name ([D7340](D7340.md) is the list position) · pin: `tests/cases/structs/one-literal-alias-field-one-record.vl` · filed 2026-10-19 against master `ff910c059`**

Repro:

    type KC = "circle"
    type C = { kind: "circle", r: f64 }
    type Ca = { kind: KC, r: f64 }
    const a: C = { kind: "circle", r: 1.0 }
    const b: Ca = a
    print(b.kind)
    // vl check: rc 0 (it hints that `b` is inferred as `C`).  vl run: invalid module,
    // expected (ref null $1), found (ref $0); $1 is `Ca`, struct {mut i32, mut f64};
    // $0 is `C`, struct {mut (ref $5), mut f64}

#### Mechanism

The checker reads `KC` as the literal `"circle"`, so `C` and `Ca` are one record type
(D3870) and the delivery needs no copy. The emitter gives them two struct rows: a field
spelled with a named literal union reps as an interned `i32` atom, and a field spelled
with one inline literal reps as a `string`. The delivery then hands one struct to a slot
typed by the other. The same split is why lane L6's type-keyed union lookup has to check
`utkStructText` before `Ca | Ra` may share `C | R`'s row, and why `mintInlineUnion` cannot
key by type yet. Fix direction: decide a record field's rep from its canonical type, so
that one record type has one struct row. The owner's `one-literal-union-rep` ruling
(2026-10-13) picks the atom: every string literal union reps as an interned atom, inline or
named, so the inline field moves to the atom.

#### The close

A bare string literal at a record field is its one-member set, so it reps as the interned
atom like `KC`. The canon keys a `TyLit` field as that set on both walks (`repFieldLitAsSet`
in `repKeyGo` and `hcCanonObjId`), the emitted field name keeps the literal rather than
softening it to `string` (`canonEmitNameTs`, `tyNameObj`), and the field code, element name
and map-value adoption read a lone literal as an atom (`fieldCodeOfSpelling`,
`fieldRecElemName`, `shapeFieldElemName`, `shapeFieldTypeCompatK`). A value read off the field widens to
`string` through the existing named-union conversion wherever a string is owed, which the
`one-literal-field-widen-to-string` and `one-literal-field-value` capability matrices grade
at every position.

The first attempt (#4185) took the string direction, and the soften could only be applied
at a field. At the union's own canon arm (`repKeyUnion`) it keyed every `KC`-typed value,
param, element and union member as `string`, while the emitter kept repping those values as
the i32 atom (`vtKindOfType` answers `i32` for a named literal union). Two reps then shared
one canon key, so one struct row and one heap type, and five oracle cases failed on the
mismatch. The atom direction has no such split: both spellings already rep as the atom
everywhere except the inline field, which is the one thing it moves.

The `utkStructText` guard stays. The union box site resolves a member by NAME against the
adopted row, so a row shared by type is safe only where the member names agree.
`mintInlineUnion` stays name-keyed for the same reason. Both wait for the type to reach the
box site.
