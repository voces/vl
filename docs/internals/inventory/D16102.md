### D16102 — a field write narrows the place to non-null even when its right-hand side replaced the receiver

**closed · runs, prints `9` `0` · was loads then traps, clause 1: `vl check` reported 0 errors and the run trapped `a null value was used where a non-null one was required` · fixed 2026-11-14: a write whose right-hand side calls something that may write the place or a receiver above it narrows nothing · found grading [D16019](D16019.md) · filed 2026-11-14 against master `84b0f334c`**

Repro:

    type A = { x: i32 }
    type H = { p: A | null }
    let h2: H = { p: null }
    const keep = h2
    function sw(): A { h2 = { p: null }; return { x: 9 } }
    h2.p = sw()
    print(keep.p?.x ?? 0)
    print(h2.p?.x ?? 0)

Want:

    9
    0

#### Mechanism

The write `h2.p = sw()` stores into the object `h2` named before `sw()` ran, which is `keep`'s.
After it, a read of `h2.p` is narrowed to the non-null value written, but `sw()` rebound `h2` to a
record whose `p` is `null`. The narrowing assumes the receiver still names the object written, and
the null check the `?.` would make is dropped.

#### Closed (2026-11-14)

`retireNarrowingsForWrite` (`compiler/check_narrow_flow.vl`) pushes the write's path narrowing only
when no call in the right-hand side may write the place (`writeRhsCallMayWrite`, asking
`callMayWrite`, which answers for the receivers above the place too). A call that provably
writes neither keeps the narrowing (`k.p = mk(); k.p.x`). Graded on
`scripts/capability-probes/matrix/write-after-receiver-rebind.matrix.vl` over direct
reassignment, a closure, a parameter, a nested field and an element receiver: 12 of 56 to 56 of
56; the 44 cells before were check-clean programs that trapped.
