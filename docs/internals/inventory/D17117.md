### D17117 — a generic function handed to one type parameter and bound to a binding of another is refused at emit as reaching no call that fixes its type

**closed 2026-11-28 with D17321 — runs, prints `x`, `3`: the open question ruled YES (DECISIONS.md "A type parameter's pin is not a binding's set") · the fixture is now `generics/binding-of-one-typaram-seeded-from-another-generic.vl`, a running case · filed 2026-11-24 against master `1784a86d`, closed by COV-CALL**

Repro:

    function same<T>(k: T): T { return k }
    function twice<T>(k: T): T { return k }
    function mid<F, G>(a: F, a1: G) {
      let b: F = a1
      print(a("x"))
      print(b(3))
    }
    mid(same, twice)
    // was: vl check rc 0, then emitProgram: a generic function taken as a value reaches no call
    // that fixes its type

Want:

    x
    3

#### Mechanism

The checker instantiates `F` and `G` per call (`mid(1, "s")` is refused at check, `mid(1, 2)`
runs), so `let b: F = a1` is accepted where the two arguments agree. The binding is seeded from a
parameter of another type parameter, and the emitter's flow walk finds no call that fixes the
seeded generic's type before mono's seeded-binding check runs. The design permits the program: the
refusal is emit's.

**Localized 2026-11-25 (lane N10, scratch probe compilers on master `1bede247`).** Three layers each
decide what `b` holds from its annotation `F`, not from the value written into it, and each
prototype moved the failure one layer down:

1. `check_fn_tag.vl` `fnTagInstanceArms` takes the callee's set from its live type,
   `fnTagSetOfTy(elabLiveTyOf(b))`, which is `F`'s `{same}`. `ftBuildArmsAt` then builds the call
   as a direct call of `same`, renaming the callee. `VL_LATE_DEMANDS=1` shows the late row
   `tag G {same}`. Taking the initializer's set instead leaves `b(3)` unrenamed, but nothing
   instances `twice` at it: `call to unknown function`.
2. Mono cannot name the seed's function at that call: `fnTagSetOfTy(elabWalkTy(a1))` is -1,
   `elabFnIdOf` is -1, and the instance's pin for `a1` (`monoInstPins`) is the closed closure
   type `(i32) => i32`. `emit_mono.vl`'s pin rule pins a parameter that seeds another type
   parameter's binding by name (`eftFirst = tpBare && !elabParamSeedsOtherTyParam(…)`). Making it
   closure-first, plus coercing the generic argument to the instance's closed pin, changes
   nothing.
3. Emit then looks `b` up as a function name, not a closure binding: `userFnCallRoutesRef` is
   false (`identNameIsLiveBound`, `identIsBoundClosure`), and the call is `call to unknown
   function` at `callee=b`.

The prototypes (a 65-line diff over `check_fn_tag.vl`, `emit_mono.vl` and `wasmEmit.vl`) kept
the controls: `let b = a1`, `mid(same, twice)` called at one type, and `a1` called at two types
directly all run. Building no arms for `b` breaks `mid(same, same)`. The design question before a
fix: should `F`'s by-name pin be taken at all while a binding of `F` holds a value of another
type parameter? D17321 shares this mechanism.
