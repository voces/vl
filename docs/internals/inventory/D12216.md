### D12216 — an un-annotated lambda handed to an `f64` callee through an alias of a hole parameter is lowered at `i32` and traps

**check-clean invalid wasm · clause 1 · open · moved 2026-10-26 under the elaboration worklist (#4819) from a trap to invalid wasm (`type mismatch: expected f64` inside `__lambda_0`): the lambda is still lowered at `i32` where the alias's callee wants `f64` · was: a trap once loaded · `vl check` rc 0 · `wasm trap: indirect call type mismatch` in `twof` · clause 1 · the same program over an `i32` callee runs · found surveying emit refusals for L3 family (d) · filed 2026-10-24 against master `b8e223f93`**

Repro:

    function twof(a: f64, b: (n: f64) => f64) { b(a) }
    function outer(h, x) {
      const f = h
      return f(x, (n) => n * 2)
    }
    print(outer(twof, 1.5))

Want:

    3

#### Mechanism

The lambda is a direct argument of a call through `f`, an alias of the hole parameter `h`.
Called through `h` itself it takes `twof`'s `(f64) => f64`; through the alias it appears to
keep the hole's default `i32` signature, and `twof`'s indirect call mismatches. The per-type
lambda instance (`monoHoleLamArgAgain`) is the likely reader that misses the alias; not traced.
