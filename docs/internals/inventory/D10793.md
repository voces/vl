### D10793 — a list of hole functions read at a constant index past 0 and handed an un-annotated lambda has no argument type

**closed 2026-10-23 by lane L1 · runs, prints `30` · built: an un-annotated lambda handed to a hole parameter that no checker bind pins takes the closed types the callee's own calls of that parameter agree on (`monoHoleLamOwnCallsPin`, the last rung of `monoPinHoleParam`, emit_mono.vl) · pins: `tests/cases/closures/hole-fn-list-indexed-past-zero-*.vl` · residue: elements whose calls disagree with element 0's types are [D10795](D10795.md), calls that pass the element's own parameter are [D10796](D10796.md) · was loud emit reject · `vl check` rc 0 · clause 2 · CAPABILITY: a neighbouring spelling runs (the ablation) · found closing [D10702](D10702.md) · filed 2026-10-23 against master `d1a33532a`**

Repro:

    function apply2(g) { print(g(1, 2)) }
    function apply3(g) { print(g(10, 20)) }
    function gen() {
      const gs = [apply2, apply3]
      gs[1]((a, b) => a + b)
    }
    gen()
    // vl check: rc 0.  vl run: emitProgram: monomorphize: unsupported argument type for `g` in a call to `apply3`

Want:

    30

#### Mechanism

The mono flow pass rewrites `gs[1]` into the element's name, `apply3`, but the checker typed the
call through the list's element type, which is element 0's. The lambda's bind therefore names
`apply2`'s parameter, so `apply3`'s parameter `g` has no bind, and every rung of
`monoPinHoleParam` comes back empty. The fix adds a last rung. It asks the fn-flow pass for the
one closed parameter list that `apply3`'s own calls of `g` agree on, which here is `(i32, i32)`,
and pins the lambda at those types.
