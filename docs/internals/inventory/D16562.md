**closed 2026-11-15 by lane R1 · now a loud check reject, `argument 1: expected i32, got f64 (`sel`'s `A` is bound by nothing at its call, so it is `i32` there: write `sel<f64>(…)`)` (the destination face: `cannot assign (i32) => i32 to 'v' of type (x: f64) => f64` with the same note) · was loads then traps, clause 1 · the checker types `sel(gid)` with `sel`'s `A` free, so the open `(A) => A` escaped into an inferred return or a list element while the elaboration built the `gid<i32>` closure · the checker now binds a callee type parameter left on a bare type variable of a generic argument at the unbound default (`callDefaultArgTyParams`, check_calls.vl), the call's row records that instance, and the elaboration's own default (`elabRowArgDefaults`) is deleted · every `i32` use keeps running and every other use is refused at check; `apply(sel(gid), 1.5)` (was invalid wasm) and `d()(4)` now run · the run face is [D16640](D16640.md) · beside [D16411](D16411.md) and [D16531](D16531.md) · filed 2026-11-15 against master `033206ff4`**

Repro:

    function gid<A>(x: A): A { return x }
    function sel<A>(f: (x: A) => A): (x: A) => A { return f }
    function __deliver() {
      return sel(gid)
    }
    const v: (x: f64) => f64 = __deliver()
    print(v(1.5))
    // vl check: loud check reject, `sel`'s `A` is bound by nothing (D16640 is the run face)

Want:

    1.5

#### Mechanism

`sel(gid)` binds `A` from no argument and, here, from no destination: the return is inferred,
so `__deliver`'s result keeps `sel`'s `A` open (`(A) => A`). The emitter builds the one closure at
the `i32` instance, and the call `v(1.5)` is typed and lowered at the `f64` signature the
annotation (or, for the list element, the call's own argument) gives the read. The value and the call
disagree on the signature and `call_indirect` traps. `dstBindOpenFnTyParams` binds an open
parameter only at the call whose destination it sees, and an inferred return hands it none.
The emitter's loud check for a disagreeing value call (D15062, the `i32` parameter case) does not
fire, because the call's own signature is the wider one.

#### Where a close lives

Three routes were tried on 2026-11-15, and each fails for its own reason.

- **An emit guard** compared the call's key with the producer's built key. Emit holds no producer key for a call
  result or a list element (`producerCloSigKeyOfRead` answers `""`), so the guard re-derived it by walking
  `const` initializers, list elements and returned expressions. That is a re-derived fact, and it needed
  exclusions (generic instances, parameter names) to keep three corpus programs running. Vetoed.
- **A record at the build site.** The generic call is where the built key is decided, but the value call
  has no link back to it except the same data-flow walk.
- **Checker provenance from the type.** `sel(gid)`'s result is `(A) => A` with `A` owned by `gid`, which
  is exactly `gid`'s own declared type. A bare generic value (`closures/generic-fn-value-returned-called-at-two-types.vl`,
  `T` owned by `k`, called at `f64`, `i32` and `string`) looks the same and runs. Telling them apart
  needs a fresh type-variable row for the call result's unbound parameter, which the monomorphizer reads by name.

The fact belongs on the function-holding slot the closure is stored in: the elaboration's slot and set rows
already follow the value into the binding, element and return. A slot fact carrying the built signature
lets the call compare without a walk.
