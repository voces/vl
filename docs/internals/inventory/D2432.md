### D2432 — an un-annotated `Map()` in a generic body whose value is the type parameter interns no map slot at the instance; the annotated twin runs

**loud emit reject · clause 2 · found while grading A15's explicit type arguments (the generic-body face) · filed 2026-09-25 against master `a277bf7b0`**

Repro:

    function tally<T>(x: T): {[string]: T} {
      const t = Map()
      t["x"] = x
      t
    }
    print(tally("s")["x"] ?? "none")
    // vl check: rc 0.  vl run: emitProgram: unsupported map value type (no rep for a
    // union-member struct, a nullable list over an unnamed element rep, or a nullable
    // litunion-result closure; any other value type here interned no mv slot)

#### Mechanism

The monomorphizer clones a generic body's `let`s through their ANNOTATIONS
(`monoCloneBodyRaw` → `monoSubstLetType`), so `const t: {[string]: T} = Map()` becomes
`{[string]: string}` in the `T = string` instance and interns its slot. An un-annotated
`const t = Map()` has no annotation to substitute; its type is the checker's `{[string]: T}`,
pinned by the store `t["x"] = x`, and nothing hands the instance the concrete value type.
The same program spelled `const t = Map<string, T>()` runs since A15 — `monoCollCtorAnn`
turns the constructor's type arguments into the instance's annotation — which is the
narrowest statement of what the bare spelling lacks. A first attempt to read the pin off
`tyToEmitName(nodeTyIxOf(init))` the same way did not move this witness and was dropped.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| `const t: {[string]: T} = Map()` (annotated) | runs, prints `s` | **yes** |
| `const t = Map<string, T>()` (explicit type arguments) | runs, prints `s` | **yes** |
| the call `tally(4)` instead (T = i32) | the same refusal | no |
| the store `t["x"] = x` | no pin, a different refusal | **yes** |
