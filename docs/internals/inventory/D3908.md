### D3908 — an alias of a parameter named like a nested generic calls the generic, not the parameter

**closed 2026-10-09 by lane SC, with D3894 · runs · was check-clean silently wrong · found in review of #3480 (`rv3481/pr3/r3`, `pr5/t2`, `pr/p10a`) · filed 2026-10-09 against master `4a7f5604d` · pins: `tests/cases/generics/alias-of-parameter-named-like-nested-generic.vl`**

Repro:

    function a() {
      function f<U>(y: U) { print("generic f"); print(y) }
      function sib(f: (n: i32) => void) {
        const h = f
        h(3)
      }
      sib((n: i32) => print(n + 1000))
      f("x")
    }
    a()
    // vl check: rc 0.  vl run: prints generic f, 3, generic f, x

Want:

    1003
    generic f
    x

#### Mechanism

The scope-aware function lookup (`fnIndexOfInScopeAt`) found the nested `f` by walking frames
outward and never asked whether a frame in between binds `f` as a parameter, so `const h = f`
copied the generic and `h(3)` called it. Closed by `paramShadowsNested`: a parameter of the
reading frame, or of any frame between it and the declaring one, shadows the nested function.
D3894's chain walk asks the same before following a link (`monoNameIsParamOnChain`), which is
what turned its two-link spelling from invalid wasm into the wrong value the review found.
