### D2274 — an if-join of an `f32[]` arm and an `f64[]` literal arm types `f64[]` but builds no element-converting copy

**closed 2026-10-26 — runs, prints `0.36666667461395264` · the `if` join is `f32[] | f64[]` under D2838's ruling (b), and `v[0]` reads the `f32` element of whichever list it holds · was a loud check reject, and check-clean invalid wasm before that · `f32s + [2.2]` still refuses at the checker · pins: `tests/cases/arrays/list-join-keeps-existing-list-apart.vl` · filed against master `6bfe5e770`**

Repro:

    function t() { 1 == 1 }
    const f32s = [(1.1 as f32)]
    const v = if t() { f32s } else { [2.2] }
    print(v[0] / 3.0)
    // vl run: 0.36666667461395264, `v` is `f32[] | f64[]`.  Was: vl check rc 1 at `f32s`.

#### Mechanism

The checker types the join as `f64[]`: annotating `const v: f32[]` refuses with `cannot
assign f64[] to 'v' of type f32[]`. So the join widens the f32 arm's element type, but the
emitter has no element-converting copy for it, and the two arms reach the join as two
different list wrappers. The rep that `exprListRep` names for the join (the f32 list, from
the then arm) is at most the second half of this. Either the checker owes a refusal, which
would be a design question since `f32s + [2.2]` also refuses loudly at emit (`do not resolve
to one list rep`), or the emitter owes the converting copy. Which one is an open ruling.
