### D3253 — a spread element in a list literal is not checked against the declared element type

**closed 2026-09-30 — now a loud check reject, the direct spelling's `cannot assign boolean[] to 'a' of type f64[]` · was check-clean silently wrong (`0.25`) · clause 1 · closed by checking a spread's element type against the destination's element in `assignableExpr`'s list-literal recursion (substituted under a pin), and by recording a composite argument carrying a hole (`ACF_COMP`) that the pin closing it asks by its node the direct call's question, once, not moved out to every caller · the rest-parameter, `string`, return, argument and one-hop generic faces refuse the same way · fixtures `tests/cases/lists/error-spread-element-type.vl`, `tests/cases/generics/error-composite-argument-at-pin.vl`, `tests/cases/lists/spread-element-type-fits.vl` · the container-widening face is [D3402](D3402.md) · found by the #3294 review (`rv3294-k7q2`) · filed 2026-09-29 against master `313a071b4`**

Repro:

    const bs = [3 > 2]
    const a: f64[] = [...bs]
    print(a[0] / 4.0)
    // PRINTS 0.25

Want:

    check reject: cannot assign

#### Mechanism

A prediction. `assignableExpr`'s array-literal recursion fits each element against the
destination's element type, but a `...xs` element contributes its list's element type without
being asked, so a `boolean[]` spread into `f64[]` is accepted and its i32 `1` is read as `1.0`.
The same gap reaches a rest parameter: `function r(...xs: i64[])` called as `r(...bs)` prints
`1`. A `string[]` spread into `i32[]` is check-clean invalid wasm (`expected (ref null $type),
found (ref $type)` in the top-level code).

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `const d: f64[] = c` over `const c = [...bs]` (a value, no literal at the slot) | loud check reject | **yes** (the spread at the slot) |
| `[0.5, ...bs]`, a spread beside an element | prints `0.25` the same way | no |
| `r(...bs)` into `...xs: i64[]` | prints `1` | no, the rest-parameter face |
| `const ss = ["x"]`, `const a: i32[] = [...ss]` | check-clean invalid wasm | no, a second face |

#### Grading list

The rest-parameter face (`r(...bs)`), the `string` face, and the generic twin of each (a spread
of `T[]` at a pin), per the rest-parameter matrices under `scripts/capability-probes/matrix/`.

Residue: a demand still open at an intermediate pin (`outer<U>(xs: U[])` calling `hop<T>(xs)`
calling `h(xs: f64[])`) is not moved out to the outer caller, so the two-hop face at a
`boolean` pin still prints a wrong value, as on master. Moving every open demand to every
caller made a generic chain's check superlinear (82x at depth 160 against 40); the
`generic chain with list-literal arguments` scaling axis now holds that shape.
