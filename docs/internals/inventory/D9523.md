Repro:

    type W = 1 | 2 | 5000000000
    const a: W = 2
    function take(x) {
      print(x + 5000000000)
    }
    take(a)
    // vl run: 5000000002

Want:

    5000000002

#### Mechanism

The body of an un-annotated parameter is checked once with `x` a hole, and the call validates
the hole's recorded operator demands at the argument's type (`validateBinCstrs`,
check_demands.vl, through `binOpDefinedFor`, check_relate_core.vl). That check keeps a literal
union's literals (`softenLitTy`), so a union whose literals soften to two widths has no
operator with `i64`. The direct spelling softens through `softenLitOpTy` (D3512) and computes
at `i64`. The same refusal reaches a function value: `take(() => a)` with `f() + 5000000000`.

Softening the demand alone is unsound and was tried and reverted (lane-D952x): the hole body
types `x op k` as the hole itself (`checkBinNumTail`, check_operators.vl), which substitutes to
`W` at the pin, so `const r: W = x * 2` accepted `10000000000`, a non-member, and the emitter
built invalid wasm for `-x`, `x * 2`, `x + y`, `<<`, `%` and `/` over the box. A close needs
the pin to type an arithmetic result over a literal-union-bound hole at the union's softened
base (`i32` for an `i32`-range union, `i64` here): the root of [D9560](D9560.md), and the
second gap [D3524](D3524.md) records for a declared `<T>`.
