### D17768 — a hole callback mapped over a list of lists of hole functions, beside another hole function's called list in a record field, is refused at emit in either statement order

**closed 2026-11-27 — the element read of a mapped list takes the list type's own closed element (`closedListElemTy`, ir_build.vl) before its rep's type, which is whichever type first reached that rep · the reduced witness of the holdout tests/cases/closures/hole-fn-list-named-callback.vl, which runs and leaves the I8 holdouts · filed against master `4fd3766c` by COV-CALL**

Repro:

    function inc6(a) { return a + 1 }
    const nested = [[inc6]]
    function apN(r) { return r[0](5) }
    print(nested.map(apN)[0])
    function inc7(a) { return a + 1 }
    const rec = { fs: [inc7] }
    print(rec.fs[0](5))
    // was: vl check rc 0, vl run emit error (rep unsup)

Want:

    6
    6

Swapped (the `rec` half first), it was the same reject, at `const rec`; it now prints the same.
Both orders are the named cells `d17768_tagged_rep_elem_{list,rec}_first`.

#### Mechanism

The order dependence was in the rep table, not the holder classes. A tagged function set's rep
is the `i32` leaf, interned with the open function type that first reached it; a plain `i32`
then hits that node, so `repTyOf` of the mapped list's element rep answered `(_) => _`, and
`openIndexRep` judged the element of `nested.map(apN)`, typed `i32[]`, open. The list type's own
element answers first now; the rep's type remains the fall-back for a list typed otherwise.
