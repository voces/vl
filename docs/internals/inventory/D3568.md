### D3568 — a `??` over a join of type parameters kept apart is joined at the pin as if its operand were still nullable

**closed 2026-10-03 — the witness prints `4` then `1` · was check-clean invalid wasm, clause 1 · found by lane KJ's no-lambda port of the #3344 review's `a4.vl` · filed and closed against master `3b9319528` · fixture `tests/cases/generics/coalesce-over-kept-apart-join.vl`**

Repro:

    function F<A, B>(k: i32, a: A, b: B) {
      const v = if k == 0 { a } else if k == 1 { b } else { null }
      print((v ?? 0) + 1)
    }
    F(0, 3, 4)
    F(2, 3, 4)
    // vl check: rc 0.  vl run on master: invalid module inside `F`, "expected i32, found (ref $type)"

Want:

    4
    1

#### Mechanism

A `??` whose operand is a nullable box desugars to `if x != null { x } else { d }` over one
shared `x` node, whose recorded type is the operand's own. The instance walk re-types that `if`
from its arms' pinned types (`monoChainPinnedTys`), so at `(i32, i32)` the join was `i32 | null`
and the `??` built the box an `i32` reader cannot take. The then arm is now read without its
`null`, past the test that excludes it. Two neighbours share the walk: with three parameters the
checker re-joins the `??` result without the kept-apart mark, so the walk left it at its
template type (`monoCoalOverTpJoin` now reads it at the pin too), and an `is` over the re-typed
`if` was folded by its arms' rep name, answering `false` for `(v ?? r9) is Rec`
(`monoStaticIsResult` now asks the `if`'s own type).
