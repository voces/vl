### D17228 — a maker joined into two inferred results that store a field differently is copied for one, and a value `if` of it beside them is refused

**closed 2026-11-28 by I8-PREP · runs, prints `7` `null` `s` · was: loud emit reject · clause 2 · `this branch hands over a record whose field types differ from the record the branches join to` · `recFreshCallCopy` (check_fit_rules.vl) copied a maker called more than once by its call count; it now declines the copy when every call is a queued delivery at one record (`recSitesAllQueuedAt`), so the maker is built there (coordinator ruling, DECISIONS.md) · filed 2026-11-25 against master `c2878db6` by IR-N5 (found building [D17224](D17224.md)'s sweep)**

Repro:

    function mk2() { return { f: null, g: 7 } }
    function mk1() { return { f: 1, g: 7 } }
    function twoReturns(m: boolean) {
      if m { return mk1() }
      return mk2()
    }
    function twoIf(m: boolean) {
      return if m { mk1() } else { mk2() }
    }
    function other(m: boolean) {
      if m { return { f: "s", g: 7 } }
      return mk2()
    }
    print(twoIf(false).g)
    print(twoReturns(false).f)
    print(other(true).f)
    // vl check: rc 0.  vl run: emit error at 8:36, this branch hands over a record whose field types differ

Want:

    7
    null
    s

#### Mechanism

`mk2`'s record is delivered at two rows that store `f` differently (`i32 | null` in `twoReturns`
and `twoIf`, `string | null` in `other`). One maker cannot be built at both, so the call in one
join is copied (`recCopyTyOf` names the copy's row). The value `if` in `twoIf` then reads its
`mk2()` arm at that copy's row, not at its own join's, and the record-join audit refuses the arm.
The refusal predates [D17224](D17224.md)'s delivery, which does not change it.

  Reading `.f`, every pair refuses, on master too; each function alone runs, `null` then `1`

- The refusal is a maker wanted at a second destination, not at a second record:
  `twoIf` beside `twoReturns`, both joining `mk2()` into `{f: i32 | null, g: i32}`, refuses.
- D17226's arm rule (`adoptArmAt`) builds a maker's call at one destination. Several value
  joins of `mk2()` in one program refuse at the third.
- Next: find which reader refuses a second delivery of `mk2()` at the same record. One record
  should need one instance; a (maker × record) instance is needed only for differing records.
  Branch `maker-at-destination` carries the arm rule.

- Probe (2026-11-28): in the minimal two-join program, both `mk1()` call nodes carry the same
  source type, `mk1`'s one result record, and are pended (`recPend`) at three destination type
  indices that are one record, `{f: i32 | null, g: i32}`: the inferred result and the `if`'s join
  for the function's arm, and the module join for the other. With one call node (one join beside
  a bare `const o = mk2()`) the literal is adopted; with two, the refused arm is left at `mk1`'s
  own row `{f: i32}`, so the maker's literal is not adopted at all. The reader that gives up on
  the second call node is not yet found; `recKeptConflicts` compares storages structurally and
  is not it.
- Found (2026-11-28): the reader is `recFreshCallCopy`, run before `recFnBuiltAtDst` in
  `recAdoptNote`'s call case. A maker called once is built where its call lands (D3444); one
  called more than once took the copy path by its call count. It now declines the copy when every
  call site is itself a queued delivery at one record (`recSitesAllQueuedAt`), never one stored
  through a container. Sites landing on differing records are copied where each lands, which is
  sound only because the record is fresh: a call returning a shared record at two differing
  records keeps its refusal (`error-shared-record-call-in-two-joins-at-differing-records.vl`).
- A generic maker at differing records has no copy path; that remainder is [D17874](D17874.md).
