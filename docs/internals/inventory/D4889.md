### D4889 — a hole function returning the complement of `is i32[]` over a hole call's two-list join is invalid at the instance

**closed · was check-clean invalid wasm (`invalid module inside ret: expected (ref $6), found (ref $0); $6 is string list`), identical on master `b8dc4604d` · fixture `tests/cases/generics/hole-complement-list-delivery-positions.vl` · filed 2026-10-15**

Repro:

    function w(t, b: boolean) {
      if b { return [t, t] }
      [1, 2, 3]
    }
    function ret(t, b: boolean) {
      const v = w(t, b)
      if v is i32[] { return [t] }
      v
    }
    print(ret("a", true)[1])

Want:

    a

#### Mechanism

Two steps. `tyParamsPart` kept a declared parameter's `T[]` apart from `i32[]` but called a
parameter's hole inference, so at a pin `w`'s `[t, t]` and `[1, 2, 3]` joined to the pin's
one list; at a top-level binding the checker then refused `is i32[]` as never matching
`string[]` or `boolean[]`. The hole is an implicit type parameter, so beside a
concrete type under a constructor it now parts as `T` does (`holeParamBesideConcrete`). Then
the pin's re-check (`monoInferListElem`) read `v` through `lookup`, which after the guard is
the narrowed arm, and recorded that arm as the slot's list. It now reads the declared type.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| both holes (`w<T>` and `ret<T>(…): T[]`) | runs | **yes** |
| the hole on `ret` only (`ret<T>(…): T[]`, `w` a hole) | still invalid, inside `ret$1` | no |
| the hole on `w` only (`w<T>`, `ret` a hole) | still invalid, inside `ret` | no |

#### Grading list

The tail, the top-level binding, `.length`, the `boolean` pin and the `<T>` face, all in the
fixture. An `f64` pin with a one-element `[t]` beside `[1]` is D4900.
