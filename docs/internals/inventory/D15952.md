### D15952 — a record whose list field holds a nested union layer is a different row from its flat spelling, and handing it across is an invalid module

**closed 2026-11-12, runs and prints `3` · was check-clean invalid wasm · clause 1 · found grading the `tySame` vector of the equality notions ([note](../refactor-notes/2026-11-12-step7-equality-vectors-graded.md)) · filed 2026-11-12 against master `cf01f012` · closed in `tySame` (check_types.vl): union layers flatten in order, as `tyEq` flattens them, so `fieldElemSame` (emit_state.vl) finds the two slots store one element · fixture `tests/cases/unions/nested-union-layer-field-crosses-to-flat.vl`**

Repro:

    type IS = i32 | string
    type U = IS | f64
    type W = i32 | string | f64
    type R1 = { u: U[] }
    type R2 = { u: W[] }
    function f(r: R2): i32 { r.u.length }
    const r1: R1 = { u: [1, "q", 2.5] }
    print(f(r1))
    // vl check: rc 0.  vl run: invalid module, expected (ref R2), found (ref R1)

Want:

    3

#### Mechanism

`structFieldCodesEq` (emit_rep.vl) merges two struct rows into one heap type only when each
list field's element is the same (`sFieldElemSame` → `fieldElemSame`, emit_state.vl). That asked
`tySame`, which compared a union's members positionally without flattening, so `U` (members
`IS`, `f64`) and `W` (three members) differed. The canon key, `tyEq` and every other notion call
them one type, and the checker accepts the hand-over, so `R1` and `R2` kept two heap types.
