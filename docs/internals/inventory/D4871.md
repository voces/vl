### D4871 — a fresh nested list literal under a spread is not built at an annotated destination's element type

**closed 2026-10-15 — now runs, printing `0.5` · was a loud check reject, clause 2 · a spread of a list literal is a literal, so its elements are typed from the destination as they are without the spread · found grading D4861's `nested-list-widen-fresh` matrix, where every annotated cell refuses and the un-annotated twin runs · also closes [D4874](D4874.md), the un-annotated face · filed 2026-10-15 against master `0a7e96cce` · pins: `tests/cases/arrays/spread-fresh-nested-literal-runs.vl`, `scripts/capability-probes/matrix/nested-list-widen-fresh-spread.matrix.vl` and `nested-list-widen-fresh.matrix.vl`**

Repro:

    const v: f64[][] = [...[[1, 2]]]
    print(v[0][1] / 4.0)
    // vl check: rc 0.  Was: rc 1, i32[] is not f64[] (reached through i32[][] into f64[][]): a container never widens implicitly

Want:

    0.5

#### Mechanism

The spread operand is a list literal, so nothing exists to be copied, but it was typed
`i32[][]` on its own instead of from the destination, and the delivery rule then refused the
inner level. The checker's literal-widening walks (`objShapeAdapterless`, `listWidenLitElems`,
`recWidenLitElems`) now recurse into a spread of a list literal, and `emitArrSpread` builds the
whole result at the destination's row (`spreadFreshDestRow`) when every source of another row
is itself a list literal.
