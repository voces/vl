### D16700 — a hole function instanced at `f64` beside an `i32` instance of its holder builds an `i32` operand into the `f64` body

**closed 2026-11-16 · runs, prints `6` `2.5` · was check-clean invalid wasm, `type mismatch: expected f64, found i32` inside `dbl$1` · clause 1 · the 12 SILENT cells of `hole-fn-bound-nested-list-returned-at-two-instances.matrix.vl` named below run, and 15 annotated cells of it that were loud emit rejects run too · fixed by `genericFnAssignable` (check_relate_core.vl) binding every un-annotated member of the source's set at the destination's parameters, so `dbl` gets its hole pin and its `i32` instance (before, only the value type's own member, `inc`, did) · a member whose body cannot hold there is now a check reject, where it built invalid wasm (`tests/cases/functions/error-hole-fn-set-member-unfit-at-delivered-type.vl`) · pin: `tests/cases/functions/hole-fn-set-member-bound-at-delivered-nested-list.vl` · filed 2026-11-16 against master `32ee97e56`**

Repro:

    function inc(a) { return a + 1 }
    function dbl(a) { return a * 2 }
    function give(_n) {
      const w = [[inc], [dbl]]
      return w
    }
    function deliver(): ((a: i32) => i32)[][] {
      return give(1)
    }
    print(deliver()[1][0](3))
    print(give("s")[1][0](1.25))
    // vl check: rc 0.  vl run: invalid module, inside `dbl$1`: expected f64, found i32

Want:

    6
    2.5

#### Mechanism

The delivery `return give(1)` at `((a: i32) => i32)[][]` reaches `genericFnAssignable`. The
source element's function type is `inc`'s, carrying the set `{inc, dbl}`, and only that type's holes
were bound at `(i32)`. So the checker banked a hole pin for `inc` alone, and the elaboration minted
`dbl` once, at `f64`, as its sole root instance. Mono then keyed `dbl`'s `i32` build at that `f64`
instance (`elabValueKeyAt`'s sole-hole fallback) and lowered an `i32` operand into the `f64` body.
This confirms the second of the trace's two readings below: no `i32` elaboration of `dbl` existed.

Lane AE's partial trace (2026-11-16), before the close above: One instance of `give` is delivered at the
annotated `((a: i32) => i32)[][]`, the other is called at `f64`. The disassembly shows `dbl$1` with an
`i32` parameter but an `f64` body and result (`f64.mul (local.get i32) (f64.const 2)`): the `i32`
instance is built from the `f64` instance's body types, while `inc$1` at `i32` is right. It is the
literal's second member that breaks, whatever its name: `[[dbl], [inc]]` breaks `inc$1`, and
`[[inc, dbl]]` breaks `dbl$1`; statement order and which member is called at `f64` do not matter.
`VL_ID_SHADOW=1` shows the first member built on the `pins/keyed/hole-key` path and the second on
`value/keyed/hole-key`: `instKeyValueTime` (emit_inst_key.vl) answers the second member with a value
key binding the `f64` instance, and `emit_mono` installs `dbl$1` under it with `i32` pins.
Three fixes were tried and reverted, none moving the witness: instancing every hole member of a
cell at every peer's parameter tuple (`elabCellPeers`); preferring `elabHoleKeyAtPins` in
`elabValueKeyAt` when its first key does not bind the pins; and rejecting a value or delivery key
that misfits the pins in `instKeyValueTime`. The last having no effect suggests either the build's
pins are not `i32` there or no `i32` elaboration of `dbl` exists; instrumenting the `ek`/`pinTys`
pair at that build is the next step.
