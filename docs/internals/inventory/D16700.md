### D16700 — a hole function instanced at `f64` beside an `i32` instance of its holder builds an `i32` operand into the `f64` body

**check-clean invalid wasm · `type mismatch: expected f64, found i32` inside `dbl$1` · clause 1 · open · `vl check` rc 0 · the 12 cells of `hole-fn-bound-nested-list-returned-at-two-instances.matrix.vl` that [D16712](D16712.md)'s close did not reach, counted by cell, not ablated per cell · found re-grading D16712's template · filed 2026-11-16 against master `32ee97e56`**

Repro:

    function inc(a) { return a + 1 }
    function dbl(a) { return a * 2 }
    function give(_n) {
      const w = [[inc], [dbl]]
      return w
    }
    function deliver(): ((a: i32) => i32)[][] {
      return give(1)
    }
    print(deliver()[1][0](3))
    print(give("s")[1][0](1.25))
    // vl check: rc 0.  vl run: invalid module, inside `dbl$1`: expected f64, found i32

Want:

    6
    2.5

#### Mechanism

Partly traced (lane AE, 2026-11-16, handed to SOUND). One instance of `give` is delivered at the
annotated `((a: i32) => i32)[][]`, the other is called at `f64`. The disassembly shows `dbl$1` with an
`i32` parameter but an `f64` body and result (`f64.mul (local.get i32) (f64.const 2)`): the `i32`
instance is built from the `f64` instance's body types, while `inc$1` at `i32` is right. It is the
literal's second member that breaks, whatever its name: `[[dbl], [inc]]` breaks `inc$1`, and
`[[inc, dbl]]` breaks `dbl$1`; statement order and which member is called at `f64` do not matter.
`VL_ID_SHADOW=1` shows the first member built on the `pins/keyed/hole-key` path and the second on
`value/keyed/hole-key`: `instKeyValueTime` (emit_inst_key.vl) answers the second member with a value
key binding the `f64` instance, and `emit_mono` installs `dbl$1` under it with `i32` pins.
Three fixes were tried and reverted, none moving the witness: instancing every hole member of a
cell at every peer's parameter tuple (`elabCellPeers`); preferring `elabHoleKeyAtPins` in
`elabValueKeyAt` when its first key does not bind the pins; and rejecting a value or delivery key
that misfits the pins in `instKeyValueTime`. The last having no effect suggests either the build's
pins are not `i32` there or no `i32` elaboration of `dbl` exists; instrumenting the `ek`/`pinTys`
pair at that build is the next step.
