### D15110 — a `let` in a generic body seeded with a generic and written with a hole lambda, returned from two instances, calls the second instance's lambda at the first's type

**now a loud emit reject, with the split plan on and off · was check-clean silently wrong, clause 1 · the floor: mono refuses a lambda the elaboration minted no key for (`mintLamKeyedOf`) when two instances of its encloser reach it and a parameter's checker type is still open (`monoSharedLamGuard`, emit_mono.vl) · still open as a capability: the build is the lambda keyed per encloser instance (per-instance-identity-2026-11.md, M3 step 2) · pin `closures/error-hole-lambda-in-generic-returned-from-two-instances.vl` · found writing slice 4b's escape control · filed 2026-11-03 against master `4a114e6cd`, pre-existing**

Repro:

    function inner<U>(u: U) { print("I"); print(u) }
    function a<T>(x: T) {
      let k = inner
      k = (u) => { print(u) }
      return k
    }
    a(1)(2)
    a(true)(false)
    // vl check: rc 0.  vl run, before the floor: prints `2` then `0`

Want:

    2
    false

#### Mechanism

Measured by a dump of the two instances: both write one closure of one lambda body, built at the
first instance's type, while the non-generic twin tags the binding and gives the lambda one arm per
call type. The elaboration mints the lambda no key, so nothing says it is per instance. Earlier: each instance alone runs correctly, so the defect needs two instances of
`a` whose returned value is the lambda written to `k`. That value leaves its instance, which the
per-instance identity design keeps a closure (M3, "an id that leaves the instance"). The second
instance's closure prints through the first instance's `print` arm: in the swapped order the output
is `false`, `true`. With `a(1)("x")` first, the second call traps.
