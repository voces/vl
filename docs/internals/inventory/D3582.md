### D3582 — a failing `as` cast in a function with an inferred return type was told to annotate the return, not to use `as!`/`as?`

**loud check reject, by design — the row was its message, fixed 2026-10-03 · sunpa SP-022 · filed 2026-10-03 against master `315552b88`**

Repro:

    const a: u8[] = [0, 0]
    function f(g: i32) {
      a[0] = g as u8
      1.5
    }
    print(f(3))
    // vl check: `as u8` propagates null — use `as!` to trap instead, or `as?` to take the null
    // here, or `as%` to keep its low bits; to propagate it, annotate the enclosing function's return type

#### Mechanism

`castPropagationFits` has three refusals, one per enclosing return: annotated but unable to
hold the null, none at all (module scope), and still being inferred (`curRet == -2`). The first
two named the cast's own fixes; the third named only the return annotation, which turns every
caller nullable. All three now lead with `as!`/`as?`, add `as%` for an integer target
(`castWrapNote`), and the inferred-return refusal keeps the annotation as the second option.

#### Ablation

| enclosing return | before | after |
| --- | --- | --- |
| void | `as!` / `as?` | `as!` / `as?` / `as%` |
| inferred value, a lambda | annotate the return | `as!` / `as?` / `as%`, then annotate |
| annotated `f64` | `as!` / `as?` | `as!` / `as?` / `as%` |
| module top level | `as!` / `as?` | `as!` / `as?` / `as%` |
