**closed · runs, prints `3.5` · was loud emit reject, `vl check` rc 0, clause 2 · CAPABILITY: the un-annotated `function g(x)` prints `3.5` since [D9631](D9631.md), and `g(2.0)` prints `3.5` · found closing [D9631](D9631.md) · filed 2026-10-22 against master `abe12f20f` · closed by keeping a declared type parameter's arithmetic beside an `i64` or `f64` operand apart from the parameter in a join, as a parameter's hole's already was (`paramArithHole`, check_tp_join.vl) · fixture `generics/hole-coalesce-join-operand-tp-list-literal.vl`, matrix `generic-list-wider-literal-arith-open` (0 → 64 of 64; before, 50 emit refusals and 14 SILENT) · with [D9870](D9870.md) closed, [D9910](D9910.md) and [D9912](D9912.md) closed with [D9914](D9914.md), [D9911](D9911.md) and [D9913](D9913.md) filed open**

Repro:

    function g<T>(x: T) {
      const xs = [x, x + 1.5]
      print(xs[1])
    }
    g(2)
    // vl run: emitProgram: index access but list type not collected

Want:

    3.5

#### Mechanism

In a `<T>` body `x + 1.5` is typed `T` itself, not a derived hole (a
`const z: boolean = x + 1.5` probe is accepted), so the list is `T[]` and the join has
nothing to keep apart. At the `i32` pin the list is `i32[]` while its second element
computes at `f64`. The un-annotated spelling mints an arithmetic hole that pins at `f64`. `paramArithHole`
recognised only a parameter's hole as the root of such arithmetic; it now recognises any
gradual parameter (`tyIsGradualParam`), so the join keeps `T` and `x + 1.5` apart and the list
is `f64[]` at the `i32` pin.
