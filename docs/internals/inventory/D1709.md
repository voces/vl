### D1709 — an INFERRED mixed-union BINDING has no registered row, so nothing can name the type it already has; the `??` join and the if-expression join are two witnesses of the one gap

**check-clean invalid wasm · filed 2026-09-06 against master `1f7406139`, scope widened
2026-09-06 · D1703's un-annotated face, and NOT `??`-specific · 0 corpus cells**

Repro:

    type A = { r: i32 }
    function mkN(): i32 | null { return null }
    function st(): A { return { r: 8 } }
    const v = mkN()
    const w = v ?? st()
    if w is A { print(w.r) } else { print(0) }
    // vl check: rc 0.  vl run: exit 70,
    // the emitted module failed to validate: type mismatch: expected i32, found (ref $type)

#### Mechanism

D1703's close names the `??` result union off the canon-keyed registry
(`nodeRegisteredUnionName`), which answers only for a union `collectU` registered — and
`collectU` registers what the program DECLARES, plus an un-annotated function's inferred
return. A join that exists only as a `??` result is neither, so the name resolves to "" and the
arm falls to the scalar tail, which puts the struct ref in the operand's `i32` block type.
Adding `type M = i32 | A` and annotating the binding is the whole difference; the checker
already types `w` as `i32 | A` either way and says so in a `redundant type annotation` hint.

The same gap wearing a LOUD sentence is an f32 default: `v ?? sm()` over an `i32 | null`
refuses with `union box atom test on a union with no recorded members: i32|f32` un-annotated,
while its declared `type F = i32 | f32` face runs.

**IT IS NOT `??`-SPECIFIC.** An if-expression binding of the same shape —
`const w = if 1 == 1 { st() } else { 7 }` — is check-clean invalid wasm too, and the annotated
spelling of THAT runs as well, so both are the one missing row rather than two lowerings. The
two fail in OPPOSITE directions (`expected (ref $type), found i32` for the if-expression,
`expected i32, found (ref $type)` for the `??`), which is why the ablation and not the message
places them together: the annotation is what fixes each.

**THE ARENA TYPE IS THE SAME IN BOTH FACES — this is a registry lookup and nothing else.**
Probed at the `??` lowering, the declared and inferred spellings of one program both report
`tyToEmitName` = `i32|{r:i32}`; the only difference is that `unRowOfCanon` finds `M`'s row for
the first and nothing for the second. So no type, rep or tag differs, and no re-rendering is
owed — a row keyed on that arena index is the whole of what is missing.

**The inferred RETURN is the working model, and the inferred BINDING is where the gap is.**
`function pick(b) { if b { return st() } return 7 }` registers and runs (`collectU`'s
inferred-return loop walks the arena and calls `registerInferRetNominalUnion`), while the
binding loop beside it calls `registerValueUnionNameAB`, which a mixed union declines because a
struct is not a value ATOM. An attempt to route the binding through the arena walk was measured
and did NOT close it: the recorder half fires (a `tyIsMixedUnion` gate on the `??`/if-expression
init records the row), and registering under the structural emit name still leaves
`nodeRegisteredUnionName` answering "". What the return path has and the binding path does not
is a NOMINAL name from the inference cascade; that is where a close should start.

#### Grading list

spelling above — it is the same missing row reported loudly rather than silently, so a close

a close that moves only one has not found the shared row. Three controls that must not move:
