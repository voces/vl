### D1669 — an un-annotated `__array_new__` local keeps the i32 list slot while the generic's `T[]` return is pinned at i64

**check-clean invalid wasm · filed 2026-09-05 against master `8725c61a8` · found while measuring D1666 · probe `scripts/capability-probes/generic-array-new-i64-fill-returned-list.vl`**

Repro:

    function pick<T>(v: T): T[] {
      const out = __array_new__(1, v)
      return out
    }
    function big(): i64 { 7 }
    print(pick(big()).length)
    // vl check: rc 0.  vl run: exit 70, the emitted module failed to validate inside
    // `pick`: type mismatch: expected i32, found (ref $type)

#### Mechanism

`arrNewIntrKind` reads the FILL's rep per monomorphized instance and answers i64, so the
`__array_new__` call emits an i64 array. The local it is bound to gets its slot from the
un-annotated binding path, which classifies it as the plain i32 list, and the `T[]` return
then substitutes to `i64[]` — three answers about one value, two of which disagree with the
bytes. Nothing in the program spells `i64[]`, which is what keeps the collect pass from
minting the row that would have reconciled them.

**This is the "two faces, two clauses" split with both faces measured.** Annotating the
local `const out: T[] = __array_new__(1, v)` RUNS — the annotation pins the slot the
intrinsic already chose. And returning `i32` instead of `T[]` (so the list never leaves the
instance) is a LOUD refusal, `emitProgram: __array_new__ i64 fill but i64 list types not
collected`, which is D1666's listed literal with the probe
`generic-array-new-i64-fill-hidden-result.vl`. One mechanism, three outcomes chosen by the
spelling.
