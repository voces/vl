### D16541 — a float constant tree whose IEEE value is an infinity is typed `f64` at an `f32` use, and refused

**closed 2026-11-15 · runs, prints `Infinity` · was a loud check reject, clause 2, ``f64 doesn't fit in f32 — the conversion is lossy and must be made explicit with `as` `` · closed by adopting a float tree the fold keeps whole (its value no finite double) at an `f32` use, as the integer tree twin adopts its destination's width (`floatTreeAdoptDst`, check_num_adopt.vl; `cexKeptF32Tree`, check_num_lit_state.vl) · fixture `tests/cases/numerics/const-float-infinity-at-f32.vl` · found grading D16414's positions · filed 2026-11-15 against master `f88ee38dd`**

Repro:

    const z: f32 = 1.0 / 0.0
    print(z)
    // vl check: f64 doesn't fit in f32 at `1.0 / 0.0`

Want:

    Infinity

#### Mechanism

The fold computes a float tree as a double and rewrites it into its literal; a value that is no
finite double (`1.0 / 0.0`, NaN) has no literal, so the fold keeps the tree whole and it is checked
as the operator it is, at its literals' `f64` default, which an `f32` use refuses. Integer trees
the fold keeps whole already take their destination's width at the delivery seam
(`litTreeAdoptDst`); a float one now does too at an `f32` use (`floatTreeAdoptDst`), when every
literal holds a finite `f32` value, so the tree computes there in IEEE `f32` arithmetic as it runs.
A finite literal past `f32`'s largest value keeps the refusal (the coordinator's reading of Q9).
