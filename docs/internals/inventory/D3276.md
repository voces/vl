### D3276 — an object literal written as a `match` arm or `if` branch body got no diagnostic naming the parentheses

**closed 2026-09-29 as a diagnostic: the witness is now a loud check reject that names the parentheses (a keyed statement `a: 1` is one parse diagnostic naming `({ a: … })`; an arm or branch recorded in `objLookBodies` adds the parentheses to a later `void` or non-object error) · the parse is design (an arm's braces are a block, as an `if` body's), only the diagnostics changed · found by the #3299 review grid · filed against master `296e1141d` · fixtures `tests/cases/match/object-arm-keyed-value.vl`, `tests/cases/match/object-arm-needs-parens.vl`**

Repro:

    function h(b: i32) { match b { 3 => { a: { b } }, _ => { a: { b } } } }
    const v = h(3)
    // was: cannot bind the void result of 'v' — a void function returns no value
    // now: the same, then "; the braces at 1:37 are a block, not an object literal;
    //      parenthesize an object there: `({ … })`"

#### Mechanism

`match` arms and `if` branches call `parseBlock` directly, so an object literal there must be
parenthesized. Two failures followed, neither naming that: `{ a: 1 }` was
`expected an expression but found COLON` once per field, and `{ a: { b } }` parsed as a labelled
block, so the arm was `void` and a use far away said so. `parseStmt` now refuses `name: value`
(a name and `:` before anything but a loop or `{`) once and skips the body's remaining fields.
The parser records an arm or branch brace that `looksLikeObject` in `objLookBodies`; once the
checker has checked one, `tErrPush` appends the parentheses to a message about `void` or a
non-object.
