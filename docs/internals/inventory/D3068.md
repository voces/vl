### D3068 — a list callback that changes its source's length reads a stale element, traps, or walks the new length, by receiver and by op

**closed · runs, prints `1,2,` · was check-clean silently wrong, clause 1, printing `1,2,3,` · owner ruling A, 2026-11-02 · found grading D3060 (the push and pop cells of its grid) · filed 2026-09-28 against master `6c2dafc0b` · fixtures `tests/cases/arrays/list-callback-fixes-the-length-at-entry.vl`, `tests/cases/traps/list-map-callback-cuts-off-an-index.vl`, `tests/cases/traps/list-map-indexed-callback-cuts-off-an-index.vl`**

Repro:

    const h: i32[] = [1, 2, 3]
    let first = true
    let out = ""
    for e in h.filter((e) => {
      if first {
        first = false
        h.pop()
      }
      return e > 0
    }) { out = out + "\{e}," }
    print(out)
    // was: printed 1,2,3,

Want:

    1,2,

#### Mechanism

The core `.map`/`.filter` read the length once, at entry, and then read the backing directly,
so after a `pop` in the callback they read the popped element out of the backing's spare slot.
Over a `readonly` view (D3028) the same read goes through the view's bound-checked getter and
traps (`out of bounds array access`). `std:array`'s `reduce` and `mapIndexed` re-read
`self.length` every step instead, so a `push` in the callback extends the walk (`reduce` over
`[1, 2, 3]` pushing `7` once sums `13`; `.map` stops at 3 elements), and a callback that pushes
every time never ends. D3060 settled the element-value half like JavaScript: the value a
callback sees is read once. The length half is a ruling: JavaScript fixes the length at entry
and skips an index at or past the current length (`filter` gives `1,2,`, `reduce` `3`), and
leaves a hole in `map`'s result, which VL has no rep for.

**Ruling A (owner, 2026-11-02; DECISIONS.md §"A list callback op fixes the length at entry"):**
every callback op, core and `std:array`, fixes the length at entry. An index at or past the
current length is skipped by `filter`, `reduce`, `some` and `every`, and ends `map` and
`mapIndexed` with the trap an out-of-range `xs[i]` read raises, on plain lists and readonly views
alike. `emitMapFilter` reads the current length each step; the `std:array` ops keep `n` and test
`i < self.length`. A converting view (`readonly i64[]` of a written `i32[]`) is now refused by
`vl check`, so the third answer in the ablation is gone.

**Follow-ups, deferred by the ruling:** the per-step length read can be dropped where the callback
provably does not change the list, first for the simple case (a callback that names no list it
could reach), then for the complex one (one that calls functions), as separate steps.
