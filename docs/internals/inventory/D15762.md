### D15762 — a `V[][] | string` instance whose `V` is inferred from a nested-list argument builds an invalid body once the argument is boxed

**closed 2026-11-12, prints `0` · was loud emit reject, a refutation pin for a type-only `unionHasRefArrayArmSlot` (step C5) · the instance face of [D4937](D4937.md) · filed 2026-11-12 against master `c7474c370` · closed by the instance's parameter-pin synthesis (`monoMakeInstance`'s D2679 arm, emit_mono.vl) gating `monoPinMintedUnion` on the parameter's own substituted type, so an instance whose `V` is inferred registers the `i32[][] | string` union its body tests, as one with written type arguments did; the type-only `unionHasRefArrayArmSlot` builds a valid body · fixture `tests/cases/generics/union-param-inferred-nested-list-arm-registers-its-union.vl`**

Repro:

    function probe<V>(v: V[][] | string) {
      if v is string { return 2 }
      0
    }
    const e: i32[][] = [[1]]
    print(probe(e))

Want:

    0

#### Mechanism

Today the delivery of `e` is refused. `unionHasRefArrayArmSlot` reads the arms of the name's
generic row (`V[][]`), which has no arm for the `i32[][]` slot. Asked of the type alone, as
step C5 first did, it finds the instance's `i32[][]` arm and boxes, which is the sound delivery.
But the instance body then fails to validate (`expected struct type at index 8, found (array
(mut i32))`), whatever the test is: `is string` above, or D4937's `is f64[][]`. That change was
refused for this new compiler trap.
