### D1702 — a `??` whose result type is a deferred hole reads the operand's residual atom for its block type, because nothing substitutes a `??` node's own type and so nothing banks its pin

**closed 2026-09-06 — the pin banks the `??` result hole, and the readers that route the value
read it through that bank · filed against master `dbd19dd4b` · the UN-ANNOTATED face of
D1699's close · 0 corpus cells**

Repro:

    function mkN(): i32 | null { return null }
    function take(a) {
      const v = a
      print(v ?? "x")
    }
    take(mkN())
    // prints x since the close; before it, `vl check` rc 0 then exit 70,
    // the emitted module failed to validate inside `take`:
    // type mismatch: expected i32, found (ref $type)

#### Mechanism

D1699 made `emitCoalesceGo` turn on the checker's recorded type for the `??` node, which is
what says whether the result is the operand's residual atom, a wider scalar, or a box. Inside a
monomorphized body that recorded type is D1693's `HD_COAL` hole, and `nodeTyPinIxOf` resolves a
hole only when its pin was BANKED — `substHoleTy` banks a derived hole when something
substitutes it, and a `??` result hole is not a constraint, so nothing ever asks. The arm reads
an unresolved `TyVar`, renders no name, and falls back to the operand's residual atom exactly as
it did before the close.

The one-annotation-different twin runs: `function take(a: i32 | null)` prints `x`. So this is a
lost REP, not a lost capability — the same shape D1693's own row is about, one layer on.

#### Grading list

The four ablation rows, the annotated control that must keep running, and the `argument`
un-annotated cell of `scripts/capability-probes/matrix/pin2-coalesce-default-kinds.matrix.vl` —
the one SILENT cell that matrix reported, at both seeds. A close that banks a `??` hole's pin
must also leave `tests/cases/arrays/unannotated-param-f64-map.vl` running: that fixture is what
refuted reading the pin from a SCALAR classifier when D1693 landed.

The close is a bank plus three readers, and the bank alone moved nothing. `bankCoalHoles`
substitutes the recorded `HD_COAL` rows at the pin purely for the side effect `substHoleTy`
already had; then the `??` lowering, `unionNameOfExpr`'s two arms and `coalesceAtomKind` read
through it. The LOWERING was the first to be fixed and the module still failed to validate,
because `print` classified the box the lowering had just built as a scalar — the producer and
the consumer are separate positions, and wiring one is what makes the other's miss visible.
The if-expression ARM needed the third reader: without it the pinned face fell to
`ifExprRefKind`, which has no union rung and hands back a numeric block type over box arms.
