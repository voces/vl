### D2180 — every call site in a function walked that whole function for its capture set, so a large function compiled in quadratic time

**closed 2026-09-23 — the witness builds in 0.12 s CPU where master took 3.6 s; plumb's `chunk_142` 46 s → 3.7 s, `chunk_73` 11.5 s → 1.9 s, `chunk_400` 4.6 s → 1.3 s, output byte-identical · was a compile-time cost, not a miscompile: every spelling ran · introduced by #3050 (D2110), reported by plumb as PL-019 · filed 2026-09-23 against master `a453c09c5`**

Repro (runs, prints `20000`):

    let g = 3
    function h(x: i32): i32 { x * 2 + g }
    function f(a: i32): i32 {
      let acc = 0
      @@repeat(2500, "{ const m = h(a) + g; acc = acc + m }; ")@@
      acc
    }
    print(f(1))
    // vl build: 3.6 s CPU on master a453c09c5, 0.12 s after the fix.

#### Mechanism

#3050 gave `calleeCloSigKeyAt` (compiler/emit_classify.vl) a loop-variable rung,
`loopVarCloSigKey`, asked of every named callee. With no live scope slot for the name, which is
every question asked outside the emit walk, it asked `frameCapturesName` first. That calls
`captureNamesOf` on the calling frame, and computing a frame's capture set walks its whole body
(`capScan`). Only after that did it ask `captureLoopVarIterOf` whether an enclosing frame binds
the name as a loop variable at all. `dispatchRewrite` asks `structIndexOfExpr` of a call operand
of every binary operator, so each call site cost one walk of its enclosing function: O(call
sites x function size). #3052's pass memo (D2017) made the walk once per pass, but a pass that
mints a node drops the memo, and `dispatchRewrite` mints one for every bare block it rewrites
to an `if`. In plumb's translated units a function is thousands of such blocks. The guest
profile of `chunk_73` on master: 85% inclusive under `capScan < capComputeNamesOf <
capMemoNamesOf < frameCapturesName < loopVarCloSigKey < calleeCloSigKeyAt <
calleeReturnsStructIdxSid < structIndexOfExpr < drwWalk`.

The fix asks the cheap question first. `enclosingLoopVarBinds` runs the table lookups
`captureLoopVarIterOf` starts with: the parent-frame chain, the per-block loop-variable table
and the module loop-variable set. The capture set is walked only when one of them binds the name
as a loop variable. The answer is unchanged, because `captureLoopVarIterOf` returns -1 whenever
that test fails.
