### D17571 — a hole function's field read at a record-union argument resolves to an open hole at the call

**closed 2026-11-25 by SOUND · runs, prints `4` · was check-clean invalid wasm, clause 1 (copies of the call's result, and a destination it does not fit, checked clean and built invalid modules), and loud emit rejects where the result was handed on · the call-site resolver for a derived field hole (`HD_FLD`, check_relate_core.vl) resolved a record base only; a union of records fell through to `rebaseHoleUnder` and the call stayed an open hole `_`, which every destination accepted; it now reads the members' shared field at their join (`sharedUnionFieldTy`, moved to check_relate_core.vl), as a receiver written at that union does · pinned by `tests/cases/types/hole-fn-field-read-at-record-union-arg.vl` · found by START-2 and lane SOUND · filed 2026-11-25 against master `12b715d9d`**

Repro:

    type K = { h: i32 }
    type J = { h: string, z: i32 }
    const k: K = { h: 4 }
    const u: K | J = k
    function ret(a) { return a.h }
    const r = ret(u)
    const c = r
    print(c)

Want:

    4

#### Mechanism

`ret`'s result is the derived hole `a.h` over its parameter's hole. At the call the parameter is
bound to `K | J`; the resolver read a field only off a record, so the union left `r` an open hole.
An open hole fits every destination, so the checker accepted each use below, and the emitter
built each at whatever its rep plan guessed. With the field read at the union's join, `r` is
`i32 | string` and every face matches the annotated `const r: i32 | string` spelling.
