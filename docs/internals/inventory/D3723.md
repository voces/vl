### D3723 — an index into an empty list traps `out of bounds` unoptimized but `unreachable` at `-O3`, so the optimized trap no longer says what went wrong

**trap after load at every rung, ruled (c) 2026-11-02: the `-O`/`-O3` banner for `unreachable` names the traps an optimizer may fold into it, an out-of-range index among them · exact kinds backlogged in ROADMAP.md · pre-existing, identical on master `0948a28e3` · found by the review of the S2 PR (reviewer's `g7_153`) · filed 2026-10-05 against master `687b42dbe`**

Repro:

    const L: i32[] = []
    let k = 0 - 1
    print(L[k])
    // vl run (plain build): wasm trap, "an index outside the bounds of an array".
    // vl build -O3, vl run: wasm trap, "an `unreachable` instruction — a compiler-emitted trap";
    // the optimized start function is the single op `unreachable`.

#### Mechanism

The emitter clamps an index to `-1` when it is not below the list's length, so the
`array.get` traps out of bounds. At `-O3` binaryen sees that the list is empty and the access
always traps, and folds the whole body to `unreachable`. Wasm does not distinguish trap kinds,
so the module is still correct, but `vl run`'s trap banner, keyed on the trap kind, now names a
compiler-emitted trap instead of an index out of range. The fix belongs to how the banner
reads an optimized trap (a source map row, or a named trap function kept through `-O3`), not
to the emitter.

#### Grading list

Amended by the ruling: the witness at `-O0` and `-O` names an out-of-range index, and at `-O3`
the `unreachable` banner lists an out-of-range index among the causes it may stand for.
