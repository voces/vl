### D2115 — a closure written after a for-in loop that captures the OUTER binding of the loop variable's name is typed as the loop variable

**closed 2026-09-23 by D2068 — the witness prints `1`, `1`, `9`: the loop variable shadows the module `f` that `g` reads, so `shadowRespell` gives it its own spelling and the capture resolves to the global · was check-clean invalid wasm, 1 witness, identical on the seed before and after D2110 · filed 2026-09-23 against master `7b16d43ab`, found reviewing #3050**

Repro:

    function a(x: i32): void { print(x) }
    function v(x: i32) { print(x); return x }
    const f: (i32) => void = a
    function go(): void {
      const vs: ((i32) => i32)[] = [v]
      for f in vs { print(f(1)) }
      const g = (): void => { f(9) }
      g()
    }
    go()

#### Mechanism

The module-level `f` is what `g` names, since the loop closed before `g` was written. The
validator fails inside `go` with `expected (ref $type), found (ref null $type)`, at the env
construction for `g`. D1142's captured-loop-variable resolution (`captureLoopVarIterOf`, via
`parentLoopVarOf`) finds a for-in binding of the name anywhere in the owner's body, not only
one whose loop body contains the lambda, which is the shape D2110's review found in the
emitter's own lookup. Not yet ablated.
