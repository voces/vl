### D1594 — a validation failure in the SYNTHETIC START function printed a bare byte offset, because only USER function bodies had a span row

**closed · every body the code section writes now has a row, and a module-scope failure names the STATEMENT it came from · reported by the glean session, VL-042, `~/glean/docs/vl-issues.md` · filed 2026-09-04 against master `83db028a`**

Repro (the CONTROL is a program that must keep RUNNING — the failure is injected between
the emitter and the engine, so no live miscompile is needed and none can be outgrown):

    function id(n: i32): i32 {
      return n
    }
    print(id(41) + 1)
    // vl run: 42
    //
    // VL_FAULT_INJECT=corrupt-start-fn-body vl build top.vl -o top.wasm   (rc 70)
    //   Error: invalid module
    //   top.vl:4:0: the emitted module failed to validate inside the module's top-level
    //     code: type mismatch: expected i32 but nothing on stack (at offset 0x125)
    //   this is a bug in vl, not in your program; please report it with this file
    // Was: `the emitted module failed to validate: …` — no clause, no position.
    //
    // VL_FAULT_INJECT=corrupt-validate-bytes over the SAME file still names `id`, which
    // is what makes the pair discriminating rather than two spellings of one assertion.

#### Mechanism

**[D1578](D1578.md) BANKED A ROW PER USER FUNCTION BODY, AND A PROGRAM'S MODULE-SCOPE CODE
IS NOT ONE.** `emitCodeSection`'s loop over `fnStmts` recorded `[start, end)` for each user
body; the start function, the `__log__` decoder, the shared runtime helpers and the export
wrappers were emitted after that loop and banked nothing. So `emitFnSpanAt` answered `-1`
for every offset in them and both channels fell back to the engine's own text. That is
7% of a small module and **all** of a program whose top level does the work — which is
what VL-042 reported: `Invalid input WebAssembly code at offset 39223`, no function, no
position, after an hour of bisecting a 480-line file.

**EVERY BODY NOW HAS A ROW, AND THE START FUNCTION HAS ONE PER STATEMENT.** `bankFnSpan`
takes a KIND (`emitFnSpanKindOf`, driver.vl: user function / module-scope statement /
export wrapper / runtime helper / the start function outside any statement) and a TAG for
a body with no `FuncDecl` to take a name from. `emitStartFnCode`'s merge loop — the one
place that already pairs a top-level node with the bytes it lowers, for `emitCurStmtIx` —
banks each statement's `bodyExpr`-relative range, and the tail rebases that suffix onto
the code payload once the locals vector and the size prefix are known. The whole-body row
is pushed AFTER them, because `emitFnSpanAt` returns the FIRST row holding the offset and
the narrower answer is the useful one.

**THE ANCHOR IS THE STATEMENT'S FIRST TOKEN, NOT ITS LAST.** `nodeToks[i]` is the LAST
token consumed, so a top-level `if` chain spanning thirty lines anchored at its closing
brace — measured on VL-042's own file: `62:0` for a statement that starts at line 34.
`stmtAnchorTokIx` prefers the declaring name where there is one and otherwise walks BACK
from that last token to the token whose `start` is the node's `pos`. Backwards rather than
a binary search over `P.toks`, because a merged program concatenates each module's token
stream and `start` offsets ascend only WITHIN one module.

**AND THE INSTRUMENT IMMEDIATELY DISAGREED WITH THE REPORT.** On VL-042 the located offset
is `src/checksum.vl:31:4` — a module-scope `for` loop in an IMPORTED module, not the
`is InflateError` narrowing on line 56 the reporter suspected. Byte 39223 is `local.set 2`
preceded by `struct.new` (`fb 00 0a`), i.e. a value built as a ref and stored into an `i32`
local, inside `c = bits32(0xEDB88320) ^ (c >>> 1)`. Fixing that belongs to the concurrent
row for the same consumer report; the point here is that the diagnostic named a file and a
line the bisect never reached.

**TWO SPELLERS, DELIBERATELY, AS WITH THE OFFSET PARSERS.** `vl check --codegen` renders
inside the CLI pump, which `vl build` / `vl run` never enter, so the clause is written
twice — `emitFnSpanWhere` (driver.vl) and `SpanWhere::what` (the host) — and each header
names the other. The host probes `emitFnSpanKindOf` OPTIONALLY, so a seed predating this
row still names the user functions it always could.

**THE CONTROL IS FAULT-INJECTED, for the reason `tests/vl_check_codegen_test.ts` gives at
length**: a test that must name a live miscompile gets re-pointed every time one is fixed.
`$VL_FAULT_INJECT=corrupt-start-fn-body` finds the start function through the module's own
start section (index minus the imported functions) and rewrites its body PAST the locals
vector, so the mismatch lands on the first module-scope statement rather than in frame
bytes no statement covers. The pre-existing `corrupt-validate-bytes` takes the first body
with room, which is a user function in any program that has one, so it can never reach the
start function — the two faults over one source are what make the pin discriminating.

#### Ablation

| ingredient | outcome |
| --- | --- |
| a failure in a module-scope STATEMENT | `<file>:<line>:<col>: … inside the module's top-level code` |
| the same, but in the start fn's locals vector or trailing `end` | `… inside the top-level code of <entry>` (the floor) |
| a failure in a user function body | unchanged: `… inside \`name\`` ([D1578](D1578.md)) |
| a failure in an export wrapper | `… inside the export wrapper for \`name\``, positioned at the wrapped declaration |
| a failure in a shared runtime helper | `… inside the shared runtime helper \`__str_eq__\``, no position (synthetic) |
| a failure outside the code section | unchanged: the engine's own text |
| `vl build -O` over an invalid module | unchanged: the engine's own text — binaryen's bytes are not the emitter's |
| a seed without `emitFnSpanKindOf` | the D1578 wording, degraded not lost |
| every program that BUILDS | byte-identical: 2,373 of `tests/cases/**` compared against master's compiler, 0 differ |
