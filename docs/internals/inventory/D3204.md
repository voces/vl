### D3204 — a hole or generic body reads a member through a record field typed `H | null` at a pin, which the direct spelling refuses

**now a loud check reject · a member read off a hole's field records a `memCstrTy` row, so the pin re-asks it in the direct spelling's words · fixture `tests/cases/generics/error-hole-call-through-nullable-field.vl` · was loads then traps · clause 1 · pre-existing, the same on master `94670f728` · found by the NF lane's grid (the `NR` field spelling) · filed and fixed 2026-09-29 against master `94670f728`**

Repro:

    type H = { v: i32 }
    type R = { h: H | null }
    function F(z) { print(z.h.v) }
    const r: R = { h: null }
    F(r)
    // vl check: member access '.v' on non-object H | null (the body of `F` at the call's argument types)

#### Mechanism

The direct spelling, `function F(z: R)`, refuses `member access '.v' on non-object H | null`.
A member read off an inference hole grows the hole's shape (`holeMemberTy`), and a read off an
unbounded `<T>` records a `memCstrTy` row, but a read off a hole's own FIELD (`?fld.h.z`) did
neither check at the pin: the argument check compares the parameter's shape, not a field's, so
`H | null` reached `.v` and trapped on `null`. A read off an `HD_FLD` hole now records the row,
and the pin refuses it by `memberFloorMsg`, as a first-level read of a `| null` pin is refused.
A null test on the field narrows it (D3197's `placeFieldTy` arm), so a guarded read still runs.
