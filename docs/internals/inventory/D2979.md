### D2979 — an un-annotated record literal of a defaulted literal takes an unrelated `f32` record's row, and its `i32` read is invalid wasm

**closed · was check-clean invalid wasm, the same on master `4dc94bd23` · the record-literal row scan now compares each field's checked type with the declared record's (`declRowFieldKindFits`) · fixture `tests/cases/soundness/record-literal-beside-f32-record-keeps-its-i32-row.vl` · found by the #3249 review grid · filed 2026-09-28 against master `264fd86f1`**

Repro:

    type R32 = { v: f32 }
    function ti(a: i32): i32 { a }
    const B = 3
    const q = { v: B }
    print(ti(q.v))
    // vl check: rc 0.  vl run: invalid module — type mismatch: expected i32, found f32

Want:

    3

#### Mechanism

`q` is checked as `{v: i32}`, so `ti(q.v)` checks. The emitter builds the literal at the declared
record whose field set matches by name, `R32`, although nothing hands `q` to it, so `q.v` is read
as an `f32` into an `i32` parameter. The defect is the record-row choice for an un-annotated
literal; the literal binding is scenery (a bare `{ v: 3 }` fails the same way).

Localised: `structIndexOfObjCtxGo`'s field-set scan let a DECLARED row take a value of another
code (`anonValueFitsField`'s `i32`-into-`f32` arm, then `declRowFieldFits`'s "adoption" leniency),
so `R32` was the literal's only match and `collectAnonShapes` minted it no row of its own. The
checker refuses `{v: i32}` at `R32` in every position (`const r: R32 = q` is `cannot assign`), so
no delivery earns that row. The close compares the literal's checked field type with the row's
field type by layout kind (`fieldScalarKindOf`), accepting only the widenings a record assignment
passes (`i32` into `i64`/`f64`, anything into its `| null`). The i32-into-`i64` / `| null` face,
which the checker DOES pass, is [D2987](D2987.md).
