### D17010 — two record-field hole lambdas called at different types build an invalid module once a record-field lambda is marked a hole lambda

**loud check reject · refutation pin for D17009's close: the program must stay a loud reject until it runs · `cannot infer a type for parameter x` today · clause 2 · marking a record-field lambda a value-bound hole lambda ahead of its emit lowering made it an invalid module · filed 2026-11-19 against master `818f9c547`**

Repro:

    const o = { f: (x) => x + 1, g: (y) => y * 2 }
    print(o.f(1))
    print(o.g(2.5))
    // vl check: cannot infer a type for parameter `x`

Want:

    2
    5

#### Mechanism

Under the refused candidate in [D17009](D17009.md) (the field lambdas marked at check, no emit
change), check accepts the program and the build emits `__lambda_1` at `i32` while its call
passes `f64`: `type mismatch: expected f64, found i32`. Today the check refuses it, which is
the loud answer this pin holds until D17009's emit lowering covers two fields at two types.
