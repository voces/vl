### D2317 — a one-shot build kept the module token cache, five columns per token, through check and emit although nothing reads it after the parse

**closed 2026-09-24 — with D2318, plumb's `chunk_662` live set at its last collection 143 → 118 MiB (`$VL_GC_STATS=1`), output byte-identical · a memory cost, not a miscompile: the witness runs · filed 2026-09-24 against master `7e80d135c`**

Repro:

    import { hypotF64 } from "std:math"
    print(hypotF64(3.0, 4.0))
    // runs, prints `5`. Under `vl build`, the compiler instance compiles this once and is
    // dropped, so the token rows `modScan` banked for `std:math` and for this file are dead
    // once `modCompile` has replayed them into `P.toks`.

#### Mechanism

`modScan` lexes each module when it is committed and banks the stream in the per-instance
cache (`modCacheTok*`: kind, text, start, line, col) so an editor re-committing an unchanged
file does not re-lex it. `vcLoadToksMod` replays the bank into `P.toks` during the parse loop.
A `vl build` / `vl run` instance never commits again, but the cache stayed reachable for the
rest of the compile: on `chunk_662` (520K tokens) that is ~10 MiB of `i32[]` columns next to
`P.toks`, all of it live at the emit peak.

#### Fix

`setOneShot(1)` (a new export; the host calls it from `compile_vl_instance`, a no-op on an
older seed) marks an instance that compiles once. `modCompile` then clears the cache right
after the parse loop. The LSP and the corpus harness never call it and keep the cache.

#### Grading list

`tests/vl_instance_state_leak_test.ts` and the LSP suites (a shared instance, which must keep
the cache); the three plumb units byte-identical at `--names --import-memory` with and without `-O`.
