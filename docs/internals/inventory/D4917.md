### D4917 — a list read over `string[] | S[]` (`.length`, an index, a `for`) is refused as not on every member

**closed 2026-10-31 — now prints `1` · was loud check reject, clause 2 · the list-union rewrite takes one literal-union element list, and its own `is` tests read the stored arm's tag, so each arm reads at its own rep; two literal-union lists (`J[] | S[]`) and a nullable literal element stay refused · pin: `tests/cases/unions/list-read-over-string-list-and-literal-list.vl` · found closing D4779 · the same refusal on master before D4779's close; that close keeps the union in an `is S[]` then-branch, which before it narrowed to `S[]` and read the list · filed 2026-10-15 against master `23dcd80be`**

#### Mechanism

The list-union rewrite (`luMembers`, check_list_union.vl) reads a union of lists through a
chain of `is` tests, one per member, and it declines any member with a literal element. Dropping
that guard (located 2026-10-31) still refuses `string[] | S[]`, but not `i32[] | S[]` or
`boolean[] | S[]`. The reason is that `is` over lists is structural (D4771): a `string[]` whose
elements all fit `S` passes `is S[]`, and an `S[]` passes `is string[]`. So D4779 keeps the
union in either `then` branch, and the chain's arm reads `.length` on the union again. The fix
is a rewrite that dispatches on the stored arm's tag, not on the structural `is`, which also
needs the guard dropped.
