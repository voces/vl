### D14120 — [CLOSED 2026-10-26] a list literal handed through a forwarder to a callee whose parameter adapts its element is built at its own type, not the forwarder clone's

**closed 2026-10-26 — prints `4` with `arrKeepsThread` family 3 deleted · was runs only through that workaround (check-clean invalid wasm without it) · `litRepTyAt` asks the call's instance for the parameter before the closed stamp · found by step 5b slice 3 · filed against master `63696a72e` · pin: `tests/cases/functions/forwarder-literal-adapts-to-callee-param.vl`**

Repro:

    function nest(a: i32, b: f64[]) { a + b.length }
    function fwdA(g, x, y) { return g(x, y) }
    function outerB(v) { return fwdA(nest, 3, [v]) }
    print(outerB(1))
    // vl check: rc 0.  vl run: 4

Want:

    4

#### Mechanism

mono's `fwdA` clone takes `y` as `f64[]`, which is the parameter of the callee it forwards to,
and the elaboration's call keys and instance pairing agree with it. The literal was the wrong
side. `[v]` in `outerB`'s instance is a copy, and `litRepTyAt` returned its source's closed
`nodeRepTyIx` stamp, which is one instance's type shared by every instance, before reaching the
rung that asks the call's instance for its parameter type. That rung also missed for a copy,
because `elabLitArg` was keyed by the source node with no `nodeSrc` fallback. A list literal
nested in an argument had no rung at all. The fix asks the call's instance first, follows a copy
to its source, and gives a nested literal the element type of the list holding it
(`elabArgTyAt`). `arrKeepsThread` family 3, which kept mono's threaded pair for these literals,
is deleted.
