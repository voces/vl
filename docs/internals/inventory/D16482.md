### D16482 — an annotated empty container of vectors escapes the checker's container refusal

**closed 2026-11-15 · now a loud check reject, `F32x4[] holds a 128-bit vector inside an array or map`, per D1981's array face · was check-clean invalid wasm, clause 1: `const xs: F32x4[] = []` passed `vl check` and failed to validate (`expected i32, found (ref $type)`), and the map twin was a loud emit reject · fixed 2026-11-15 by lane L: a `let`/`const` annotation runs `v128NestCheck` beside `voidStoreCheck`, as the shared annotation resolver does (check_statements.vl) · found by D16480's position sweep · filed 2026-11-15**

Repro:

    import { F32x4 } from "std:simd"
    const xs: F32x4[] = []
    print(0)
    // vl check: F32x4[] holds a 128-bit vector inside an array or map, which has no lowering yet
    //   (a `0` once a `v128` array lowers, D1981)

#### Mechanism

`tyNestsV128` answers true for both containers, but nothing reaches `v128NestCheck`. The `let`
annotation path (`check_statements.vl`) runs `voidStoreCheck` and not its sibling, and no
expression is typed with the container: the literal is empty, or a `Map()`, and nothing reads
the binding. A read of `xs`, an element in the literal, or the same annotation on a parameter or
return each refuses, as D1981 says.
