### D4066 — a declaration named like an ambient function is called by some calls and not others, and checked against the ambient signature

**closed 2026-10-12 · runs today and must keep running · was loud check reject · the refusal was wrong: the call runs the program's own `print` and is typed by the ambient one · found writing `docs/spec/modules.md` (lane SPEC) · filed 2026-10-11 against master `98a4ed71b`**

Repro (runs, prints `103` then `105`):

    function viaFn(): i32 {
      function print(x: i32): i32 { x + 100 }
      print(3)
    }
    function viaLambda(): i32 {
      const print = (x: i32): i32 => x + 100
      print(5)
    }
    print(viaFn())
    print(viaLambda())

    // BEFORE: `function print(x: i32): i32 { x + 100 }` then `const y: i32 = print(3)` was
    // vl check rc 1, "cannot bind the void result of 'y'"; a `const print` lambda was never called

Under either answer to Q11 the void-result refusal at the call goes: the program is refused
at the declaration (Q11 (a)), or it runs and `y` is `103` (Q11 (b)).

#### Mechanism

`print`, `fromCodePoint`, `fromCodePoints`, `Map` and `Set` are the five ambient
functions: visible in every module with no import (`docs/spec/modules.md` §M5.3). The row is
about these five only. The other ambient names behave consistently: a float or integer
intrinsic (`abs`, `sqrt`, `clz`, …) is shadowed cleanly by a declaration, a compiler
intrinsic (`__trap__`) refuses one, and a type name (`i32`, `Map` as a type) accepts one.

A program may declare one of the five, and nothing refuses it, but the declaration only half replaces the ambient one. A
`function print` is the function a call runs, while the call's TYPE is still the ambient
signature (`void` for `print`, `string` for `fromCodePoint`). A `const print = …` lambda is
not reached at all: the call runs the ambient `print`, so `const print = (x: i32): i32 => x`
followed by `print(5)` prints `5` where its author's lambda prints nothing. Whether the declaration should shadow or be refused is
`docs/spec/OPEN-QUESTIONS.md` Q11; either answer removes this row's outcome.

#### Ablation

| variant | outcome |
| --- | --- |
| top-level `const print = (x: i32): i32 => x`, `print(5)` | the ambient `print` runs, prints 5 (wrong) |
| the same `const` inside a function | the ambient `print` runs, prints 5 (wrong) |
| `function print(x: i32): i32 { x + 100 }`, `const y: i32 = print(3)` | refused, "cannot bind the void result of 'y'" (wrong) |
| `function print(x: string) { n = n + 1 }`, `print("hidden")` | the user's function runs, nothing printed |
| `function fromCodePoint(x: i32): string { "mine" }` | the user's function runs, prints `mine` |
| `function fromCodePoint(x: i32): i32 { x + 1 }`, `fromCodePoint(65) + 1` | refused, "'+' is not defined for string and i32" (wrong) |
| control: `function abs(x: i32): i32 { x + 100 }`, `print(abs(1))` | prints 101 (right: the intrinsic is shadowed) |
| control: `const sqrt = 3`, `print(sqrt)` | prints 3 (right) |
| control: `function __trap__(): i32 { 4 }` | refused, "is a compiler intrinsic and cannot be redefined" (consistent) |
| `type Map = { a: i32 }`, `const m: Map = { a: 1 }` | accepted |
| `const i32 = 3` | accepted |

#### Grading list

Once Q11 is ruled, every row of the table should follow the one answer: either each
declaration is refused, or each shadows the ambient name for both the call and its type.

#### Ruling

Q11 ruled 2026-10-12 as (b): the declaration shadows the ambient name, for the call and its type; intrinsics stay refused (DECISIONS.md §"A declaration shadows an ambient name of the same name"). Built: see §Fix.

#### Fix

The checker and the emitter recognise the five ambient functions by SPELLING at many sites, so
the fix makes the spelling stop matching instead of gating each site. The module merge's
scope-aware rewrite (`compiler/driver.vl`, `modRwStmt`/`modRwExpr`) renames every binding named
like an ambient function — top-level or local `function`, `const`/`let`, parameter, `for`
variable, match binding — to `name$m<module>`, with its references in scope. A single-source
program now takes the same rewrite (`ambientRenameSingle`) when it binds one of the five names;
one that does not is untouched. `$m<n>` is stripped from diagnostics as before, and a
single-source `export function print` still exports `print`. A top-level self-function keeps
its `x.print()` spelling through the UFCS alias table.

Graded on a 253-cell matrix (11 ambient names × 13 declaration positions × single-source and
module mode, each printing a value that proves which binding ran): **173/253 before, 253/253
after**; the 80 that moved are all five functions, at every face but `top_fn`/`imported`
in module mode, which already worked. The float/integer intrinsics passed before and after.
LSP hover and go-to-definition now land on the program's own binding (before: no answer, and
the hover of `const z = fromCodePoint(5)` read `string`). Fixture:
`tests/cases/functions/declaration-shadows-ambient-name.vl`.

Built-in TYPE names are unchanged: `type i32 = …` stays refused at the declaration (the D1585
ruling), `const i32 = 3` and `type Map = { … }` are accepted and both names keep working.
