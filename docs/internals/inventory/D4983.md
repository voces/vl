### D4983 — a `.map` over a type-parameter list delivered straight into a concrete list parameter is invalid wasm

**check-clean invalid wasm · clause 1 · the copy the D4928/D4963 refusal suggests, inside a closure where the narrowing does not reach the callback · related to [D2214](D2214.md) (a `.map` result delivered straight into a `readonly` list) · filed 2026-10-15 against master `d9468f145`**

Repro:

    function sumF(xs: f64[]) { print(xs.length) }
    function t<V>(q: V[]) {
      sumF(q.map((x) => x))
    }
    t([1])
    // vl check: rc 0.  vl run: invalid module, type mismatch inside `t`

#### Mechanism

A `V[]` delivered to `f64[]` is gradual to the checker, and at the `V = i32` instance a
direct `sumF(q)` converts each element. A `.map` result delivered straight into the
parameter is not converted: the instance passes its `i32[]` result where `f64[]` is taken.
Whether the instance should convert or refuse is not settled, so this row has no `Want:`.

#### Ablation

| change | outcome | needed? |
| --- | --- | --- |
| `t([1.5])` for `t([1])` | prints `1` | **yes** |
| `const w = q.map((x) => x)` then `sumF(w)` | prints `1` | **yes** |
| `sumF(q)` | prints `1` | **yes** |

#### Grading list

- Inside an `is f64[]` arm over an empty `const q: V[] = []`, a closure `() => sumF(q.map((x) => x))`
  is the same invalid module, which makes the refusal's suggested copy fail in a closure.
