### D2275 — five `expr*Array` predicates each ran their own rung ladder, so two of them could claim one expression

**runs today and must keep running — the witness prints `2.5` then `1` on master and on this change · refactor, no program changes bytes · `exprRefArray`, `exprStringArray`, `exprF64Array`, `exprI64Array` and `exprU8Array` are now projections of `exprListRep`, joining `exprF32Array` (D2270) · `list-kind-audit-2026-09.md` §4 step 2 · filed against master `ba5378dd5`**

Repro:

    type S = { n: i32 }
    function go() {
      const fm: {[string]: f64[]} = Map()
      fm["a"] = [1.5, 2.5]
      for r in fm.values() { print(r[1]) }
      const sm: {[string]: S[]} = Map()
      sm["a"] = [{ n: 7 }]
      for r in sm.values() { print(r.length) }
    }
    go()
    // vl check: rc 0. vl run: 2.5, then 1.
    // Before the change, the first `r` was claimed by BOTH exprF64Array (its recorded type)
    // and exprRefArray (the name `r` resolves to the S[] loop's slot); now it answers f64list.

#### Mechanism

Each predicate carried its own ladder of rungs: a recorded-type opener (`tyKindOf` 7/12/20,
`tyIsU8ArrayTy`; none for the ref list), a map-read rung, literal, ident, member, call, index
and concat arms. Nothing forced the ladders to disagree, so an expression could be claimed by
two predicates at once and the caller's order decided which rep it got. `exprListRep` now
answers one kind. A recorded scalar, object, function or map type answers null, and a recorded
array over a primitive answers its list, except where a float literal or a spread makes the
record differ from the rep built. Then the f32 recorded-type claim, then `arenaListRep` (the
same `tyKindOf` vocabulary the openers read, at every node shape, from one descriptor), then
`syntacticListRep`, whose rungs are the union of the five ladders. Each rung still names only
the kinds that asked it, through `gatedListRep` (D2277). The unpinned `i32[]` reading yields to
any syntactic claim, since no narrow predicate read it, except at a concat: there the recorded
list, a ref list's included, is the answer and the operands are not asked, so a chain of
`a + a + …` stays linear. Answers are memoised per expression for one outermost query, indexed
by node and stamped with the query's generation, which keeps a chain of global aliases linear:
`globalListRep` asks each global predicate, and each asks `exprListRep` of the same initializer.
`exprArray` is not moved: it is wide (any non-ref literal, any concat, a global bound to `[]`),
and its projection changes the bytes of one fixture, so it moves on its own.

#### Grading list

A shadow build ran each old predicate beside its projection at every call. Over the
self-compile it disagreed nowhere. Over `tests/cases`, the distilled corpus, `std` and
`scripts/capability-probes` (11,535 programs) it disagreed in six fixtures, every one a
double claim above: an expression two old predicates both answered true for. As a control,
the shadow built with three broken rungs (a `string[]` field read as the i32 list, and a
recorded `i64[]` as the f64 list at both recorded-type rungs) fired in 214 programs. Every one
of the 11,535 programs builds byte-identical against a `2d8341305` seed, and the compiler reaches its fixpoint in two
compiles. `rep-fuzz-check.sh` is exact, and `list-kind-grid.py --run` prints the same grid.
Nested if-expression joins at depth 30 and 60 take the same time as on master for every
list kind.

The first head of this change descended into every concat and scanned its memo linearly. Its
self-compile took 9.2–9.4 s CPU and 2.15 GB, and `const v = a + a + …` at 1,000 operands of
`i32[]` or `P[]` was a compiler trap (`allocation size too large`) where master took 1.8 s and
2.4 s. Now, over four alternating rounds with a master seed, the self-compile takes
6.95–7.09 s and 1.55 GB against master's 6.99–7.06 s and 1.57 GB, and the 1,000-operand chains
take 0.9 s (`i32[]`), 0.8 s (`f64[]`) and 1.4 s (`P[]`). The `list concat chain length` pair in
`tests/vl_scaling_shape_test.ts` reads 12.5 on that head, 1.45 on master and 0.88 now.

A recorded non-list type answers null without reading the shape, except at a call: in
`tests/cases/generics/mono-callback-bound-arm-beside-layout-twin.vl` the call
`reduce([1, 2], addTo, seed)` records `i32`, another instantiation's return, while its rep is a
ref list. Disabling the memo (`memo-generation-probe.py --run --only listRepQuery`) changes no
program's bytes and brings back the compiler trap in `tests/cases/globals/global-reference-chain-cost.vl`.
