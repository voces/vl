#### Mechanism

`holeLetJudge` (`compiler/check_relate_core.vl`) collects every function a `let` may hold
(`elabFnLetMembers`) and refuses through `holeLetDisagreeMsg` when their results at the call's
widened parameters differ. A list element (D15791) and a call result (D13965) keep the member set
and the call dispatches on the member it holds. A `let` has no such lowering, so the judge's
refusal stands in for one.

#### Close

A written `let` and a `const` choice of un-annotated functions are sets the tag decision can
lower as an id; a call through one dispatches on the member it holds and gives the join of their
results, as a list element's does (D15791). Now run: the witness and `run(false)` (`4`), returned
and called (`sel(true)(3)`), three members, a loop re-pointing the binding, a closure capturing
it, an `is` narrowing of the result, generic members, `const g = if c { str } else { inc }` and
D9003's `i32`/`f64` pair (`1.5`, where it once trapped). Still refused: a use the join cannot
serve (`f(3) + 1`), a seed returning a value later written with one returning nothing (owner
ruling B2), a hand to an open parameter (D16009) and lambdas (D16090).
