### D3848 — a `let` alias of a hole lambda written with a value of concrete function type (a typed parameter, an annotated lambda) leaves the hole lambda at its `i32` default

**closed 2026-10-08 by lane SC · was check-clean invalid wasm · found in review of #3442 (`p06`, `p06b`, `p06d`, `p02`) · filed 2026-10-08 against master `7eca4407b` · pins: `tests/cases/closures/hole-lambda-alias-written-values.vl`**

Repro:

    function f(x: string, p: (y: string) => string) {
      const c = (y) => y + "C"
      let d = c
      const g = () => d(x)
      print(g())
      d = p
      print(g())
    }
    f("a", (y: string) => y + "P")
    // vl check: rc 0.  vl run: invalid module inside `c`, `expected (ref $2), found i32`

Want:

    aC
    aP

#### Mechanism

The alias walk of D3844/D3845 declines when a `let` in the chain, or a capture cell, is written
with a value it cannot trace to a hole lambda, and the hole lambda then stays at its `i32`
default. A value recorded at a function type naming no type variable, such as a typed
parameter `p`, needs no tracing: the call's arguments fit that type, so the lambda is pinned
at them (`monoValueFnTyConcrete`). The pinning peer of a write `d = e` may itself have no hole:
`monoAssignedPeerFe`'s caller now takes the pins of an annotated, never-instantiated peer from
its declaration (`p02`, a module `let` initialized with an annotated lambda and written from
a sibling function). The write index is banked on an arena prefix, so writes in instance
bodies cloned during the pass join it.
