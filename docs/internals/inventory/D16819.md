### D16819 — a maker returning its lambda through a local `const`, its two call bindings both called at two pins, is refused at emit

**open · loud emit reject · clause 2 (`vl check` rc 0) · the two-binding residue of [D16818](D16818.md) and [D16815](D16815.md) · cell `lambda_bound_first` of `maker-generic-at-two-results.matrix.vl` · filed 2026-11-16 against master `fae99e93f`**

Repro:

    function adder(n) {
      const f = (a) => a + n
      return f
    }
    const v = adder(2)
    print(v(3))
    const x = adder(1.5)
    print(x(2.0))
    // vl check: rc 0.  vl run: emit error, `a function-value call has no interned signature — parameter 1 of type `_` has no representation in the function-value ABI`

Want:

    5
    3.5

#### Mechanism

Parked 2026-11-16 by lane AE, traced this far. Both instances' lambdas are lifted at one signature,
`(f64) => f64` (with `v(3.0)` the program runs, `5` `3.5`), so the `i32` call through `v` finds no
closure built for it. The plumbing classes are already per maker instance: the slot of `f`, read
in maker instance 0, finds one call at `(i32)`; in instance 1, one at `(f64)`; one member each. The
leaf then finds no lambda instance at those parameters and stays open.

Ruled out, each built and graded with no movement and no regression: a member lookup under the
instance being read (`EPL.k`) when the root lookup misses; `eplFrameMember`, which demands the
instance under the frame, for a holder read in the member's own enclosing instance; and D16711's
`elabLamDeliveredNumRet` given the instance's own parameters at `monoLamPinRetAnn`. The suspect is
mono's instancing of a lambda bound to a `const` (`monoCloneLambdaSubst`, `monoLamInstanceNamed`),
which the directly returned lambda does not take.
