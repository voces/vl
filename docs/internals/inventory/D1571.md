### D1571 — an imported value named like a builtin type made the type unspellable, because the merge's rename map is ONE namespace and the language is TWO

**closed (fixed) — `modTyRenamedSeg` is the one home of the TYPE-position rename and it renames a BUILTIN type name only from a `type` row; the export stays legal, which is what the tree's own rule for user type names already says · was a loud check reject at `vl check` (clause 2: `vl check` refused a legal program) · ZERO corpus cells, 0 runs → not-runs · reported by the glean session, VL-015, `~/glean/docs/vl-issues.md` · filed 2026-09-03 against master `4490423c`**

Repro (runs, prints `2` then `4`):

    // file: lib.vl
    export function u8(x: i32): i32 { return x + 1 }

    // file: main.vl
    import { u8 } from "./lib"

    const b: u8[] = [1, 2]
    print(b.length)
    print(u8(3))

    // BEFORE: main.vl:3:12: unknown type 'u8' within 'u8[]'

#### Mechanism

**THE TREE'S RULE IS "TWO NAMESPACES", MEASURED NOT ASSUMED.** `type Circle` + `function
Circle` in one file is `vl check` rc 0 and both names work; so is `type Circle` + `const
Circle`; and so is a module exporting BOTH, imported by name — the importer spells `Circle`
as a type and calls `Circle(3)` in the same file. A single-file `function u8` beside `const b:
u8[]` was rc 0 all along. So the brief's second horn is the one the tree is on: the export is
legal and the IMPORTER's type resolution was consulting the value namespace.

The consulting happens in the MERGE, not the checker. `modBuildRename` mints one row per
top-level declaration — `FuncDecl`, `LetDecl`, `TypeDecl`, `UnionDecl` alike — plus one per
import, and `modRwTsName` rewrites every identifier segment of a type annotation through it.
For a USER name that is harmless and always has been: a type and a value of one name mint the
SAME `Circle$mN` target, so the two readings never disagree. A BUILTIN name has no declaration
and therefore no row of its own, so the VALUE row was the only one — `import { u8 }` rewrote
`u8[]` to `u8$m1[]`, which resolves to nothing, and the checker said so about a name that had
never left the primitive.

**THE GATE IS THE ROW'S KIND, AND IT LIVES IN ONE FUNCTION.** `modBuiltinTyTargets` holds the
merged targets of `type` declarations that took a builtin name; `modTyRenamedSeg` renames a
builtin-named segment only onto one of them and returns every other segment's answer byte for
byte. Registering on the TARGET is what lets an IMPORT row carry no kind of its own — it
renames onto the dep's own `u8$mN`, which the dep's row already registered, and
`modCollectSelfFns` builds every module's map dependency-first before any rewrite runs.

**ONE HOME BECAUSE THERE ARE TWO ROUTES.** The first fix guarded only `modTypeRenamed`, the
character scanner, and changed nothing: a `TypeRef` annotation goes through the spelling TREE
(`modRwTsName`), and the scanner is its fall-through. Both now call `modTyRenamedSeg`.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the `import` (an un-exported `u8` in the dep) | runs — the importer mints no row | **yes** |
| the second module (one file, `function u8` + `u8[]`) | runs — no merge, no rename map | **yes** |
| `u8` being a BUILTIN name (`function circle` + `Circle[]`) | runs — the type row mints the same target | **yes** |
| the value/type collision (`export type u8`) | runs BEFORE and after — a `type` row may rename | **yes** |
| `u8` specifically (`string`, `i32`, `f64`, a `{[string]: i32}` key) | same defect at every primitive spelling | no |

#### Grading list

* `tests/cases/modules/builtin-type-name-export/` — the value face, at six delivery positions: the imported `self`-function called both ways, an annotation, an array element, a `string`/`i32` annotation one line from their value use, and a `{[string]: i32}` MAP KEY (the tree walk's `TS_MAP` arm, which the character scanner would have missed).
* `tests/cases/modules/builtin-type-name-user-type/` — THE CONTROL, and it is the reason the rule is narrow: a rule spelled "a builtin name is never renamed" would have taken this program away without saying so. **The OWNER has since taken it away deliberately (D1585, 2026-09-04)** — an exported `type u8` is now refused at its declaration, and the fixture asserts the refusal rather than `@log 5`. D1571's rule is unchanged: it is about a VALUE row, and `builtin-type-name-export/` is untouched.
