### D3089 — a hole function's `.map` or `.filter` over a list literal of its parameter traps on a `null` at a `string | null` pin

**closed · `exprNulStrArray` asks the pin of the instance for a list whose recorded element is a type variable, so the element read of such a result keeps the `null` · fixture `tests/cases/generics/hole-map-nullable-string-pin.vl` · was loads then traps · clause 1 · the residue of [D3066](D3066.md)'s close: the `mcapidx`, `mcapx` and `nested` `nsnull` cells of the lane HL grid, and 9 `snN` cells of the #3237 review grid (`lamList`, `litFilter`, `litMap`), which were invalid wasm on master · filed 2026-09-28 against master `d408f2da4`, closed 2026-09-28 against master `f14a8cca2`**

Repro:

    function f(x) {
      print([x].map((e) => x)[0])
    }
    const v0: string | null = null
    f(v0)
    // vl check: rc 0.  vl run: wasm trap: null reference (before the close)

Want:

    null

#### Mechanism

A `(string | null)[]` shares the plain string list's backing, and only its element read differs:
it keeps the `(ref null)` where a `string[]` read recovers non-null. `exprNulStrArray` decides
which, and it read the list's recorded element type. Inside a hole instance a `.map` or `.filter`
result's recorded element is the hole's variable, so the read recovered non-null and trapped on
the `null` before `print`'s own null test ran. The classifier now asks what the element holds at
the instance's pin (`iterElemPinTy`) when the recorded element names a type variable. The `<T>`
spelling was right already because its exact instance substitutes the recorded type.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `const m = [x].map((e) => x)` then `print(m[0])` | traps | no |
| `(e) => e` in place of `(e) => x` | traps | no |
| `.filter((e) => true)` in place of `.map` | traps | no |
| `const v0: string \| null = "s"` | prints `s` | **yes** (the `null`) |
| an `i32 \| null` pin, no string-literal union declared in the module | prints `null` | **yes** (with one declared, a `cast failure` trap: [D3092](D3092.md)) |
| `function f<T>(x: T)` | prints `null` | **yes** (the hole) |

#### Grading list

The lane MT grid's `string | null` cells, both value orders: every `.map`, `.filter`, bound
result, bound list and `for` face runs (part of [D3092](D3092.md)'s 3,190). A hole
`string | null` value STORED into a string list, by index assignment or as a nested literal's
element, still recovers non-null and traps: that is [D3114](D3114.md), a store-side sibling this
read fix does not reach.
