### D14910 — a generic's `const l = [x]` read from module scope had an `i32` cell kind

**closed 2026-11-01 by `readSlotlessOwnLet` declining a function body's `let` at module scope · runs, prints `true` then `1` · was a wrong store answer no consumer acted on: `collectA`'s frame-blind walk asked `exprString` of `[l[0]]`'s element at frame `-1`, and the read of `l` inside `f<T>` was answered as module scope's own `let`, at the template type `T[]`, so `letCellKind` said `i32` · 4 name reads in 2 files · filed 2026-11-01 against master `6850065c`**

Repro:

    function f<T>(x: T) {
      const l = [x]
      for e in [l[0]] { print(e) }
    }
    const t: boolean | null = true
    f(t)
    const i: i32 = 1
    f(i)

Want:

    true
    1

#### Mechanism

`readDeclOwnerOf` answers `-1` both for a module-scope binding and for a binding no frame on
`fnIx`'s chain declares. Asked at `fnIx = -1` (module scope, which `collectA`'s whole-program walk
uses), every `let` therefore looked like module scope's own, and `identStoreVKind` read the
binding's cell at module scope: the generic template's `T[]`, which names no rep, so `letCellKind`
fell to `i32`. The instances emit `l` as `(local $1 (ref $4))`, a list, and every ask from the
instance frame was right all along. The fix: module scope declares no `let` the checker recorded
inside a function body (`letDeclFn`), so such a read has no cell at `-1` and the ladder answers it.
