### D3287 — a member read through a nullable field of a hole parameter is accepted and traps on `null`

**now a loud check reject · the pin re-asks a member read off a hole's field, element, call result or `is` remainder for a `null` member, in the direct spelling's words · fixtures `tests/cases/generics/error-hole-member-read-through-nullable-field.vl`, `tests/cases/generics/hole-guarded-member-read-through-nullable-field.vl` · was loads then traps · clause 1 · 70 cells of the flow-narrowing join grid of #3304 (member use, hole spelling, field and element places), every one present on master · filed 2026-09-29 against master `296e1141d`, fixed 2026-09-29 against master `e70102886` · closes D3204 by the same rule**

Repro:

    type O = { n: i32 }
    function no(v: i32): O | null {
      if v < 0 { return null }
      return { n: v }
    }
    function f(b) {
      return b.v.n
    }
    print(f({ v: no(3) }))
    print(f({ v: no(-1) }))
    // vl check: member access '.n' on non-object O | null (the body of `f` at the call's argument types)

#### Mechanism

The body of an un-annotated `f` records `.v` and `.n` as field demands on its hole, and the call
site checked the demands against the argument's shape, `{ v: O | null }`, never asking the `.n`
read about the `null` member. A member read off a derived hole a `null` can reach (`HD_FLD`,
`HD_ELEM`, `HD_ELEMV`, `HD_RET`, and an `is` remainder `HD_GNOT` of a non-null type) now records
a `memCstrTy` row (`noteNullReadCstr`, prop `?.` + name) that the pin answers only for a `null`
member, with `memberFloorMsg`'s sentence; every other floor stays unasked, which is what keeps
the `is`-else reads of D3216 at master's behaviour. A null test narrows the read to the hole's
non-null face, which records nothing, so a guarded read runs. A write narrows a hole's field to
the written value (`holeFieldWriteTy`): a hole value is read as itself, whose reads the pin
re-asks the same way, so `b.v = a; b.v.n` runs where `a` is pinned non-null.
