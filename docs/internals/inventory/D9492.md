### D9492 — a function returning a mixed-width numeric literal union is not assignable to one returning `i64`

**closed 2026-10-22 by lane-D9490 · now a loud check reject, DESIGN, `cannot assign () => N to 'g' of type () => i64` · clause 2 · closed as the rule `tests/cases/types/fn-value-numeric-return-invariant.vl` pins: a named function VALUE's numeric result is invariant inside a function type, so `() => N` relates to `() => i64` no more than `() => i32` does; a lambda LITERAL in the same position adopts the wider result and converts at its return, and that spelling, `const g: () => i64 = () => f()`, was refused too and prints `2` since this close (`numLitUnionConvertsRet` in `finishInferredReturn`, check_inferred_return.vl) · fixtures `literal-unions/fn-value-lambda-adopts-num-litunion.vl`, `literal-unions/error-fn-value-i32-as-num-litunion.vl` (the value spelling), matrix `fn-value-lambda-num-litunion-as-wider-scalar` 19 → 46 of 48 · residue [D9523](D9523.md) · found closing [D9382](D9382.md) · filed 2026-10-21 against master `56e51b394`**

Repro:

    type N = 1 | 2 | 5000000000
    const a: N = 2
    const f: () => N = () => a
    const g: () => i64 = f
    print(g())
    // vl check: cannot assign () => N to 'g' of type () => i64

#### Why a check refusal

`numLitUnionBaseTy` answers -1 for a union whose literals soften to two widths, so D9382's slot
rule (`fnSlotStoreTy`) does not apply. `N` is a value box here, not an `i64`, so `f` and `g`
cannot share one signature, and relating them would need an adapter at the assignment. That is
exactly the case the numeric invariance rule refuses for `() => i32` into `() => i64`, and
accepting it for a literal union alone would make the union more permissive than its own
widest member. The lambda spelling needs no adapter: the lambda adopts `i64` when every value it
returns converts to `i64` exactly (the numeric-join ruling), and the return seam converts.

The invariance rule's fixture says no adapter thunk exists at the assignment seam. The
function-value adapter (`fvaAdapt`, DECISIONS.md, "A function value at another function type is
adapted where it is delivered") now exists, so lifting numeric invariance is a language
decision for every numeric function value, not for this row.
