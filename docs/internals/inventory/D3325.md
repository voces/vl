### D3325 — a record-list read out of a hole's field and handed to a second hole callee has no monomorphization pin

**loud emit reject · clause 2 · found by #3305's review · the same on master `b6378e95b` · filed 2026-09-30 against master `b6378e95b`**

Repro:

    type O = { n: i32 }
    type P = { v: O | null, xs: (O | null)[] }
    function mk(n: i32): P { return { v: { n: n }, xs: [{ n: n }, { n: n + 1 }] } }
    type P2 = { v: O, xs: O[] }
    function popf(a) { a.pop() }
    function t(z) { if z.xs[0] != null { popf(z.xs)
     print(z.xs[0].n) } }
    t(mk(3))
    // vl check: rc 0.  vl run: emitProgram: monomorphize: unsupported argument type for `a` in a call to `popf`

Want:

    3

#### Mechanism

Not traced. The refusal is raised where a hole callee's argument type is named at its pin: `a`
is bound from `z.xs`, itself a read through another hole's field, and no rung names a list of
records reached that way. The nullable element is not the ingredient (a plain `O[]` refuses the
same way) and neither is the callee's body (`return a` and `a.push(null)` refuse alike).

Every variant below is the filed program with ONE edit.

The filing's claim stands: the `popf`-annotated twin is a CHECK reject. `popf(a: (O | null)[])`
alone gives `member access '.n' on non-object O | null (the body of `t` at the call's argument
types)`, because the call ends the narrowing of `z.xs[0]` at the pin. Annotating both is a check
reject too (`'z.xs[0]' is no longer narrowed to O: the call to 'popf' on line 6 may reassign it`),
so the guarded read can only be written with a re-test. Annotating `t(z: P)` alone RUNS and prints
`3`. A twin with no `.n` read after the call (`popf(z.xs)` then `print(1)`) runs under every
annotation, which is why the un-guarded variants below grade the pin rather than the narrowing.
