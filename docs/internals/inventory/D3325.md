### D3325 — a record-list read out of a hole's field and handed to a second hole callee has no monomorphization pin

**loud emit reject · clause 2 · found by #3305's review · the same on master `b6378e95b` · filed 2026-09-30 against master `b6378e95b`**

Repro:

    type O = { n: i32 }
    type P = { v: O | null, xs: (O | null)[] }
    function mk(n: i32): P { return { v: { n: n }, xs: [{ n: n }, { n: n + 1 }] } }
    type P2 = { v: O, xs: O[] }
    function popf(a) { a.pop() }
    function t(z) { if z.xs[0] != null { popf(z.xs)
     print(z.xs[0].n) } }
    t(mk(3))
    // vl check: rc 0.  vl run: emitProgram: monomorphize: unsupported argument type for `a` in a call to `popf`

Want:

    3

#### Mechanism

Not traced. The refusal is raised where a hole callee's argument type is named at its pin: `a`
is bound from `z.xs`, itself a read through another hole's field, and no rung names a list of
records reached that way. The nullable element is not the ingredient (a plain `O[]` refuses the
same way) and neither is the callee's body (`return a` and `a[0].n` refuse alike).

The filing said the annotated twin is a check reject. It is not: annotating `popf`'s parameter,
annotating `t`'s, or both, all RUN and print `1`. (`t(z: P2)` fed `mk(3)` is a plain type error,
`expected P2, got P`, because `mk` returns a `P`; that is an ill-typed program, not a twin.)

#### Grading list

The un-annotated `const ys = z.xs` spelling, which is the second delivery position, and `popf`
returning its argument. [D2920](D2920.md) is the sibling for a record list built INSIDE a hole
body (`[x]`); this row is a list handed IN from a field, and the two may share a rung.
