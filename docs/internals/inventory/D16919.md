### D16919 — a record binding re-pointed at another record binding of a different function set builds an invalid module

**closed 2026-11-17 by lane AE — the witness prints `6` · the tag decision tagged the joined set `{inc0, dbl}` without re-typing `q`'s record literal, so `q` was built at a closure list holding ids: a record literal a write reads through a binding read nowhere else now joins and is stamped at the written binding (`ftRecWriteJoins`, `ftStoreLits`, `compiler/check_fn_tag.vl`), its field's list is kept at the tagged type where mono pins the `const` (`monoPinObjFields`), and a record binding read elsewhere too, holding another set, keeps the set untagged (`ftRecSourceKeepsRow`) · fixture `tests/cases/closures/record-repointed-at-record-binding-of-other-set.vl` · was: check-clean invalid wasm · clause 1 · found by lane AE on the [D16916](D16916.md) position matrix · filed 2026-11-17 against master `4e9738079`**

Repro:

    function inc0(a) { return a + 1 }
    function dbl(a) { return a * 2 }
    let r = { f: [inc0] }
    const q = { f: [dbl] }
    r = q
    print(r.f[0](3))
    // vl check: rc 0.  vl run: invalid module, a `(ref $q's row)` stored where `(ref null $r's row)` is wanted

Want:

    6

#### Mechanism

The call through `r` tags the joined set `{inc0, dbl}`, and the write `r = q` makes `dbl` one of
its ids. The store path followed `q` to its initialiser literal only where the record solve had
widened that literal, so `q`'s record was built at `r`'s row with its field's list still a closure
list, which then held an id; mono's pin of the `const` also closed that list back to a signature.
