### D1821 — a helper whose parameter is annotated with a CONCRETE function type takes the argument the first instance pinned it with, and the checker's own refusal is lost at the pin

**closed 2026-09-06 — the witness is now a loud check reject, `argument 1: expected (i32) =>
i32, got (i32) => f64` · was `loads then traps`, `wasm trap: indirect call type mismatch` after
printing the first pin's value · clause 1 · filed against master `23c39222e`, named without an
id by the argument-hop row [D1795](D1795.md), whose close does not reach this spelling; closed
against master `fbfe3ff40` · fixtures `tests/cases/generics/pin-argument-recheck.vl` and
`pin-argument-recheck-ok.vl`**

Repro:

    function o(n) {
      function k(x: i32) { return n }
      function use(p: (i32) => i32) { return p(1) }
      return use(k)
    }
    print(o(2))
    print(o(2.5))
    // vl check: rc 0, "Found 0 errors, 1 warning."
    // vl run:   prints 2, then
    //           wasm trap: indirect call type mismatch

#### Mechanism

**Measured, and the prediction was half right.** The filed reading said the checker owed the
diagnosis and the pin threw it away. The probe — the checker's own `tErr` channel, since
`typecheck.vl` cannot import `emit_bytes` — shows the comparison is not skipped at all. It runs
and it passes:

    witness   ARG n=1 want=[(i32) => i32] got=[(i32) => _] ok=1 gotHasVar=1
    direct    ARG n=1 want=[(i32) => i32] got=[(i32) => f64] ok=0 gotHasVar=0

At check time the argument's type still rides the enclosing frame's unsolved hole, and a hole is
assignable to anything, so `assignableExpr` answers yes CORRECTLY. The deciding type does not
exist yet. It is a comparison asked one pass too early, not a lost one.

The close parks the demand and re-asks it where the type arrives. `notePinnedHole` is that
moment, and it sees each pin separately before the bank collapses — probed, because the whole
design rests on it:

    PROBEPIN name=[?o.0] ty=[i32]
    PROBEPIN name=[?o.0] ty=[f64]

That is what `holePinTys`'s own `-2` poisoning could never tell you: the collapsed bank knows
two calls disagreed but not which one offends. `argPinPark` records the demand where a
CONCRETE parameter accepted a hole-bearing argument, and `argPinRecheck` substitutes each pin
as it lands and re-asks `assignable`, reporting through `argMismatchErr` — the same sentence,
with the pin's own types. It is `holeCastPinCheck`'s shape (D1342) in the other direction:
there the parameter is the hole, here the argument is.

**The first candidate was refused by the fixtures, and its price named the scope.** Parking on
the hole NAME and re-asking every pin lost a `runs` cell:
`functions/generic-fn-value-explicit-type-param.vl` passes one `idT<T>` to two concrete
boundaries in one program, and `T` is bound per boundary — so a row parked at `applyTS(idT)`
was re-asked against `applyTI`'s `i32` and wrongly refused. Two soundness rejects also gained a
second sentence for one fault, the recorded demand (`holeDemandOk`) having already reported.
The scope that survives both: the demand parks only where the parameter's expected type is a
FUNCTION type and the argument is not itself a generic function value the boundary binds.
