### D17725 — a map read of a tagged set's id, returned in a list a `for` walks and calls, is recorded non-null though its key may be missing

**loud emit reject · clause 2 · `the compiler cannot yet lower this statement (narrowed read)` · filed 2026-11-27 against master `ff95d049f` (lane COV-CLOS) · the read's typing is fixed (see Mechanism); the walk's narrowed read is what still refuses · owner I8-PREP**

Repro:

    function inc(a) { return a + 1 }
    const m = Map()
    m["k"] = inc
    function ret() { return [m["zz"]] }
    for f in ret() { if f != null { print(f(3)) } else { print("none") } }
    // vl check: rc 0.  vl run: emit error at the loop's narrowed read (narrowed read)

Want:

    none

#### Mechanism

In this program the checker records the map read `m["zz"]` inside `ret` as the bare function
type `(i32) => i32`, both at the instance and as recorded (`nodeTyAt(ix, -1)`), so `ret`'s list
is built at a non-null closure element and the IR's id-to-closure crossing (RTagClo, #10536)
takes the read's i32 with no null arm. The loop variable is that closure, while its narrowed
read is typed `((_) => _) | null`, so the read refuses. That refusal is the only thing between
this program and a trap: a lowering for the narrowed read alone would turn the missing key into
`unreachable` where `none` is owed. The same `ret` indexed at module scope types the read
nullable and prints `none`. Fix the read's recorded type first; only then let the walk's
narrowed read take `irConvert`.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the `for` (`const f = ret()[0]`, then the same test) | runs, prints `none` | **yes** |
| the call of `f` (`print(f == null)` in the body) | refuses, `return refused` | no |
| `ret()` bound to a `const` first, then walked | still refuses (`narrowed read`) | no |
| the list returned (`for f in [m["zz"]]` inline) | refuses, `return refused` | no |

#### The typing half, fixed

The non-null record was the monomorphizer's, not the checker's: `monoStoredSlotFnTy` closed each
value written into the list's function slot at the slot's pinned type through `monoRecordOpen`,
which dropped the open read's `| null`; `monoRetFnListTy` held `ret`'s list at the pin's non-null
element the same way. Both now keep the null the checker gave the node (`tyKeepNullOf`), so `ret`
builds a nullable element and `const f = ret()[0]` prints `none`
(`maps/map-read-of-a-fn-slot-returned-in-a-list-stays-nullable.vl`). The walk still refuses at its
narrowed read: the variable is held at `((i32) => i32) | null`, while the read `f` in `f(3)` is
recorded at the open `((_) => _) | null`, as if the loop's `f != null` narrowed nothing.
