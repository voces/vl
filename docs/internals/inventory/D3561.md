### D3561 — a trap frame names the function's declaration line, and `-O`/`-O3` dropped the only per-statement map

**closed · sunpa SP-010 · filed 2026-10-03 against master `fae55dec2`, closed by `vl build --source-map` + `vl addr2line`**

Repro:

    const xs = [1, 2, 3]
    export function pick(i: i32): i32 {
      let s = 0
      for k in 0 until 3 { s += xs[k] }
      s + xs[i]
    }
    // vl build --names -O3, then pick(7) from JS:
    //   RuntimeError: array element access out of bounds
    //       at pick@2 (wasm://wasm/vl-…:wasm-function[0]:0x5a)
    // `@2` is where `pick` is declared; the read is on line 5.

#### Mechanism

A name-section entry is per FUNCTION, so its `@file:line` suffix can only be the declaration's.
The per-statement `vl-src` rows that `vl run` joins against a frame's offset describe the
EMITTER's bytes, so the host strips them before the first `wasm-opt` run, and an optimized
module had no line table at all. And a JS host never reads `vl-src`. The fix converts the rows
to a source map v3, which is the wasm convention: one generated line, and each segment's column
a MODULE byte offset, the same offset V8 prints after `wasm-function[i]:`. Nested rows are
flattened so the narrowest one wins. The map goes through every `wasm-opt` run (the escape
step and the rung) as `--input-source-map`/`--output-source-map`, and a `sourceMappingURL`
section names it. `vl addr2line` reads the map back, or the `vl-src` section of an unoptimized
`--names` build.

#### Grading list

`tests/vl_addr2line_test.ts` traps each module under Deno's V8 and maps the offset the engine
printed: the witness at plain, `-O`, `-O3`, `--names` and `-O3 --names` (line 5); a 300-line
function at `-O3` (line 251, where the name section reads `big@2`); a callee inlined at `-O3`
(binaryen keeps the CALLEE's line, `helper.vl:6`, in the caller's frame); a pasted trace on
stdin; and builds without the flag, which write no map and no section.
