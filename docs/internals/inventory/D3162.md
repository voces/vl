### D3162 — at module scope, a `continue` guard's narrowing does not reach a lambda written in an interpolation hole

**loud check reject · open · clause 2 · found by the #3281 round-2 review (`rv3281r2-5785/c/c_interp_cont_mod.vl`) · the same on master `b1794003a` · filed 2026-09-29 against master `b1794003a`**

Repro:

    type K = "a" | "b"
    function sk(x: K) { return x }
    const vs: (K | i32)[] = ["a", 3, "b"]
    for e in vs {
      if e is i32 { continue }
      print("<\{(() => sk(e))()}>")
    }
    // vl check: argument 1: expected K, got K | i32 — 'e' is not narrowed inside the function
    // on line 6: it may run before 'e' is narrowed

Want:

    <a>
    <b>

#### Mechanism

Not localised past the ablation. The checker's post-guard narrowing (`if … { continue }`) of a
module-scope loop variable is visible to a lambda written as a statement or in a plain
argument, but not to one written inside a template-string hole. The same hole inside a function
checks.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `print((() => sk(e))())`, no interpolation | checks, and runs on #3281 | **yes** (the interpolation hole) |
| the loop inside a function | runs | **yes** (the module scope) |
| `if !(e is i32) { print("<\{…}>") }`, no `continue` | checks, and runs on #3281 | **yes** (the post-guard narrowing) |
| a `K \| i32` parameter guarded by `if e is i32 { return }` | runs | **yes** |
| `if true { const f = () => e; print("\{f()}") }` after the guard (`c/c_rawblock_cont_mod.vl`) | `an interpolation hole is … — this one is K \| i32` | no (a second face: the lambda's result keeps the un-narrowed type) |

#### Grading list

The witness, its in-function twin, and the `if !(…)` spelling.
