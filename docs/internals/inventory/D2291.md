### D2291 — a map's index and its compaction disagreed about the target size, so steady insert/delete churn grew the index and shrank it back every cycle

**closed 2026-09-23 — the witness prints `done`; a steady churn at a fixed live window now
settles the index at one capacity instead of cycling 16→32→64→16 (measured with temporary
byte-counter instrumentation, not committed) · reported in review of #3101 · filed against
master `b088e0749`**

Repro:

    const m: {[i32]: i32} = Map()
    for k in 0 until 200 {
      m[k] = k
      if k >= 4 { m.delete(k - 4) }
    }
    print("done")
    print(m.length)
    // prints done then 4

#### Mechanism

`__map_resize__` grows the index whenever `count*2 >= len(index)` (D2280 — `count` bounds
occupied slots, live and dead). `emitMapCompact` reclaimed tombstones whenever
`count - size > size + INITIAL_CAP`, then rebuilt the index at `next pow2 >= 2*size`. The two
targets disagreed: a steady insert/delete churn at a fixed live size `N` drives `count` up to
roughly `2*N + INITIAL_CAP` between compactions — enough to make `__map_resize__` double the
index once or twice past `2*N` before compaction's own trigger fires and rebuilds it back down
to `next pow2 >= 2*N`. At `N = 4` this cycled the index 16 → 32 → 64 → 16 every ~13 operations,
each turn paying a full rehash both growing and shrinking.

Fixed by changing ONLY `emitMapCompact`'s target capacity, not either trigger: it now rebuilds
at the next pow2 STRICTLY ABOVE `4*size + 2*INITIAL_CAP` — algebraically the exact ceiling
`__map_resize__` would already grow the index to on its own before compaction's UNCHANGED
trigger next fires (compaction bounds `count` at `2*size + INITIAL_CAP`, and resize doubles
whenever `count*2 >= cap`, so `cap` must exceed `2*(2*size + INITIAL_CAP)`). Landing on
resize's own ceiling rather than `2*size` is what stops the shrink from immediately being undone
by the next few inserts. The compaction TRIGGER, and hence the amortized call frequency, is
unchanged — an earlier version of this fix instead tightened the trigger to preempt resize
directly (`count*2 + 2 >= len(index)`), which did eliminate the growth but compacted 4-5x more
often at a smaller size each time and cost 30-80% MORE CPU on the churn benchmarks below; that
approach was reverted in favor of this one.

An insert-only program never calls `emitMapDelete`, so it never reaches `emitMapCompact` at
all — its index sizing is byte-for-byte unchanged.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the `delete` (insert-only) | `emitMapCompact` never runs; index sizing unchanged | **yes**, this is the "byte-for-byte unchanged" case |
| a window of 100 or 1000 instead of 4 | same cycle, larger caps (256↔512, 2048↔4096); same fix stabilizes at 512 / 4096 respectively | no, confirms the fix generalizes |

#### Grading list

Measured with `/usr/bin/time -v` (median of 5 runs), 1M and 25M churn operations at windows
4/100/1000, alternating against master (`709d73205`) — CPU (user+sys) fell 11-21% at every
window/scale pair measured, peak RSS fell (small scale) or held equal within noise (large
scale, where the wasmtime/GC baseline dominates the index's few-KB delta), never rose:

| window | ops | master CPU | fixed CPU | master maxRSS | fixed maxRSS |
| --- | --- | --- | --- | --- | --- |
| 4 | 1M | 0.09s | 0.08s | 94.1 MB | 75.3 MB |
| 100 | 1M | 0.09s | 0.08s | 71.8 MB | 62.4 MB |
| 1000 | 1M | 0.08s | 0.07s | 61.6 MB | 54.0 MB |
| 4 | 25M | 1.53s | 1.21s | 263.4 MB | 263.5 MB |
| 100 | 25M | 1.84s | 1.61s | 263.5 MB | 263.4 MB |
| 1000 | 25M | 2.32s | 2.07s | 263.2 MB | 263.4 MB |

`bench/collections/map-i32`, `map-string` and `word-freq` (none call `.delete`, so this row's
own threshold change touches no byte any of them emit) are unaffected at `-O`, the reading
that matters for a real build: `bench/run.sh`, 9 reps, `vl-O` medians map-i32 1164ms (master) vs
1161ms (fixed), map-string 889ms vs 855ms — both within ordinary run-to-run noise on a loaded
box. The unoptimized `vl` (no flag) column is noisier and not the deployment path; it moved by
up to +11% on map-i32 in one pairing and −6% in another, consistent with contention rather
than a direction this row's own change could cause.
`tests/support/nativeRelease.ts`'s `SHAPE_TABLE` rows for those three benchmarks moved on
per-instruction byte count from D2290's trap message alone (structural counts — `fns`,
`allocs`, `indirect`, `refEq` — unchanged).
