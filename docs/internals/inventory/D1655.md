### D1655 — a module-scope binding of a ref-list-returning call takes the i32 cell, because `globalCellKind`'s memo stamps no generation for the pass that fills the inferred return kind

**closed 2026-09-05 · was check-clean invalid wasm (`type mismatch: expected i32, found (ref $type)`, exit 70) · filed 2026-09-05 against master `ea407d11a` · found by `matrix/covar-list-delivery.matrix.vl`, `return_inferred`/un-annotated · 0 corpus cells**

Repro:

    type Circle = { r: i32 }
    type Sq = { s: i32 }
    type Shape = Circle | Sq
    function __deliver() {
      const a: Circle[] = [{ r: 7 }]
      const b: Shape[] = a
      return b
    }
    const v = __deliver()
    const e0 = v[0]
    if e0 is Circle { print(e0.r) } else { print(0) }
    // vl check: rc 0.  vl run: prints 7.

#### Mechanism

Not the covariant-write analysis, and not covariance: the same program with a plain
`Circle[]` and no widening anywhere fails identically. `globalCellKind` memoises a module
binding's cell kind under a generation stamped on the arena epoch and on the LENGTH of every
collect table a rung reads — and `fRetKind`, which the call rung reads through
`fnRetRefArraySid`, is filled IN PLACE by `computeRetInference`, so it is invisible to that
stamp. `capNarrowBuild` runs before `computeRetInference` and, for `if e0 is Circle`, resolves
`e0`'s initializer `v[0]` down to `globalCellKind(v)`. That query lands while `__deliver`'s
inferred return is still the seeded `"i32"`, the answer is cached, and nothing afterwards
invalidates it: `globalPromotable` reads `"i32"` as "a plain numeric scalar", promotes the
binding to a start-function local declared i32, and the start function stores the `(ref
$rlWrap)` the call really returns into it.

The fix is the generation: `emitPassGen` counts pass-table rows and `gckStale` reads it, so a
memo answer may not outlive the pass that computed it. `gPromoOk`'s own contract — "a hole in
`globalPromotable` is a loud reject, never a wrong class" — is what the stale answer broke.
