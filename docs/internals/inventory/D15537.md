### D15537 — an instance bound at the call key's type, where an argument is built at a wider row, builds that argument at a row the instance does not read

**runs today and must keep running · REFUTATION PIN · check-clean invalid wasm under a candidate that takes the call key's binding for a record pin (lane F's c98, refused) · filed 2026-11-07 against master `7836b63a9`**

Repro:

    type Circle = { r: i32 | null }
    type K = { r: null }
    function mkcall() { { r: null } }
    const c = mkcall()
    const k: K = { r: null }
    function listViaField<T>(a: T[], _b: { f: T }): T { a[0] }
    const w: { f: Circle } = { f: c }
    print(listViaField([c], { f: k }).r ?? 6)

Want:

    6

#### Mechanism

`c`'s type is `{r: null}`, and the store into `w` builds it at the wider row `Circle`. The call
key `elabWalkKeyOf(call, true, listViaField)` binds `T` at the type, `{r: null}` (`K`'s row),
while the list argument `[c]` is built at `Circle`. Mono's rebuild pins each parameter at the
row its argument is built at, so it binds `T` at `Circle` and the program runs. A candidate that
takes the call key's binding instead (c98, `monoCallKeyBinding` without its literal-or-record
cut) instances `listViaField` at `K`, and the module fails to validate inside it: `expected (ref
$0)` (`K`) `found (ref $5)` (`Circle`). The key's binding is right as a type. What it lacks is the
row each argument is built at (`callArgRepTy`), which the rebuild reads through its pins. That
is the row key's question (#6629): the call key has to carry, or be read beside, the rep its
arguments are built at before it can stand in for the rebuild on a record pin.
