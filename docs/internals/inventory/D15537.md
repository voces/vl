### D15537 — an instance bound at the call key's type, where an argument is built at a wider row, builds that argument at a row the instance does not read

**closed 2026-11-07 by lane rowintern · runs, prints `6` · was a REFUTATION PIN (check-clean invalid wasm under the call-key binding without its literal-or-record carve-out, lane F's c98) · closed by `elabCallKeyBinding` binding each type parameter at the checker's rep row (`callBindRepTysAt`) where it records one, and the carve-out deleted · named set `ckb-callkey-binding-price` 4 of 4 runs · filed 2026-11-07 against master `7836b63a9`**

Repro:

    type Circle = { r: i32 | null }
    type K = { r: null }
    function mkcall() { { r: null } }
    const c = mkcall()
    const k: K = { r: null }
    function listViaField<T>(a: T[], _b: { f: T }): T { a[0] }
    const w: { f: Circle } = { f: c }
    print(listViaField([c], { f: k }).r ?? 6)

Want:

    6

#### Mechanism

`c`'s type is `{r: null}`, and the store into `w` builds it at the wider row `Circle`. The call
key `elabWalkKeyOf(call, true, listViaField)` binds `T` at the type, `{r: null}` (`K`'s row),
while the list argument `[c]` is built at `Circle`. Mono's rebuild pins each parameter at the
row its argument is built at, so it binds `T` at `Circle` and the program runs. A candidate that
takes the call key's binding instead (c98, `monoCallKeyBinding` without its literal-or-record
cut) instances `listViaField` at `K`, and the module fails to validate inside it: `expected (ref
$0)` (`K`) `found (ref $5)` (`Circle`). The key's binding is right as a type. What it lacks is the
row each argument is built at (`callArgRepTy`), which the rebuild reads through its pins. That
is the row key's question (#6629): the call key has to carry, or be read beside, the rep its
arguments are built at before it can stand in for the rebuild on a record pin.

#### Closed: the rep row, read by the binding and not by the key

At every call where the call key's binding differs from mono's rebuild, a probe logged the
checker's two bind rows: `callBindTysAt` (the type) and `callBindRepTysAt` (the row the arguments
are built at). Over 23,828 programs, the carve-out's cases split by class:

| class | decisions | key | rebuild | checker's rep row | under c98 |
| --- | --- | --- | --- | --- | --- |
| record | 13 | `{r: null}`, `{f: i32}`, `{y, x: i32}` | `Circle`, `J`, `V` | the rebuild's | this row's trap, `ckb_bound_wider`'s, `ckb_hole_inst_stored`'s refusal |
| record, wider structure | 10 | `{r: null}`, `{y: i32, x: i32}` | `{r: i32 \| null}`, `{y, x: i32 \| string}` | `Circle`, `V`, the same types named | (the trap programs) |
| numeric literal union | 68 | `NK`, `K`, `N`, `1 \| 2 \| 7` | `i32` | none | `ckb_filled_litunion`: D3540, closed by #6651 |

So the key is right as a type and the rebuild is right as a row; the checker already records
both. `elabCallKeyBinding` binds at the rep row where there is one, and the call key itself keeps
the type. Widening the producer instead (`elabRowTys` taking the rep row without
`callBindRepKeyedAt`) moves the call's own rows and breaks three of the four price cells (two
invalid modules, one type error): that guard holds the call at its type wherever a parameter does
more than hand its value on.
