### D2411 — the written-container walk stopped at an assignment used as a value, so a handle bound to it was not an alias

**closed 2026-09-25 — the witness is now a loud check reject, the refusal the direct spelling
already had · was check-clean invalid wasm, clause 1 · pre-existing on master `a277bf7b0` ·
filed and closed against `a277bf7b0`, found grading [D2398](D2398.md)'s readonly-copy template ·
fixture `tests/cases/arrays/error-list-widening-through-assignment-value.vl`**

Repro:

    let c: readonly f64[] = [1.5]
    const x = [5, 2]
    const v = (c = x)
    v[0] = 9
    print(x[0])
    // vl check before the close: rc 0.  vl run: invalid module, expected (ref null $type), found (ref $type)

#### Mechanism

`c = x` into a `readonly f64[]` is an element-converting copy, which the checker refuses when
the source list is written, since the write would not reach the copy. The refusal decides
"written" from the alias closure of `x` (`cwGrow`, `cwContainerAliases`, `typecheck.vl`),
and the closure followed an assignment only to its target: `c` joined, but the assignment's
own value, which is `x`, did not reach the binding, write or argument that consumed it. So
`v` was not a handle on `x`, `v[0] = 9` was not a write to it, and the program was accepted.
The walk now crosses the assignment to its consumer (a binding, a write, or an argument), and
`covarRootName` roots a value-position assignment at its right side, so `pass(c = x)` binds
the parameter. The direct spelling, `c = x; const v = x; v[0] = 9`, always refused.
