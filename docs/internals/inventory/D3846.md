### D3846 — a function whose tail is a call through a capture cell (`d[0](x)`) is inferred void, so its caller reads a result that is not there

**closed (2026-10-08, lane SC) · was check-clean invalid wasm · found closing D3845 (`l3`) · filed 2026-10-08 against master `52c8e492d` · pins: `tests/cases/closures/tail-call-through-capture-cell.vl`**

Repro:

    function f(x: string) {
      const c = (y: string) => y + "C"
      const e = (y: string) => y + "E"
      let d = c
      const g = () => d(x)
      d = e
      d(x)
    }
    print(f("a"))
    // vl check: rc 0.  vl run: invalid module inside the module's top-level code, `expected (ref $type) but nothing on stack`

Want:

    aE

#### Mechanism

`computeVoidFns` asks `stmtIsTailValue` of the tail, and for a callee that is no identifier it
decides by the call's resolved `$fnsig` (`cloCallSigKey`). The capture rewrite leaves its read
`d[0]` untyped on purpose, so that key was empty, the tail counted as a statement, and `f` was
void. `cloCallSigKey` now keys an untyped `Index` callee by the element type of its list, which
the cell carries. The hole-lambda spelling also needs the cell retyped at the lambda's
instance (D3851, #3446).
