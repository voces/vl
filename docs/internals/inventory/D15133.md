**closed 2026-11-03 · now a loud check reject at `zs`, D2161's own refusal: `((T) => T)[] is not ((i32) => i32)[]: a container never widens implicitly, and only a readonly list is covariant…` · was check rc 0 then a loud emit reject, clause 2 · `listWidenWalk` (check_fit_rules.vl) claims a list literal a `const` names whose function-set elements a mutable closed function list would read (`listConstLitFnSet`, `listFnSetNeedsCopy`), where `listElemWidens` declined on the generic member's hole · fixtures `tests/cases/closures/error-fn-set-list-shared-by-mutable-closed-list.vl` and the controls in `closures/fn-set-list-mutable-alias-controls.vl` · filed 2026-11-03 against master `91585f3a`**

Repro:

    function id<T>(x: T): T { return x }
    function dbl<T>(x: T): T { return x + x }
    let f = id
    f = dbl
    print(f("s"))
    print(f(1))
    const zs = [f]
    const ys: ((x: i32) => i32)[] = zs
    print(ys[0](41))
    // vl check, before: rc 0, then vl run: emit error, with the split plan on and off

#### Mechanism

`ys` is a mutable list bound to the same list as `zs`, whose elements are the set `{id, dbl}`
called at two types. A readonly destination is copied through adapters (`fvaListSetCopy`,
D15069), but a mutable one aliases the source, and a covariant mutable list is refused by design
(D2161). The checker accepts the binding, so the refusal arrives at emit: the checker owes it,
naming the alias and offering `readonly` or an annotated source list.
