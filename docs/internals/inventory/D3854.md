### D3854 — a chain of two `let`/`const` aliases of a hole lambda at module scope is refused at emit for want of a function-value signature

**closed (2026-10-08, lane SC) · was a loud emit reject · 174 of 600 generated programs moved to module scope (`gen.py`, lifted out of `mk`) · found closing D3847 · filed 2026-10-08 against master `5b2ec9f85` · pins: `tests/cases/closures/module-let-alias-chain.vl`**

Repro:

    const c = (y) => y + "C"
    const e = (y) => y + "E"
    let d = c
    const d2 = d
    print(d2("a"))
    d = e
    print(d("b"))
    print(d2("c"))
    // vl check: rc 0.  vl run: emit error `a function-value call has no interned signature`

Want:

    aC
    bE
    cC

#### Mechanism

A single alias (`let d = c`) keys its call through `fieldValueFeOfIn` (D3847). That resolution
stops at one hop on purpose: following a chain there would also rename the call to the
initializer's lambda, which is wrong once a link is written. The signature key now takes its
own chain walk at module scope. `identCopySourceNodeAt`, the copy rung of
`calleeCloSigKeyAt`, which a function's bindings already used, also reads a module-scope
binding read at module scope. A read from inside a function is left alone: it would key an
uninstantiated lambda's `i32` default and validate wrong (`gen3.py` r0239).
