### D1581 — a continuation line could not begin with a binary operator, because `binPrec("NEWLINE")` is 0 everywhere and the parser had no notion of bracket depth

**closed (fixed) — the parser now carries a bracket depth (`brDepth`), and inside one a NEWLINE run leading to a binary operator is consumed as whitespace; `parseBlock` resets the depth to zero so statement level is untouched · was a loud PARSE reject · grid 6 -> 19 of 24 running, `runs -> not-runs` 0, the five still refused are the controls that must stay refused · ZERO corpus cells · reported by the glean session, VL-031, `~/glean/docs/vl-issues.md`, probe `~/glean/vl-probes/VL-031-leading-operator.vl` · ruling: DECISIONS.md, "Newlines inside brackets are whitespace before a binary operator" · filed 2026-09-04 against master `9ba97704`**

Repro (runs, prints `true`):

    const a = 1
    const b = 2
    const ok = (a == 1
      || b == 2)
    print(ok)

#### Mechanism

VL's NEWLINE is a real token and the precedence climber stops on it for one reason:
`binPrec("NEWLINE")` returns 0, which is also the loop-terminating sentinel. There is
exactly one continuation mechanism today — `parseBinary` calls `skipNewlines()` AFTER
consuming an operator, which is what makes the trailing spelling (`a == 1 ||` newline
`b == 2`) work — and it cannot help the leading one, because the newline arrives BEFORE
the operator is seen. The parser had no bracket depth at all (only ad-hoc local scan
counters), and the lexer's only depth counter, `gBrace`, counts block braces too, so
neither could answer "is a statement even possible here".

The fix is the leading-dot rule's shape one construct over: a parser-side `brDepth`
raised at `(` (group and call args), `[` (array literal and index) and an object
literal's `{`, and RESET to zero by `parseBlock`; and in the climber, when `brDepth > 0`
and the token is NEWLINE, `binOpAfterNewlines()` peeks past the run and the cursor moves
only if what follows is an operator. Look-before-consume is load-bearing: `takeSep`
decides a missing comma by reading `kindAt(P.pos - 1) == "NEWLINE"`, so a run left in
place is what keeps a missing CLOSER at end of line from being read as a missing comma
that swallows the next statement.

**WHY IT CHANGES NO EXISTING PROGRAM.** A newline is not a separator in any bracketed
list — `takeSep` refuses to insert a comma across one — so `[1` newline `2]` and
`{a: 1` newline `b: 2}` are parse errors before and after. The only tokens that are both
binary operators and expression starters are `-` and `+`, and a line leading with either
inside a bracket was a parse error too. Match arms, which ARE newline-separable, can
never start with an operator token (`matchPatStartsType` is a closed set of IDENT /
LBRACE / NULL / NUMBER / STRING).

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the parentheses (statement level) | still a parse error, `expected an expression but found OR` | **yes** — the bracket is the whole gate |
| the operator leads (trailing `\|\|` instead) | ran before and after | **yes** — only the leading form was refused |
| `\|\|` replaced by `+`, `-`, `*`, `??`, `&&` | all refused before, all run after | no — every binary operator, not a set |
| the bracket is `[` or an object-literal `{` | same before, same after | no — all three brackets |
| the bracket is a BLOCK (`(x) => { v` newline `-v }`) | two statements before AND after | **yes** — `parseBlock` resets the depth |
| the list uses a newline where a comma belongs | parse error before and after | **yes** — the newline is left in place unless an operator follows |
| the `(` is never closed | parse error before and after | **yes** — the recovery path is unchanged |
