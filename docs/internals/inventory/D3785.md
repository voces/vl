### D3785 — an integer-literal assignment as an annotated `f32` function's tail is refused as a lossy `i32` to `f32` delivery

**loud check reject · open · found by lane S4's review round on [D3733](D3733.md) · filed 2026-10-06 against master `a37097b64`**

Repro:

    function s(): f32 {
      let x: f32 = 0
      x = 255
    }
    print(s() / 2.0)
    // vl check: rc 1, `expected f32, got i32` at the assignment

Want:

    127.5

#### Mechanism

An assignment is typed by its right side, so `x = 255` is an `i32` value, and delivering an `i32`
to an `f32` result is refused as lossy above 2^24. The literal itself adopts `f32` at that
delivery (a bare `255` tail runs), and the store already wrote it at `f32`; the assignment's value
does not adopt with it. The `i64` and `f64` results run, because `i32` widens to both exactly.

#### Ablation

On master `a37097b64`.

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `255` → `0xff` | the same refusal | no |
| `255` → `if c { 0xff } else { 1 }` | the same refusal | no |
| the function's result `f32` → `f64` | runs, `127.5` | **yes** |
| the assignment → a bare `255` tail | runs | **yes** |
| `const a = (x = 0xff)` beside `print(a / 2)` | runs, `127` (the value is `i32`) | no |

#### Grading list

The `f32` rows of [D3733](D3733.md)'s ablation. A close lets the assignment's value adopt the
destination as the literal does, at a delivery whose width the store shares, without re-typing the
assignment for its other uses (`const a = (x = 0xff)` stays `i32`).
