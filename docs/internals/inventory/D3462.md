#### Mechanism

A literal of N elements that each allocate (a record, a nested list, a boxed union member, a
closure, a string) lowered as ONE `array.new_fixed` over N operands up to the 10,000-operand cap.
Every operand is a GC allocation, so Cranelift sees N safepoints, each with every earlier operand
live on the stack, and its compile of that function grows like N^2.6 in time and N^2 in memory:
records at 1,000 / 2,000 / 4,000 ran 3.5 s / 25 s / 107 s and a 12,345-record literal ran past
300 s, all of it the engine compiling the module (`vl build`, which only validates, took 0.04 s
to 0.4 s). A string or ref literal longer than 256 elements now builds in chunks of 256 (the
`array.new_default` + `array.new_fixed` + `array.copy` form a literal past the cap already used,
`ALLOC_LIT_CHUNK`, compiler/emit_base.vl). A global's constant initializer is the same cost —
the engine compiles it like a body — and cannot chunk through locals, so a literal past 256
elements is a constant initializer only when it builds a bare scalar backing (`isConstInit`'s
`arrLitBuildsScalar`, and `letInitLongIntoBoxedCell` for an annotation that boxes its numeric
elements, like a literal-union list); any other goes to the start function, where it chunks.

#### Ablation

`VL_NO_CACHE=1`, box load 8 to 40, so wall times are indicative; a scalar literal of the same
length ran in under a second either way.

| witness | master | after |
| --- | --- | --- |

| 4,000 two-element nested lists | 5.9 s, 1.37 GB | 1.9 s, 419 MB |

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| elements are number literals into a bare scalar list | fast at any length | **yes**, an allocating element (a literal-union list boxes its numbers) |
| the literal is a global's constant initializer (`const xs = [{ a: 1, b: 2 }, …]`, every field a literal) | the same super-linear cost: the engine compiles the initializer too | no |
