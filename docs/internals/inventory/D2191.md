### D2191 — a compound assignment read its place through the same target node it wrote, so a side-effecting receiver or index ran twice

**closed 2026-09-23 — each compound statement's receiver and index are spilled once, in source order, before the read · was check-clean wrong evaluation (`xs[k()] += 4` called `k` twice; the stored value was right only when `k` answered the same both times) · found while building plumb PL-021's bitwise compound forms · filed 2026-09-23 against master `66e74235a`**

Repro (runs, prints `k`, `k`, `k`, `14`; master printed each `k` twice):

    const xs = [1, 2, 3]
    function k(): i32 {
      print("k")
      return 1
    }
    xs[k()] += 4
    ++xs[k()]
    function f() { xs[k()] *= 2 }
    f()
    print(xs[1])

#### Mechanism

The parser desugars `p op= v` to `p = p op (v)` and shares the target node between the outer
write and the inner read (`mkCompoundAssign`, `mkPreIncr`), so the emitter lowers the place's
receiver and index once for the read and again for the write. `dispatchRewrite` now asks
`spillCompoundPlace` of every statement in a block and every top-level statement: a receiver or
index that is not re-readable (`exprReReadable`) is bound to a `const` ahead of the statement,
receiver first, and the shared target reads the spill. An element read that a user `"[]"`
answers is a call, so `cpReReadable` does not count it as re-readable (`g[1][0] += 5` runs the
`"[]"` once). A top-level statement's spills go in a
block of their own, so they are locals of the start function rather than module globals. The
target node itself is kept, so a user `"[]"`/`"[]="` pair the checker banked on it still resolves.

#### Ablation

| ingredient removed | outcome on master | needed? |
| --- | --- | --- |
| the call, `xs[i] += 4` over a local `i` | runs, one read | **yes** |
| the index, `mk().v += 1` (a call receiver) | runs, `mk` twice | no |
| the scope (inside a function) | runs, `k` twice | no |
| the arithmetic, a plain `xs[k()] = 4` | runs, `k` once | **yes** |
