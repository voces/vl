### D17227 — the record-join audit reads a lambda maker's call at the row its literal shares with another maker, though the call is built at the join

**closed 2026-11-28 by I8-PREP · runs, prints `null` `null` · was: loud emit reject · clause 2 · `this branch hands over a record whose field types differ from the record the branches join to` · the record-join audit's row reader (`rjaRowOf`, emit_value_sites.vl) now reads a call at the record the solve builds it as (`litKeptRepOf`), the emitter's own reader, before the call's shared syntactic row · filed 2026-11-25 against master `c2878db6` by IR-N5 (found building [D17224](D17224.md)'s sweep)**

Repro:

    function mk2() { return { f: null, g: 7 } }
    const mkL = () => ({ f: null, g: 7 })
    function viaLambda(m: boolean) {
      if m { return { f: 1, g: 7 } }
      return mkL()
    }
    const own = mk2()
    print(own.f)

    // vl check: rc 0.  vl run: emit error at 5:14, this branch hands over a record whose field types differ

    null

#### Mechanism

With [D17224](D17224.md)'s delivery, `mkL`'s result is built at the join's row: with the audit
off, the module validates, the closure is called at a signature returning the join's struct, and
the program prints the Want block. `auditRecordJoinLeaves` reads the call's row through
`structIndexOfExpr`, which answers the row `{ f: null, g: i32 }` that `mk2`'s live call keeps, not
the row the closure is built at, so the audit refuses a branch the emitter builds correctly.
