### D2755 — a generic delivered as a function value is keyed by its destination's spelling, so a Set and its boolean map share one instance

**closed 2026-09-26 — the filed repro RUNS and prints `true` then `false` · was check-clean silently wrong (`true` twice) · clause 1 · found by #3202's review (`p1c`) · closed by pinning a function-value instance at the parameter types of the destination's function type, so D2684's exact key splits it · filed 2026-09-26 against master `876559d2f` · fixture `tests/cases/generics/pin-exact-key-function-value.vl`**

Repro:

    function f<T>(u: T | string): boolean { u is Set<string> }
    function app(g: ({[string]: boolean} | string) => boolean, v: {[string]: boolean}): boolean { g(v) }
    function aps(g: (Set<string> | string) => boolean, v: Set<string>): boolean { g(v) }
    const s: Set<string> = Set()
    const m: {[string]: boolean} = Map()
    print(aps(f, s))
    print(app(f, m))
    // PRINTS false

#### Mechanism

`monoInstanceFor` pins a generic reached as a value by the destination's function-type
spelling, which renders `Set<string>` as `{[string]: boolean}`, and it passed no pin types, so
`monoExactBind` bound nothing and both deliveries took one instance. It now takes the parameter
types of the value's recorded function type, or of the destination's annotation (threaded
through `monoCoerceFnValueName`), and the exact key separates the two. The annotated binding
spelling (`const fm: ({[string]: boolean} | string) => boolean = f`) was a loud emit reject and
now runs too.

#### Ablation

| --- | --- | --- |

| the Set (`string[]` against `i32[]`) | runs | **yes** |
| the string key (`Set<i32>`) | refuses: an i32-keyed Map/Set inside a function type | no |
