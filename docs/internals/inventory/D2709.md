### D2709 — an operator tree over integer literals is computed at 32 bits before it is delivered to an `i64` destination

**closed 2026-09-26 — the witness prints `12884901888` · was check-clean silently wrong, clause 1
· Reported by plumb (PL-047) · filed against master `fdd0050af` · fixture
`tests/cases/literals/literal-tree-width-at-destination.vl`**

Repro:

    const a: i64 = 3 << 32
    print(a)
    // PRINTS 12884901888
    // vl check: rc 0.  On master it printed 3: `3 << 32` shifted an i32 by 32 mod 32 = 0.

Want:

    12884901888

#### Mechanism

`checkNodeReal` types an integer literal by its own digits, so every operand of `3 << 32`,
`2147483647 + 1` or `100000 * 100000` is `i32`, the operator is typed `i32`, and the emitter
computes it with `i32.shl`/`i32.add`/`i32.mul` before `assignableExpr` widens the wrapped result
into the destination. A bare literal did not have the defect, because the destination re-encodes
it directly (`emitExprAsI64`'s literal peel). The close lets the tree adopt the destination as
the bare literal does: `litTreeAdoptDst`, at the `assignableExpr` seam every position delivers
through, types every node of a tree of integer literals `i64` at a 64-bit destination. A float
destination is D2711's, pending a ruling, and keeps the 32-bit reading. Tails of a value `if`, `match` and block, object fields and list elements reach it through
D2617's walk (`radixLitAdoptDst`). An operand beside a wide one takes that one's type the same
way (`x + (1 << 40)` over an `i64`), and so does the operand of an exact cast to `i64`
(`(1 << 40) as i64`; the wrap cast `as% i64` keeps the 32-bit reading). A literal
keeps its adopted type in `litTreeTy` across re-checks. An `i32` operand is never widened: a
tree mixing an `i32` variable keeps the 32-bit reading, and a shift count it would wrap is
D2710's refusal.

#### Ablation

On master `fdd0050af`, all at an `i64` destination unless the row says otherwise.
