Repro:

    function add(a, b) { return a + b }
    function mul(a, b) { return a * b }
    function apply2(g) { print(g(1, 2)) }
    const k = apply2
    k(add)
    k(mul)
    function viaFor(h) {
      for f in [apply2] { f(h) }
    }

    // vl check: rc 0.  vl run: the emitted module failed to validate inside `viaFor`: type mismatch: expected (ref $type), found i32

    3
    2
    3

#### Mechanism

The tag decision tries `{apply2}`, since `for f in [apply2] { f(h) }` calls through it, and
declined it at the module call `k(add)`: `k` is an alias, so the call was neither a member's
direct call nor a call the check noted through the set (D15441's decline). `{apply2}` stayed one
closure. The late decision then tagged whichever of `{add}` and `{mul}` the first alias call
instanced, and `viaFor(add)` handed `{add}`'s `i32` id through `f(h)` into the closure, which
takes a closure. With the calls in the other order `{add}` stayed a closure and the program ran.
