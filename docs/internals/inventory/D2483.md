### D2483 — an unrelated declared row's nullable `f64`/`i64` field asks a same-named boolean literal for a value box the module never minted

**loud emit reject · clause 2 · found in review of #3147 against master `0a0d24ac9`, filed 2026-09-25**

Repro:

    type Q = { k: f64 | null }
    const r = { k: true }
    print(r.k)
    // vl check: rc 0.  vl run: emitProgram: union atom has no value box

#### Mechanism

The same declared-row-by-field-name confusion as D2482, one step further. `Q`'s field is
`f64 | null` rather than `i32 | null`, so the module never mints a value box for `boolean`
inside that union — nothing declared ever puts a boolean there. Building `r` at `Q`'s row asks
for a box the emitter has no member for, and it refuses rather than emit invalid wasm. The same
shape over `i64 | null` refuses identically. Over a string-literal union (`"a" | "b" | null`)
with a numeric literal (`{ k: 7 }`) the same row-confusion refuses too, but with a different
message (`print of a literal-union atom whose type carries no member texts`), since `print`'s
own string-union arm asks a different question of the same underlying rep.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the declared type `Q` | runs, prints `true` | **yes** |
| `Q`'s field `i64 \| null` instead of `f64 \| null` | same refusal | no |

#### Grading list

`type Q = { k: "a" | "b" | null }` with `const r = { k: 7 }; print(r.k)` (same family, different
message); D2482, the `i32 | null` twin that misreads instead of refusing.
