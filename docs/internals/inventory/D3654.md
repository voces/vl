### D3654 — `as?` to a number over an un-annotated parameter is typed at the bare target before the pin, so every position refuses at emit

**closed 2026-10-05 — the witness prints `null`, `5` · was a loud emit reject, clause 2 · the `as?` residue of [D3624](D3624.md) · filed 2026-10-04 against master `32b753681` · fixture `tests/cases/numerics/as-opt-over-hole.vl`**

Repro:

    const k = (x) => x as? u8
    print(k(300))
    print(k(5))
    // vl run: emit error, `as? i32` over a type parameter needs the instance's exact pin

Want:

    null
    5

#### Mechanism

Over a type parameter the checker types `x as? N` as `N | null` at every pin (D2754), but the
hole case is excluded (`checkCastNode`: `argH.tvName[0] != '?'`), so the cast is typed bare `N`
and only re-typed `N | null` at the pin (`castPinNullResult`), after the body, its bindings and the
inferred return were already typed bare. The emitter's `emitHoleNumAsOpt` reads only the generic
exact pin and refuses. Reading the hole pin there as well (tried on lane WV) makes a cast whose
value only reaches `print` run, and turns one bound to a `const` and returned into check-clean
invalid wasm (`expected i32, found (ref $type)`), so the fix starts on the checker side: type the
hole cast `N | null` up front as the generic one is, then let the emitter read the hole pin. That
changes the type of `x as? i32` over a hole pinned at `i32`, so grade the direct spelling with it.

Fixed as filed: `checkCastNode` now types `x as? N` over a hole `N | null` up front, as over a
type parameter, and `emitHoleNumAsOpt` reads the hole instance's pin (`holeOperandTyOf`), or for
a cast inside a lambda lifted into one, the enclosing instance's (`holeCaptureTyOf`). A hole
pinned at `i32` now types `x as? i32` as `i32 | null`, which is what the type-parameter spelling
has typed since D2754; every position of this cast refused at emit before, so no running program
changes type.

Two prices, both measured on the `rv85` review grids. A hole function never called at all now
types its cast `N | null` too, so `function f(x) { (x as? i32) + 1 }` is refused for `+` over a
nullable: an owed refusal, since the `<T>` spelling and the annotated `x: i32 | null` spelling
already refuse it. And a hole spelling now reaches the generic lowering's own defects: 13 cells
of `rv85`'s `gc` grid moved from this row's loud emit reject to [D3692](D3692.md)'s invalid
module, and a hole pinned at a union that holds a number (`i32 | null`, `i32 | string`) prints
`null` for `x as? f64` exactly as the `<T>` spelling does (the direct spelling is a check error,
`as f64 names a type that is not a member`).
