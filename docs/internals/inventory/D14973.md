### D14973 — a lambda returning a `Map()` that no use pins, handed to an un-annotated parameter, passes check and is refused at emit

**closed · now a loud check reject, `cannot infer a type for this argument — an empty Map it holds has no key or value type until it is used` · was loud emit reject, `vl check` rc 0, clause 2 · the design's refusal: the binding twin is refused as `cannot infer a type for 'm'` · filed 2026-11-02 against master `097423370`**

Repro:

    function take(a) {
      const v = a
      print(v(2).length)
    }
    take((x: i32) => Map())
    // vl check: rc 0.  vl run: emitProgram: monomorphize: unsupported argument type for `a` in a call to `take`

#### Mechanism

Nothing gives the lambda's `Map()` a key or a value type: the parameter is a hole, and
`.length` constrains neither. The same map at a binding, `const m = Map(); print(m.length)`,
is refused by the checker as `cannot infer a type for 'm'`, so the design owes this program
that refusal, not a lowering. The spellings where the callee does pin the map, a write
through `a(2)` or a delivery of `a(2)` to a typed parameter, run: the call re-asks the
result's map demand (`holeKidMapDemands`) and the replayed argument constraint pins it.
At the program's end, an inline lambda or `Map()` argument to a hole parameter that still
holds an open map is refused (`flushOpenArgMaps`), as a binding is at its scope close. This
waited on D14976, whose legal program the same rule would have refused.
