### D2259 — a generic returning a closure over its parameter, pinned at two types, builds the second pin's closure at the first pin's rep

**check-clean invalid wasm · `vl check` rc 0, then the emitted module fails validation inside
the second instance, clause 1 · found by the #3088 review's generic cells of the D2252 grid,
which reproduce with no shadowing at all · filed 2026-09-23 against master `7d369c028`**

Repro:

    function gen<T>(r: T): () => T { () => r }
    print(gen(5)())
    print(gen("q")())
    // vl check: rc 0.  vl run: invalid module,
    // "type mismatch: expected i32, found (ref $type)"

#### Mechanism

Only the first pin's closure is right: one instance, or two instances at the same type, run;
a second pin at another type (`string`, or `f64`: `expected i32, found f64`) fails inside that
instance, so the lambda the two instances share is typed once, at the first pin. Pinning the
string first turns the failure loud instead (`function-value call arity has no interned
signature`). A prediction until a close confirms which table keeps the one lambda's rep.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the second pin (`gen(5)` alone) | runs | **yes** |
| the second pin's type differing (`gen(5)`, `gen(6)`) | runs | **yes** |
| the pin order (`gen("q")` first) | now a loud emit reject | no |
| `string` for `f64` at the second pin | still invalid wasm | no |
| the parameter as the capture (`const r = x`, capture `r`) | still invalid wasm | no |
