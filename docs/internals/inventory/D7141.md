### D7141 — a list of a generic-initialized, lambda-written `let` handed to a hole parameter and called there is invalid wasm

**closed 2026-10-19 by lane L1 · runs, prints `L 3 O true` · was check-clean invalid wasm · `vl check` rc 0 · clause 1 · the hole parameter's list pin takes a written element's result from its own type · pins: `tests/cases/closures/written-let-in-list-arg-called-beside-generic-first.vl` · found closing [D7103](D7103.md) · the same on master `8e787a973` · filed 2026-10-19 against master `8e787a973`**

Repro:

    function other<V>(v: V) { print("O"); print(v) }
    function run(fs) { fs[0](3) }
    function main() {
      let k = other
      k = (n) => { print("L"); print(n) }
      run([k])
      other(true)
    }
    main()
    // vl check: rc 0.  vl run: the emitted module failed to validate inside `run`: type mismatch: expected structref, found i32

Want:

    L
    3
    O
    true

#### Mechanism

Probed at the pin of `run`'s hole parameter `fs`, with the `const` spelling as the control. The
list-pin rung (`monoListSlotPinnedFnTy`) asks each element's single declaration for its
result, and a `let` written twice has none, so the rung declined. The floor that took over
named the pin `(() => void)[]` after the pruned `other` stub, and the call through `fs[0]`
keyed a `call_indirect` taking only the closure environment. The rung now asks an element
with no single declaration for the result of its own function type.
