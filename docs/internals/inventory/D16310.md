### D16310 — an un-annotated lambda delivered to a closed function type builds its result at its body's own type, not the delivered result's rep

**closed 2026-11-14 · runs, prints `1` · was check-clean invalid wasm, clause 1, with an indirect-call trap and a false `is` as its other faces · an un-annotated lambda delivered to a closed function type is checked as its annotated twin: the delivered result is written as its return annotation before the body is checked (`lamDeliveredRet`, check_fn_decl.vl), unless it came through a generic parameter (D2459's join); a union's record arm with an array, union, nullable, map or literal field is seeded too (`unionArmSeedSafe`, tyquery.vl) · fixture `tests/cases/closures/lambda-at-closed-fn-type-built-at-delivered-result.vl` · grids `scripts/capability-probes/matrix/lambda-at-closed-fn-type-*.matrix.vl` · the `return_inferred` residue is [D16296](D16296.md) · 9 of the 16 unsound fuzz findings of 2026-11-14 · filed 2026-11-14 against master `fe9585a72`**

Repro:

    const f: () => {z: f64[] | i32} = () => {z: [14.5]}
    print(1)

Want:

    1

#### Mechanism

The lambda carries no result annotation, so its tail is built at the type its body infers
(`{z: f64[]}`, a record whose field is a bare list), while the binding, the call sites and every
reader use the delivered function type's result (`{z: f64[] | i32}`, a union-box field). The two
reps meet in the lambda's own `return`, so the module fails to validate inside `f`. The same
seam is a trap when the reps are two scalar widths (`f: () => i64` given `() => 6`, called through
`$fnsig` `() => i64` while the closure was built at `() => i32`), and a silently false `is` when the
field is itself a union of function types (the closure is boxed under its own signature's tag).
Annotating the lambda's result with the delivered one makes every face run, so the fix is the
delivered result standing in for a missing annotation.
