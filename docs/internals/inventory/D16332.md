found i32` in the top-level code, where `$1` is the closure struct `{structref, i32, i32}`.
`wasm-dis` of the witness shows:
- `v` lives in an `i32` local, written `(i32.const 5)` twice (init and write).
- `v(5)` is devirtualized to `call $id`.
- The list argument is `(array.new_fixed $0 2 (local.get $0) (global.get $global$0))`: the

- In the plain-list spelling `const l = [v, inc]`, which runs, the element `v` is instead
  `global.get` of `id`'s static closure.

So the delivery of a list literal to a closure-list PARAMETER reads the written `let`'s slot,
where the plain-list path resolves it to the closure it holds. Where the plain path does that is
not yet found.

- a list literal delivered to a function-typed list parameter, generic or not;
- the direct call `v(5)`.
