#### Mechanism

Two faces of one gap, both at the env field of `const c = <walk variable>`, which is typed with
no frame's locals registered. For `i32 | null` narrowed out of `i32 | null | string`, the frame
binds `c` at the box but `letIsUnion` asked `exprUnion` of the loop variable, which reads the
live local table, and typed the field `i32`; `letIsUnion` now also takes a read whose recorded
type is the box and whose name `readIsLoopBox` finds as a walk variable over box elements. For
`K` narrowed out of `(K | null)[]`, the field is right (`captureLoopCopySrc` redirects the copy to
the loop variable), but the closure's read asked `bindingIsLitAtom` of `c`'s declaration and
read a string; `capturedLoopVarIsLitAtom` now follows the same copy to the loop.

Two more faces of the same gap were found by the grid and closed with it. An annotated
`const c: Circle = e` over `(Circle | null)[]` keeps the niche in the frame ([D1632](D1632.md)),
and `captureValKind` asked `letInitCellKind` of the initializer, which cannot see the loop, so
the env field was the non-null ref; it now also asks `letInitLoopElemKind`. And
`uC(id(e))` pinned `id` at `i32`: `monoArgTyName`'s struct and variant rungs read the locals
table, which mid-mono has none; `monoLoopVarRecordPin` (`emit_mono.vl`) pins a walk variable
the checker typed as a nominal record at the record's name.
The niche channel `capturedIsNulLitUnion` takes the same loop path, so a closure comparing a
captured `(K | null)[]` walk variable, or a copy of one, with `null` reads the atom niche instead
of refusing (`bare null needs a struct-typed context`).

The #3281 review found that the first version of this close resolved a capture by the FIRST
binding of its name in the frame. That regressed programs that walk two lists under one name
(`for e in ks { }` and then `for e in ns { const c = e; () => c }` stopped building). The
lookups now resolve by position:
- `frameLoopEnclosing` finds the loop that encloses the closure.
- `frameLetAt` finds the `let` in scope at the closure, and a loop variable enclosing it
  shadows an outer `let`.
- `frameBlindIter` re-asks a bare local iterable through its initializer. This is shared by
  the capture and by `readLoopNodeOf`'s readers.
- `captureLoopCopySrc` follows an un-narrowed copy of a `let` to that `let`.
- `letInitCopiesBox` reads a copy of a copy of a box through the chain's declarations.
- The monomorphiser's local arm resolves at the argument's position.
- `letInitIsNulLitBox` finds a walk variable by its loop.

Round 2's positional lookups walked the frame body per query (`modLoopHolding`, then a full
`nodeSubtreeHas`), which made compile cost quadratic in the number of loops. At N = 300 loops
each capturing a copy, the compiler trapped. Round 3 answers them off the frame's cached
`parentLetOf` plan instead. The plan's loop-extent rows now name their loop, `parentLoopAt`
takes the innermost row covering the read, and a chain longer than eight rows is binary
searched over a per-sid index valid for the plan's generation. `tests/vl_scaling_shape_test.ts`
carries the shape as a growth pair ("loops each capturing a copy of one loop variable").
