### D14750 — a shared field one record stores as a literal atom and another as an integer reads the atom as its integer id

**runs, prints `b` — CLOSED 2026-11-01: a boxing shared read widens a member's atom-stored literal set to its string and boxes it under the string tag (`sharedFieldArmBoxKind`) · was check-clean silently wrong, clause 1 · pin: `tests/cases/unions/shared-field-atom-set-beside-scalar-arm.vl` · found ablating [D14746](D14746.md) · filed 2026-11-01 against master `4cb9dd26`**

Repro:

    const u: { k: "b" } | { k: i32 } = { k: "b" }
    print(u.k)
    // was: prints 0

Want:

    b

#### Mechanism

`u.k` is typed `"b" | i32`. Both arms store `k` as an i32, the first as the interned atom of
`"b"` and the second as the integer. The read dispatches on the box tag, but each arm hands back
its raw i32 and the join is printed through `__print_i32__`. The atom arm's value is never
converted to the string it names, so `"b"` prints as its atom id `0`. A value of the integer
arm (`{ k: 7 }`) prints `7`, which is correct.

The read plan (`sharedUnionFieldPlan`) called two `i32`-coded arms one atom unless both had a
scalar atom kind, and a literal set has none. It now counts the set as the string it names,
so the read boxes: the set arm widens its atom through `emitAtomToStrChain` and boxes under the
string tag, which is how an annotated `K | i32` value already carries the set. The box is named
with the set spelled as `string` (`valueUnionNameOfSoftTy`), since the read's own type has no
value-union spelling.
