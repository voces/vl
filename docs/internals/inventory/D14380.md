### D14380 — two same-field-set owner literals whose nested values take different union arms still need `anonNestPolyPremint`'s early mint

**runs today and must keep running · refutation pin filed 2026-10-26 against master `6f7dcdd8e` with slice 2's fact-only build rows applied · 2 cells: `tests/cases/unions/anon-nested-arm-layout-polymorphic.vl` and `named/d179nestpoly.vl`**

Repro:

    type Cir2 = { c2: i32 }
    type Sq2 = { s2: i32 }
    type Shape2 = Cir2 | Sq2
    const p = { r: { c2: 1 } }
    const q = { r: { s2: 2 } }
    print(p.r.c2)
    print(q.r.s2)

Want:

    1
    2

#### Mechanism

Slice 2 replaced the record-destination walk with the checker's build fact, and the brief
asked whether `anonNestPolyPremint` could then go. It cannot. Without the call (emit_collect.vl,
`anonNestPolyPremint(nestOwner)`), both witnesses become a loud emit reject:
`emitProgram: object literal matches no union variant`. The build fact covers a literal whose
destination has a declared type. Here the owners are un-annotated, so no fact exists, and
`anonValueFitsField` can only tell the two owner rows apart when both nested rows were minted
before the owner scan. The early mint is still what makes that order hold.
