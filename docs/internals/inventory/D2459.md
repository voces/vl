### D2459 — a type variable binds at its first use with no join, so a callback's result type depends on argument order

**closed 2026-11-02 · runs, prints `3` · was loud check reject, clause 2 · owner ruling: a type variable's uses JOIN over numeric widening only (`i32` to `i64` or `f64`, `f32` to `f64`), DECISIONS.md §"A type variable's uses join over numeric widening" · `checkCallOnFuncTy` re-checks a call's arguments with the variable bound at the wider use (`bgWiden*` in `bindGenWalk`), and mono binds that instance from the call's bind row (`monoPreBindNumJoin`, `elabCallBindTy`) · fixtures `tests/cases/generics/numeric-join-binds-the-wider-use.vl` and `numeric-join-refuses-a-non-widening-use.vl` · a call inside a generic body whose narrow use is the enclosing type parameter keeps its refusal, [D15041](D15041.md) · found reviewing #3152, filed 2026-09-25 against master `20651a88b`**

Repro:

    function f<T>(x: T, g: (i32) => T) { return g(2) }
    const two: i32 = 2
    print(f(two, (i) => i * 1.5))
    // vl check: rc 1: argument 2: expected (i32) => i32, got (i32) => f64.
    // The callback-first declaration `f<T>(g: (i32) => T, x: T)` with `f((i) => i * 1.5, 2)`
    // runs and prints 3.

Re-pointed 2026-11-02 to a named `i32`: with a literal first argument (`f(2, …)`, the row's
first witness) the call now runs and prints `3`, because a number literal binds its variable
after the arguments beside it ([D3541](D3541.md)). The question below stands for a value that
is not a literal.

#### Mechanism

`checkCall` binds a type variable at its first use (`bindGenWalk`, first use wins). `x: 2`
binds `T = i32` before the callback's return is seen, and `(i32) => f64` then fails the
substituted parameter. In the other order the callback binds `T = f64` first and `2` is
admitted as an f64. The two declarations are the same signature up to parameter order.

**Ruled 2026-11-02 (owner, option A):** inference JOINS the uses over numeric widening only
(`i32 ∨ f64 → f64`), so both orders run and print 3. Uses that disagree by anything else still
refuse. A literal `2` already followed this rule when a later use pins `f64` (D3541).

#### Close

A use wider than the variable's first binding asks for a join (`bgWidenNames`, recorded in
`bindGenWalk`'s type-variable arm while a call argument binds). `checkCallOnFuncTy` then rolls
back the argument pass's diagnostics and constraint rows (`RB_CALL_REJOIN`) and checks the
arguments again with the variable bound first at the wider number, as a written type argument
binds it. The call is marked joined (`callNumJoinNote`), and mono binds the instance from the
call's bind row rather than from the narrower argument's own type (`monoPreBindNumJoin`, which
reads `elabCallBindTy`). An instance's re-check joins only a call its template joined.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| parameters in the other order | runs, prints 3 | the order: **yes** |
| `x: 2.0` | runs, prints 3 | the disagreeing uses: **yes** |
| `(i: i32) => i * 1.5` | same refusal | no |

#### Grading list

Both orders, annotated and un-annotated callback: all four print `3` (master: the
value-first two refused). Beside them, two typed arguments (`mix(i32, f64)`, `mix(i32, i64)`,
`mix(f32, f64)`, both orders), three uses, a list result holding both uses, a join inside a
generic body over closed values, and a nested join all run with the written-type-argument
answer; `i64` beside `f64`, `i32` beside `f32`, a string beside a number and a string callback
result still refuse with master's message.
