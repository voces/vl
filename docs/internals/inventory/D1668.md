### D1668 — an if-expression array element is classified by no `arrLitIsRef` rung, so a struct ref is stored into an i32 backing

**check-clean invalid wasm · filed 2026-09-05 against master `8725c61a8` · found while measuring D1666 · probe `scripts/capability-probes/if-expr-array-element-beside-a-union.vl`**

Repro:

    type P = { x: i32 }
    type Q = { y: i32 }
    type UU = P | Q
    const p: P = { x: 1 }
    const xs = [if true { p } else { p }]
    print(xs.length)
    // vl check: rc 0.  vl run: exit 70, the emitted module failed to validate inside the
    // module's top-level code: type mismatch: expected i32, found (ref $type)

#### Mechanism

`arrLitIsRef` decides an array literal's backing from its FIRST element, through an
`ObjLit` / nested-array test plus four checker-typed rungs (`arrLitUnionElemName`,
`arrLitMapElemName`, `arrLitNominalElemName`, `arrLitNestedElemName`,
`arrLitNulRefElemName`). None of them claims an IF-EXPRESSION element, so the literal falls
to the i32 backing while the arm still evaluates to a struct reference. `emitArr`'s own loud
floor misses it for the same reason — `exprStruct` is false for an if-expression too — so the
program gets a bad module rather than `struct array elements are not supported`.

The union declaration is load-bearing and it is the surprising half: with `type Q` and
`type UU` deleted, the identical literal compiles and runs. The union is what moves `p`'s
element resolution onto the path the if-expression then escapes.

Both faces are silent: annotating `const xs: P[] = …` produces the identical validator
sentence at the identical offset.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the union declarations (`type Q`, `type UU`) | runs, prints `1` | **yes** |
| the if-expression element (`const xs = [p]`) | runs, prints `1` | **yes** |
| the annotation on the binding (`const xs: P[] = …`) | still invalid wasm | no |

#### Grading list

`emitArr`'s loud floor is the second half of this row: a fix that teaches `arrLitIsRef` the
if-expression element must also make `exprStruct` (or whatever replaces it there) see one, or
the next unclaimed element shape lands here again silently instead of loudly. Re-grade
`scripts/capability-probes/generic-pin-struct-array-literal.vl` (D1666's listed
`struct array elements are not supported`) with it — that is the loud face of the same
classifier.
