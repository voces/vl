### D7281 — a `let` bound to one hole lambda and written with another, in a list inside a generic called at two types, traps on an indirect call type mismatch

**closed 2026-10-19 by lane L1 · runs, prints `S 3 S s` · was loads then traps · clause 1 · a lifted lambda's own hole parameter, and its result where that reads the parameter, are pinned by the call type its value reaches in each instance (`monoLamReachParamTy`), not left at the hole's default · pin: `tests/cases/closures/two-lambda-written-let-in-two-instances.vl` · found closing [D7201](D7201.md) · present on master `966471462` · filed 2026-10-19 against master `966471462`**

    function g<T>(x: T) {

#### Mechanism

#4179 asked the call type a lambda's value reaches in each instance for a parameter whose type
names another declaration's type variable ([D7181](D7181.md)), and skipped a parameter that is
the lambda's own hole (`!tyIsParamHole` in `monoLamParamPinAnn`). These two lambdas' parameters
are holes, so both instances shared one lift at the default `i32`, and the call at `string`
went through a table slot of the wrong type. Both the parameter and the result pin
(`monoLamPinRetAnn`) now ask the reached call type. Lifting the parameter's guard alone traps
`tests/cases/generics/hole-list-literal-local-nullable.vl` on a null reference, because the
result stays at the default while the parameter is pinned at `string | null`.
