### D17084 — a callback parameter's scope type is the annotated sibling's `J` while its reads are typed `{ f: null }`, so a closure capturing it misses at `capture binding`

**runs today and must keep running · the IR claims the closure since lane COV-CLOS read a capture held at a row its read does not record as held (`capRowlessTy`, 2026-11-26) · the IR's `capture binding` (held rep is not the read's) · found by lane IR-N4 in `capture binding`'s record-twin shape · filed 2026-11-23 against master `b03c57be`**

Repro:

    type J = { f: i32 | null }
    function mk2() { return { f: null } }
    const dA: J = mk2()
    const src = [mk2()]
    const r = src.filter((y) => {
      const go = () => print(y.f)
      go()
      return true
    })
    print(r.length)
    // vl run: prints null, 1. VL_IR_SHADOW=4 vl check --codegen: "blockers capture binding" in __lambda.

Want:

    null
    1

#### Mechanism

The checker types every read of the callback parameter `y` as `{ f: null }`: `const a: J = y` is an
error inside the callback and inside `go` alike, and `const a: { f: null } = y` checks in both. The
parameter's scope type in its frame (`scopeTyAt`, which the IR's `capTyOf` reads for the capture's
binding) is `J` instead, the type `const dA: J = mk2()` gives `mk2()`'s result. The two record reps are
not stored alike (`repStoresAs` false both ways), so the capture's held rep is not its read's and
the IR refuses the closure. Legacy's bytes run correctly; which of the two types is the frame's
truth is the checker's question.

| ingredient | outcome | needed? |
| --- | --- | --- |

| the closure (`print(y.f)` in the callback body) | `narrowed read`, no `capture binding` | **yes** |
| `filter` (a plain function `k(y: J)` instead) | matched | **yes** |
