### D5750 — a function handed to an un-annotated parameter is called with more arguments than it takes, and the checker does not refuse it

**closed 2026-10-17 by lane L3 · now a loud check reject, "wrong number of arguments: expected 1, got 2", naming the body of `apply` · was loud emit reject · clause 2 (the checker owes the diagnosis) · a call through a hole re-checked at the pinning call gives the direct spelling's exact-arity sentence (`callFloorMsg`, `callPinArityMsg`), and a declared generic, still open there, is refused rather than re-recorded (`callPinOpenArityMsg`) · pins: `tests/cases/functions/error-fn-value-to-hole-param-wrong-arity.vl` · found closing [D5612](D5612.md) · filed 2026-10-17 against master `5aa033e26`**

Repro:

    function idg<T>(v: T): T { v }
    function apply(g, x, y) { return g(x, y) }
    print(apply(idg, 3, 0))
    // vl check: rc 0.  vl run: emitProgram: a function-value call has no interned signature — the callee has no function type to key a signature from

Want:

    a `vl check` error naming the arity: `idg` takes one argument and `apply` calls `g` with two

#### Mechanism

From the ablation only. The program is ill-typed: `g` is called with two arguments and is
handed a one-parameter function. With `g` annotated, the checker refuses it at the argument.
Un-annotated, the hole's type is fixed by the call inside the instance, and the checker never
compares it with the argument's arity. The emitter then refuses with a different sentence for
each kind of argument.

#### Close

One place: the deferred call constraint `validateMemCstrs` re-checks at the pinning call now
carries the inner call's node, so the floor compares the function's parameter count with the
arguments that call passes. Exact arity, as a call through a function value has: a default
does not widen it. A spread argument is left to the existing paths.
