### D13860 — a hole function parameter handed on to a generic at two types is refused at emit

**closed 2026-11-01 · runs, prints `3 8` · `outer`'s instance binds `h` to `add`'s set, a parameter handed on to a named function's hole takes the set that function's calls take (`mintParamTakes`), and the tag decision after the elaboration tags it, so `apply2` calls `add` at each call's own types with no split · was loud emit reject · `vl check` rc 0 · `emitProgram: cannot take the generic function `add` as a value — a function value carries ONE signature` · clause 2 · grading list: the lambda spelling (`const run = (x) => { apply2(h, x) }`) runs too, a captured parameter handed on from a nested function being a forward edge (`elabMintHandedNested`) and the lambda's call keying `apply2` by the set its instance binds `h` to; both captured fixtures keep running · pins: `tests/cases/closures/hole-fn-param-handed-on-to-generic-at-two-types.vl`, `tests/cases/closures/hole-fn-param-handed-on-from-lambda-at-two-types.vl` · found by lane L1 closing [D13720](D13720.md) · filed 2026-10-25 against master `0efe9c8bf`**

Repro:

    function add(a, b) { return a + b }
    function apply2(g, s) { print(g(s, s)) }
    function outer(h) {
      apply2(h, 1.5)
      apply2(h, 4)
    }
    outer(add)
    // vl check: rc 0.  vl run: emitProgram: cannot take the generic function `add` as a value

Want:

    3
    8

#### Mechanism

Not traced past the ablation. `outer`'s two calls ask `h` for two signatures,
`(f64, f64) => f64` and `(i32, i32) => i32`. The argument `add` is pinned at the first, or at
neither, but never split into one copy of `outer` per signature. A direct `add` handed to
`apply2` at both types does get two pins. [D12231](D12231.md) is the same refusal reached
through a list element rather than a parameter. The lambda spelling, `const run = (x) => {
apply2(h, x) }` called as `run(1.5)` and `run(4)`, refuses the same way.
