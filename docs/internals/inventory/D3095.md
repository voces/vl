### D3095 — a generic callback taker given an un-annotated named function has no pin for the function argument

**closed 2026-10-09 by lane SC, with D3913 · runs · was loud emit reject · clause 2 · found by the #3271 review · filed 2026-09-28 against master `505bb44e0` · pins: `tests/cases/generics/named-hole-function-to-generic-callback-parameter.vl`**

Repro:

    function app<T>(x: T, f: (T) => boolean): boolean { return f(x) }
    function g(w) { return w is i64 }
    const z: (string | i64)[] = [5, "t"]
    for e in z { print(app(e, g)) }
    // vl check: rc 0.  vl run: emitProgram: monomorphize: unsupported argument type for `f`
    // in a call to `app`

Want:

    true
    false

#### Mechanism

D3913's. A named function with a hole parameter is generic to the monomorphizer, so it has no
signature of its own for `f: (T) => boolean` to bind `T` from. The value argument `x` had already
pre-bound `T`. Closed with D3913: a generic function value takes the arrow parameter's annotation
substituted at those bindings. The grading list's record-union element runs too.

The concrete twin `appc(x: string | i64, f: (string | i64) => boolean)`, and a record-union element.
