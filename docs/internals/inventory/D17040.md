### D17040 — a record field typed by one bare string literal is stored as its atom or its string by row, so no type-only rep rule matches both rows

**runs today and must keep running · an I8 precondition (one of the misses I8 needs at zero) · filed 2026-11-21 against master `4c186c33`**

Repro:

    function mk() {
      const y: "a" = "a"
      return { f: y }
    }
    type A = { kind: "a", x: i32 }
    const a: A = { kind: "a", x: 1 }
    function mk2(n: i32): A { return { kind: "a", x: n } }
    print(mk().f)
    print(a.x + mk2(2).x)
    // vl run: prints a, then 3. $VL_IR_SHADOW=1 on ir-field-lit-atom: `mk2` and the cell `a`
    // match, and `mk` misses as `uncovered object field coercion`.

Want:

    a
    3

#### Mechanism

A field typed by one bare string literal is stored as the atom (D7440). That is the row `A`
builds, and the rep tree's record kid agrees with it once `rtOfObjAs` asks D7220's
`repFieldLitAsSet`. A record whose value at that field is a binding holding the string (D15083,
`const y: "a" = "a"`) is built at a row whose store type is the string: `sFieldStoreTy` is chosen
at row construction from the value, not from the field type. The rep tree is keyed by type, so its
kid for a field of type `"a"` is either the atom or the string, and either answer leaves one of
the two rows a named miss. The IR fails closed there, keeping legacy's bytes, so output is correct.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| `y`'s binding (`return { f: "a" }`) | covered and matched | **yes** |
| the annotation `: "a"` on `y` (`const y = "a"`) | the field types as `string`, covered | **yes** |

#### Deferred design (option b)

Deferred by coordinator ruling, 2026-11-21. It stays an I8 precondition: I8 still needs this miss
at zero. The design: `rtOfObjAs` takes each field's kid from the row's store type rather than the
field type. It reaches `sFieldStoreTy` through a hook, because `structIndexOfTy` lives in
`emit_atom_kinds` and a direct import would make a cycle. The freshness risk is that the rep
tree is memoized by type and rebuilt only by `rtSync`. A row added after the tree is built would
leave a stale kid, so `rtSync` would also have to rebuild when struct rows grow. That costs fuel
on every row added, and it can change the reps of records that no row ambiguity touches. It needs
the self-compile fuel reading and an `ir-identity.sh --names` pass before it ships.
