### D14980 — a list literal delivered into a union-element list mints an `i32[]` list row nothing references, and for a mixed literal the spelling order decides it

**open 2026-11-02 · runs today and must keep running · a dead type, not a wrong answer: one canonical type should mint one set of rows (step 7), and here the member order of the element union decides whether an extra `i32[]` wrapper is minted · filed 2026-11-02 against master `e97881e1`**

Repro:

    type AB = "a" | "b"
    const k: AB = "b"
    const xs: (AB | i32)[] = [4, k]
    for v in xs { print(v) }

Want:

    4
    b

#### Mechanism

The list is built as a list of union boxes, `struct {ref (array (ref null box)), i32, i32}`, under both spellings. Spelled `AB | i32`, the module also holds `struct {ref (array i32), i32, i32}`, an `i32[]` list wrapper that no function, global or instruction references; spelled `i32 | AB`, it does not. The box struct and every tag are the same under both spellings, because `boxTagOfTy` reads the member alone, so the program behaves the same. The extra row is minted while the literal's elements (an `i32` and an atom, both `i32` at the rep) are still read as an `i32` list, before the list is built at its element union.

#### Grading list

The `[4]` spelling, which mints the unreferenced wrapper at both orders; the `i32 | string` parameter and map value pair, which differ only in type order (`box-dst` shadow grading, #5816).
