### D2881 — a record literal in an un-annotated list, later bound to a declared `{ f: i64 | null }[]`, takes an annotated `{ f: i32 }` row

**closed 2026-09-27 — the repro RUNS and prints `7` then `4` · was check-clean invalid wasm, the same on master `829bd497c` · closed by building an un-annotated list of object literals at the record row its declared destination names when that differs from the row its own elements pick (`letRecordListDestSlot`, read by the literal's build, the binding's cell and a global's element name) · fixture `tests/cases/soundness/list-literal-builds-at-declared-record-destination.vl` · found while writing the D2865 fixture · filed 2026-09-27**

Repro:

    const i: { f: i32 } = { f: 4 }
    type I = { f: i64 | null }
    const il = [{ f: 7 }]
    const ic: I[] = il
    print(ic[0].f)
    print(i.f)
    // vl check: rc 0.  vl run: invalid module in the top-level code — expected (ref null $type), found (ref $type)

Want:

    7
    4

#### Mechanism

The checker admits `il` into `I[]`, but types the literal itself `{f: i32}[]`. The emitter
picked the literal's record row by matching field names, and with an annotated `{ f: i32 }`
record in the module that row exists, so the list held `{ f: i32 }` rows where `ic` expects
`I`'s. Without that record the only row the literal fits is `I`'s, which is why it ran. The
destination walk D381 built for a union-box element (`letRefListDestSlotK`) already finds a
plain record destination; it was asked only to detect a conflict with a union-box one.

#### Ablation

| ingredient removed | outcome | needed? |

| the union field (`type I = { f: i64 }`) | still invalid | no |
