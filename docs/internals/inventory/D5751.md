### D5751 — an un-annotated generic handed to a const lambda's un-annotated parameter is not instanced at the call the lambda makes

**closed 2026-10-17 by lane L5 · runs, prints `-4` · was loud emit reject · clause 2 · the flow table walks a call through an un-annotated `const` hole lambda once more in the instance context mono builds for that call (`ffConstLamCall`, `ffInstCtx`), with the checker's own hole names for a lambda (`ffHoleName`), so the body's call closes a pin and `monoHoleGenFnPin` takes it · pins: `tests/cases/closures/hole-lambda-takes-generic-fn-value.vl` · found closing [D5612](D5612.md) · filed 2026-10-17 against master `5aa033e26`**

    function neg(a) { return 0 - a }

#### Mechanism

From the ablation only. [D5612](D5612.md)'s close instances a generic at the one pin past a call
to a hole FUNCTION. A const lambda's parameter is not a function hole: `lap` is one closure
value, not instanced per call, so `monoHoleGenFnPin` never runs for `lap(neg, 4)` and nothing
else pins `neg`.

#### Close

The flow table walked a const lambda once, in its declaring context, where `x` is the
lambda's own open hole, so the pin of `g(x)` stayed open and `neg` reached no closed pin. Its
per-call contexts named a lambda's holes `?__lambda_0.i` where the checker says `?#L<node>.i`,
so even a per-call walk would have bound nothing. A call through the const now also walks the
lambda in that call's context, and an edge carries each argument into it, one direction only,
so two calls passing two functions do not share pins.
