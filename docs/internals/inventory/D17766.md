### D17766 — a const-bound lambda whose slot holds an instance's clone is called as a closure, not directly

**runs today and must keep running · a refutation pin: 211 call sites in 173 corpus programs that the D17748 rule declines only for the slot · filed 2026-11-27 against master `fddec816e`**

Repro:

    const outer = () => {
      const l = (x) => x
      return l
    }
    const v = outer()
    print(v(41) + 1)

Want:

    42

#### Mechanism

The D17748 rule (`constLambdaCallee`, `compiler/ir_build.vl`) makes a call through a `const`
bound to a capture-free lambda a direct call, but `constLambdaPos` declines it when the slot
`fnStmtsPosOf` names does not hold the lambda itself (`fnStmts[pos] != init`). That happens in two
shapes:

- The lambda's body holds a hole lambda (`outer` above), so the monomorphizer instantiates it and
  the template's slot holds an instance's clone. `identLetOfRead` finds the binding, but no
  instance slot is keyed to the call.
- A lambda captured from an enclosing generic frame (`d15110_captured_*`), where
  `identLetOfRead` names no binding in the reading frame.

The call stays a closure call, which runs, so this is debt, not a defect: the decline is what
instance-slot keying in lifting PR 2b removes.

site counts separately):
