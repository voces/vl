### D3868 — an uncalled top-level function that reads and rewrites a module-scope alias of a hole lambda is emitted with the alias at the wrong signature

**closed (2026-10-08, lane SC) · now a loud emit reject, `the reassigned function binding \`d4\` holds lambdas called at more than one argument type` · was check-clean invalid wasm · the module-scope twin of D3864 · found by the rv3458 review of #3457/#3458 · filed 2026-10-08 against master `fd225840b` · pins: `tests/cases/closures/error-module-alias-called-at-two-types-in-dead-function.vl`, `tests/cases/closures/module-alias-chain-called-in-function.vl`**

Repro:

    const x = "a"
    const n = 4
    const c = (y) => y + y
    const e = (y) => y + y + y
    let d1 = e
    print(d1(x))
    print(d1(n))
    let d3 = d1
    let d4 = d3
    function rw2(): string { const r = d4(x); d4 = c; r }
    print(d4(n))
    // vl check: rc 0.  vl run: rc 70, invalid module inside `rw2`, `type mismatch: expected i32, found (ref $type)`

#### Mechanism

Two halves. A module-scope alias found from inside a function was taken to live in that
function's frame (`monoLetFrameOf`), so the next link of its chain (`d3`, then `d1`) was looked
up in `rw2` and not found; on the emit side a copy-initialized binding's key was read from its
initializer's hole-typed checker type rather than chased to the lambda (`calleeCloSigKeyAt`).
So `d4(x)` in `rw2` resolved to nothing and lowered against the module's `i32` form. Both now
resolve a module-scope binding at module scope, which makes every chain of module-scope `let`
and `const` aliases called inside a function run (gen3: 65, gen5 at module scope: 25 programs,
loud on master). With the chain resolved, the witness is what D3857 refuses: `d4` is called
at `i32` and, in `rw2`, at `string`. `rw2` is uncalled, but a module-scope function is lowered
whether or not anything names it, so its call counts. Stubbing an unnamed module-scope function
instead broke callback specialisation and imported self-functions, so it is not done here.
