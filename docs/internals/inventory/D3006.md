### D3006 — an `i32 | null` field re-seated at a wider declared `f64 | null` record is read back through `??` at its own type

**closed · was check-clean invalid wasm on master `b34730ad9` and on #3253 · a box delivered into a wider record's union field is rebuilt at the wider member (`emitUnionBoxArg` → `emitBoxAtomRetag`), and a field read through the own handle rebuilds it back at the own member (`memReadBoxNarrowName`), at `emitMem` and at the `??` field arm · fixture `tests/cases/objects/record-literal-widened-nullable-box-read.vl` · found by the #3253 review grid · filed 2026-09-28**

Repro:

    type D = { v: f64 | null }
    const x: i32 | null = 3
    const c: {[string]: D} = Map()
    const o = { v: x }
    c["k"] = o
    print(o.v ?? 0)
    // vl check: rc 0.  vl run: invalid module — type mismatch

Want:

    3

#### Mechanism

Two halves, both about the box. The literal is built at `D` (the two records share one wasm struct), so its field is the `f64 | null` box, but `x`'s `i32 | null` box was stored in it unconverted: the wider handle cast the `i32` payload to `f64` (a trap, even on master). And a read at the own type took the field's declared `f64 | null` spelling, so `o.v ?? 0` produced an `f64` where the checker's `i32` was expected. Every box stored into a union now widens the members the destination lacks, and a read whose receiver's checked field lacks the stored member narrows back, so every consumer (the un-narrowed box, `??`, a `!= null` narrowing) sees the own member set.

As filed: The map store builds `o` at `D`, whose `v` is an `f64 | null` box, and `o.v ?? 0` is lowered at the checker's `i32 | null` rep, so the box's payload is read at the wrong width. The D2991 box retag (#3252) converts a box delivered into a wider field; nothing converts one read back out at the narrower type.
