### D17565 — a concrete `null ?? "m"` delivered to a `"m" | "n"` binding is refused, while the same `??` inside a hole function called at `null` runs

**loud check reject · clause 2 · `cannot assign string to 'w' of type "m" | "n"` · found tracing D17561 · owner SOUND (design question: the coordinator rules) · filed 2026-11-25 against master `4f2c230e`**

Repro:

    const n = null
    const w: "m" | "n" = n ?? "m"
    print(w)
    // vl check: [ERROR] cannot assign string to 'w' of type "m" | "n"

Want:

    m

#### Mechanism

A concrete `??` types its result with the literal default widened to its base, so `n ?? "m"` is a
`string`, and a `string` is not a `"m" | "n"`. The same `??` inside an un-annotated function, a
deferred `HD_COAL` result, resolves at a `null` pin to the default's own literal type
(`coalJoinAtPin`), so `function j(x) { return x ?? "m" }` delivers `j(null)` to that binding and
runs. One of the two typings is wrong for the language; which one is a design ruling. The
coordinator ruled 2026-11-25 that D17561's close leaves `j(null)` alone and this row stays unfixed
until ruled.

#### Ablation

| spelling | outcome |
| --- | --- |
| `const n = null; const w: "m" \| "n" = n ?? "m"` | refused |
| `function j(x: null) { return x ?? "m" }; const w: "m" \| "n" = j(null)` | refused |
| `function j(x) { return x ?? "m" }; const w: "m" \| "n" = j(null)` | runs, `m` |
