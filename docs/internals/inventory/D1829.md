### D1829 — `xs.get(i) ?? d` over a nullable-element list is check-clean invalid wasm, while the subscript spelling runs

**check-clean invalid wasm · filed 2026-09-06 against master `0c76469bd` · found while
closing D1828, which built the arm the SUBSCRIPT spelling of the same read needed**

Repro:

    const xs: (i32 | null)[] = [7, null]
    print(xs.get(0) ?? 0)
    // vl check: rc 0. Then: the emitted module failed to validate inside the module's
    //   top-level code: type mismatch: expected (ref $type), found (ref null $type)
    // Should print 7 — `xs[0] ?? 0` does.

#### Mechanism

Not yet ablated to a rung. The `.get(i)` form has its own fused `?? d` arm — the one D1677
staged the index and the receiver for — and that arm reads the element as a non-null ref. An
element that is a nullable value-union BOX is `(ref null $box)` in the backing, so the arm
leaves a nullable ref where its block type wants a non-null one. The subscript spelling
`xs[0] ?? 0` takes a different arm and runs (D1828), which is what makes this its own row: one
capability, two spellings, and only one of them wired.
