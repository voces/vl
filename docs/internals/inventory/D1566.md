### D1566 — an OPERATOR over an unpinned `__array_new_default__` element trapped the compiler, and the `-1` guard alone leaves 15 positions refusing and 2 miscompiling

**closed 2026-09-04 — the witness runs and prints `1` · was a compiler trap (`vl check` rc 70, `wasm trap: out of bounds array access`, the "the compiler itself trapped" banner) · clause 1 by outcome and clause 2 in substance: the user gets a wasm backtrace where a diagnostic belongs · fixed by having an operator operand PEEK the intrinsic's default instead of taking it, leaving the row open so a later store still decides · found by the hole-link fixpoint agent on #2496, reproduced against master `dd269620`, landed on top of #2494**

Repro (before: `vl check` rc 70 with a wasm backtrace; now: prints `1`):

    function f() {
      let a = __array_new_default__(3)
      print(a[0] + 1)
    }
    f()

Second grade, the cell the `-1` guard alone cannot reach (before: same trap; with #2494's guard
alone: `operator '+' is not defined for i32 and _`; now: prints `1`):

    function g() {
      let a = __array_new_default__(3)
      print(1 + a[0])
    }
    g()

#### Mechanism

`__array_new_default__(n)` returns an array row whose element is a HOLE, because
`array.new_default` promises each slot's zero and says nothing about which element — the
destination pins it, and a hole nothing pins takes the `i32` default at `flushUninferred`
(D1470). That flush runs when the SCOPE CLOSES, i.e. after the body is checked, and until then
`a[0]` reads back as the in-band `-1` that `arrElemValueTy` hands out for "no answer".

Most positions tolerate that. `print(a[0])` runs and `const v = a[0]` runs, because nothing on
those paths uses the element type: the emitter reads the ROW, after the pin. The operator arms
are the exception — `checkBinExprNodeReal`'s dispatch does `const odsp = T.tys[lt]` — so a `-1`
operand is an out-of-bounds array access inside the compiler. That is the trap: `T.tys[-1]`,
one unguarded read, reached by every arithmetic, bitwise, ordering and coalescing spelling.

**THE `-1` GUARD STOPS THE TRAP AND IS NOT THE FIX.** #2494 added `if lt < 0 { return TY_ERR }`
for D1462, and it carries this row's own witness to `runs` — `TY_ERR` suppresses the arms and
the emitter resolves the row after the flush. Measured on merged master (`d4568ff1`, seed
2,063,568) with only that guard, what it leaves behind is:

* **15 of 20 un-annotated matrix positions refuse loudly** — the guard covers only `lt`, so
  `print(1 + a[0])` reaches the arms with `rt == -1` and answers `operator '+' is not defined
  for i32 and _` where its `let a: i32[]` face prints `1`. `-a[0]` is the same hole at the
  unary arm, and `return a[0] + 1` refuses because `TY_ERR` propagates into the inferred return.
* **two cells become check-clean INVALID WASM** — `print("v=" + a[0])` and `print(a[0] + "x")`.
  The guard's `TY_ERR` suppresses the diagnostic their `i32[]` face raises, and the emitter
  then builds a string concat over an i32 element. A trap traded for a clause-1 miscompile.

So the operand takes the answer the flush is going to give it — `arrDefOperandElemPeek`, for a
row that is the intrinsic's own or ONE HOP from it through a `noteHoleLink` pair.

**IT PEEKS, IT DOES NOT PIN, AND THE DIFFERENCE IS TWO `runs`.** The first candidate wrote the
element in place through `arrDefPinHoleElem`. That answers the arms and costs the STORE its
turn: `print(a[0] + 1)` followed by `a[0] = 1.5` (or `a.push(1.5)`) runs on the guard-only seed
and became `cannot assign f64 to i32` — a `runs -> not-runs` the pin caused and the peek does
not, because the ROW is left open and D1470's rule still decides the element. What the read
does record is its OWN node type, which `checkNode` banked as `-1` a moment earlier and the
emitter reads: without that, `print(a[0] ?? 1)` refuses at emit while its annotated face runs.

**A BARE `[]` IS DELIBERATELY NOT SERVED.** `array.new_default` is what licenses the default;
`const xs = []` never promised a zero and its element is genuinely under-determined (D1462).
That witness lands on its binding's own `cannot infer a type for 'xs' — add a type annotation`.

#### Grading list

* **The two ordering constraints on the `-1` guard, which is the only line satisfying both.**
  It must sit BELOW the `=` arm (D1462's, since `xs[i] = v` pins the open element from the RHS
  while `lt` is still `-1`) and BELOW the peek (this row's, or the witness refuses instead of
  running). `const xs = [0]` / `xs[0] = 5` / `print(xs[0] + 1)` must print `6`, and it is a

* **A CORRECTION THIS ROW OWNS: `const xs = []` / `xs[0] = 5` / `print(xs[0] + 1)` IS NOT A
  COMPILER TRAP.** It was recorded here as one and it is the PROGRAM's own out-of-bounds store:
  `const xs = []` is a zero-length array, so `xs[0] = 5` traps at runtime, exit **1**, no
  "the compiler itself trapped" banner, and the backtrace names `vl!<wasm function 4>` — the
  user's module, not the compiler's. Measured on three seeds by the D1569 agent (#2501), whose

  Only the banner and exit 70 separate them, and any grader that does not test for the banner
  will make this mistake again.
