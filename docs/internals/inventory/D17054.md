#### Mechanism

`arrLitShortWhy` (`compiler/wasmEmit.vl`) answers `long` when a literal has more elements than its
arm's cap: `allocLitChunk()` (`ALLOC_LIT_CHUNK`, 256) for a string list, `NEW_FIXED_MAX` (10,000)
otherwise. The IR's list-literal build (`compiler/ir_build.vl`, the `arrLitShortWhy` call) misses
on any non-empty answer, so the function stays legacy's. Legacy has three routes past the cap: one
data segment when every element is a constant, a data segment plus stores for computed elements,
and a chunked build. The 2026-11-20 measurement put this class at 14 corpus plus `tests/cases`
cells and 0 in the self-compile (`refactor-notes/2026-11-20-ir4-long-lit.md`). Phase A (the
constants-only route, with segments deduplicated by content) was built and measured on branch
`ir4-long-data` (voces/vl#9275, parked, then closed unmerged): 4 of the 14 matched, `ir-identity` differ
0, L2 fuel +0.059%, +202 / −22 compiler lines. Its design and its refactor note
(`docs/internals/refactor-notes/2026-11-20-ir4-long-data.md`) are on that branch. The fix is a
re-implementation on the current tree covering all three routes, not a rebase: the branch is 309
commits behind and conflicts in `ir_build.vl`, `ir_lower.vl` and `lint.vl`.
