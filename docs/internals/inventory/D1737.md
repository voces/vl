### D1737 — a `??` join's STRUCT default names no arm of its result union when another struct row precedes the arm's, because the lookup reads a variant-table index as a struct-table row

**closed 2026-09-06 — the annotation's struct-row resolver answers struct rows only, and finds
a variant's structurally-named row through the arena · filed against master `6de9fd11a` ·
0 corpus cells**

Repro:

    type A = { r: i32 }
    type W = { f: string | null }
    function st(): A { return { r: 8 } }
    function mkS(): string | null { return null }
    const w: W = { f: mkS() }
    const v = w.f
    const k = v ?? st()
    if k is A { print(k.r) } else { print(0) }
    // prints 8 since the close; before it, `vl check` rc 0 then exit 1,
    // emitProgram: `??` default names no arm of the union its result is

#### Mechanism

`retStructIndex` resolves a return annotation to a struct-TABLE row, and where the name scan
misses it answers `variantIndexOf` — a VARIANT-table index, on the same channel, documented as
being for `pushVT`'s kind-8 case. Every reader that treats the answer as a struct row is then
reading another table, and the two agree only while the arm's struct is row 0. One more
declared struct is enough to separate them, which is why `type W` is the ingredient and the
`??` is not.

The name scan misses because a struct that becomes a union VARIANT through an INFERRED join is
registered under the structural render (`{r:i32}`), not under `A`. A declared
`type M = string | A` gives it a named row and does not reproduce the defect.

Two edits. `retStructRowIndex` answers struct rows only and gains the arena rung the name scan
needs — `repRowOfTyStruct` on the recorded type, which finds a structurally-named row by its
TYPE. Every struct-row reader takes it: the return-value seed for `pendingStructIdx`, the
signature's result valtype, the `fRetStructIdx` producer (gated on the same `fRetKind` its
readers gate on), the anon-leaf row, and `annValtypeSlotOf`'s tail — where every variant kind
is already answered above, so a variant index reaching it was one table's index in the other's
channel.
