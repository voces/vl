Repro:

    type O = { v: i64 | boolean }
    function f(o: O) {
      while o.v is i64 {
        print(o.v + 1)
        o.v = true
      }
    }
    f({ v: 3 })
    // vl check: rc 1,
    // operator '+' is not defined for i64 | boolean and i32

#### Mechanism

Two filters, one rule, spelled once each: `checkWhileStmtNode` keeps only condition facts
whose key `!isPathKey`, and `emitWhile` / `collectLocalsWhile` hold `narrowBareIdentOnly`
across the loop-body push, which `pushNarrowRep` enforces at the single bottleneck every
narrowing channel bottoms out at. Neither half can narrow what the other does not, which is
why the refusal is loud rather than a rep disagreement.

It is the PATH that declines, not the `is` — `while o.v != null` over `{ v: i32 | null }`
refuses with `operator '+' is not defined for i32 | null and i32`, and both `if` spellings of
both guards run. So the cell is (loop x path), not (loop x pin), and D1736's close narrowed
the loop's restriction to exactly this one without touching it.

**The stated reason is REFUTED by measurement, 2026-09-07.**
`tests/cases/loops/while-body-path-guard-not-narrowed.vl` justifies the restriction with an
alias hole in the `if` spelling: "with a `clr(o) { o.v = null }` in the arm,
`if o.v != null { clr(o); o.v.length }` is `vl check`-clean and TRAPS". Run today that program
is a loud check reject — `'o.v' was narrowed by a guard, but the call to 'clr' on line 5 can
write it — re-test 'o.v' after the call` — because `noteCallInvalidations` now retires a path
narrowing across a call. The hole the loop was kept out of is closed, so what remains is a
capability the `if` has and the `while` does not.
