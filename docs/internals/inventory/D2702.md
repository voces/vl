### D2702 — a single-arm list literal written directly as a lambda's argument is built with the wrong element storage

**check-clean invalid wasm · `type mismatch` inside `f`, the same on master `1a3088c65` and after D2696 · filed 2026-09-26 from the #3196 re-review (its a1, a2b, a5)**

Repro:

    type Circle = { r: i32 }
    type Sq = { s: i32 }
    type Shape = Circle | Sq
    function sum(xs: Shape[]): i32 {
      let t = 0
      for e in xs { if e is Circle { t = t + e.r } else { t = t + e.s * 10 } }
      t
    }
    function f() {
      const k = (xs: Shape[]) => sum(xs)
      print(k([{ s: 1 }]))
    }
    f()
    // vl check: rc 0.  vl run: invalid module inside `f`; should print 10

#### Mechanism

Not yet located. An argument literal takes its element storage from the call it is passed
to, not from a binding, so [D2696](D2696.md)'s destination scan never sees it; the call-site
seeding that serves `sum([{ s: 1 }])` (which prints 10) evidently resolves only a top-level
function callee. The prediction to check: the argument's `pendingListKind` is seeded from the
callee's `FuncDecl` found by name, and a lambda-valued local, parameter or module `const`
reaches none — so the fix is the scope-first resolution `dsCalleeParamSlot` already does.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the lambda (call `sum([{ s: 1 }])` directly) | prints 10 | **yes** |
| the inline argument (bind `const out = [{ s: 1 }]`, pass `out`) | prints 10 after D2696 | **yes** |
| the single-arm literal (`[{ r: 1 }, { s: 1 }]` infers `Shape[]` itself) | prints 11 | **yes** |

#### Grading list

The re-review's a1 (a module-level lambda called from the top level), a2b (a block-local
lambda shadowing a module one) and a5 (a nested closure's parameter shadowing an outer
lambda, whose own part now runs); the same call with the lambda as a function-typed
parameter.
