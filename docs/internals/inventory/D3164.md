### D3164 — a `for-in` directly over a `"[]"` operator's literal-union list prints the atom ids

**closed · a user operator's call carries the operator expression's checked type, so a walk over its `K[]` result flags the element as an atom · fixture `tests/cases/operators/index-operator-literal-union-walk.vl` · was check-clean silently wrong · clause 1 · found by lane NC re-grading the #3281 round-3 review (`rv3281r3-10862/x/y01.vl`) · the same on master `b1794003a` · filed 2026-09-29 against master `b1794003a`, closed 2026-09-29 against master `a0b9acaf8`**

Repro:

    type K = "a" | "b"
    type Bag = { ks: K[] }
    function "[]"(self: Bag, i: i32): K[] { return self.ks }
    function h(bag: Bag) {
      for e in bag[0] {
        print(e)
      }
    }
    h({ ks: ["b"] })
    // PRINTS 0
    // vl check: rc 0.  vl run: prints the member's atom id; over `["b", "a"]` it prints 0 and 1

Want:

    b

#### Mechanism

`drwWalk` rewrites a user `"[]"` (and a user binary operator) into a call node appended past
the arena, and the new node recorded no checked type. `forInVarIsLitAtom` asks the iterable's
recorded type whether the element is a literal union, so the loop variable was never flagged as
an atom and `print` widened it as a plain `i32`; a capture of it read the env field as a string.
The rewrite now carries the operator expression's type onto the call (`drwOpCall`). The same
fix takes `nb[0] ?? d` over an operator returning `K | null` from a loud refusal to running.
