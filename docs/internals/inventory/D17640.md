### D17640 — a list literal of records a declared record's row serves looks its list up by that record's type, which keys none

**closed · a list literal whose row type keys no list (a declared record whose function field has another signature serves its elements by rep) now takes the list its own element type keys (`arrLitRowSlotIn`) · fixture `tests/cases/structs/list-of-record-beside-declared-record-with-another-field-function.vl` · was loud emit reject (`emitProgram: ref valtype with no interned shape`) · clause 2 · found by lane COV-START writing the array-element retag sweep · filed 2026-11-26 against master `4e1e72f0b`, closed 2026-11-26 by lane COV-START**

Repro:

    type R = { v: i32, f: () => boolean }
    const xs = [{ v: 2, f: () => 11 }]
    print(xs[0].f())

Want:

    11

#### Mechanism

The list literal's element type (`{ v: i32, f: () => i32 }`) has the same rep key as `R`
(`() => i32` and `() => boolean` both lower to an i32 result), so `R`'s struct row serves the
elements (`repRowOfTyStruct`). The direct binding does the same and runs, since a call through the
field reads the receiver's own type (D3180's `instRecvFieldFnTy`). The list's wrapper row is
minted keyed by the literal's own element type. But `arrLitRowSlotIn` looked it up by `R`'s type
(`arrLitRowTyIn`), which keys no list, so the global's cell had no list slot.
