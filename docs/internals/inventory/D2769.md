### D2769 — an `is` test between two list types of one storage cannot tell them apart

**check-clean silently wrong · the #3207 round-2 review · filed 2026-09-27 against master `f6db92e0d`**

Repro:

    function h(c: boolean, t: boolean) {
      if c { return [t] }
      [1]
    }
    const q = h(false, true)
    if q is boolean[] { print(q[0]) } else { print(-1) }
    // PRINTS true

#### Mechanism

`boolean[]` and `i32[]` are both stored as the i32 list, and the value carries no tag, so
`q is boolean[]` has nothing to test at run time and answers from the static type. `h(false,
true)` returns `[1]`, an `i32[]`, and the test says `boolean[]` and prints `true` where `-1` is
right; `is i32[]` on `h(true, true)` answers true the same way. The generic spelling at
`T := boolean` builds one list for the pair too (D2766) and answers the same.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the shared storage (`t: string`) | invalid wasm ([D2768](D2768.md)) | **yes** |
| the `is` test (`print(q.length)`) | loud check reject, `not on every member` | **yes** |
| a type parameter `h<T>(c, t: T)` at `T := boolean` | prints `true` | no |

#### Grading list

The #3207 round-2 grid's `b_G_boolean_*_isT` cells: one of each true/false pair is wrong on
master and on the PR, which one depending on the list the pair is built as.

#### Design (not built): a tag for `boolean[]`, not a wasm type

Investigated 2026-09-27 against master `7323baf55` for the whole family (D2769, D2800, D2809,
D2813, D2820), and not built, because the cheaper form still touches the box ABI in about
25 functions and the family is three mechanisms, not one.

**The concrete spellings already box.** In D2769's own witness `h` returns the union box
`(struct i32 anyref)` on both paths. What is missing is the tag, not the box: both arms carry
tag `uVariants.length + 7`, because `valueAtomKind` answers 7 for `i32[]` and for `boolean[]`
alike, and `is boolean[]` compares against that same tag. So `is` has a tag to read, and it
reads the same value for both arms.

**Option A, a distinct wasm type for `boolean[]`** (the brief's first guess): a second
`(array (mut i32))` plus wrapper struct at other indices of the one rec group, which WasmGC
treats as distinct types, so `ref.test` could tell them apart. Cost measured by reference
count: `lTypeIdx`/`aTypeIdx`, the one i32 list type, is read at **318 sites in 99 functions**.
Every one would need a per-value choice between the two heaps. On top of that it needs a new
`VKind` family (`boollist`, `nulboollist`), the parameter and return ABI, `print`, `==`, the
list methods, and every `std` function over `boolean[]`. The f32 list family is the size
precedent: `f32list` 113 references, `F32Array` 49. It is also unnecessary, since the box
already discriminates by tag.

**Option B, recommended: a distinct atom code for `boolean[]`, same payload heap.** Give
`boolean[]` its own value-atom kind and keep its storage on the i32 list, so a union box
tags the two arms differently and the unbox casts to the same `(ref $list)` either way.
Sites (measured by grep for the kind-7 arms):

* seven producers that map `boolean` to 7: `valueAtomKind`, `valueRowListKind`,
  `valueRowNulElemKind`, `nulElemListAtomKind`, `retAtomKindOf` (typecheck.vl), and
  `tyValueAtomKindOf` and `unMemAtomKind` (emit_classify.vl);
* about 17 consumers that read kind 7 as "the i32 list": `listWrapHeapOfKind`,
  `emitUnionCoerce`, `emitEqNonNullCore`, `coalNicheAtomKind`, `refAtomElemName`
  (wasmEmit.vl), and `identListRep`, `callListRep`, `indexListRep`, `retKindPri`,
  `retAnnKindChain`, `leqCoreKindOfAtomKind`, `eqCoreKindOfBin`, `mapValuesResultKind`,
  `retListKindFlag`, `markValueUnionAtoms` (emit_classify.vl), `leqNoteBin` (emit_collect.vl),
  `eqCoreKindOfTyToken` (typecheck.vl);
* the band: codes are append-only tag offsets and `uAtomBandTop` already lifts conditionally
  (13, 14 for `u8[]`, 15 for `v128`, 17 for the integer-keyed maps, and above that
  `mTwinExtra`). The new code has to sit above all of them under its own `used` flag, or it
  renumbers every tag in every program;
* `(boolean | null)[]` also rides kind 7 (`nulElemListAtomKind`) and needs the same split.

That closes D2769 and D2813, where the union is concrete. It does **not** close:

* **D2800**, the generic pin: at `T := boolean` the instance collapses `T[]` beside `i32[]`
  into one list because the two share storage, so there is no union to tag. The pin rule
  (`tyParamBesideConcrete`, D2783) has to keep them apart at `boolean` as it does at `string`.
  That lands in the checker and the monomorphizer (`monoTwoListRet`, D2766), both of which
  #3214 is changing now.
* **D2809**, the record twin: `{a: boolean}` and `{a: i32}` are one struct row, and a list tag
  does not reach a record. The same keep-apart rule is needed at the record join.
* **D2820** (unfiled: D2820 — its row lands with #3214), which is a separate mechanism: `print` classifies an element read of a generic
  call's result from the call node's template type `T[]`, never from the pinned instance's
  `boolean[]`. It needs no storage change.

**Cost not measured.** Seed size and plumb-shape fuel need a build. The expected price is
small, since only programs with a `boolean[]` union arm get the new code: one more tag
constant, and no new wasm type. That is a prediction, not a measurement.
