### D15091 — a list literal compared with a list whose elements are stored apart is refused

**closed · prints `true` · was loud check reject, clause 2 · the `==` check delivers a list literal beside a list stored apart at the other operand's type when it fits it, else at its own, and records which, so the compare reads the rep it is built at; a lossy number pair stays refused, as `f32 == 1` is (D15090) · matrices `xrep-float-list-vs-int-literal-eq`, `xrep-int-list-vs-float-literal-eq`, `xrep-nullable-int-list-vs-literal-eq` · the literal half of D15055's close · found closing it · filed 2026-11-03 against master `e1eb2e973`, closed 2026-11-03**

Repro:

    const g: f64[] = [1.0, 2.0]
    print(g == [1, 2])
    // was: vl check rc 1, "`==` over f64[] and i32[] has no lowering: a list literal beside a
    // list whose elements are stored apart is built at its own element type"

Want:

    true

#### Mechanism

D15055 compares two lists stored apart by reading each operand at the rep the emitter
classifies it at. A list literal operand is built sometimes at its own element type and
sometimes at the other operand's, and the classifier cannot tell which, so the cross-storage
compare would read it at the wrong rep: check-clean invalid wasm, or a wrong answer for
`(i32 | null)[] == [1.0, null]`. The checker therefore refuses the pair, as it did before D15055.
The close is a recorded fact naming the rep each list literal is built at, which the
storage-rep record plans (architecture-target-2026-10.md, step 6/7, "A reader to move here"):
`xrepEmitPair` then reads it instead of re-deriving the rep at emit.
