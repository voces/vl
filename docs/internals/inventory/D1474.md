### D1474 — an UNCALLED lambda whose body calls a function-typed parameter is a loud emit reject: nothing interns a `$fnsig` for that arity, and any unrelated call of the same arity makes it run

**loud emit reject · `vl check` rc 0 (one `Unused variable` warning) · clause 2 · the LAMBDA
spelling only; the identical `function` declaration runs · found 2026-09-03 by
`scripts/day-one/sample.py --seed 21` pair 17 (axis `scenery`), against master `cdfdc14e` —
the sampler drew it as an unrelated NEIGHBOUR and it broke every program it was attached to**

Repro (two lines; `vl check` rc 0, then the emitter refuses at 1:38):

    const apply = (f: (i32) => i32) => f(1)
    print(7)

#### Mechanism

`emitCallFnValue` resolves the call `f(1)` inside the lambda through `cloSigPosOfKey`, falls
back to `fnSigIdxForArity(args.length)`, and refuses at `wasmEmit.vl:16361` when that is `-1`.
It is `-1` because **nothing in the module interned an arity-1 closure functype**: the lambda
itself is never called, so no call site mints one, and a lambda binding — unlike a `function`
declaration — does not mint one from its own signature. The refusal is therefore about what
the MODULE happens to contain, not about the program under it, which is why an unrelated
neighbour is enough to fix it.

That is also why it reaches so far: as a plausible unrelated declaration this line is
`check`-clean and turns every program it shares a module with into an emit reject. In the
first 640-program sample it accounted for **41 of 69 non-agreeing pairs**; the sampler's
`--exclude hof` face is how the rest of the population was measured
(`docs/internals/day-one-sampler.md`).

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the lambda, spelled `function apply(f: (i32) => i32): i32 { return f(1) }` | runs | **yes** |
| the call of the parameter — `(f: (i32) => i32) => 1` | runs | **yes** |
| the parameter's function type — `(n: i32) => n + 1` | runs | **yes** |
| calling the lambda — `print(apply((x: i32) => x + 1))` | runs | **yes** |
| the arity — `(f: () => i32) => f()` | still refuses | no |
| the scope — the same binding inside `function go() { … }` | still refuses | no |
| adding an unrelated arity-1 call (`const inc = (x: i32) => x + 1` / `print(inc(1))`) | runs | **yes** |
| annotating the binding — `const apply: ((i32) => i32) => i32 = …` | runs | **yes** |

The last two rows are the mechanism stated twice: an interned arity-1 functype from anywhere
in the module, or an annotation on the binding that mints one, each removes the refusal
without touching the lambda.
