### D14576 — a parameter's annotation is found by name, shadowed through the live scope stack

**runs today and must keep running · a named floor, not a wrong answer: `paramTypeNode(fnIx, name)` declines a parameter whose name a live `let` shadows by asking `scopeSlotOf(name)` · deletion target: every caller handed the read node, after which `paramTypeNodeOfRead` (the read's declaration) answers and the name form goes · filed 2026-10-28 against master `7673b502b`**

Repro:

    function f(x: f64, m: {[string]: i32}) {
      if true {
        const x = 7
        const m = "s"
        print(x + 1)
        print(m)
      }
      print(x / 2.0)
      print(m["k"] ?? 0)
    }
    const mm: {[string]: i32} = Map()
    mm["k"] = 4
    f(3.0, mm)

Want:

    8
    s
    1.5
    4

#### Mechanism

`paramTypeNode(fnIx, name)` returns the annotation of `fnIx`'s parameter spelled `name`, and -1
when a `let` of that name is in scope (`scopeSlotOf(name) >= 0`), so a shadowed parameter's
type does not answer for the local's read. Every caller that holds the read node now asks
`paramTypeNodeOfRead(fnIx, atIx)`, which answers from the read's declaration and needs no
scope stack. The name form stays behind callers that hold only a name: the `param*`
predicate family (`paramMap`, `paramIsFuncType`, `paramNulClosure`, `paramNulStr`,
`paramF64`, `paramNulVariant`, `paramNulMap`, `paramNulRefArray`), `emit_list_rep`,
`emit_sig_tokens`, `emit_start_block`, `emit_union_atoms`, `emit_closure_sites` and two sites in
`emit_classify`, and eight sites in `emit_mono.vl`. It is right today because those callers
run while the frame is emitted, so the scope stack is the read's scope.

#### Grading list

The witness: the shadowing `let`s are `i32` and `string`, the parameters `f64` and a map, so a
parameter type answering for the local's read builds the wrong valtype.
