### D3972 — a nullable function narrowed by a test is refused as the value of an un-annotated capture cell

**closed by design · now a loud check reject · was a loud emit reject · ruling C (#3500) refuses it 2026-10-10 · clause 2 · found in review of #3498 (`rv3498/round5/f05`) · filed 2026-10-10 against master `56f77d80f`**

Repro:

    function inner<U>(u: U) { print("I"); print(u) }
    function other<V>(v: V) { print("O"); print(v) }
    function main() {
      let k = inner
      const f: ((n: i32) => void) | null = other
      const w = () => { if f != null { k = f } }
      k(1)
      w()
      k(1)
    }
    main()
    // vl check: cannot assign (i32) => void to `k`: it keeps the generic type of its initializer (ruling C)


#### Mechanism

Under ruling C (#3500) `k`, seeded with the generic `inner`, keeps the generic's type, so writing
the concrete `(n: i32) => void` held by `f` is a check error with an annotation fix; the program is
ill-typed. The annotated spelling, `let k: (n: i32) => void = inner`, is allowed and still traps
(D3974). Before the ruling: `f` is a nullable function narrowed by `if f != null` inside the closure `w`. Its narrowed read
keeps the nullable representation, and storing it into the cell `k`, whose element is a plain
function, trapped on the instance before #3498, which refuses it instead (`monoNameDeclNullable`).
D3973 and D3974 are the same narrowed store into an annotated cell, which no check reaches.
