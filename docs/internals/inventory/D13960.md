### D13960 — a wider record list spread into a narrower rest parameter skips the width-drop refusal its argument and list siblings get

**check-clean invalid wasm · clause 1 · carried as an unfiled ROADMAP item until the roadmap index split · filed 2026-10-26 against master `1501cdf28`**

Repro:

    type Shape = { r: f64 }
    type Circle = { r: f64, name: string }
    function total(...xs: Shape[]): f64 {
      let t = 0.0
      for x in xs { t = t + x.r }
      t
    }
    const cs: Circle[] = [{ r: 1.5, name: "a" }, { r: 2.0, name: "b" }]
    print(total(...cs))
    // vl check: rc 0.  vl run: invalid wasm, type mismatch: expected (ref $type), found (ref $type)

#### Mechanism

A `Circle` flowing into `Shape` drops a field, and the checker refuses that delivery with
"drops the field `name`: type-valid (structural width subtyping) but not yet supported by
codegen" at a plain argument and at a list handed to a `Shape[]` parameter. A spread into a
rest parameter is a third delivery of the same elements and reaches no such refusal, so the
emitter builds the rest list from the `Circle` structs unconverted. The fix is either the
element-converting copy at the spread or the same check refusal there.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the spread: `total(cs[0], cs[1])` | loud check reject (drops the field `name`) | **yes** |
| the rest: `function total(xs: Shape[])`, `total(cs)` | loud check reject (drops the field `name`) | **yes** |
| the annotation on `cs` | still invalid wasm | no |
| the dropped field as `w: f64` rather than `name: string` | still invalid wasm | no |
| a literal beside the spread: `total(...cs, { r: 0.5 })` | still invalid wasm (`expected (ref null $type)`) | no |
