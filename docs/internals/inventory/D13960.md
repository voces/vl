### D13960 — a wider record list spread into a narrower rest parameter skips the width-drop refusal its argument and list siblings get

**closed 2026-11-02 · now a loud check reject, the refusal its argument and list siblings give (drops the field `name`) · was check-clean invalid wasm, clause 1 · the numeric-field face that no refusal owes is [D14960](D14960.md) · fixture `tests/cases/objects/error-width-record-list-spread.vl` · carried as an unfiled ROADMAP item until the roadmap index split · filed 2026-10-26 against master `1501cdf28`**

Repro:

    type Shape = { r: f64 }
    type Circle = { r: f64, name: string }
    function total(...xs: Shape[]): f64 {
      let t = 0.0
      for x in xs { t = t + x.r }
      t
    }
    const cs: Circle[] = [{ r: 1.5, name: "a" }, { r: 2.0, name: "b" }]
    print(total(...cs))

#### Mechanism

A `Circle` flowing into `Shape` drops a field, and the checker refuses that delivery with
"drops the field `name`: type-valid (structural width subtyping) but not yet supported by
codegen" at a plain argument and at a list handed to a `Shape[]` parameter. A spread into a
rest parameter is a third delivery of the same elements and reaches no such refusal, so the
emitter builds the rest list from the `Circle` structs unconverted. Closed by the same check
refusal there: the width-drop check's list-literal arm (`objShapeAdapterless`) judged a spread
element at the spread's LIST type, which no record matches, so it found no adapter needed; it
now judges the list's element type, as a single element is judged. A list literal `[...cs]`
into `Shape[]` had the same gap and refuses the same way.
