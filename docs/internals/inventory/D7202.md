### D7202 — a list of a generic-initialized, lambda-written `let` inside a generic called at two types, iterated by `for`, has no signature at the second instance

**closed 2026-10-19 by lane L1 · runs, prints `L 3 L s` · was loud emit reject · `vl check` rc 0 · clause 2 · CAPABILITY · the loop variable's call keys its signature on the instance's binding, as [D7201](D7201.md)'s field read does (`cloInstanceSigKey`) · pin: `tests/cases/closures/written-let-in-list-iterated-in-two-instances.vl` · found closing [D7142](D7142.md) · the same on master `966471462` · filed 2026-10-19 against master `ee7f38cb5`**

Repro:

    function other<V>(v: V) { print("O"); print(v) }
    function g<T>(x: T) {
      let k = other
      k = (n) => { print("L"); print(n) }
      const fs = [k]
      for f in fs { f(x) }
    }
    g(3)
    g("s")
    // vl check: rc 0.  vl run: emitProgram: a function value's signature is not known at this call — the type it was given takes fewer parameters than the call passes

#### Mechanism

The value-flow question already reached the loop variable's call (`vrForVar`). The call's
signature key (`cloCallSigKey`'s `Ident` branch) read the loop variable's recorded type, which
names the frame's type parameter and is shared by both instances, so the first instance's key
stood for both. It now substitutes the instance's binding, as [D7201](D7201.md)'s field read does.
