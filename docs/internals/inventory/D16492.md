### D16492 — a radix literal beside an operand spelled with an `i64` decimal folds as a 32-bit pattern

**closed 2026-11-15 · runs, prints `3000000000` then `3270148182` · was check-clean silently wrong, clause 1 · the fold (`cexEvalBin`, check_num_lit_state.vl) leaves a pattern beside a tree holding a decimal outside `i32` to the typed check, which reads the pattern zero-extended in that `i64` context · fixture `tests/cases/numerics/radix-beside-i64-decimal-tree.vl` · found by the independent oracle (fuzz-nightly cells `ar_s30_0123`, `ar_s44_0020`) · filed 2026-11-15 against master `7bf2afc7a`**

Repro:

    print(0xFFFFFFFF & 3000000000)
    print(0xFFFFFFFF & (9223372036854775807 / (-9000000003)))
    // master: vl check rc 0, prints -1294967296 then -1024819114

Want:

    3000000000
    3270148182

#### Mechanism

T2.3: in an `i64` context a radix literal is its zero-extended value, and an operand spelled with
an `i64` decimal is that context. The constant fold computes a pattern's operation exactly and
then reads the result as a 32-bit pattern. `cexPatRingOk` stops `+ - *` folding when the other
operand's value is outside `i32`, but `cexBitwise` had no such guard (`0xFFFFFFFF & 3000000000`
wrapped `3000000000`), and neither looked at the operand's spelling, so an `i64` tree whose value
fits `i32` folded at 32 bits under any operator. One value-blind check now covers both: a pattern
beside a tree that spells an `i64` decimal is no constant, so the typed check computes it.
