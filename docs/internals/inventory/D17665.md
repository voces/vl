### D17665 — a one-element list literal of a record holding two different un-annotated functions lays the field out as a closure where the element writes the set's id

**check-clean invalid wasm · filed 2026-11-26 against master `8697cb4e9` by lane COV-START**

Repro:

    function inc0(a) { return a + 1 }
    function dbl(a) { return a * 2 }
    const xs = [{ r: inc0, s: dbl }]
    print(xs[0].r(6))
    // vl check: rc 0.  vl run: invalid module, type mismatch: expected (ref $2), found i32; $2 is struct {structref, i32, i32}

#### Mechanism

Legacy writes the element's `r` field as a tagged set's i32 id. The list's ref-list row lays that
field out as a closure struct (`$2`), so `struct.new` meets an i32 where the row's field wants a
`(ref $2)`. Each field holds a single function whose set no other value widens. With two elements
that cross the functions, each field's set has two members, the row stores ids, and the program
runs. Which side picks the wrong storage (the element's field code or the list row's) is not yet
localised.

#### Grading list

- The nested spelling: `const xs = [{ r: { f: inc0 }, s: { f: dbl } }]` and `print(xs[0].r.f(6))`.
- A maker's results in the list. This is how it was found, beside D17131's `mk`:
  `const xs = [mk(0), mk(1)]` then `print(xs[0].r.f(6))`.
- Reading the other field, `print(xs[0].s(6))`.
- The IR declines the nested maker spelling (`array element coercion`), so an IR close must build
  the list at the storage the element is written at, and `$VL_IR_REQUIRE_CLAIM=1` must exit 0.
