### D2931 — a hole value returned through a generic call's lambda argument prints a `boolean` pin as `1`

**closed 2026-09-28 — the witness prints `true` · was check-clean silently wrong · `monoCloneLambdaSubst` pins a hole instance's lambda through the instance's hole binding, and the template every instance cloned is pruned (`monoLamSlotIsHoleTemplate`) · grid rows graded against master `d408f2da4`, 0 runs lost · fixture `tests/cases/generics/hole-binding-reaches-lambdas-and-reads.vl` · first filed as: check-clean silently wrong · clause 1 · the `argGen` cells of the #3237 review grid at `boolean` and `boolean | null` · the same on master `e91e04a8f` · filed 2026-09-28 against master `e91e04a8f`**

Repro:

    function appG<T>(g: () => T): T {
      return g()
    }
    function F(x) {
      print(appG(() => x))
    }
    F(true)
    // vl check: rc 0.  vl run: prints `1`

Want:

    true

#### Mechanism

Not localised. `appG` is pinned from the lambda's function-value signature key, which spells a
`boolean` result as `i32`, so its instance returns `i32`. [D2919](D2919.md) is the same symptom
where the argument is a shared node, closed by the hole instance's own binding; a lambda argument
takes the closure route in `monoArgTyName` before that question is asked of anything it returns.
