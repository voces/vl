### D3084 — a hole for-in loop variable captured by a closure is invalid wasm at an `i32 | string` pin

**closed 2026-09-28 — the witness prints `s` · was check-clean invalid wasm · `monoPinnedTyOf` reads a hole instance's list literal, element read and function-value call at the instance's hole binding, which the parameter binding `monoPinBodyLambdas` walks with does not name · grid rows graded against master `d408f2da4`, 0 runs lost · fixture `tests/cases/closures/hole-loop-variable-and-literal-captured.vl` · first filed as: check-clean invalid wasm · clause 1 · found by the #3269 review · the same on master `67ca68cf3` · filed 2026-09-28 against master `67ca68cf3`**

Repro:

    function f(x) {
      const l = [x]
      for e in l {
        const k = () => e
        print(k())
      }
    }
    const v: i32 | string = "s"
    f(v)
    // vl check: rc 0.  vl run: invalid module inside `f`, expected i32, found (ref $type)

Want:

    s

#### Mechanism

A hole instance shares its template's expression nodes, so a list literal of the parameter, an element read and a call of a function value keep the recorded type over the hole's variable. `monoPinBodyLambdas` re-types such nodes through the instance's binding, but a hole function's binding names its type parameters, of which it has none; the hole's own binding (`monoHoleBinding`) was read only for a binding's initializer and a for-in iterable. `monoPinnedTyOf` now substitutes through the hole binding too, for those three node kinds, so the literal builds at the pin wherever it stands. A record-element list is left to the rows its literal collects, and a method call's result to its receiver.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `print(e)`, no closure | prints `s` | **yes** (the capture) |
| `const k = () => x` | runs | **yes** (the loop variable) |
| `function f<T>(x: T)` | runs | **yes** (the hole) |
| `monoPinnedTyOf` without the hole binding | invalid wasm | **yes** (the fix) |
