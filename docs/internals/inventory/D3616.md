### D3616 — a lambda joining two parameter holes with no `null` collapses the join at its call, so the caller reads the second arm as the first

**check-clean silently wrong · open · clause 1 · the same on master `0c087fb3c` · found by lane LR re-landing [D3520](D3520.md) · filed 2026-10-04 against master `0c087fb3c` · re-witnessed unchanged against master `32b753681` (lane NJ)**

Repro:

    type K = "a" | "b"
    const xn: K | null = "a"
    function F(k: i32, a, b) {
      const g = () => { if k == 0 { a } else { b } }
      print(g())
    }
    F(1, xn, 3)
    // PRINTS b

Want:

    3

#### Mechanism

[D3520](D3520.md)'s collapse, left at the hole spelling. A lambda's join of two parameter holes
with no `null` stays a deferred join, so the call types it as its first hole and the caller
reads `3` as the `K | null` atom `1` (`b`). Keeping it apart (`deferredJoinOverOpenParams`
admitting holes without a `null`) closes this witness but a hole instance does not substitute
types, it reads a hole's pin (`holeOperandTyOf`), and several readers of a union of holes have
no such read: the #3344 review's `g-my` grid lost 39 right cells (a lambda in a list at an
alike pin, `fs[0]()`; arithmetic or `print` over the join at an `i32`/`f64` pin, refused as
"an operator over a numeric union has no recorded result type at this instance"; an `if`
around the call) while 107 hole cells moved to right. So holes keep apart in a lambda only
when the join carries a `null`.
