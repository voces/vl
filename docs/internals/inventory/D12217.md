### D12217 — a lambda written into a list element or record field holding a generic, then called at a type the lambda refuses, passes the checker

**loud emit reject · `vl check` rc 0 · `emitProgram: a lambda written into an element or field holding a generic function cannot take the type the calls through it give it — annotate its parameters` · clause 2 · DESIGN: the same write to a `let` is refused at check (`a function written to this binding takes `string` there`) · found surveying emit refusals for L3 family (d) · filed 2026-10-24 against master `b8e223f93`**

Repro:

    function pick<A, B>(a: A, b: B): A { a }
    const fs = [pick]
    fs[0] = (x, y: string) => x
    print(fs[0](1, 2))

#### Mechanism

The call passes `2` where the written lambda takes `string`, so the program is ill-typed.
`fsbArgsFit` (check_node_rules.vl) judges each call through a `let` against the functions
written to it, but its tables are keyed on identifier bindings, so a write to `fs[0]` or
`r.f` is never judged. `monoPinWrittenLam` (emit_mono.vl) is the only place that sees the
disagreement. The close is the checker's: carry the written-function judge to element and
field paths, then demote the emit arm.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the list (`let f = pick; f = (x, y: string) => x; f(1, 2)`) | check reject | **yes** |
| the disagreeing call (`fs[0](1, "s")`) | runs | **yes** |
| the list (`const r = { f: pick }; r.f = …`) | still refuses at emit | no |

#### Grading list

The record-field spelling, and the annotated list `const fs: ((a: i32, b: i32) => i32)[]`,
which the checker already refuses at the write.
