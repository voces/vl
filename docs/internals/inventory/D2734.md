### D2734 — `T` inferred from a nullable map argument against `T | string` answers `is` for the wrong map, or emits an invalid module

**closed 2026-09-26 — the filed repro RUNS and prints `false` · was check-clean silently wrong (`true`) · clause 1 · found by #3202's review (the `b/` grid's `inferred` cells) · closed by binding a union annotation's type-parameter member to the argument's members no concrete member names, in both the pin's spelling (`monoBindUnionRest`) and its exact key (`exactBindWalk`) · filed 2026-09-26 against master `74bd044d7` · fixture `tests/cases/generics/pin-inferred-from-union-argument.vl`**

Repro:

    function f<T>(u: T | string): boolean { u is Set<i32> }
    const x: {[i32]: boolean} | null = Map()
    print(f(x))
    // PRINTS false

#### Mechanism

With no type argument, `T` is inferred from a `{[i32]: boolean} | null` argument against the
union `T | string`. The monomorphizer's binding walk (`bindGenWalk`) has no arm for a union
expected type, so the instance has no exact binding for `T` and falls back to the rep key,
where a Set and its boolean map share one tag. The explicit spelling
`f<{[i32]: boolean} | null>(x)` is keyed exactly and prints `false` (master printed `true`
for it too). The same family's `string | T` spelling (the grid's `__2__` cells, 14 of them)
emits a module that fails validation.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the inference (`f<{[i32]: boolean} \| null>(x)`) | runs, prints `false` | **yes** |
| the `null` on the argument's type | refuses (D2717) | **yes** |

Review round 1 (#3208) corrected the order: the union rule binds `T` only after every other
parameter has, since the checker's walk passes a union over (`f<T>(u: T | string, v: T)` at
`f(x, true)` binds `T := boolean` from `v`). A union parameter whose spelling then cannot hold
its argument is pinned at the argument's own type. The review's two-parameter grid (`gC`, 168
cells) has no wrong value and no invalid module left.

Review round 2 (#3208): a union parameter over `T` is minted at the type the call binds `T` to
from its bare `T` parameters, as an explicit type argument mints it, so `f(x, y)` at
`f<T>(u: T | string, v: T)` with `y: R` runs as `f<R>(x, y)` does (D2792), and a list of
references counts as a reference arm at the pin (`f<R[]>("q")` at `T | string`, invalid on master).
