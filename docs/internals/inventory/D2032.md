### D2032 — `vl fmt` cannot wrap a `new { … }` record body that overflows the line, and refuses the file as "invalid output"

**runs today and must keep running · the program is `vl check`-clean and runs; `vl fmt` exits 3 on it · found writing the getters v1 fixtures (#3031) · filed 2026-09-22 against master `ad8712231`**

Repro (runs, prints `1`):

    type W = new { aaaaaaaaaaaa: i32, bbbbbbbbbbbbbbb: i32, cccccccccccccc: i32, dddddddddddddddd: i32, e: i32 }
    const w: W = { aaaaaaaaaaaa: 1, bbbbbbbbbbbbbbb: 2, cccccccccccccc: 3, dddddddddddddddd: 4, e: 5 }
    print(w.aaaaaaaaaaaa)
    // vl fmt: formatter produced invalid output — file left unchanged, please report (exit 3)

#### Mechanism

Not yet traced. The same body without `new` (`type W = { … }`) wraps to one field per line and
round-trips, and a `new` body that fits on the line is left alone, so the `new` keyword on the
over-long path is the ingredient: the wrapped rendering the formatter builds for it fails its
own re-parse check.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the `new` keyword | wraps and round-trips | **yes** |
| the line overflow (fewer fields) | left as written | **yes** |
| a map-typed field | still refuses | no |

#### Grading list

The same over-long body with a nested record field and with a generic parameter
(`type B<T> = new { … }`); a `flat type` body that overflows.
