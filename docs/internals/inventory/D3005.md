### D3005 — an `f32` field re-seated at a wider declared `f64` record is read back at its own `f32` type unconverted

**closed · was check-clean invalid wasm on master `b34730ad9` and on #3253 · `memReadNarrowOp` narrows to the checked `f32` too (`f32.demote_f64`), and `exprIsF64` / `exprIsF32` classify the read to match · fixture `tests/cases/objects/record-literal-widened-read-any-handle.vl` · found by the #3253 review grid · filed 2026-09-28**

Repro:

    type D = { v: f64 }
    const x: f32 = 1.5
    const c: {[string]: D} = Map()
    const o = { v: x }
    c["k"] = o
    const z: f32 = o.v
    print(z)
    // vl check: rc 0.  vl run: invalid module — type mismatch

Want:

    1.5

#### Mechanism

The narrowing table only held `i32` targets. It is now one kind table (`atomNarrowOp`: `i32` from `i64`, `f64` or `f32`; `f32` from `f64`), shared with the union-box retag below, and exact because nothing writes the widened slot a wider value (D2060).

As filed: The map store builds `o` at `D`, so `o.v` loads an `f64` where the checker's `f32` is expected. #3253's `memReadNarrowOp` narrows only to `i32` (`i32.wrap_i64`, `i32.trunc_f64_s`); an `f32` read needs `f32.demote_f64`, which is exact for a value that came from an `f32`.
