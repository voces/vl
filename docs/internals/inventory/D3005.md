### D3005 — an `f32` field re-seated at a wider declared `f64` record is read back at its own `f32` type unconverted

**closed by design · now a loud check reject · was check-clean invalid wasm on master `b34730ad9` and on #3253 · since the D3339 ruling `o` adopts `D`, so `const z: f32 = o.v` is an `f64` into `f32`, refused as its annotated twin's is · fixture `tests/cases/objects/record-literal-widened-read-any-handle.vl` (reads `f.v` without the `f32` annotation) · found by the #3253 review grid · filed 2026-09-28**

Repro:

    type D = { v: f64 }
    const x: f32 = 1.5
    const c: {[string]: D} = Map()
    const o = { v: x }
    c["k"] = o
    const z: f32 = o.v
    print(z)
    // vl check: rc 0.  vl run: invalid module — type mismatch

#### Mechanism

The narrowing table only held `i32` targets. It is now one kind table (`atomNarrowOp`: `i32` from `i64`, `f64` or `f32`; `f32` from `f64`), shared with the union-box retag below, and exact because nothing writes the widened slot a wider value (D2060).

As filed: The map store builds `o` at `D`, so `o.v` loads an `f64` where the checker's `f32` is expected. #3253's `memReadNarrowOp` narrows only to `i32` (`i32.wrap_i64`, `i32.trunc_f64_s`); an `f32` read needs `f32.demote_f64`, which is exact for a value that came from an `f32`.

#### Under the D3339 ruling (2026-09-30)

The owner ruled (D3339 (A)) that a literal-holding binding delivered to a record storing a number at another width or kind takes that record as its type at every read, as its annotated twin does. `o.v` is therefore an `f64`, and binding it at `f32` is the lossy conversion the annotated twin `const o: D = { v: x }` is refused for; `const z = o.v` runs and prints `1.5`.
