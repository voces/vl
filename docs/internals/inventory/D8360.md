### D8360 — a `.pop()` statement on an empty numeric list reads past the end, because the statement form skipped the length test the value form makes

**closed 2026-10-20 · runs, prints `0` · was trap after load (`out of bounds array access` at the pop) · `vl check` rc 0 · clause 1 · the statement pop of an `i32[]`/`i64[]`/`f64[]`/`f32[]`/`u8[]` list now pops under the `len != 0` test and drops the element itself (`emitPopGo`, compiler/wasmEmit.vl); the value form is unchanged · pin: `tests/cases/lists/pop-statement-empty-list.vl` · filed 2026-10-20 against master `b56512057`**

Repro:

    let a: i32[] = []
    function f() {
      a.pop()
      0
    }
    f()
    print(a.length)

Want:

    0

#### Mechanism

`emitCallStmt` lowers a `.pop()` statement through `emitPop` with `nulBox` false, so a
numeric element skips the value form's `T | null` box (`emitPopNulBox`), which is where the
`len != 0` test lives. It fell to the unchecked tail, which decrements the length to -1 and
reads `backing[-1]`. Boolean, atom, string and record lists were unaffected: their arms are
checked in both forms. The statement now takes `pushTakeCond` around `pushTakeElem` and drops
the element inside the `if`.
