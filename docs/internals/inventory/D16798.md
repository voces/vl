**closed 2026-11-16 · runs, prints `0.625` · was check-clean invalid wasm, `vl check` rc 0, `type mismatch: expected i32, found f64` (the division lowered as `i32.div_s` over an `f64.const`) · clause 1 · the checker typed a call through a binding of an un-annotated maker's call as a bare hole `_`, so float arithmetic on it lowered as `i32` and a `string` destination accepted it (`const y: string = v(3)`: rc 0, then an invalid module); fixed in check_calls.vl: `makerCallLamRet` reads the lambda's body at the call's arguments under the binding the maker call pinned (`?adder.0 = i32`), so `v(3)` is `i32`, float arithmetic widens, and the `string` destination is refused (`cannot assign i32 to 'y' of type string`, as with `n: i32`) · pins: `tests/cases/functions/maker-hole-param-call-result-typed-at-pins.vl`, `tests/cases/functions/error-maker-hole-param-call-result-at-string.vl` · the un-annotated face of `maker-hole-param-at-two-results.matrix.vl`'s `two_instances` position · filed 2026-11-16 against master `76c7015b4`**

Repro:

    function adder(n) { return (a) => a + n }
    const v = adder(2)
    print(v(3) / 8.0)
    // vl check: rc 0.  vl run: invalid module, expected i32, found f64

Want:

    0.625

#### Mechanism

Partly traced. A maker row for an un-annotated binding comes from the signature the binding is
called at (`fvaCallSig`), and `v(3)`'s result is still open when the rows are banked, so no row
names the `f64` result. With `n` annotated or absent, the lambda's result is decided from its
calls (D16711) on the maker's own instance; with a hole parameter the call's instance is the
hole-pinned one, which that path does not reach, so it keeps the body's `i32`.
