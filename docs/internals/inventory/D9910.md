### D9910 — a `<T>` body returning `x ?? 1.5` at a never-null `i32` pin returns an `i32` where its caller reads the `f64` the call is typed at

**closed · runs, prints `2` · was check-clean invalid wasm, clause 1 · `vl check` rc 0 · the `f64` pin prints `2.5` · found closing [D9870](D9870.md) · present on master `8700f0727` · filed 2026-10-22 against master `8700f0727` · closed with [D9914](D9914.md), by typing a `??` over a parameter at a never-null number pin as the pin, whatever the default's width (`coalDeadAtPin`, check_hole_pins.vl), and by no longer re-joining a `??`'s operands as a number pair in a hole call's re-check (`holeArithNodeTy`, check_relate_core.vl) · fixture `generics/hole-coalesce-join-operand-tp-list-literal.vl`**

Repro:

    function f<T>(x: T) { return x ?? 1.5 }
    const z: i32 = 5
    print(f(z) / 2)
    // vl run: the emitted module failed to validate inside the module's top-level code: type mismatch: expected f64, found i32

Want:

    2

#### Mechanism

At a never-null `i32` pin the default is dead, so `f(z)` is `5`, an `i32`, and `/ 2` is integer
division. The concrete `x ?? 1.5` over `x: i32` is typed `i32`. The call's re-check instead joined
the pin with the default's `f64` as a number pair (`holeArithNodeTy` applied `numPairTy` to `??`),
so the caller read an `f64` the instance never returned. The filed Want, `2.5`, was the join's
answer and wrong: the un-annotated face printed `2.5` on #4413's head, a wrong value ([D9914](D9914.md)).
