### D1768 — a CAPTURED literal-union list element spelled INLINE leaks the interned atom id, and the same capture inside any block is check-clean invalid wasm instead

**check-clean silently wrong · `vl check` rc 0, `vl run` prints `0` where `green` is expected · clause 1 · filed 2026-09-06 against master `0a6a31c0b` · found by `inline-litunion-from-list-element.matrix.vl`'s four capture cells, silent at both seeds of #2775 · [D1541](D1541.md)'s class at the capture · 0 corpus cells**

Repro:

    const srcArr: ("red" | "green")[] = ["green", "red"]
    const v: "red" | "green" = srcArr[0]
    const g = () => v
    print(g())
    // PRINTS 0
    // want: green

Spell the union as an alias — `type Color = "red" | "green"`, `srcArr: Color[]`,
`const v: Color = …` — and the same four lines print `green`. So does deleting the capture
(`print(v)`), and so does a CALL source instead of the list element.

#### Mechanism

Predicted from the ablation, not probed. [D1541](D1541.md) records the seam: a litunion ARRAY
is always the interned-i32 ATOM list, while a scalar litunion destination's rep follows the
SPELLING — an alias is the atom, an inline member set is the string ref — so the two ends
disagree exactly when the spelling is inline. Its close reached the direct read; the CAPTURE is
a third end, and the env field is typed by a classifier that reads the same spelling.

**One shape, two outcome classes, decided by where the capture sits.** At plain module scope
and at every un-annotated spelling the env field takes the atom and the read prints the id — a
wrong value. Inside a block or a function body with the annotation present the env field takes
the string ref over an atom slot and the module fails to validate. The wrong value is the
worse half and is what this row's status names.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the INLINE spelling (an alias `type Color` at both ends) | runs `green` | **yes** |
| the capture (`print(v)` directly) | runs `green` | **yes** |
| the LIST ELEMENT source (a call returning the union) | runs `green` | **yes** |
| the literal union (a struct element and a struct annotation) | runs `3` | **yes** |
| the annotation, at plain module scope | prints `0` | no — same class |
| the annotation, inside a module block or a function body | prints `0` | no — same class |
| the plain module scope, with the annotation (an `if true` block) | **check-clean invalid wasm** | no — the other class |
| the same, in a bare block, a module `while`, a function body, or a function's `if` block | **check-clean invalid wasm** | no |
| the first element swapped for the second (`srcArr[1]`) | **check-clean invalid wasm** | no |

Needed: the inline spelling AND the capture AND the list-element source. Not needed: the
annotation or the scope — those pick which of the two classes you get, not whether it fires.

#### The two sites, probed

Three name-gated `emitFail` probes, each read against the ALIAS control that runs. A probe
that is not name-gated reports only the FIRST failure in the program, which is `srcArr`, and
that artefact hid the `v` row on the first two readings.

**The CELL — `captureValKind`'s annotated arm.** Fires for the block and function-body faces
and stays silent for the module-scope ones, so a captured GLOBAL does not reach it:

| face | `annK` | `initK` | `initIsLitAtom` | `letIsLitUnion` |
| --- | --- | --- | --- | --- |
| inline, module block | **`str`** | **`i32`** | **T** | F |
| alias, module block | `i32` | `i32` | T | **T** |
| inline, CALL source | `str` | `str` | **F** | F |
| struct element | `struct` | `struct` | F | F |

The annotation renders `str` for the inline spelling ([D1541](D1541.md)'s soften) while the
init cell is the atom the litunion array hands over. `letInitIsLitAtom` separates the two
litunion faces from both controls, and it answers at `frameOk=F`, so it is frame-blind.

**The GLOBAL's cell is NOT the module-scope site.** `globalCellKindGo` was probed on the same
table and the emitted module settles it: both spellings declare `v` as `(mut i32)`, the atom.
The direct read (`print(v)`) and the direct compare both print correctly at module scope; only
the CAPTURED read is wrong, so the capture is the ingredient at every scope.

**The READER — `exprIsLitAtom`'s Call arm, and its exclusion is deliberate.** The read is
`print(g())`, a CALL, so the Ident arm never applies. The arm that answers is:

    if nodeTyIsLitUnionAlias(unwrapParen(exprIx)) { return true }

with its own comment saying *"a named call to an inline-litunion-returning function reps as a
string ref, correctly excluded"*. True while the env field IS a string ref — and false the
moment the cell rung makes it the atom.

#### The cell rung alone is a class REGRESSION, measured and reverted

The rung below — `captureValKind`'s annotated arm, after D1632's niche test:

    // An initialiser committing a literal-union ATOM decides the env field, whatever the
    // annotation renders (D1768).
    if letInitIsLitAtom(b, parentBindingFrameArenaOf(fe, name)) { return "i32" }

moves the six invalid-wasm cells to a WRONG VALUE, because the reader still renders the id:

| cell | before | with the cell rung alone |
| --- | --- | --- |
| ann capture, `if` / bare / `while` block | SILENT | **WRONG (`0`)** |
| ann capture, fn body / fn + `if` block | SILENT | **WRONG (`0`)** |
| ann capture, second element | SILENT | **WRONG (`0`)** |
| ann capture, plain module | WRONG | WRONG |
| UN-ann capture, block / fn body | WRONG | WRONG |
| no-capture · CALL source · alias · struct control | runs | runs |

`runs -> not-runs` 0 and no new SILENT, but **WRONG 3 -> 9**: the block face reads
`expected i32, found (ref $type)` before and prints `0` after. Six silent cells for six wrong
values is the trade the standing rule forbids, so it was reverted rather than shipped.

**CELL AND READER HAVE TO LAND TOGETHER**, and that is this row's main finding. The remaining
work is the reader half: the Call arm must claim when the callee is a CLOSURE whose result rep
is the atom, without claiming a NAMED call to an inline-litunion-returning function, which
genuinely reps as a string ref. `cloCallResultLitUnion` is the neighbouring rung that already
asks the callee's own substituted annotation, and is the place to start.
