### D4993 — a `.map` callback over an `is K[]` arm's empty receiver of another element type is typed at the receiver's element

**closed 2026-10-15 — now prints `10` · was check-clean invalid wasm, clause 1 · the callback face of [D4911](D4911.md) and [D4962](D4962.md) · the record pair (`is Q[]` over an empty `P[]`, `a.map((e) => e.y)`) and the reverse (`is P[]` over an empty `f64[]`) now run too · pins: `tests/cases/generics/is-list-arm-map-callback.vl` · filed 2026-10-15 against master `358350b10`**

Repro:

    type P = { x: i32 }
    function h<V>(a: V[]) {
      if a is f64[] {
        const ys = a.map((e) => e + 1.5)
        print(ys.length + 10)
      }
    }
    const pe: P[] = []
    h(pe)
    // vl run: the emitted module failed to validate inside `__lambda_1`: type mismatch:
    // expected f64, found (ref $type)

Want:

    10

#### Mechanism

Not ablated. The arm reads `a` as an empty `f64[]` (D4911), but the lifted callback's
parameter `e` is typed from the instance's own element, `P`, while its body is checked at
`f64`, so the lambda adds `1.5` to a struct ref. The list never iterates, so any callback the
arm hands it is dead code that still has to validate.

#### Close

One type-taking answer serves all three rows: `listFitArmTyOf` (emit_classify.vl) names the
`K[]` a read of the receiver takes inside an `is K[]` arm whose elements can never be `K`,
from the checked types alone, so collect and emit agree. `exprListRepOf` and
`refListElemNameOfExpr` ask it first, which types the `.map`/`.filter` receiver, its scratch
frame and a `for` variable at `K`. `monoPinMapLambdas` pins the callback at the arm element
when the instance pinned a disjoint one (`monoFitArmElem`). `tyLeavesDisjoint` (typecheck.vl,
factored out of `listDisjointDepth`) now also answers a record against a primitive or a list,
which the reverse face (`is P[]` over an empty `f64[]`) needs; a nonempty `f64[]` stays false.
