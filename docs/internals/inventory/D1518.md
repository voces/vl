### D1518 — a struct that is BOTH a union arm and the nested-struct FIELD of another union's arm has no struct-table row, and which sentence you get depends on declaration order

**closed 2026-09-03 — the repro now RUNS in both declaration orders. Was: loud emit reject, positionless · reported by the glean session, VL-024, `~/glean/docs/vl-issues.md`**

Repro:

    type E = { msg: string }
    type B = { base: i32, length: i32 }
    type M = { a: B, n: i32 }
    function f(ok: boolean): M | E {
      if !ok { return { msg: "f" } }
      return { a: { base: 1, length: 16 }, n: 2 }
    }
    function g(ok: boolean): B | E {
      if !ok { return { msg: "g" } }
      return { base: 2, length: 8 }
    }
    const m = f(true)
    if m is M { print(m.a.base) }
    const b = g(true)
    if b is B { print(b.base) }
    // vl check: rc 0.  Was: emit error, no line:col.  Now prints 1 then 2.

#### Mechanism

`collectS` SKIPS a `type X = {…}` that is a union member — an arm's fields ride the variant
table — so an arm has no `sNames` row. D761 built the mint that gives it one
(`internArmFieldShape` → `variantStructHeapTwinAt`), but ran it only from a declaration that
OWNS a struct row. Here the declaration carrying the field is ITSELF an arm, so the mint never
ran and `B` had no row under either role. Two orders, two sentences, one missing intern:
`M | E` first coded the field 15 through `nameIsStructDecl` (`B` was not yet a variant) against
a target row that never existed — `nested-struct field element type is not interned`, from the
TYPE SECTION; `B | E` first made `nameIsStructDecl` decline, so the field had no code at all —
`only i32 / … / array union-variant fields are supported`, from `collectU`.

Measured at the refusing site in each order (instrumented seed, `sNames.length = 0` in both —
every one of `E`, `B`, `M` is an arm, so the struct table is EMPTY):

| order | site | `variantIndexOf(B)` | `structIndexByName(B)` | `structIndexOfTy(B)` | `armFieldStructRow(B)` |
| --- | --- | --- | --- | --- | --- |
| `f` first | type section, `uFieldTgtStructIdx` | 2 | −1 | −1 (elemTyIx 41) | −1 |
| `g` first | `collectU`, `collectVariantFields` | 0 | −1 | — (`declTyIxOfName` = 41) | −1 |

The fix is order-independent by construction. The arm-field mint now runs over EVERY
`TypeDecl`'s fields (a declaration that is itself an arm has exactly the same field TARGETS),
and the field CODE is decided one phase earlier by a pure predicate — `armFieldDeferredRowOk`,
the mirror of the mint, rendered through the same `armMintShapeName` so the two cannot
disagree. `uFieldTgtStructIdx` gained the arm-twin rung the variant table needs because its
name column banks the ARM's own name (recorded before the mint).

**This is the cross-product shape: two individually sound features failing only together.**
`B` as an arm ALONE works; `B` as a nested field ALONE works; D1473's reverse map works. Only
the pair fails, and no single-feature grid can see it.

#### What the second sentence is true of now

`only i32 / boolean / string / array union-variant fields are supported` is RETIRED — it was
false of every composite it named and both of its sites now print D734's
`fieldTypeRefusalMsg`, which names the arm. Graded one variant-arm field type per row, before
and after (15 + 12 cells):

| field type | before | after |
| --- | --- | --- |
| i32, boolean, string, i32[], f64, i64, f32, map, nested-struct, inline shape, struct-list, nullable-struct, union-box, closure | runs | runs |
| **arm-struct** (this row) | refuses | **runs** |
| arm with 2 fields, arm with f64 / map / closure field, `arm \| null`, `arm[]` field | refuses | **runs** |
| arm whose OWN field is a nested struct (no cross-table heap twin) | refuses | refuses (D734's sentence) |
| self-recursive arm (`type A = {f: A \| null}` as an arm) | refuses | refuses (D734's sentence) |

So the allow-list sentence was true of exactly ONE of the fifteen types it excluded, and that
one is this row.
