### D17166 — the IR misses a list field of hole functions read off a call's list result when the function also sits in a list of records beside another

**closed 2026-11-24 by lane IR-P1 · runs, prints `41`, the IR claiming it · was an IR coverage defect: `buildMember` (`ir_build_ref.vl`) now reads a plain struct field whose kid rep is not the read's own into a temp at the operand's stored-row kid, the row legacy reads · filed 2026-11-24 against master `aef0be317` by lane IR-N2 (census class `start: field read coercion`, family S, 1 cell)**

Repro:

    function inc0(a) { return a + 1 }
    function dbl(a) { return a * 2 }
    function mk() { return [{ fs: [inc0] }] }
    function nest() { return [{ f: inc0 }, { f: dbl }] }
    print(mk()[0].fs[0](40))
    // VL_IR_SHADOW=1 vl build: `start uncovered field read coercion` (kid rep list → list)

Want:

    41

#### Mechanism

`buildMember` (`ir_build_ref.vl`) declines a plain struct field read when the field's kid rep is
not the read's rep: here two different list reps (measured with a probe build naming both). Legacy
reads the operand's stored row, so the fix reads at that row's kid; at the receiver type's kid
the read fails verifier rule 2 (self-test `field-read-at-receiver-type-kid`).
