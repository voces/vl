### D13281 — two nested hole functions with one name in two functions share their operator re-ask, and the second call's type is refused

**loud check reject · clause 2 · CAPABILITY: renaming either function, or annotating either parameter, runs · open · `operator '+' is not defined for string and i32 (the body of `inner` applies '+' to this argument)` · pre-existing on master `247fb2679` · found writing [D13082](D13082.md)'s fixture · filed 2026-10-25 against master `247fb2679`**

Repro:

    function num() {
      function inner(s) { return s + 1 }
      print(inner(10))
    }
    num()
    function g() {
      function inner(s) { return s + "!" }
      print(inner("a"))
    }
    g()
    // vl check: argument 1: operator '+' is not defined for string and i32 (the body of `inner` applies '+' to this argument)

Want:

    11
    a!

#### Mechanism

Located from the code path, not yet fixed. A named function's parameter hole is keyed on the
function's NAME and the parameter's position, `?inner.0` (`paramHoleName`, check_tp_join.vl), so
the hoisted signature and the body bind the same hole. Two nested functions with one name and
one parameter position therefore share a hole, and the operator demand one body records on it
(`binCstr`, check_demands.vl) is re-asked at the other's call. The flow table mints the same
name independently (`fn_flow_shadow.vl`), so a fix keys a nested declaration on its node in
both producers and every reader that compares against the name. Bodies that apply no operator
to the hole, and calls through a `const` alias, are not affected.
