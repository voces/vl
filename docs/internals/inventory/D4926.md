### D4926 — a list's element narrowing `v is K[]` outlives a write to an element

**closed · now a loud check reject · was check-clean silently wrong (clause 1) · related to D4771 (`is` over a list tests every element) and D2390 (a) (a call that may write ends a narrowing) · filed 2026-10-15 against master `23dcd80be`**

Repro:

    type K = 0 | 1
    const v: i32[] = [0, 1]
    const f = () => { v[0] = 5 }
    if (v is K[]) {
      f()
      const e: K = v[0]
      print(e)
    }
    // vl check: rc 0.  vl run: prints 5, a value outside K

#### Mechanism

`v is K[]` banks a narrowing of the name `v` to `K[]`, but the write-retirement machinery only
knew the keys it narrows as names and `.field` paths. An element store (`v[i] = x`), a `push`,
or either one through an alias or a closure produced no write shape that hit the key `v`, so
the narrowed element type survived the write. The close adds a list-every key `v[*]` beside
the narrowing whenever the narrowed element differs from the declared one, gives `push` an
append write shape, and lets every element store hit that key unless the stored list's
element already fits the narrowing. A direct store or push through `v` itself is checked
against the narrowed element and keeps it.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `f()` removed | prints 0, right | **yes** (a write between guard and read) |
| `const alias = v` and `alias[0] = 5` for the call | printed 5 | no (any alias write) |
| closure body `v.push(7)`, read `v[2]` | printed 7 | no (any append) |
| read as `for x in v { f(); const e: K = x }` | printed 0 then 5 | no (the loop variable too) |
| `v` declared `K[] \| i32[]`, holding an `i32[]` the closure writes | printed 5 | no (a list union too) |
| closure writes a `string[]` instead | prints 0, right | **yes** (a store that may reach `v`) |
