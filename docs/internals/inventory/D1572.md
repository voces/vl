### D1572 — `match` had no arm vocabulary for an integer scrutinee, so a tag dispatch had to be an if-chain or a table filled at module init

**closed (built) — an INTEGER scrutinee (`i32`/`i64`, and a HOLE whose arms are integer literals) is a third arm vocabulary: integer LITERALS plus a MANDATORY `_`, with duplicates and an arm after the `_` refused · was a loud check reject at check tier, `match scrutinee must be a union, got i32` and `got _` (clause 2) · TWO position matrices, annotated and un-annotated scrutinee, 0 -> 54 of 54 each, both faces · ZERO corpus cells · asked by the glean session as VL-020, `~/glean/docs/vl-issues.md`, probe `~/glean/vl-probes/VL-020-int-match.vl` (which annotates nothing and now runs verbatim) · design ruling DECISIONS.md §"`match` over an integer scrutinee" · filed 2026-09-03 against master `d4568ff1`**

Repro (runs, prints `14`, `22`, `99`, `-1`, `two`):

    function len(id: i32): i32 {
      match id {
        0x10 => 14
        0x11 => 22
        -1 => 99
        _ => -1
      }
    }
    print(len(0x10))
    print(len(0x11))
    print(len(-1))
    print(len(7))
    const v = match len(7) { -1 => "two", _ => "?" }
    print(v)

#### Mechanism

**THE REFUSAL WAS ONE `if`, AND EVERYTHING BEHIND IT ALREADY EXISTED.** `checkMatchExprNode`
asked `tyIsLitUnion(st)` and then `uMems.length > 1`, so an `i32` fell to
`matchScrutRejectMsg` — a scrutinee tier the arm checkers never saw. The lowering it would
have needed was already written twice over: `desugarMatchAt`'s `matchArmCond` has a
non-`IsExpr` arm that builds `scrut == pat`, which is how a literal-union's `StrLit` pattern
becomes a compare, and the chain it splices is the if/else the emitter has always lowered.

Two pieces were genuinely missing. The PARSER minted a NUMBER in pattern position as a numeric
literal TYPE (`mkIsExpr(scrut, "0")`), which is a member-type test rather than a value compare;
it now mints the `NumLit` — and a `Unary "-"` over one for the negative spelling, which had no
pattern form at all (`matchPatStartsType` never admitted `MINUS`). Nothing regressed by that
move, because a numeric literal UNION is still refused at the scrutinee, so its arms were never
validated as types. And the CHECKER needed the third arm vocabulary: `checkMatchIntArms`, which
type-checks each pattern as the expression it is (so an `i32` literal reaches an `i64` scrutinee
by the widening lattice and never the reverse), claims its 64-bit VALUE through `parseI64Pair`
so `0x10` and `16` are one arm and `-1` is not `1`, and requires the wildcard.

**THE UN-ANNOTATED FACE WAS A SECOND, SEPARATE GAP, and the consumer's own probe sits in it.**
With the annotated route built, `function len(id) { match id { 0x10 => 14, _ => -1 } }` still
refused — `match scrutinee must be a union or an integer, got _` — because an un-annotated
parameter's type is a `TyVar` and no vocabulary can be chosen from one. The hand-written twin
`if id == 0x10 { … }` compiles and runs at that spelling, so this was a capability the twin had
and `match` did not, at exactly the spelling VL-020 was reported with. The twin does not SOLVE
the hole either (`len("a")` proves it: the parameter stays open and the call refuses with
`argument 1: operator '==' is not defined for string and i32`) — it DEFERS, through
`noteBinCstr`. So the hole route does the same: when every pattern reads as an integer literal
or `_`, the ARMS choose the vocabulary and each arm records the identical `==` constraint, which
the call that pins the parameter adjudicates. `len("a")` through a `match` now prints the twin's
sentence word for word.

**THE WILDCARD IS MANDATORY, and that is the whole exhaustiveness story here.** A union has a
closed member set to be complete over; `i32` has 2^32 values, so there is no arm list that could
stand in for a `_`. An arm AFTER the `_` is refused for a sharper reason than deadness:
`matchElseArmOf` makes the wildcard arm the chain's bare `else`, so a later arm would be tested
FIRST and `match` promises first-match-wins — allowing it would silently REORDER the program.

**THE SEED-SIZE RATCHET IS REWRITTEN HERE, and 92.7% of what tripped it is not this row.** The
committed baseline stood at 2,043,139 bytes while master's own fixpoint had already reached
2,101,053 — **+2.83% of a +3.0% bar** across five landings, none of which rewrote it. This
change adds **4,538 bytes (+0.216%)**, which is what tips the total to +3.06%. Rewritten to
2,105,591 in this PR, as the gate's own instruction says; the bytes this row bought are
`checkMatchIntArms` and its five helpers plus the parser's two pattern branches. Read the
+3.06% as the tree's number, not as this row's — that distinction is the whole reason the gate
asks for a sentence rather than a flag.

**A GUARD IN THIS ROW MADE A NEIGHBOUR'S UNGUARDED READ VISIBLE, and that is the lint working.**
`sentinel-index-unguarded` derives its HOLE FIELDS from the module's own text — a field the
module compares `< 0` or `>= 0` — so `matchNegPatNum`'s `pn.unArg >= 0` is what taught
`typecheck.vl` that `unArg` can be in band, and `paramDefaultIsLiteral`'s pre-existing
`P.nodes[d.unArg]` (a signed literal parameter default, untouched by this row) became the
seventy-second hit against a baseline of seventy-one. The ratchet was NOT raised: both reads now
carry the full bound test `>= 0 && < P.nodes.length`, and `typecheck.vl`'s hit SET is identical
to master's, entry for entry. Note the direction — the new code added the COMPARISON, not the
unguarded read; the read had been there all along and nothing had made a consumer adopt the
idiom, which is the gap `docs/internals/sentinel-index-lint.md` says the rule exists to close.
