### D3656 — an `if` nested in an arm of an ANNOTATED return's join boxes its widened runtime tail at the tail's own type

**closed 2026-11-02 · runs, prints `true` `-1.5` · was check-clean silently wrong, clause 1 · fixture `tests/cases/numerics/nested-scalar-join-returned-into-number-union.vl` · D3571's mechanism at the return position · found by the #3379 review (`rv79`) · the same on master `32b753681` and with #3379 · filed 2026-10-05**

Repro:

    function mk(q: i32 | null, r: i32 | null): i32 | f64 {
      if q != null { q } else { if r != null { r } else { 2.5 } }
    }
    const x = mk(null, -3)
    print(x is f64)
    print(x / 2)

Want:

    true
    -1.5

#### Mechanism

The inner `if` alone types `f64`, as in [D3571](D3571.md). A function returning a union box
takes the union sink, which splits a returned `if` into one exit per arm (`emitIfTail`,
`emitUnionRetIfSink`) without asking `ifJoinAdaptsScalar`, so `r` was boxed at its own `i32`
member. The sink now keeps such an `if` whole (`retIfIsOneNumber`) where it adapts and a literal
tail already has the wider number's type, as D3571's join does; a join of runtime tails alone,
as an instance's kept-apart type parameters, still boxes each at its own member.

#### Findings from three refused attempts (#3387)

Each round returned the inner join as one value, boxed once at its type
(`tailIfReturnsWhole`/`emitReturnWhole` in `wasmEmit.vl`, gated on `ifJoinAdaptsScalar` and a
union result), at the return path's recursion points: the body tail, an `else if` link, a nested
arm, a returned `if`. Review refused all three rounds, the change is reverted, and the row stays open.

- **Round 1: the outermost `if`.** The rule also fired at the outermost returned `if`, so
  `if q != null { q } else { s }` at `: i32 | f64` stopped delivering `q` as `i32` (`l1(4) is i32`
  printed `false`). An un-annotated lambda made it worse, because its join of a runtime `i32` and
  a runtime `f64` is typed `f64` ([D3710](D3710.md)).
- **Round 2: an `f32` literal typed `f64`.** The rule was limited to nested `if`s. A lambda's
  nested join over an `f32` value types its literal arm `f64` beside the `f32` member, so the
  join was not the wider number and 5 grid cells went right→wrong. It was then limited further,
  to `i32` tails.
- **Round 3: a mixed-member `else if`.** The round-2 review's witness is runs → not-runs:

      function f(q: i32, c: boolean): i32 | f32 {
        if c { 1.5 } else if !c { q } else { 1.5 }
      }
      print(f(4, false))
      // master prints 4; round 2 gave invalid wasm, expected i32, found f64

  The nested spelling fails the same way. The join is typed `f64`, read off the literal `1.5`,
  and neither member of `i32 | f32` is the number the join was taken at.
- **The `is` answer is user-visible.** The rule re-boxes a nested value at the join's type, so
  `q` read beside a nested `w: i64` answers `is i64`, not `is i32`, in programs that run today.
  That is what the fix intends, but it changes observable results, so it needs a ruling beside
  the numeric-join one.

The emitter cannot decide this from the join's type while the checker types the join
inconsistently, so this likely needs [D3710](D3710.md)'s checker fix first: one join type per
`if`, the same for a function and a lambda, and agreeing with the width the literal adopted.
