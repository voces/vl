### D2342 — a write to a for-in index carried into the next iteration, so capturing the index changed what the loop printed

**closed 2026-09-24 — the witness prints `2 1 2 3`. Was check-clean silently wrong (it printed
`2 3 4 5`); found by the review of D2339's PR, filed against master `90c3ba566`. Fixture
`tests/cases/loops/for-in-index-write-per-iteration.vl`**

Repro:

    for _v, k in [10, 20, 30, 40] {
      if k == 0 { k = 2 }
      print(k)
    }
    // prints 2 then 1 2 3 on separate lines

#### Mechanism

`emitForInStmt` (`compiler/wasmEmit.vl`) kept the index of `for v, k in xs` in `k`'s own local
and stepped that local after the body, so a write to `k` moved every later index. D2339 rules a
for-in variable per iteration, so once a closure captured `k` it lived in a per-iteration cell
seeded from the local, and the same loop printed `2 1 2 3`: adding a closure changed the output.
A body that assigns the index now gets a hidden counter, and `k` is copied from it at the top of
each iteration. A body that does not write `k` compiles as before.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the write to `k` | prints 0 1 2 3 | **yes** |
