### D2878 — a closure in a hole-parameter function returning the parameter's `string | null` field traps on a null field

**closed 2026-09-27 — the filed repro prints `null` · was loads then traps, clause 1, identical on master `0284dc2a8` · closed by pinning a lambda clone's return through the instance's holes, not only its explicit binding · found by the RF lane's `holecap` grid · filed 2026-09-27**

Repro:

    function hc(o) {
      const c = () => o.f
      print(c())
    }
    const r: { f: string | null } = { f: null }
    hc(r)
    // vl check: rc 0.  vl run: wasm trap: null reference in `__lambda_1`

Want:

    null

#### Mechanism

The lambda is cloned per instance (its capture makes it a template), and
`monoCloneLambdaSubst` pins an un-annotated return by substituting the return expression's type
through the instance's explicit binding only. A hole parameter's variable is bound in
`monoCgcHoleN`/`monoCgcHoleT`, not there, so the return stayed unpinned and the emitter inferred it
from the captured value as a non-null `string`. The return is now substituted through the holes
too (`monoHoleTy`), for a lambda whose return expression is a hole parameter or a field chain
off one, bound by a `const` and only called directly outside any lambda. A lambda read as a
value, or called from inside another lambda, keeps its inferred return, because that read sees
the template's signature (the #3237 review's `min_loss` was invalid wasm without this gate).
Those shapes still trap at a null value: [D2926](D2926.md). Removing the pin brings the trap
back; the D2900 edit alone does not fix it.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the closure (`print(o.f)`) | runs, prints `null` | **yes** |
| the null (`{ f: "s" }`) | runs, prints `s` | **yes** |
| the hole (`const c = () => r.f` at top level) | runs, prints `null` | **yes** |
