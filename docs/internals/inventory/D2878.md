### D2878 — a closure in a hole-parameter function returning the parameter's `string | null` field traps on a null field

**loads then traps · clause 1 · identical on master `8e10ef58b` · found by the RF lane's `holecap` grid · filed 2026-09-27**

Repro:

    function hc(o) {
      const c = () => o.f
      print(c())
    }
    const r: { f: string | null } = { f: null }
    hc(r)
    // vl check: rc 0.  vl run: wasm trap: null reference in `__lambda_1`

Want:

    null

#### Mechanism

Not localised past the ablation. The lambda is lifted once, from the template, and its result
is lowered as a non-null string ref, so reading a null field out of it traps. The instance's
own read of `o.f` keeps the nullable ref.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the closure (`print(o.f)`) | runs, prints `null` | **yes** |
| the null (`{ f: "s" }`) | runs, prints `s` | **yes** |
| the hole (`const c = () => r.f` at top level) | runs, prints `null` | **yes** |

#### Grading list

The RF grid's `holecap_nstr*`, `hcbind_nstr*`, `hcret_nstr*`, `hcelem_nstr*`, `hceq_nstr*` and
`hcarg_nstr*` cells whose `string | null` value is null trap on master. The same programs with a
non-null value run, so no static refusal separates them. A change that gives such a record
its own row, or lets a sibling pin in the same function print, exposes this trap in cells
that fail another way today; #3230 pulled both for that reason.
