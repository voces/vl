### D1977 — the string pool decodes each distinct literal into ONE `i32[]` of code points, so a single literal past 2^23 code points traps the compiler

**compiler trap (`allocation size too large`, exit 70) · residue of D1976 · filed 2026-09-22 against master `48a295c72` plus D1976's fix · the literal-side sibling of D1975 (source intake) and D1976 (output buffers)**

Repro (one 8.4M-character literal, in an imported module so the entry stays small and the
compile keeps the null collector):

    // file: m.vl
    export function s(): string { "@@repeat(8400000, "a")@@" }
    // file: main.vl
    import { s } from "./m"
    print(s().length)
    // vl check: rc 0.  vl build / vl run: the compiler traps, exit 70

#### Mechanism

`collectStrPool` (`emit_sections.vl`) decodes every distinct string literal with `strToCps`
(`emit_base.vl`), which pushes the literal's code points onto one `i32[]`. Under the null
collector one object is at most 64 MiB, so `.push`'s growth to 2^24 slots traps once a single
literal passes 2^23 code points. Named backtrace: `strToCps@emit_base.vl` ←
`collectStrPool@emit_sections.vl` ← `emitModule` ← `emitProgram` ← `modCompile`. The trap is
before any byte is emitted, so D1976's packed output buffers do not reach it.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| 8.3M characters instead of 8.4M | builds; wasmtime refuses the 25 MB body at its limit | **yes** |
| the import (one file, the literal inline) | same trap | no |

#### Grading list
