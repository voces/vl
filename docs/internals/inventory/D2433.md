### D2433 — an un-annotated lambda handed to a generic higher-order function lowers its parameter at the wrong rep when the type parameter binds to f32, a nullable, a union or a map

**check-clean invalid wasm · found while grading #3155's review (B2), whose explicit-type-argument face this row's implicit face shares · filed 2026-09-25 against master `70450b586`**

Repro:

    function apply<A, B>(f: (A) => B, a: A): B { f(a) }
    const x: f32 = 3
    const r = apply((q) => q, x)
    print(r / 2)
    // vl check: rc 0.  vl run: the emitted module failed to validate inside `apply`:
    // type mismatch: expected i32, found f32

#### Mechanism

The `apply` instance converts the callback's result with `f32.convert_i32_s`: the pin it
builds for the open lambda reads the lambda's result at the i32 default, while the lifted
lambda itself returns `f32`. The annotated twin `(q: f32) => q` runs, and so does every
spelling with written type arguments since #3155 (`apply<f32, f32>((q) => q, x)`), because
those annotate the lambda before checking. The inferred face has no annotation to lower
from. Its siblings refuse loudly instead: at `A = i32 | null` and `A = string | i32` it is
`emitProgram: value-call union parameter has no resolvable union name`, and at
`A = {[string]: i32}` it is `` `??` over this nullable value is not supported yet ``.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the lambda's parameter annotated (`(q: f32) => q`) | runs, prints `1.5` | **yes** |
| written type arguments (`apply<f32, f32>(…)`) | runs, prints `1.5` | **yes** |
| `x` an i32 / i64 / f64 / string | runs | **yes** — f32, nullable, union and map only |
