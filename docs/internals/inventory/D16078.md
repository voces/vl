### D16078 — a `const`-bound lambda maker's un-annotated deliveries banked their row under the binding, not the lambda, so a second type had no twin

**closed · the `two_instances` un-annotated cell of `hole-lambda-returned-by-lambda-at-two-types` · found by lane I from the matrix · filed 2026-11-14 against master `d920175a`**

Repro:

    const outer = () => {
      const l = (x) => x
      return l
    }
    function one() {
      const v = outer()
      print(v(41) + 1)
    }
    function two() {
      const v = outer()
      print(v("s"))
    }
    one()
    two()

Want:

    42
    s

#### Mechanism

`fvaMakerCallRows` (check_assignable) banks a maker row for each binding of a maker call whose
reads are calls at one closed signature. The elaboration builds a twin per row, and mono builds
each call's maker there. Its last loop banked the row under `identDeclOf` of the callee. For a
`const`-bound lambda that is the `LetDecl`, which no instance answers to, so a second type had
no twin. The annotated loop already went through `fvaMakerOfBinding` (D12234). Both loops now
use it. A lambda that returns a call's result through an un-annotated `const` copy
(`const g = () => { const v = c; return v }`) is left to its bundle path (D15744), just as a
lambda returning the call directly already was. Without that, `bundle_copy_closure_returned`
emitted invalid wasm.
