### D4015 — an un-annotated lambda and a generic written into one binding share the lambda's default instance, so the call takes the wrong type

**closed 2026-10-12 by lane SC with D3961 (#3570): the call through the binding pins its seed and the generic written takes that signature · runs · was check-clean silently wrong · clause 1 · found in review of #3517 (`rv3517/l01_lambda_then_generic_write`, `l02`, `L09`) · filed 2026-10-11 against master `20fa382fe` with #3517 applied**

Repro:

    function inner<U>(u: U) { print("I"); print(u) }
    function other<V>(v: V) { print("O"); print(v) }
    function main() {
      inner(3)
      let f = (u) => { print("L"); print(u) }
      f = inner
      f(true)
    }
    main()
    // vl check: rc 0.  vl run: prints I 3 I 1

Want:

    I
    3
    I
    true

#### Mechanism

#3517 keeps master's path for any binding with a lambda written into it, because one lambda body
is shared by every instance and instancing the generic beside it at the call's type made
`rv3498/round4/e23` print a silent `L 1` instead of refusing. On master's path the call pins
nothing: the lambda's parameter hole and the generic both fall to `i32`. A refusal at the call
would also close this row; it then wants a `// want` refusal fixture in place of the `Want:` above.
