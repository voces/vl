### D2801 — a nullable value box read where a narrowing pins it to `null` is unboxed as the arm it does not hold

**closed 2026-09-27 — the filed repro RUNS and prints `5` · was check-clean invalid wasm · clause 1 · found by #3208's review (`gPr` `nnar` cells) · closed by lifting a `null` narrowing for the read (`narrowedToNullKey`) so `print` dispatches on the box's tag and `??` tests it at run time · filed 2026-09-27 against master `b586b6063` · fixture `tests/cases/unions/nullable-box-null-arm-reads.vl`**

Repro:

    const v: i32 | null = 5
    if v != null { print(v) } else { print(v) }
    // vl run: invalid module — type mismatch: expected i32, found (ref $type)

#### Mechanism

`i32 | null` is a value box. The `else` of `v != null` (and the `then` of `v == null` or
`v is null`) pushes the narrowing `v → null`. `print`'s box plan declines a one-member
narrowing (`printNarrowKeepsBox`), and nothing else in its ladder claimed the `null` arm, so it
fell to the scalar tail and called `__print_i32__` with the box on the stack. A parameter
instead reached the loud `tag dispatch cannot classify` floor, and `v ?? d` in the same arm
refused (`?? over this nullable value is not supported yet`). The narrowing is not a proof the
value is still null: a loop back-edge, a closure or a call can write the place after the test
(the first close answered statically and printed `null` where `10`, `42` and `11` were owed).
Both consumers now lift the narrowing for the read (`maskNarrowFor`) and test the box's tag at
run time; `print`'s plan does the same, so the scratch-frame reservation agrees with it.
