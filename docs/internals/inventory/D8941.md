### D8941 — a generic function widening its `T` argument to `f64` with no declared result is typed `T` at the call

**closed 2026-10-21 by lane L1 · now a loud check reject (`f64 doesn't fit in i32`) · was check-clean invalid wasm · clause 1, present on master `30ff8d9b5` · fixtures `tests/cases/soundness/error-generic-fn-widening-at-i32.vl` and `tests/cases/generics/generic-fn-widening-runs.vl` · filed 2026-10-21 against master `30ff8d9b5`**

Repro:

    function w<T>(x: T) { return x / 2.0 }
    const r: i32 = w(3)
    print(r)
    // vl check: f64 doesn't fit in i32 — the conversion is lossy and must be made explicit with `as`

#### Mechanism

The checker types `x / 2.0` over a type parameter as `T`, so `w`'s signature is
`(T) => T` and `w(3)` is `i32`. D8161's re-derivation from the body
(`directHoleBodyRet`, `check_relate_core.vl`) was gated by `directHoleDecl` to functions
with an un-annotated parameter, so a declared type parameter never reached it. Closed
there: `directHoleDecl` admits a generic function with no declared result, and
`directGenericNumRet` limits what the generic case may take from the body to numeric
results, so only a numeric widening is re-derived and every other generic is left as before.

#### Ablation

| --- | --- | --- |
| `<T>` (`x` un-annotated) | check refuses (D8161) | **yes** |

| `/ 2.0` replaced by `+ 1` | runs, `4` | **yes** |

#### Grading list

The generic wrapper `w<T>(x: T) { return half(x) }` at an `i32` binding, as an `i32`
argument, and at `(i32) => i32`: all invalid wasm on master and refused after. The
un-annotated and `f64` bindings and an `f64` argument run on both seeds.
