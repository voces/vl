#### Mechanism

**The row's own two claims were both wrong, and the probe that found it is the ref-list
TABLE, not the literal's classifier.** Dumped at the same point in both programs:

    un-annotated  rlTable len=1 [0 name=P      kind=1 nul=0]
    annotated     rlTable len=2 [0 name=P|null kind=1 nul=1] [1 name=P kind=1 nul=0]

Both bindings resolve to slot 0, so the annotated one reads a NICHE and the inferred one reads
a non-null struct — `letIsNulRef` then answers 0, the binding's cell is `struct`, and
`emitNulIsNullTest` declines, leaving `v != null` to the struct-compare refusal below it.

Neither an `#anon` row nor a value box was missing. `{n:i32}` already dedupes onto the declared
`P` (`elemName=[P]` in both spellings), and **`arrLitNulRefElemName` — which the row records as
answering `""` for all three spellings — answers `P|null` and passes both of its gates**:

    nulRefElem nen=[P|null] refElemArrName=[(P|null)[]] nameIsRefArray=1 nominalStructNameOfTy=[P]

It is never asked. `arrLitElemName`'s object-literal arm returns `sNames[si]` and the nullable
producer sits forty lines below it. The fix is that ordering, plus the arm-for-arm twin in
`arrLitElemHintTy`, which DECLINES rather than hand over the non-null struct row — hinting it
keyed a second slot for one wrapper and the annotated program interned the same row twice.

**Question (2) is answered: there is no second defect at the guard.** Once the niche row
exists, `v != null` lowers through the null test, and the message was the EMITTER's all along
(`wasmEmit.vl`'s `emitFail`), not the checker's.
