### D3486 — importing `std:math` costs every module about 3.3 KB unoptimised, and one `sinF64` call about 2.0 KB at `-O`

**runs today and must keep running · a SIZE note, neither clause 1 nor clause 2 · low priority · reported by sunpa (28.8 to 31.9 KB, +3.1 KB, after SP-002) · measured on master `e5ff25ff9` · filed 2026-10-03**

Repro (runs, prints `0.8414709848078965`; the byte counts are in the table):

    import { sinF64 } from "std:math"
    print(sinF64(1.0))

#### Mechanism

`sinF64` and `cosF64` reduce their argument with a full-range Payne–Hanek step: a 21-word
`i64[]` table of the bits of 2/π, `twoOverPiAt`, and `reducePio2Large`, with a short fast path
for small arguments. The unoptimised build keeps every function of an imported module whether
or not it is called (inferred from the table: the unoptimised size does not move with the names imported), so the table and both reductions ship in every importer. `-O` removes what
is unreachable and keeps what a call reaches, which is the reduction in full.

Bytes from `vl build` of one program, the loop `s = s + f(i as f64)` over `i < 1000` (so `-O3` cannot
fold the call away; a constant argument folds to 69 bytes at `-O`):

| program | no flag | `-O` | `-O3` |
| --- | --- | --- | --- |
| `hypotF64` only, `std:math` BEFORE sin/cos (`e5ff25ff9^`) | 953 | 111 | 111 |
| `hypotF64` only, `std:math` now | 4,237 | 111 | 111 |
| `hypotF64` and `sinF64` | 4,243 | 2,178 | 2,149 |
| `hypotF64`, `sinF64` and `cosF64` | 4,249 | 2,342 | 2,312 |

So: importing the module costs **+3,284 bytes unoptimised for any program that imports any name
from it**, calling `sinF64` costs **+2,067 bytes at `-O`** (+2,038 at `-O3`), and `cosF64` after it
adds only **+164** because the reduction is shared once the call graph reaches it. A program that
imports `std:math` but calls nothing from sin/cos pays nothing at `-O`. The constant-argument
spelling (`print(sinF64(1.0))`) measured 4,184 unoptimised, 164 at `-O`, 69 at `-O3`: the
optimiser folds it, so it is not the cost a real program sees.

#### Ideas, none urgent and none decided

* Put the 2/π table in a data segment instead of an `i64[]` global built by array initialisers;
  the table is 21 words (168 bytes of payload) and the initialiser code around it is larger.
* Split the large-argument reduction behind the fast path so the unoptimised module could drop it
  if the compiler learned to omit unreachable imported functions at no flag, which would help
  every std module, not this one, and is the larger lever (the +3,284 is the whole module).
* One reduction shared by sin and cos already holds at `-O` (+164 for the second function); keep
  it that way when `tan` or a sincos arrives.

#### Grading list

Re-measure the four rows with the same loop after any change to the reduction or to unreachable-function
removal. The `sinF64(1.0)` value above must keep printing `0.8414709848078965`.
