### D16450 — a value `if` or `match` outside a function's tail does not seed its arms' lambdas with the type it is delivered to

**closed · was a loud check reject, ``cannot infer a type for parameter `x` `` · clause 2 · bucket (f), a local fix: the tail spelling of the same `if` runs · found from lane D's return-rule migration of `tail-if-arm-legal-returns-run` and `map-boxed-ref-element-result` · filed 2026-11-15 against master `c3049ce76`**

Repro:

    function f(n: i32): (i32) => i32 {
      return if n == 0 { (x) => x + 1 } else { (x) => x * 2 }
    }
    print(f(1)(2))

Want:

    4

#### Mechanism

`seedExpected` (`check_expected.vl`) gives an expression the type its position delivers it to.
For an `if`, `match` or block it banked the join's want and the destination of each call leaf,
but it did not seed an arm's lambda, so the lambda had no parameter types. A function's tail
used `seedTailArms` instead, which also seeded each value leaf. So a tail `if` ran and the same
`if` after `return`, in an annotated `const`, as an argument or as an assignment's right side
was refused. `seedExpected` now seeds each value leaf of a join itself. `seedTailArms` is
deleted and the tail calls `seedExpected`, so every position reads one seed.
