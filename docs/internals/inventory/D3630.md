#### Mechanism

D3625's step (`scripts/vl-host/src/multivalue.rs`) refused two kinds of record that no write
can reach. It charged a `struct.set` to every record of the written type's SHAPE, so the
in-place `Spark` (three `mut f64`, like `V3`) disqualified `V3`. And it refused every type
in any subtyping relation, while the emitter (D622, `buildStructSupers`) declares each record
a subtype of the longest record whose fields are a proper prefix of its own, so any `{ x: f64,
y: f64 }` in the program makes `V3` `(sub $Pt …)`. In sunpa, `V3` was type 83, `(sub 51 …)`,
with 51 being body.vl's `Pt` and fx.vl's `Dir`. Shape was the safe unit only because two type
indices might name one wasm type. VL emits every struct type into ONE rec group, though, and
there two distinct indices are distinct types. The step now checks that, and when it holds
charges a write to the written type and its subtyping component (union-find over the
declared supertypes). A subtype's value can stand where its supertype is expected, so a
write through either reaches both, while a record no write reaches stays a record. Comparing
a value's type with a use's type is then by index. A module whose struct types span several
groups keeps the shape rule and still refuses subtyped records. The written-shape set is now
read before that refusal, so a subtyped type's write still counts against its shape.

`$VL_MV_EXPLAIN=1` reports on stderr, per record type a function takes or returns, whether
the step takes it and which write refuses it. It also reports, per record-returning function,
whether it gets a result twin and why not, and groups each producer's struct-keeping call
sites by what they do with the value. The step's output is byte-identical with it on or off.
