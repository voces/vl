#### Mechanism

A list is a `{ backing, length, capacity }` header over an array. Binaryen's `--heap2local`
melts both once the producer is inlined and every index is a constant: with `mix3` given a
single caller the same program builds with no allocation, and forcing the inline on the
three-caller module and running `-O3` twice more melts every list but the one stored in a
global. Neither `-O` step reaches it: the escape step's producer rule
(`escape_inline_choice`) takes small RECORDS only and skips heap-held types, which every list
header is, and the multi-value step's twins return record fields only. A trial that let
numeric list headers through the producer rule (lane PF, not landed) moved nothing in sunpa:
`mix3` is 357 bytes before `-O` (the bound is 320, and bounds-checked reads are most of it),
`ray`'s result is merged with a second literal (`p = ray(…)`, then `p = [ … ]`), which
`--heap2local` refuses, and `scale3`'s results flow into the uninlined `mix3`.

Proposal. A program writing `f64[]` as a 2-, 3- or 4-vector is asking for a VALUE, and the
cheap, general answer is the value type the fixed-array design already chose (Q1 = (a): an
immutable value, `m[i] = v` replaces the whole value, plain syntax). A `f64[3]` (or a record)
takes the record path, where the multi-value and escape steps already remove the
allocations (D3625, D3765–D3767, D3803). A list-specific `-O` rule would need a size bound
that discounts bounds checks, a merge-aware use test, and a multi-value twin for lists of a
known length. That is three changes to recover what the value type gives by construction,
and it would still miss every merged or stored use. Recommendation: no list rule. Build fixed
arrays when sunpa asks, and tell sunpa that a 3- or 4-field record (`V3`, `Q`) is
allocation-free across calls today.
