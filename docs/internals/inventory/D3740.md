#### Mechanism

`rsIxReady` (emit_classify.vl, D2914) builds the use index that `objLitBindDestRow`,
`rsNarrowUseRefuse` and `rsElemListDestSlot` read. The index holds ten whole-arena columns and
two string-keyed maps. It was rebuilt whenever `P.nodes.length` had changed since the last
build. The arena still grows after `emitArenaFinal`: binding a `.get` read pins the binding's
annotation while its function is emitted, which appends a `TypeRef`. So every function holding
such a binding and an object literal whose field names fit two rows rebuilt the index. That
was 8 rebuilds and about 490 MB on sunpa. A rebuild also replaced `rsRecRow`, the per-literal
memo, and `sNames` growth replaced it too. Each later answer then regrew that memo with -2 up to
the literal's node index, the D3737 pattern: 60% of the allocation once the rebuilds were gone.

The close extends the index when the arena only grew, which means the epoch is unchanged and no
slot was rewritten (`rsIxGrow`). The appended nodes take the rows a rebuild gives a node the
root does not reach. The per-binding answers (`rsDoneLet`, `rsLetDst`, the return-walk marks,
`rsRecRow`) are dropped at the entries written since they were last dropped, which is exactly
where a rebuild drops them. `rsRecRow` is cleared the same way when `sNames` grows.

The late annotation pins are the exception to "appended nodes are unreachable": a pinned
`TypeRef` hangs under its `LetDecl`, so a rebuild gives it a parent and the extension does not.
No query starts at a `TypeRef` or climbs through one. A cross-check compiler rebuilt the index
beside every extension and compared all six structural columns. On sunpa's `game.vl`, the
compiler and all 4,532 `tests/cases` programs the only differences were such `TypeRef`s
(3 on sunpa), and every identifier chain was identical.

sunpa's `game.vl`: fuel 79.73G to 77.13G, allocation 2.24 GB to 1.71 GB. Output is
byte-identical.
