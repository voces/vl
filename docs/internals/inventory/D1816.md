### D1816 — one array-literal node cannot carry two ref-list rows, so a capturing element under a TWICE-pinned frame still has no element name

**loud emit reject — `emitProgram: callee is not a function name` · clause 2 · filed
2026-09-06 against master `57b54ccdd`, the residue [D1794](D1794.md)'s close names and does
not move · re-measured 2026-09-07 against master `678f578e3`, with the frame hop
([D1817](D1817.md)'s `fnInstOrigin`) in: unchanged, and that shape provably does not reach
this one**

Repro:

    function o(n) {
      function k(x: i32) { return n }
      const fs = [k]
      return fs[0](1)
    }
    print(o(2))
    print(o(2.5))
    // vl check: rc 0, "Checked 1 file, no errors."
    // vl run:   emitProgram: callee is not a function name

#### Mechanism

**Measured to the pin bank, not past it.** [D1794](D1794.md) names the array element through
the enclosing hole's banked pin. `notePinnedHole` banks `-2` for a hole two calls pinned
differently, and `pinnedHoleTyOf` reads that as no answer — correctly, because the array
literal is ONE arena node shared by both instances (an accumulating probe reads `ARR ix=8` at
every visit, at one pin and at two), while the two instances need two different rows:
`((i32)=>i32)` and `((i32)=>f64)`. A closure-element ref-list row carries the callee's
signature by NAME (`cloArrSlotSigKey` reads `rlElemName[slot]`), so one row cannot serve both.

The annotated destination is not the workaround it looks like — `const fs: ((i32) => i32)[] =
[k]` is a correct CHECK reject at the second pin (`cannot assign ((i32) => f64)[] to 'fs'`).

**Re-measured with the frame hop in, and the `fnInstOrigin` shape does not reach this.** That
hop repaired a walk which ALREADY carried the reader's frame; this row's row-mint has no frame
to carry. Probed at `arrLitIsRef` with the emitting function printed, two pins:

    ARR ix=8 curFn=-1[]     cen=[] fnStmts=0
    ARR ix=8 curFn=-1[]     cen=[] fnStmts=2
    ARR ix=8 curFn=-1[]     cen=[] fnStmts=4
    ARR ix=8 curFn=31[o]    cen=[] fnStmts=4   (x4)

The row is interned during a COLLECT pass at `curFn=-1` — a flat scan over `P.nodes`, before
any function is emitted — and the literal is never classified again while `o$1` is emitted, so
there is no moment at which a per-instance answer could be given. The one-pin control has the
same shape and differs only in `cen`.

**And the pin SET survives nowhere, which is the fatal half.** `holePinTys` is one scalar per
hole: first pin wins, a disagreeing second writes `-2`, and no list is kept
(`notePinnedHole` is its only writer). So a collect scan could not mint one row per pin even
if it wanted to — it cannot learn what the pins were.

**No candidate was built, deliberately.** Both prerequisites would have to land first — a
durable pin SET in the checker's bank, and a frame at the row-mint — and building either alone
adds machinery with no consumer, which this repo has refused before. Naming them is the
useful output; the price of guessing is not.
