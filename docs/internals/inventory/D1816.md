### D1816 — one array-literal node cannot carry two ref-list rows, so a capturing element under a TWICE-pinned frame still has no element name

**loud emit reject — `emitProgram: callee is not a function name` · clause 2 · filed
2026-09-06 against master `57b54ccdd`, the residue [D1794](D1794.md)'s close names and does
not move**

Repro:

    function o(n) {
      function k(x: i32) { return n }
      const fs = [k]
      return fs[0](1)
    }
    print(o(2))
    print(o(2.5))
    // vl check: rc 0, "Checked 1 file, no errors."
    // vl run:   emitProgram: callee is not a function name

#### Mechanism

**Measured to the pin bank, not past it.** [D1794](D1794.md) names the array element through
the enclosing hole's banked pin. `notePinnedHole` banks `-2` for a hole two calls pinned
differently, and `pinnedHoleTyOf` reads that as no answer — correctly, because the array
literal is ONE arena node shared by both instances (an accumulating probe reads `ARR ix=8` at
every visit, at one pin and at two), while the two instances need two different rows:
`((i32)=>i32)` and `((i32)=>f64)`. A closure-element ref-list row carries the callee's
signature by NAME (`cloArrSlotSigKey` reads `rlElemName[slot]`), so one row cannot serve both.

What the close would need, and what [D1794](D1794.md) deliberately does not attempt: the row
resolved from the FRAME the literal is read in rather than from the node, which is the shape
[D1782](D1782.md) gave the binding resolver one delivery earlier. The annotated destination is
not the workaround it looks like — `const fs: ((i32) => i32)[] = [k]` is a correct CHECK
reject at the second pin (`cannot assign ((i32) => f64)[] to 'fs'`).
