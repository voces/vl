### D12940 — a loop over hole functions is typed before the walk reaches the instance of a hole function that pushes a lambda its argument also flows to

**loud emit reject · `vl check` rc 0 · clause 2 · CAPABILITY: the same program with `more(5)` called before the first loop runs · found closing [D12880](D12880.md) · filed 2026-10-25 against master `407c858fd`**

Repro:

    function snd(a, b) { return b }
    function apply2(g) { print(g("x", 2)) }
    const fs = [apply2]
    function add(k) { fs.push((g) => { print(g("z", k)) }) }
    add(9)
    for f in fs { f(snd) }

    const hs = [apply2]
    function more(k) { hs.push((g) => { print(g("z", k)) }) }
    function go() { for f in hs { f(snd) } }
    more(5)
    go()
    more(6)
    go()
    // vl check: rc 0.  vl run: emitProgram: a generic function is passed to a function value whose parameter type names a type parameter this closure does not bind

Want:

    2
    9
    2
    5
    2
    5
    6

#### Mechanism

`snd`'s pins at the first loop are the calls of every parameter it flows to, so they include
the call `g("z", k)` inside `more`'s lambda, at `more`'s type variable `?more.0`. D12880 binds a
hole function's type variables from the instance rows (`monoHoleSubN`, `monoOneInstHoleBinds`
in emit_mono.vl), and those rows hold only the instances built so far: the walk types the first
loop before it reaches `more(5)`, so `?more.0` is still open and the pins do not close. The
binding is read in walk order, not from a table of every instance the program will have.
