### D3267 — a join of a literal-union parameter, a boolean parameter and a `null` arm prints the wrong arm

**closed 2026-09-30 · was check-clean silently wrong, clause 1, on master `b6378e95b` (`a b b`) · found by the #3297 round-2 review (`q4.vl`) · fixture `tests/cases/generics/join-type-params-with-null-arm.vl`**

Repro:

    type K = "a" | "b"
    function g<T, U>(a: T, b: U, k: i32) {
      const r = if k == 0 { a } else if k == 1 { b } else { null }
      return r
    }
    const x: K = "a"
    const y: boolean = true
    print(g(x, y, 0))
    print(g(x, y, 1))
    print(g(x, y, 2))

Want:

    a
    true
    null

#### Mechanism

The chain joins from the inside: `U` beside `null` is `U | null` (D2533), then `T` beside
`U | null`. No rule of `joinTys` saw two parameters there (`tyParamsPart` reads a bare `T`
against a nullable as apart from nothing), so `assignable` folded the whole of `U | null` into
`T`, and the instance built the join as `K`'s atom. `tpOpenJoin` now joins any set of declared
parameters and a null, one of them the checked body's own, as `T | U | null`; `substTyDeep`
re-joins the members under the null, the inferred-return floor no longer refuses a nullable
union over a parameter, and the emitter registers a nullable union's box at the pin
(`monoTyIsUnionOrNulUnion`: the binding, the chain's join, a record literal's field).
