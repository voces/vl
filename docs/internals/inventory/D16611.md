### D16611 — `==` between operands that can both hold a map through a union arm is refused at emit, not at check

**closed 2026-11-15 · now a loud check reject, the refusal the design owes, moved to check with the map-equality contract · was: loud emit reject · clause 2, a refusal in the wrong phase · `emitProgram: \`==\` over a struct union is not supported yet` and `emitProgram: union \`==\` over a non-binding union value is not supported yet` · found proving the unprobed `--sites` rows (wasmEmit.vl struct-union `==` and non-binding union `==`) live, for lane J · filed 2026-11-15 against master `033206ff4` · by: `==`/`!=` is refused at check when a union operand and the other can both hold a map, as a bare map compare is (`uncomparableArmEqRefused`, check_identity.vl; `tyCanHoldMap`, check_ty_relate.vl) · fixture `tests/cases/soundness/eq-union-arm-holding-map-refused.vl`**

Repro:

    type A = { m: {[string]: i32} }
    const u: A | i32 = 3
    const x: A = { m: Map() }
    print(u == x)
    // was: vl check rc 0, vl run: emit error, `==` over a struct union is not supported yet

Want: a check reject, as `x == x` and two maps are refused:

    `==` compares values, and a map has no defined equality: `A | i32` and `A` can both hold one

#### Mechanism

A map has no defined value equality (T7.3; `{[string]: i32} isn't equatable`), and a record
holding one is refused at check too. Through a union arm the checker asked neither: the compare
passed and reached the emitter's union `==`, whose variant compare declines a map field
(`variantFieldComparable`) and whose staged core declines a map arm (`unionBoxEqColumns`). The
rule is the function-arm one (`fnEqRefused`, A15) with maps: refused when both sides can hold a
map; `u == 5` stays legal. A union *field* (`{ n: i32 | string }` arm) is compared by the arm
compare and keeps running: the rule asks only for maps.

#### Ablation

| --- | --- | --- |
