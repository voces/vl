    function main() {

#### Mechanism

The checker joined the arms to `i32 | void` — `.push` yields its new length, `print` yields
nothing — and recorded that as the closure's inferred return, although DECISIONS.md §`void`
rules `void | i32` a type no value has. The emitter took the closure's functype from that
return (a union box) and lowered the `print` arm into a value position with nothing to put
there, so both arms ended in the compiler's `unreachable`. A top-level function with the same
body ran only because the emitter's own `computeVoidFns` classified `.push` as a statement and
disagreed with the checker in the direction that happened to work.

The rule the close states: **a tail `if`/`else` or `match` yields a value only when every arm
that completes yields one; an arm ending in a void call, a statement, an empty block, or such
an `if` nested as its tail makes the whole tail a statement, and an arm that always exits
(`return`, `break`) contributes nothing to the join.** It is D1034's empty-arm rule and the
tail-`if` arm rule behind `tailIfNullableIsReal`, said once: an empty arm and a void arm are
the same absence. The checker banks the verdict per `if` node (`ifNoValueAt`), rewinds any arm
values it had seeded into the inferred return (`dropTailIfSeeds`), and the totality check reads
the same verdict, so a `return 5` beside a value-less arm infers `i32 | null` rather than
`void | i32`. One arm shape is deliberately left undecided: an arm ending in a bare `{ … }`
block, whose value is the open bare-block-as-expression ruling (`open-rulings.md`); the verdict
is not computed there, so [D1903](D1903.md)'s pinned cells keep running exactly as before. An
`if` under an explicit `return` is a value slot, not a tail statement, and keeps the `return
expects a value, got i32 | void` refusal.
