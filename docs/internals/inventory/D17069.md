### D17069 — a record's function-field storage is chosen per row, not per record type

**runs today and must keep running · 3 split + 14 late-mint programs of the `--cases` list · filed 2026-11-23 against master `53f48d7`**

Repro:

    function id0(a) { return a }
    function id1(a) { return a }
    function mk<T>(x: T) { return { f: id1, x: x } }
    const r = mk(1)
    r.f = id0
    print(r.f(2))
    const s = mk("s")
    s.f = id0
    const g = s.f
    print(g(3))
    print(s.f("q"))

Want:

    2
    3
    q

#### Mechanism

A function-typed field is stored either as an `i32` function id or as a closure cell, and
legacy decides that when it mints each struct row, from the literal or registration that
mints it, not from the record type. So one record type can hold two rows that store the
same function field differently, and a row can be minted during emit after the type's rep
was built. The rep tree keys a record by type and answers closure for every function field,
so for these programs no type-keyed answer is right. The planned fix (coordinator ruling
2026-11-23) chooses one storage per record type at row registration, as its own
byte-changing PR, after which the field folds into `rowFieldStorage`.
