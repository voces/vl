### D16431 — a top-level list of un-annotated functions widened by a write, handed to an un-annotated callee declared below it, builds an invalid module

**check-clean invalid wasm · clause 1 · open · bucket (c), an L2 acceptance row ([engineering-review-2026-11.md](../engineering-review-2026-11.md) §6, L2) · a declaration-order face of [D16301](D16301.md), left by `eagerCheckable`'s un-annotated-parameter exemption · found ablating D16301's un-annotated-callee cells · filed 2026-11-15 against master `a058e28fa`**

Repro:

    const xs = [inc0]
    xs.push(half)
    const r = run(xs)
    print(r + 0.5)
    function inc0(a) { return a + 1 }
    function half(a) { return a / 2.0 }
    function run(xs) { return xs[1](3) }
    // vl check: rc 0.  vl run: invalid module.

Want:

    2

With `run`'s parameter annotated it runs and prints `2`:

    const xs = [inc0]
    xs.push(half)
    const r = run(xs)
    print(r + 0.5)
    function inc0(a) { return a + 1 }
    function half(a) { return a / 2.0 }
    function run(xs: ((a: i32) => f64)[]) { return xs[1](3) }

#### Mechanism

`run`'s un-annotated parameter is solved by the statement's call, so `eagerCheckable`
(`compiler/check_top_level.vl`) leaves `run` to source order, and `const r = run(xs)` is
typed before `run`'s body has read the widened list. Unlike [D16430](D16430.md), an early
`main()` does not rescue it. There the write `xs.push(half)` is refused at check, because
`half` returns `f64` where `inc0`, already written, returns `i32`. Declaring `run` before
the statement makes it run. So the list's element signature is decided by whichever of the write
and the callee's body is checked first, which an inferred interface for `run` (L2) would remove.

#### Ablation

| spelling | outcome | needed? |
| --- | --- | --- |
| the witness | invalid module | — |
