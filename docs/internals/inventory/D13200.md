### D13200 — a forwarded hole function handed to a list whose element another list shares at a different key has no interned signature

**loud emit reject · `vl check` rc 0 · clause 2 · CAPABILITY: each loop alone runs · found closing [D12701](D12701.md) · present before lane L1's D12701 PR (seed at `e07ab908c`) and after it · filed 2026-10-25 against master `db5624b1c`**

Repro:

    function add(a, b) { return a + b }
    function apply2(g, s) {
      print(g(s, s))
    }
    function apply4(g, s) {
      print(g(s, 2))
    }
    function inner(k, h) {
      for f in [apply2] { f(h, k) }
    }
    inner(0.5, add)
    function innerThree(k, h) {
      for f in [apply2, apply4] { f(h, k) }
    }
    innerThree(0.5, add)
    // vl check: rc 0.  vl run: emitProgram: a function-value call has no interned signature — parameter 1 of type `` has no representation in the function-value ABI

Want:

    1
    1
    2.5

#### Mechanism

Measured. The first compile refuses every such list call, and the program builds only if a
split round does (fn_split.vl). The split gives `apply2`'s `g` a slot per key over every list
it is in, so `apply2` carries the key `c:_,i32,` that only `apply4` calls. `inner`'s own `h`
reaches `apply2` alone, so it has one key and does not split. Since lane L1's D13200 PR, the
call handing `h` to `apply2` passes it to both slots (`hpRead`, `fsPlanHoleRewrites`). A
direct call `apply2(h, k)` now builds. Through `inner`'s one-element list `[apply2]`, the
function value's second slot is never called there, so its type stays open, and the apply
round refuses at `innerThree(0.5, add)` with the original message. The reader that needs a
signature for the uncalled slot is the list's element signature in `inner`.
