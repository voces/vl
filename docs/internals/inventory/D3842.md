### D3842 — a for-in over a call through a function-typed parameter of an enclosing `<T>` binds the loop variable at the `i32` rep, so a `boolean` prints `1`

**closed 2026-10-08 by lane SC · was check-clean silently wrong · found in review of lane SC (round 4, `g1_fnparam`) · filed 2026-10-08 against master `04be94d88` · pins: `tests/cases/generics/for-in-iterable-at-pin-any-spelling.vl`**

Repro:

    function outer<T>(x: T, f: (t: T) => T[]) {
      for e in f(x) { print(e) }
    }
    outer(true, (t) => [t, t])
    // vl check: rc 0.  vl run: rc 0
    // PRINTS 1
    // PRINTS 1

Want:

    true
    true

#### Mechanism

`iterElemPinTy` answered a for-in loop variable's element type by one case per iterable
spelling: a literal of the parameter, a literal holding a generic call (D3835), a bound list
(D3831), and a direct generic call (D3841). A call through a function value matched none of
them, so the variable fell back to the `i32` rep a `boolean` and a literal union share. The
close replaces those cases with one rule, the one the iterable's index read already follows:
take the iterable's recorded type, substitute it through the binding chain of the instances
the loop is lifted inside (`pinSubOperandTyOf`), and step to its element. Only a call the
instance body copied, which carries no recorded type, still reads its instance's declared
return.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the for-in (`print(f(x)[0])`) | prints `true` | **yes** |
| the call (`const ys = f(x)`, then `for e in ys`) | prints `true` | **yes** |
| `boolean` for `f64` | prints `2.5` | the rep is not shared |
| `boolean` for a literal union `b` | prints `3` | no |
