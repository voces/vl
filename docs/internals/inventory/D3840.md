### D3840 — a nested generic declaring the same type-parameter name as its enclosing generic cannot tell the two apart, since instances substitute type variables by name

**now a loud emit reject (2026-10-08, lane SC) · was check-clean invalid wasm, and a silent `1` for `true` with one instance · found in review of lane SC · filed 2026-10-08 against master `a6c18eb0e` · pins: `tests/cases/generics/error-nested-generic-shadowed-param-capture.vl`, `tests/cases/generics/nested-generic-capture-callers-that-run.vl`**

#### Mechanism

Not yet located. Every instance-binding table (`monoPinSubN`, `monoExactSubN`) and every reader
of one substitutes a `TyVar` by its NAME, so inside `inner`'s instance the captured `ys: T[]`
reads `inner`'s `T`. D3826's per-enclosing-instance keying, applied here, turned this into a
silent wrong value (`1` for `true`), so `monoNestedShadowsOuter` declines it and the program
keeps master's loud invalid module. A fix needs the type variable's owner (`tyVarOwnerOf`)
carried into the substitution, not the name. Until then such a function is refused when it reads
a capture typed at the shadowed name (`monoShadowedCaptureRead`), at one instance or many; a
shadowing function whose captures are typed otherwise, or that captures nothing, runs. With one `outer` instance the same shape is
already a silent wrong value on master and unchanged here: `outer(true)` alone prints `1`
for `ys[1]`.
