### D7183 — a two-element hole-function list iterated by `for` and handed a generic function is refused

**loud emit reject · `vl check` rc 0 · clause 2 · CAPABILITY: the one-element list iterated the same way runs ([D7140](D7140.md)) · found closing [D7140](D7140.md) · the same on master `6a89bc66d` · filed 2026-10-19 against master `6a89bc66d`**

Repro:

    function add(a, b) { return a + b }
    function apply2(g) {
      print(g(1, 2))
      print(g(1.5, 2.5))
    }
    function apply3(g) {
      print(g(10, 20))
      print(g(0.5, 0.25))
    }
    const fs = [apply2, apply3]
    for f in fs { f(add) }
    // vl check: rc 0.  vl run: emitProgram: a generic function is passed to a function value whose parameter type names a type parameter this closure does not bind

Want:

    3
    4
    30
    0.75

#### Mechanism

Probed 2026-10-19 against master `966471462`. The ingredient is two DISTINCT hole functions
in the list. `monoFlowElemsGen` resolves a loop variable over a list to its generic only when
every element is the same function. With two, the loop variable's call has no generic to take
an instance of, and the argument `add` meets the type-parameter floor. A close has to pin the
element at one closed function type, built from both bodies' calls of `g` and the argument's
result at them, and instance each element and `add` there. Re-read 2026-10-19 while closing
[D7182](D7182.md): each body here calls `g` at two types, so no one closed function type can
serve them both. The element needs a per-call-type record (the shape of the D3975 ruling) or
a loop unrolled over the literal list, and both are new mechanisms.
