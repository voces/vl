### D16810 — `==` in a generic body over field reads of two nullable records stored apart builds invalid wasm

**closed 2026-11-16 by lane AE — the witness prints `true` · the generic body's field-read operands compare field by field at the instance, a null side equal only to a null side (`monoPinBin`, `monoPinnedReadTy`, `recEqPureRead`) · matrix `eq-generic-read-operands-stored-apart.matrix.vl` `nullable_record` both faces · fixture `tests/cases/generics/eq-generic-read-operands-stored-apart.vl` · was check-clean invalid wasm, clause 1, `type mismatch: expected (ref null $0), found (ref null $2)` inside `eq` · found grading D16470 · filed 2026-11-16 against master `aad822655`**

Repro:

    function eq<T, U>(a: {v: T}, b: {v: U}): boolean { return a.v == b.v }
    const x: { f: i32 } | null = { f: 1 }
    const y: { f: f64 } | null = { f: 1.0 }
    print(eq({ v: x }, { v: y }))
    // vl run: prints true (was an invalid module inside `eq`)

Want:

    true

#### Mechanism

The instance's `==` over two field reads reached the emitter's one-row struct compare, which for a
nullable pair emitted a `ref.eq` between two struct types stored apart, so the module failed to
validate, where the non-null pair was refused loudly (D16470). Both now take the per-field compare.
