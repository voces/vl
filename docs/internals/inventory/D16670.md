### D16670 — an `as!` cast of a float constant is folded as an exact constant and takes an `i64` destination's width

**closed 2026-11-15 · runs, prints `-294967296` · was check-clean silently wrong, clause 1, `vl check` rc 0, printing `4000000000` · closed by keeping an `i32` cast in `castConstSettle` (check_leaf_steps.vl): it rewrites only the cast's operand, so the cast stays a typed `i32` no literal adoption moves · fixture `tests/cases/numerics/cast-of-float-constant-stays-typed.vl` · E9.1 lists no cast among a constant's operators, so `(2.0 as! i32)` is a typed `i32`, and D3043 keeps a fitting constant beside it at `i32` · the decimal spelling `(2 as i32)` and a typed value both wrap at `i32` · found by the independent oracle's arithmetic generator (fuzz cell `ar_s91_0048`, `gen.ts --seed 91`) · filed 2026-11-15 against master `93ad5a25c`**

Repro:

    const x: i64 = (2.0 as! i32) * 2000000000
    print(x)
    // master: vl check rc 0, prints 4000000000

Want:

    -294967296

#### Mechanism

`castConstDecide` (check_demands.vl) settles a cast of a float constant through `castConstSettle`
(check_leaf_steps.vl), which rewrote the cast node itself into the integer literal `2` typed
`i32`. The tree above it was then a literal tree, and literal adoption (4.3) carried it to the `i64`
destination, where `2 * 2000000000` computed exactly. The fix rewrites the cast's operand instead:
the cast node stays, its type is the `i32` it names, and E9.1 keeps a tree over it out of the
constants, so the product wraps at `i32` before the destination reads it. An `i64` cast is
unchanged. A narrower domain (`u8`) still becomes its literal: `u8` is storage only, so its value
is an `i32` either way, and its kept range test has no lowering (keeping it broke D3588's
`px.push(255 as u8)` with an emit error).
