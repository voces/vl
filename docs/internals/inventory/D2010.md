### D2010 — a closure calling a module-scope `for` variable spelled like a numeric intrinsic (or an extern) called the opcode (or the import), not the variable

**closed 2026-09-22 (`captureLoopVarIterOf` and `capScan` in `compiler/emit_classify.vl`, the numeric-intrinsic fallback in `wasmEmit.vl`'s `emitCall`) · was check-clean silently wrong (this witness prints 4); the same fix closes D1480, the env field of a captured module-scope loop variable typed `i32` whatever its element (residue: D2011) · found reviewing #3018 (D1997) · filed against master `5c4fc52ba`**

Repro:

    const fns = [(x: f64) => x + 1.0]
    for sqrt in fns {
      const h = () => sqrt(16.0)
      print(h())
    }
    // PRINTS 17
    // was: prints 4 — the closure called `f64.sqrt`, not the loop variable

#### Mechanism

A module-scope `for` variable is a local of the start function, and the module scope is not
a lifted frame, so `parentBindingFrameOf` answers -1 for a closure written in the loop body.
Three readers stopped there. `captureLoopVarIterOf`, which gives the env field its element
kind (D1142), declined, so every capture took the `i32` default. `capScan`'s shadowing
guard for intrinsic and extern callees never saw the binding, so the callee was not captured
and `emitCall` wrote the opcode or the import. And `emitCall`'s numeric-intrinsic fallback ran
by spelling even for a name the frame binds. The fix reads the module's loop-variable table
(`moduleBindsLoopVar`, `parentLoopVarOf(emitRootIx, …)`), which is what `capRecord` already
read, and gates the fallback on `userBindsName`.
