### D14842 — a hole parameter read by a function nested in it is taken as each instance's set id, though the nested body is one for every instance

**closed 2026-11-01 · runs, prints `3 4 2 3.75` · was check-clean silently wrong · clause 1 · found probing #5703's forwarded-parameter keying at the coordinator's ask; introduced by #5703 (`de20432ff`), correct at its parent `8970e00f6` · the elaboration notes a captured parameter's forward through a set only outside a nested function (`elabMintHandedNested`), and the tag decision admits a parameter as bound to its instances' sets only when no nested function reads it (`ftParamForwardsSet`, `ftParamBoundTagged`) · pin: `tests/cases/closures/forwarded-hole-param-captured-by-nested-fn-at-two-sets.vl` · filed 2026-11-01 against master `9d1d7374a`**

Repro:

    function add(a, b) { return a + b }
    function mul(a, b) { return a * b }
    function apply2(g) {
      print(g(1, 2))
      print(g(1.5, 2.5))
    }
    function run(h) {
      function inner() {
        for f in [apply2] { f(h) }
      }
      inner()
    }
    run(add)
    run(mul)

Want:

    3
    4
    2
    3.75

#### Mechanism

#5703 let a hole parameter bound to tagged sets be handed on as each instance's ids. It noted a forward from inside a nested function too (`elabMintSetFwd` in `elabMintHandedNested`), and the tag decision then committed `{add}` and `{mul}`. But `inner` has one body for both of `run`'s instances, and its list element was instanced at the first set, so `run(add)` ran `mul`: it printed `2 3.75 2 3.75`. With the split plan off the same shapes print the same wrong values; with several nested shapes in one program the module is invalid (`expected i32, found f64` inside `apply2`).

| the second instance (`run(mul)`) | runs | **yes** |
| the list (`apply2(h)` in `inner`) | runs | **yes** |
