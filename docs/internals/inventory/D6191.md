### D6191 — a hole lambda or generic forwarded through a hole parameter to a hole parameter nothing reads has no monomorphization pin

**closed 2026-10-17 by lane L3 · runs, prints `4` · was loud emit reject · clause 2 · a hole parameter read only as a bare argument to an un-annotated parameter of a declared function that never reads it counts as unread, through up to eight such hops (`holeParamUnreadIn`, `check_calls.vl`), so [D6112](D6112.md)'s default applies · pin: `tests/cases/functions/hole-lambda-forwarded-to-unread-hole-param.vl` · the generic spelling refuses at the direct spelling too and is [D6213](D6213.md) · found closing [D6112](D6112.md) · filed 2026-10-17 against master `c6cd62ec1`**

Repro:

    function apply(h, x: i32, g) { return h(x) }
    function inc(n: i32): i32 { return n + 1 }
    function outer(g) { return apply(inc, 3, g) }
    const f = (n) => 0 - n
    print(outer(f))
    // vl check: rc 0.  vl run: emitProgram: monomorphize: unsupported argument type for `g` in a call to `outer`

Want:

    4

#### Mechanism

From the ablation only. [D6112](D6112.md)'s default applies when the callee's own body never
names the parameter. `outer` names `g`, handing it on to `apply`, which never reads it, so
`outer`'s parameter is read as used and no call pins it.

#### Close

The witness runs. So do the same call through two forwarding functions and a written `let`
lambda. A callee that does call the parameter still pins it there. The generic spelling
(`neg`) also refuses at emit when it is handed straight to a parameter nothing reads, so it is
not this row's mechanism. It is filed as [D6213](D6213.md).
