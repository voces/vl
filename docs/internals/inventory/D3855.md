### D3855 — a hole lambda written into a binding through another binding's capture cell (`d1 = d2[0]`) takes no peer signature, so it and the cell's other lambdas are lowered at `i32`

**closed (2026-10-08, lane SC) · was check-clean invalid wasm · `r552` of the rv3443 generator, found in review of #3446 · filed 2026-10-08 against master `cc1ee0a89` · pins: `tests/cases/closures/hole-lambda-peer-through-cell-read.vl`**

Repro:

    function mk(x: string) {
      const c = (y) => y + "C"
      const e = (y) => y + "E"
      const g = (y) => y + "G"
      let d1 = c
      let d2 = e
      d1 = d2
      const w4 = (): i32 => { d2 = g; 0 }
      w4()
      print(d1(x))
    }
    mk("a")
    // vl check: rc 0.  vl run: invalid module inside `mk`, `expected i32, found (ref $4)`

Want:

    aE

#### Mechanism

`d2` is written by a closure, so the rewrite boxes it, and `d1 = d2` becomes `d1 = d2[0]`.
`monoAssignedPeerFe` finds the writes that store a lambda by matching the written value
against the lambda, but it only looked through a bare name, never a cell read. So `e`, stored
into `d1` only through `d2[0]`, never took `c`'s signature from `d1`. `g`, whose peer is `e`
through the cell, stayed unpinned with it, and both were lowered at the hole's `i32`. A cell
read now counts as a name read there. The peer rounds (D3851) settle `g` after `e`.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the closure's write (`d2` no longer boxed) | runs | **yes** |
| `d1 = d2` | `e` is left in a cell nothing reads, and is refused loudly (D3851) | **yes** |
| `c` (`let d1 = d2` from the start) | runs | **yes** (the peer that pins) |
| a call through `d2` as well | runs | **yes** (pins `e` by a call) |
| the closure for a nested function | still invalid | no |
