### D6832 — hole functions sharing a list, each called through it with a generic at two types, are refused at emit

**closed 2026-10-18 by lane L1 · runs, prints `3`, `4`, `3`, `4` · was loud emit reject · `vl check` rc 0 · clause 2 · CAPABILITY · the split gives functions sharing a list literal one parameter list, each splitting its hole parameter at the keys all of them are called at, in one order, so a list element keeps one function type · a `const` alias of an element and a call on the functions by name beside it run too · pins: `tests/cases/functions/hole-fns-sharing-a-list-split-together.vl` · found closing [D6792](D6792.md) · filed 2026-10-18 against master `608df323a`**

Repro:

    function add(a, b) { return a + b }
    function apply2(g) { print(g(1, 2)); print(g(1.5, 2.5)) }
    function apply3(g) { print(g(1, 2)); print(g(1.5, 2.5)) }
    const fs = [apply2, apply3]
    fs[0](add)
    fs[1](add)
    // vl check: rc 0.  vl run (master): emitProgram: a generic function is passed to a function value whose parameter type names a type parameter this closure does not bind

Want:

    3
    4
    3
    4

#### Mechanism

From the ablation only. The split rewrote a list element's call only when the list held one
hole function; with two, each splitting its parameter alone, the list's elements would have two
function types, so the split declined and the generic had no instance to choose.
