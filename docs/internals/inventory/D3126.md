### D3126 — `y == null` inside a lambda of a `<T>` or hole instance at a non-null pin is refused at emit

**closed · `== null` and `!= null` fold to their constant when the operand, a read typed at a type parameter or hole, holds a type that admits no `null` at the pin: a lambda's pinned parameter, or a capture read in the frame that declares it · fixture `tests/cases/generics/lambda-null-test-at-pin.vl` · was loud emit reject · clause 2 · 52 cells of the #3276 review's `g3` grid, 156 cells of lane FF's `ff2` grid · the same on master `cc890c9f4` · filed 2026-09-28 against master `cc890c9f4`, closed 2026-09-29 against master `07d414042`**

Repro:

    function f<T>(x: T) {
      print([x].filter((y) => y == null).length)

    // vl check: rc 0.  vl build: emitProgram: bare null needs a struct-typed context

#### Mechanism

The dead-null-test fold (`deadNullTestOperand`) asked only the operand's checked type. In an
instance body the parameter's annotation is re-checked at the pin, but a lambda's body is the
template's, so `y` still reads `T` and the test fell through to lowering `null` itself, which
needs a reference type to name. The fold now also reads the pin: the lambda's own pinned
parameter annotation, or, for a captured name, the enclosing frame that declares it.
