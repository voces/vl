### D17680 — a function returning a record global held at another row than its type's builds a module that fails to validate

**closed 2026-11-26 · runs, prints `1` · fixed on `cov-call-mapdef`: a returned read of a record global is built at the global's storage record (`frsGlobalCellTy`), and the IR holds the cell there (`cellAtStorageRow`) · was check-clean invalid wasm · clause 1 · 1 spelling · filed 2026-11-26 against master `3a7b1df55` by COV-CALL, found writing the record-global storage-row positions**

Repro:

    type J = { f: i32 | null }
    const m = Map()
    m.set("a", { f: 4 })
    const wm: {[string]: J} = m
    const d = { f: 1 }
    const w3 = { k: { x: { f: 7 } } }
    w3.k = { x: m.get("a") ?? d }
    function asReturn() { return d }
    print(asReturn().f)
    // was: vl check rc 0, vl run invalid module inside `asReturn`, expected `#anon1` ({mut i32}), found `J`

Want:

    1

#### Mechanism

`d` is typed `{ f: i32 }`, and that type has a struct row of its own (`w3`'s `x` lays one out),
but legacy stores `d` at `J`'s row, the map's value row, because `?? d` delivers it there. `asReturn`'s
result is declared at the type's own row (`fRetStructIdx`), and nothing converts the stored `J`
back to it. The IR misses `convert record -> record` at the same return. A row copy would break
aliasing (START-2's withdrawn row copy). The fix declares the result at the global's storage row,
as a function returning a hole parameter already has it (D17676's named control):
`frsValuesBuiltRow` and `frsValuesStampRow` read a returned global's `letBindTy`.
