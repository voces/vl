### D3506 — a closure body joining two parameter holes and a `null` drops the null at a record pin

**loud emit reject · open · clause 1 (was invalid wasm on master, now refused at the return) · split out of [D3504](D3504.md), where it was filed for want of an id; not that row's mechanism · found by #3337's review (the `clo` rows of its `g1` grid, `clo__rec_rec`) · filed 2026-10-03 against master `937445a42`**

Repro:

    type Rec = { x: i32 }
    const r7: Rec = { x: 7 }
    function F(k: i32, a, b) {
      const g = () => { if k == 0 { a } else if k == 1 { b } else { null } }
      g()
    }
    print(F(2, r7, r7) == null)
    // vl check: rc 0.  vl run: emit error, "a `null` is returned where this instantiation's result is a non-null record"

Want:

    true

#### Mechanism

A hole is not kept apart inside a lambda: `tyParamOfInnermostBody` answers false under
`lamCheckDepth` (D3357), so the closure's join of `a`, `b` and `null` lets the holes absorb
the null, and at a record pin the lambda's result is a non-null `(ref $Rec)`. The `null` arm
is now refused at the return (`retNullIntoNonNullRef`) instead of emitted as invalid wasm.
The same drop at a box pin (`3`/`"t"`, a record beside `i32`) still runs and answers `false`
for `== null` on the `null` arm: that wrong-value face is unchanged from master. Fix
direction: keep the null join apart inside a lambda BODY (not a pin's re-join of a deferred
return). Doing that alone was tried in #3342 and exposed [D3520](D3520.md) and
[D3521](D3521.md) at the hole spelling, so those land first.
