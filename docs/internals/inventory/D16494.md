### D16494 — under `as% i64` a radix literal tree reads its 32-bit pattern zero-extended or sign-extended depending on the operator

**check-clean silently wrong · clause 1 · open · needs a ruling: [D3053](D3053.md)'s ruling (A) covers a bare radix literal and a chain of negations over one, not another radix tree under `as% i64` · `vl check` rc 0 · the same 32-bit pattern `0xFFFFFFFE` prints `4294967294` spelled `0xFFFFFFFF - 1` and `-2` spelled `0xFFFFFFFF * 2`, so at least one spelling is wrong under any ruling · the oracle skips the unruled trees · found reviewing #8363's `0xFFFFFFFF as% i64` question (that one is the oracle's, fixed in #8367) · filed 2026-11-15 against master `d31ab4440`**

Repro:

    print((0xFFFFFFFF - 1) as% i64)
    print((0xFFFFFFFF * 2) as% i64)
    // master: vl check rc 0, prints 4294967294 then -2

The want below assumes the ruling reads the tree as `as i64` does (T2.4). Under a
32-bit-pattern ruling (E8.4's sign-extend), both lines are `-2`.

Want:

    4294967294
    8589934590

#### Mechanism

Not ablated to a compiler function yet. The pattern on master: a tree whose 64-bit value fits
`u32` and is not a `/` prints that value; one whose value leaves `u32`, or a `/`, prints the
32-bit result sign-extended. Neither reading is a rule. A ruling picks the reading; the fix makes
every operator follow it.
