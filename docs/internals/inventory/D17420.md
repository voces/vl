### D17420 — a null-unit place read as a guarded nullable compare's operand had its read written where it was built, outside the compare's guard

**closed 2026-11-24 by lane S1 · now IR-covered and byte-matched: `RNullOf` carries the read (`nuRead`), written where the null is read · was IR-uncovered: the right operand fell back with `non-stack temp: out of order`, the left was claimed with other bytes · pin: `scripts/capability-probes/matrix/null-unit-read-guarded-compare.matrix.vl` · filed 2026-11-24 by lane S1 against master `838bb284`, unmasked from `tests/cases/lint/deep-record-compare.vl::@start` by the `nullable record eq bare side` close**

Repro:

    type T = { id: i32, tags: string[] | null }
    function f(t: T): boolean { return t == { id: 2, tags: null } }
    print(f({ id: 1, tags: null }))
    // vl run: false.  VL_IR_SHADOW=6 vl build (was): `mismatch unlowered: non-stack temp: out of order`

Want:

    false

#### Mechanism

A field typed `null` holds only `null`. Legacy reads one (`emitNulNoneRead`) as one operand:
the read for its effect, `drop`, then the destination's null. The IR built a drop node where the
read was built and a separate `RNullOf` where it was read. A guarded nullable compare
(`RNulNicheEq`) reads its operands inside the guard. So on the left, the drop landed before the
guard (other bytes); on the right, which is built twice, two drops were pending (out of order). A
record compared with a literal of another shape compares field by field, and the literal's own
`tags: null` field is such a read.
