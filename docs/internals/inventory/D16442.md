### D16442 — a `const` of a call's fresh record beside a held part at a wider record is refused with a message naming one type twice and no field

**closed 2026-11-15 — the witness runs and prints `1` · was: loud check reject · clause 2 · `{x: f64} is not {x: f64}: they store field `` differently` · found with [D16440](D16440.md) · filed 2026-11-15 against master `6adb40099` · closed: `recStoresAgree` (check_fit_rules.vl) counts a stored value whose own record already stores as the list's build as built there; the maker, called once, is built where its call lands (D3444), so the refusal named one type twice · fixture `tests/cases/soundness/record-list-call-part-beside-wider-part-runs.vl`**

Repro:

    function mk() { return { x: 1 } }
    const a = { x: 2.5 }
    const m = mk()
    const l = [a, m]
    print(l[1].x)
    // was: vl check: {x: f64} is not {x: f64}: they store field `` differently

Want:

    1

#### Mechanism

`mk` has one call, so it is built where that call lands (D3444), and `m`'s record is `{x: f64}`
before the list is checked. `recStoresAgree` judges the list binding's stored values: a value is
built at the list's build only as a literal or a kept destination, so `m` was refused onto a
storage equal to its own, by `recRefuseAtOwnRow`, which renders `{x: f64}` twice and finds no
field. A value whose own record stores as the build now counts as built. A later widening write
through the list, or `m` handed on at `{x: i32}`, is still refused.
