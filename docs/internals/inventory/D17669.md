#### Trace (2026-11-28, I8-PREP; parked, coordinator ruling)

- No face that runs instances `pick` per call except the `const r` form: there mono types the call
  `pick("j")` at its use's result through the maker rung (`monoWalkIdentCall`, from
  `elabMakerCallSig`, noted by `fvaMakerCallRows`). A returned `??` is no maker: `fvaOpenMakerCall`
  requires `fvaRetsNamed` (every returned value a lambda or a name), and its comment rules a
  returned choice out on purpose: "built through its own deliveries", the set dispatch.
- The returned `if` (`return if … { inc0 } else { dbl }`) runs that way: its result carries the
  tagged set `{inc0, dbl}`.
- The `??` loses that in two places. (1) `checkBinExprNodeReal` types it the left's non-null face
  when the default fits, so the result's set is the map's `{inc0}`, dropping `dbl`; `joinTys` does
  not union sets either, where `joinArmTys` (the `if`'s) does. (2) With that joined as the `if`
  joins, the call's set is `{inc0, dbl}` as the `if`'s is, but the tag decision leaves it untagged
  (the `if`'s is tagged), and the call stays a plain closure call with no signature. The likely
  reader is the tag decision's `??` arm (`ftJoinOk`, check_fn_tag.vl), which asks the left's
  nullable to carry the whole set (`ftNulOfS`), where a map read of `{inc0}` carries a subset.
- Every directly returned `??` refuses (`r ?? dbl` with `r` a binding, a parenthesised one, an
  arrow lambda's body); the same `??` bound and returned, the `if` it spells, and `dbl` among the
  map's own writes all run.
