### D2301 — a `.map` whose callback is a function VALUE interned no row for a struct result, and since #2897 every read of that result indexed the ref-list tables at -1

**closed · was a compiler trap (`out of bounds array access`, exit 70) · D1666's `?.` live-sites probe · filed 2026-09-24 against master `c2f040366`**

Repro:

    type A = { v: i32 }
    type B = { w: i32 }
    function toB(a: A): B { return { w: a.v + 1 } }
    function go(f: (A) => B, xs: A[]): i32 { return xs.map(f).get(0)?.w ?? 0 }
    print(go(toB, [{ v: 1 }]))
    // vl check: rc 0.  vl run: 2

#### Mechanism

`collectMapFilterUse` (`compiler/emit_collect.vl`) interns the ref-list row a struct-returning
`.map` produces only when the callback resolves to a lifted function entry. A callback
delivered as a parameter or a binding (`xs.map(f)`, `f: (A) => B`) has none, so no `B` row
was interned and `refListSlotOfExpr` found no slot for the result. Until #2897 (63214b516,
D1835) that miss was clamped to slot 0 — the SOURCE list's `A` row — and the `?.` read refused
one step later with `` `?.` field is not on the struct ``, the literal D1666 witnessed. #2897
made the miss `-1` on the premise that every caller tests it; `emitPopGo` indexed
`rlWrapIdx[rslot]` untested, and so did the index read, indexed write, `.push`, `.clear`,
`for` walk, `?.`-over-`.get`, and `emitMapFilter`/`.slice`'s source and result slots. The
other positions (index, push, pop, clear, a `.filter` on the result, a captured closure in a
binding) trapped even before #2897, in `emitMapFilter` itself. The fix interns the row from
the call's own recorded `B[]` when the callback has no lifted entry, and the ten untested
sites now refuse with `a ref list's element row does not resolve` instead of indexing at -1.
