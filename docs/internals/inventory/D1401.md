**closed 2026-09-03 by narrowing the guard to a POSITIVE allow-list of receiver types · was
check-clean invalid wasm, clause 1, `type mismatch: expected i32, found (ref $type)` · ZERO
corpus cells · fixture
`tests/cases/types/coalesce-merged-row-fn-value-beside-method-call.vl` · found 2026-09-03
while re-grading [D1100](#d1100)'s position matrix, by ablating its struct-FIELD cell down to
the ingredient that was NOT the container**

Repro (`vl check` rc 0; deleting the single line `xs.push(1)` makes the same program print
`0`, `true`, `7`):

    function src(p: {r: i32}): {r: i32} | null {
      p
    }
    function rd() {
      const h = src
      const xs: i32[] = []
      xs.push(1)
      print(xs.length)
      print(h({ r: 3 }) != null)
      const g1 = src({ r: 7 }) ?? { r: "s" }
      print(g1.r)
    }
    rd()

#### Mechanism

`anonLeafAnyIndirectCall` asks "could any call in this program go through a function VALUE" —
the one question that makes a funcref dangerous to the `??` row merge, because a `call_ref`
passes arguments no mark can read. It walks every `Call` and its non-`Ident` arm answered YES
unconditionally: `} else { return true }`. A `Member` callee is not evidence of a function
value; `xs.push(1)` is a BUILT-IN method whose target is as knowable as a named call's.

**AND THE VETO'S FALL-THROUGH IS NOT NEUTRAL** — the same fact D1090 recorded for the name
keying. With the merge refused, `?? { r: "s" }` still resolves the `{r: i32}` row by field-name
set and stores a string ref into an i32 slot. So the guard does not decline into safety, it
declines into a miscompile, which is why an over-approximation here costs `runs` cells rather
than optimisation.

The guard is now a POSITIVE allow-list rather than a subtraction: only a receiver the checker
recorded as a `TyArray`, a `TyMap` or a `TyPrim` is admitted, because those carry a built-in
method surface and no closure fields. A STRUCT receiver — `o.f({r: 9})`, a closure-typed field,
which is [D1100](#d1100)'s own first cell — keeps the veto, as do a hole, a union, an `Index`
callee, a `Call` callee and an untyped one.

**THE BLAST RADIUS IS WHY THIS IS FILED SEPARATELY FROM D1100.** D1100 is five CONTAINER
delivery positions; this is every module that uses a list, map or string method ANYWHERE beside
a `??` row merge over a function used as a value — which is to say nearly every real one. The
distilled corpus holds zero cells for it, and D1090's own 26-cell position matrix could not see
it either: every cell in that matrix is method-free.

All three admitted receiver kinds, `--before` this worktree's pre-fix seed and `--after`:

| the method call beside the merge | before | after |
| --- | --- | --- |
| `xs.push(1)` over `i32[]` | **SILENT** | runs `1 true 7` |
| `m.set("a", 1)` / `m.has("a")` over `{[string]: i32}` | **SILENT** | runs `true true 7` |
| `s.slice(0, 2)` over `string` | **SILENT** | runs `ab true 7` |
| `o.f({r: 3})` over a struct (the D1100 control) | SILENT | SILENT — unchanged |
