### D9952 — two records of un-annotated functions at one open record row, handed to one un-annotated parameter whose field call pins them at two types, share one instance

**closed · runs, prints `7.5` `4` · was loud emit reject, `vl check` rc 0, `emitProgram: cannot take the generic function `dbl0` as a value`, clause 2 · found closing [D9731](D9731.md) · present on master `c4fbdc8d1` · filed 2026-10-22 against master `c4fbdc8d1` · closed by keying and rechecking an instance pinned at an open row at that row with each open function field at the type the call's walk pins it (`monoOpenRowPinnedTy` in `monoPinHoleParam`, emit_mono.vl), so each pinned row is its own instance · fixture `closures/hole-fn-records-one-open-row-two-types.vl`**

Repro:

    function inc0(a) { return a + 1 }
    function dbl0(a) { return a * 2.5 }
    function take(a) { return a.f(3) }
    function mk() { return { f: dbl0 } }
    function mk2() { return { f: inc0 } }
    print(take(mk()))
    print(take(mk2()))
    // vl check rc 0.  vl run: emit error: emitProgram: cannot take the generic function `dbl0` as a value

#### Mechanism

Neither argument is a source `monoOpenFnRecSrcPin` can retype to a closed row (a call result),
so each pins `a` at its arena row, and both rows are the one open `#anon` row `{f: (_) => _}`.
The instance key renders the pin's type, so both calls reused the first call's instance, whose
field call has the first record's signature and whose result the first record's function
decides. Midway through the fix of [D9731](D9731.md) the second call ran through `call_ref` at
the wrong type and trapped, or failed validation with a named annotated `dbl0` beside it.
