### D2854 — a closure called inside a hole-parameter function at two pins builds one instance's value into the other's rep

**closed 2026-09-27 — the filed repro prints `7` then `s` · closed by giving each instance of the function its own copy of every call through a hole lambda's binding · identical on master `721781075` · found by the #3220 round-3 review (`r3/K6.vl`) · filed 2026-09-27**

Repro:

    function mk(x) {
      const c = (y) => y
      return c(x)
    }
    print(mk(7))
    print(mk("s"))
    // master: vl check rc 0.  vl run: invalid module inside `mk` — expected (ref $type), found i32

Want:

    7
    s

#### Mechanism

The lambda body was never the shared thing. A lambda bound to an un-annotated `const` is
already instantiated per call like a generic function (`monoWalk` → `monoInstantiate` on its
slot, keyed by the argument's pin), so `c(7)` and `c("s")` got two lambda instances. What the
two instances of `mk` shared was the `Call` node: `monoCloneGenericCalls` copied only calls
whose callee NAME is a generic function, `c` is a value binding, and the later instance's
rename of `c(x)` to `__lambda_0$1` landed on the node both instances read. Cloning every nested
lambda per instance (the brief's design) would not have helped by itself; the call has to be
the instance's own. The close, in `emit_mono.vl`:

1. Calls through a binding of a lambda with a hole parameter — a local, a `const` alias of one,
   or a module-scope one — are copied per instance, and the first instance's call is named too,
   since the value path reads the template's element and result kinds.
2. The copy is typed at the instance's binding and holes, so a `boolean` result prints as one
   ([D2884](D2884.md)).
3. A `const` alias chain is re-spelled to the lambda's binding when it ends at one read
   unshadowed at the call ([D2896](D2896.md)); a call inside a nested lambda to a captured
   binding resolves up the lexical frames.
4. A lambda cloned per instance because it captures a hole, and still carrying hole parameters
   of its own, is instantiated per call like its template.

Pins come only from each call's own argument, so an instance whose call cannot be pinned keeps
master's behaviour for that call, and no instance reads a sibling's clone: lambda instances are
keyed by pin, so two instances share one only at an identical pin. The pulled per-instance pin
(#3231) decided one pin per lambda per instance and failed exactly where this does not — a
shadowed name, and a `string | null` instance beside a `string` one.
