### D4060 — an escaping lambda with no return annotation that reads a captured path narrowing reports two follow-on errors, one naming `<error>` and one naming `''`

**open · loud check reject · the first error is right, the two after it are cascade · found writing `docs/spec/narrowing.md` (lane SPEC) · filed 2026-10-11 against master `98a4ed71b`**

Repro:

    type O = { v: i32 | null }
    function f(o: O): () => i32 {
      if o.v != null {
        return () => o.v + 1
      }
      () => 0
    }
    print(f({ v: 1 })())
    // vl check: rc 1, three errors:
    //   "a function of type `() => <error>` cannot be used as `() => i32` here: …"
    //   "operator '+' is not defined for i32 | null and i32 — 'o.v' is not narrowed inside the function on line 4: …"
    //   "cannot infer a return type for '' — annotate a return type"

Want:

    one error, the second of the three above

#### Mechanism

By the D2407 ruling, the returned lambda does not keep the captured `o.v` narrowing, so
`o.v + 1` is refused. That refusal is right and well worded. The lambda's return type is
then inferred from an expression that failed to check. The failed type goes on to two more
diagnostics: a conversion check at the `return` prints it as `<error>`, and the return-type
inference reports the anonymous lambda by the empty name `''`. With the return annotated,
`(): i32 => o.v + 1`, only the one correct error is reported.

#### Ablation

| variant | outcome |
| --- | --- |
| `() => o.v + 1` returned | three errors |
| `(): i32 => o.v + 1` returned | one error |
| a parameter `x`, `() => x + 1` returned | runs, prints `2` |

#### Grading list

The repro should report exactly the narrowing error. No diagnostic should print
`<error>` or name a function `''`.
