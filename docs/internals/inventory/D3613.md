### D3613 — `==` between a pinned `i64 | f64` join and its `i64` member is refused by the emitter, not the checker

**loud emit reject · clause 2 · found by lane HL's grid (its `eqa` reader at the `i64-f64` pin, 14 cells) · filed 2026-10-04 against master `c473889d1`**

Repro:

    function F<A, B>(k: i32, a: A, b: B) {
      const v = if k == 0 { a } else { b }
      print(v == a)
    }
    const x: i64 = 7
    const y: f64 = 4.5
    F(0, x, y)
    // vl check: rc 0.  vl run: "emitProgram: a numeric union member pair has no operator type"

#### Mechanism

At concrete types the checker refuses `==` over `i64 | f64` and `i64` ("mixes the members f64 and
i64"), the numeric-join ruling's pair rule. Inside a generic body the operands are `A | B` and `A`,
which the template admits, and no pin-time validation re-asks the pair rule, so the emitter's
`emitNumUnionBin` is the first to see the `f64`-`i64` pair. The refusal is the design's; the
checker owes it at the pin, with the `as` fix it gives at concrete types.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `F` concrete over `i64` and `f64` | the checker's refusal | **yes**: the generic body |
| pins `i32`, `f64` | prints `true` | **yes**: the `i64`-`f64` pair |
