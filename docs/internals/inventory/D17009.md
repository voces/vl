### D17009 — an un-annotated lambda written in a record literal's field is not a value-bound hole lambda, so its parameter is refused as uninferable

**closed 2026-11-19 · runs, prints `6` · was loud check reject, `cannot infer a type for parameter x`, clause 2 · fixed in check_match_hoist.vl `hoistRecFieldLambdas`: a record literal's un-annotated field lambda in an un-annotated binding is bound to a hidden `const` ahead of the binding, in its block, so it infers as a bare binding of it does and a call through the field reaches it by name · pin `closures/record-field-hole-lambda-at-every-position.vl` · open neighbours: [D17013](D17013.md) · `cannot infer a type for parameter x` · clause 2 · open · the bare binding `const g = (x) => x * 3` runs as a value-bound hole lambda ([D4019](D4019.md)); one level down, in a record field, the same lambda is refused · positions include [D16998](D16998.md)'s lambda spelling · found tracing D16998 · filed 2026-11-19 against master `818f9c547`**

Repro:

    const v = { f: (x) => x * 3 }
    print(v.f(2))
    // vl check: cannot infer a type for parameter `x`

Want:

    6

#### Mechanism

Only a lambda that is the whole initializer of an un-annotated binding is marked a value-bound
hole lambda (`noteValBindLambda`, check_statements.vl and the pre-pass in check_top_level.vl), so
its un-annotated parameters type as inference holes. A lambda that is a field value of that
binding's record literal is not marked: with no contextual type its parameter types at the error
placeholder (`(TY_ERR) => <error>`, no hole, no set id) and is refused when nothing pins it. Where
a later delivery does pin it, as `xs.push(v)` into a set-typed list does in D16998, the pin closes
it at the binding's closed type, and the record adopts there.
