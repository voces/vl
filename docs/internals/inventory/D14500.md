### D14500 — a generic call whose type parameter a union arm absorbs is elaborated at the checker's `i32` default, not at the instance's binding

**closed · runs, prints `3`, `100`, `100` · was check-clean silently wrong, clause 1 · closed with [D14572](D14572.md): an instance call's binding starts from the template's recorded binding under the instance substitution (`bindTemplateRow`, check_calls.vl), so the checker instance `elabDemandFrom` takes is `len<T = string>`, the demand's own binding · fixture `generics/enclosing-param-into-generic-union-annotated-let.vl` · filed 2026-10-26 against master `8fb015d29`**

Repro:

    function len<T>(f: () => T | string) {
      const t: T | string = f()
      if t is string { t.length } else { 100 }
    }
    function outer<U>(x: U) { print(len(() => x)) }
    outer("abc")
    outer(2.5)
    outer(7)

Want:

    3
    100
    100

#### Mechanism

At `len(() => x)` inside `outer` the argument's type `() => U` meets `() => T | string`; the
template-level check leaves `T` unbound and binds it by the D4551 default, `i32`. Mono's demand
for the `outer<string>` instance binds `T = string`. `elabDemandFrom` prefers the checker's own
instance (`elabCkUsable`) whenever it takes the pins, so `len`'s body is elaborated with
`t: i32 | string`, the `is string` test is lowered against a box whose string arm the value
never enters, and `outer("abc")` prints `100`.

Step 7 slice 3's `letBindRepClaims` records each such checker-instance parameter
(`elabGuessNote`) and declines to read a binding's rep through it (`elabKeyReadsDefault`), so the
rep path does not make it worse; the wrong value is the elaboration's, and the fix is for the
demand's binding to win over a defaulted checker instance.

#### Grading list

`outer(2.5)` and `outer(7)` are the controls that already print `100`; an annotated
`len<string>(() => x)` twin.
