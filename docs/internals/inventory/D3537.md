### D3537 — a record type that declares one field twice is accepted, and a literal at it is refused naming an empty field

**loud check reject · open · needs a ruling: the D3484 ruling covers object literals, not type declarations · found 2026-10-03 while closing D3484 · filed against master `f6e17953b`**

Repro:

    type P = { a: i32, a: i32 }
    const p: P = { a: 1 }
    print(p.a)
    // vl check: this object literal sets , which P does not declare: ...

#### Mechanism

A record type's field list is not compared with itself, so `type P = { a: i32, a: i32 }` lays
out two fields named `a`. A literal giving `a` once then fails the literal-shape check against
the second slot, and `objDroppedFieldList` renders the mismatch as an empty name. Any literal
giving `a` twice is now refused by D3484's ruling, so no literal can build a `P` at all. With
no literal at the type (a parameter only, `function f(p: P) { … }`), the declaration checks
clean; a union arm declaring a field twice (`{ k: "x", a: i32, a: i32 } | { k: "y" }`) also
checks clean and runs when only the other arm is built.

Question for the owner: is a field declared twice in a record type a check error at the
repeated field, as a repeated key in a literal now is? Recommendation: yes, the same wording
("field `a` is declared twice in this type (first at L:C)"), spanning the repeated field name,
at `type` declarations, inline record annotations and union arms alike. It is the same slip,
and today the type is unusable without saying why.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| no literal at `P` (a parameter `p: P` only) | check rc 0, runs | the declaration alone is accepted |
| `type P = { a: i32, a: string }` | check rc 0 with no literal | the two fields need not agree |
| a union arm `{ k: "x", a: i32, a: i32 }`, only the other arm built | check rc 0, runs | no |
| `type P = { a: i32 }` | runs | control |
