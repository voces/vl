### D8302 — a literal-building function whose calls land on different field storage is refused beside a declared record of its fields

**closed 2026-10-20 · runs, prints `4` `4` · was loud check reject · clause 2 · a call delivered nowhere that is only read for a field (`k.f`, or an un-annotated `const` whose every use is a field read) is served by the build at a landing that only adds `null` to a field (`recReadInPlace`, `recNullWidened`, `check_fit_rules.vl`); a call stored anywhere else still refuses the landing · pins: `tests/cases/soundness/fresh-call-read-in-place-beside-declared-row.vl` and its error twin `error-fresh-call-stored-beside-declared-row.vl` · matrices `fresh-call-beside-unlanded-call-and-declared-row` and `unlanded-call-beside-call-into-wider-record` · present on master `82bf510a3` and `02d8f4c21` · found closing [D8201](D8201.md) · filed 2026-10-20 against master `82bf510a3`**

Repro:

    type II = { f: i32 }
    type J = { f: i32 | null }
    function mk() { { f: 4 } }
    const xj: J = mk()
    const k = mk()
    print(xj.f ?? 0)
    print(k.f)
    // vl check: {f: i32} is not J: they store field `f` differently ... only a fresh record widens

Want:

    4
    4

Runs, and prints `4` `4`.

#### Mechanism

`mk` is one function body, so it builds one record row. D8201 lets several calls share the
build at the destination when every call is delivered to the same field storage
(`recSitesLandAt`, check_fit_rules.vl). Here the second call is delivered nowhere: `k` reads
`mk`'s own row, so the build at `J` cannot serve it. `mk`'s literal stays at its own row, `II`
names that row, and `recBuiltAtDeclared` refuses the delivery into `J`. Running it needs either
a build per landing (a clone of `mk` for each storage) or `k` typed at the row it is built at.

Why the unused `type II` decides the outcome: emit maps an anonymous record to a declared row
by its field names. Without `II`, `J` is the only declared record with field `f`, so `mk`, `k`
and every `{f: i32}` value are built at `J` and the program runs by accident. With `II`
declared, `{f: i32}` maps to `II`'s row exactly, so a `{f: i32}` destination — a list, a record
field, a map value, an annotated return — is built at `II` while `mk` builds at `J`.

The close takes neither of the two routes the row first named. A build per landing (a clone of
`mk` per storage) lives in `emit_mono.vl`, and `k` typed at the row it is built at needs emit
to carry the value's row into every container built around it. Both are emit work outside this
lane. What the checker can say alone is narrower: a call delivered nowhere and read only for a
field never reaches a `{f: i32}` row, because a field read takes the field out of whatever row
`mk` built. So `recSitesLandAt` serves such a call from the build at `J` (`recReadInPlace`),
and refuses the landing as before when the call is stored, returned, aliased, captured or
handed to a method. A blanket relaxation (every unqueued call served) was tried first and made
`[k]`, `{ a: k }`, `const w = { f: mk() }` and an annotated `return mk()` check-clean invalid
wasm: eight new SILENT cells in `unlanded-call-beside-call-into-wider-record`.

The serving is limited to a landing that only widens a field to `T | null` (`recNullWidened`). A
numeric widening is excluded, because there the field read sees the row it is built at: with
`type R = { v: f64 }`, `const d1: R | string = mk1(7)` and `const e1 = mk1(3)`, serving `e1`
from the build at `R` printed `e1.v / 2` as `1` instead of `1.5`
(`tests/cases/soundness/record-fresh-call-into-union-destination.vl`). Calls landing on `{ f: f64 }`
beside a field-read call therefore still refuse, as on master.
