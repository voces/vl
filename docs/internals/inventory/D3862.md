### D3862 — a hole lambda written into a binding that is then delivered to a typed function parameter is not instantiated at that parameter's signature

**closed (2026-10-08, lane SC) · was loads then traps · found in review of #3453 (`rv3453-probes/r1.vl`) · filed 2026-10-08 against master `67ff2a485` · pins: `tests/cases/closures/delivered-alias-pins-written-lambda-renamed.vl`, `tests/cases/closures/delivered-alias-pins-written-lambda.vl`, `tests/cases/closures/delivered-alias-annotated-let-and-return.vl`, `tests/cases/closures/delivered-alias-function-scope.vl`**

Repro:

    const c = (y) => y + y
    const e = (y) => y + y + y
    let d = c
    function mk(f: (y: i32) => i32, n: i32) {
      print(f(n))
    }
    function w(): i32 { d = e; 0 }
    w()
    mk(d, 4)
    print(e("s"))
    // vl check: rc 0.  vl run: indirect call type mismatch at `mk(d, 4)`, exit 70

Want:

    12
    sss

#### Mechanism

D3857 gives a binding one signature from the calls through it and instantiates each lambda
written into it by name at that signature. A delivery of the binding is no call, so `mk(d, 4)`
recorded nothing: `e` was built only at the `string` its own call takes, and `f(n)` reached it
at `i32`. With the parameter named `d` the program ran only because `d(n)` in `mk` was read by
name as a call through the module's `d`, the reading D3843 corrects. A delivery to a typed
function parameter, to an annotated function-typed binding or at an annotated function-typed
return is now recorded as a call at that annotation's signature (`monoNoteBindDelivery`), and
counts as one where D3857 asks whether the binding is called.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the write (`w()` and `function w`) | runs, `8` and `sss` | **yes** |
| `e`'s own call at `string` | runs, `12` | **yes** |
| the parameter's name apart from the binding's (`mk(d: …)`) | runs on master by the name read | **yes** |
