### D16365 — an un-annotated parameter handed `[]` and pushed two records of an empty-list field builds that field at `i32` where a later push stores `f64`

#### Mechanism

Each list method called on the hole `a` is checked against a list whose element is a hole
derived from `a`, so both pushes deliver their record into that hole, never into the first
push's record `{ys: T1[]}`. The second record's `ys: []` (T2) was linked to nothing: T1 pinned
`f64` and T2 defaulted to `i32`. A record written to a hole receiver's derived element, by a push
or an index store, now links each open list field to the first such record's (`holeElemRecLink`,
over stage 2c's hole union), so the pin solves both. Fixture:
`tests/cases/closures/hole-param-two-records-empty-list-field-pinned-once.vl`.
