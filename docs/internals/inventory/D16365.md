### D16365 — an un-annotated parameter handed `[]` and pushed two records of an empty-list field builds that field at `i32` where a later push stores `f64`

**check-clean invalid wasm · `type mismatch: expected (ref $type), found (ref $type)` · clause 1 · the parameter annotated, or one record pushed, runs; the same body over a named `[]` is a loud check reject · found grading `empty-list-shared-record.matrix.vl` (cell `argument`, un-annotated) · filed 2026-11-14 against master `b45a06ef` · open, a stage-2b acceptance row of the slot-store plan, with `hole-param-record-empty-list-field.matrix.vl`**

Repro:

    function take(a) {
      a.push({ ys: [] })
      a.push({ ys: [] })
      a[0].ys.push(0.5)
      print(a[0].ys[0])
    }
    take([])
    // vl check: rc 0.  vl run: invalid module inside `take`

Want:

    0.5

#### Mechanism

Each list method called on the hole `a` is checked against a list whose element is a hole
derived from `a`. Both pushes therefore deliver their record into a type variable, never into
the first push's record `{ys: T1[]}`. So the second record's `ys: []` (T2) is linked to nothing:
T1 is pinned `f64` by `a[0].ys.push(0.5)`, T2 defaults to `i32`, and the instance builds two
record rows. The demanded list is now one per hole, as its map is, but the element stays a type
variable at check. A later write would need to read that element through its solution, the
first record, which stage 2b gives a hole once `tyPinElem` solves it.
