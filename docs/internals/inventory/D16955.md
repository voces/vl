### D16955 — an un-annotated `let x = null` filled only by a function declared before it keeps the type `null`, so every read yields `null`

**check-clean silently wrong · clause 1 (`vl check` accepts the program, and it prints `null` where `5` was written) · open · found by grading every capability-matrix template for WRONG cells (`null-let-read-before-fill.matrix.vl`, the `argument` cell, annotated face) · filed 2026-11-18 against master `8168bc374` by lane F2**

Repro:

    function take() {
      x = 5
      print(x)
    }
    let x = null
    take()
    // prints `null`

Want:

    5

#### Mechanism

The flow-sensitive `let` rule (DECISIONS.md, "A read of a `let` takes its most recent write's
type") widens an un-annotated `let x = null` by its later writes. A write inside a function
declared ABOVE the `let` is not counted, so the binding stays typed `null`. The write `x = 5` is
then stored as a `null` and every read, inside the function or at module level, yields `null`.

#### Ablation

| spelling | outcome | needed? |

| `let x = 1` (a number, not `null`) | runs (`x + 1` prints `6`) | the `null` initializer: **yes** |
| the `let` declared before `take` | prints `5` | the function declared first: **yes** |
