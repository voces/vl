#### Mechanism

The checker leaves the call's result an unconstrained hole: in `p4`, `const v = run(1.5)` accepts
`const w: string = v`. A destination that pins it (`const v: f64 = run(1.5)`) runs and prints `3`;
an unpinned one (`print(run(1.5))`) is written at the i32 a hole defaults to while the value is
`f64`. The lambda's result is `app(h, x)`'s, a generic call over the captured hole function `h`;
the same lambda calling `h(x, x)` itself is typed and runs. Not fixed by D17641's built-rep keying
(#10333): the argument is a scalar, not a storage row.

Trace (I8-PREP, 2026-11-28; the one-instance face landed from branch `d17664-call-key`). The holdout
`closures/hole-typed-closure-call-at-key-scalar-positions.vl` refuses its bound position
(`const v = run(4)`, `local rep unsup`) for one reason: the call has no type a reader can take.
`callRefPlainKey` is "" for it (`callRefPlainTail`'s lift exit), because `run` is lambda-lifted
and `callRhs` builds it as a direct call of the lifted lambda (`directCallAt`); `exprTyOf`'s call
rung only resolves a callee declared as a function, so it answers the hole. The printed position
builds because the print operand is built first and reads the direct call's own result. The fix
decides the target once per call node (`directCallPosOf`: lifted, capture-free lambda, or named
function, as `callRhs` routes it), the local reads its initializer's `exprTyOf`, and an open read
of a scalar the IR holds closed reads that variable (`storedVarOf`): with one instance of the hole
function the bound and arithmetic positions then run. With two instances the second's `run` is
not lifted (`cloLiftCalleeOf` -1 in that frame) and its closure call exits on `exprNulClosure`, so
it still refuses; that frame's lift decision is instance keying (COV-START's 2b-2, coordinator
routing), and this row stays open on the two-instance witness. The one-instance face is pinned by
`closures/bound-call-of-lifted-lambda-over-hole-fn-one-instance.vl`.
