### D3451 — a list literal and `??` still widen two runtime numbers of different types instead of joining them apart

**closed 2026-10-03 · was runs today and must keep running, pending an owner ruling · ruled 2026-10-03 (A): `??` and list literals join runtime numbers as a union, as `if`/`match` arms do since #3327 · fixtures `tests/cases/numerics/coalesce-joins-runtime-numbers-apart.vl` and `tests/cases/numerics/list-literal-joins-runtime-numbers-apart.vl` · filed 2026-09-30 against master `028dedb33`**

      const xs = [x, y]

#### Mechanism

The ruling's lane joined apart the arms of a value `if` or `match` and an inferred return set
(`joinArmLit`, `inferRetJoin`); a list literal's element join (`checkArrayLitNode`) and the `??`
result (`assignableExpr(default, inner)` then `joinTys`) still took `joinTys`' widening. The close
routes both through `joinArmLit`: `coalJoinApart` for a runtime default (a literal default still
adapts), `coalHoleJoin` for the same join a hole's pin resolves, and `listJoinApart`, which joins
the runtime elements apart and then lets each literal element adapt to that join, so element
order does not change the type. The emitter reads the box where it had read an atom: the `??`
result's atom kind (`coalesceAtomKind`), a record field's list code when the literal's first
element is a number literal (`anonFieldCodeSyn`), and a left-grouped `??` chain's re-associated
links (`emitCoalesceGo`).

Three positions keep master's widening, each because joining apart there reaches a defect the
lane did not fix: a `??` in a body that declares type parameters ([D2562](D2562.md)), a list
literal with a literal element in a generic or hole body ([D3534](D3534.md)), and a list with a
nullable runtime element outside one ([D3535](D3535.md)).
