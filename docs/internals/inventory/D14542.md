### D14542 — both variables of a two-variable `for … in` share one declaration node, so a rewrite that moves the loop tells them apart by name

**runs today and must keep running · a name pick in the binder audit, owned by its deletion · filed 2026-10-27 against master `a22130bcc`**

Repro:

    function pick(b: boolean): i32[] | string[] {
      if b { return [7, 8] }
      ["x", "y"]
    }
    for v, i in pick(true) {
      print(i)
      print(v)
    }
    const mi = Map<string, i32>()
    mi["a"] = 3
    const m: Map<string, i32> | Map<string, string> = mi
    for k, w in m {
      print(k)
      print(w)
    }

Want:

    0
    7
    1
    8
    a
    3

#### Mechanism

The parser gives `for a, b in xs` one declaration node, the `ForIn`, for both variables, so
`identDeclOf` answers the same id for a read of `a` and a read of `b`. The list-union and
map-union for-in rewrites (`luForInAt`, `lmForInAt`, check_statements.vl) move each variable to
its own fresh declaration, and `identRedirectLoop` (symbols.vl) can only pick which one a read
means by comparing the read's name with the second variable's. That is a name pick standing in
for a declaration id, the same shape as the ~80 `fiVar2` sites that compare `decl == ForIn` and
then the name.

Close: the parser mints the second variable its own declaration node, readers compare decl ids
only, and `identRedirectLoop`'s name argument, the `fiVar2` name compares and the audit's
name split are deleted. The witness above is the program that must keep running across it.
