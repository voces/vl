### D5760 — a module's stable id is keyed on its path relative to the CLI's cwd, so one module has a different merge suffix per working directory and per runtime

**runs today and must keep running · the id key, not the program's output · filed 2026-10-17 against `s5-parse-arena` (S5 step 2)**

Repro:

    // file: lib.vl
    export function twice(n: i32): i32 { return n * 2 }
    // file: main.vl
    import { twice } from "./lib"
    print(twice(21))
    // vl run: prints 42 from every working directory. The defect is in `--names`:
    //   cd sub && vl build main.vl --names   → twice$m1503105556
    //   vl build sub/main.vl --names         → twice$m1742982019
    // without --names the two builds are byte-identical.

#### Mechanism

`modIdKeyOf` (driver.vl) hashes the module's normalised path made relative to `vlCwd`, the
working directory the Rust host stages. A key that is not under the cwd stays absolute, and the
LSP stages no cwd, so its keys are absolute too. The same file therefore has one id per
directory a build is launched from and another in the editor. Emitted code does not depend on
the id; names, and any per-module cache keyed by the id (S5's check and parse caches), do. The
right key is the path relative to a root found from the MODULE itself: the nearest ancestor
holding a marker that already exists (`deno.json`, `package.json`, `.git`, the set
`lsp/src/moduleGraph.ts` `ROOT_SENTINELS` uses). A root found from the entry would make a
library shared by two projects key differently in each, which is the importer-dependence S5
removes. The guest cannot stat files, so the host has to stage each module's root beside its
key (Rust `stage_vl_root_and_cwd` and the LSP's module commit).

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| `--names` | the two builds are byte-identical | **yes** |
| launching both builds from one directory | one suffix | **yes** |
