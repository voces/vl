### D14000 — an `if` join in a generic body whose list-literal arm comes first does not adapt the literal to the pin

**closed 2026-10-26 — now prints `1` `2.5` · was check-clean invalid wasm, clause 1 · `joinTys`'s last rung returned whichever arm was first when each side was assignable to the other, and inside a generic body a type parameter's list is assignable both ways, so `[1, 2, 3]` first typed the join `i32[]`; the rung now takes the open side in either order, which also deletes `tpIfBindTy`, the binding-side patch that re-typed a non-numeric collapse · found closing [D4884](D4884.md), its arm-order mirror · filed 2026-10-26 against master `935da52aa`, pre-existing · pin: `tests/cases/generics/type-param-list-join-literal-arm-first.vl`**

Repro:

    function g<T>(t: T, b: boolean) {
      const v = if b { [1, 2, 3] } else { [t] }
      print(v[0])
    }
    g(2.5, true)
    g(2.5, false)
    // vl check: rc 0.  vl run: the emitted module failed to validate inside `g`

Want:

    1
    2.5

#### Mechanism

`ifTailBankValTy` joins the arms through `joinArmLit` into `joinTys`. Its final rung asked
`assignable(b, a)` first and returned `a`, so for `i32[]` beside `T[]` (both directions hold in
the body) the first arm won. With `T[]` first (D4884's spelling) the template typed the join
`T[]` and each pin re-joined it; with the literal first it was `i32[]`, and the pin built an
`i32[]` where `f64[]` was stored. The rung now prefers the side holding a type parameter when
the other side holds none and fits it back.
