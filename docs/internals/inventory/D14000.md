### D14000 — an `if` join in a generic body whose list-literal arm comes first does not adapt the literal to the pin

**check-clean invalid wasm · clause 1 · found closing [D4884](D4884.md), its arm-order mirror · filed 2026-10-26 against master `935da52aa`, pre-existing (it fails validation before and after D4884's close)**

Repro:

    function g<T>(t: T, b: boolean) {
      const v = if b { [1, 2, 3] } else { [t] }
      print(v[0])
    }
    g(2.5, true)
    g(2.5, false)
    // vl check: rc 0.  vl run: the emitted module failed to validate inside `g`

Want:

    1
    2.5

#### Mechanism

Not yet ablated past the table below. D4884's spelling, with the type parameter's list first
and the literal second, runs at `T := f64` both un-annotated and annotated `const v: T[]`, so
the literal adapts to `f64[]` there. With the literal first, the annotated twin is refused by
the checker at the pin (`i32[] is not f64[]: a container never widens implicitly`), so the
literal arm is typed `i32[]` before the join sees the parameter's arm. The checker's arm join
depends on arm order; the un-annotated spelling is predicted to run once it does not.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| arms swapped, `if b { [t] } else { [1, 2, 3] }` (D4884) | runs, `2.5` `1` | **yes** (the literal arm first) |
| annotated `const v: T[] = …` | loud check reject at the pin, `i32[] is not f64[]` | no |
| the direct spelling `t: f64` | runs, `1` `2.5` | **yes** (the type parameter) |
