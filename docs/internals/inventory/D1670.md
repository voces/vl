### D1670 — `?? d` over a `?.` whose receiver is a CALL refuses, because the lowering re-reads the receiver instead of staging it

**loud emit reject · filed 2026-09-05 against master `dcea29414` · found while closing D1667 ·
clause 2: the checker accepts the program and `optRecvReReadable` is the only thing that stops it**

Repro:

    type B = { y: i32 }
    function mk(): B | null { { y: 7 } }
    print(mk()?.y ?? 0)
    // vl check: rc 0.  vl run: emit error,
    // emitProgram: `??` over this nullable value is not supported yet — narrow it first

#### Mechanism

`emitOptMemberValue` gates on `optRecvReReadable`, which admits a bare name and a `.`/`?.`
chain of names and nothing else, because the fused `?? d` shape emits the receiver once for
the null test and again for the field read. A call is not re-readable, so the gate declines
and the `??` falls through to the generic nullable arm, which has no rep for this value.

The refusal names a real hazard and the fix is not to widen the gate: the receiver has to be
staged in a scratch local first, the way `emitCallRef` stages a closure and `unionAsSlot`
stages a union operand. Then `optRecvReReadable` is about whether staging is NEEDED, not
about whether the program is legal.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the inline call (`const t = mk()` then `t?.y ?? 0`) | runs, prints `7` | **yes** |
| the `??` (`mk()?.y == null`) | runs, prints `false` | **yes** |
| the call through a VALUE (`const g = mk`, `g()?.y ?? 0`) | refuses identically | no |
| the annotation (`const g: () => B \| null = mk`) | refuses identically | no |

#### Grading list

D1671 is the other half of the same re-read: where the leaf field is itself a nullable
struct, the `== null` spelling does not refuse — it emits the receiver twice and runs it
twice. A staging local closes both, so grade D1671's witness with any fix here.
