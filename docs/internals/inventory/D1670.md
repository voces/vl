### D1670 — `?? d` over a `?.` whose receiver is a CALL refuses, because the lowering re-reads the receiver instead of staging it

**closed 2026-09-05 — the witness prints `7` · was a loud emit reject · filed 2026-09-05
against master `dcea29414` · found while closing D1667 · fixture
`tests/cases/expressions/optchain-call-receiver-once.vl` · matrix
`scripts/capability-probes/matrix/optchain-call-receiver-coalesce.matrix.vl`**

Repro:

    type B = { y: i32 }
    function mk(): B | null { { y: 7 } }
    print(mk()?.y ?? 0)
    // was: vl check rc 0, then emitProgram: `??` over this nullable value is not
    // supported yet — narrow it first. Now prints 7.

#### Mechanism

`emitOptMemberValue` gated on `optRecvReReadable`, which admits a bare name and a `.`/`?.`
chain of names and nothing else, because the fused `?? d` shape emits the receiver once for
the null test and again for the field read. A call is not re-readable, so the gate declined
and the `??` fell through to the generic nullable arm, which has no rep for this value.

The gate is gone and the receiver is staged instead: `optChainStagesRecv` decides whether the
chain's base needs the frame's `(ref null struct)` stash, and `emitOptRecvBase` tees it in on
the first read and casts it back to the base's own struct row on every later one. So
`optRecvReReadable` now answers whether staging is NEEDED, not whether the program is legal —
its refusal literal is gone from the compiler.

The standalone value spelling reached the literal directly (`const v = mk()?.y`, `vl check`
rc 0 then `emitProgram: `?.` needs a re-readable receiver`) and runs too.
