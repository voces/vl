### D1794 — a nested CAPTURING function held in an ARRAY has no element name, because the literal's recorded element type rides the enclosing frame's hole and a hole renders as nothing

Repro:

    function o(n) {
      function k(x: i32) { return n }
      const fs = [k]
      return fs[0](1)
    }
    print(o(2))
    // vl check: rc 0, "Checked 1 file, no errors."

#### Mechanism

Measured, one accumulating `emitFail` probe per build on scratch seeds, three programs that
differ in one ingredient each. At `arrLitIsRef`, the witness reads `refarr=0 slot=0 kind=-1
rlLen=0` — **the whole ref-list table is empty**, so no row was interned for `[k]` at all —
while the capture-free and annotated-parameter twins both read `refarr=1 kind=5
elemName=[((i32)=>i32)] rlLen=1`. One rung deeper the split is exact: the array's recorded
element is `TyFunc` in every one of the three, and only its RENDER differs —
`ELEM nP=1 ret=54 rk=TyVar tv=[?o.0] pin=0 pinNm=[i32] elemNm=[]`. `k` captures `n`, so its
result is the enclosing frame's inference hole; `tyToNameGo`'s `TyVar` arm renders "" by
design, `nodeArrayElemName` hands that "" on, and `arrElemIsClosureTy`'s emptiness gate turns
the checker's decline into "not a closure". The literal falls to the i32 list, nothing interns
a kind-5 row, `exprIsClosure` over `fs[0]` answers false, and `emitCall` refuses.

The hole is PINNED, and that is the fix: `pinnedHoleTyOf(?o.0)` already answers `i32` here. The
element at this instance is the recorded signature with each hole at its banked pin
(`pinResolvedFnTy`), consulted only where the direct render declined, so nothing that renders
today changes. A hole two calls pinned differently banks `-2` and the refusal stands — one
shared literal node cannot carry two rows, which is [D1816](D1816.md).
