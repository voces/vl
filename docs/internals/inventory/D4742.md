### D4742 — `tyIsArray` answered no for a union of lists whose members render one list

**closed 2026-10-14 — the witness prints `3` and `1` before and after · `tyIsArray` (now in `compiler/tyquery.vl`) answers a multi-member union a list when every member spells the first's list, the collapse `tyToNameGo`'s union arm makes when it drops duplicate member renders, so `scripts/twin-agreement.vl --twins arr` reads 0 disagreements where it read `DISAGREE arr i32[] twin=0 orig=1` · instrument-only: the twin's one consumer (the D1822 map-index narrow in `emit_classify.vl`) moved no program · filed 2026-10-14 against master `3a8eb2b61`**

Repro:

    type K = 0 | 1
    const a: i32[] | K[] = [1, 0, 1]
    if a is i32[] { print(a.length) }
    const b: i32[] | i32[] = [1]
    print(b.length)

Want:

    3
    1

#### Mechanism

`i32[] | K[]` over a numeric literal union, and `i32[] | i32[]`, are two-member `TyUnion`
rows whose members both render `i32[]`: a numeric literal union softens to `i32` inside a
list, and the renderer drops a member whose spelling it already holds. The union therefore
renders `i32[]`, and an inline binding of it is a plain list (`is i32[]` folds to a
constant). The type-taking twin returned false for every union of more than one member, so it
disagreed with `nameIsArray` of that render. The render is the rep here: a structural `is`
(D3885) has nothing to tell `i32[]` and `K[]` apart by.
