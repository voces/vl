### D1593 — a start-function BLOCK binding claimed a same-named read from a sibling top-level scope

**closed · filed 2026-09-04 against master `83db028a` · consumer report VL-042 (glean, `/home/verit/glean/docs/vl-issues.md`)**

Repro:

    type E = { msg: string }

    function pick(): i32 | E { return 7 }

    for n in 0 to 1 {
      let c = n
      c = c + 1
      print(c)
    }

    if true {
      const n = pick()
      if n is E { print(0) } else { print(n) }
    }
    // before: vl check rc 0; vl run -> invalid module,
    //   "type mismatch: expected i32, found (ref $type)"
    // after:  1 2 7

#### Mechanism

Every module's top-level statements are merged into ONE wasm start function, so a `const n =
pick()` declared inside a top-level block is a start-function LOCAL, not a wasm global.
`globalLetOfSidIn` guards the module-global rung with `identBoundInFrame` (D705) so a shadowed
read cannot be claimed by a global of the same name; the block-let rung, `startBlockLetOfSid`,
had no such guard — it ran `parentLetOfSid` over EVERY top-level statement and returned the
first `LetDecl` with that name, from any scope in the frame.

So the `for n in …` body's read of `n` was handed the union `const n` from a SIBLING block.
`letUnionNameOf` then typed `let c = n` as the kind-4 union, and `emitAssign`'s union arm
boxed the right-hand side: `(local.set $2 (struct.new $1 (i32.const 1) (struct.new $2 (i32.add
…))))` into an `i32` slot. `vl check` returned 0 and the engine refused the module. After the
fix the same line is `(local.set $2 (i32.add (local.get $2) (i32.const 1)))`.

The fix: at module scope the LIVE lexical binding outranks the name scan, and the read denotes
that slot's own `localDeclIx`. A loop variable pins no `LetDecl` and so declines. That also
stops the scan handing one sibling block's `const r` to another's — asking only "is the name
covered?" is NOT enough, and a first candidate that did exactly that turned
`tests/cases/unions/module-block-union-binding.vl` (twelve sibling blocks, all binding `r`)
red. Inside a function nothing changes: the caller's own `parentLetOf` arm has already run.
A scope-less pass (`localNames` empty) keeps the scan it had, because under-answering THERE is
an un-reserved scratch frame — the residue below.

#### Ablation

Held fixed: the `for` loop at module scope, the union-returning `pick`, the block.

The last six rows are the SECOND mechanism the collision reaches and are NOT closed here — see
the grading list. They print `unknown local N: local index out of bounds` (or `uninitialized
local: 0`), never this row's message, and they graded the same before and after this fix.

#### Grading list

`tests/cases/scope/start-block-let-shadowed.vl` (both the inferred and the annotated face of
the covering binding, plus a read from INSIDE the block, which must keep unboxing) and
`tests/cases/modules/start-block-let-shadowed-cross-module/` (the consumer's own shape: the
loop and the block in different modules).

RESIDUE, still open and needing its own row — the scratch DETECTION half of the same
collision. `emitStartFnCode` runs `collectStartLocals` and then `startFnDetectScratch` with the
scope stack empty, so `declaredSlotOf` falls back to a flat first-match-by-name scan over
`localNames`. With two start-function locals of one name that scan picks the wrong slot, the
string-op / map / push frames go unreserved, and the body then `local.set`s into locals the
vector never declared:

    type E = { msg: string }
    function pick(): i32 | E { return 7 }
    for n in 0 to 1 { print(n) }
    if true {
      const n = pick()
      if n is E { print(n.msg) } else { print(2) }
    }
    // vl check rc 0; vl run -> invalid module,
    //   "unknown local 3: local index out of bounds"

Adding any unambiguous string op at top level (`const pad = "x" + "y"`) makes that program run,
which is what identifies the missing frame. A fix has to make the detection resolve names with
the emit pass's scope discipline, or reserve conservatively under an ambiguous name; neither is
this row's change. It is standing in `scripts/capability-probes/start-block-shadow-scratch-frame.vl`
so it is re-graded by the probe runner rather than only remembered here.

SECOND RESIDUE, and NOT this family — the consumer's earlier spelling of VL-042, identical
except that the two `Buf`-taking helpers' buffer parameters are un-annotated. It refuses with a
different message in a different function — ``src/checksum.vl:42: … inside `crc32Continue$m8`:
type mismatch: expected (ref $type), found i32`` — and grades identically before and after this
fix. Not minimised: an un-annotated buffer parameter alone, with a module-scope table read and
the same body shape, runs.
