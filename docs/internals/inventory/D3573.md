### D3573 — a std generic instance's compound-statement `vl-src` rows name the caller's file and line

**runs today and must keep running · the defect is in the `--names` line table, not the program's output: the instance's simple statements are anchored in `std:array`, but its loops and `if`s are anchored at the caller's last line · found by the #3351 review · filed 2026-10-03 against master `3b9319528`**

Repro:

    import { sort } from "std:array"

    const xs = [3, 1, 2]
    sort(xs, (a, b) => a < b)
    print(xs[0])
    // prints 1. With `vl build --names`, the `vl-src` rows inside `sort$m1` read
    // `std:array` 156, 157, 160… for simple statements, while every enclosing loop or
    // `if` reads file 0 (`srt.vl`) line 5, col 12: a position past the end of `print(xs[0])`.
    // A trap in that range reports the caller's file.

#### Mechanism

Not yet ablated. A guess: `emitFnSpanTokIx` anchors kind-5 rows at `stmtAnchorTokIx(node)`, and a
compound statement in a monomorphized clone carries a node minted after parsing. Its anchor
token is then the EOF token of the entry module, the same failure `monoOrigNodeOfSlot` already
avoids for function rows.

#### Grading list

Any generic std function holding a loop or `if`: `sorted`, and `map`/`filter` over a lambda.
The un-annotated and the annotated element type. A user-module generic too, to see whether the
fault is std-specific.
