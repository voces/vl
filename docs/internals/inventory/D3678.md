#### Mechanism

A VL record is a shared WasmGC struct, so `j.rot = qnorm(…)` stored a reference to a fresh
`Q` box, and the multi-value step (D3625) could not remove it: it removes a record only
where every use reads fields, and a store is not one. The host's inline-record step
(`scripts/vl-host/src/inline.rs`, run before the multi-value step) now replaces a parent's
field of a record type that nothing can tell from a copy — never written, never compared by
identity, a leaf of the subtyping order, unable to reach the module boundary — with the
record's own fields. A store takes the value apart where it is produced (so the producer's
`call; local.set` is field-only and gets its twin), a field read is one `struct.get`, and a
read that needs the whole record re-boxes. sunpa's posing (tools/check/feet-test.ts, 8,394
posed characters): `Q` allocations 78,441 → 53,275, identical output. `V3` is refused there,
because an export hands a record holding one to JS (`animationReady` returns a struct with a
`V3` field) and the boundary rule follows fields; with `$VL_INLINE_BOUNDARY=direct` (follow
signatures only, since a JS host cannot read a struct's fields) `V3` falls 106,805 → 89,937 too.
That rule is the owner's question 2 in inline-records-design.md §6.
