### D16776 — a maker's hole lambda read back out of its holder through a generic function keeps its own result at a function type returning `f64`

**closed 2026-11-16 · runs, prints `0.5` · was loads then traps, `vl check` rc 0, `wasm trap: indirect call type mismatch` · clause 1 · fixed in emit_elab.vl: the call search returns through the call it entered a function by, which the instance filter refused for a call at the root, and reads each entered call's parameter afresh, so a second call of the same generic reader (`getOr(m, "z")`) no longer hides the first's · the generic store and `getOr` map faces run too · pin: `tests/cases/functions/maker-lambda-held-by-field-param-generic-values.vl` · found by the maker/map/relay hunt · filed 2026-11-16 against master `6fb5ac348`**

Repro:

    function deliver() { return (a) => a + 1 }
    function first<V>(xs: V[]): V { return xs[0] }
    const xs: ((a: i32) => f64)[] = []
    xs.push(deliver())
    const f = first(xs)
    print(f(3) / 8.0)
    // vl check: rc 0.  vl run: wasm trap, indirect call type mismatch

Want:

    0.5

#### Mechanism

The lambda's result is decided by the calls the lambda reaches ([D16711](D16711.md), `elabLamDeliveredRet` in emit_elab.vl), found by the call search `elabSlotClimb` / `elabReadOn`. From the push it reaches the holder's element reads, but a read inside a generic callee (`xs[0]` in `first`) returned to the caller is not followed out through the call's result to the call `f(3)`.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `xs[0](3)` read directly | runs, `0.5` | **yes**: the generic read |
| a generic store `store<V>(m, k, v) { m[k] = v }` for the push | the same trap | no: the store face |
| `getOr<V>(m, k): V | null { return m[k] }` over a map | the same trap | no: the map and nullable face |

#### Grading list

The generic store face and the `getOr` map face named in the ablation.
