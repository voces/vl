### D1980 — an F32x4 lane has no read-back spelling: `.x`/`.y`/`.z`/`.w` need property syntax VL does not have, and `laneF32x4(v, i)` cannot carry the literal `i` through a std wrapper

**loud check reject · design question for the owner, found building SIMD S3 · filed 2026-09-22 against master `a8a104432`**

Repro:

    import { f32x4 } from "std:simd"
    const v = f32x4(1.0, 2.0, 3.0, 4.0)
    print(v.x)
    // vl check: member access '.x' on non-object F32x4

#### Mechanism

`simd-design.md` O3 rules two lane-read spellings for S3 and neither is buildable without a
compiler or language change, so S3 shipped with NEITHER rather than bend the API.

- **Named accessors `.x/.y/.z/.w`.** A member read on a `new v128` brand has no field to find.
  §E calls them "ordinary methods", and an ordinary `export function x(self: F32x4): f32`
  works today through type-bound UFCS — but it spells `v.x()`, not `v.x`, and a std name is
  permanent. Measured: a local named `x` does NOT shadow the method (`const x = 5;
  print(v.x())` still dispatches), so the method form is safe; the open question is only
  which spelling O3 meant. `v.x` needs either a property-getter rule ("a zero-argument
  `self` function reads as a field") or a compiler-known lane table, which would make the
  compiler know std's type names.
- **`laneF32x4(v, i)` / `withLaneF32x4(v, i, x)`.** The lane is a wasm immediate, so O3 makes
  a non-literal `i` a checker error. `std:simd` can only pass `i` on to
  `__extract_lane_f32x4__(v, i)`, where `i` is now a parameter, not a literal, and the
  checker refuses it inside std. Carrying a literal through a call needs a compile-time
  parameter (const-generic in all but name, which O10 rules out as a dependency) or a
  checker rule that re-checks a marked parameter at each call site.

Workaround today: `storeF32x4` to a `Buf` and `loadF32` at byte `4 * lane`;
`reduceAddF32x4`/`dot` give scalar answers directly.

#### Grading list

Whatever lands must grade the un-annotated spelling (`const v = f32x4(…)`) and a vector
parameter as the receiver, and a lane read inside a `std:simd` function body, not only at
a user call site.

#### Update — the language half is built

The owner ruled `docs/internals/property-access-design.md` (#3019): lanes read as declared,
nominal-only getters, and an index read takes a literal-union parameter (`i: 0 | 1 | 2 | 3`).
Getters v1 is built (`get x(self: T): R`), and `tests/cases/getters/getter-lane-over-v128.vl`
reads `.x`–`.w` off a local `new v128` brand, one `f32x4.extract_lane` each at `-O`. The
witness above still refuses because `std:simd` declares no getter yet: adding `get x/y/z/w`
and `lane`/`withLane` to `std:simd` is its own lane, after D1984.
