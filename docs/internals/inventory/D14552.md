### D14552 — a variant row is looked up by its record type, so a plain record that shares an arm's arena node reads as that arm

**closed 2026-10-27 · runs, prints `7` · filed 2026-10-27 against master `9ae57ff23` · fixed: every variant row is minted by `mintVariantRows` with its member position; a reader holding a union row asks `variantRowInRowOfTy`, a reader holding a bare record asks the rep's shape row (`repVariantShapeRowOf`), and `armRowOfRecordTyShim` and its exact index `vrIxFirst` are deleted · pins: this row's witness and D14551's**

Repro:

    function src(p: {r: i32}): {r: i32} | null { p }

    const f = src
    const _h = f({ r: 9 })
    const g1 = src({ r: 7 }) ?? { r: "s" }
    print(g1.r)
    // vl run: 7

#### Mechanism

Under D3870 a plain `{r: i32}` and the `{r: i32}` arm of `{r: i32} | {r: string}` are one
TYPE; what differs is the REP at that position (the arm is boxed and tagged). So a variant
belongs to a POSITION in a union row, not to a record node. The emitter asks the opposite
question: `uVarTyIx` maps each variant row to a record type, and every reader below goes from
a type to "the first variant row carrying it" (`armRowOfRecordTyShim`, formerly
`variantRowOfTy`, indexed by `vrIxFirst`). The witness runs today only because site 46 (the
`??` join) mints its union row from a re-parse that makes a FRESH `{r: i32}` node; minting at
the held type makes `src`'s return the same node as the arm, the shim then calls it a variant,
and the fn-value signature refuses. The re-parse is a hidden second producer that smuggles
position identity into a node index.

Slice 1 (this row's PR) adds the identity as the one producer: `mintVariantRows`
(`emit_collect.vl`) mints every variant row and records its member position in `uVarMemPos`;
`variantRowAt(u, pos)` and `variantRowInRowOfTy(u, ty)` (`emit_mv_slots.vl`) read it. Readers
that hold a union row moved to it. Readers that hold only a type reach the old answer through
one named shim, `armRowOfRecordTyShim`, which the later slices delete.

Slice 2 moves the shim and its index into `emit_rep.vl`, beside the shape index it falls back
to, so `repNulObjKind` asks it rather than keeping a second exact scan of `uVarTyIx`.

#### Ablation

The reader census, by file. (i) = the caller holds a union row (or that row's arm list) and
asks about one of its arms. (ii) = the caller holds a bare record type and asks whether it is
an arm. (s) = a structural scan over every variant row (by `repCanonId`, `tySame` or shape),
which the last slice's rep keying replaces. (r) = row to type: a read of `uVarTyIx[vi]` for a
row already in hand, which the identity keeps.

Exact index against shape index, measured. A probe build compared, at every shim call, the
exact answer with the first variant row of the record's canonical shape, over all 6,789
`tests/cases` programs; 376 programs reach a call where they differ. The callers that
differ: `objVariantRowCtx` (95 programs, 30 where both find a row and the rows differ),
`variantRowOfShapeTy` (94), the `internArmShapeRow` sites in `emit_collect.vl` (71 and 46),
`tyObjHasRefRow` (14), `annVariantRowOf`, `mvValArmName` (10 each), `repSlotOfKind`,
`emit_mono.vl`'s member pin (7 each), and eight more under 6. Where only the shape finds a
row, `variantRowOfRepTy`'s callers already take it. A caller that never differs asks a rep
question: group 1 moves those to the shape row, or to `repTyHasArmShape` for a `>= 0`
test. A caller that differs is expected to hold a union row, which a later group threads to it.
A second probe compared the shim with `repVariantShapeRowOf` itself, which also declines a
nominal type and a record with a declared struct row, at the shim calls and at group 1's new
calls: 367 programs differ, at the same callers, and at none that group 1 or 2 moved. Exact
finds a row the shape row declines (a declared struct row) only at `objVariantRowCtx` (1),
`emit_collect.vl`'s `internArmShapeRow` (7) and `emit_nullable_rets.vl` (1). The
`variantRowOfRepTy` callers that differ only where exact finds nothing (`repSlotOfKind`, the
`: Arm` return slot, `annVariantRowOf`) already answer with the shape row; group 3 asks it directly.
