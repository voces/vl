### D3082 — a `<T>` for-in over a list literal mixing an element read with the parameter prints the `i32` cell at a `boolean` or literal-union pin

**check-clean silently wrong · clause 1 · open · the D3065 residue, found by the #3269 review · the same on master `67ca68cf3` · filed 2026-09-28 against master `67ca68cf3`**

Repro:

    function f<T>(x: T) {
      const l = [x]
      for e in [l[0], x] { print(e) }
    }
    const t: boolean | null = true
    f(t)
    // vl check: rc 0.  vl run: prints `1` twice

Want:

    true
    true

#### Mechanism

Not localised past the ablation. D3065 taught `iterElemPinTy` a literal whose every element is
a read (`arrLitReadsPinTy`) and it already knew a literal of the parameter alone
(`arrLitSameIdentName`); a literal mixing the two kinds, or repeating a local beside the
parameter (`[y, x, y]`), matches neither rung, so the loop variable prints as the `i32` cell. A
nested `[e, x]` inside another loop is the same miss, or a loud refusal at a literal-union pin.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `[l[0]]` | prints `true` (D3065) | **yes** (the mix) |
| `[x, x]` | prints `true` | **yes** |
| `[y, x, y]` with `const y = l[0]` | prints `1` three times | no (the same miss) |
