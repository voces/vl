### D14513 — a call passed to an un-annotated parameter reads the field as an i32 after another call of the function is delivered to a wider record type

**closed · now runs, prints `5` · was check-clean invalid wasm, clause 1 · filed 2026-10-27 against master `8f810b02b` · closed 2026-10-31 against master `cb178881` with [D14426](D14426.md): the instance is typed at the checker's binding and the parameter is stored at the record the argument is built at · fixture `generics/hole-instance-typed-at-binding-stored-at-build.vl`**

Repro:

    type J = { f: i32 | null }
    function mk() { { f: 4 } }
    function sink(_j: J) { }
    sink(mk())
    function take(a) { print(a.f + 1) }
    take(mk())

Want:

    5

#### Mechanism

`sink(mk())` builds `mk`'s record at `J`, where `f` is boxed as `i32 | null`. `take`'s parameter
is inferred from `take(mk())` as `{ f: i32 }`, so its body reads `a.f` as a bare `i32`, and the
module fails to validate inside `take` (`expected i32, found (ref $type)`). Unlike D14512, it
stays invalid with `recReadInPlace` removed from `recSitesLandAt`, so it is not part of the D14509
rip.

#### Grading list

Without the `sink` delivery the program prints `5`. It is the same with `const wideJ: J = mk()`
in place of `sink(mk())`. `function take(a) { … }` called with `{ f: 4 }`, or with a binding of
`mk()`, and no wider delivery also runs.
