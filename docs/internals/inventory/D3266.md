### D3266 — a join of three bare type parameters prints the wrong members

**closed 2026-09-30 · was check-clean silently wrong, clause 1, on master `b6378e95b` (`null 0 null`) · found by the #3297 round-2 review (`m3.vl`) · fixture `tests/cases/generics/join-three-bare-type-params.vl`**

Repro:

    type K = "a" | "b"
    function g<T, U, V>(a: T, b: U, d: V, k: i32) {
      const r = if k == 0 { a } else if k == 1 { b } else { d }
      return r
    }
    const x: i32 | null = null
    const y: K = "a"
    const z: string = "x"
    print(g(x, y, z, 0))
    print(g(x, y, z, 1))
    print(g(x, y, z, 2))

Want:

    null
    a
    x

#### Mechanism

Three causes in a row, one per layer. `tyParamsPart` kept two bare type parameters collapsed
(`T | U` was typed `T`), so the instance built the join at the first parameter's pin. Once the
join is `T | U | V`, the pin re-joins its members by a left fold (`rejoinMembers`): `i32 | null`
beside `K` flattens the literal union to `"a" | "b"`, and the later `string` did not absorb
them, so the join was `i32 | "a" | "b" | string | null` where the direct chain gives
`i32 | string | null`; `rejoinDropSubsumed` drops a literal arm a wider member holds. The
string-op scan then reserved no scratch frame for the arm's atom-to-string widening
(`unknown local`), which D3280's direct twin shared: `exprHasStrOp` now reserves it for a
`string | null` join too, and the #3297 park (`monoMultiParamLitNullJoin`) is gone.
