### D15068 — a one-element list literal of a hole function, iterated inside a hole function and handed that function's own parameter, is invalid wasm

**closed 2026-11-03 · runs, prints `3`, with the split plan on and off · was check-clean invalid wasm, clause 1 · `ftScan` (check_fn_tag.vl) no longer declines a list's set for being iterated in an open function that hands a function on; `ftHoldCtxOk` alone decides the holder · fixture `tests/cases/closures/hole-fn-list-literal-iterated-handed-hole-param.vl` · found grading D15062 item 2's hazard spellings · filed 2026-11-03 against master `1484b3d7`**

Repro:

    function add(a, b) { return a + b }
    function apply2(g) {
      print(g(1, 2))
    }
    function viaFor(h) {
      for f in [apply2] { f(h) }
    }
    viaFor(add)
    // vl check: rc 0.  vl run, before: the emitted module failed to validate inside `viaFor`: type mismatch: expected (ref $type), found i32

Want:

    3

#### Mechanism

`ftScan` declined the set of `[apply2]` when the literal sat in an open function (`viaFor`) that
hands a function on (`f(h)`), before asking `ftHoldCtxOk` whether the literal is a holder there.
The declined set left `apply2` untagged while the call through `f` was emitted as a dispatch, so
`h` reached `apply2`'s parameter as an `i32` id where a closure was expected. The literal is a
holder in its own frame, so the veto goes and `ftHoldCtxOk` decides.
