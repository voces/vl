### D1230 — a UFCS method whose free function is exported but NOT imported blamed the receiver; the refusal now names the missing import, under `ufcs-not-imported`

**now a loud check reject in its REMAINING domain — an orphan method (exported by a module that
does NOT declare the receiver's type), a non-nominal receiver (string), or an absent name ·
the HOME-MODULE case it was first filed against now RESOLVES type-bound with no import (the
type-bound-UFCS feature, design #3001), which supersedes the suggestion there · a
DIAGNOSTIC-QUALITY row, neither clause 1 nor clause 2 · CLOSED 2026-09-02, witness re-pointed
2026-09-07 · filed as [D1230](../../DECISIONS.md)**

Repro (check rc 1 — the sentence is the subject of the row, not the exit code):

    import { join } from "std:str"
    print("hi".trim())

`trim` is a free `self`-function exported by `std:str`; the receiver is a STRING, which has no
declaring module, so type-bound resolution cannot reach it and the import is genuinely needed.
Before this row the message was `no field 'trim' on string`. Now:

    'trim' is not imported — a free `trim(self: …)` accepting string is exported by "std:str";
    a UFCS call resolves only names in scope, so import `trim` from there — add `trim` to the
    existing `import { … } from "std:str"`

* **THE OLD SENTENCE WAS TRUE, PERMANENT, AND USELESS.** `string` has no field `trim` and
  never will. What the compiler knew and did not say is that `trim` is a free `self`-function
  exported by `std:str`, one import away from working. (When the receiver's OWN declaring
  module exports the method — `buf.storeI32(…)` on a `Buf` from `std:buffer` — type-bound
  resolution now makes the call work with no import at all, so no suggestion is owed; D1230 is
  what remains for the cases type-bound resolution does not cover.)

* **THE PAYLOAD RIDES A DATA CHANNEL, NOT THE SENTENCE AND NOT THE CODE**, so a quick-fix
  never parses English — and never splits a code string either. The code is the bare category
  `ufcs-not-imported`; the answer travels on `diagDataLen`/`diagDataByte` (`TDiag.tdata`),
  the parallel pair beside `diagCodeLen`/`diagCodeByte`:

      6:member,4:trim,7:modules,7:std:str,4:recv,6:string,

  Netstrings — `<byte-length> ":" <bytes> ","` — read as alternating key and value; a
  repeated key is a LIST, which is how `modules` carries every candidate. The length is
  authoritative, so no value's characters can bite the framing and nothing is escaped or
  order-dependent. Pinned in `tests/selfhost_native_diag_code_test.ts`, including a receiver
  rendering as `{a: i32, tag: "a;b,c|d" | "éè"}` — every separator the first design used, plus
  two non-ASCII characters so a byte length and a JS `.length` disagree. ONE diagnostic lists
  every candidate module: the fix is a choice among them, and N diagnostics would stack N
  squiggles on one token.

  **IT SHIPPED PACKED INTO THE CODE FIRST** — `ufcs-not-imported;member=…;modules=…;recv=…`,
  with `recv=` last because it was the one field that could contain the separators — and that
  is the shape of the mistake: there was one string channel, so the answer went in it, and
  every consumer then owed a `diagCategory` cut at the first `;` before it could compare a
  code. `diagCategory` survives as a tolerant reader that nothing depends on.

* **THE LOOKUP IS THE ONE UFCS ALREADY DOES, ASKED AGAIN ON THE FAILURE PATH.**
  `typecheck.ufcsWouldDispatch` mirrors `ufcsCallTy`'s GATE arm for arm — the lookup, the
  `self`-name rule, the arity RANGE, `assignable(recvTy, params[0])` — and deliberately
  nothing after it. Running `ufcsCallTy`'s side-effecting tail (a pending-return force, a
  deferred constraint, argument reordering) speculatively over every same-named candidate in
  the graph would raise diagnostics for functions the program never calls.

* **THE SCOPE IS THE MODULE GRAPH, AND ITS EXCLUSIONS WERE DECIDED, NOT DRIFTED INTO.** A
  module the file does NOT import is covered when — and only when — its key is a `std:`
  specifier, because a `std:` specifier is absolute and therefore the same text from every
  file (`tests/cases/modules/ufcs-not-imported-transitive-std/`). A RELATIVE module the file
  does not import gets nothing: its key is a normalized path, and turning that back into a
  specifier relative to the entry is `..`-arithmetic that can name a different module. A
  self-function in the SAME FILE that is out of scope also gets nothing
  (`tests/cases/objects/ufcs-nested-self-fn-out-of-scope.vl`), and an UN-EXPORTED one is the
  third exclusion — cross-module UFCS reaches only a module's public surface, so no import
  would resolve it (`tests/cases/modules/ufcs-unexported-not-callable/`).

* **THE CONTROLS RUN IN THE SAME GRAPH AS THE SUGGESTION**, which is what makes them controls
  and not vacuous passes. `tests/cases/modules/ufcs-not-imported/entry.vl` now holds the two
  refusals that survive type-bound resolution — `nosuch` (no self-function anywhere) and
  `hidden` (a self-function in the same imported module, un-exported) both keep
  `no field '…' on Box` — while `area` (exported by `Box`'s OWN module) resolves type-bound
  with no import, which is the positive half the type-bound-UFCS fixtures cover.
