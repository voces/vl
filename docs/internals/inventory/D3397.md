### D3397 — a string-keyed read off a hole's map field has no derived hole, so the pin never resolves it and a bound miss reads the raw zero

**check-clean silently wrong · clause 1 · open · the string-keyed face of [D3155](D3155.md), which lane MH fixed for an `i32` key only · found by lane MH's map-read grid (`skey` cells) · filed 2026-09-30 against master `8df60e472`**

Repro:

    type H = { m: {[string]: i32} }
    function mk(): H {
      const v: {[string]: i32} = Map()
      v["a"] = 7
      { m: v }
    }
    function use(r) {
      const x = r.m["z"]
      print(x)
    }
    use(mk())
    // PRINTS 0

Want:

    null

#### Mechanism

An `i32` index on a hole is an element derivation (`HD_ELEMV`), which lane MH reads at a map pin
as the value or `null`. A key of any other type takes the checker's other arm
(`checkIndexNode`, `holeMapDemandTy`): the read is typed `V | null` over the hole's DEMANDED
map, whose value is still unfilled (`TyNullable` over `-1`), with no derived hole to resolve at
the pin. So the binding synthesises no `i32 | null` annotation and the instance's cell is the
raw `i32`. A candidate that read such a node through its receiver's pin fixed the hole spelling
only by breaking the `<T>` one (`only i32 locals are supported` on a hit), so it was not kept.
Giving the key-typed read the same derived hole as the `i32` one is the likely fix; #3282's F2
tried it only for the left operand of a `??`.
