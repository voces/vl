### D3390 — an all-`null` list literal written directly as a lambda's argument at an `(i32 | null)[]` parameter has no element context

**closed 2026-10-03 by [D3605](D3605.md) (lane CL2): a function-value call now seeds each argument's container shape from the callee's parameter, never the enclosing position · fixture `tests/cases/closures/value-call-list-literal-element-storage.vl` · was loud emit reject · the `_nu` cells of #3304's price (`rv3304r4-17562/g13/*_elem_closure_nu*`), named in [D3337](D3337.md)'s note · filed 2026-09-30 against master `4ff12b994`**

#### Mechanism

Not traced; the ablation places it beside [D3337](D3337.md). An argument literal takes its
element storage from the callee's parameter, and a lambda-valued local is a callee that seeding
does not resolve. With an element that tells its own storage (`[null, 5]`) the literal builds and
runs; with only `null`s nothing seeds the element, and the bare `null` reaches the emitter with
no context. D3337 is the same unresolved callee giving a literal of real elements the wrong
storage; one close probably serves both.

Closed by [D3605](D3605.md): `emitCallRef` and `emitCapturedCall` seeded no list kind or slot from the parameter, so the literal built at whatever the enclosing position had left in `pendingListKind`. Both now seed it from the `$fnsig` key or the declaration, as the direct call seeds it.
