### D3127 — a hole instance reads a literal-union map field's index and `??` at the template's types

**check-clean invalid wasm · pre-existing on master `cc890c9f4` · exposed at `anon-litunion-map-field-call`'s `argument`/un-annotated cell once [D3123](D3123.md) lifted that cell's refusal · filed 2026-09-28 against master `cc890c9f4`**

Repro:

    type AB = "a" | "b"
    function mkL(k: i32, x: AB): {[i32]: AB} {
      const m: {[i32]: AB} = Map()
      m[k] = x
      m
    }
    type R = { direct: {[i32]: AB} }
    function wrapL(k: i32, x: AB): R {
      const m = mkL(k, x)
      { direct: m }
    }
    function __take(a) {
      const v = a
      print(v.direct[3] ?? "a")
    }
    __take(wrapL(3, "b"))
    // vl check: rc 0.  vl run: invalid module inside `__take`, expected i32, found (ref $type)

Want:

    b

#### Mechanism

The instance for the un-annotated parameter reads `v.direct[3] ?? "a"` at the template's types
rather than at the pin. An i32 index on a hole is an element derivation (`HD_ELEMV`), and both
`substHoleTyReal` and `holePinReadOf` resolve it for a list or string pin but not for a map, so
the read stays a hole. The `??` result hole (`HD_COAL`) carries the default as the widened
`string`, so at a literal-union pin it joins to `string` where the concrete `??` keeps the
union. The map read yields the i32 atom, and the default and every consumer of the result
expect a string ref. Resolving both derivations at the pin is not enough on its own: with the
map default also keyed at the pin (`nodeTyMapValLitUnionTexts` reading `nodeTyPinIxOf`), the
module validates and `print` shows the atom id `1`, a wrong value. The consumers of the `??`
result still read the template type, so the fix has to reach them too.
