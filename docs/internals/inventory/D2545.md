Repro:

    function fold<T, A>(xs: T[], i: i32, acc: A, f: (A, T) => A): A {
      if i >= xs.length { return acc }
      return fold(xs, i + 1, f(acc, xs[i]), f)

The scratchpad witness this was found from, `rv3159-probes/r4/x7_fold_explicit.vl`, no longer
reaches this defect: an unrelated, now-conservative narrowing-invalidation refusal (the D2407
family, #3159) fires first on that file's `if o.v is i32 { ...; print(o.v + 1) }` shape and
rejects it before monomorphize is reached. The underlying capability gap is unchanged; the
repro above reaches it without that obstacle.

#### Mechanism

When a generic function's own function-typed parameter (`f: (A, T) => A`) is bound at a call
site, the monomorphizer names its concrete function type from the ARGUMENT expression
(`monoArgFnTypeName`, `emit_mono.vl`) — which works for a lambda literal or a already-concrete
function reference. Here the recursive call passes `f` itself, i.e. the very parameter whose
type still rides the CURRENT instantiation's type variables, as the argument. `monoArgFnTypeName`
has no answer for "the type of this already-generic-typed parameter, one level removed", so it
returns `""` and the site's `emitFail` fires rather than continuing.

#### Grading list

Any generic function recursing through itself (directly or mutually) while forwarding a
function-typed parameter of its own type variables — `rec<T>` shapes generally, not `fold`
alone.
