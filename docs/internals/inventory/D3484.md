### D3484 — a duplicate key in an object literal is accepted: the first wins, later initialisers are dropped or run once per duplicate squared

**check-clean silently wrong · clause 1 · open · the right behaviour (refuse the duplicate, or last-wins) awaits a ruling, so there is no `Want:` · found 2026-10-03 · filed against master `e5ff25ff9`**

Repro:

    const o = { a: 1, a: 2 }
    print(o.a)
    // vl check: rc 0, no diagnostic
    // PRINTS 1

#### Mechanism

Neither the parser nor the checker compares an object literal's keys with each other, and the
emitter then reads the first of them. The mechanism past that is inferred from the ablation, not
read from the emitter: the duplicate effect counts (4 for two keys, 9 for three) say each of the
n slots re-evaluates the first matching initialiser, and a second `a` is never read. A refusal at
`vl check` is the likely answer (a duplicate key is a typo), last-wins would be the JavaScript
reading, and which one is a language ruling, so this row records what runs. A type declaration
repeating a field is accepted too.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| shorthand `{ a, a }` (with `const a = 1`) | check rc 0, prints `1` | no |
| `{ a, a: 5 }` with `a = 7` / `{ a: 5, a }` | prints `7` / `5` (first wins) | no |
| `{ a: 1, b: 2, a: 3 }` | `o.a` is `1`, `o.b` is `2` | no |
| `{ a: g(), a: 2 }` with `g` printing `9` and returning `3` | prints `9` FOUR times, then `3` | **yes**: an initialiser with an effect |
| `{ a: g(), a: 2, a: 4 }` | prints `9` NINE times, then `3` | the count is n squared |
| `{ a: 1, a: g() }` | `g` never runs, prints `1` | the dropped initialiser's effect is lost |
| `{ a: g(), b: 2 }` (no duplicate) | prints `9` once, then `3` | control |
| `{ a: 1, a: "x" }` (different types) | check rc 0; `vl run` refuses at emit `object literal field count does not match struct` | the loud emit reject is this row's sibling |
| `type P = { a: i32, a: i32 }` | accepted at `vl check`; a literal at `P` is then refused with `this object literal sets , which P does not declare` (the field name is empty in the message) | the same omission in the type declaration, plus a mis-rendered diagnostic |
| `{ ...o, a: 5 }` | parse error: VL has no spread in an object literal | not this row |

#### Grading list

Whatever the ruling, every spelling above must agree: a refusal at `vl check` for all of them, or
last-wins with each initialiser evaluated exactly once in source order. The `g()` rows are the
ones a "first wins" patch would still get wrong.
