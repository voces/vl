### D3484 — a duplicate key in an object literal is accepted: the first wins, later initialisers are dropped or run once per duplicate squared

**check-clean silently wrong · clause 1 · open · the duplicate-key ruling is pending: the right behaviour (refuse the duplicate, or last-wins) awaits the owner, so there is no `Want:` · the multiplied evaluation is fixed 2026-10-03 against master `59d72ed63`: every initialiser now runs exactly once, in source order, and the first still wins (fixture `tests/cases/eval-order/struct-literal-duplicate-key-runs-each-once.vl`) · found 2026-10-03 · filed against master `e5ff25ff9`**

Repro:

    const o = { a: 1, a: 2 }
    print(o.a)
    // vl check: rc 0, no diagnostic
    // PRINTS 1

#### Mechanism

Neither the parser nor the checker compares an object literal's keys with each other, so the
literal's struct lays out one slot per occurrence (`{a: i32, a: i32}`) and every read of `.a`
takes the first slot. The emitter filled each slot by name, so every slot of `a` took the first
initialiser of `a`, and D1510's source-order stash matched each initialiser against every slot of
its name: n initialisers ran the first one n squared times and the rest never. The n-th
initialiser of a name now feeds the n-th slot of it (`objFieldValAt`, `objFieldSrcOrder`), so each
runs once, in source order, and first-wins is what the reads give. A literal delivered to a
declared record or union arm is refused at `vl check` already (the last two ablation rows). A
refusal at `vl check` is the likely answer (a duplicate key is a typo), last-wins would be the
JavaScript reading, and which one is a language ruling, still pending; this row stays open for it.
