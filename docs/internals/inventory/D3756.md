### D3756 — the fused `xs.get(i) ?? d` evaluated the index before the receiver

**closed — the witness prints `recv`, `idx`, `2` · was check-clean wrong evaluation (`idx` before `recv`, where `xs.get(i)` and every other `.get` spelling evaluate the receiver first) · found by review of lane SP · filed 2026-10-06 against master `b05991d98`**

Repro:

    const l: i32[] = [1, 2]
    function g(): i32[] { print("recv"); l }
    function h(): i32 { print("idx"); 1 }
    print(g().get(h()) ?? -1)
    // master: idx, recv, 2

Want:

    recv
    idx
    2

#### Mechanism

`emitListGetOrGo` (wasmEmit.vl) built the bounds test as `idx`, `recv.len`, `i32.lt_u`, so a
side-effecting index ran before a side-effecting receiver. It applied to the fused `?? d` over
an `i32[]` or `f64[]` on master. Lane SP (SP-046) routed two more forms through it, the i64/f32
`?? d` and the `const v = recv.get(i)` a null test takes apart, which had evaluated
receiver-first. The test is now `recv.len`, `idx`, `i32.gt_u`. Both operands already sit in the
`.get` stash when staged, so the element read that follows reuses them.

#### Ablation

| spelling | master | after |
| --- | --- | --- |
| `g().get(h()) ?? d` over `i32[]`, `f64[]` | idx, recv | recv, idx |
| over `i64[]`, `f32[]`; `const v = g().get(h())` null-tested | recv, idx | recv, idx |
| `m.get(k) ?? d`, `m[k] ?? d` | recv, idx | recv, idx |

`tests/cases/lists/get-or-default-receiver-first.vl`: every scalar list kind, both the `??`
