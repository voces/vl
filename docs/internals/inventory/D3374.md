### D3374 — `{ a: { b } }` is a labelled block as an if-expression's then arm and an object literal as its else arm

**closed 2026-09-30 by the owner's label ruling: a label is `@name`, so `{ name: … }` is always an object literal and both arms read it alike (`parseArmBody` in `compiler/parser.vl`; DECISIONS.md, "A label is `@name`") · was a loud check reject, pre-existing, found by the #3295 review · filed 2026-09-30 against master `6e6a5301b` · fixtures `tests/cases/conditionals/if-arms-object-agree.vl`, `tests/cases/conditionals/object-literal-arm-bodies.vl`**

Repro:

    function h(c: boolean, b: i32) {
      const t = if c { a: { b } } else { a: { b: 0 } }
      const e = if c { a: { b: 0 } } else { a: { b } }
      print(t.a.b)
      print(e.a.b)
    }
    h(true, 5)
    h(false, 6)
    // was: parse error in the then arms (`b: …` starts no statement), the arm read as a labelled
    // block; the filed spelling (`if c { a: { b } } else { 0 }`) typed `t` as `i32` and `e` as
    // `i32 | {a: {b: i32}}`
    // now: prints 5, 0, 0, 6

Want:

    5
    0
    0
    6

#### Mechanism

The then arm is parsed by `parseBlock`, where `a: {` opens a labelled block whose value is `b`,
so `t` is `i32`. The else arm's braces go through the object-literal look-ahead, which reads the
same text as the object `{ a: { b } }`, so `e` is `i32 | {a: {b: i32}}`. The same spelling means
two things by arm position. Which reading both arms take was a language ruling. The owner ruled
on 2026-09-30 for an object, and removed the ambiguity rather than resolving it: a label is
written `@name`, so `name:` never opens one. Every arm, branch and body now reads braces that open
`{ name: …` as an object literal (`parseArmBody`), the same test a function body always used.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the else-arm position (both arms spelled as the then arm) | `t` checks as `i32` | **yes** |
| the nested braces (`{ a: b }`) | parse error: `a: …` starts no statement | **yes** |
