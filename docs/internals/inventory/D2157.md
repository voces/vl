### D2157 — `const Z = "zz"` infers `string`, so a compare against it walks a runtime string

**closed 2026-09-23 — the witness prints `true` then `false`, and `self.kind == Z` compiles to one `i32.eq` · was a working program with an O(n) compare and D2120's getter refusal, clause 2 under the owner's ruling (2026-09-23) that a `const` bound to a string literal has that literal's type · filed 2026-09-23 against master `b5debe165` · fixture `tests/cases/getters/getter-step-budget-allows.vl`**

Repro:

    const Z = "zz"
    type N = new { name: string, kind: "zz" | "yy" }
    get isK(self: N): boolean { self.name == Z }
    get isKind(self: N): boolean { self.kind == Z }
    const n: N = { name: "zz", kind: "yy" }
    print(n.isK)
    print(n.isKind)

#### Mechanism

The binding's type is now the literal, minted fresh per `const` and flagged widening
(`wideLitTyIxs`), after TypeScript's widening literal. The literal is kept where it is read and
widened to `string` where the value is stored somewhere reassignable: a `let`, a list or object
literal, a type argument, an operator's operand, and the element, key or value an empty container
pins from it. The widening is structural (`widenLitTy`): a join of two constants, a function
returning one, a list of them, a map keyed by one. A `const` bound to anything but a literal (or to
another such `const`) takes its initializer's type widened. The
recorded node type is the widened `string`, so every emitter classifier sees the rep it always
saw; `nodeWideStrLitText` is the one place the literal is asked for. A `let` keeps `string`, and a
numeric `const` is unchanged. A compare against a literal outside the const's value is an
ordinary false test, not the non-member refusal a declared literal type gets.
