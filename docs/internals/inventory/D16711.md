### D16711 — an un-annotated lambda returned by a function and bound at a function type returning `f64` keeps its `i32` result and traps at the call

**closed · runs, prints `0.5` · was loads then traps, `vl check` rc 0, `wasm trap: indirect call type mismatch` · clause 1 · the lambda's instance returns the numeric result of the function type its calls take where its body gives another numeric type, in both mint paths: the clone inside a maker's twin (`monoLamPinRetAnn`) and an instance `monoInstanceFor` mints (`monoLamInstDeliveredRet`), read by `elabLamDeliveredRet` (emit_elab.vl) the way `elabLamParamTy` reads its parameters · fixture `closures/hole-lambda-relayed-by-inferred-return-at-f64.vl`, matrix `hole-fn-lambda-relayed-by-inferred-return-at-f64` · still open: a maker call stored into a map ([D16733](D16733.md)), one maker delivered at two results ([D16734](D16734.md)) · the `return_inferred`/annotated cell of `hole-fn-lambda-relaying-i32-at-f64-fn-type.matrix.vl` ([D9020](D9020.md)'s template) · filed 2026-11-16 against master `c040079c`**

Repro:

    function deliver() { return (a) => a + 1 }
    const v: (a: i32) => f64 = deliver()
    print(v(3) / 8.0)
    // vl check: rc 0.  vl run: wasm trap, indirect call type mismatch

Want:

    0.5

#### Mechanism

`deliver()` is typed `(_) => _`, so the lambda's own checked type names no result, and D9020's
rule (the instance takes its checked scalar result) has nothing to read. The `f64` exists only
at the delivery. Mono mints the lambda in one of two ways. Where every read of `deliver` takes
a closed result, `deliver` is a maker built per result (`monoMakerTwin`) and the lambda is cloned
in that twin (`monoCloneLambdaSubst` → `monoLamPinRetAnn`). Where some read reaches the
maker's root (`fvaMakerCoverCheck` blocks it: an unused `relay` that returns `deliver()` is
enough), the lambda is instanced by `monoInstanceFor` at its parameter pins. Both paths took the
result from the body's elaboration, `i32`, while the binding's call went through
`(structref, i32) -> f64`. Both now read the result of the closed function type the lambda's
calls take (`elabLamDeliveredRet`, the call climb `elabLamParamTy` already uses for the
parameters) and take it as the instance's annotation when it is another numeric type.
