### D15030 — a void generic written to a `let` initialized with a generic returning a value traps when called through it

**closed · now a loud check reject, `cannot write 'inner' to 'k': called at (i32) it returns void, where 'retV', also written to it, returns i32` · DESIGN (owner ruling 2026-11-05 (Q5, W-split): a `let` holding a function that returns nothing cannot be written with one that returns a value, or the other way round, in either order) · was loads then traps · found grading D14785's close · filed 2026-11-02 against master `b4ffadefd`**

Repro:

    function inner<U>(u: U) { print("I"); print(u) }
    function retV<V>(v: V): V { print("R"); print(v); v }
    function main() {
      let k = retV
      k = inner
      k(3)
    }
    main()

#### Mechanism

Not probed. It is D3969 with the order of the two values reversed. Here the binding's type is the
initializer's `(V) => V`, and the void generic written to it is accepted. The call is lowered at a
signature returning `i32`, and `inner`'s instance returns nothing.

#### Grading list

#### Ruling

Refused by design, owner ruling 2026-11-05 (Q5, W-split): a `let` holding a function that returns nothing cannot be written with one that returns a value, or the other way round, in either order. The annotated spelling already refused a void function written to a `let` whose type returns a value; `holeLetJudge` (check_relate_core.vl) now judges a member whose signature returns nothing as `void` against every member that returns a value, in both orders, so the hole and generic spellings agree with it (D15015).
