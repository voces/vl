### D10293 — a hole function's bound join of its hole parameter and an `f64` reads the `i32` arm as `f64`

**closed · runs, prints `true` · was check-clean silently wrong, clause 1 · found closing [D10280](D10280.md) · present on master `d5ec7f160` · filed 2026-10-22 against master `d5ec7f160` · closed in check_tp_join.vl: `tyParamBesideBare`, `noteHoleTpJoin` and `tpGradualView` read a hole's non-null read under a null test as the hole itself, so the join is the hole's own `_ \| f64` at every pin and arithmetic over it checks · fixture `numerics/runtime-numeric-join-read-by-value-hole-mutual.vl`, new matrix `hole-null-test-runtime-numeric-join` 0 → 48 of 48 and its generic `-open` twin 34 → 48 of 48**

Repro:

    function g(q, d: f64) {
      const r = if q != null { q } else { d }
      print(r is i32)
    }
    g(5, 1.5)
    // vl check: rc 0.  vl run: prints `false`

Want:

    true

#### Mechanism

Under `q != null`, `nonNullNarrowTy` (check_type_shape.vl) reads `q` as a derived hole, the
non-null read of the hole parameter. `joinTys` asks `tyParamBesideBare` whether a parameter
sits beside a concrete type, and that read was not recognised as the hole. So the join fell
through to the numeric widening and the pin's `is i32` tested an `f64`; `print(r)` prints
`5` either way, which is why only the `is` test showed it.
