### D17044 — a hole lambda handed to a function that calls it once and returns it is a function tag in the callee but held as a closure by the caller

**fixed 2026-11-22 · runs, `4.5` · was: check-clean invalid wasm · `vl check` clean, `vl run` refuses an invalid module (validation error) · clause 1 · filed 2026-11-21 against master `7781e9bd` by IR-D1, found while measuring the open-parameter class · fixed by `ftReturnedPastSet` (check_fn_tag.vl): a parameter callee its function returns, where that function's result does not carry the set, keeps the set closures · fixture `closures/hole-lambda-called-once-and-returned.vl`**

Repro:

    function lap(f) {
      f(2.5)
      return f
    }
    const k = lap((a) => a + 1)
    print(k(3.5))
    // vl check: rc 0.  vl run: invalid module, the emitted module failed to validate inside
    // the module's top-level code: type mismatch: expected (ref null $1), found i32

Want:

    4.5

#### Mechanism

`lap` takes its argument as a function tag. The lambda is the only member, so the parameter is
an `i32` id, the call `f(2.5)` is a direct `call $__lambda_0`, and `lap` returns the `i32`. The
module binding `k` that holds `lap`'s result is typed as a closure (`(mut (ref null $3))`, the
closure struct), and `k(3.5)` is a `call_indirect` through that struct. The `global.set` stores
`lap`'s `i32` into it. The callee's tag decision and the caller's closure decision for the same
value disagree. The IR claims `lap` with legacy's own bytes and does not build the start body
(`call of a non-declaration`), so the faulty bytes are legacy's.

#### Where the decision was (IR-D1, 2026-11-21)

- `lap`'s body is `local.set $2 (local.get $0)` then a direct `call $__lambda_0`. That is
  `check_fn_tag.vl`'s dispatch over a one-member tagged set, `{__lambda_0}`, and `i32.const 14`
  is the lambda's tag id. The set is tagged through `lap`'s parameter and its `return f`. The
  caller's value, `k` or `lap(...)` called directly, is a closure.
- The mechanism as diagnosed before the fix, partly refuted below: the call node `lap(...)` does not carry the set (its type
  is pinned to `(f64) => f64`), so `ftScan` never visits it. `ftCtxOk`'s `RetStmt` arm admits
  the return through `ftRetCarries`, which reads `lap`'s inferred result type, not its callers'
  call nodes. The fix belongs where a set-returning function's callers are required to carry
  the set, else the set stays closures. The callee's tag decision and the escaping value's
  closure decision then become one fact, with no coercion added.
- Refuted, each with a rebuilt seed and no change in the output:
  - `ftCtxOk`'s `LetDecl` arm requiring the binding to carry the set;
  - `ftScan` refusing the set at a set-returning call whose own type does not carry it, keyed
    off `ftRetCarries`;
  - `monoBakeCallback`: gating its one decision, `monoSpecializableCallbackName`, on the
    parameter being read only as a callee. This is no bake.

#### Fix

A checker probe (`tErr` in `ftPlan`) confirmed the call `lap(...)` does not carry the set and
`ftRetCarries(lap)` is false. The read `f` in `return f` is typed at `lap`'s type parameter, so
`ftScan` never visits it and `ftCtxOk`'s `RetStmt` arm never runs. The set is tagged only through
the mint fact for `f(2.5)`, whose parameter callee `ftMintComplete` accepted. `ftMintComplete` now
also refuses a parameter callee that one of its function's return values reads when that
function's result does not carry the set (`ftReturnedPastSet`). The set stays closures, so the
callee and its caller hold the same value, and no coercion is added.
