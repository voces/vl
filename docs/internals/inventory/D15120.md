### D15120 — a call through an un-annotated `let` copy of a type-parameter function parameter, at two members, is not tagged, so it leans on the split plan

**closed 2026-11-03 · runs, prints `x 4 dup x dup 4`, without the split plan too · was a split-plan dependency · split-plan census F-B · filed 2026-11-03 against master `12de83558` · a written copy is [D15122](D15122.md)**

Repro:

    function id<T>(x: T): T { x }
    function dup<T>(x: T): T {
      print("dup")
      x
    }
    function one<F>(a: F) {
      let b = a
      print(a("x"))
      print(b(3) + 1)
    }
    one(id)
    one(dup)

Want:

    x
    4
    dup
    x
    dup
    4

#### Mechanism

With the split plan off (`compileSrc` returning after its first compile) this refused at emit: `a
function-value call has no interned signature` at `b(3)`. Every node's checked type and tag set is
the same for `let b = a` and `const b = a` (a dump diff at the late tag decision). The difference
was the elaboration's own typing of a `let` holding a function: `elabFnLetTy` widened it to the set
of every function written to it even when nothing writes it, so the late tag plan found no leaf for
that set and `b(3)` stayed a closure call. A `let` nothing assigns (`pcLetUnassigned`, the copy
record's flag) now keeps its initialiser's type, as a `const` does.
