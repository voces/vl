### D2315 — deleting enough of the map a `for`-in walks compacts it mid-walk, and the walk skips live entries

**closed 2026-09-24 — the witness prints `40`. Was check-clean silently wrong (it printed `25`,
leaving 15 keys unvisited and still in the map); found by the D2313 variant matrix, filed against
master `403fcd5e8`. Closed under the owner's ruling (a): a walk that writes the map it walks is
defined, with JS `Map` semantics (DECISIONS.md, "Deleting from a map while walking it is
defined"). Fixtures `tests/cases/maps/forin-walk-deletes-and-inserts.vl`,
`forin-walk-mutation-against-reference.vl`**

Repro:

    import { toString } from "std:fmt"
    const m: {[string]: i32} = Map()
    for i in 0 until 40 { m["k" + toString(i)] = i }
    let n = 0
    for k in m { m.delete(k) ; n = n + 1 }
    print(n)
    // prints 40

#### Mechanism

`emitMapDelete` compacted when `count - size > size + 8` (`emitMapCompact`), rebuilding `keys`,
`vals`, `live` and `hashes` from the live entries only. The walk's cursor is an index into the
entry arrays and survived the rebuild unchanged, so after the compaction at the 25th delete it
pointed 25 entries past where the survivors now started; the walk ended with 15 keys unvisited
and still in the map. Deleting ahead of the cursor without reaching the trigger was correct (a
tombstone is skipped), and so was deleting from a DIFFERENT map (D2313).

The fix: `delete` never moves an entry (it clears the live flag and nulls the key and value
refs), compaction runs on insert (a per-shape `__map_compact__` helper, in place), and since an
insert inside the walk can still compact, each entry carries an i64 insertion sequence the walk
resyncs by (`__map_resync__`); D2323 is why it is an i64. All of it is emitted only in a module
that calls `.delete`.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |

| the walked map being the deleted-from map | runs (D2313's fixture, L5) | **yes** |
| the string key (`{[i32]: i32}`) | still printed `25` | no |
