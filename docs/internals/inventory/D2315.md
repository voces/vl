### D2315 — deleting enough of the map a `for`-in walks compacts it mid-walk, and the walk skips live entries

**check-clean silently wrong — found by the D2313 variant matrix; filed against master `403fcd5e8`,
and the same on `a8a104432` (2026-09-08). Needs an owner ruling on what a walk promises when its
body deletes from the walked map; not fixed with D2313**

Repro:

    import { toString } from "std:fmt"
    const m: {[string]: i32} = Map()
    for i in 0 until 40 { m["k" + toString(i)] = i }
    let n = 0
    for k in m { m.delete(k) ; n = n + 1 }
    print(n)
    // PRINTS 25

#### Mechanism

`emitMapDelete` compacts when `count - size > size + 8` (`emitMapCompact`), rebuilding `keys`,
`vals`, `live` and `hashes` from the live entries only. The walk's cursor is an index into the
entry arrays and survives the rebuild unchanged, so after the compaction at the 25th delete it
points 25 entries past where the survivors now start; the walk ends with 15 keys unvisited and
still in the map. Deleting ahead of the cursor without reaching the trigger is correct (a
tombstone is skipped), and so is deleting from a DIFFERENT map (D2313). The fix is a choice
between deferring compaction to the next insert, counting live walks on the map struct, or
calling this unspecified the way `collections-design.md` does for list pushes.
