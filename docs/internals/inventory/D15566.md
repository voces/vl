### D15566 — [CLOSED 2026-11-09] a hole function parameter handed on inside a list literal to a callee that calls the element at two types is taken as a value with no signature

**closed 2026-11-09, runs and prints `5` then `s` · was loud emit reject, clause 2, `vl check` rc 0, then `emitProgram: a generic function taken as a value reaches no call that fixes its type — annotate the destination's function type` · filed 2026-11-08 against master `9bbf9564` · closed in the elaboration's mint facts (emit_elab.vl): a parameter read inside a list literal handed whole to a named function's parameter, or inside a `const` of one handed only whole, forwards that parameter there (`elabLitFwdTargets`), and a call through an element of the instance's own list parameter notes that parameter's set (`elabMintFactAt`), so the set the callee calls at reaches the caller's hole · fixture `functions/hole-param-list-literal-called-at-two-types.vl` · two different functions joined in the literal is [D15610](D15610.md), the hand-on beside a direct call is [D15609](D15609.md)**

Repro:

    function id(v) { return v }
    function call0(fs, x) { print(fs[0](x)) }
    function run(g) {
      call0([g], 5)
      call0([g], "s")
    }
    run(id)

Want:

    5
    s

#### Mechanism

The tag decision takes `run`'s hole at the set `{id}` only where the elaboration noted a call
through it. `run` hands `g` on inside `[g]`, which `elabMintHandedIn` did not follow to
`call0`'s parameter, and `call0` calls `fs[0]` through its own list parameter, which noted no set
for that parameter. Neither fact reached `run`, so `id` was a stub value with no instance. Both
are noted now: the read inside the literal forwards to the callee's parameter, and the indexed
call notes the parameter's set.
