### D17764 — one generic function's value, returned by a function called at an annotated and an un-annotated destination of two signatures, was built at one and called at the other

**closed 2026-11-27 by lane START-2 — the witness is refused, as the both-annotated spelling is, with `cannot take the generic function `id` as a value — a function value carries ONE signature` · clause 1 (check-clean program trap) · a function value carries one signature, so a returned literal's slot holding one generic function (a one-member set included) whose reads pin it at two signatures is refused at that value (`monoSlotPinsTwoAtOneFn`, `monoDeliverLitAt`), whatever the destination order (coordinator ruling, 2026-11-27) · fixtures `tests/cases/functions/error-returned-fn-value-read-at-two-signatures-one-annotated.vl`, `…-fn-list-value-…`, and the runs beside it `returned-fn-value-at-one-signature-per-value-runs.vl` · was: `vl check` rc 0, `wasm trap: indirect call type mismatch` · filed 2026-11-27 against master `1faa021d1`**

Repro:

    function id(a) { return a }
    function deliver() { return { f: id } }
    const v: { f: (a: f64) => f64 } = deliver()
    const u = deliver()
    print(v.f(2.5) + u.f(2))
    // vl check: rc 0.  vl run: emit reject (cannot take the generic function `id` as a value)

#### Mechanism

`{ f: id }` holds one value of the generic `id`; every read of it is one signature. Mono's flow
table already pinned the returned slot at two (`f64` from `v`, `i32` from `u.f(2)`), and with no
single pin the record field was built at one closure signature the other read then called. The
both-annotated spelling was refused at emit by the value floor; dropping one annotation must not
change that verdict. A tagged set of two or more distinct members is not this: each member has its
own signature, and its reads dispatch by id.
