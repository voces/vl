### D15032 — a lambda that captures an instance's parameter, written to a slot of a generic's value in a generic body called at two types, is check-clean invalid wasm

**closed · runs, prints `1`, `4`, `1`, `s`, `4`, `s` · was check-clean invalid wasm, clause 1, `the emitted module failed to validate inside w$1` · found closing D12212 (its grading list's capturing lambda) · filed 2026-11-02 · fixture `tests/cases/generics/generic-value-slot-written-in-generic-body-at-two-instances.vl`**

Repro:

    function id<U>(x: U): U { x }
    const fs = [id]
    function w<T>(t: T) {
      fs[0] = (x) => {
        print(t)
        return x + x
      }
      print(fs[0](2))
      print(t)
    }
    w(1)
    w("s")

#### Mechanism

Not probed. The lambda captures `t`, whose type is the instance's `T`, and `w$1` (`T = string`)
builds a capture or a call that reads the `string` where an `i32` is expected. D12212 was the
same program with `id`'s parameter named `T`; with that name capture closed, the two spellings
now fail the same way (one trapped before).

Closed. The lambda's parameter `x` is a hole typed at `id`'s open `U`, so the lambda is a hole
template, and its first instance (at `fs[0](2)`) takes over its lifted slot. The per-instance clone
of `w`'s body asked that slot for the lambda's capture count (`monoSlotOfLamNode`), found no slot,
read no capture, and shared one closure whose environment holds `w(1)`'s `t` across both instances.
The lookup now also finds the slot a template's instance holds. A clone's return typed at another
generic's variable is left open, as its parameter is (`monoLamPinRetAnn`). With `id`'s parameter
also named `T`, the capturing lambda is still invalid wasm: [D15034](D15034.md).
