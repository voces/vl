### D3180 — a record read back from an annotated map calls a declared record's field function when that record shares its field names

**check-clean silently wrong · clause 1 · pre-existing, the same on master `995bbc74e` and `a6cb22568` · found by the #3285 review (`rv3285-2112/p/y9.vl`, `c5a.vl`) · no generic needed · filed 2026-09-29 against master `a6cb22568`**

Repro:

    type R = { v: i32, f: () => boolean }
    const named: R = { v: 1, f: () => true }
    const lit = { v: 2, f: () => 11 }
    const m: {[string]: { v: i32, f: () => i32 }} = Map()
    m.set("a", lit)
    const q = m.get("a")
    if q != null { print(q.f()) }
    // PRINTS true

Want:

    11

#### Mechanism

Not localised past the ablation. The map's value type `{ v: i32, f: () => i32 }` shares its
field names and data types with the declared `R`, and a function field's rep does not depend on
its signature, so the value is claimed by `R`. The read `q.f()` then calls at `R`'s
`() => boolean`. It is D3177's claim-by-field-names reached through a map value instead of a
generic instance key, which #3285's `monoDeclFnFieldTwin` does not see.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |

| `print(lit.f())` directly, no map | prints `11` | **yes** (the map read) |
