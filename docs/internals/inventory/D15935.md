### D15935 — a refusal's wording carries the previous program's claimed pair on a shared instance

**closed · now a loud check reject worded as checked alone · was a cross-program leak: `vl check --batch` (and the LSP) worded a container refusal as the previous program's record-storage refusal, naming that program's field · filed 2026-11-12 against master `6a2ef29f` · closed the same day: the claimed-pair registers (`shapeAdaptRecStorage`, its field, the copy and width flags, the stopped-on pair) are cleared when a pass starts (`shapeAdaptFlagsReset`, check_leaf_steps.vl; `shapeAdaptPairReset`, check_type_shape.vl) · test `tests/vl_check_json_test.ts` "a refusal's wording does not carry over from the previous program" · found by `scripts/batch-order-sweep.vl`, which also reports [D15934](D15934.md)'s pair**

Repro:

    // vl check --batch a.vl b.vl, with VL_JOBS=1
    // a.vl: tests/cases/unions/record-arms-same-field-over-nullable.vl (passes)
    // b.vl:
    function sumF(xs: f64[]) { print(xs.length) }
    function idL<W>(xs: W[]): W[] { xs }
    function t<V>(q: V[]) { sumF(idL(q)) }
    t([1])
    // vl check: i32[] is not f64[]: a container never widens implicitly

#### Mechanism

`recWidenObj` sets the record-storage flag and field when it claims a pair, and the refusal that
reads it clears it. A walk that claims a pair no refusal then reports leaves both set. Nothing
cleared them per program, so `b.vl`'s container refusal took the record wording: "they store field
`n` differently", with `n` from `a.vl`.
