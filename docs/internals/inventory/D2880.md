### D2880 — two nested records whose inner field is `string` in one and a literal set in the other share the outer row

**closed · was check-clean invalid wasm, the same on master `8615a730d` · closed by D2933's binding close: `r2`'s one use hands it to the outer row's `string`-record field, so the literal is built at that record (`objLitBindDestRow`) · fixture `tests/cases/soundness/record-literal-built-at-enclosing-field-row.vl` · found by the RF lane's `field` grid · filed 2026-09-27**

Repro:

    type K = "x" | "y"
    const r1 = { f: "s" }
    const v2: K = "x"
    const r2 = { f: v2 }
    const w1 = { g: r1 }
    print(w1.g.f)
    const w2 = { g: r2 }
    print(w2.g.f)
    // vl check: rc 0.  vl run: invalid module in the top-level code — expected (ref null $type), found (ref $type)

Want:

    s
    x

#### Mechanism

Not localised past the ablation. The inner records have two rows, but `{ g: r2 }` matches the
outer row minted for `{ g: r1 }`, so it stores the literal-set row into a slot typed as the
string row. D2841's `nestedAnonRowFits` asks the literal's nested field type, which does not
catch this pair.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the first outer record (`w1`) | runs, prints `x` | **yes** |

#### Grading list

The RF grid's `field_strlit_litlit`, `field_litlit_strann` and `field_strann_litlit`.

#### Close

Closed as a side effect of D2933, not by the mechanism above. `{ g: r2 }` still picks the row
minted for `{ g: r1 }`. `r2` is now built at that row's inner `string` record, because that
field is the one place `r2` is handed on. The atom is stored as its string, and a read of `r2.f`,
the outer field and a later write through `r2` all read one struct.
