### D3110 — a lambda calling a record field's function through a parameter traps with `indirect call type mismatch` when two record layouts share the function

**closed · an instance binds a record argument that differs from its anonymous row only in a function field's type at the argument's own type, spells a pin of it by the row, and a field call in an instance picks the literal whose closure has the receiver's field type · fixture `tests/cases/closures/lambda-field-call-per-record-instance.vl` · was loads then traps · clause 1 · found by the #3274 review (`rv3274-5974/p/nb/c1.vl`, `c3.vl`) · the same on master `d408f2da4` · filed 2026-09-28 against master `d408f2da4`, closed 2026-09-28 against master `f14a8cca2`**

Repro:

    const s = { f: () => "ok" }
    const b = { f: () => 7 }
    function hole(z) {
      const k = () => z.f()
      print(k())
    }
    hole(s)
    hole(b)
    // vl check: rc 0.  vl run: prints `ok`, then wasm trap: indirect call type mismatch (before the close)

Want:

    ok
    7

#### Mechanism

`{f: () => "ok"}` and `{f: () => 7}` share one anonymous struct row, since a closure field's
layout does not depend on its signature, and the row records the first literal's type. The
monomorphizer keyed the two calls apart ([D988](D988.md)) but bound both instances' parameter to
the row's type, so the second instance believed `z.f` returns `string`: the lambda clone's return
was pinned `string` and the call through the field was keyed at `() => string` while the table
entry held `() => i32`. A direct `print(z.f())` escaped only because [D987](D987.md) resolves the
callee through the call-site argument and nothing else read the binding. Three changes, one
fact: `monoMakeInstance` binds the argument's own type where it differs from the row only in
function-typed fields; `monoPinAnnSpelling` spells a pin of that type by the row's handle, so a
lambda returning the record still names a row; and `fieldClosureFeOfRecv` inside an instance
prefers the literal whose closure has exactly the receiver's field type, since the literal scan
otherwise reaches only the row's first literal (the `const k = () => z; k().f()` face).

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `print(z.f())`, no lambda | prints `ok` `7` | **yes** (the lambda) |
| `hole(b)` removed | prints `ok` | **yes** (the second layout) |
| `function hole<Z>(z: Z)` | traps the same | no |
| `const k = () => z; print(k().f())` | traps the same | no |
| `{ n: 1, f: … }`, a data field beside the function | traps the same | no |
| two records whose function fields have the same type | runs | **yes** (the differing signature) |
