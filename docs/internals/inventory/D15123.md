### D15123 — a `let` seeded from one bare-type-parameter parameter and written from a sibling leans on the split plan

**closed 2026-11-05, runs with the split plan on and off · was split-plan dependent; the two-source half of D15122 · filed 2026-11-03 against master `a51f718e5` · closed by `pcLetSourcesOneTyParam` (check_elab_cap.vl): a `let` seeded from one parameter and written only from another, both annotated with one bare type parameter, holds a value of that one type in every instance, so `elabFnLetTy` keeps it unwidened**

Repro:

    function id<T>(x: T): T { x }
    function dup<T>(x: T): T {
      print("dup")
      x
    }
    function two<F>(a: F, a1: F, c: boolean) {
      let b = a1
      if c { b = a }
      print(a("y"))
      print(b(4) + 1)
    }
    two(id, id, true)
    two(dup, dup, false)

Want:

    y
    5
    dup
    y
    dup
    5

#### Mechanism

With the split plan off this refuses at emit (`a function-value call has no interned signature`).
`b` is written from `a1` and from `a`, two parameters sharing `F`, so the copy record's
`pcLetHoldsInit` (one source throughout) is false and `elabFnLetTy` widens it to the written
binding's set. At each call both parameters carry the same generic, which the copy record cannot
see. The fact that would close it is the elaboration's carried instance per parameter,
`elabParamCarriedInstAt(k, i)` (emit_elab.vl): `b` holds its initialiser's value where every source
parameter carries the same instance key in the frame. That is per-instance-identity work.
