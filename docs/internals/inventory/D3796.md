### D3796 — `??` in an un-annotated function whose instances pin its result to different types reads no result type, and refuses

**loud emit reject · clause 2 · found grading D3744 (lane S5) · filed 2026-10-07 against master `a37097b64`**

Repro:

    function take(a) {
      print(a[1] ?? 0)
    }
    const l: (i32 | null)[] = [null, 4]
    take(l)
    const m: (f64 | null)[] = [null, 2.5]
    take(m)
    // vl check: rc 0.  vl run: emitProgram: `??` over this nullable value is not supported yet

Want:

    4
    2.5

#### Mechanism

The generic body records the `??` node at a hole. D3744's close reads it at `nodeTyPinIxOf`, which
answers only when every call pins the hole to the same type. Here one instance pins `i32` and the
other `f64`, so the read stays the hole and the unboxing arm finds no result kind. The operand is
recorded per instance (`i32 | null`, `f64 | null`), but the result is not. A per-instance type for
the `??` node would close it, and so would a result kind derived from the operand and the default.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| every call pins `(i32 \| null)[]`, plus one `i32[]` | runs, prints `4`, `5`, `2` | **yes** |
| one call only | runs, prints `4` | **yes** |
| `take<T>(a: T[])`, declared generic | runs, prints `4`, `2.5` | **yes**, the hole |

#### Grading list

* A hole default (`take(a, d)`, `a[1] ?? d`), called as `take(l, 1.5)` and `take(k, 9)` with
  `k: i32[]`, refuses the same today.
