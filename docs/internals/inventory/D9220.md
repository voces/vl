### D9220 — a `const` choosing generic functions inside a generic body, handed to a generic parameter, is check-clean invalid wasm when the body is instanced at two types

**closed 2026-10-21 — the filed repro RUNS and prints `6`, `abab` · was check-clean invalid wasm, `vl check` rc 0, `type mismatch` inside `run$1` · clause 1 · found closing [D9190](D9190.md) · filed 2026-10-21 against master `7ad01b8b3` · closed in emit_mono.vl: each instance takes its own read of the binding**

Repro:

    function idg<T>(t: T): T { return t }
    function kg<T>(t: T): T { return t + t }
    function app<T>(g: (x: T) => T, v: T): T { return g(v) }
    function run<U>(v: U, c: boolean): U {
      const h = if c { kg } else { idg }
      return app(h, v)
    }
    print(run(3, true))
    print(run("ab", true))
    // was: vl check rc 0, vl run: invalid module, `run$1` requires `string` but the callee returns `i32`

#### Mechanism

The read `h` in `app(h, v)` is typed at `kg`'s open signature, which neither instance's
binding closes, so the pin walk left the template's read node in both instances.
`monoCoerceChoiceBinding` types that read at the first delivery, `(i32) => i32`, and the
second instance read the same node. `monoPinFnValueTy` now remakes a call argument that reads
a binding of an open choice whenever its type still holds a type variable.

The same body spelled `run<T>` ran on master only by accident. The by-name substitution
closed `kg`'s `T` with `run`'s, which happened to give the right type. D9190's fix removed
that, and this row is what it exposed.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the second instance, keeping `run(3, true)` only | runs, `6` | **yes** |
| the choice, for `const h = kg` | runs, `6` `abab` | **yes** |
| the generic body, for `run(v: i32, c: boolean): i32` called twice | runs, `6` `8` | **yes** |
