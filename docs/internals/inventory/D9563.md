### D9563 — an `i32` default for a nullable all-`i64` literal union joins at `i32`, so `+` on the result is refused

**closed · runs, prints `6000000001` · was loud check reject, clause 2 · CAPABILITY: the same `(a ?? 0) + 1` over `i64 | null` runs, binding `a ?? 0` to an `i64` first runs, and a default spelled `5000000000` runs · found closing [D9521](D9521.md) · filed 2026-10-22 against master `95725e040` · closed by computing arithmetic over a union of integer literals and integer scalars over two widths at `i64`, as an all-literal mixed-width union already was (`litIntUnionWidens` in `softenLitOpTy`, check_union_mint.vl) · fixture `literal-unions/coalesce-litunion-int-default-arith.vl` · closed with [D9561](D9561.md)**

Repro:

    type L = 5000000000 | 6000000000
    const a: L | null = 6000000000
    print((a ?? 0) + 1)
    // vl check: operator '+' is not defined for 5000000000 | 6000000000 | i32 and i32

Want:

    6000000001

#### Mechanism

The `??` joins `L` with the literal `0` at `L | i32`, and the operator check had no `+` for a
union whose members soften to two widths: `softenLitOpTy` computed an integer-literal union over
two bases at `i64`, but not one holding an `i32` scalar beside its literals. It now does, which
is the type the emitter's literal-side numeric dispatch (`njPairSideTy`) already computes such
an operand at. The `??` itself still joins as `L | i32` rather than adopting `0` into `i64`:
adopting broke `x ?? 5` over `9000000000 | 1 | null` delivered into `f64`, which converts
exactly only while the `??` stays a union (`unions/litunion-mixed-width-into-wider-number.vl`).
The same refusal reached the `if` spelling, `if a != null { a } else { 0 }` followed by `+ 1`,
which runs too.
