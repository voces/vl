### D1780 — a nested function that CAPTURES its enclosing function's parameter is lifted ONCE and shared across every monomorphized instance, so the second pin calls it with the wrong captured type: check-clean invalid wasm

**check-clean invalid wasm — `the emitted module failed to validate inside \`o$1\`: type
mismatch: expected i32, found f64` · found 2026-09-06 grading ROADMAP B15, whose emit floor
turns out to be masking this · clause 1**

Repro:

    function o(n) {
      function k(x: i32) { return x + n }
      return k(1)
    }
    print(o(2))
    print(o(2.5))
    // vl check: rc 0, "Checked 1 file, no errors."
    // vl run:   the emitted module failed to validate inside `o$1`:
    //           type mismatch: expected i32, found f64

#### Mechanism

`wasm-dis` on the emitted module names it in the function list: `$o` (param i32), `$k`
(param i32), `$o$1` (param f64) — and **no `k$1`**. The monomorphizer builds a second
instance of the enclosing `o` for the `f64` pin but not of the nested `k`, so `o$1` calls the
one shared `$k` with its `f64` capture where `$k` was emitted for `i32`.

**WHICH GATE DECLINES TO CLONE IT IS NOT YET INSTRUMENTED, AND TWO READINGS OF THE SOURCE
WERE ALREADY WRONG.** The first was that `monoPinBodyLambdas` has a `LetDecl` arm and no
`FuncDecl` arm — refuted, the `const k = (x: i32) => x + n` spelling fails identically. The
second was its `typarams.length == 0` early return, which would make this an inference-hole
generic's defect — refuted, an explicit `function o<T>(n: T)` fails identically. Instrument
the decline before fixing it; the four spellings below are the population any fix must move.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the CAPTURE (`x + 1`, so `k` is closed) | runs, prints `2` / `2` | **yes** |
| the SECOND pin (`print(o(2))` alone) | runs, prints `3` | **yes** |
| `function k` → `const k = (x: i32) => x + n` | invalid wasm, identical | no — both spellings |
| un-annotated `o(n)` → explicit `o<T>(n: T)` | invalid wasm, identical | no — both faces |
| the nested function's own use of `x` (`return n`) | invalid wasm, identical | no |

#### Grading list

* The capture-free twin and the single-pin twin, which RUN today and must keep running.
* **ROADMAP B15's emit floor is load-bearing over this row and must not be lifted first.**
  `function o(n) { function k(x) { return x + n }; return k(1) }` — the un-annotated nested
  parameter — is refused today by `emitClosureValue`'s
  `cannot take the generic function \`k\` as a value` floor, reached through
  `emitCapturedCall` because a direct call to a capturing function synthesizes a closure.
  At ONE pin that refusal is over-broad (the annotated twin runs), which is B15's own
  clause-2 complaint; at TWO pins it is the only thing standing between the program and this
  row. Build the instancing, then narrow the floor — the D965 order.
* `monoPinnedSigsOf`'s message under-reports: at two pins it still prints
  `Call sites pin \`k\` at (i32)`, naming one of the two. A fix that adopts "the unique
  pinned signature" would therefore adopt `(i32)` and miscompile the `f64` instance.
