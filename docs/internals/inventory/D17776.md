### D17776 — a ref-list row's recorded element type is read as a value's type, though several record types share one row

**closed 2026-11-28 by lane START-2 — the witness prints `4.5` · a fresh list of records delivered whole at a closed annotation is copied through `.map` (`fvaRecListMapCopy`), each element rebuilt at the annotated record · fixture `tests/cases/functions/list-of-records-set-field-through-map.vl` · was: loads then traps · clause 1 · the witness of [D17764](D17764.md)'s list form · filed 2026-11-27 against master `a1edbdabf` (lane START-2)**

Repro:

    function id(a) { return a }
    function deliver() { return [{ f: id }] }
    const v: { f: (a: f64) => f64 }[] = deliver()
    const u = deliver()
    print(v[0].f(2.5) + u[0].f(2))
    // vl check: rc 0.  vl run: wasm trap: indirect call type mismatch

Want:

    4.5

#### Mechanism

Records whose fields lower alike share one ref-list row: `{f: (i32) => i32}` and
`{f: (f64) => f64}` are one row, its function fields the one closure struct. The row records one
element type at its mint (`rlElemTyIxAt`), whichever minted it last, and a reader asking a value's
TYPE of the row gets that one: `retValBuiltListTy` gave `deliver`'s result `v`'s `f64` closures
while its literal's own stamp is the join, `{f: (i32) => i32}[]`. The rule it breaks: a row's
recorded element type is not a value's type.

Of the 27 calls of `rlElemTyIxAt`, 9 answer a type or signature question by their own use
(`retValBuiltListTy`, `listRowElemIs`, `listElemRowRep`, `listRowTyOf`, `rlElemCloSigKey`,
`slotTwinReadSigKey`, `variantElem`, `arrRefUnionElemTy`, `idxStoreClassify`'s `unionTy`); the
other 18 ask a layout question (struct index, heap, inner slot, nullability, map value slot,
union row, equality columns). No second victim found yet: two record lists of other closure
signatures in one program (`[{ f: inc }]` beside `[{ f: half }]`, bound or returned) run.
