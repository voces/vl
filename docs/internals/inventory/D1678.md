### D1678 — `vl build` validated the OUTPUT PATH read back off disk, so `-o /dev/null` failed a check-clean build

**closed — `vl build <clean program> -o /dev/null` printed `wrote /dev/null (0 bytes)` then
`Error: invalid module … unexpected end-of-file (at offset 0x0)`, rc 70; now prints the true
byte count and exits 0, matching a build to a real file · reproduced on the shared host,
2026-09-05 22:40 · filed 2026-09-05 against master `39b4f2b4a`**

Repro (the defect is in the `-o` ARGUMENT, not the program — every plain `vl check`-clean
program hits it at `-o /dev/null`; see Mechanism and Grading list for why
`check-filed-witnesses.py` cannot see this row):

    print("hello")
    // vl build hello.vl -o /dev/null
    //   was: wrote /dev/null (0 bytes)
    //        Error: invalid module
    //        the emitted module failed to validate: unexpected end-of-file (at offset 0x0)
    //        this is a bug in vl, not in your program; please report it with this file
    //        (rc 70)
    //   now: wrote /dev/null (1878 bytes)                                        (rc 0)
    // control, unchanged either way:
    // vl build hello.vl -o hello.wasm  ->  wrote hello.wasm (1878 bytes)         (rc 0)

#### Mechanism

`validate_written_module` (`scripts/vl-host/src/main.rs`) re-read `path` off disk to get the
bytes it validated, instead of validating the buffer `build_cmd` had already written — the
comment justified this by `-O`/`-O3`, which really do rewrite the file out from under the
in-memory `bytes` (binaryen's CLI, not this host). `/dev/null` discards what it's given, so
`std::fs::read("/dev/null")` came back empty, and an empty buffer fails `Module::validate`
with "unexpected end-of-file" — a message that reads exactly like a real emit bug. The write
had already succeeded; only the re-read to CHECK it had failed. The "wrote N bytes" line had
the same disease one step earlier: `std::fs::metadata(&out).len()` stats the same unreadable
path, so `/dev/null`'s real size (0) printed even though the module written to it was not
empty.

Fixed by decoupling validation and reporting from the filesystem: `validate_written_module`
now takes `bytes: &[u8]` and never touches `path` except to name it in an error, and
`build_cmd` prints `final_bytes.len()` rather than a `fs::metadata` stat. The one case that
still needs a disk read — `-O`/`-O3`, where `wasm-opt` really did rewrite `out` to bytes this
process never held — reads `out` back itself into `final_bytes` and uses that for both the
length and the validation, so the read happens once, for the one reason it is needed, and
nowhere else.

#### Ablation

| ingredient | outcome |
| --- | --- |
| `-o` a real file, no `-O` | wrote N bytes, rc 0 (always worked; N unchanged by this fix) |
| `-o /dev/null`, no `-O` | **was** wrote 0 bytes, rc 70 ("unexpected end-of-file") — **now** wrote N bytes, rc 0 |
| `-o /dev/null --no-validate` | wrote 0 bytes, rc 0 either way — validation is skipped, so there was nothing to re-read (the stale `fs::metadata` line still under-reported the size before this fix; also corrected) |
| `-o /dev/null -O` | stays broken, unrelated mechanism: `wasm-opt` is invoked with `/dev/null` as BOTH its input and output path, so it round-trips through the same unreadable file this row is about, one layer down (a binaryen CLI limitation, not this row's re-read). Not this row's scope — `-O` to a real file is unaffected |

#### Grading list

`check-filed-witnesses.py`'s three-channel classifier (`vl check`, `vl run`, `vl build -o
<tempfile>`) never passes `-o /dev/null`; it always builds to a real path. This row's own
witness therefore grades `runs` whether or not the fix is present — the doc pins the
narrative, not the regression. The regression pin is the native host test exercising `vl
build -o /dev/null` directly (see the PR's test file), which is what must be re-run to know
whether this row is still fixed.
