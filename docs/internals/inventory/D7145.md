### D7145 — a record field holding a written `let`'s first `<F>`-generic function, called through the field, has no call signature

**closed 2026-10-19 by lane L1 · runs, prints `3` · was loud emit reject · `vl check` rc 0 · clause 2 · CAPABILITY · the value-flow question treats a hole-bearing callee type as open, as it does one with a type variable · pins: `tests/cases/closures/hof-written-let-in-record-field-called-with-fn.vl` · found closing [D6885](D6885.md) · the same on master `8e787a973` · filed 2026-10-19 against master `8e787a973`**

Repro:

    function apply3<F>(g: F) { print(g(1, 2)) }
    function apply4<F>(g: F) { print(g(3, 4)) }
    function add(a: i32, b: i32) { a + b }
    let h = apply3
    const r = {f: h}
    h = apply4
    r.f(add)
    // vl check: rc 0.  vl run: emitProgram: a function-value call has no interned signature — parameter 1 of type `` has no representation in the function-value ABI

Want:

    3

#### Mechanism

The callee `r.f`'s type was `(() => _) => void`. That type carries a hole but no type
variable, so `vrCallTy` took it as closed and returned it unchanged, and mono did not record
the reached call type on the callee. The parameter then rendered empty at the function-value
ABI. A hole now counts as open, both there and in mono's reached-callee record.
