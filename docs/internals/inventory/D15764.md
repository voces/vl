### D15764 — `tySame` reads a newtype as its base, so a newtype's union and its base's union are "the same type"

**runs today and must keep running · internal predicate: the checker and the union registry keep the two apart, only `tySame` answers equal · filed 2026-11-12 against master `487d86004`**

Repro:

    type EntityId = new i32
    function f(x: EntityId | string) {
      if x is EntityId { print("id") } else { print("s") }
    }
    function g(x: i32 | string) {
      if x is i32 { print("i") } else { print("s") }
    }
    f(7 as EntityId)
    f("a")
    g(3)
    g("b")

Want:

    id
    s
    i
    s

#### Mechanism

A newtype interns as a `TyPrim` carrying its base's `primName`. Its identity lives beside the
arena (`nomNameOfTy`). `tySameAt`'s `TyPrim` arm compares `primName` alone, so
`tySame(EntityId | string, i32 | string)` is true. The checker reads the identity: it refuses
`i32 | null` where `NtI32 | null` is declared, and the reverse, and so for arguments. The union
registry keys the two rows apart too (`EntityId ; string` against `i32 ; string`). So the
program runs, with one row per union. A registry or emit change that merged rows by `tySame`
would fold the two boxes into one and answer `x is EntityId` for the plain `i32`.
