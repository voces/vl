### D15364 — an un-annotated function returning a call through an element of a widened list of functions of different results is check-clean invalid wasm

**closed · runs, prints `1.5` · was check-clean invalid wasm, `vl check` rc 0 · clause 1 · found closing [D15363](D15363.md), whose lift reaches this from a literal too · filed 2026-11-04 against master `73062b831` · closed 2026-11-04: a function read out of a hole whose type stands for a set of several members gives, called, the set's join at the call's argument types (`holeOpenFnRetAt`, check_relate_core.vl), the producer the same call reads at module scope and in the instance · fixture `tests/cases/closures/hole-fn-returns-call-through-widened-fn-list-runs.vl` · the element bound to a `const` first is [D15365](D15365.md)**

Repro:

    function inc0(a) { return a + 1 }
    function half(a) { return a / 2.0 }
    function run(xs) { return xs[1](3) }
    const xs = [inc0]
    xs.push(half)
    print(run(xs))

Want:

    1.5

#### Mechanism

The caller types `run(xs)` by substituting `run`'s hole return with the argument's binding. That
return is a call-result hole (`HD_RET`) over a function read out of the parameter, and its
resolution reached `holeOpenFnRetAt`. That asks the declaration owning the function type's first
parameter hole.

A widened list's element type is built from its first member's signature (`elabFnListLetTy` copies
`fnParamTypes` and `fnRet`), so the declaration asked was `inc0`, and the return came out `i32`. The
instance's own re-check typed the same call `f64`, through `holeSetCallRetOf` over the set its
parameter is bound to, and so did the call at module scope. The instance's return slot was the
caller's `i32` while its body returned `f64`.

A probe at the call (`retTy` before and after `substTyDeep`, the binding `?run.0 = ((_) => _)[]`)
showed the `i32` coming from the substitution alone. So the defect was the checker's inferred
result, not emit reading the first member.
