### D9311 — un-annotated functions of different results written into one un-annotated `Map()` have no map value type, where the same pair in a list is refused at check

**closed 2026-11-03 · runs, prints `1.5` · was a loud check reject from 2026-10-21, graded DESIGN then, a grade the list spelling running since [D14646](D14646.md) retired · before that loud emit reject, `unsupported map value type`, `vl check` rc 0 · clause 2 · closed with [D15137](D15137.md), the same program filed again from D14648: `holeSlotJudge` lifts its comparison for a map whose slot writes `elabSlotJoinTy` joined. The 2026-10-21 close judged a map's `.set` and index writes, and its `.get` and index reads, as a list's elements are judged; the index read is [D15139](D15139.md)**

Repro:

    function inc0(a) { return a + 1 }
    function half(a) { return a / 2.0 }
    const m = Map()
    m.set("a", inc0)
    m.set("b", half)
    const x = m.get("b")
    if x != null { print(x(3)) }
    // vl check rc 0.  vl run: emit error: emitProgram: unsupported map value type (no rep for a union-member struct, ...)

#### Mechanism

Not traced. The two writes give the value slot two results at the pinned `(i32)`, so the
map's value type stays open and the emitter has no rep for it. The list spelling
`const xs = [inc0, half]` is refused by `vl check` (`cannot store 'half' in an element
of 'xs': called at (i32) it returns f64, where 'inc0', also stored in it, returns i32`);
a map write has no such check, so the refusal reaches the emitter instead.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the `inc0` write | runs, `1.5` | **yes** |
| the map (`const xs = [inc0, half]`) | loud check reject | **yes** |

#### Why the refusal is owed

The design rule is the list twin's, not a mechanism: a call through a value read from the
map may run any function written to it, and a call has one result type, so every such
function must return one type at the call's argument types. `inc0` returns i32 and `half`
f64 at `(i32)`, so no type for `x(3)` holds for both. Annotating the map's value type
(`Map<string, (a: f64) => f64>`) or the parameters is the spelling that runs. Functions
of one result are not refused (`m.set("a", inc0)`, `m["b"] = dbl` runs, printing `6` and `4`).
