### D14723 — the elaboration keys no instance for a call that hands a relayed hole lambda to an un-annotated parameter; mono's flow-table pin is its only answer

**runs today and must keep running · step 2 residue (architecture-target-2026-10.md): `monoPinHoleParam`'s `monoOpenFnFlowPin` rung cannot go until the elaboration closes this key · found ablating that rung · filed 2026-10-31 against master `8f2ad9c3f`**

Repro:

    function fw(f) { return f }
    const lam = (x) => x
    const q = fw(lam)
    print(q(3))

Want:

    3

#### Mechanism

`fw(lam)` hands an un-annotated lambda to an un-annotated parameter, so the argument's type is
an open function type and the call's key stays open. The elaboration therefore mints no
instance for it, and `elabCallParamTy` is -1 at the call. The type it runs at,
`(i32) => i32`, is known only to the fn-flow table, which pins the lambda by its call past
`fw` (`q(3)`). Mono reads that through `monoOpenFnFlowPin` (D6001). With the rung ablated,
this witness is a loud emit reject (`unsupported argument type for 'f' in a call to 'fw'`),
as are D6201, D6241, D6262 and the fixture `closures/hole-fn-or-lambda-through-hole-handed-on.vl`.

The fix is for the elaboration to close the key at the flow table's pinned signature. Mono's
rung then goes.
