#### Mechanism

The span was the `type W` line, not the construction, and the ablation says why: **deleting
`const w: W = …` left the refusal exactly where it was.** `collectNestedFieldShapes` interns
each declared field's inline shape through `internInlineShapeTy` BEFORE `collectS` builds the
struct table, so a nested shape whose own field is `A[]` or `A[] | null` was classified while
`A` had no row — and both halves of the mint asked the table.

Instrumented rather than read off the code path, with the failing witness as the control:
`PROBE inline-field-uncoded nm={xs:A[]|null} txt=A[]|null arena=-2 name=-1` for the code-28
face, and `PROBE code5-elemname-EMPTY nm={xs:A[]} txt=A[] deferred=[A]` for the code-5 one —
the deferred key was already computable and unused. So two sentences, two halves, one
pass-order cause: the CODE (`nameFieldCodeTy` had no arena `S[] | null` rung, only
`fieldCodeOfSpelling`'s node path did) and the KEY (the code-5 and code-28 recorders gave up
on `""` where `shapeFieldElemName` answers `A`).

The element KIND is the ingredient because the two tables are filled at different times: a
UNION element ran at both seeds (`collectU` fills `unNames` before the declaration walk),
only a declared STRUCT element could be classified before its own row existed.
