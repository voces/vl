Repro:

    function id1(a) { return a }
    const xs = [{ f: id1 }]
    let i = 0
    print(xs[i].f(2))
    print(xs[i].f(2.5))
    const ys = [{ f: id1 }]
    print(ys[0].f(2.5))

Want:

    2
    2.5
    2.5

The row was filed with `xs[1]`, past the literal's length; that program now validates, prints
`2` and traps out of bounds, as it says.

#### Mechanism

`ys`'s one use builds its literal at that use's closures: the binding takes the annotation
`{f: (f64) => f64}[]` (`recStoreMismatchMsg`'s literal rule), so its record's field is `id1`'s own
instance there, not an id. The tag plan read `ys`'s literal as a holder of `{id1}`'s ids, refused
it because its binding is annotated (`ftHoldCtxOk`), and refused `id1` at the field
(`ftNamedAtClosed` asked only the record solve's own places). The set stayed closures, and the
calls through `xs` met one closure at two signatures. The plan now takes such a literal as holding
closures, one list level deep.

The original analysis follows.


`xs[1]` is past the literal's length, so mono cannot read the element it names
(`monoFlowElemAt`), and the list's field stays one closure. Fn-tag would tag `{id1}` and dispatch
each call by signature, as it does without the second list; with it the plan refuses (a direct
call `id1(2.5)` beside the list refuses the same way, at `ftCtxOk`). The closure is built at
`f64`, and `xs[0].f(2)` called it with a converted argument and read its `f64` result as `i32`.

The function-value call (`emitCallRefAt`, wasmEmit.vl) now refuses a wider result read as `i32`,
and a string or heap argument into an `i32` parameter, beside the wider-number argument it
already refused. A direct call of a member counts as a call of the set before the elaboration too
(`ftMemberDirectCall`, no longer late only), so the `id1(2.5)` spelling runs to its out-of-bounds trap. Fixtures:
`tests/cases/soundness/fn-value-closure-built-wider-than-an-i32-call-reject.vl` and
`fn-value-closure-built-at-i32-read-past-its-length.vl`.
