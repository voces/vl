### D16794 — a parenthesised `??` over a hole map parameter's `get`, read as an `f64`, builds an invalid module

**closed 2026-11-16 by lane L2-S2 · runs, prints `1.5` · was check-clean invalid wasm, clause 1 · `tests/cases/maps/hole-param-parenthesised-coalesce-read.vl` · found grading the S3.4a floor-removal experiment ([D16714](D16714.md)) · filed 2026-11-16 against master `d59e4401` · the same read through [D16795](D16795.md) trapped the compiler and through [D16797](D16797.md) refused at emit**

Repro:

    const m: {[string]: f64} = Map()
    m.set("a", 1.5)
    t(m)
    function t(q) { print((q.get("a") ?? 0.0)) }
    // vl check: rc 0.  vl run: invalid module inside `t`, "type mismatch: expected i32, found f64"

Want:

    1.5

#### Mechanism

`exprScalarWidth` (`emit_classify.vl`), which picks `print`'s import, asked `coalResultTyOf` only
of a bare `??`. A parenthesised one read the Paren node's recorded type, which inside a hole's
instance is the open type the body was checked at, and fell to `__print_i32__`. It now peels the
parentheses first, through `exprValueTyAt`, which D16795's operand read shares.
