**loud check reject, by design, and the diagnostic now names the function · plumb PL-070 (its diagnostic half; the typing half, inferring a literal-only return from the function-value context, is an owner ruling in PL-054/PL-056's family) · filed and fixed 2026-09-28 against master `6c2dafc0b` · typing unchanged: `vl check` verdict and error count identical on all 11,690 tests/cases, distilled-corpus and std programs**

Repro:

    function never(x: i64) { -1 }
    function apply(f: (i64) => i64, v: i64): i64 { f(v) }
    print(apply(never, 3 as i64))
    // master: argument 1: expected (i64) => i64, got (i64) => i32   (nothing names line 1)
    // now:    … — `never` returns the literal `-1` on line 1, so its return defaulted to `i32`;
    //         annotate it: `function never(x: i64): i64 { … }`

#### Mechanism

An un-annotated function whose every return (a tail value, `return <literal>`, or several) is a
bare numeric literal gets the literal's default type, `i32` or `f64`, as its return, so its
value is refused wherever a function type with a wider return is wanted. D2860/D2966/D2977's
note looked only for literal BINDINGS. The destination sites that know their type (argument,
explicit and tail return, annotated `let`/`const`, and now assignment) raise through
`tErrWant`; `numLitFnNoteQueue` walks the refused value against that type through record and
list literals to a function name (`lookupFnDeclNode`) or a lambda binding (a new depth-paired
`fnLitBind*` table, so shadowing holds) whose `FuncDecl` has no return annotation and no type
parameters, the same parameters, a return the literals also fit (`numLitFitsStore`), and every
literal kept exactly (`numLitValuesFit`: an `f32` only up to 2^24). The note names the function,
each literal and its line, and the declaration re-spelled with the annotation (`function f(…): T
{ … }`, or `const k = (…): T => <literal>` / `=> { … }` for a lambda). It is withheld, per
function, when no single annotation fixes every use: another read of the name that is not a
noted delivery and not a call whose result still checks at the suggested type
(`numLitUseAccepts`, a discarded call statement, or an annotated `let` the type fits) — a value
use where `i32` is wanted, an alias, a reassignment — or when two notes on one function suggest
different types.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the literal return (`x as% i32`) | the bare mismatch, no note | **yes** |
| the missing return annotation (`: i32`) | the bare mismatch, no note | **yes** |
| the function-typed destination (`const y: i64 = never(1)`) | accepted, `i32` widens | **yes** |
| a named function (a lambda binding `const k = (x: i64) => -1`) | still refused | no — same note, lambda spelling |
| an inline lambda (`apply((x: i64) => -1, …)`) | runs: contextually typed | **yes** |
