### D16040 — a list of a generic call's records keys its ref-list row at the call's untagged checker type

**closed 2026-11-13 — the name lookup is deleted; the element finds the row recorded at its type up to function-value sets · was runs today and must keep running, 6 programs of the sweep population · filed 2026-11-13 against master `1a24ba21`**

Repro:

    function inc0(a) { return a + 1 }
    function mk<T>(x: T) { return { fs: [inc0], x: x } }
    const rs = [mk(1)]
    print(rs[0].fs[0](2))

Want:

    3

#### Mechanism

Two ref-list rows are minted for the list of `mk`'s records.
- The global literal `[mk(1)]` mints one in `collectAArrayLit`'s record-list arm. Its mint hint
  (`arrLitMintHintTy`) declines a record, so the key resolves from the element name. Its held
  rep (D15350) sits on the list node, and that element type is the instance's TAGGED record
  (`{fs: i32[], x: i32}` stored).
- The row `rlElemStructRow` is asked about is minted elsewhere, from a CHECKER type (the
  binding's or the read's), as `{fs: ((i32) => i32)[], x: i32}` with `fs` untagged.

The values are built at the tagged record, and its row key differs (`repRowId` 13 against 9), so
no type rung finds the row and it is found by the element NAME. Keying the literal's slot by its
held rep only adds a second row. The fix is that a list type of function-holding records minted
from a checker type is minted at the stored (tagged) type its values carry. That type exists only
on value nodes today. The trace is lane D's and lane F's, on master `739db770`.
