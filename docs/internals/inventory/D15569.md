### D15569 — a width-generic numeric intrinsic as a value takes its default width, not its destination's

**closed 2026-11-08 (`ivSeedWidth`, `compiler/check_intrinsic_values.vl`) · the filed repro RUNS and prints `2` · was loud check reject · the destination picks the overload: a function-typed destination seeds the forwarding lambda #6876 mints, and its parameters take that width when the intrinsic computes at it (f32/f64 float, i32/i64 integer, all four for `min`/`max`/`abs`); with nothing pinning it the f64/i32 default holds · fixture `tests/cases/intrinsics/intrinsic-as-value-destination-width.vl` · matrices `intrinsic-numeric-pinned-{f32,i64}-as-value` annotated face 0 -> 31 of 32 each · filed 2026-11-08 on the D2621 fix branch**

Repro:

    const g: (f32) => f32 = sqrt
    print(g(4.0))
    // vl check: cannot assign (f64) => f64 to 'g' of type (f32) => f32

#### Mechanism

D2621 lifts an intrinsic in value position into a forwarding lambda before the checker runs, so
the lambda's parameter types cannot read the destination when it is built. They are re-widthed
when the destination seeds the lambda (`seedExpected`, and a list method's element), before the
lambda is checked. Wrapping by hand, `(x: f32) => sqrt(x)`, already ran.

#### Grading list

- the repro must print `2`.
- `const h: (i64) => i64 = clz` then `print(h(1 as i64))` must print `63`.
- `return_inferred` stays at the default: `function d() { sqrt }` has no destination to read.
