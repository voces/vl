### D16836 — a list of lists of records holding un-annotated functions of different result types is refused at check where a function returns it, where a returned list of the records runs

**loud check reject · clause 2 · residue of D16824 · found by lane WIDTH closing D16824 · filed 2026-11-16 against master `a78100c9b`**

Repro:

    function inc0(a) { return a + 1 }
    function half(a) { return a / 2.0 }
    function mk() { return [[{ f: inc0 }], [{ f: half }]] }
    const xs = mk()
    print(xs[1][0].f(3))
    // vl check: cannot store 'half' in 'xs[][].f': called at (i32) it returns f64, where 'inc0', also stored in it, returns i32 — every function a call through 'xs[][].f' may run must return one type

Want:

    1.5

#### Mechanism

D16824 lifts a list of lists' element field only where list literals build every level
(`holeSlotListLitsFrom`); a list a call returns is not lifted. Lifting the call path too (after
D16824's slot-order fix) leaves two refusals:

- `mk()[1][0].f(3)`, read straight off the call, is refused at emit by `retStorageMismatch`
  (`wasmEmit.vl`): the returned literal's ref-list slot is the held rep's (`{f:i32}[]` as its
  element), but the function's recorded result (`fnRecordedRetTy`) and the literal's rep stamp are
  both the unstamped `{f: (_) => _}[][]`, so the result has no ref-list row. The returned literal
  reaches `monoRetFnListTy`, whose `elabRetTaggedJoinTy` (D15226) builds a returned literal at the
  result's tagged join only where the result's set at that path is tagged. Here the result's set
  is the join of the two inner lists' sets, which the elaboration's join note does not record
  (`elabFnArmJoinAt`: "a join of lists of two sets is not noted"), so it is never decided, and
  `elabHeldValTy` of the literal is -1.
- `const xs = mk(); xs[1][0].f(3)` is still refused by the judge: the read's set does not hold
  `half` (`holeSlotSetHolds`). A bound list-of-lists literal joins its sets through the binding's
  slot widening (`elabFnListLetTy` / `fnListWidened`, D14645); a function result has no binding.

Giving the returned literal a deep rep in `fnTagLitRep` changes neither, and nor does noting each
inner list's type against the first as a return join (`elabFnRetJoinNote` from the return
check), so the note alone does not decide the result's set. The next step is to trace why the
result's joined set is not tagged when its members are (the held rep is `{f:i32}[]`), then the
judge's call-path lift.
