### D2574 — `x.pop()` over a generic `T[]` returned un-annotated declares an `i32` result

**closed 2026-09-26 — the filed repro RUNS and prints `false` · was check-clean invalid wasm · clause 1 · pre-existing on master `dcc88a350` · found by #3174's review · filed 2026-09-26 · fixture `tests/cases/generics/pop-over-type-param-list-inferred-return.vl`**

Repro:

    function f<T>(x: T[]) { return x.pop() }
    const r = f([1.5, 2.5])
    print(r == null)
    // vl check: rc 0.  vl run: invalid module inside `f`, "type mismatch: expected i32, found f64"

#### Mechanism

Two halves, both in the per-instance clone (`emit_mono.vl`). (1) The instance walk rebuilt an
expression only when one of its operands changed, so `x.pop()`, whose operands are shared with
the template, kept the template's recorded type `T | null`. `emitPop` picks the checked,
boxed read from that type, so every instance emitted the raw element read (at `i32` the caller
then read a box that was never built). The walk now re-makes any expression whose recorded type
names a type parameter the instance binds (`monoPinRetype`), and registers the value box a
nullable number needs, which the collect pass had no expression to find (`monoPinRecordTy`).
(2) The instance's un-annotated result came from D2037's rung, which read the template's checked
return only when it named no type parameter, so `T | null` fell to the `i32` default. That rung
now reads the return at the instance's binding. The annotated `: T | null` spelling was invalid
wasm too, through half (1) alone.
