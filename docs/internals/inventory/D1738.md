### D1738 — once a struct is a union VARIANT, its own object literal resolves against another struct's row, and any second declared struct is enough

**closed 2026-09-06 — the same resolver D1737 names: the return seed for `pendingStructIdx`
now answers a struct row only, and finds a variant's structurally-named row through the arena ·
filed against master `6de9fd11a` · 0 corpus cells**

Repro:

    type A = { r: i32 }
    type W = { g: i32 }
    function st(): A { return { r: 8 } }
    function mkS(): string | null { return null }
    const v = mkS()
    const k = v ?? st()
    if k is A { print(k.r) } else { print(0) }
    // prints 8 since the close; before it, `vl check` rc 0 then exit 1,
    // emitProgram: object literal is missing a struct field

#### Mechanism

`st()`'s body is the literal `{ r: 8 }` and its declared return type is `A`, so nothing about
the literal is ambiguous. The return path seeds `pendingStructIdx` from `retStructIndex`, which
answers a VARIANT-table index where its name scan misses — and the name scan misses because a
struct that becomes a union variant through an INFERRED join is registered under the structural
render, not under `A`. `emitObj` then walks `W`'s field list and reports `A`'s own field as
missing.

Probed at `emitObj` on the witness: `pin=0 si=0 rows=[0:W:g][1:{r:i32}:r]` — the seed is 0, row
0 is `W`, and `A`'s row is 1 under a structural name. Declaration ORDER is not the ingredient
(`A` first and `W` first behave alike), and neither is arity; what is needed is a second struct
row and the join.

The close is D1737's: `retStructRowIndex` answers struct rows only and resolves a
structurally-named row by its recorded TYPE, and every struct-row reader takes it.
