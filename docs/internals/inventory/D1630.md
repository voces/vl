### D1630 — a UNION-typed `__array_new__` fill matches no arm of the kind ladder, so the list is allocated as the i32 list

**check-clean invalid wasm · `vl check` rc 0 · clause 1 · a nullable-struct, nullable-`i32`,
nullable-`f64` or value-union fill, at module scope, in a function and through a generic
wrapper alike; a `string | null` fill and a `boolean | null` fill run · filed 2026-09-05
against master `b292eb83` from `scripts/capability-probes/array-new-nullable-ref-fill.vl`, one
of the four SILENT probes `run.py` reports**

Repro:

    type Node = { count: i32, symbol: i32 }
    function mk(): Node | null { return { count: 1, symbol: 2 } }
    const seed: Node | null = mk()
    const a: (Node | null)[] = __array_new__(2, seed)
    const e = a[1]
    if e != null { print(e.symbol) }
    // vl check: rc 0.  vl run: the emitted module failed to validate inside the module's
    //   top-level code: type mismatch: expected i32, found (ref null $type)

#### Mechanism

`arrNewIntrKind`'s ladder asks its fill ten questions — `exprIsF64`, `exprIsI64`,
`exprString`, `ObjLit`, `exprStruct`, `exprIsClosure`, `exprArray`, `exprRefArray`,
`exprStringArray`, `exprMap` — and a `Node | null` ident answers none of them, so the ladder
falls through to its unnamed `return 0`, the i32 list. The disassembly shows the module
interning the correct pair for the destination and then not using it: `$5 = (array (mut (ref
null $0)))` with wrapper `$6` is `(Node | null)[]`, and the emitted allocation is `(struct.new
$4 (array.new $1 (global.get $global$0) …))` — `$1 = (array (mut i32))` and `$4` its wrapper,
handed a `(ref null $0)` fill.

The two spellings that run do so for two different reasons, which is why neither of them
narrows the row: `string | null` is claimed by the string arm, whose classifier is already
`| null`-aware, and `boolean | null` is an i32 niche, so the fall-through happens to be the
right answer. The same gap has a LOUD face — a fill written as a struct LITERAL under a
`Node | null` annotation refuses with `emitProgram: __array_new__ fill type not yet supported
natively` — so `mk()` is what selects the silent channel, and a fix owes both.

#### Grading list

* `scripts/capability-probes/array-new-nullable-ref-fill.vl` — the standing probe, GAP today.
* The three spellings that RUN and must keep running: the `string | null` fill, the
  `boolean | null` fill, the non-nullable `Node` fill into a `(Node | null)[]`. They are
  `d1630_*` cells in `scripts/silent-sweep/distilled/named/`.
* The LOUD face, `emitProgram: __array_new__ fill type not yet supported natively` on a
  struct-literal seed: a close that leaves it refusing has closed half the row.
* `std:array.filled` inherits every one of these (`docs/internals/std-notes.md`), so its
  fixtures are the consumer-side grading list.
* PREDICTION, to be graded rather than assumed: D1631 falls through the same `return 0`, and
  a fix that took the kind from the DESTINATION — as `arrNewDefaultKind` already does for
  `__array_new_default__` — would close both. A fix that only adds a union ARM closes this
  row alone. Re-grade D1631's cells either way; do not assume the residue.
