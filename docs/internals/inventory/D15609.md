### D15609 — [CLOSED 2026-11-10] a hole function called directly at one type and handed on inside a list literal to a callee that calls the element at another is refused by the checker

**closed 2026-11-10, runs and prints `5` then `s` · was loud check reject, clause 2, `argument 1: expected i32, got string (the call of \`f\` at the call's argument types)` · filed 2026-11-09 against master `d4901c70` · closed in the hole-instance walk (check_relate_core.vl): a hand-on of the hole inside a list literal, or a `const` of one, counts as an open call (`holeBindArgListsHole`), so the argument stays generic and each call takes its own instance · fixture `functions/hole-param-called-and-handed-on-in-list.vl` · the nested-list hand-on is [D15637](D15637.md), the record-field one [D15638](D15638.md)**

Repro:

    function id(v) { return v }
    function call1(f, x) { print(f(x)) }
    function call0(fs, x) { call1(fs[0], x) }
    function run(g) {
      call1(g, 5)
      call0([g], "s")
    }
    run(id)

Want:

    5
    s

#### Mechanism

At `run(id)`, `instGenFnHolePins` instantiates the generic `id` at the one instance every call
through `run`'s hole takes (`holeBindInstance`). That walk counts the direct call `g(5)` and
follows `g` handed on bare to a callee's hole parameter, but it did not see `g` inside `[g]`.
So it found one instance, `(i32) => i32`, and the listed hand-on's re-recorded demand (`g`'s
parameter at `string`) was checked against it. With no direct call the walk sees no call, and
`id` stays generic (D15566's spelling).
