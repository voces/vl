### D2835 — an annotation `T[] | string[]` in a generic body resolves to `T[]`, so a concrete list bound to it is refused at every pin that binds `T` apart

**loud check reject · clause 2 · the concrete spelling runs · the same on master `0eae57b89` · 28 cells of `uj/g1` (`ann_is` and `ann_arg`, concrete arm first) · filed 2026-09-27 against master `0eae57b89`, found grading D2832**

Repro:

    function f<T>(xs: T[], ys: string[]) {
      const r: T[] | string[] = ys
      if r is string[] { print(r.length) } else { print(0 - r.length) }
    }
    f([2.5], ["a", "b"])
    // vl check: rc 1 — cannot assign string[] to 'r' of type f64[] (the body of `f` at the
    // call's argument types)

#### Mechanism

The annotation route dedups its members with `sameVariantTy` (`annUnionPushDistinctMember`,
`pushDistinctVariantTy`), and `T[]` and `string[]` are mutually assignable through `T`, so the
union keeps one member: `const z: i32 = r` in the body reports `cannot assign T[]`. The binding
records the pair for its pin (D572), which then compares `string[]` with `f64[]`. D2760 made two
type parameters' lists apart in `sameVariantTy`; a type parameter's list beside a concrete one is
not, outside the return-set join. Keeping the two members makes `r.length` in the body a check
reject at every pin, including the agreeing ones that run today, so the fix needs that read
deferred to the pin as D2832 does for a join.
