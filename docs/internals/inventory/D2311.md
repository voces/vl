### D2311 — `vl build -O` paid for work and memory the optimised module never used: the `vl-src` section it strips, the compiler's heap held through `wasm-opt`, and one binaryen thread per core

**closed 2026-09-24 — plumb units at `--names -O --import-memory`, median CPU of 5 interleaved: `chunk_550` 1.40 → 0.99 s, `chunk_662` 5.38 → 3.54 s, `chunk_466` 8.19 → 6.50 s (with D2309/D2310); process-tree peak RSS 212/503/663 → 169/417/420 MB; output byte-identical · a host cost, not a miscompile: the witness runs, and the behaviour is graded by `tests/selfhost_native_opt_test.ts` and `tests/selfhost_native_release_escape_test.ts` · filed 2026-09-24 against master `ab942030b`**

Repro:

    function f(n: i32): i32 { n * 2 + 1 }
    print(f(20))
    // runs, prints `41`. Build it `vl build --names -O`: the module carries a `name` section
    // and no `vl-src`, as before, and `wasm-opt` is handed BINARYEN_CORES <= 4.

#### Mechanism

Three costs in `build_cmd` (scripts/vl-host/src/main.rs). A `--names` build asked the seed
for `vl-src`, whose rows are offsets into the unoptimised bytes, and the `-O` path then stripped
it: `emitSrcSection` was 4.8% of `chunk_466`'s compile. The compiler's `Store` stayed alive
through both `wasm-opt` runs although an optimised build never reads it again, so the tree
held the compiler's 420 MB GC heap and binaryen's working set at once. And `wasm-opt` ran with
binaryen's default of one worker per core: on the 24-core box that cost 1.2–1.7x the CPU of a
four-thread run and up to 2.5x the memory, for the same bytes.

#### Fix

`Names::NoSrcMap` asks the seed not to build `vl-src` (`setEmitSrcMap(0)`, a no-op on a seed
without the export); an optimised build drops the compiler session before the first `wasm-opt`;
and `wasm-opt` gets `BINARYEN_CORES=min(4, cores)` unless the caller set it.
DECISIONS.md, "`wasm-opt` runs on at most four threads".
