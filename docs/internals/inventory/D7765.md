### D7765 — a string interpolation hole counts as a call that may end a narrowing, on a function's first check

**closed 2026-10-20 · runs, prints `0` then `g g` · was loud check reject (`'g' is no longer narrowed to G: the call earlier in this statement may reassign it`) · clause 2 · only on a function's first check: `inferReturnsPrePass` checked an un-annotated function quietly first, so annotating the return was what exposed it · pin: `tests/cases/soundness/string-hole-render-keeps-narrowing.vl`, and the two spurious reads it took from `tests/cases/soundness/call-keeps-narrowing-callee-local-refused.vl` · found while narrowing the pre-pass (D7761) · filed against master `573358403`**

Repro:

    type G = { name: string, ty: i32 }
    function find(k: i32): G | null {
      if k > 0 { { name: "g", ty: k } } else { null }
    }
    function nested(): string {
      let g = find(2)
      const k = (): i32 => {
        g = null
        0
      }
      print(k())
      g = find(3)
      if g != null { return "\{g.name} \{g.name}" }
      "none"
    }
    print(nested())

Want:

    0
    g g

#### Mechanism

A string-typed hole's render call is rewritten in place to a `Paren` around the hole
(`tplHoleHandled`). The `Call` arm of `checkNodeReal` then asked `noteCallInvalidations` of
that index. It is no longer a `Call`, so it was taken for an operator site that dispatched to
no declaration, and such a site may reach any writer of `g`. The rewrite happens on the first
check only. A re-check finds a `Paren` already and asks nothing, so a function checked twice
never saw it. The `Call` arm now skips a node that has become a `Paren`.
