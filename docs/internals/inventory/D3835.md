### D3835 — a for-in over an inline list literal whose element is a generic call on an enclosing `<T>` binds the loop variable at `i32`, so a `boolean` prints `1`

**check-clean silently wrong · found in review of lane SC · filed 2026-10-08 against master `cd42914e6`**

Repro:

    function id<U>(u: U): U { u }
    function outer<T>(x: T) { for e in [id(x), x] { print(e) } }
    outer(true)
    // vl check: rc 0.  vl run: rc 0, prints 1 then 1

Want:

    true
    true

#### Mechanism

Inferred from the ablation, not read off the code. The loop variable's type is taken from the inline literal's element, which is a call to a generic `id<U>` whose argument is a `T`-typed value of the enclosing generic. At the `outer<boolean>` instance that element is delivered at the `i32` rep a `boolean` shares, and `print` then sees an `i32`, not a `boolean`. Every other spelling that names the list or the element differently prints `true`: binding the list first, indexing the literal, a non-generic `id`, and a concrete `outer`. `string` and `f64` are unaffected, which fits a rep-sharing cause (`boolean` and `i32` share one), so the defect hides at any `T` whose rep another type shares.

#### Grading list

* The same program at a `u8`-like or other type sharing a rep with another, and at a record `T`.
* `for e in [id(x), x]` with `e` consumed by `e == x` and `if e { … }` rather than `print`.
* The un-annotated and annotated (`const ys: T[] = …`) bound-list spellings, which print `true` today and must keep doing so.
* The nested-generic rows of lane SC (D3831 and its neighbours); re-grade them together in case the cause is shared.
