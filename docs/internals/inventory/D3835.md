### D3835 — a for-in over an inline list literal whose element is a generic call on an enclosing `<T>` binds the loop variable at `i32`, so a `boolean` prints `1`

**closed 2026-10-08 by lane SC · was check-clean silently wrong · found in review of lane SC · filed 2026-10-08 against master `cd42914e6` · pins: `tests/cases/generics/for-in-literal-of-generic-call-at-pin.vl`**

Repro:

    function id<U>(u: U): U { u }
    function outer<T>(x: T) { for e in [id(x), x] { print(e) } }
    outer(true)
    // vl check: rc 0.  vl run: rc 0, prints 1 then 1

Want:

    true
    true

#### Mechanism

`iterElemPinTy` answers a for-in loop variable's element type at an instance. Its list-literal
arm knew a literal of the instance's own parameter (`[x, x]`) and a literal of plain reads
(D3066), and nothing else, so with a generic call among the elements it gave no answer and the
variable fell back to the `i32` rep a `boolean` shares. The arm now substitutes the literal's
recorded `T[]` through the instance's binding (`pinSubOperandTyOf`), as a bound list is read.

#### Grading list

* The same program at a `u8`-like or other type sharing a rep with another, and at a record `T`.
* `for e in [id(x), x]` with `e` consumed by `e == x` and `if e { … }` rather than `print`.
* The un-annotated and annotated (`const ys: T[] = …`) bound-list spellings, which print `true` today and must keep doing so.
* The nested-generic rows of lane SC (D3831 and its neighbours); re-grade them together in case the cause is shared.
