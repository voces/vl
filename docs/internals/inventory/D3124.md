### D3124 — a second `<Z>` instance at a nullable record pin calls the first instance's field function

**closed · a member call's receiver typed at a type parameter reads the instance's own binding of it (`valueReadPinTy`, past its `null`) when choosing which record literal's closure types the call, so a `Z | null` pin reads its own record · fixture `tests/cases/generics/nullable-pin-field-function-per-instance.vl` · was check-clean silently wrong · clause 1 · the `nullable__gen__*__b_i` and `listel__gen__*__b_i` cells of the #3276 review's D3110 grid · the same on master `cc890c9f4` · filed 2026-09-28 against master `cc890c9f4`, closed 2026-09-29 against master `07d414042`**

Repro:

    function F<Z>(z: Z | null) { if z != null { print(z.f()) } }
    const r0 = { f: () => true }
    const q0: { f: () => boolean } | null = r0
    F(q0)
    const r1 = { f: () => 7 }
    const q1: { f: () => i32 } | null = r1
    F(q1)
    // vl check: rc 0.  vl run: prints true, then true

Want:

    true
    7

#### Mechanism

The two records share one anonymous row. The call dispatches through the record's own
closure, so the value is right, but `exprIsBool` asks which literal's closure the field holds
(`fieldClosureFeOfRecv`), and D3110's rung reads the receiver's type only where the instance is
keyed by its exact pins. A `Z | null` instance is not, the narrowed `z` still reads `Z`, and
the walk answered the first literal's `() => boolean`, so `7` printed as `true`. The receiver
now reads the instance's parameter annotation, past its `null`.
