### D2469 — a `Set()` passed as a `{[string]: boolean}` parameter answered `.values()` with its membership booleans, not its elements

**now a loud check reject 2026-09-25, by owner ruling Q2 — `Set<T>` is its own type, so a set no longer satisfies a `{[K]: boolean}` parameter; the `Set<string>` parameter prints the elements · was check-clean silently wrong (printed `true`, want `a`) · design doc `collections-representation-design.md` §10 F1 (`critic-learn/r1.vl`) · filed 2026-09-25 against master `086466d1a`**

Repro:

    function f(t: {[string]: boolean}) { for v in t.values() { print(v) } }
    const s: {[string]: boolean} = Set()
    s.add("a")
    const m: {[string]: boolean} = Map()
    m["b"] = true
    f(s)
    f(m)
    // was: true, true — now: cannot assign Set<string> to 's' of type {[string]: boolean}

#### Mechanism

A set was the map rep with a flavor bit, and the emitter read the flavor off the BINDING that
built it (`letIsSet`: an initializer that is a `Set()` call). Through a parameter, field or
return the flavor was gone, so the emitter walked `vals` and printed the membership booleans.
The checker agreed with neither: its `mSet` bit was written only by `Set()` and by a graft onto
an annotated binding. With `Set<T>` a distinct type (`mSet` 1 at every spelling, assignable to no
map), the emitter's shape resolver reads the flavor from the expression's TYPE
(`setShapeOfTy`, first in `mapShapeOfExpr`, and in `letIsSet`), so every position agrees.

#### Ablation

| ingredient removed | outcome | needed? |
| --- | --- | --- |
| the parameter (`for v in s.values()` at the binding) | printed `a` | **yes** — a position with no `Set()` in sight |
| a return or a struct field instead of a parameter | the same `true` | no — any non-binding position |
| `.values()` replaced by `for v in t` | printed `a` | **yes** — `.values()` |
