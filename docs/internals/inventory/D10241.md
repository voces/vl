### D10241 — a generic's own `() => x` lambda beside a second lambda for one `() => T | null` callee calls through the wrong signature

**closed · runs, prints `1` `1` · was loads then traps, `wasm trap: indirect call type mismatch` inside `len`, clause 1 · closed in check_assignable.vl (`fvaAdaptEnclosing`: a lambda whose result is the enclosing generic's own type parameter is adapted to the callee's union result, so both lambdas share one instance's signature) and check_relate_core.vl (`bindFnRetUnionDefault` binds the open member to that enclosing parameter), check_calls.vl calling it before the call's pin constraints · fixture `generics/fn-result-widens-into-generic-nullable.vl` (`outer(5)` and `outer("s")`) · filed 2026-10-22 against master `57b3adb1e`**

Repro:

    function len<T>(f: () => T | null) {
      const t = f()
      if t == null { 0 } else { 1 }
    }
    function outer<T>(x: T) {
      print(len(() => 4))
      print(len(() => x))
    }
    outer(5)
    // vl check: rc 0.  vl run: prints 1, then wasm trap: indirect call type mismatch in len

Want:

    1
    1

#### Mechanism

Not traced. Inside the generic `outer`, `len(() => x)` binds `len`'s `T` to `outer`'s `T`,
and its instance is the one `len(() => 4)` already built, so the call through `f` reaches a
lambda of another signature. Called also as `outer("s")`, the module fails to validate inside
`len$1` instead.

#### Ablation
