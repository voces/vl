### D10241 — a generic's own `() => x` lambda beside a second lambda for one `() => T | null` callee calls through the wrong signature

**loads then traps · `vl check` rc 0 · `wasm trap: indirect call type mismatch` inside `len`, after the first line prints · clause 1 · present on master `57b3adb1e` · found closing [D10211](D10211.md) · filed 2026-10-22 against master `57b3adb1e`**

Repro:

    function len<T>(f: () => T | null) {
      const t = f()
      if t == null { 0 } else { 1 }
    }
    function outer<T>(x: T) {
      print(len(() => 4))
      print(len(() => x))
    }
    outer(5)
    // vl check: rc 0.  vl run: prints 1, then wasm trap: indirect call type mismatch in len

Want:

    1
    1

#### Mechanism

Not traced. Inside the generic `outer`, `len(() => x)` binds `len`'s `T` to `outer`'s `T`,
and its instance is the one `len(() => 4)` already built, so the call through `f` reaches a
lambda of another signature. Called also as `outer("s")`, the module fails to validate inside
`len$1` instead.

#### Ablation

| ingredient changed | outcome | needed? |
| --- | --- | --- |
| `outer` not generic, `x: string` | runs, `1` `1` | **yes** |
| the `len(() => 4)` line removed | loud emit reject, `value-union closure RESULT is not yet representable` | **yes** |

#### Grading list

The repro with `outer("s")` added (check-clean invalid wasm on master), and the same with
`len(() => null)` in place of `len(() => 4)`.
