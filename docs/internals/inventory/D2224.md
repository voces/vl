### D2224 — a generic instantiated over a nullable-string-list element loses its list type, with no empty literal in sight

**closed 2026-09-26 — the filed repro RUNS and prints `3` · was check-clean invalid wasm · clause 1 · closed by D2572's rung: the instance's returned local is annotated in the parser's spelling of `(string|null)[]` · found during PR #3069's review · filed against master `07d5e3b66` · fixture `tests/cases/generics/instance-expressions-typed-at-pin.vl`**

Repro:

    function g<T>(xs: T[]) { const r = xs; r }
    const src: (string | null)[] = ["a", null]
    const out = g(src)
    out.push("b")
    print(out.length)
    // vl check: rc 0 (one hint: the annotation on `src` is redundant).
    // vl run: Error: invalid module — "the emitted module failed to validate inside `g`:
    // type mismatch: expected (ref $type), found (ref $type)"

#### Mechanism

No empty `[]` literal appears anywhere. `g`'s own body rebinds its `T[]` parameter to a
local and returns it, and the instance is over `(string | null)[]`, the string-list rep
with a nullable niche. The failure is already present with no downstream use of `out` at
all — the instance's own body is invalid on emission, before the two calls that follow it
ever run. `function g<T>(xs: T[]) { xs }` (no rebind) still fails, but at a *different*
site — "the module's top-level code", "expected struct type at index 0, found (array (mut
i32))" — so the rebind changes which mechanism fires rather than curing either.
