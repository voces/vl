### D16235 — pushing a record holding a generic function onto a `T`-typed list in a generic body is checked at the first instance's `T`

**closed 2026-11-15 · runs, prints `3` `ab` · was loud check reject, `push: cannot add {f: (i32) => i32} to {f: (string) => string}[]` · clause 2 · found ablating [D16234](D16234.md) · filed 2026-11-15 against master `55151b054` · fixed by `fvaAdapt` building no adapter while a call's re-check of the generic body holds its stamps (`stampsHeld`, check_assignable.vl): the re-ask of the body's push demand at one call's bindings had rewritten the shared body's `id` into that instance's adapter · residue [D16571](D16571.md), [D16572](D16572.md) · fixture `generics/generic-body-push-record-of-generic-fn-two-instances.vl`, matrix `generic-body-push-record-of-generic-fn-per-instance.matrix.vl`**

Repro:

    function id<T>(x: T): T { return x }
    function run<T>(x: T) {
      const rs: {f: (x: T) => T}[] = []
      rs.push({ f: id })
      return rs
    }
    print(run(3)[0].f(3))
    print(run("ab")[0].f("ab"))
    // vl check: push: cannot add {f: (i32) => i32} to {f: (string) => string}[]

Want:

    3
    ab

#### Mechanism

The call `run(3)` re-asks the body's deferred push demand at its bindings (`callFtyPinCstrs` →
`validateBmCstrs` → `bmArgPred`). That is a loud `assignableExpr` on the body's own `{ f: id }`.
The delivery reached `fvaAdapt`, whose stable-name arm rewrote the field `id` in place into an
`(i32) => i32` adapter lambda. The `string` instance's re-check then typed that lambda, not `id`.
`validateBmCstrs` holds the stamps around the re-ask so that one call decides no build for a
shared node (D14721), but `fvaAdapt` did not read `stampsHeld`.
