### D3252 — a `??` whose right operand is a type parameter is never re-checked at the pin against the destination

**closed 2026-09-30 — now a loud check reject at the pin, the direct spelling's `cannot assign f64 | boolean to 'v' of type f64` · was check-clean silently wrong (`0.25`) · clause 1 · closed by recording, at each destination's deferred constraint (binding, assignment, return, argument, literal element), a `??` over a hole default as a derived hole (`HD_COALD`, `coalPinTy`) that the pin answers as the concrete `??` types it; the body's own type for the `??` is unchanged, so every instance master built still builds the same · the `string` face refuses the same way · fixtures `tests/cases/generics/error-coalesce-hole-default-at-pin.vl`, `tests/cases/generics/coalesce-hole-default-at-pin.vl` · the un-annotated and union destinations of the join are the residue below · found by the #3294 review (`rv3294-k7q2`) · filed 2026-09-29 against master `313a071b4`**

Repro:

    function gco<T>(x: T) {
      const o: f64 | null = null
      const v: f64 = o ?? x
      v / 4.0
    }
    print(gco(3 > 2))
    // PRINTS 0.25

Want:

    check reject: cannot assign

#### Mechanism

A prediction. The body checks `o ?? x` against `f64` while `x` is a hole, so the fit is vacuous,
and no deferred constraint is recorded for the `??` result the way one is for a bare `x` (the
`letCstr` table, which `ab1` below shows refusing at the pin). At `T = boolean` the `boolean`'s
i32 `1` is delivered into the `f64` slot and read as `1.0`. At `T = string` the same program is
check-clean invalid wasm (`expected i32, found (ref $type)` inside `gco`).

| `o` non-null (`2.0`), so the right operand is never read | prints `0.5`, correct | the read |
