### D1717 — comparing a litunion atom against a member inside an un-annotated parameter is check-clean INVALID WASM, where the same read through `print` is merely a wrong value

**closed 2026-09-06 with [D1545](D1545.md) — the same missing monomorphization rung, at the
reader that validates rather than the one that merely prints · filed 2026-09-06 against master
`a867d044b`, closed against `5530f6132` · 0 corpus cells**

Repro:

    const srcArr: ("red" | "green")[] = ["green", "red"]
    function take(a) {
      if a == "green" { print("EQ") } else { print("NE") }
    }
    take(srcArr[0])
    // vl check: rc 0.  vl run: rc 0, prints EQ

Was: `invalid module`, `type mismatch: expected (ref $type), found i32`. Swap the `==` for
`print(a)` and the same program was [D1545](D1545.md)'s wrong value — it printed `0`. One hole
parameter carried both classes, decided by which reader consumed the atom.

#### Mechanism

Measured, where the row filed it as predicted. `monoArgTyName` had no rung for an INLINE literal
union, so the argument fell to the ladder's `"i32"` catch-all; an `i32` pin gives a hole
parameter no annotation, so `exprIsLitAtom` had no channel and the raw atom reached the reader.
`print` emitted an i32 print of the id, which validates and is merely wrong; `==` emitted the
STRING compare core, which wants a `(ref $type)` and got the i32 — so the module failed
validation. `is` is a third reader in the same class and behaved like `==`; the row's own
27-cell grid did not carry it.

The close gives the argument the pin it always had a soften for: an inline set reps as `string`,
so the parameter takes the string ref and the caller widens the atom to its member text — the
lowering the ANNOTATED inline spelling already had, byte for byte.
